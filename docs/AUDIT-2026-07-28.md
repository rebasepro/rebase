## Findings

### 1 — HIGH — `@rebasepro/firebase` imports seven packages it never declares

**FIXED** — `e234b5951`

The package declares `firebase` as a peer dependency but every source file
imported the scoped subpackages: `@firebase/app`, `@firebase/auth`,
`@firebase/firestore`, `@firebase/storage`, `@firebase/functions`,
`@firebase/database`, `@firebase/app-check`. All seven appear only in
`devDependencies`.

Rollup externalises every bare specifier, so they survived into the published
build verbatim — verified against the built artefact, not inferred:

```
grep 'from"@firebase/' packages/firebase/dist/index.es.js   # 7 specifiers
```

Inside this monorepo, and for anyone installing with npm or yarn, they resolve
by accident: `firebase` depends on all seven, and a hoisted `node_modules` puts
them at the top level. Under pnpm's isolated layout — which this repo itself
uses — a consumer who installs `@rebasepro/firebase` and `firebase` as
documented gets `ERR_MODULE_NOT_FOUND` on first import.

Fixed by importing the umbrella entry points (`firebase/app`, `firebase/auth`,
…), which are the documented public API, re-export the same symbols, and are
covered by the peer dependency already declared. Confirmed by rebuilding: the
dist now imports only `firebase/*`, and every bare specifier left in the output
is a declared dependency or peer.

Leftover: the seven `@firebase/*` devDependencies are now unused. Removing them
touches the lockfile, so it was left for a normal install rather than done in a
worktree.

### 2 — HIGH — no gate could catch finding 1

**FIXED** — `76f3ad855`

An undeclared import passes typecheck, build, lint and every test, because all
of them resolve it through the monorepo's hoisted `node_modules`. Nothing in
the pipeline distinguishes "declared" from "reachable".

Added `scripts/check-undeclared-deps.mjs` (`pnpm check:deps`), wired into
`verify.yml`. It parses each publishable package's `src/` with the TypeScript
compiler rather than a regex — so prose in a comment and `", "` inside a SQL
string are not mistaken for specifiers — and ignores `import type`, which
leaves no runtime require behind.

Deliberate exceptions live in an allowlist that must state why the import
cannot fail. One entry: `@rebasepro/cli` resolves `typescript` with
`createRequire()` against the *user's* project root, wrapped in try/catch with
a documented JSON fallback. An allowance that stops matching is itself an
error — a stale one is a silent hole in the gate.

Verified both directions: green on `main`, and re-breaking a single import
reproduces the failure.

### 3 — MEDIUM — the docs drift verifier ran in no pipeline, and had drifted

**FIXED** — `5de928f18`

`scripts/verify-docs.mjs` existed and was wired to `pnpm verify:docs`, but
appeared in no workflow, and defaulted to exit 0 besides ("Drop `--strict` in
once the baseline is clean" — the baseline never got clean). Documented APIs
had drifted behind it:

- `useBuildNavigationStateController({ data: rebaseClient.data })` cannot
  compile. The admin takes Entity-shaped `RebaseData`; `rebaseClient.data` is
  the SDK's flat-row `TypedDataLayer`. The real wiring builds it with
  `buildRebaseData`.
- the same example passes `userManagement`, which is not a prop of
  `BuildNavigationStateProps` and never has been.
- entity actions documented `icon: "publish"` as a string. `icon` is a
  `ReactElement` and the renderer interpolates it directly (`{action.icon}`),
  so a string renders as the literal text "publish".

All three existed in all six locales; the code inside the fences was fixed in
every one. The prose sentence added to the English page was not hand-translated
— `website/scripts/translate_docs.mjs` owns that.

### 4 — MEDIUM — the docs verifier reported bogus errors on correct snippets

**FIXED** — `5de928f18`

Fixing finding 3 unmasked a bug in the verifier itself. `isStubbable()` resolves
a specifier from `packages/{app,server,admin}`, but tsc compiles the snippets
from a scratch directory under the workspace root, which cannot see a
package-local `node_modules`. Any package resolvable to Node and invisible to
tsc reported "Cannot find module" against a snippet that was correct, and the
fix each time had been another hand-written `paths` entry — `hono`, `zod`,
`react`, `react-dom`, `drizzle-orm`, `@hono/node-server` had all accumulated
that way.

The resolver now records where Node found each package and hands tsc the same
answer. Explicit entries still win, because a few need a different target than
Node picks: React resolves to a runtime package that ships no declarations, so
it has to be mapped to `@types/react`.

Keyed on the package name, never the full specifier — mapping
`drizzle-orm/pg-core` to the package root is an *exact* `paths` key, and it
beats the `drizzle-orm/*` wildcard, silently resolving every subpath import to
the root barrel. (Found the hard way: it broke five snippets that had been
passing.)

The baseline is clean, so the gate now runs `--strict` and can fail. Verified
in both directions.

### 5 — MEDIUM — the same rule was reported twice, 2739 times

**FIXED** — `ad8736567`

`no-unused-vars` and `@typescript-eslint/no-unused-vars` were both enabled, over
the same files, with the same options. typescript-eslint's own guidance is to
turn the base rule off, because it cannot see a type position:

```ts
((value: string) => string)                       // a function *type*
declare function gtag(...args: unknown[]): void;  // an ambient signature
```

Neither `value` nor `args` is a binding; both were reported as unused variables.

Every one of the 843 findings the TypeScript-aware rule reported was duplicated
by the base rule, which then added 1896 more of that kind — all false, all in
`.ts`/`.tsx`. Turning it off for TypeScript loses no signal: the count of real
findings is unchanged at 843.

9206 warnings → 6463. Also removed four `eslint-disable-next-line` directives
ESLint reports as unused; a directive is only unused when its rule reports
nothing at that line, so none were load-bearing.

The remaining bulk is `object-property-newline` (4233). The 179
`react-hooks/exhaustive-deps` warnings are the ones most likely to be real bugs
and are now findable — **left open**, see below.

### 6 — MEDIUM — the lint gate exempted the repo's own tooling

**FIXED** — `00e0b7c28`

`scripts/**` was in the ESLint ignore list — 35 files, including every quality
gate the repo runs on itself. It arrived in a "fix: stability fixes" commit with
no rationale, bundled with unrelated work; the ESLint CI step was added later
precisely so a lint error could not sit on main indefinitely. One had: three
`no-fallthrough` errors in the agent harness, the same severity as the
`rls-check` error that was fixed for blocking the gate.

The harness cases each end in `process.exit()`, so nothing falls through at
runtime — invisible to ESLint, and to a reader. Made terminal intent explicit.

Widened the main config glob to `mts`/`cts` as well:
`pluginReact.configs.flat.recommended` is unscoped and matches every file, while
`settings.react.version` lives in the globbed block, so a file outside it got
the plugin without its settings and eslint-plugin-react warned on every run.
`scripts/verify-selfhost.mts` was that file, and it only became visible once
scripts were linted at all.

### 7 — MEDIUM — e2e Postgres containers leaked on any interrupted run

**FIXED** — `b74ad0db9`

Teardown lived only in `afterAll`, which does not run when the runner is killed
— Ctrl-C, a cancelled CI job, an OOM. The containers are detached, so they
outlive the process and keep their port and memory. Found while auditing: two
`rebase-test-postgres-*` containers still up ten hours after the run that made
them.

Both copies of `pg-setup.ts` (`packages/cli` and `packages/server-postgres`,
which have drifted apart but shared this bug) now track what they started and
force-remove it from `exit`, SIGINT, SIGTERM and SIGHUP. `--rm` is added too,
but only covers postgres exiting on its own — a killed *runner* leaves the
container up and healthy, which is the case that actually leaked.

Verified by starting a container through the real helper and killing the process
with SIGTERM before teardown could run: previously it survived, now it is gone.

### 8 — LOW — `WhereFilterOp` is duplicated and nothing pinned it

**FIXED** — `8bd1169cc`

The operator union is declared twice on purpose — `@rebasepro/ui` is a
standalone component library with no dependency on `@rebasepro/types`. The two
were in sync, but nothing enforced it, and the drift would be close to
invisible: VirtualTable takes the UI copy, callers pass the types copy, and
structural typing keeps everything compiling until a filter reaches the table
carrying an operator the table's own union does not list.

Added a test comparing membership (not declaration order), which also asserts
each union parsed non-empty — two emptied unions compare equal, which is exactly
the shape a guard fails silently in.

### 9 — LOW — four compiler logs were committed, and the ignore rule missed them

**FIXED** — `67b369dac`

`.gitignore` had a section headed "Accidentally committed build output" listing
`build_output.txt` and `tsc_output.txt` — and named `tsc_output.txt` a second
time, 66 lines earlier. Four such files were tracked anyway (651 lines total).
Two reasons: a `.gitignore` entry has no effect on an already-tracked path, and
the rule matched exact names, so `_2` and `_full` were never covered.

### 9 admin test suites "failing"

A measurement error of mine, recorded so nobody re-derives it: running every
package's jest with `NODE_OPTIONS="--experimental-vm-modules"` makes

matching CI exactly.

Worth knowing anyway: **the headline count lies when a suite fails to load.**
Jest printed "302 passed" with 9 suites dead — the 72 missing tests are only
visible in the suite count, not the test count.

`e2e/tests/*.spec.ts` holds tests across 5 files (`collections`, `e2e`,

red or flaky. It wants a human to run it once locally and confirm.

#### Amendment — 2026-07-31

Two corrections and a resolution.

**The count was wrong.** It is 10 tests, not 21 — `playwright test --list`
reports "Total: 10 tests in 5 files". The 21 came from counting `test(`
occurrences textually, which also catches helper calls. Recorded because the
number was used to argue the suite's value.

**The caution was right, for a reason nobody had named.** The suite was not
flaky. It could not run in CI at all, and would have failed on the first
unattended run — but from the *database*, not from timing. CI's database is
always empty, so `/auth/config` reports `needsSetup` and `LoginView` renders its
bootstrap ("create the first admin") form directly. There is no "Sign in with
email" button on that screen, which is the only thing `globalSetup` knew how to
click. It waited 30s, retried three times, and threw — in `globalSetup`, which
fails all ten tests at once and reads as "the e2e is broken".

The suite passed locally only because a developer's database already has the
demo user in it. That is the exact shape of a gate that reports success on the
one starting state that cannot contain the bug.

**Resolved.** `signIn()` in `e2e/global-setup.ts` now branches on whichever
screen is up, so the same run covers first-run bootstrap *and* ordinary
sign-in. Bootstrap had no automated coverage at any tier before this, despite
being the first thing every new user of Rebase does.

Verified before wiring in — four runs, all green, 30–34s each:

| Run | Database | Mode | Result |
| --- | --- | --- | --- |
| 1 | populated | reuse server | 10 passed (31.7s) |
| 2 | populated | `CI=true`, cold boot | 10 passed (30.3s) |
| 3 | **fresh** (`db push` + seed) | `CI=true`, cold boot | 10 passed (33.4s) |
| 4 | populated, after the fix | `CI=true`, cold boot | 10 passed (32.7s) |

Run 3 is the one that matters: it is CI's starting state, and it is the run that
failed before the fix. Runs 2 and 4 are the regression pair — the branch a
developer's machine takes still works.

Now `verify.yml` → `e2e` → **Admin panel E2E (Playwright)**, which creates its
own database, pushes the schema and seeds it. `db push` being in the step is
deliberate: it is what a developer runs, so a break in it fails here rather than
in somebody's first ten minutes.
