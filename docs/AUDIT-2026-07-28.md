## Findings

### 1 — HIGH — `@rebasepro/firebase` imports seven packages it never declares

**FIXED** — `e234b5951`

The package declares `firebase` as a peer dependency but every source file
imported the scoped subpackages: `@firebase/app`, `@firebase/auth`,
`@firebase/firestore`, `@firebase/storage`, `@firebase/functions`,
`@firebase/database`, `@firebase/app-check`. All seven appear only in
`devDependencies`.

Rollup externalises every bare specifier, so they survived into the published
build verbatim — verified against the built artefact, not inferred:

```
grep 'from"@firebase/' packages/firebase/dist/index.es.js   # 7 specifiers
```

Inside this monorepo, and for anyone installing with npm or yarn, they resolve
by accident: `firebase` depends on all seven, and a hoisted `node_modules` puts
them at the top level. Under pnpm's isolated layout — which this repo itself
uses — a consumer who installs `@rebasepro/firebase` and `firebase` as
documented gets `ERR_MODULE_NOT_FOUND` on first import.

Fixed by importing the umbrella entry points (`firebase/app`, `firebase/auth`,
…), which are the documented public API, re-export the same symbols, and are
covered by the peer dependency already declared. Confirmed by rebuilding: the
dist now imports only `firebase/*`, and every bare specifier left in the output
is a declared dependency or peer.

Leftover: the seven `@firebase/*` devDependencies are now unused. Removing them
touches the lockfile, so it was left for a normal install rather than done in a
worktree.

### 2 — HIGH — no gate could catch finding 1

**FIXED** — `76f3ad855`

An undeclared import passes typecheck, build, lint and every test, because all
of them resolve it through the monorepo's hoisted `node_modules`. Nothing in
the pipeline distinguishes "declared" from "reachable".

Added `scripts/check-undeclared-deps.mjs` (`pnpm check:deps`), wired into
`verify.yml`. It parses each publishable package's `src/` with the TypeScript
compiler rather than a regex — so prose in a comment and `", "` inside a SQL
string are not mistaken for specifiers — and ignores `import type`, which
leaves no runtime require behind.

Deliberate exceptions live in an allowlist that must state why the import
cannot fail. One entry: `@rebasepro/cli` resolves `typescript` with
`createRequire()` against the *user's* project root, wrapped in try/catch with
a documented JSON fallback. An allowance that stops matching is itself an
error — a stale one is a silent hole in the gate.

Verified both directions: green on `main`, and re-breaking a single import
reproduces the failure.

### 3 — MEDIUM — the docs drift verifier ran in no pipeline, and had drifted

**FIXED** — `5de928f18`

`scripts/verify-docs.mjs` existed and was wired to `pnpm verify:docs`, but
appeared in no workflow, and defaulted to exit 0 besides ("Drop `--strict` in
once the baseline is clean" — the baseline never got clean). Documented APIs
had drifted behind it:

- `useBuildNavigationStateController({ data: rebaseClient.data })` cannot
  compile. The admin takes Entity-shaped `RebaseData`; `rebaseClient.data` is
  the SDK's flat-row `TypedDataLayer`. The real wiring builds it with
  `buildRebaseData`.
- the same example passes `userManagement`, which is not a prop of
  `BuildNavigationStateProps` and never has been.
- entity actions documented `icon: "publish"` as a string. `icon` is a
  `ReactElement` and the renderer interpolates it directly (`{action.icon}`),
  so a string renders as the literal text "publish".

All three existed in all six locales; the code inside the fences was fixed in
every one. The prose sentence added to the English page was not hand-translated
— `website/scripts/translate_docs.mjs` owns that.

### 4 — MEDIUM — the docs verifier reported bogus errors on correct snippets

**FIXED** — `5de928f18`

Fixing finding 3 unmasked a bug in the verifier itself. `isStubbable()` resolves
a specifier from `packages/{app,server,admin}`, but tsc compiles the snippets
from a scratch directory under the workspace root, which cannot see a
package-local `node_modules`. Any package resolvable to Node and invisible to
tsc reported "Cannot find module" against a snippet that was correct, and the
fix each time had been another hand-written `paths` entry — `hono`, `zod`,
`react`, `react-dom`, `drizzle-orm`, `@hono/node-server` had all accumulated
that way.

The resolver now records where Node found each package and hands tsc the same
answer. Explicit entries still win, because a few need a different target than
Node picks: React resolves to a runtime package that ships no declarations, so
it has to be mapped to `@types/react`.

Keyed on the package name, never the full specifier — mapping
`drizzle-orm/pg-core` to the package root is an *exact* `paths` key, and it
beats the `drizzle-orm/*` wildcard, silently resolving every subpath import to
the root barrel. (Found the hard way: it broke five snippets that had been
passing.)

The baseline is clean, so the gate now runs `--strict` and can fail. Verified
in both directions.
