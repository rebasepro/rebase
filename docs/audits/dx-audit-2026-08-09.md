# DX audit — 2026-08-09

A hands-on pass over every developer-facing surface of Rebase: the CLI, the
scaffold, the running server, the REST contract, the generated SDK, the admin
panel, the docs, the self-host path, the cloud CLI, and the repo itself as a
place to contribute.

**Method.** Scaffolded two fresh projects with the *published* `@rebasepro/cli@0.13.0`
(`rebase init`, no `--install`), installed, ran them against real Postgres
containers, registered a user, drove the API with `curl`, drove the admin panel
in a browser, generated the typed SDK and typechecked real usage of it, ejected a
copy and built it, introduced deliberate schema drift, and read the docs against
the code. Where a finding could be an artifact of tooling, it was re-checked
against the DOM or the source. Everything below was reproduced, not inferred.

Successor to [dx-audit-2026-07-25.md](dx-audit-2026-07-25.md). Items that audit
left open are marked **[still open]** or **[fixed]**.

---

## Verdict

The craft is real and it is concentrated in the places that are hardest to fake:
error messages, generated comments, the type system, and the docs pipeline. The
happy path — `rebase init` → admin panel with data in it — works, and works from
a cold machine with three other Postgres instances already running.

Two things are broken badly enough to block a real user:

1. **The documented self-host path cannot run.** The runtime image the scaffolded
   `docker-compose.yml` pulls does not exist on any public registry.
2. **The `where` contract silently lies.** A typo'd operator is not rejected — it
   is reinterpreted into a different query that returns wrong rows with a 200.

Below those, the recurring theme is **the seam between a well-built thing and its
consumer**: a UI kit that supports accessible labels wired up by callers that
don't pass them; a codegen that emits correct names in a version nobody has
installed yet; agent instructions that teach an API the type system deleted; a
lazy-loaded 940 KB dependency that the bundler puts back in the entry chunk.

## What is genuinely good

**First run.** `rebase init dxtest --yes` → `pnpm install` (23.8 s) → `docker compose
up -d db` → `pnpm run db:push` → `pnpm run dev` → a working admin panel with
auth, RLS, CDC and Swagger. No manual step, no editing, no surprise.

**Port probing works, including the case that used to break it.** The host had
Postgres on 5432 (loopback-only) and containers on 5433/5434. The first scaffold
took 5435, the second took 5436. The `.env`, the compose mapping and the running
server all agreed. `rebase dev` derived backend port 3372 and Vite fell forward
from 5173 to 5174 without either process getting confused.

**The "not in a project" error is a model of the form.** Same text from `dev`,
`doctor`, `db push` and `generate-sdk`:

```
✗ Could not find a Rebase project root.
  Looked in this directory and every parent for a rebase.json,
  a package.json with a "backend" workspace, or a backend/ next to a config/.
  Run this from inside a project, or create one with `rebase init`.
```

It says what it looked for, where, and the two ways out.

**Generated files explain *why*, not just what.** The scaffold's `.env` and
`docker-compose.yml` are the best artifacts in the product. The `.env` explains
why `sslmode=disable` is there, why `VITE_API_URL` must stay empty, why the
storage separator is a double underscore, and why `rebase dev` ignores `PORT`.
The compose file explains why the healthcheck exists, why `CORS_ORIGINS` is
required rather than guessed, and why collection tables are not created on
container restart. These read like a senior engineer left notes for the next
person.

**Docs verification is clean and blocking.** [still open → **fixed**] `pnpm
verify:docs` reports **zero** findings across 2 491 code fences in 516 files, 931
typechecked snippets, marketing snippets, skill/example shell commands and MCP
manifests — and `verify:docs:strict` runs in `verify.yml`. The 182-finding
backlog from July is gone. Translation coverage is complete: of 65 English prose
docs, all 65 exist in de/es/fr/it/pt; the only gap is `CHANGELOG.md`, correctly.
This is unusually good for a project this size.

**Query *field* errors are excellent.**

```json
{"error":{"message":"Unknown filter field 'nope' on collection 'posts'. Valid fields: author_id, content, id, status, title",
 "code":"UNKNOWN_FILTER_FIELD","details":{"validFields":[...]},"requestId":"7acf8525-…"}}
```

Message, machine code, the valid set, and a request id. Same for `orderBy`.

**Runtime errors are translated into actions.** `api/errors.ts` maps a Postgres
`42703` to *"Schema drift: column "x" does not exist. Run `pnpm db:push` to sync
your schema."* and a permission denial to *"…(row-level security). Check the RLS
policies for this table."* The DB `message`/`detail`/`hint` are attached outside
production only, deliberately and with the reason in a comment.

**`rebase doctor`.** Correct on a clean project, correct on drift, and it names
the table, the column and the exact fix:

```
┌─ ✗ Missing Column ────────────────────────────
│ Table: posts │ Column: subtitle
│ Column "subtitle" is defined in collection "posts" but missing from table "posts".
│ Fix: Run `rebase db push` or `rebase db generate && rebase db migrate`
└────────────────────────────────────────────────
```

Exit code 1 on drift, 0 when clean — usable in CI.

**`rebase eject`.** `--dry-run` lists the six files it would touch and changes
nothing. The real run explains what you have just taken on ("You now own CORS,
auth wiring, storage and shutdown"), leaves `docker-compose.yml` intact, and the
ejected backend **builds clean** (`rebase schema generate && tsc`, exit 0). The
generated `Dockerfile` even documents which lines to change if you are on npm
rather than pnpm, and says the `COPY`s fail first.

**`rebase skills install`.** 20 skills installed to `.claude/skills`, correctly
refuses to guess without a TTY, and tells you exactly how to script it.

**`rebase telemetry`.** Off by default, records the date you declined, prints the
endpoint, the config path, and `rebase telemetry show` for the exact payload.
This is how consent should look.

**The relation type system.** `packages/types/src/types/relations.ts` is a closed
discriminated union (`belongsTo | hasOne | hasMany | manyToMany | via`) with the
authored form and the resolved form deliberately separated, and roughly 40 lines
explaining which bugs the old open-interface design produced. `ResolvedHasMany.sourceKey`
carries a comment explaining why it is the one field that stays optional.

**Small mercies that turn out to matter.** The scaffold's `.npmrc` sets
`verify-deps-before-run`, so a user who follows the README literally — which
omits `pnpm install` — gets an automatic install instead of a crash. All 22
`@rebasepro/*` packages are published at a consistent 0.13.0.

## Findings

### P0 — blocks a real user

#### 1. The self-host runtime image does not exist

`rebase init` writes a `docker-compose.yml` whose header describes it as *the*
self-hosting story — "the artifact you self-host is the artifact Rebase Cloud
runs" — and whose `api` service is:

```yaml
image: rebasepro/server:${REBASE_VERSION:-latest}
```

It is not pullable:

```
$ docker manifest inspect rebasepro/server:0.13.0
denied: requested access to the resource is denied
$ curl -s https://hub.docker.com/v2/repositories/rebasepro/server/tags
{"message":"object not found"}
$ curl -o /dev/null -w '%{http_code}' https://ghcr.io/v2/rebasepro/server/tags/list
401
```

So `docker compose up` — step 4 of the instructions written into the file — fails
on an image pull for every user. `rebase eject` is currently the only self-host
path that works, because its `Dockerfile` builds from `node`. That Dockerfile's
own comment asserts the managed compose file "is still here and still works",
which is not true today.

This also matches the open memory note that `rebasepro/server` is on no public
registry at any tag; the scaffold has been shipping a reference to it since.

**Fix:** publish the runtime image, or have `rebase init` write the ejected-style
compose file until it is published. Add a CI check that every image referenced by
a scaffolded template resolves anonymously.

#### 2. An unknown `where` operator is silently reinterpreted

`packages/common/src/data/filter-dialect.ts:388` accepts a `[op, value]` tuple
only when `toCanonicalOp(op) === op`. Anything else falls through to line 410,
`result[field] = ["in", raw]` — so the operator string itself becomes a *value*
in a membership test. Observed against a live server, one row `{id:1, title:"Hello"}`:

| Request | Status | Result | Should be |
| --- | --- | --- | --- |
| `where={"title":["~~","Nope"]}` | 200 | 0 rows | 400 |
| `where={"title":["!!","Hello"]}` | 200 | **1 row — a false match** | 400 |
| `where={"title":["contains","Hell"]}` | 200 | 0 rows | 400 |
| `where={"id":[">>",0]}` | **500** | `INTERNAL_ERROR`, `dbMessage: invalid input syntax for type integer: ">>"` | 400 |

Three distinct failure modes from one root cause: a wrong-but-plausible answer, a
*false positive*, and a 500 with a raw Postgres error where a 400 belongs. The
last two are the serious ones — `["!!","Hello"]` becomes `title IN ('!!','Hello')`,
which matches, so a filter the caller believed was applied returns rows it should
have excluded.

The contrast is what makes this a defect rather than a gap: an unknown *field*
gets a 400 with the valid set listed, and `orderBy` was already hardened to 400
on a bad direction (with a comment explaining why). Operators were left behind.
`contains` is exactly the kind of name a developer guesses first.

**Fix:** reject an unrecognised operator in a 2-tuple with a 400 naming the
supported set, the way `UNKNOWN_FILTER_FIELD` does. The `["in", raw]` fallback
should only apply to values that were never operator-shaped.

### P1 — wrong or misleading, high blast radius

#### 3. The published typed SDK is wrong in three ways (fixed on main, unreleased)

`rebase generate-sdk` is the headline typed-client feature. Run from the
**published** 0.13.0 (what `pnpm dlx @rebasepro/cli init` installs), against the
default blog template:

```ts
posts: { Row: { id?: number; content?: string; authorId?: number; … } }
```

Against the same collections with the CLI built from `main`:

```ts
posts: { Row: { id: number; content?: string | null; author_id?: number | null; … } }
```

Three defects in the shipped version:

- **`authorId` does not exist.** The wire returns `author_id` — verified:
  `{"id":1,"title":"Hello","content":"world","status":"draft","author_id":null}`.
  `row.authorId` compiles and is `undefined` forever. It is also the key `where`
  and `orderBy` are typed off, so the type hides the column that does work.
- **`| null` is missing.** Nullable columns arrive as `null`, are typed
  `string | undefined`. `if (row.content !== undefined) row.content.trim()`
  typechecks and throws.
- **`id` is optional.** `const id: number = row.id` fails with TS2322 — on a
  `isId: "increment"` primary key that is present on every read.

`packages/codegen/src/generate-types.ts` on main is correct *and* its comments
describe exactly these bugs ("Reshaping it into `authorId` described a column
that does not exist and hid the one that does"). So this is purely a release-lag
finding — 0.13.0 shipped 2026-08-04, the fix landed 2026-08-08 — but until it
ships, the flagship DX feature is broken for everyone who installs it.

Related consistency problem that is *not* fixed by that release: the API uses two
naming conventions at once. `GET /api/data/users` returns `displayName`,
`photoURL`, `createdAt`; `GET /api/data/posts` returns `author_id`. Both are
"the wire names", but a developer moving between two collections has to know
which convention each one landed on.

**Fix:** cut 0.13.1. Separately, decide whether the wire is snake_case or
camelCase and make derived FK column names follow the same rule as declared
property keys.

#### 4. The admin panel eagerly loads ~6.2 MB of JS, including a 940 KB spreadsheet library

`packages/cms/src/components/CollectionViewBinding/CollectionViewActions.tsx:11`
says `// Lazy-load import/export — pulls in exceljs only on demand`. The built
entry chunk disagrees:

```js
// frontend/dist/assets/index-BMAjUoI7.js
import{c as $s,E as zx}from"./vendor-exceljs--yQhf7jV.js"
import{l as qx,f as Bx}from"./vendor-datefns-CF_SVQHF.js"
```

A **static** import, so `index.html` `modulepreload`s it. The eagerly-preloaded
set includes `vendor-exceljs` (940 KB), `vendor-lucide-react` (822 KB),
`vendor-datefns` (641 KB) and the 1.43 MB entry — ~6.2 MB of JS, ~1.5 MB gzipped,
before the login form is interactive. lucide-react and date-fns at those sizes
mean neither is being tree-shaken.

The build also emits Vite's own "chunks are larger than 500 kB" warning, which
has evidently been living there.

**Fix:** find what re-statics `data_import` into the entry graph (`file_to_json.ts`
has a value import of `exceljs`), switch lucide to per-icon imports, and check
the date-fns import style. Then add a size budget to CI so it cannot silently
regress.

#### 5. Roughly half the form fields have no accessible name

The UI kit does this correctly: `packages/ui/src/components/TextField.tsx` takes
a `label` prop and wires `aria-labelledby` to it. Consumers frequently bypass it
and render a visual label beside the field instead:

```tsx
<Typography variant="label" color="secondary">Email</Typography>
<TextField placeholder="you@example.com" … />   // no label, no aria-label
```

`LoginView.tsx:1039–1051`.

> **Two corrections to this finding, both found by fixing it.**
>
> **1. `Typography variant="label"` is not a span — it renders a real `<label>`**
> (`packages/ui/src/components/Typography.tsx:29` maps the variant to the `label`
> element, and it forwards `htmlFor`). The symptom I observed was right; the mechanism
> I gave was wrong. It matters, because it makes the cheap fix a real `label[for]`/`id`
> pairing rather than an `aria-label` — and clicking the label then focuses the field,
> which `aria-label` never gives you.
>
> **2. "43 of 87 pass a `label`" was a grep artifact.** My count used an 8-line
> lookahead from each `<TextField`; widening it walks the number up — 43 at 8 lines,
> 48 at 15, 53 at 25 — against a true figure of **54**. So **33 sites needed fixing,
> not ~44.** A multi-line JSX call whose `label=` sits further down was silently
> counted as unlabelled. Same class of mistake as the zsh probe in #14: the tool,
> not the target.

Counted correctly across `packages/{app,admin,studio}/src`: **87 `<TextField>` call
sites, 54 pass a `label`, 0 pass an `aria-label`.**

**The two real defects were underneath the call sites, and neither was reachable by
editing them:**

- **Every entity-form field was nameless**, regardless of call site. The form sets
  `hideLabel: !selfLabelling`, so the control's own label is suppressed, and
  `FieldBlock` draws the visible label in a `<span>` pointing at nothing. Nine of nine
  fields on a demo form read back their own values as their names.
- **`DateTimeField` was unnamed even when visibly labelled** — an `InputLabel` with no
  `htmlFor` next to an `<input>` with no `id`.
- **`TextField` silently erased a caller-supplied `aria-labelledby`**, applying its own
  `aria-labelledby={label ? labelId : undefined}` *after* the prop spread. The one
  standard escape hatch did nothing.

Observed consequences, confirmed against the DOM rather than only the a11y tree:

- Login screen: the email field's accessible name is `"you@example.com"`, the
  password field's is `"••••••••"`. [still open from 2026-07-25]
- Entity form: the Title input is `<input id="_r_13_">` with no `label[for]`, no
  `aria-label` and no wrapping `<label>` — its accessible name is its *value*.
- The collapsed nav rail (viewport ≤ ~1280px) renders `/c/posts`, `/c/authors`,
  `/c/tags`, `/schema`, `/c/users` as icon-only links with no accessible name.
  Expanded (1440px) they carry visible text and are fine.
- The logo link to `/` has no accessible name at any width.

The README markets "Premium UI — Fast, **accessible** design system". The
capability is there; the wiring isn't.

**Fix:** pass `label` at the ~44 bare call sites, `aria-label` on the icon-only
rail links and logo, and add an axe check to the existing Playwright e2e run so
the count can only go down.

#### 6. The repo's own agent instructions teach an API that no longer exists

`AGENT.md:20`:

> Relations are defined **inline on the property** using `type: "relation"` with
> `target`, `cardinality`, and `direction` fields directly on the property definition.

`direction` does not exist anywhere in `packages/types`. The authored shape is
`relation: { kind: "belongsTo" | …, target, relationName }`. `.agent/workflows/schema-migration.md:143–172`
is worse — it carries a full worked example built on `cardinality: "one"` +
`direction: "owning"`, and prose explaining what "owning relations with
cardinality many" do. `AGENT.md:19` also names `PostgresCollectionConfig` as the
authoring type, where the templates and all 145 doc examples now use
`defineCollection`.

Any agent that reads these writes code that does not compile — against a product
whose README says "agent-native".

Root cause: `verify:docs` covers `website/`, `tooling/rebase-agent-skills/` and
`examples/`, but **not** `AGENT.md`, `.agents/AGENTS.md` or `.agent/workflows/`.
That is why this drifted while everything it checks stayed clean. There are six
agent-instruction surfaces at the repo root (`AGENT.md`, `.agents/AGENTS.md`,
`.agent/workflows/` ×5, `.claude/`, `.aiexclude`, `tooling/rebase-agent-skills/`) and
only the last is verified.

**Fix:** point `verify:docs` stage 1 at the root agent files too, then fix what it
finds. Consider collapsing the duplicated instruction files into one canonical
file with pointers, the way the *scaffold* already does (`CLAUDE.md`,
`AGENTS.md`, `.cursorrules`, `.windsurfrules` are all 2-line pointers to
`ai-instructions.md` — that part is done well).

### P2 — friction, noise, inconsistency

#### 8. First boot emits 56 `INFO` lines, almost none actionable

`rebase dev` on a fresh scaffold: 56 `INFO`, 1 `WARN`. The signal — the backend
URL — is line 52. The rest is internal wiring (`Native storage attached to
singleton`, `Contract routes mounted`, `SQL capability attached to singleton`).
One `INFO` line is a 90-word paragraph explaining `access: "public"` semantics —
good content, but it is documentation printed on every boot. The prior audit
counted ~40; it has grown. [still open]

#### 9. Human CLI output goes through the structured logger

`rebase doctor` renders a box-drawn report in which every line, including the
banner and the red error boxes, is prefixed `ℹ️ [INFO]`:

```
ℹ️ [INFO]   🩺 Rebase Schema Doctor
ℹ️ [INFO]   ┌─ ✗ Missing Column ────────────────────────────
```

Same for `rebase db push` and `rebase schema generate`. The content is excellent
and the presentation actively undercuts it. [still open]

#### 10. A third-party promo prints on every CLI run and every production boot

```
◇ injected env (13) from .env // tip: ◈ encrypted .env [www.dotenvx.com]
◇ injected env (14) from ../.env // tip: ⌘ custom filepath { path: '/custom/path/.env' }
```

`dotenvx` advertising itself in `rebase dev`, `rebase build` and `rebase start` —
i.e. in production server logs. [still open]

#### 11. Every boot warns about a condition `rebase init` created

```
⚠️ The database connection runs as a superuser ("rebase_app"). … connect as a
non-superuser table-owner role in production …
```

The scaffold's own `docker-compose.yml` sets `POSTGRES_USER: rebase_app`, which
makes it the superuser. So the only `WARN` a new user ever sees is about a
decision the tool made for them, with no scaffolded way to fix it. Either
provision a table-owner role in the scaffold, or suppress the warning when the
connection is the scaffolded local one.

#### 12. `/health` is not under `/api`

`GET /health` → 200. `GET /api/health` → 404. Every other route is `/api/*`.
Matters for reverse proxies and for the folded single-origin deploy. [still open]

#### 13. A missing collection breaks the JSON error envelope

```
$ curl -H "$AUTH" localhost:3372/api/data/nonexistent
404 Not Found          # plain text, not JSON
```

Every other error is `{"error":{"message","code","requestId"}}`. A client that
does `res.json()` on the error path gets a parse failure instead of a code. Also
note that *unauthenticated*, the same URL returns 401 rather than 404 — defensible
as anti-enumeration, but it means a developer who typos a collection name while
their token is expired is told the wrong thing.

#### 14. `rebase cloud` prints an internal warning on every invocation

```
$ rebase cloud whoami
[Rebase] Realtime is enabled but no WebSocket URL could be derived from baseUrl
"https://app.rebase.pro" — … Pass an absolute `baseUrl`, set `websocketUrl`
explicitly, or pass `realtime: false` to say this was intended. …
```

The CLI is telling the user to fix the CLI's own client construction. It should
pass `realtime: false`.

One more real problem in the same surface: off-TTY, `cloud deploy` emits JSON while
`cloud whoami` and `cloud projects list` emit human-formatted text, so a script
cannot rely on either. (It turned out to be worse than this: roughly half the family
— `whoami`, `projects`, `orgs`, `link`, `metrics`, `webhooks`, `storage`, `clusters`,
`billing`, `db list|create|test` — never checked JSON mode at all, printing prose on
success and a JSON envelope only on failure.)

> **Retracted.** This finding originally claimed a third problem: that human output was
> split across both streams, "the `🔐 Rebase Cloud session` header appears on both". That
> was **an artifact of my own probe, not a defect.** I ran
> `rebase cloud whoami 2>&1 >/dev/null` in **zsh**, where `MULTIOS` is on by default and
> that redirection tees stdout to the pipe as well as to `/dev/null`:
>
> ```
> zsh   ./twostream.sh 2>&1 >/dev/null | cat  →  THIS-IS-STDOUT / THIS-IS-STDERR
> bash  (same)                                →  THIS-IS-STDERR
> zsh   setopt no_multios; (same)             →  THIS-IS-STDERR
> ```
>
> There is exactly one `console.log` of that header, in `auth.ts`, and no second sink.
> The header was only ever on stdout; the *warning* above was on stderr, so `2>&1`
> interleaved two unrelated voices. **Lesson for this repo's audits: verify stream-
> separation claims in `bash -c`, or with `setopt no_multios`, before believing them.**

#### 15. The root README names ports that will almost never be right

> Your admin panel is running at `http://localhost:5173` and the API at
> `http://localhost:3001`.

Observed: 5174 and 3372. The July audit corrected this in all six quickstart

✅ Collections → SDK Types: In sync

Two adjacent lines saying the SDK is synchronised and that it does not exist.

#### 17. Empty relation pickers look like stuck skeletons

In the entity form, `Author` and `Tags` with zero target rows render as a grey

#### 18. Repo hygiene contradicts the repo's own rule

`AGENT.md` says: *"**NEVER** create one-off scripts, codemods, or utility files in
the repo root … put it in `/scripts/`"*. Tracked at the root of the public repo:

`rebase_cto_technical_handbook.md` and `.html` (an internal document), and
`videos/`. A first-time contributor reading `ls` has to work out which of these
is the project.

**Mostly fixed 2026-08-09.** `convert_md.js` and `eslint.saas.tmp.mjs` were already
gone; `rebase_cto_technical_handbook.md`, its generated `.html`, and the
`tooling/scripts/convert-handbook.js` that rendered one from the other are now deleted.
`videos/` (a Remotion project, 127 MB) is still tracked at the root.

#### 19. `examples/` does not cover the flagship path

**Corrected 2026-08-09, after checking.** The first draft of this finding implied the
examples might be unmaintained. They are not. `examples/*` is a declared member in
`pnpm-workspace.yaml:9`, `check:examples` (`pnpm --filter "./examples/*" -r run typecheck`)
is gated in `.github/workflows/verify.yml:245`, and **both typecheck clean today** — I ran
it. What remains is a coverage gap, not rot. One undeclared oddity: `examples/firebase`
pins `typescript: ^6.0.3` / `vite: ^8.1.5` while the scaffold pins `^5.9.2` / `^6.4.3`.

Two examples: `examples/firebase` (the legacy package) and `examples/sdk-demo`.
Both depend on `workspace:*`, so neither runs standalone for someone who copies
the directory. Nothing demonstrates the Postgres BaaS or CMS flow the README
leads with. [audit-map #86, never audited — this is a first look, not a full pass]
