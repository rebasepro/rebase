# Unit 13 — Upgrading an existing deployment

Read-only audit of the upgrade / version-skew subsystem on `main` at
`c678e1745`. Scope: `packages/server/src/boot/version-skew.ts`,
`packages/server-postgres/src/auth/schema-version.ts`,
`tooling/scripts/record-schema-snapshot.mts` and the two snapshot corpora, the
upgrade e2e harnesses, the FK-rename auto-migration, and Drizzle journal
handling.

Nothing was executed against a database. Every claim below is from reading
source and fixtures; scenarios I could not observe running are marked
**UNCONFIRMED**.

## Verdict

The *machinery* is in better shape than the *corpus*. Every mechanism this unit
needs exists and is well reasoned: an auth schema stamp that refuses a
backwards boot, a health probe that 503s on a shape the runtime cannot write,
a driver-skew corpus that boots four released driver versions under today's
runtime, a boot-ensure that renames rather than shadows a moved foreign key, and
a diagnosis for the 0.13 brick that is precise and unit-pinned in three files.

What is thin is the evidence. The two upgrade-replay suites are the only gates
that see an *aged* starting state, and both are currently running against
starting states that cannot express the failure they were written for:

- `project-snapshots/` holds exactly one snapshot, `v0.13.0`, whose recorded
  generated schema already declares the post-rename column. Both stale-codegen
  assertions early-return on it. The regression test for the defect that
  motivated the whole directory is, today, a no-op.
- `schema-snapshots/` holds exactly two files, both hand-written era-1
  reconstructions. Zero recorded release snapshots exist, and unlike the project
  recorder, `record-schema-snapshot.mts` is wired into neither `package.json`
  nor `tooling/scripts/release.sh`.

The KNOWN OPEN defect (**FK rename bricks 0.12 → 0.13**) is **substantially
fixed but not closed**. The boot still hard-fails, permanently, on a stale
`schema.generated.ts` — that part is intentional and correct. The three
mitigations added since (`rebase dev` auto-regenerates, `rebase schema stale`,
and a corrected error message) cover the first-party paths. Two paths are still
exposed, and one of them is worse than the original bug because the corrected
message states a fact that is false there (H1).

Severity counts: **2 high, 4 medium, 3 low.**

**Answer to "is there a version gate that REFUSES rather than proceeding?"**
Yes, four of them, and they are the good part of this unit:

1. `bundleFormat > BUNDLE_FORMAT_VERSION` → `BundleError` (`boot/bundle.ts:131-136`).
2. `runtime.contract !== RUNTIME_CONTRACT_VERSION` → `BundleError`, both directions (`boot/bundle.ts:140-148`).
3. `databaseVersion > AUTH_SCHEMA_VERSION` → `AuthSchemaVersionError`, rethrown out of the swallowing catch (`auth/ensure-tables.ts:31,891`).
4. `ensureCollectionSchema` failure is fatal by design (`boot/boot.ts:676-679`), and `searchDrift` refuses before applying anything (`ensure-collection-tables.ts:781-783`).

Contract 1 — the `rebase` range in `rebase.json` — is the one that does **not**
gate anything (L1).

## Findings

### HIGH

#### H1 — Ejected / custom-entrypoint deployments get a boot refusal whose fix text is false, and following it makes things worse

`packages/server-postgres/src/collections/validate-relations.ts:118-120`

```
"regenerate it with `rebase schema generate` (or `pnpm run schema:generate`). The "
"database column has already been renamed for you at boot, so nothing else is needed. "
```

That sentence is true on exactly one path. `ensureCollectionSchema` — the only
caller of `ensureCollectionTables`, and therefore the only thing that emits the
`RENAME COLUMN` — is invoked from `packages/server/src/boot/boot.ts:215`, inside
`bootFromBundle`. The ejected backend template
(`packages/cli/templates/eject/backend/src/index.ts:103`) calls
`initializeRebaseBackend` directly and never calls it. `initializeRebaseBackend`
ensures **auth** tables only (`packages/server/src/init.ts`, via
`bootstrapper.initializeAuth` → `ensureAuthTablesExist`).

**Failure scenario.** An ejected 0.12 project with a `manyToMany` off a plural
slug upgrades its packages.

1. Boot: registry built from the stale `schema.generated.ts` (`categorie_id`);
   collections now derive `category_id`; `staleCodegenRename`
   (`validate-relations.ts:90-102`) matches, so the *stale-codegen* branch is
   taken and boot dies with the message above.
2. The developer does what the message says and runs `rebase schema generate`.
   The module now declares `category_id`.
3. Boot now passes `assertRelationsResolve` — the two artifacts agree. **The
   database still has `categorie_id`**, because nothing ever renamed it.
4. Every query through that relation now references a column Postgres does not
   have. UNCONFIRMED that this is `42703` specifically; what is confirmed is
   that the module and the catalogue now disagree with no gate between them.

This converts a loud, boot-time refusal into a runtime failure — the precise
inversion the corrected message was written to prevent. It is the same bug class
as the original ("advice that names a column the database does not have"), just
pointed the other way.

**Fix direction.** The claim has to be conditional on the ensure having run.
Either (a) have `assertRelationsResolve` compare against the live catalogue, or
at minimum say *which* artifact it read and that it did not read the database;
or (b) pass a flag from the boot path so the "already renamed for you" clause is
only emitted where `ensureCollectionSchema` actually ran, and otherwise say
"run `rebase db push` / `rebase db migrate` first, then regenerate". The
`schemaRecoveryGuidance` helper in `packages/server/src/boot/version-skew.ts:146`
already models exactly this "two audiences, name both" pattern.

#### H2 — The project-upgrade corpus cannot exercise the defect it exists for

`packages/server-postgres/test/e2e/project-upgrade-e2e.test.ts:306-324` and
`:326-354`

Both stale-codegen tests begin:

```ts
const defects = findRelationDefects(collections, staleRegistry());
if (defects.length === 0) { /* … */ return; }
```

The only snapshot in the corpus is `project-snapshots/v0.13.0/`, and its
`generated-schema.json:10-13` records `categories_products: ["product_id",
"category_id"]` — the **post**-rename name. `staleCodegenRename` requires
`available.has(legacy) && !available.has(current)`
(`validate-relations.ts:101`), so it never matches; `findRelationDefects`
returns `[]`; both tests return without asserting anything.

This is structural, not accidental. `record-project-snapshot.mts` reads
`generated-schema.json` back from the catalogue of a database it just
provisioned with the current checkout (documented in
`project-snapshots/README.md`), so a snapshot recorded at release *N* can never
disagree with release *N*. Only a `v0.12.0` snapshot could trip the check, and
it does not exist — the recorder was added after 0.13 shipped, and it cannot be
run against an old release without checking that release out.

The suite's own header (`project-upgrade-e2e.test.ts:20-23`) names this exact
hazard for hand-written fixtures. It applies to a same-release recorded snapshot
for the same reason.

**Fix direction.** Record a `v0.12.0` snapshot by checking out `v0.12.0` and
running the recorder there (the recorder provisions its own Postgres, so no
vintage database is needed). Failing that, make the corpus refuse to be vacuous:
assert that at least one snapshot in the directory produces a non-empty
`findRelationDefects`, the way `MINIMUM_SNAPSHOTS` guards against an empty
`describe.each`. A conditional assertion with no snapshot that satisfies the
condition is a green gate that ran on nothing — which is the failure mode both
READMEs in this subsystem explicitly warn about.

### MEDIUM

#### M1 — `--skip-schema` still ships the brick, and the recovery command cannot reach a managed tenant

`packages/cli/src/bundle.ts:978` gates regeneration on `options.skipSchema !== true`
(`packages/cli/src/commands/build.ts:69,160`). A project that builds with
`--skip-schema` — offered in the help text as the option for a "deliberately
hand-maintained" schema, and the very thing an error message elsewhere
recommends (`bundle.ts:904`) — ships the stale module into the bundle.

On a managed tenant the resulting boot loop is unrecoverable from the message
alone: `validate-relations.ts:388` says `rebase schema generate`, which is a
project-local codegen command. There is no shell on the pod, and regenerating
locally does nothing until the bundle is rebuilt and redeployed. This is the
same lesson `version-skew.ts:131-145` documents at length for `rebase db push`
("`rebase db push` cannot reach a tenant's in-cluster database — redeploy
instead"), and the relation validator does not carry the managed variant.

**Fix direction.** Give `assertRelationsResolve` the managed/self-host split
that `schemaRecoveryGuidance` already implements, and consider having
`rebase build --skip-schema` run `schema stale` (non-`--fix`) so the build fails
rather than shipping a bundle that cannot boot.

#### M2 — Rollback is undetectable outside auth, and the auth gate has never been able to fire

`packages/server-postgres/src/auth/schema-version.ts:37` — `AUTH_SCHEMA_VERSION = 2`,
and 2 is the first value ever written (the file says so at `:13-19`). The refusal
at `:139` triggers on `databaseVersion > AUTH_SCHEMA_VERSION`. Since no release
has ever stamped a value above 2, **no deployed database can currently make this
gate fire**. It is correct, well-tested (`test/auth-schema-version.test.ts:82-115`)
and entirely prospective.

Everything outside the auth schema has no stamp at all — `grep schema_meta`
across `packages/` yields exactly one key, `auth_schema_version`. There is no
framework-version stamp and no collection-schema version. Consequently a
0.13 → 0.12 rollback after the FK rename is silent: 0.12 derives `categorie_id`,
does not find it, and `ADD COLUMN`s it nullable (`ensure-collection-tables.ts:451`
appends `NOT NULL` only when `fresh`), leaving relations reading an empty column
beside the populated `category_id`. Nothing errors. UNCONFIRMED — reasoned from
the planner, not executed.

`docs/compatibility.md:109-148` argues correctly that contract 6 cannot be
version-gated *per column*. That does not preclude stamping the framework
version that last touched the schema into `rebase.schema_meta` and warning on a
downgrade.

**Fix direction.** Write a `framework_version` key alongside `auth_schema_version`
in `stampAuthSchemaVersion` (the table and the write path already exist,
`schema-version.ts:150-167`) and warn loudly at boot when the running version is
below it. A warn, not a refusal — rollback is a legitimate operation and must
stay possible — but a silent one is how a rename becomes invisible data.

#### M3 — The auth snapshot corpus has zero recorded release snapshots, and its floor cannot fire

`packages/server-postgres/test/e2e/schema-snapshots/` contains
`era-1a-user-id-legacy-roles.sql` and `era-1b-uid-device-session.sql` and
nothing else. Both are hand-written era-1 reconstructions
(`schema-snapshots/README.md`, "Hand-written — for an era that predates
snapshotting"). `MINIMUM_SNAPSHOTS = 2` (`upgrade-e2e.test.ts:53`) is exactly
satisfied by that pair, so the guard against a silently empty `describe.each`
can never fire even though the intended corpus — one recorded snapshot per
release — is empty.

The asymmetry with the project corpus is the mechanical cause:
`record:project-snapshot` has a root `package.json` script (`package.json:70`)
and is run by `tooling/scripts/release.sh:248-254`; `tooling/scripts/record-schema-snapshot.mts`
has neither. It is documented only in a file header and a README, and it also
requires a real database of the right vintage, which the project recorder
deliberately avoided needing.

Practical consequence: the auth upgrade gate's newest starting point predates
the stamp entirely. Nothing in CI upgrades *from* a stamped v2 database except
the second-run idempotency case at `upgrade-e2e.test.ts:321-339`, which starts
from an era-1 database this same test just migrated.

**Fix direction.** Give `record-schema-snapshot.mts` the treatment the project
recorder got: a `package.json` script, a `release.sh` step, and — the harder,
higher-value change — the ability to provision its own database from the current
checkout so "record one per release" stops depending on someone having a vintage
database to hand. Then raise `MINIMUM_SNAPSHOTS` past the hand-written pair.

#### M4 — The Drizzle out-of-order-migration gate runs in no pipeline

`tooling/scripts/harness/checks/migration-order.mjs` is a genuinely good check: it
verifies `when` rises with `idx` inside each journal (`:43-57`) *and* that a
branch's new migrations sort after everything on `main` (`:61-80`), and it
explicitly downgrades to a WARN when main's journal is unreadable rather than
reporting a green line for work that did not happen.

It is not wired into CI. `.github/workflows/verify.yml:266` runs
`pnpm run test:harness`, which is `node --test tooling/scripts/harness/test/harness.test.mjs`
— the harness's own unit tests. The runner itself, `package.json:78`
(`"harness": "node tooling/scripts/harness/harness.mjs"`), is invoked by no workflow.
So the established failure — two branches merge, the lower `when` is skipped
forever, silently — is caught only if a human or agent runs `pnpm harness`.

Two mitigating facts, both worth stating so this is not over-weighted:

- The check targets `saas/backend/drizzle/meta/_journal.json` and
  `cloud-platform/backend/drizzle/meta/_journal.json` only. The second does not
  exist. The first is **currently monotonic** — 44 entries, verified.
- The OSS framework does **not** use the Drizzle migrator. `rebase db migrate`
  shells out to Atlas (`packages/server-postgres/src/cli.ts:288-294`,
  `runAtlas("migrate", ["apply", …])`) with `--revisions-schema rebase`, and
  `db generate` runs `migrate hash` (`:194`) to maintain `atlas.sum`. Atlas
  tracks each revision individually and validates the directory checksum, so the
  high-water-mark skip does not apply to a user's project. UNCONFIRMED at the
  level of specific Atlas flags — I did not verify Atlas's out-of-order
  behaviour directly.

**Fix direction.** Add a `migration-order` step to the saas pipeline (memory
records that saas CI builds against this repo's `main`), or run
`pnpm harness migration-order` from `verify.yml` and let the "cannot read main's
journal" WARN be non-fatal.

### LOW

#### L1 — Contract 1 (`rebase` range in `rebase.json`) is emitted but never enforced

`docs/compatibility.md:37` lists the `rebase` range as "Checked in: CLI at
build". `packages/cli/src/manifest.ts:315-324` validates only that the key is a
non-empty string, with a helpful message about the `runtime` → `rebase` rename.
The value is copied verbatim into `manifest.runtime.range`
(`packages/cli/src/bundle.ts:1083,1279`). Nothing then compares it to anything:
the runtime checks only `manifest.runtime.contract` (`boot/bundle.ts:140`), and
`packages/cli/src/commands/cloud/bundle-deploy.ts:34` checks the field's
*presence*. `canReach(d.range, …)` at `bundle.ts:745` is about declared npm
dependency ranges, not this.

Low because contracts 2 and 3 cover the failure that matters, and the range is
documented as advisory in spirit. But the compatibility table currently
overstates it.

**Fix direction.** Either compare `runtimeRange` against the CLI's own version
at build (a warn is enough), or amend `docs/compatibility.md:37` to say
"declared, not enforced".

#### L2 — The driver-skew corpus only ever meets a fresh database

`tooling/scripts/verify-bundle-corpus.mts:154` pins `DRIVER_SKEW = ["0.10.0", "0.11.0",
"0.12.0", "0.13.0"]` and boots each with today's `@rebasepro/server` symlinked
over it, exactly as `infra/docker/entrypoint.mjs` does — the single strongest gate in
this unit, and the one that reflects what managed tenants actually run. But the
database it boots against is created fresh (`createdb rebase_corpus` in
`verify.yml`, and per-version isolation noted at `:350`). So the two axes never
cross: aged DB is tested with the current driver, old driver is tested with a
new DB, and "old driver meets aged database" — the actual managed-fleet state
after an image rollout — is tested nowhere.

**Fix direction.** Restore a `schema-snapshots/` file into the corpus database
before one of the skew iterations. Cheap, given both harnesses already exist.

#### L3 — A half-applied collection ensure is re-runnable, but the log does not say a rename already happened

`ensure-collection-tables.ts:730-733` documents the choice: each statement runs
on its own, not in one transaction, so one failure does not roll back the tables
that succeeded. `add-constraint` and `comment-column` failures are collected and
survived (`:817-820`); everything else throws with the statement attached
(`:821-823`). The next boot re-reads the live catalogue (`:756`) and re-plans, so
a half-applied upgrade converges — this is the right design and
`project-upgrade-e2e.test.ts:204-213` pins it.

The gap is narrative, not mechanical. If a `rename-column` succeeds and a later
action throws, the operator sees only the failing statement. The rename was
logged at info (`:763-770`) before the apply loop, so it is in the log, but
nothing correlates "this boot already moved a column" with "this boot then
died" — which is precisely the state H1's message is wrong about.

**Fix direction.** Include the actions already applied in the thrown error, or
re-log applied renames at the failure site.

## Checked and clean

- **`version-skew.ts`** is careful in the right places. `parseVersion` returns
  `undefined` rather than guessing (`:59-66`), prerelease sorts below its release
  so canaries do not read as newer (`:76-88`), and `describeDriverSkew` returns
  `stale: false` whenever it cannot tell (`:109-129`). `readRuntimeVersion`
  resolves *through the bundle* on purpose so an entrypoint symlink that did not
  happen is visible rather than papered over (`:182-204`).
- **`assertAuthSchemaCompatible` runs outside the swallowing catch**
  (`ensure-tables.ts:26-31`), and the catch rethrows `AuthSchemaVersionError`
  specifically (`:891`). The distinct error class exists for exactly that, and
  the comment says so.
- **The stamp is written last among the migrations** (`ensure-tables.ts:855-858`),
  so a boot that dies partway leaves the older stamp and the next boot re-runs.
  The one write ordered after it (`revokeInternalTableAccess`) is justified in
  place: `schema_meta` is created *by* the stamp.
- **`readAuthSchemaVersion` uses `to_regclass`** so a missing schema or table is
  `null` rather than a thrown 42P01, and an unparseable value is `null` rather
  than `0` (`schema-version.ts:106-125`) — refusing to boot over a garbled string
  would be worse than the drift it guards.
- **`probeAuthSchema` never throws** and checks two independent things — the
  stamp (catches runtime-older-than-database) and the structure (catches
  database-older-than-runtime, and works on the unstamped databases that are
  today's entire population). `:181-196` explains why either alone has a blind
  spot.
- **The probe reaches `/health` and returns 503.** `init.ts:1908-1912` →
  `init/health.ts:33-46` → `boot/boot.ts:286-311`. `/livez` deliberately does not
  touch the database (`boot.ts:318`), so a database blip cannot get healthy pods
  killed.
- **`upgrade-e2e.test.ts` asserts results, never "it booted."** Given that the
  migration block swallows and continues, this is the only thing that makes the
  suite mean anything, and every assertion reads the catalogue or the rows. Its
  sharpest test is a *write* — two live tokens for one session (`:303-317`), the
  42P10 a shape-only check cannot see. `MINIMUM_SNAPSHOTS` guards against
  `describe.each([])` reporting green on nothing (`:45-53`). The seed-rows
  precondition (`:121-122`) prevents a snapshot that cannot catch a dropped
  back-fill.
- **The three era-specific describes are real coverage** the generic loop cannot
  give: legacy roles junction → inline column (`:344-430`), expand-not-rename of
  `user_id`/`uid` with a bidirectional sync trigger tested from both pod eras
  (`:404-429`), mixed-case email folding (`:434-480`), and the colliding-emails
  case that must *not* fold and must not abort the migrations after it
  (`:482-544`).
- **`session_started_at` is back-filled from `created_at`, not `NOW()`**, and the
  test says why (`:287-299`) — a `NOW()` back-fill would let every pre-existing
  session outrun a password-reset invalidation issued before the upgrade.
- **Per-row `session_id`** is asserted by distinctness, not presence
  (`:274-285`), which is what distinguishes a per-row `gen_random_uuid()` from a
  column DEFAULT that stamps every row alike.
- **The FK rename fires only where nothing is guessed** — new name absent, old
  name present (`ensure-collection-tables.ts:375-376`) — and is reported at info
  before it is applied, naming both spellings and the `localKey` opt-out
  (`:763-770`).
- **The stale-codegen diagnosis is precisely scoped.** `staleCodegenRename`
  checks against the *sources* a default could derive from rather than guessing
  backwards from the wanted name (`validate-relations.ts:90-102`), skips names
  that never moved (`legacy === current`), and requires the table to carry the
  old spelling and not the new one. It is applied on all three derived-name
  paths — `belongsTo` localKey, `hasOne`/`hasMany` foreignKeyOnTarget, and both
  junction columns (`:176-186`, `:200-213`, `:236-268`) — with the junction case
  correctly called out as the one that actually moved.
- **`legacy-fk-rename-boot-seam.test.ts` pins the diagnosis properly**, including
  a self-check that the fixture still expresses the rename at all (`:99-106`) —
  a guard against the test passing against an unbroken fixture.
- **`generated-schema-staleness.ts` is deliberately narrow** and says so
  (`:20-23`): it answers "does this file name a FK the way the previous rule did",
  not "is this what we would generate now". `tableBlock` scopes per table so two
  junctions with same-named columns cannot cross-attribute (`:38-53`), and
  `declaresColumn` requires the Drizzle column shape so a comment or a policy
  expression naming the old column does not read as a declaration (`:55-68`).
  Both are the difference between a check that gets fixed and one that gets
  switched off.
- **`rebase dev` runs `schema stale --fix` regardless of `--generate`** and
  never blocks on it (`cli/src/commands/dev.ts:436-464`) — the reasoning in the
  comment ("this is not 'keep my schema fresh', it is 'do not hand the runtime a
  file that cannot boot'") is right.
- **`rebase build` fails rather than shipping an ungeneratable schema**
  (`cli/src/bundle.ts:898-907`).
- **Bundle format is backward-compatible, contract is exact-match, both refuse
  loudly** (`boot/bundle.ts:123-149`), and `upgradeLegacyManifest` normalises
  format 1 → 2 with a frozen `format1-cms` fixture proving it
  (`fixtures/bundles/README.md:46-50`, `verify-bundle-corpus.mts:438`).
- **The corpus recomputes `schemaVersion` independently** rather than comparing
  the manifest to itself, and the comment records that the naive version went
  green against a deliberately corrupted fixture (`verify-bundle-corpus.mts:466-492`).
- **Both e2e suites are in CI.** `.github/workflows/verify.yml:494` runs
  `test:e2e` for `@rebasepro/server-postgres`, which globs `test/e2e/**`.
- **`release.sh` records a project snapshot at the right moment** — after the
  version bump so the file is stamped correctly, before the commit so it lands in
  the release, before the next migration is written — and warns loudly without
  blocking when Docker is absent (`tooling/scripts/release.sh:230-254`).
- **The two snapshot READMEs are unusually good** and both name the exact trap
  their corpus is prone to. The findings above are largely that the discipline
  they describe has not been kept, not that they are wrong.
- **`saas` journal is monotonic today** — 44 entries, `when` strictly increasing.

## Open questions

1. **Is `rebase eject` a supported production path?** H1's severity hinges on it.
   If ejected projects are expected to run `rebase db push` / `db migrate`
   themselves before booting, then the message at `validate-relations.ts:119` is
   simply wrong for them and the fix is a one-line conditional. If ejected
   projects are expected to get boot-ensure, the gap is in the template.
2. **Should `ensureCollectionSchema` move into `initializeRebaseBackend`?** It
   currently lives only in `bootFromBundle`, and the comment at `boot.ts:779-783`
   explains the ordering constraint (the hooks run *before* `initializeDriver`).
   That constraint looks satisfiable inside `init.ts` too, but I did not trace
   whether the driver result is available early enough there.
3. **Can a `v0.12.0` project snapshot be recorded retroactively?** The recorder
   provisions from `tooling/scripts/derived-names.mts`'s reference project using the
   current checkout. Checking out `v0.12.0` and running it should work, but the
   recorder did not exist at that commit — so it would have to be cherry-picked
   onto a detached `v0.12.0`, and it is not obvious whether its imports resolve
   against 0.12's package surface.
4. **What is the intended trigger for `record-schema-snapshot.mts`?** It needs a
   real database "provisioned by THIS release" and is in no script. Was the
   intent that it be superseded by the project recorder, or that both run per
   release? The two corpora cover different axes, so I read it as the latter, but
   the release script only knows about one.
5. **Does Atlas actually refuse an out-of-order migration**, or only a checksum
   mismatch? This determines whether the established Drizzle high-water-mark
   defect has any analogue on the OSS `rebase db migrate` path. I did not verify
   Atlas's behaviour, only that `atlas.sum` is maintained (`server-postgres/src/cli.ts:194`).
6. **Is `--skip-schema` used by anyone?** If not, making it imply a `schema stale`
   check is free. If the managed build path can reach it, M1 is worth more than
   medium.
7. **Should the managed intake enforce a driver floor?** Memory records
   `minimumFrameworkVersion` as NULL everywhere and only driver `0.13.0+` as able
   to create tables. That is cloud-side and outside this unit, but it is the
   other half of the "old driver, new server" story that `DRIVER_SKEW` covers on
   the OSS side.
