# DX audit — 2026-07-25

Hands-on audit of the developer experience, plus a record of what was fixed the
same day and what was deliberately left.

Kept in `docs/` on purpose. The first copy of this lived at the repo root as
`AUDIT-2026-07-25-DX.md`, untracked alongside the other `AUDIT-*.md` / `PLAN-*.md`
files, and a concurrent "clear repo debris" pass deleted all of them. Untracked
notes at the repo root do not survive.

**Method.** Scaffolded both flavors from the published `@rebasepro/cli@0.10.0` via
`pnpm dlx`, ran them against real Postgres containers, edited collections, broke
things on purpose, typechecked the snippets the tooling prints, and read the docs
against the code. Every finding was reproduced, not inferred.

---

## Verdict

The happy path is good. `pnpm dlx @rebasepro/cli init` → working admin panel took
**under two minutes**. The BaaS flavor delivered on its headline promise with zero
config: a table created in `psql` with RLS enabled was auto-discovered and served.
`rebase doctor`, `rebase db push`, the release-gap guard and the `.env` secret
generation all show real craft.

The problems clustered in three places:

1. **The seams between components lied to each other.** The generated README
   contradicted the generated `.env`; the CLI's success message contradicted the
   SDK it had just generated; an error hint named a docker service that did not
   exist in the compose file the same CLI wrote.
2. **The type story was undersold** — and, it turned out, largely absent. See the
   addendum.
3. **Safety nets existed but were not armed.** `pnpm verify:docs` reported 189
   findings and was warn-only.

## Addendum: silently-dropped type parameters

Fixing cluster 3 exposed a defect class the original audit missed, and the root
cause was not what it guessed. The pattern:

> A generic parameter carrying the user's own property names is computed
> correctly, then dropped at a seam — a declaration merge, a re-export alias, a
> hardcoded `Record<string, unknown>`. `Extract<keyof M, string>` widens to
> `string`, every key-shaped field silently accepts anything, and the feature's
> own documentation describes a check that has never run.

Nothing detects this. The code compiles either way; only a deliberate probe
("does a nonsense key error?") finds it.

### 1. The admin block was never checked (fixed)

`augment.ts` merged the block on as `admin?: AdminCollectionOptions` — **no type
arguments**. `M` fell back to `Record<string, unknown>`, so `titleProperty`,
`sort`, `propertiesOrder` and `listProperties` accepted any string.
`defineCollection` computed the inference correctly the whole time and it was
dropped one line short of the fields that needed it. The completion those fields'
docs promised had never worked.

Now checked, with `defineCollection` supplying `M`: `titleProperty`, `sort`,
`propertiesOrder`, `listProperties`, `previewProperties`, `fixedFilter`,
`defaultFilter`, `filterPresets`, `orderProperty`, and `AdditionalFieldDelegate.dependencies`.

Three non-property forms stay legal: a dotted path into a `map` property
(root checked, path below it not), `subcollection:<slug>`, and an
`additionalFields` key — the last via an explicit `as AdditionalFieldKey` cast,
because `AdditionalFieldDelegate.key` is a plain `string` and nothing carries
those keys into the type. The brand on `AdditionalFieldKey` is **required**; an
optional one is satisfied by every string and would quietly restore the old
behaviour.

Pinned by a type-level test in `packages/admin-types/test/admin_collection.test.ts`
(`tsconfig.tests.json` typechecks that directory, so `@ts-expect-error` is a real
assertion there). One bad key per call — with several in one literal, overload
resolution reports a single `TS2769` against the call and the directives read as
unused, so the assertions would pass for the wrong reason.

### 2. SDK query parameters were never checked (fixed)

`FindParams` was not generic: `where?: FilterValues<string>`, `orderBy?:
OrderByTuple`. Passing a generated `Database` to `createRebaseClient` typed the
*rows* but not the *query*, so `find({ where: { nonexistent_column: ["==", 1] } })`
compiled and failed as a 400 at runtime — or matched nothing.

`FindParams<M>` now carries the row type. The chain that must stay intact is
`createRebaseClient<DB>` → `SDKCollectionClient<M>` → `FindParams<M>` →
`FilterValues<FieldPath<M>>`. The alias that hid it was one line in
`client/src/transport.ts`:

```ts
export type FindParams = TypesFindParams;   // dropped M back to its default
```

`include` is unchanged — relation names come from `relations`, not the row type.
The fluent builder's internal accumulator stays keyed by `string`, because a
`Partial<Record<FieldPath<M>, …>>` is read-only under a generic `M` (TS2862) and
cannot be built up in place; its public setters were already typed.

Pinned in `e2e/baas-typecheck/src/sdk.ts`, so `pnpm check:baas-types` fails if the
check comes back off.

### 3. A NUL byte made a whole file invisible to grep (fixed)

`packages/client/src/offline.ts` contained a **raw NUL byte** in a sentinel:

```ts
const MISSING = "<0x00>missing";
```

The value is deliberate — an id can never contain it — but written as a raw byte
rather than the escape `"\u0000"`, it made the file test as binary. Every `grep` over the
repo silently skipped all 1,700 lines of it, including while auditing it. Now an
escape; identical at runtime, and 761 client tests still pass.

Worth generalising: **a repo-wide grep that finds nothing is not evidence of
absence.** `file packages/**/*.ts | grep -v text` is a cheap check.

### Verified healthy

- **Entity callbacks** are properly typed — `beforeSave` / `afterSave` reject a
  nonexistent field. `M` flows correctly through `CollectionCallbacks<M, USER>`.
- **Property-level errors** are excellent: `'validaton' does not exist in type
  'StringProperty'. Did you mean to write 'validation'?`

## Still open

**`CONTRIBUTING.md` step 3 does not exist.** `pnpm run db:push` from the repo root
is `ERR_PNPM_NO_SCRIPT`. The third command a new contributor types.

**Four admin fields still drop `M`**, all blocked on the same variance problem
rather than on a type edit:

| Field | Why it is hard |
| --- | --- |
| `kanban.columnProperty` | **Required**, so a generic-dependent type is in an invariant position: `AdminCollection<M>` stops being assignable to `AdminCollection`. Measured: ~15 errors alone. |
| `entityViews` | Hardcodes `EntityCustomView<Record<string, unknown>>`, so a custom view's `entity.values` is untyped |
| `formView` | `FormViewConfig` used without its `M` |
| `Actions` | `ComponentRef<CollectionActionsProps>` used without `<M, USER>` |

All three of the latter, plus `columnProperty`, measured **95 errors** together.
The fix is to stop passing collections between `AdminCollection<M>` and
`AdminCollection` in the admin package (~15 call sites: `CollectionBoardViewBinding`,
the collection editor, the view bindings), then narrow. Worth doing; not a
type-only change.

**Runtime controller state is legitimately permissive** and should stay that way:
`SelectionController.filterValues` / `sortBy` / `propertyKey`,
`useDataTableController`, and `CollectionViewBinding`'s column-drag order all
carry ids the user produced at runtime, including additional-field and
`subcollection:` ids.

**`verify:docs` is still warn-only** (182 findings at the time of writing, since
reduced by concurrent work). The remaining ones are genuine content bugs —
`uploadFile`/`getDownloadURL` on `StorageSource`, `entityId` on `AfterSaveProps`,
`context.dataSource`, an unresolvable `@rebasepro/data_enhancement` import. Clear
the backlog, then make `--strict` blocking so the number can only go down.

**Other DX findings from the original audit, unfixed** (lower severity, listed in
priority order): `rebase dev` requires `--generate` to regenerate on collection
change and its warning box over-prescribes (`db push` alone resolves all three
drift checks); `doctor` and `db push` route human output through the structured
logger so every line reads `ℹ️ [INFO]`, including red error boxes; error
presentation is inconsistent (a formatted box for a dead database, a raw
`ZodError` dump for a short `JWT_SECRET`); `dotenvx` prints third-party promos
into every CLI run; first boot emits ~40 `INFO` lines and two `WARN`s, one of
which is internal wiring the user cannot act on; routine 4xx log at `WARN`;
`/health` is not under `/api`; the login form's inputs have no accessible labels
(the password field's accessible name is `"••••••••"`).

## How to look for more of this

The defect class is invisible to tests and to typecheck. What finds it is a probe
that asserts a **negative**:

```ts
defineCollection({ …, admin: { titleProperty: "deliberate_nonsense" } });
//                              ^ if this compiles, the check is not running
```

Two greps that locate candidates:

```bash
# A generic type used without its argument, in a field declaration
grep -rn "Record<string, unknown>>\|: FormViewConfig;\|CollectionActionsProps>" packages/*/src

# The permissive-escape idiom, which accepts every string
grep -rn "string & {}" packages/*/src
```

Then check whether each escape is load-bearing (a runtime controller, a
target-collection key list) or vestigial (an authoring field that should be
checked). The distinction is whether the value is authored by a developer in a
collection file or produced by the running UI.
