Toda falha retornada por um backend Rebase usa um envelope padronizado e traz um `code` estável. O código é o elemento sobre o qual deve ser feita a tomada de decisão (branching): a mensagem é escrita para pessoas e pode ser reformulada, o status é compartilhado por dezenas de problemas diferentes, e o código não é nenhum dos dois.

## O envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — legível por humanos. Para um `4xx`, é a mensagem do próprio servidor; para um `5xx`, é deliberadamente genérica, porque o texto subjacente pode citar um host, uma role ou o nome de uma coluna.
- **`code`** — um dos valores abaixo. Estável entre versões menores (minor versions).
- **`details`** — opcional e nunca garantido. Veja as regras abaixo.
- **`requestId`** — presente sempre que a requisição passou pelo middleware de request-ID, o que inclui todas as rotas sob `basePath`.

### `X-Request-ID`

Toda requisição sob `basePath` recebe um ID: o cabeçalho `X-Request-ID` do chamador quando for um UUID; caso contrário, um novo é gerado. Ele é retornado na resposta como `X-Request-ID`, incluído no envelope de erro como `requestId` e anexado à linha de log do servidor referente àquela requisição.

Essa é a chave de junção. Cite-a em um relatório de bug e um operador poderá encontrar a linha de log exata que explica a falha, contendo o motivo que nunca foi exibido ao cliente.

Enviar o seu próprio ID é a maneira de um rastreamento (trace) sobreviver a múltiplos saltos (hops): um gateway ou executor de tarefas (job runner) que encaminha o cabeçalho mantém um único ID em todos os serviços que processaram a requisição. Um valor inválido é ignorado em vez de rejeitado — não vale a pena falhar uma requisição por causa de um cabeçalho malformado enviado pelo chamador —, portanto, não presuma que o ID enviado é o mesmo ID recebido. Leia o cabeçalho da resposta.

### O que há em `details`

`details` tem finalidade diagnóstica, não contratual. Três regras o regem:

1. **Tudo o que uma rota define explicitamente é sempre retornado.** Esses são os erros do próprio chamador descritos com precisão: qual campo de filtro era desconhecido, qual relação não permite gravação, qual valor não correspondeu ao seu tipo.
2. **Diagnósticos do banco de dados são omitidos em produção.** Quando a falha tem origem no Postgres, `details.dbCode` — o SQLSTATE — está sempre presente: ele indica a classe do problema e não revela nada sobre os dados. `dbMessage`, `detail` e `hint` são adicionados apenas quando `NODE_ENV` não for `production`, pois o Postgres insere o conteúdo das linhas neles. O código `23505` reporta `Key (email)=(a@b.c) already exists.`, o que responde à pergunta "esta pessoa já está registrada?" para qualquer endereço que alguém decida testar.
3. **Nunca faça branching em `details`.** Faça branching em `code`. O conteúdo sob `details` é simplesmente o que era útil para uma pessoa naquele local de chamada, e isso pode mudar.

## Lendo um status

| Status | O que diz sobre a requisição |
| --- | --- |
| `400` | Malformada ou solicitando algo que não existe no esquema. Corrija a requisição. |
| `401` | Não autenticado ou a credencial expirou. Faça login ou renove. |
| `403` | Autenticado e não permitido. Tentar novamente com a mesma identidade não ajudará. |
| `404` | Rota, tabela ou linha inexistente — ou uma linha que a segurança em nível de linha oculta. |
| `409` | Conflito com o estado existente: duplicata ou gravação concorrente. |
| `413` `415` `422` | O corpo é muito grande, tipo de mídia incorreto ou rejeitado semanticamente. |
| `429` | Limite de taxa excedido (rate limited). Reduza a frequência; a mensagem informa por quanto tempo. |
| `500` | O servidor ou o banco de dados falhou, não o chamador. Verifique os logs. |
| `501` | A rota existe e esta implantação não pode atendê-la — um recurso desativado ou não configurado. |
| `502` `503` `504` | Uma dependência estava inacessível, não configurada ou muito lenta. |

## `PG_<SQLSTATE>` — uma constraint que o banco de dados recusou

Gravações que o Postgres recusa por inconsistência *nos dados enviados pelo chamador* respondem trazendo o SQLSTATE no próprio código: `PG_23505`, `PG_23503`, e assim por diante. Trata-se de uma família de códigos, não de uma lista fixa — o Postgres define centenas de SQLSTATEs —, mas apenas duas classes chegam a ser repassadas, por serem as únicas atribuíveis a falhas do chamador:

- **classe 23**, violação de restrição de integridade: duplicatas, chaves estrangeiras apontando para registros inexistentes, colunas NOT NULL vazias;
- **classe 22**, exceção de dados: valor incompatível com o tipo da coluna.

Todas as outras falhas — queda de conexão, coluna ausente, problemas de privilégios — são de responsabilidade do servidor e resultam em `500`. Dessa forma, `code.startsWith("PG_")` é um teste seguro para identificar que "os dados enviados na linha estavam incorretos", sendo os quatro códigos abaixo os mais comuns no cliente. `details.dbCode` traz o mesmo SQLSTATE para todos eles, e a mensagem indica a restrição violada.

| Código | Status | Significado | O que fazer |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | O valor não pôde ser interpretado no tipo da coluna — equivalente no lado da escrita a `INVALID_FILTER_VALUE`. | Envie um valor compatível com o tipo da coluna. |
| `PG_23502` | 400 | Uma coluna `NOT NULL` foi enviada vazia. | Envie o campo ou defina um valor padrão para a coluna. |
| `PG_23503` | 400 / 409 | Na criação/atualização, a chave estrangeira aponta para uma linha inexistente (400). Na exclusão, outras linhas ainda referenciam este registro (409; chave com `RESTRICT` gera `PG_23001`, também 409). | Crie a linha de destino antes ou corrija o ID; para exclusões, remova ou reaponte as linhas que a referenciam primeiro. |
| `PG_23505` | 409 | Violação de constraint de unicidade (unique constraint). A mensagem identifica a constraint. | Use um valor diferente ou atualize a linha existente. |

via `POST /api/admin/schema/reconcile/plan` e aplica via
`/reconcile/apply`. Uma recusa não altera nada; apenas `SCHEMA_RECONCILE_FAILED`
deixa partes do plano aplicadas.

| Código | Status | Significado | O que fazer |

### Por que a tabela de uma branch não pode ser mesclada

O erro `BRANCH_MERGE_BLOCKED` lista em `details.tables` cada tabela recusada, associada a
um dos códigos a seguir. O mesmo código é exibido no campo `blocked` da tabela no próprio diff,
permitindo que o Studio avise o usuário antes que ele clique em **Merge**. Nenhum desses códigos constitui uma resposta de erro independente.

| Código | Status | Significado | O que fazer |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | As colunas da tabela divergem entre a branch e o pai. As linhas são comparadas com base nas colunas comuns a ambas. | Adicione as colunas faltantes ao pai por meio de migrations (`rebase db push`) e repita o merge. Migrations que reescrevem tabelas (mudança de tipo de coluna) geram `TABLE_REWRITTEN`: faça o merge antes de alterações assim ou recrie a branch após a mudança. |
| `NO_PRIMARY_KEY` | — | A tabela não possui chave primária, inviabilizando a comparação linha a linha; o diff retorna apenas a contagem total de linhas. | Adicione uma chave primária à tabela ou transfira os dados manualmente. |
| `PRIMARY_KEY_DIFFERS` | — | As colunas da chave primária ou seus tipos divergem entre as duas branches. | Aplique o esquema correspondente no pai primeiro. |
| `TABLE_ADDED` | — | A tabela foi criada na branch. O processo de merge nunca cria tabelas novas. | Crie a tabela no pai por meio de migrations e depois mescle suas linhas. |
| `TABLE_DROPPED` | — | A tabela foi removida na branch. O processo de merge nunca remove tabelas. | Remova a tabela no pai por meio de migrations. |
| `TABLE_REWRITTEN` | — | Um dos lados reescreveu todas as linhas da tabela após a criação da branch — alteração no tipo de coluna, `ADD COLUMN` com default volátil, `VACUUM FULL`, `CLUSTER` — fazendo com que todas as linhas pareçam modificadas e impossibilitando determinar a autoria de cada alteração. | Mescle a branch antes de migrations desse tipo ou recrie a branch a partir do pai após executá-las. |
| `TOO_LARGE` | — | A tabela contém em um dos lados mais linhas do que o diff compara individualmente (100.000 por padrão, `maxRowsPerTable`). | Aumente `maxRowsPerTable` no diff e no merge, ou transfira as linhas por outro método. |

## Mantendo esta página exata

O comando `pnpm verify:docs` falha se algum código que o servidor pode emitir estiver ausente destas
tabelas, se uma tabela listar um código que nada emite, se os status de uma linha não corresponderem
exatamente àqueles com que o código é lançado no código-fonte ou se uma família como `PG_<SQLSTATE>` não contiver a linha
de um SQLSTATE comum encontrado pelos chamadores. A etapa de validação é executada por
`tooling/scripts/docs-verify/check-error-codes.mjs`.

O script valida a si mesmo antes de começar. A varredura analisa os códigos diretamente no TypeScript e não a partir de um servidor em execução; portanto, pontos cegos seriam silenciosos por natureza: anteriormente, o script não identificava códigos passados por wrappers de uma linha ou códigos declarados logo após mensagens contendo `)`, reportando erroneamente que "todos os códigos do servidor estão documentados" em uma página que deixava dezessete de fora. Para evitar isso, a validação executa fixtures com essas exatas estruturas antes de ler esta documentação, recusando-se a validar qualquer arquivo caso não consiga identificá-las.
