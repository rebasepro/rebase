<span class="since-badge" data-since="0.31">Desde 0.31</span>

As regras de uma coluna são declaradas uma única vez, na própria coluna, e
impostas pelo servidor em cada gravação que atinge a API. O CMS lê as mesmas
regras a partir do descritor da tabela e as valida no formulário antes de salvar,
para que o operador veja o erro no campo, e não como uma requisição recusada.

```ts
// backend/schema/events.ts
import { defineTable, col } from "@rebasepro/server/schema";

export const events = defineTable("events", {
    columns: {
        id:      col.uuid().primaryKey().defaultRandom(),
        title:   col.text().notNull().validate({ min: 2, max: 200, requiredMessage: "Every event needs a title" }),
        slug:    col.varchar({ length: 80 }).notNull().unique()
                     .validate({ matches: "^[a-z0-9-]+$", matchesMessage: "Lowercase letters, digits and hyphens only" }),
        isFree:  col.boolean().notNull().default(false),
        price:   col.numeric({ precision: 10, scale: 2 }).validate({ min: 0 }),
        seats:   col.integer().validate({ positive: true }),
    },
    rls: "admin-only",
});
```

:::note[Vindo de collections?]
Não há mais um bloco `validation` no frontend. As regras são escritas na
coluna com `.notNull()` e `.validate({ … })`, e o CMS as lê.
:::

## O que o formulário verifica

<span class="since-badge" data-since="0.31">Desde 0.31</span>

| Na coluna | No formulário |
|---|---|
| `.notNull()` | Obrigatório, com `requiredMessage` como o erro quando informado. Não é obrigatório onde ninguém digita o valor: uma chave gerada, um stamp, uma coluna gerada ou `.readOnly()`. |
| `.unique()` | O valor é verificado contra a tabela antes de salvar um valor alterado, e uma duplicata é apontada em seu respectivo campo. |
| `varchar(n)`, `char(n)` | No máximo `n` caracteres. |
| text `min`, `max`, `length` | Contagem de caracteres, inclusivo. |
| `matches`, `matchesMessage` | O valor inteiro deve corresponder ao padrão; a mensagem é o erro. |
| `email`, `url` | O valor deve ser um e-mail, uma URL. |
| `trim`, `lowercase`, `uppercase` | O valor tem os espaços em branco removidos ou a caixa convertida antes de ser salvo. |
| number `min`, `max`, `moreThan`, `lessThan`, `positive`, `negative`, `integer` | Limites e apenas números inteiros. Colunas do tipo integer e serial são números inteiros independentemente do que o `.validate()` definir. |
| date `min`, `max` | A data mais antiga e mais recente aceita. |
| array `minItems`, `maxItems`, `uniqueItems` | Quantidade de itens, e nenhum item duplicado. |

Todas as regras estão listadas, com seus significados exatos, em
[Colunas](/docs/schema/columns/#validation).

## Onde a validação é executada

<span class="since-badge" data-since="0.31">Desde 0.31</span>

O servidor verifica as regras de uma coluna no limite da requisição (REST, o
socket em tempo real e MCP) com base no que o chamador enviou, antes da execução
de `beforeSave`, e responde a uma gravação que viole uma regra com um erro 400
indicando cada campo com falha. O código de servidor que grava em processo é
considerado confiável e não é validado contra essas regras; o que se aplica nesse
caso é o que o banco de dados impõe. Consulte
[Colunas](/docs/schema/columns/#validation).

O CMS verifica as mesmas regras antes de salvar, no formulário do registro e no
editor inline da tabela. Uma célula da tabela avalia um valor assim que você a
edita: um valor armazenado que viole uma regra adicionada posteriormente não
exibirá erro até que alguém edite essa célula.

## Campos condicionais

<span class="since-badge" data-since="0.31">Desde 0.31</span>

Um campo pode reagir aos próprios valores do registro: tornar-se obrigatório,
desativado, somente leitura ou oculto. Existem duas formas, ambas em `customizeTable`:

```tsx
// frontend/src/cms/events.tsx
import { customizeTable } from "@rebasepro/cms";
import type { events } from "../../../backend/schema/events";

export const eventsCms = customizeTable<typeof events>("events", {
    fields: {
        price: {
            conditions: {
                disabled: { "==": [{ "var": "values.isFree" }, true] },
                required: { "!=": [{ "var": "values.isFree" }, true] },
                min: 0,
                disabledMessage: "Free events have no price",
                clearOnDisabled: true,
            },
        },
        seats: {
            dynamicProps: ({ values, authController }) => ({
                disabled: values.isFree === true || !authController.user?.roles?.includes("admin"),
            }),
        },
    },
});
```

### `conditions`: JSON Logic

`conditions` contém regras [JSON Logic](https://jsonlogic.com/) sobre o registro
que está sendo editado (`values.<key>`). Elas são dados, portanto o editor de
schema pode lê-las e alterá-las. Uma condição pode definir:

- `disabled`, `disabledMessage`, `clearOnDisabled`, `hidden`, `readOnly`;
- `required`, `requiredMessage`, `min`, `max`;
- `defaultValue`;
- `enumConditions`, `allowedEnumValues`, `excludedEnumValues`;
- `referencePath`, `referenceFilter`;
- `canAddElements`, `sortable`, para arrays.

`disabledMessage` é o que o usuário vê ao lado do controle desativado. Sem isso,
um campo desativado não fornece nenhuma explicação.

### `dynamicProps`: uma função

`dynamicProps` recebe o registro enquanto ele está sendo editado (`values`,
incluindo alterações não salvas, e `previousValues` após ser salvo) junto com o
usuário autenticado em `authController`, e retorna as opções de campo aplicáveis
no momento. O que ele retorna é aplicado sobre as outras opções do campo sempre
que o formulário solicita, permitindo retornar qualquer opção de campo: `disabled`,
`hidden`, `readOnly`, `name`, `description`, `enumLabels`…

:::caution[Condições são comportamentos do formulário]
`conditions` e `dynamicProps` são executados no navegador e moldam o que o CMS
oferece. A API aceita uma gravação que os ignore. Uma regra que precisa ser aplicada
a todos os chamadores deve ficar na coluna (`.notNull()`, `.validate()`) ou na
[segurança em nível de linha](/docs/collections/security-rules/) da tabela, que o
banco de dados impõe para qualquer pessoa.
:::

## Rótulos para um conjunto fechado

<span class="since-badge" data-since="0.31">Desde 0.31</span>

Os valores de um `col.enum([...])` ou `.oneOf([...])` pertencem à coluna. Seus
rótulos, cores e ordem pertencem ao CMS, definidos com `enumLabels` e `enumOrder`;
consulte [conjuntos fechados](/docs/collections/properties/#closed-sets-of-values).
