Um campo de arquivo é uma coluna [`col.storage()`](/docs/schema/columns/#storage-columns).
A coluna armazena texto, a chave do objeto no bucket (ou sua URL, se
a coluna assim definir), e o CMS o renderiza como um campo de upload com pré-visualização.

O que um campo de armazenamento faz é dividido em dois, dependendo de onde é executado:

| Declarado | Onde | Opções |
|---|---|---|
| na coluna, em `backend/schema` | lido pelo servidor **e** pelo CMS | `path`, `source`, `accept`, `maxBytes`, `imageResize`, `public`, `fileName`, `metadata`, `includeBucketUrl`, `storeUrl` |
| em `customizeTable`, em `frontend/src/cms` | apenas no navegador | `storage.path(…)`, `storage.fileName(…)`, `storage.processFile`, `storage.postProcess`, `storage.previewUrl` |

As opções da coluna são serializáveis, portanto viajam no descritor da tabela
e o servidor aplica o que pode delas. As opções de `customizeTable` são
funções: elas não podem chegar ao servidor, portanto moldam apenas os uploads feitos a
partir do CMS.

## Um arquivo

<span class="since-badge" data-since="0.31">Desde 0.31</span>

```ts
// backend/schema/listings.ts
import { defineTable, col } from "@rebasepro/server/schema";

export const listings = defineTable("listings", {
    columns: {
        id:     col.uuid().primaryKey().defaultRandom(),
        title:  col.text().notNull(),
        cover:  col.storage({ path: "listings/{id}/", accept: ["image/*"], maxBytes: "10MB",
                              imageResize: { maxWidth: 1600, format: "webp", quality: 80 } }),
        photos: col.storage({ path: "listings/{id}/gallery/", accept: ["image/*"] }).multiple(),
    },
    rls: "admin-only",
});
```

`cover` é um campo de upload que aceita uma imagem de no máximo 10 MB, redimensionada para no
máximo 1600 pixels de largura e armazenada como WebP. Uma coluna cujo `accept` especifica um
tipo de imagem exibe uma pré-visualização como imagem, e a primeira coluna desse tipo preenche o
espaço de imagem do registro em cartões e listas.

## Vários arquivos

<span class="since-badge" data-since="0.31">Desde 0.31</span>

`.multiple()` transforma a coluna em um `TEXT[]` e o campo em um upload de múltiplos arquivos,
reordenável por arrastar e soltar. Todas as opções se aplicam a cada arquivo.

## Opções no navegador

<span class="since-badge" data-since="0.31">Desde 0.31</span>

```tsx
// frontend/src/cms/listings.tsx
import { customizeTable } from "@rebasepro/cms";
import type { listings } from "../../../backend/schema/listings";

export const listingsCms = customizeTable<typeof listings>("listings", {
    fields: {
        cover: {
            storage: {
                // A folder per listing title, computed in the browser.
                path: ({ values }) => `listings/${String(values.title ?? "untitled").toLowerCase()}/`,
                fileName: ({ file }) => `${Date.now()}-${file.name}`,
            },
            urlPreview: "image",
        },
        photos: {
            sortable: true,
            storage: { processFile: async (file) => file },
        },
    },
});
```

| `storage.` | Execução | Efeito |
|---|---|---|
| `path(context)` | antes de um upload | A pasta para onde o arquivo vai, substituindo o template `path` da coluna. |
| `fileName(context)` | antes de um upload | O nome do arquivo armazenado, substituindo o template `fileName` da coluna. Pode ser assíncrono. |
| `processFile(file)` | antes de um upload | Transforma o arquivo (compactar, remover metadados). |
| `postProcess(pathOrUrl)` | após um upload | Transforma o caminho ou URL antes de ser gravado na coluna. |
| `previewUrl(fileName)` | ao renderizar | A URL para pré-visualizar um arquivo armazenado, quando não for o valor do campo. |

`path` e `fileName` recebem o contexto do upload: o `file`, o `id` do registro
(ausente em um novo registro), seus `values` conforme editados, a `propertyKey` e as
regras de armazenamento resolvidas. Em uma coluna `.multiple()`, as mesmas opções de `storage` vão
diretamente no campo e se aplicam a cada arquivo.

`urlPreview` define como o valor armazenado é pré-visualizado (`"image"`, `"video"`,
`"audio"`, `"file"`, ou `true` para um link), e `clearable` adiciona um controle que
limpa o campo.

## O que o servidor verifica

<span class="since-badge" data-since="0.31">Desde 0.31</span>

`accept` e `maxBytes` são aplicados pelo servidor com base em **onde o arquivo é
gravado**. O `path` de uma coluna é para onde seus arquivos vão, portanto é também onde seus
limites se aplicam: qualquer upload cuja chave seja um arquivo diretamente sob esse caminho deve
cumpri-los, seja a partir do CMS, `client.storage.putObject`, um upload retomável, o
navegador de armazenamento do Studio ou `curl`, independentemente de especificar ou não a coluna, no
próprio bucket da coluna. Os placeholders correspondem ao que o CMS preencheria:
`{id}`, `{rand}`, `{file}` e similares representam um segmento de caminho, `{path}`
para qualquer quantidade. O caminho de uma coluna `public: true` fica sob `public/`.

- Várias colunas compartilhando o mesmo caminho: um arquivo que uma delas aceite é aceito.
- Um upload que também especifica sua coluna, como fazem os uploads do CMS, fica sujeito a
  essa coluna também. Especificar uma coluna mais permissiva não desbloqueia o caminho de uma coluna mais restrita.
- Uma função `storage.path` em `customizeTable` não pode ser lida pelo servidor,
  portanto um arquivo enviado sob o caminho que ela calcula só fica sujeito aos limites da coluna
  quando o upload especifica a coluna, o que os uploads do CMS sempre fazem.
- Um caminho que nenhuma coluna reivindica fica sujeito apenas ao limite do próprio bucket
  (`STORAGE_MAX_FILE_SIZE`).

`imageResize`, `processFile` e `postProcess` ocorrem no navegador, antes que os
bytes sejam enviados: um arquivo enviado por outro meio é armazenado exatamente como foi enviado.

## Para onde um arquivo pode ir

<span class="since-badge" data-since="0.31">Desde 0.31</span>

`path` é um padrão, não um limite restritivo: nada no servidor confina um upload a
ele. Quem pode gravar onde é uma regra de autorização de armazenamento; consulte
[Armazenamento](/docs/backend/storage/).

## Arquivos nunca são excluídos para você

<span class="since-badge" data-since="0.31">Desde 0.31</span>

Limpar um campo de arquivo, substituir seu arquivo ou excluir a linha deixa o
objeto armazenado onde ele está. Cada upload recebe uma chave própria, portanto uma substituição grava
um novo objeto, e nada remove o anterior: duas linhas podem conter a mesma
chave, então o CMS não tem como saber se um arquivo não está em uso. Objetos aos quais nenhuma linha aponta permanecem
no bucket e são cobrados até que você os exclua pelo navegador de armazenamento do
Studio, com `client.storage.deleteObject(key)` ou com uma regra de ciclo de vida no
bucket. `rebase storage orphans` lista os arquivos não referenciados por nenhuma linha e os
exclui com `--delete`; consulte [a CLI](/docs/cli/#rebase-storage).

## Movendo uma coluna para outro bucket

<span class="since-badge" data-since="0.31">Desde 0.31</span>

Um campo de arquivo armazena a chave do objeto, não seu bucket. Alterar o `source`
de uma coluna aponta todos os valores existentes para o novo bucket, onde essas chaves não
existem, fazendo com que as pré-visualizações de arquivos mais antigos retornem "não encontrado". Copie primeiro os objetos para o
novo bucket mantendo as mesmas chaves, com
`rebase storage move --from <old> --to <new> --prefix <path>` ou com as ferramentas do
próprio provedor, como `aws s3 sync` ou `gcloud storage cp`, ou mantenha o bucket antigo
para os arquivos existentes.
