Um campo de arquivo é uma propriedade **string** comum com um bloco `storage`. A
coluna armazena texto — a chave do objeto no bucket, ou sua URL se você solicitar
isso — e o bloco especifica para onde os bytes vão e o que o formulário aceitará.

Essa divisão importa mais do que parece. A maior parte do `storage` é lida pelo
uploader do painel administrativo no caminho para a API, portanto, uma gravação que
não venha de um formulário não passa por ele — essas opções trazem a etiqueta abaixo.
As duas que decidem o que um arquivo pode *ser*, `maxSize` e `acceptedFiles`, são a
exceção: o servidor as verifica em cada upload para o `storagePath` da propriedade.

## Um arquivo

```typescript
avatar: {
    type: "string",
    name: "Main image",
    storage: {
        storagePath: "avatars",
        acceptedFiles: ["image/*"],
        maxSize: 2 * 1024 * 1024
    }
}
```

## Vários arquivos

Um array da mesma coisa. O bloco `storage` vai para `of`, pois descreve
cada elemento em vez da lista:

```typescript
images: {
    type: "array",
    name: "Images",
    of: {
        type: "string",
        storage: { storagePath: "images", acceptedFiles: ["image/*"] }
    }
}
```

## Opções de storage

Tudo dentro de `storage`.

| Propriedade | Tipo | Descrição |
|-------------|------|-----------|
| `storagePath` | `string \| function` | **Obrigatório.** Onde o arquivo vai no bucket. Uma string com marcadores — `{file}`, `{file.name}`, `{file.ext}`, `{rand}`, `{id}` (o id do registro; `{entityId}` é lido da mesma forma), `{propertyKey}`, `{path}` — ou uma função do contexto de upload, que nomeia o id do registro como `id`. **Apenas no formulário do admin — não imposto pela API ou pelo banco de dados:** é o uploader do painel que o resolve, e `client.storage.upload()` define sua própria chave. Um caminho em string também é onde o servidor aplica `maxSize` e `acceptedFiles` desta propriedade a cada upload |
| `fileName` | `string \| function` | O nome de arquivo do objeto enviado, com os mesmos marcadores. **Apenas no formulário do admin — não imposto pela API ou pelo banco de dados.** |
| `storageSource` | `string` | Qual bucket registrado usar, quando um projeto tem mais de um. O identificador `bucket("media")` também funciona aqui |
| `public` | `boolean` | Armazena sob o prefixo público e disponibiliza através de uma URL estável, sem token e com suporte a cache. `false` por padrão, o que significa objetos privados e URLs assinadas de curta duração |
| `acceptedFiles` | `FileType[]` | Tipos MIME que esta propriedade aceita. O formato com asterisco funciona — `image/*`. **Imposto pelo servidor** para cada upload no `storagePath` da propriedade — consulte [O que o servidor verifica](#o-que-o-servidor-verifica) |
| `maxSize` | `number` | Maior arquivo aceito, em bytes. **Imposto pelo servidor**, assim como `acceptedFiles`, tanto no fluxo de upload comum quanto no retomável |
| `metadata` | `Record<string, unknown>` | Metadados do objeto para armazenar junto com o arquivo |
| `includeBucketUrl` | `boolean` | Grava `s3://my-bucket/path/to/file.png` na coluna em vez de `path/to/file.png`. `false` por padrão |
| `storeUrl` | `boolean` | Grava a URL de download na coluna em vez da chave. `false` por padrão, e vale a pena manter assim: uma URL que carrega um token deixa de funcionar quando o token expira, e a referência original é perdida |
| `imageResize` | `ImageResize` | Redimensiona e corta antes do upload, para `image/jpeg`, `image/png` e `image/webp`. **Apenas no formulário do admin — não imposto pela API ou pelo banco de dados.** |
| `processFile` | `(file: File) => Promise<File>` | Transforma o arquivo antes de ser enviado. Executa no navegador. **Apenas no formulário do admin — não imposto pela API ou pelo banco de dados.** |
| `postProcess` | `(pathOrUrl: string) => Promise<string>` | Transforma o caminho ou URL resolvido antes de ser salvo. Executa no navegador. **Apenas no formulário do admin — não imposto pela API ou pelo banco de dados.** |
| `previewUrl` | `(fileName: string) => string` | Gera a URL de pré-visualização, para quando o endereço real do arquivo não for o valor do campo. **Apenas no formulário do admin — não imposto pela API ou pelo banco de dados.** |

### Redimensionamento

`imageResize` aceita `maxWidth` e `maxHeight` em pixels, um `mode` de
`"contain"` (reduzir proporcionalmente para caber, o padrão) ou `"cover"` (preencher os
limites e cortar), um `format` de `"original"`, `"jpeg"`, `"png"` ou `"webp"`, e uma
`quality` entre 0 e 100 para os formatos com perdas (lossy) — 80 por padrão. O processamento
ocorre no navegador, antes que os bytes sejam enviados, portanto, um upload que não tenha
vindo do painel será armazenado em seu tamanho original.

### O que o servidor verifica

`maxSize` e `acceptedFiles` costumavam ser impostos por exatamente uma coisa: o
navegador. A rota de upload conhecia um único limite global de tamanho e nada sobre
a propriedade à qual o arquivo se destinava; assim, um `curl -F file=@payload.exe`
que burlasse o seletor colocava um executável de 40 MB no bucket de avatares e a
configuração que dizia o contrário nunca era consultada.

Ambos agora são verificados pelo servidor com base em **onde o arquivo é gravado**. Na
versão 0.23, eles são verificados apenas em relação à propriedade informada pelo upload, e
um upload que não informa nenhuma fica sujeito unicamente ao limite da própria fonte. O
`storagePath` de uma propriedade é para onde seus arquivos vão, portanto, é também onde
seus limites são aplicados: todo upload cuja chave for um arquivo diretamente sob esse
caminho — vindo do painel, de `client.storage.putObject`, de um upload retomável, do
navegador de storage do Studio ou via `curl` — estará sujeito a eles, quer informe a
propriedade ou não, na própria fonte de storage da propriedade. Os marcadores correspondem
ao que o painel preencheria: `{id}`, `{rand}`, `{file}` e afins representam um único
segmento de caminho, `{path}` qualquer quantidade de segmentos. O caminho de uma propriedade
com `public: true` fica sob `public/`.

- Várias propriedades compartilhando um caminho: se uma delas aceitar o arquivo, ele é aceito.
- Um upload que também informa sua propriedade (`collection` + `property`, conforme
  enviados por `putObject({ context })`) fica sujeito a essa propriedade também. Indicar uma
  propriedade mais flexível não desbloqueia o caminho de uma mais restritiva.
  Os uploads do painel (campos de arquivo, células de tabela e imagens em markdown) sempre a
  informam.
- Um `storagePath` definido como função não pode ser lido sem executá-lo, portanto
  não possui regra no lado do servidor: esses limites se aplicam apenas a uploads que
  informam a propriedade, o que os uploads do painel fazem.
- Um caminho que nenhuma propriedade reivindica fica sujeito apenas ao limite da própria
  fonte (`STORAGE_MAX_FILE_SIZE`).

### Imagens em um campo markdown

Uma propriedade markdown (`admin.markdown: true`) com um bloco `storage` aceita
uploads de imagens em seu editor. O texto armazena cada imagem como uma **referência de storage** —
`![](rebase-storage:posts/abc_cover.png)` — e não como uma URL: a URL de um arquivo
privado carrega um token de download que expira em minutos, e o texto é salvo. O editor
e as pré-visualizações do painel administrativo substituem cada referência por uma URL
nova ao exibi-la; um site que renderiza o campo faz o mesmo com
`resolveStorageReferences(text, client)` — consulte
[Arquivos dentro de texto](/docs/sdk/storage#files-inside-text).

Textos salvos antes da existência das referências contêm as próprias URLs de download, com
tokens expirados. O editor, as pré-visualizações e o `resolveStorageReferences` as renovam
ao exibir o texto, pois o token ainda identifica seu objeto; reinserir a imagem ou
reescrever o texto com `storageReferencesForDownloadUrls(text)` armazena uma referência.

### Para onde o arquivo tem permissão de ir

`storagePath` é um padrão, não um limite restritivo: nada no servidor confina um
upload a esse prefixo. Decidir quem pode gravar onde é a finalidade de uma
regra de autorização de storage — consulte [Storage](/docs/backend/storage).

### Arquivos nunca são excluídos automaticamente

Limpar um campo de arquivo, substituir seu arquivo ou excluir a linha à qual ele
pertence mantém o objeto armazenado onde está. Cada upload recebe uma chave própria,
de modo que uma substituição grava um novo objeto em vez de sobrescrever o antigo, e
nada remove o anterior: duas linhas podem conter a mesma chave, logo o painel não tem
como saber se um arquivo não está sendo utilizado. Objetos aos quais nenhuma linha faz
referência permanecem no bucket, e são faturados, até que você os exclua — pelo navegador
de storage do Studio, com `client.storage.deleteObject(key)` ou por meio de uma regra de
ciclo de vida no bucket. O comando `rebase storage orphans` lista os arquivos aos quais
nenhuma linha faz referência e os exclui com `--delete` — consulte [a CLI](/docs/cli/#rebase-storage).

### Movendo uma propriedade para outra fonte de storage

Um campo de arquivo armazena a chave do objeto, não sua fonte. Alterar o
`storageSource` de uma propriedade faz com que todos os valores existentes apontem para
a nova fonte, onde essas chaves não existem; assim, as pré-visualizações de arquivos
enviados antes da alteração responderão com "não encontrado". Copie os objetos para a
nova fonte com as mesmas chaves antes de alterar a propriedade — `rebase storage move
--from <old> --to <new> --prefix <storagePath>`, ou use as ferramentas do próprio provedor,
como `aws s3 sync` ou `gcloud storage cp` — ou mantenha a fonte antiga para os arquivos
existentes.
