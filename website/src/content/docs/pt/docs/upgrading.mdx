# Atualizando um aplicativo existente

Treze saltos, do mais recente ao mais antigo. Comece pelo que estiver logo acima da versão em que você está e siga para baixo — ou, se você estiver vindo da 0.12, comece de baixo e suba.

| Você está em | Leia | O que isso afeta |
|---|---|---|
| **0.30** | [0.30 → 0.31](/docs/upgrading/0-30-to-0-31/) | Tabelas em `backend/schema` (`defineTable`) substituem `config/collections`, e não há pacote de configuração: execute `rebase migrate collections-to-tables`, que move o projeto e comprova que o SQL gerado não foi alterado. O painel de administração renderiza as tabelas fornecidas pelo servidor, customizadas a partir de `frontend/src/cms`; o SDK passa a usar `data.table(slug)` e `tables: tablesDictionary`; os bundles são de formato 3, portanto, recompile antes de implantar; o suporte ao MongoDB foi descontinuado. |
| **0.29** | [0.29 → 0.30](/docs/upgrading/0-29-to-0-30/) | Um backend inicializado com `initializeRebaseBackend` mantém o token de atualização em um cookie, a menos que defina `cookieAuth: false`, portanto, um chamador que o lê do corpo sem `x-rebase-auth-flow: json` recebe `""`. |
| **0.27 – 0.28** | [0.27 → 0.29](/docs/upgrading/0-27-to-0-29/) | Tudo o que o admin passa para o seu código é a linha do servidor acompanhada de seu id: o `context.data` e os `browserCallbacks` do navegador passam strings ISO e chaves estrangeiras onde antes passavam `Date`s e objetos de relação, o que nenhum compilador detecta; os hooks de dados de `Entity` tornam-se internos; e callbacks, painéis, o painel lateral e a seleção recebem `row` e `id` em vez de `entity` e `entityId`. A versão 0.28 não declara nenhuma alteração de quebra, portanto este é um salto a partir da 0.27. |
| **0.26** | [0.26 → 0.27](/docs/upgrading/0-26-to-0-27/) | Um agendamento de cron que restringe ambos os campos de dia é executado em qualquer um deles, portanto executa com mais frequência, e um agendamento com um número malformado é recusado, fazendo com que esse job pare de rodar. Uma chave cuja estratégia `isId` não puder ser atendida pelo seu tipo impede a inicialização. No Rebase Cloud, um deploy ou preview falha quando um arquivo de função ou cron não carrega. |
| **0.25** | [0.25 → 0.26](/docs/upgrading/0-25-to-0-26/) | Uma escrita nomeando uma relação `via` de múltiplos saltos, um nome de perfil (role) que não seja um único perfil, um token de página do local storage anterior à atualização e um upstream de funções que não possa operar são recusados. O login OAuth consolida uma conta não verificada em vez de retornar `local-account-unverified`, o servidor MCP não envia mais `REBASE_TOKEN` para o aplicativo, e os tipos gerados removem a chave de um belongsTo com `excludeFromApi`. No Rebase Cloud, `rebase cloud webhooks` e `--scale-to-zero true` foram descontinuados, e tokens mais antigos podem precisar ser recriados. |
| **0.24** | [0.24 → 0.25](/docs/upgrading/0-24-to-0-25/) | `?count=` em uma listagem REST passa a ser o alternador para a contagem em `meta.total`, de modo que um filtro em uma coluna chamada `count` deve ir dentro de `?where=`; o `list_collections` do MCP remoto envia sua listagem apenas no bloco de texto, sem `structuredContent`; e o `@rebasepro/app` não exporta mais a tabela de tradução em espanhol `es`. Uma requisição simples de `OPTIONS` para uma rota sem manipulador, nomes de tabela em conflito na inicialização, um upsert na coleção de usuários, `page` com `offset`, uma string vazia em um campo obrigatório e a senha de um administrador que viole a política de senhas são recusados. As sessões duram 30 dias de inatividade por padrão, `client.cron` chama `/api/admin/cron`, leituras offline que não puderem ser respondidas integralmente falham com `OFFLINE`, e algumas exportações internas e propriedades não utilizadas foram removidas. |
| **0.23** | [0.23 → 0.24](/docs/upgrading/0-23-to-0-24/) | O SQL que `db push` e `db generate` renderizam é movido de `drizzle/` para o diretório não comitado `.rebase/sql/`, a flag `--generate` do `rebase dev` foi removida porque o `dev` sempre regenera os tipos do SDK, e uma edição de esquema em tempo real não comita nenhum SQL. Permissões tornam-se escopos: interfaces de administração solicitam um escopo em vez da role de admin, chaves de API mantêm escopos em vez de uma lista de permissões e uma flag `admin`, e `schema-admin` não é mais um administrador. Um caminho relativo em `--collections` é lido a partir de onde o comando é executado, um upsert em uma linha excluída e uma atualização que altera uma chave são recusados, o endpoint remoto do MCP aceita os argumentos do SDK, e sockets realtime abertos, links de verificação de e-mail, `signUp` e códigos de recuperação de MFA mudam a forma como tratam uma sessão. |
| **0.21 – 0.22** | [0.21 → 0.23](/docs/upgrading/0-21-to-0-23/) | Uma chave de API em um caminho aninhado requer `read` em seus ancestrais, variáveis numéricas ilegíveis e tempos de vida de sessão inválidos impedem a inicialização, um repositório de autenticação personalizado requer `unlinkUserIdentity`, e upgrades de convidados exigem o captcha de `register`. A versão 0.22 não declara nenhuma alteração de quebra, portanto este é um salto a partir da 0.21. |
| **0.18 – 0.20** | [0.18 → 0.21](/docs/upgrading/0-18-to-0-21/) | `context.client.data` deixa de compilar em um callback de coleção — faça consultas através de `context.data` — e `selectedEntities` dá lugar a uma seleção que pode representar linhas que ninguém carregou. As versões 0.19 e 0.20 não declaram alterações de quebra, portanto este é um salto a partir da 0.18. |
| **0.17** | [0.17 → 0.18](/docs/upgrading/0-17-to-0-18/) | Onze alterações de quebra, a maioria erros de compilação em vez de mudanças silenciosas de comportamento. `rebase.data` desaparece em tempo de execução, os intervalos de dependências de pares se restringem a circunflexos (carets), e a versão mínima do Node passa para 22.22.0. |
| **0.14 – 0.16** | [0.14 → 0.17](/docs/upgrading/0-14-to-0-17/) | Os pacotes de administração foram renomeados, recursos são declarados em vez de configurados, e um bundle compilado anteriormente não inicializará em um runtime atual. As versões 0.15 e 0.16 não quebram nada, portanto este é um salto a partir da 0.14. |
| **0.13** | [0.13 → 0.14](/docs/upgrading/0-13-to-0-14/) | Todas as chaves de transmissão (wire) passam a ser em camelCase, e o login anônimo passa a ser opt-in. |
| **0.12** | [0.12 → 0.13](/docs/upgrading/0-12-to-0-13/) | O maior salto, e o único que altera **quem pode ler seus dados**. Ele remove o esquema `auth`, renomeia pacotes, altera o significado de `id`, remove o suporte a CJS, migra o painel de administração para o react-router 8 e corrige três maneiras pelas quais o acesso poderia ser concedido sem que você tivesse solicitado. |

As seções de cada página estão na ordem em que você deve executá-las, e cada uma indica o sintoma que, de outra forma, você depuraria pela ponta errada.

Em seguida, independentemente do salto realizado:

- [A lista de verificação de atualização](#upgrade-checklist) abaixo — os greps e comandos que valem a pena executar depois, reunidos em um único bloco.

## Upgrade checklist

```
[ ] grep for authenticated() and (auth|rebase).uid() IS NOT NULL in config/collections/
[ ] decide the intent of each rule; rewrite the ones that meant "public"
[ ] replace not(authenticated()) with serverContext()
[ ] if realtime.requireAuth was true with an AuthAdapter, treat the socket as
    having been open — verify RLS on every subscribable collection (section 2)
[ ] SELECT ... FROM pg_policies — record the qual of every policy BEFORE
[ ] update package names and imports
[ ] grep for rebase.data — it is now rebase.dataAsAdmin (section 8)
[ ] grep for the other ten removed deprecated exports (section 8)
[ ] drop react-router-dom; import RouterProvider from "react-router/dom"
[ ] check node >= 22.22.0 and react >= 19.2.7 (react-router 8 requires both)
[ ] move defaultSecurityRules into config/collections/index.ts
[ ] grep for .userId
[ ] grep for row.id on tables not keyed on id
[ ] run db push
[ ] run rebase doctor --policies — expect no Insecure or Orphaned entries
[ ] SELECT ... FROM pg_policies again — confirm every intended change landed
[ ] exercise the app signed OUT, in a private window — watch the websocket too

--- 0.13 → 0.14 (part 2) ---
[ ] re-run rebase generate-sdk, then build — the compiler finds row.author_id
[ ] grep for snake_case where/orderBy keys; a stale one is a 400, not a warning
[ ] grep for raw fetch consumers reading row.<something>_id — these read
    undefined and raise nothing
[ ] if the project was introspected, re-run rebase schema introspect
[ ] decide anonymous sign-in: set auth.allowAnonymous: true, or confirm you
    never used it (grep for signInAnonymously)
[ ] drop @rebasepro/client-postgres from package.json

--- 0.14 → 0.17 (part 3) ---
[ ] rename @rebasepro/admin → @rebasepro/cms and admin-types → cms-types,
    and RebaseAdmin → RebaseCMS
[ ] move dataSources / storageSources out of the backend config into
    rebase.json and config/, then `rebase build` — an old bundle will not boot
[ ] grep collections for admin.titleProperty; it is refused at boot now
[ ] grep crons for ctx.client and for `userId` as an identity key
[ ] rename --legacy to --workspace wherever build/start is scripted
[ ] if you implement EmailService yourself, `send` must return a result

--- 0.30 → 0.31 ---
[ ] bump every @rebasepro package to 0.31 first, then pnpm install
[ ] rebase migrate collections-to-tables on a clean tree; read the manual steps
[ ] move config/index.ts `callbacks` to backend/hooks.ts by hand, if you had them
[ ] rebase generate-sdk; rebase db push --dry-run plans no change
[ ] run the git rm line the codemod printed (your own config/ modules may stay)
[ ] send a to-one relation as its key, not { id } — that is a 400 now
[ ] call /api/docs signed in, or set REBASE_ENABLE_SWAGGER=true to publish it
[ ] rename the MCP tools in prompts and allow-lists (list_tables, query_table, …)
[ ] rebuild the bundle and deploy — a format-2 bundle is refused
```

`rebase doctor --policies` é o comando a ser integrado ao CI: ele encerra com status diferente de zero caso uma política ainda contenha a tautologia permissiva ou tenha sido substituída por um push anterior. As consultas a `pg_policies` antes e depois ainda valem o minuto gasto — elas exibem as próprias expressões, que é a única maneira de identificar uma política aberta por padrão (fail-open) escrita de uma forma que o detector não consiga reconhecer. Nem os pacotes nem o sistema de tipos avisarão você: a alteração reside no banco de dados, e o `db push` é a única coisa que a coloca lá.

## Revertendo uma versão

Antes de reverter para uma versão anterior àquela que introduziu os companions de solicitação de admin (consulte o [changelog](/docs/changelog/)), torne-os inertes. Um runtime mais antigo nunca remove um companion, de modo que uma regra alterada após a reversão continuaria admitindo qualquer administrador em qualquer linha. Execute `REVOKE rebase_admin_request FROM rebase_user_admin;` uma vez por role de solicitação de admin, ou remova as políticas `_ar_`. [Leituras de admin usam os índices do proprietário](/docs/deployment/existing-database/#admin-reads-use-the-owners-indexes) explica esse funcionamento.
