# Atualizando de 0.24 → 0.25

Estas são as entradas `### Breaking` que a 0.25 traz para um app na 0.24.

As três primeiras vêm com o trabalho de desempenho: a chave de contagem nas listas REST,
a listagem de coleções do MCP e as traduções do admin. O restante vem da
varredura do backlog: recusas mais rígidas na inicialização e em `OPTIONS`, o caminho de cron do SDK
e as leituras offline, o registro de fontes de storage, props não usadas do kit de UI, o
upsert na coleção de usuários, uma leitura que nomeia `page` e `offset` ao mesmo tempo, e os nomes de
policies padrão em tabelas com nome longo. As três últimas são decisões de produto: a duração padrão
da sessão, a política de senha sobre a senha escolhida por um administrador e
uma string vazia em um campo obrigatório. Seguem três remoções: duas exportações do cliente que
eram apenas engines, um hook do admin de que nada precisa e uma opção de storage que
não chegava a nenhum cliente.

:::note[Comportamento alterado e nomes obsoletos]
A 0.25 também muda o que algumas chamadas existentes fazem, sem quebrá-las.
Confira estas se o seu app depende do comportamento antigo:

- **Os wrappers de campo dos plugins se compõem.** O `fieldBuilder.wrap` de todo plugin é renderizado,
  cada um em volta do campo que os plugins anteriores deixaram, em vez de apenas o último.
- **As substituições de componentes se compõem.** A substituição `wrap: true` de uma coleção recebe
  a substituição do app para o mesmo componente como `OriginalComponent`, e não o
  componente integrado.
- **`rebase.auth`, `rebase.admin`, `rebase.functions` e `rebase.cron` no
  servidor alcançam as rotas do backend em processo,** então o middleware que você adicionou ao
  seu próprio app Hono não roda mais nelas.
- **O socket de tempo real atende apenas o seu próprio caminho** (`/` para uma API em `/api`).
  Um cliente que discava outro caminho no mesmo servidor recebe um 404, ou o seu próprio
  listener de `upgrade`.
- **O socket recebe o token como o HTTP,** então `client.setAuthTokenGetter()`
  agora o autentica, e depois de um logout ele não recorre mais à opção
  `token`.

Estes nomes ainda funcionam, avisam uma vez em tempo de execução e têm um substituto:

| Obsoleto | Use |
|---|---|
| `loadFunctionsFromDirectory`, `loadFunctionsWithDiagnostics` | `loadFunctions(dir, { onSkip })` |
| `loadCronJobsFromDirectory`, `loadCronJobsWithDiagnostics` | `loadCrons(dir, { onSkip })`, depois `declareCrons(crons)` onde o par antigo os declarava |
| `client.ws.setAuthTokenGetter()` | `client.setAuthTokenGetter()` |
| `hooks.modifyCollectionAsync` de plugin (nunca chamado) | `hooks.modifyCollection`, com os dados buscados antes de o `<Rebase>` renderizar |
| `lifecycle.onCollectionChange` de plugin (nunca chamado) | `context.data.collection(slug).listen(…)` a partir de `lifecycle.onMount` |
| `DatabaseAdapter.mountRoutes`, `BackendBootstrapper.mountRoutes` (nunca chamados) | uma factory de rotas que o seu app monta |
:::

## 68. Um filtro em uma coluna chamada `count` vai dentro de `?where=`

`?count=` em uma lista REST agora é a chave da contagem por trás de `meta.total`:
`?count=none` a pula e `?count=exact` é o padrão. Qualquer outro valor é
recusado com `400 INVALID_COUNT`. Antes, `?count=5` filtrava as linhas cuja
coluna `count` era 5.

**O que alterar:** nada com o SDK, que já envia um filtro em uma
coluna chamada `count` dentro de `?where=`. Uma chamada REST escrita à mão que filtra em
tal coluna move o filtro para lá:

```diff lang="http"
- GET /api/data/products?count=5
+ GET /api/data/products?where={"count":["==",5]}
```

**Um SDK novo contra um servidor antigo:** `iterate()` e `findAll()` enviam
`?count=none` em cada página, e `find({ count: "none" })` também. Um servidor
0.24 o lê como um filtro em uma coluna chamada `count`. Onde a coleção não tem
tal coluna, ele responde `400 UNKNOWN_FILTER_FIELD`, e o SDK envia a leitura
de novo sem ele. Onde a coleção tem uma coluna **de texto** chamada `count`, o
servidor antigo filtra, em vez disso, as linhas cujo `count` é `'none'`, sem erro:
a página volta curta ou vazia e uma varredura termina antes da hora. Atualize o servidor
antes do SDK quando uma coleção tiver tal coluna.

Veja [Pulando a contagem](/docs/backend/api/#skipping-the-count).

## 69. O `list_collections` do MCP remoto não tem `structuredContent`

O `list_collections` enviava sua listagem duas vezes: formatada no bloco de texto e
de novo como `structuredContent`. Em um projeto grande, as duas juntas eram mais do que
o contexto de um modelo. Agora ele envia a listagem uma vez, no bloco de texto, como JSON
compacto. As outras ferramentas mantêm o seu `structuredContent`.

**O que alterar:** nada para um assistente, que lê o texto. Um programa
que lia a listagem de `structuredContent` passa a analisar o bloco de texto;
o conteúdo é o mesmo. Veja [O endpoint remoto](/docs/ai/mcp/#the-remote-endpoint).

## 70. `@rebasepro/app` não exporta mais `es`

A entrada do pacote reexportava a tabela de tradução em espanhol, `es`, o que colocava
as strings em espanhol em todo bundle construído a partir dele. As traduções que não são inglês
agora são buscadas quando um usuário escolhe o idioma, e `es` não é mais
exportado. `en` ainda é.

**O que alterar:** nada, a menos que você importasse `es`. Para mudar as strings do admin,
passe substituições para `<Rebase translations={…}>`; para fixar o idioma,
passe `locale`.

```bash
grep -rnE "import \{[^}]*\bes\b[^}]*\} from \"@rebasepro/app\"" --exclude-dir=node_modules .
```

## 71. Um `OPTIONS` simples para uma rota sem handler é um 404

O middleware de CORS costumava responder a toda requisição `OPTIONS` por conta própria, com um
`204` vazio. Agora ele responde apenas a preflights de CORS (um `OPTIONS` com
`Access-Control-Request-Method`); qualquer outro `OPTIONS` chega à sua rota. Uma rota
sem handler de `OPTIONS` responde `404`. `OPTIONS /api/storage/tus` agora retorna
as capacidades do TUS (`Tus-Version`, `Tus-Extension`, `Tus-Max-Size`), como a
documentação sempre disse.

**Quem é afetado:** um cliente, proxy ou health check que sondava uma rota com
`OPTIONS` e lia o `204` como "ela existe". Os preflights dos navegadores
não mudam.

**O que alterar:** sonde com o método real da rota (`HEAD` ou `GET`).

## 72. Nomes em colisão são recusados na inicialização, com o motivo

Uma tabela, tabela de junção ou tipo enum cujos nomes são iguais após o truncamento de
63 bytes do Postgres costumava falhar no `db push` com "already exists". Duas
propriedades que resolvem para a mesma coluna (`myTitle` e `my_title`), e um
`target` de relação escrito como string (`target: "authors"`), falhavam mais tarde ou de forma
confusa. Cada um agora é recusado quando a configuração carrega, e a mensagem
diz o que renomear ou escrever.

**Quem é afetado:** um projeto que declara tal par. Ele também não conseguia concluir
`db push` antes, então isso apenas antecipa a falha.

**O que alterar:** renomeie um dos nomes em colisão e escreva o alvo de uma relação
como a coleção, não como o seu slug:

```diff
- relation: { kind: "belongsTo", target: "authors" },
+ relation: { kind: "belongsTo", target: () => authors },
```

## 73. `client.cron` chama `/api/admin/cron`

O cliente de cron do SDK usava como padrão `/api/cron`, o alias obsoleto. Agora ele
chama `/api/admin/cron`, onde vive toda superfície de admin.

**Quem é afetado:** um servidor (ou uma regra de proxy) que serve apenas o caminho antigo.
As chamadas de cron do SDK respondem `404` contra ele.

**O que alterar:** atualize o servidor junto com o SDK, ou mantenha o caminho antigo
explicitamente:

```ts
const client = createRebaseClient({ baseUrl, cron: { cronPath: "/api/cron" } });
```

## 74. Leituras offline que não podem ser respondidas por completo falham com `OFFLINE`

Enquanto offline, `findAll()` e `iterate()` retornavam a parte da coleção
que este dispositivo tinha em cache como se fosse toda ela, e `count()` contava as linhas
em cache. Uma página que este dispositivo nunca buscou agora falha com `OFFLINE`, e o mesmo ocorre com um
`count()` sem contagem do servidor em cache.

**Quem é afetado:** um app que mostra essas leituras offline.

**O que alterar:** capture o erro onde o app desenhava resultados parciais e
mostre o que tem com uma observação, ou peça uma página que o dispositivo já possui.

```ts
let rows;
try {
  rows = await client.data.posts.findAll();
} catch (e) {
  if (e instanceof RebaseApiError && e.code === "OFFLINE") rows = cached;
  else throw e;
}
```

## 75. `getOrDefault(key)` lança um erro para uma fonte de storage não registrada

`ClientStorageSourceRegistry.getOrDefault(key)` retornava a fonte padrão para
uma chave que não conhecia, então uma propriedade que nomeava uma fonte que o painel ainda não tinha
carregado enviava para o bucket padrão. Agora ele lança um erro.

**Quem é afetado:** código que chama `getOrDefault` com uma chave que não
registrou. O próprio admin não faz mais isso.

**O que alterar:** registre a fonte primeiro, ou use `get(key)`, que retorna
`undefined` para uma chave desconhecida, onde uma fonte ausente é esperada.

## 76. `TextField.maxRows` e seis props de `MultiSelect` foram removidos

`TextField` declarava `maxRows`, e `MultiSelect` declarava `onChange`, `name`,
`position`, `endAdornment`, `multiple` e `padding`. Nenhuma jamais foi lida, então
passar uma não fazia nada. Elas foram removidas dos tipos, e passar uma agora é
um erro de tipo.

**Quem é afetado:** código que passava uma delas. Nada muda em tempo de execução.

**O que alterar:** exclua a prop. Para as mudanças de um multi-select, use
`onValueChange`.

## 77. Um upsert na coleção de usuários é recusado

A coleção de usuários (a que tem `auth` habilitado) agora responde um 400
`INVALID_CONFLICT_TARGET` a um upsert, em toda porta: `?on_conflict=`, `/bulk`
com `upsert: true`, uma operação `upsert` de `_batch`, `upsert()` e
`createMany(…, { upsert: true })` do SDK, e o socket de tempo real. Um upsert só
descobre dentro da escrita se cria ou atualiza, então ele não aplicava nenhum dos
conjuntos de regras: sem hash de senha, normalização de e-mail, `onCreateUser` ou
convite em uma criação, e sem verificação do último administrador em uma atualização.

**Quem é afetado:** código que faz upsert de usuários, por exemplo uma sincronização que executava
`client.data.users.upsert(user, { onConflict: ["email"] })`.

**O que alterar:** procure o usuário e depois crie ou atualize.

```ts
const user = { email: "ada@example.com", displayName: "Ada" };
const { data: [found] } = await client.data.users.find({ where: { email: ["==", user.email] }, limit: 1 });
if (!found) await client.data.users.create(user);
else await client.data.users.update(String(found.id), user);
```

## 78. `page` com `offset` é recusado com `PAGE_WITH_OFFSET`

Uma leitura que nomeia `page` e `offset` ao mesmo tempo agora é recusada. O servidor responde
`400 PAGE_WITH_OFFSET`, e o SDK recusa o par antes de qualquer requisição, com um
`RebaseClientError` que carrega o mesmo código: por HTTP, em processo
(`rebase.data`) e offline. Antes, `page` vencia e o `offset` era descartado
sem uma palavra.

**Quem é afetado:** código que envia os dois, por exemplo um `find({ page, offset })`
ou uma chamada REST com `?page=3&offset=40`. Tal leitura já lia apenas
`page`.

**O que alterar:** envie um dos dois. Para manter o que a leitura retornava antes,
remova `offset`.

```diff lang="ts"
- await client.data.products.find({ page: 3, offset: 40, limit: 20 });
+ await client.data.products.find({ page: 3, limit: 20 });
```

## 79. Tabelas longas recebem novos nomes de policy de escrita do admin padrão

Em uma tabela cujo nome tem 42 bytes ou mais, as três policies padrão de escrita do admin
(`…_default_admin_write_insert`, `_update` e `_delete`) agora são chamadas
`<head>_<hash8>_<op>`, com no máximo 63 bytes. O Postgres guarda 63 bytes de um nome, então
os três nomes antigos eram cortados para o mesmo nome e só existia uma policy, a de
DELETE: os admins não conseguiam inserir nem atualizar.

**Quem é afetado:** um projeto com um nome de tabela de 42 bytes ou mais, e
qualquer coisa que se refira a essas policies pelo nome, como uma migration ou um script
que as remove. Os nomes antigos nunca existiram no banco de dados.

**O que alterar:** nada para o banco de dados. A próxima inicialização ou `rebase db push`
remove a policy truncada e cria uma policy por operação. Atualize qualquer
script que nomeie as policies antigas.

## 80. As sessões duram 30 dias de inatividade por padrão

A duração padrão do refresh token agora é de 30 dias em todo ponto de entrada. Um
servidor iniciado com o runtime `rebase-server` (ou `rebase start`) usava 400
dias sempre que `JWT_REFRESH_EXPIRES_IN` não estava definida; um
`initializeRebaseBackend` escrito à mão já usava 30.

A duração é deslizante: cada renovação emite um token válido por mais 30
dias, então um usuário que abre o app pelo menos uma vez por mês continua conectado. Um
usuário inativo por mais tempo entra de novo. Os tokens emitidos antes da atualização mantêm a
expiração com que foram emitidos até a próxima renovação.

**Quem é afetado:** uma implantação no runtime que nunca definiu
`JWT_REFRESH_EXPIRES_IN`, cujos usuários voltam menos de uma vez por mês.

**O que alterar:** nada, para adotar o novo padrão. Para manter o comportamento anterior,
defina-o explicitamente:

```bash
JWT_REFRESH_EXPIRES_IN=400d
```

ou `auth: { refreshExpiresIn: "400d" }` em um backend ejetado. Os navegadores limitam
o cookie de renovação a 400 dias, então um valor maior não adianta no modo cookie.

## 81. A senha escolhida por um administrador deve cumprir a política de senha

`POST /api/admin/users` e uma criação na coleção de usuários pela API de
dados (`POST /api/data/users`, `/bulk`, um batch, `create_document` do MCP, um salvamento
pelo socket) agora recusam uma `password` que não cumpre a política com `400 WEAK_PASSWORD`,
como o cadastro, as redefinições e `PUT /api/admin/users/:uid` já faziam. Nada
é escrito e nenhum hook de criação é executado. Em um `/bulk`, a mensagem começa com
`Row <n>: `, como os outros erros de linha do bulk. Uma criação sem senha não
muda: uma senha é gerada, ou um convite é enviado.

**Quem é afetado:** código que cria usuários com uma senha escolhida em outro lugar,
como uma importação ou uma sincronização de outro sistema.

**O que alterar:** para importar contas cujas senhas foram definidas em outro lugar, envie
`skipPasswordPolicy: true` no corpo de cada criação (em cada linha de um `/bulk`), como
administrador ou com a chave de serviço:

```ts
await client.admin.createUser({ email, password: legacyPassword, skipPasswordPolicy: true });
```

De qualquer outro chamador, a opção não dispensa nada. Ela nunca é armazenada e nunca
chega a `onCreateUser` ou `onAdminCreateUser`. A importação do painel de administração
a envia por você nas linhas que carregam uma `password`. Um `AuthAdapter` customizado recebe
a decisão como o novo terceiro argumento de `prepareUserCreation`
(`{ mayWaivePasswordPolicy }`); um adaptador que a ignora mantém o comportamento atual.
Para mudar a própria política, passe `auth.hooks.validatePasswordStrength`.

## 82. Uma string vazia em um campo string obrigatório é recusada

Uma escrita que envia `""` para uma propriedade `string` com `validation.required` agora
responde `400 VALIDATION_CONSTRAINT`, com uma entrada em `details.violations`
`{ field, code: "required" }`: a mesma resposta de um valor ausente. Isso vale
para criações e atualizações em toda porta (REST, bulk, batch, upsert, o socket de tempo real,
MCP), e mesmo quando a propriedade tem um `defaultValue`, já que um padrão
preenche uma chave ausente, não uma vazia. O painel de administração já escreve `null`
para um campo limpo, então não é afetado.

**Quem é afetado:** código que escreve `""` em um campo string obrigatório, por
exemplo um formulário ou uma importação que envia todas as colunas, preenchidas ou não.

**O que alterar:** envie um valor, omita a chave na criação quando um `defaultValue`
deva ser aplicado, ou remova `required` dos campos que podem legitimamente ficar vazios.
Coleções que declaram um `beforeSave` não são verificadas na fronteira (o
hook pode preencher o valor), como antes. O código de servidor que escreve em processo
(`rebase.data`) não é afetado.

## 83. `QueryBuilder` e `createBackups` não são mais exportados de `@rebasepro/client`

Ambos eram as engines por trás de chamadas do cliente.

- `new QueryBuilder(collection).where(…)` → `client.data.<collection>.where(…)`;
  os helpers `or`, `and`, `not` e `cond` continuam exportados.
- `createBackups(transport)` → `client.backups` (os mesmos `list`, `download`,
  `downloadUrl`, `stream`). `CreateBackupsOptions` saiu junto;
  `BackupStream` continua exportado.

`client.ws` não muda.

## 84. `useBackendStorageSource` foi removido de `@rebasepro/app`

```ts
// before
const storageSource = useBackendStorageSource({ apiUrl, getAuthToken });
// after — the client you already pass to the admin
const storageSource = client.storage;                     // default source
const media = client.createStorageSource("media");        // a named source
```

A fonte do cliente também envia `public` e `context` nos uploads (limites da propriedade
verificados no servidor) e `storageId` para fontes nomeadas, o que o hook
não fazia.

## 85. `signedUrlExpiration` foi removido da configuração de storage S3 e GCS

Exclua a chave de `storage: { type: "s3" | "gcs", … }`; o TypeScript a reporta
como propriedade desconhecida. Ela nunca definiu a duração de uma URL que um navegador recebia.
Para mudar por quanto tempo a URL de um arquivo privado funciona, defina `storageDownloadTokenTtl`
(segundos; `STORAGE_DOWNLOAD_TOKEN_TTL` em uma implantação de bundle). O código de servidor que
chama `controller.getSignedUrl()` diretamente recebe uma URL válida por uma hora.
