Cada fallo que devuelve un backend de Rebase utiliza un único envoltorio y contiene un `code` estable. El código es el elemento sobre el que bifurcar la lógica: el mensaje está escrito para una persona y puede cambiar de redacción, el estado se comparte entre una docena de problemas diferentes, y el código no sufre ninguno de estos inconvenientes.

## El envoltorio

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — legible por humanos. Para un `4xx`, es el mensaje propio del servidor; para un `5xx`, es deliberadamente genérico, ya que el texto subyacente puede citar un host, un rol o un nombre de columna.
- **`code`** — uno de los valores a continuación. Estable entre versiones menores.
- **`details`** — opcional y nunca garantizado. Consulta las reglas más abajo.
- **`requestId`** — presente siempre que la solicitud haya pasado por el middleware de ID de solicitud, lo que ocurre en cada ruta bajo `basePath`.

### `X-Request-ID`

Cada solicitud bajo `basePath` recibe un ID: el encabezado `X-Request-ID` del cliente cuando es un UUID; de lo contrario, uno nuevo. Se devuelve en la respuesta como `X-Request-ID`, se incluye en el envoltorio de error como `requestId` y se adjunta a la línea de registro (log) del servidor para esa solicitud.

Esa es la clave de unión. Cítala en un informe de error y un operador podrá encontrar la línea exacta del registro que explica el fallo, con el motivo que nunca se mostró al cliente.

Enviar el tuyo propio es la forma en que una traza sobrevive a un salto: una pasarela (gateway) o un ejecutor de tareas que reenvía el encabezado obtiene un único ID en cada servicio que procesó la solicitud. Un valor no válido se ignora en lugar de rechazarse —no vale la pena hacer fallar una solicitud por un encabezado mal formado de un cliente—, así que no asumas que el ID que enviaste es el ID que recibiste. Lee el encabezado de respuesta.

### Qué hay en `details`

`details` tiene fines de diagnóstico, no contractuales. Se rige por tres reglas:

1. **Todo lo que una ruta establece explícitamente se devuelve siempre.** Estos son los errores propios del cliente descritos con precisión: qué campo de filtro era desconocido, qué relación no es de escritura, qué valor no encajaba con su tipo.
2. **Los diagnósticos de la base de datos se recortan en producción.** Cuando el fallo proviene de Postgres, `details.dbCode` (el SQLSTATE) siempre está presente: nombra la clase del problema y no revela nada sobre los datos. `dbMessage`, `detail` e `hint` solo se agregan cuando `NODE_ENV` no es `production`, porque Postgres incluye en ellos el contenido de las filas. `23505` informa `Key (email)=(a@b.c) already exists.`, lo que respondería a "¿está registrada esta persona?" para cualquier dirección que cualquiera quiera probar.
3. **Nunca bifurques la lógica según `details`.** Hazlo según `code`. Lo que está bajo `details` es aquello que resultó útil para una persona en ese punto de llamada concreto, y cambia.

## Interpretar un estado

| Estado | Qué indica sobre la solicitud |
| --- | --- |
| `400` | Malformada, o solicita algo que no existe en el esquema. Corrige la solicitud. |
| `401` | No autenticado, o la credencial ha expirado. Inicia sesión o renueva el token. |
| `403` | Autenticado, pero no permitido. Reintentar con la misma identidad no servirá de nada. |
| `404` | No existe tal ruta, colección o fila — o se trata de una fila oculta por la seguridad a nivel de fila (RLS). |
| `409` | Conflicto con el estado existente: un duplicado o una escritura concurrente. |
| `413` `415` `422` | El cuerpo es demasiado grande, el tipo de medio es incorrecto o fue rechazado semánticamente. |
| `429` | Límite de tasa excedido (rate limited). Reduce la frecuencia; el mensaje indica por cuánto tiempo. |
| `500` | El error reside en el servidor o en su base de datos, no en el cliente. Revisa los registros. |
| `501` | La ruta existe, pero este despliegue no puede atenderla (una característica desactivada o no configurada). |
| `502` `503` `504` | Una dependencia no estaba disponible, no estaba configurada o fue demasiado lenta. |

## Datos, consultas y escrituras

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `AGGREGATE_MASKED_BY_AFTER_READ` | 400 | Una agregación distinta de `count()` sin `groupBy` en una colección donde un callback `afterRead` reescribe datos (global, colección o propiedad). ## `PG_<SQLSTATE>` — restricción rechazada por la base de datos

Una escritura que Postgres rechaza por una razón atribuible a *los datos del cliente* responde con el SQLSTATE en el código: `PG_23505`, `PG_23503`, etc. Se trata de una familia, no de una lista estática —Postgres define cientos de SQLSTATE—, pero solo dos clases llegan aquí, ya que solo esas dos son responsabilidad del cliente:

- **clase 23**, infracción de restricción de integridad: un duplicado, una clave foránea que apunta a nada, una columna NOT NULL dejada vacía;
- **clase 22**, excepción de datos: un valor que el tipo de columna no puede admitir.

Cualquier otra causa —una conexión caída, una columna faltante, un problema de privilegios— es problema del servidor y devuelve un `500`. Por tanto, `code.startsWith("PG_")` es una comprobación segura para "la fila que envié era incorrecta", y las cuatro a continuación son con las que un cliente suele toparse. `details.dbCode` lleva el mismo SQLSTATE para todas ellas, y el mensaje nombra la restricción.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Un valor no pudo interpretarse según el tipo de la columna — el equivalente de escritura para `INVALID_FILTER_VALUE`. | Envía un valor del tipo correspondiente a la columna. |
| `PG_23502` | 400 | Se dejó vacía una columna `NOT NULL`. | Envía el campo o asigna un valor por defecto a la columna. |
| `PG_23503` | 400 / 409 | Al guardar, una clave foránea apunta a una fila inexistente (400). Al eliminar, otras filas todavía referencian a esta (409; una clave `RESTRICT` genera `PG_23001`, también 409). | Crea la fila de destino primero o corrige el ID; para una eliminación, elimina o redirige las filas que la referencian antes. |
| `PG_23505` | 409 | Se violó una restricción de unicidad. El mensaje especifica la restricción. | Usa un valor diferente o actualiza la fila existente. |

| `SQL_EXPORT_UNSUPPORTED` | 501 | `POST /api/admin/sql/csv` no puede transmitir un resultado en este entorno: la base de datos de desarrollo en proceso (PGlite) tiene una sola conexión, y un cursor retenido durante una descarga bloquearía cualquier otra consulta posterior; o el origen de datos carece de cursor SQL. | Apunta `DATABASE_URL` a un Postgres propio (`rebase dev --docker` inicia uno), o agrega un `LIMIT` y exporta las filas visibles en pantalla. |

### Reconciliación de esquemas

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) planifica a través de `POST /api/admin/schema/reconcile/plan` y aplica mediante `/reconcile/apply`. Un rechazo no cambia nada; únicamente `SCHEMA_RECONCILE_FAILED` deja aplicada una parte del plan.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | El cuerpo no es un objeto JSON, o `drop` no es una lista de cadenas `"<collection>.<column>"`. | Envía `{ "drop": ["voice_cache.wav"] }` o prescinde de `drop`. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Una sentencia falló a mitad del proceso. Las sentencias anteriores se ejecutaron y permanecen aplicadas; `details.applied` las enumera. | Corrige lo que señale el mensaje y luego vuelve a planificar: el nuevo plan omitirá lo que ya se ejecutó. |
| `SCHEMA_RECONCILE_INVALID` | 400 | El plan no se puede aplicar y el mensaje lista las razones: un `drop` que no cumple con `<collection>.<column>`, que no nombra ninguna colección o columna, o que nombra una columna que la colección todavía declara. `details.plan` es el plan. | Corrige la lista `drop`. Una columna declarada se elimina quitando su propiedad, desplegando y luego reconciliando. |
| `SCHEMA_RECONCILE_STALE` | 409 | La base de datos o las colecciones cambiaron después del plan que confirmaste. `details.plan` contiene el nuevo plan. | Revisa el nuevo plan y confirma su `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | No se envió `confirm` a `/reconcile/apply`. | Planifica primero y envía el `digest` del plan como `confirm`. La CLI hace esto automáticamente cuando escribes `yes`. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | El driver de este backend no puede planificar una reconciliación o no puede ejecutar SQL. | La reconciliación funciona en Postgres. |

### Por qué no se puede fusionar la tabla de una rama

`BRANCH_MERGE_BLOCKED` nombra cada tabla que rechazó en `details.tables`, con uno de estos códigos. El mismo código aparece en el campo `blocked` de la tabla en el propio diff, de modo que Studio pueda indicarlo antes de que nadie presione **Merge**. Ninguno es una respuesta HTTP independiente.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Las columnas de la tabla difieren entre la rama y su padre. Las filas se comparan según las columnas que comparten. | Agrega las columnas faltantes al padre mediante tus migraciones (`rebase db push`) y luego fusiona. Una migración que reescriba la tabla (un cambio de tipo de columna) la convierte en `TABLE_REWRITTEN`: fusiona antes de tal cambio o vuelve a crear la rama después de él. |
| `NO_PRIMARY_KEY` | — | La tabla no tiene clave primaria, por lo que las filas no pueden emparejarse una por una; el diff solo muestra sus recuentos de filas. | Asigna una clave primaria a la tabla o traslada sus filas manualmente. |
| `PRIMARY_KEY_DIFFERS` | — | Las columnas de la clave primaria o sus tipos difieren entre ambas. | Aplica el esquema al padre primero. |
| `TABLE_ADDED` | — | La rama creó la tabla. Una fusión nunca crea tablas. | Créala en el padre mediante tus migraciones y luego fusiona sus filas. |
| `TABLE_DROPPED` | — | La rama eliminó la tabla. Una fusión nunca elimina tablas. | Elimínala mediante tus migraciones. |
| `TABLE_REWRITTEN` | — | Uno de los lados reescribió por completo cada fila de la tabla después de crearse la rama —un cambio de tipo de columna, un `ADD COLUMN` con valor por defecto volátil, `VACUUM FULL`, `CLUSTER`— por lo que todas las filas figuran como escritas posteriormente y ya no se puede determinar qué lado modificó cuál fila. | Fusiona la rama antes de realizar dicha migración, o créala de nuevo a partir del padre después de ella. |
| `TOO_LARGE` | — | La tabla contiene más filas en uno de los lados de las que un diff puede comparar una a una (100.000 por defecto, `maxRowsPerTable`). | Aumenta `maxRowsPerTable` tanto en el diff como en la fusión, o transfiere las filas por otro medio. |

## Códigos genéricos

Una ruta recurre a uno de estos códigos cuando no aplica ninguno más específico.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Solicitud malformada y no aplica nada más específico. | Consulta el mensaje. |
| `UNAUTHORIZED` | 401 | No autenticado o la credencial fue rechazada. | Inicia sesión o renueva el token. |
| `FORBIDDEN` | 403 | Autenticado, pero no autorizado. | Reintentar con la misma identidad no servirá. |
| `CONFLICT` | 409 | Conflicto con el estado actual. | Consulta el mensaje. |
| `INTERNAL_ERROR` | 500 | Ocurrió un fallo en el servidor. El mensaje es genérico a propósito. | Cita el `requestId`; el motivo figura en los registros. |
| `NOT_CONFIGURED` | 503 | Una dependencia requerida por esta ruta no está configurada en este servidor. | Consulta el mensaje. |
| `SERVICE_UNAVAILABLE` | 503 | No se pudo contactar con un servicio del que depende la solicitud: un bucket de S3 o MinIO, o un host al que una función hace `fetch()` que rechaza la conexión o no se resuelve. El registro del servidor especifica el host; la respuesta no. Una base de datos inalcanzable devuelve `DATABASE_UNAVAILABLE`. Una conexión fallida a dicho servicio responde esto; en 0.24 responde un `500` cuyo código es el error de socket (`ECONNREFUSED`), o `INTERNAL_ERROR`. | Reintenta; revisa los registros. |

## Mantenimiento de la exactitud de esta página

`pnpm verify:docs` falla si falta en estas tablas algún código que el servidor pueda emitir, si una tabla incluye un código que nada puede generar, si los estados de una fila no coinciden exactamente con los que el código fuente utiliza para emitirlo, o si una familia de códigos como `PG_<SQLSTATE>` carece de una fila para un SQLSTATE con el que los clientes puedan toparse. El script responsable es `tooling/scripts/docs-verify/check-error-codes.mjs`.

Se verifica a sí mismo primero. El análisis lee los códigos directamente desde TypeScript en lugar de hacerlo desde un servidor en ejecución, por lo que sus puntos ciegos son silenciosos por diseño: en una ocasión no detectó un código pasado a través de un wrapper de una sola línea, ni otro escrito después de un mensaje que contenía un `)`, reportando "todos los códigos que el servidor puede emitir están documentados" en una página a la que le faltaban diecisiete de ellos. Por ello, el script ejecuta una prueba con esas estructuras exactas antes de leer esta página y se niega a emitir cualquier informe si no es capaz de detectarlas.
