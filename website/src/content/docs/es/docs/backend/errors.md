Cada fallo devuelto por un backend de Rebase utiliza un único formato de sobre (envelope) y contiene un `code` estable. El código es el valor sobre el que se debe bifurcar la lógica: el mensaje está escrito para una persona y puede cambiar de redacción, el estado HTTP se comparte entre una docena de problemas distintos, y el código no se ve afectado por ninguno de estos factores.

## El sobre (envelope)

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — legible por humanos. Para un error `4xx`, es el propio mensaje del servidor; para un `5xx`, es deliberadamente genérico, ya que el texto subyacente puede incluir nombres de hosts, roles o columnas.
- **`code`** — uno de los valores detallados a continuación. Estable a lo largo de las versiones menores.
- **`details`** — opcional y nunca garantizado. Consulta las reglas a continuación.
- **`requestId`** — presente siempre que la solicitud haya pasado por el middleware de request-ID, lo cual aplica a cada ruta bajo `basePath`.

### `X-Request-ID`

Cada solicitud bajo `basePath` recibe un identificador: el encabezado `X-Request-ID` del cliente cuando es un UUID válido; de lo contrario, uno nuevo. Se devuelve en la respuesta como `X-Request-ID`, se incluye en el sobre de error como `requestId` y se adjunta a la línea de log del servidor correspondiente a esa solicitud.

Esa es la clave de unión. Si la incluyes en un reporte de error, un operador podrá localizar la línea exacta en los logs que explica el fallo, conteniendo el motivo que nunca se mostró al cliente.

Enviar tu propio ID es la manera de mantener la trazabilidad a través de saltos: una pasarela (gateway) o un ejecutor de trabajos que reenvía el encabezado mantiene un único ID en todos los servicios que procesaron la solicitud. Los valores no válidos se ignoran en lugar de rechazarse —no vale la pena hacer fallar una solicitud por un encabezado mal formado de un cliente—, por lo que no debes asumir que el ID enviado es el mismo que recibes. Lee el encabezado de respuesta.

### Qué hay en `details`

`details` tiene un propósito diagnóstico, no contractual. Se rige por tres reglas:

1. **Todo lo que una ruta establece explícitamente se devuelve siempre.** Se trata de los errores propios del cliente descritos con precisión: qué campo de filtro era desconocido, qué relación no admite escritura o qué valor no coincidía con su tipo.
2. **Los diagnósticos de la base de datos se recortan en producción.** Cuando el fallo proviene de Postgres, `details.dbCode` —el SQLSTATE— siempre está presente: identifica la clase de problema sin revelar nada sobre los datos. `dbMessage`, `detail` y `hint` solo se agregan cuando `NODE_ENV` no es `production`, ya que Postgres incluye contenidos de filas en ellos. `23505` reporta `Key (email)=(a@b.c) already exists.`, lo que respondería a "¿está registrada esta persona?" para cualquier dirección que alguien decida probar.
3. **Nunca bifurques tu lógica basándote en `details`.** Hazlo siempre en función de `code`. El contenido de `details` es aquello que resultó útil para una persona en ese punto de la llamada y está sujeto a cambios.

## Interpretar un estado

| Estado | Lo que indica sobre la solicitud |
| --- | --- |
| `400` | Malformada, o solicita algo que no existe en el esquema. Corrige la solicitud. |
| `401` | No autenticado, o la credencial ha expirado. Inicia sesión o renueva el token. |
| `403` | Autenticado, pero no autorizado. Reintentar con la misma identidad no servirá. |
| `404` | No existe dicha ruta, tabla o fila — o se trata de una fila que la seguridad a nivel de fila (RLS) oculta. |
| `409` | Un conflicto con el estado existente: un duplicado o una escritura concurrente. |
| `413` `415` `422` | El cuerpo es demasiado grande, el tipo de medio es incorrecto o fue rechazado semánticamente. |
| `429` | Límite de tasa excedido (rate limited). Reduce la frecuencia; el mensaje indica por cuánto tiempo. |
| `500` | El error reside en el servidor o en su base de datos, no en el cliente. Revisa los logs. |
| `501` | La ruta existe, pero este despliegue no puede atenderla — una característica desactivada o sin configurar. |
| `502` `503` `504` | Una dependencia no estuvo disponible, no estaba configurada o respondió demasiado lento. |

## `PG_<SQLSTATE>` — una restricción rechazada por la base de datos

Una escritura rechazada por Postgres debido a *los datos enviados por el cliente* responde incluyendo el SQLSTATE en el código: `PG_23505`, `PG_23503`, etc. Se trata de una familia de errores y no una lista cerrada —Postgres define cientos de SQLSTATEs—, pero únicamente dos clases llegan a manifestarse aquí, dado que solo estas dos corresponden a fallos imputables al cliente:

- **clase 23**, violación de restricción de integridad: un duplicado, una clave foránea que apunta a la nada, una columna NOT NULL vacía;
- **clase 22**, excepción de datos: un valor incompatible con el tipo de la columna.

Cualquier otra causa —caída de conexión, columna faltante, error de privilegios— es responsabilidad del servidor y devuelve un `500`. Por lo tanto, `code.startsWith("PG_")` es una validación confiable para comprobar si "la fila enviada era incorrecta", siendo las cuatro siguientes las que un cliente encontrará en la práctica. `details.dbCode` contiene el mismo SQLSTATE para todas ellas y el mensaje identifica la restricción afectada.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Un valor no se pudo interpretar como el tipo de la columna — el equivalente de escritura para `INVALID_FILTER_VALUE`. | Envía un valor compatible con el tipo de la columna. |
| `PG_23502` | 400 | Una columna `NOT NULL` se dejó vacía. | Envía el campo o asigna un valor por defecto a la columna. |
| `PG_23503` | 400 / 409 | Al guardar, una clave foránea apunta a una fila inexistente (400). Al eliminar, existen otras filas que aún referencian a esta (409; una clave `RESTRICT` genera `PG_23001`, también 409). | Crea la fila de destino primero o corrige el id; al eliminar, borra o reasigna antes las filas que la referencian. |
| `PG_23505` | 409 | Se violó una restricción de unicidad. El mensaje especifica la restricción. | Usa un valor diferente o actualiza la fila existente. |

### Conciliación de esquemas (Schema reconcile)

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) planifica mediante `POST /api/admin/schema/reconcile/plan` y aplica cambios con `/reconcile/apply`. Un rechazo no modifica nada; solo `SCHEMA_RECONCILE_FAILED` puede dejar un plan aplicado parcialmente.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | El cuerpo no es un objeto JSON o `drop` no es una lista de cadenas con formato `"<table>.<column>"`. | Envía `{ "drop": ["voice_cache.wav"] }` o prescinde de `drop`. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Una sentencia falló a mitad de ejecución. Las sentencias previas se ejecutaron y permanecen aplicadas; `details.applied` las lista. | Corrige lo que indica el mensaje y vuelve a planificar: el nuevo plan excluirá lo ya ejecutado. |
| `SCHEMA_RECONCILE_INVALID` | 400 | El plan no puede aplicarse y el mensaje explica los motivos: un `drop` sin formato `<table>.<column>`, una tabla o columna inexistente, o una columna que la tabla aún declara. `details.plan` contiene el plan. | Corrige la lista `drop`. Una columna declarada se elimina quitándola de su `defineTable`, desplegando y luego ejecutando reconcile. |
| `SCHEMA_RECONCILE_STALE` | 409 | La base de datos o las tablas cambiaron desde el plan confirmado. `details.plan` contiene el plan actualizado. | Revisa el nuevo plan y confirma su `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | `/reconcile/apply` no recibió el parámetro `confirm`. | Planifica primero y envía el `digest` del plan como `confirm`. La CLI realiza esto tras escribir `yes`. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | El controlador de este backend no puede planificar reconciliaciones o no admite SQL. | La conciliación funciona sobre Postgres. |

### Por qué no se puede fusionar la tabla de una rama

`BRANCH_MERGE_BLOCKED` nombra cada tabla rechazada en `details.tables`, con uno de estos códigos. El mismo código aparece en la propiedad `blocked` de la tabla dentro del propio diff, permitiendo a Studio advertirlo antes de presionar **Merge**. Ninguno constituye una respuesta HTTP independiente.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Las columnas de la tabla difieren entre la rama y su padre. Las filas se comparan únicamente sobre las columnas compartidas. | Agrega las columnas faltantes al padre mediante tus migraciones (`rebase db push`) y luego fusiona. Una migración que reescriba la tabla —un cambio de tipo de columna— la convertirá en `TABLE_REWRITTEN`: fusiona antes de aplicar dicho cambio o recrea la rama después de él. |
| `NO_PRIMARY_KEY` | — | La tabla carece de clave primaria, impidiendo comparar filas individualmente; el diff solo muestra recuentos de filas. | Añade una clave primaria a la tabla o transfiere sus filas manualmente. |
| `PRIMARY_KEY_DIFFERS` | — | Las columnas de la clave primaria o sus tipos difieren entre ambos entornos. | Aplica el esquema al padre en primer lugar. |
| `TABLE_ADDED` | — | La rama creó la tabla. Una fusión nunca crea tablas. | Créala en el padre mediante tus migraciones y luego fusiona sus filas. |
| `TABLE_DROPPED` | — | La rama eliminó la tabla. Una fusión nunca elimina tablas. | Elimínala mediante tus migraciones. |
| `TABLE_REWRITTEN` | — | Un extremo reescribió todas las filas de la tabla tras la creación de la rama — un cambio de tipo de columna, un `ADD COLUMN` con valor por defecto volátil, `VACUUM FULL`, `CLUSTER` — haciendo que todas las filas figuren como modificadas y haciendo imposible determinar qué lado alteró cada fila. | Fusiona la rama antes de tal migración o vuelve a crear la rama desde el padre tras haberla aplicado. |
| `TOO_LARGE` | — | La tabla contiene más filas en uno de los lados de las que un diff puede comparar individualmente (100.000 por defecto, `maxRowsPerTable`). | Aumenta `maxRowsPerTable` tanto en el diff como en el merge, o transfiere las filas por otra vía. |

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Solicitud malformada sin un código más específico aplicable. | Consulta el mensaje. |
| `UNAUTHORIZED` | 401 | No autenticado o la credencial fue rechazada. | Inicia sesión o renueva credenciales. |
| `FORBIDDEN` | 403 | Autenticado, pero sin permisos suficientes. | Reintentar con la misma identidad no tendrá efecto. |
| `CONFLICT` | 409 | Conflicto con el estado actual del recurso. | Consulta el mensaje. |
| `INTERNAL_ERROR` | 500 | Fallo interno en el servidor. El mensaje es genérico intencionadamente. | Facilita el `requestId`; el motivo reside en los logs. |

Una conexión fallida hacia dichos servicios responde con este error. | Reintenta; verifica los logs. |

## Mantener esta página verificada

`pnpm verify:docs` falla si falta algún código emitible por el servidor en estas tablas, si una tabla incluye un código que nada puede generar, si los estados HTTP de una fila no coinciden exactamente con los que el código fuente emite, o si una familia de códigos como `PG_<SQLSTATE>` carece de fila para un SQLSTATE que los clientes puedan recibir. El script encargado es `tooling/scripts/docs-verify/check-error-codes.mjs`.

Se valida a sí mismo primero. El escáner extrae los códigos analizando TypeScript en lugar de consultar un servidor en ejecución, por lo que sus puntos ciegos son silenciosos por diseño: en el pasado no detectaba códigos envueltos en funciones de una sola línea o escritos tras mensajes que contenían un `)`, reportando falsamente que "todos los códigos del servidor están documentados" en una página a la que le faltaban diecisiete de ellos. Por ello, la verificación ejecuta una prueba estructurada con esas variantes antes de analizar esta página, negándose a emitir un resultado si no es capaz de verlas.
