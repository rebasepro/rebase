Cada fallo que devuelve un backend de Rebase utiliza un único envelope y contiene un `code` estable. El código es el elemento sobre el que realizar bifurcaciones lógicas: el mensaje está redactado para una persona y puede cambiar de redacción, el estado se comparte entre una docena de problemas diferentes, y el código no sufre de ninguno de estos dos inconvenientes.

## El envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — legible por humanos. Para un `4xx` es el mensaje propio del servidor; para un `5xx` es deliberadamente genérico, ya que el texto subyacente puede citar un host, un rol o un nombre de columna.
- **`code`** — uno de los valores a continuación. Estable entre versiones menores.
- **`details`** — opcional y nunca garantizado. Consulta las reglas a continuación.
- **`requestId`** — presente siempre que la petición haya pasado por el middleware de request-ID, que corresponde a todas las rutas bajo `basePath`.

### `X-Request-ID`

Cada petición bajo `basePath` obtiene un ID: la cabecera `X-Request-ID` del emisor cuando es un UUID; de lo contrario, uno nuevo. Se devuelve en la respuesta como `X-Request-ID`, se incluye en el envelope de error como `requestId` y se adjunta a la línea de log del servidor para esa petición.

Esa es la clave de unión. Indícala en un reporte de error y un operador podrá encontrar la única línea de log que explica el fallo, conteniendo el motivo que nunca se mostró al cliente.

Enviar el tuyo propio es la forma en que una traza sobrevive a un salto: una pasarela (gateway) o un ejecutor de tareas que reenvía la cabecera obtiene un único ID en todos los servicios que procesaron la petición. Un valor no válido se ignora en lugar de ser rechazado —no vale la pena hacer fallar una petición por una cabecera malformada enviada por el emisor—, por lo que no debes asumir que el ID que enviaste es el ID que recibiste. Lee la cabecera de la respuesta.

### Qué contiene `details`

`details` tiene fines diagnósticos, no contractuales. Se rige por tres reglas:

1. **Cualquier cosa que una ruta establezca explícitamente se devuelve siempre.** Estos son los propios errores del emisor descritos con precisión: qué campo de filtro era desconocido, qué relación no es de escritura, qué valor no encajaba con su tipo.
2. **Los diagnósticos de la base de datos se recortan en producción.** Cuando el fallo proviene de Postgres, `details.dbCode` —el SQLSTATE— está siempre presente: nombra la clase de problema y no revela nada sobre los datos. `dbMessage`, `detail` y `hint` solo se añaden cuando `NODE_ENV` no es `production`, ya que Postgres incluye el contenido de las filas en ellos. `23505` reporta `Key (email)=(a@b.c) already exists.`, lo cual responde a "¿está registrada esta persona?" para cualquier dirección que alguien decida probar.
3. **Nunca bifurques lógica sobre `details`.** Hazlo sobre `code`. Lo que está bajo `details` es simplemente aquello que fue útil para una persona en ese punto de llamada concreto, y puede cambiar.

## Cómo interpretar un estado

| Estado | Qué dice sobre la petición |
| --- | --- |
| `400` | Malformada, o solicita algo que no existe en el esquema. Corrige la petición. |
| `401` | No autenticada, o la credencial ha expirado. Inicia sesión o renueva el token. |
| `403` | Autenticada, pero no permitida. Reintentar con la misma identidad no servirá de nada. |
| `404` | No existe tal ruta, tabla o fila — o es una fila que la seguridad a nivel de fila oculta. |
| `409` | Conflicto con el estado existente: un duplicado o una escritura concurrente. |
| `413` `415` `422` | El cuerpo es demasiado grande, el tipo de medio es incorrecto o fue rechazado semánticamente. |
| `429` | Límite de tasa excedido (rate limited). Reduce la frecuencia; el mensaje indica por cuánto tiempo. |
| `500` | El error proviene del servidor o de su base de datos, no del emisor. Revisa los logs. |
| `501` | La ruta existe, pero este despliegue no puede atenderla — una funcionalidad que está desactivada o no configurada. |
| `502` `503` `504` | Una dependencia no estuvo disponible, no estaba configurada o fue demasiado lenta. |

## `PG_<SQLSTATE>` — una restricción rechazada por la base de datos

Una escritura que Postgres rechaza por un motivo imputable a *los datos del emisor* responde con el SQLSTATE en el código: `PG_23505`, `PG_23503`, etcétera. Se trata de una familia, no de una lista fija —Postgres define cientos de SQLSTATEs—, pero solo dos clases llegan a manifestarse aquí, ya que solo esas dos son responsabilidad del emisor:

- **clase 23**, infracción de restricción de integridad: un duplicado, una clave foránea que no apunta a nada, una columna NOT NULL vacía;
- **clase 22**, excepción de datos: un valor que el tipo de columna no puede albergar.

Todo lo demás —una conexión caída, una columna inexistente, un problema de privilegios— es del servidor y permanece como un `500`. Por lo tanto, `code.startsWith("PG_")` es una comprobación segura para "la fila que envié era incorrecta", y las cuatro a continuación son las que un cliente experimenta habitualmente. `details.dbCode` transporta el mismo SQLSTATE para todas ellas, y el mensaje nombra la restricción.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Un valor no se pudo interpretar como el tipo de la columna — el equivalente de escritura a `INVALID_FILTER_VALUE`. | Envía un valor correspondiente al tipo de la columna. |
| `PG_23502` | 400 | Se dejó vacía una columna `NOT NULL`. | Envía el campo o asigna un valor por defecto a la columna. |
| `PG_23503` | 400 / 409 | Al guardar, una clave foránea apunta a una fila inexistente (400). Al eliminar, otras filas siguen referenciando a esta (409; una clave `RESTRICT` produce `PG_23001`, también 409). | Crea la fila de destino primero, o corrige el id; para una eliminación, elimina o reasigna antes las filas que la referencian. |
| `PG_23505` | 409 | Se infringió una restricción de unicidad. El mensaje indica la restricción. | Usa un valor diferente o actualiza la fila existente. |

### Conciliación de esquemas (Schema reconcile)

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) planifica
a través de `POST /api/admin/schema/reconcile/plan` y aplica mediante
`/reconcile/apply`. Un rechazo no altera nada; solo `SCHEMA_RECONCILE_FAILED`
deja parte de un plan aplicado.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | El cuerpo no es un objeto JSON, o `drop` no es una lista de cadenas con formato `"<table>.<column>"`. | Envía `{ "drop": ["voice_cache.wav"] }`, o prescinde de `drop`. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Una sentencia falló a mitad del proceso. Las sentencias previas a ella se ejecutaron y quedan aplicadas; `details.applied` las enumera. | Corrige lo que indica el mensaje y vuelve a planificar: el nuevo plan excluirá lo que ya se ejecutó. |
| `SCHEMA_RECONCILE_INVALID` | 400 | El plan no puede aplicarse y el mensaje lista los motivos: un `drop` que no es `<table>.<column>`, no nombra ninguna tabla o columna, o nombra una columna que la tabla todavía declara. `details.plan` contiene el plan. | Corrige la lista `drop`. Una columna declarada se elimina retirándola de su `defineTable`, desplegando y luego conciliando. |
| `SCHEMA_RECONCILE_STALE` | 409 | La base de datos o las tablas cambiaron desde el plan que confirmaste. `details.plan` es el nuevo plan. | Revisa el nuevo plan y confirma su `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | A `/reconcile/apply` no se le envió ningún `confirm`. | Planifica primero y envía el `digest` del plan como `confirm`. La CLI hace esto automáticamente cuando escribes `yes`. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | El driver de este backend no puede planificar una conciliación o no puede ejecutar SQL. | La conciliación funciona sobre Postgres. |

### Por qué no se puede fusionar la tabla de una rama

`BRANCH_MERGE_BLOCKED` enumera cada tabla que rechazó en `details.tables`, con uno
de estos códigos. El mismo código figura en la propiedad `blocked` de la tabla en el propio diff,
permitiendo que Studio lo advierta antes de que alguien presione **Merge**. Ninguno es una respuesta
independiente por sí mismo.

| Código | Estado | Significado | Qué hacer |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Las columnas de la tabla difieren entre la rama y su padre. Las filas se comparan sobre las columnas que comparten. | Añade las columnas faltantes al padre mediante tus migraciones (`rebase db push`) y luego fusiona. Una migración que reescriba la tabla —un cambio de tipo de columna— la convierte en `TABLE_REWRITTEN`: fusiona antes de dicho cambio, o crea la rama nuevamente tras él. |
| `NO_PRIMARY_KEY` | — | La tabla no tiene clave primaria, impidiendo comparar las filas una a una; el diff únicamente proporciona sus recuentos de filas. | Asigna una clave primaria a la tabla o traslada sus filas manualmente. |
| `PRIMARY_KEY_DIFFERS` | — | Las columnas de la clave primaria o sus tipos difieren entre ambos. | Aplica el esquema al padre primero. |
| `TABLE_ADDED` | — | La rama creó la tabla. Una fusión nunca crea una tabla. | Créala en el padre mediante tus migraciones y luego fusiona sus filas. |
| `TABLE_DROPPED` | — | La rama eliminó la tabla. Una fusión nunca elimina una tabla. | Elimínala mediante tus migraciones. |
| `TABLE_REWRITTEN` | — | Uno de los lados reescribió cada fila de la tabla por completo tras crearse la rama — un cambio de tipo de columna, un `ADD COLUMN` con valor por defecto volátil, `VACUUM FULL`, `CLUSTER` — haciendo que cada fila figure como escrita posteriormente, imposibilitando determinar qué lado modificó cada fila. | Fusiona la rama antes de tal migración, o recrea la rama desde el padre después de ella. |
| `TOO_LARGE` | — | La tabla contiene en uno de sus lados más filas de las que un diff compara una por una (100.000 por defecto, `maxRowsPerTable`). | Incrementa `maxRowsPerTable` tanto en el diff como en el merge, o traslada las filas por otro medio. |

## Mantenimiento de la exactitud de esta página

`pnpm verify:docs` falla cuando un código que el servidor puede emitir falta en estas
tablas, cuando una tabla lista un código que nada puede emitir, cuando los estados de una fila no coinciden
exactamente con aquellos con los que el código fuente emite el código, o cuando una familia de códigos como `PG_<SQLSTATE>` carece de una fila
para un SQLSTATE que los emisores puedan encontrar. La fase se ejecuta en
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Se verifica a sí misma primero. El escaneo lee los códigos directamente desde TypeScript y no desde
un servidor en ejecución, por lo que sus puntos ciegos son silenciosos por diseño: en una ocasión no fue
capaz de detectar un código transmitido a través de un wrapper de una sola línea, o uno escrito tras un mensaje
que contenía un `)`, reportando "todos los códigos que el servidor puede emitir están documentados"
sobre una página a la que le faltaban diecisiete de ellos. Por ello, la fase ejecuta un fixture exactamente
con esas estructuras antes de leer esta página, y se niega a reportar resultado alguno si no puede verlos.
