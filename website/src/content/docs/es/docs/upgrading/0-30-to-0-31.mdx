# Actualización de 0.30 → 0.31

<span class="since-badge" data-since="0.31">Desde 0.31</span>

0.31 hace que el backend esté centrado en Postgres (Postgres-first). Las tablas que declaras con `defineTable` en `backend/schema/` son lo único que el backend conoce sobre tus datos; lo que el panel de administración muestra sobre ellas reside en el frontend. Casi cada entrada a continuación es una consecuencia de esa separación, y casi todo se realiza automáticamente con un solo comando.

### Lista de verificación por proyecto

1. **Actualiza primero cada paquete de `@rebasepro`**, en cada paquete del workspace, para que los tipos que lee el codemod sean los de 0.31: `pnpm -r up "@rebasepro/*@0.31.0"`, luego `pnpm install`. Un proyecto en una versión anterior a la 0.30 debe aplicar primero los cambios de código de las guías intermedias ([Upgrading](/docs/upgrading/)): el codemod carga un `config/` de 0.20–0.29 y su comprobación de SQL pasa, pero esa comprobación compara el compilador 0.31 consigo mismo; solo el paso 7, contra tu base de datos, demuestra que el DDL generado es lo que tiene tu base de datos.
2. **Haz commit y luego ejecuta el codemod en modo de prueba (dry run):** `rebase migrate collections-to-tables --dry-run`. Imprime los archivos que escribiría, lo que rechaza (con archivo y línea), las notas y los pasos manuales, sin escribir nada. Corrige primero en `config/` lo que haya rechazado.
3. **Ejecútalo de forma definitiva:** `rebase migrate collections-to-tables`. Escribe `backend/schema/`, `frontend/src/cms/` (con `ui-config.json`), los módulos de `backend/` y los archivos del proyecto, añade `rebaseBackendGuard()` al `vite.config.ts` del scaffold, reescribe tus llamadas al SDK, mueve las importaciones de los nombres que 0.31 movió a otro paquete ([sección 135](#135-rebaseprotypes-y-rebaseprocommon-eliminan-el-modelo-de-colecciones-de-sus-raíces)), y demuestra que el SQL generado es idéntico byte por byte — o restaura cada archivo. Consulta la [sección 108](#108-las-tablas-en-backendschema-reemplazan-a-configcollections--ejecuta-el-codemod-primero).
4. **Lee la última sección de su salida, "Review before deploying: these rules change meaning"**, y toma una decisión sobre cada regla que enumera ([más abajo](#revisar-antes-de-desplegar-estas-reglas-cambian-de-significado)).
5. **Realiza los pasos manuales que imprime**, en orden. Cada uno indica su archivo, y la mayoría incluye el fragmento de código a escribir: el montaje de `<RebaseCMS>` con `tableCustomizations` y `uiConfig` cuando tu `App.tsx` no es el del scaffold, `rebaseBackendGuard()` cuando tu `vite.config.ts` no lo es ([sección 130](#130-rebase-build-rechaza-un-frontend-sin-rebasebackendguard)), hooks globales, una importación de un nombre que 0.31 eliminó ([sección 135](#135-rebaseprotypes-y-rebaseprocommon-eliminan-el-modelo-de-colecciones-de-sus-raíces)), y `rebase skills install` cuando el proyecto contiene agent skills ([sección 128](#128-la-skill-de-agente-rebase-collections-ahora-es-rebase-tables)). Ejecuta `pnpm install` cuando la salida indique "Dependencies added". Luego revisa dos listas en la parte del SDK de la salida:
   - **"Rewritten by name — review"**: llamadas a `.collection(` sobre un receptor sin tipo (`any`), reescritas porque el receptor se llama `dataAsAdmin`, o es `.data` con un nombre literal de tabla. Comprueba que cada una corresponda al SDK.
   - **"Left unchanged — check each"**: llamadas a `.collection(` que el codemod no pudo comprobar que fueran del SDK, como una llamada a través de un tipo que tu proyecto declara por sí mismo. Una llamada que permanezca aquí y que *sea* del SDK fallará en tiempo de ejecución en 0.31: cámbiala a `.table(` manualmente. El código que verifica si `collection` existe (`typeof data.collection === "function"`) requiere un paso manual: en 0.31 tomará silenciosamente la otra rama.

   Un archivo commiteado como resultado de compilación (un `.js` empaquetado o minificado) nunca se edita: se incluye en la lista, así que vuelve a compilarlo tras migrar y reemplaza cualquier copia vendored del cliente por la compilación de 0.31. Los pasos repetidos de un mismo tipo se imprimen una sola vez, indicando cada archivo y línea correspondientes; `--json` mantiene cada paso por separado.
6. **`rebase generate-sdk`** — los nombres del módulo generado han cambiado ([sección 115](#115-el-sdk-se-dirige-a-una-tabla-datatableslug)).
7. **Contra tu base de datos**, ejecuta `rebase db push --dry-run` y espera el mensaje "No changes: the database already matches these tables.", luego `rebase doctor --policies` y espera que no haya desfase (drift) de políticas. La comprobación SQL del codemod demuestra que la conversión es fiel; estas dos comprobaciones lo demuestran frente a la base de datos real, y cualquier diferencia de directivas que cualquiera de ellas señale representa un cambio en quién puede acceder a qué.
8. **`rebase verify`** — ahora también lee `frontend/src/cms`: una personalización que hace referencia a una tabla o campo que no existe, una columna requerida excluida del formulario, la ausencia de `rebaseBackendGuard()`, o un `ui-config.json` no transferido a `<RebaseCMS>`.
9. **Ejecuta la línea de `git rm` que imprimió el codemod** una vez revisado el diff: `git rm -r config/collections …` y las conexiones que movió a `backend/`, o `git rm -r config` cuando no quede nada propio allí ([sección 109](#109-ya-no-existe-el-paquete-config)).
10. **Vuelve a compilar y despliega.** Un bundle generado antes de 0.31 no arrancará en un entorno de ejecución 0.31 ([sección 112](#112-formato-de-bundle-3-se-rechazan-los-bundles-en-formato-2)). El primer arranque volverá a sellar la versión del esquema de la base de datos una sola vez ([sección 113](#113-la-versión-del-esquema-se-calcula-a-partir-de-las-tablas-v2)).

Ejecuta `rebase migrate collections-to-tables --check` en CI hasta que `config/` haya desaparecido: verifica que las tablas migradas sigan generando el mismo SQL que las colecciones de las que provienen, y sale con código 1 mientras no se reconozca alguna regla listada en "Review before deploying" — pasa `--accept-rule-changes` una vez que las hayas revisado.

### Revisar antes de desplegar: estas reglas cambian de significado

El codemod conserva cada regla de seguridad tal como fue escrita, y cada una mantiene el nombre de su directiva (policy). Sin embargo, el compilador 0.30 solo leía el primero entre `condition`, `using`, `access: "public"` y `ownerField`, y no reconocía ningún otro valor de `access`, por lo que cuatro variantes de reglas ahora otorgan permisos diferentes. Dos de ellas amplían el acceso:

| La regla | 0.30 otorgaba | 0.31 otorga | |
|---|---|---|---|
| un `access: "authenticated"` simple (sin `roles`) | nada | cualquier emisor autenticado, incluidos invitados | **amplía** |
| `access` + `check`, sin `condition`, en `select` / `update` / `delete` / `all` | ninguna fila existente | todas las filas existentes, a los emisores con `access` | **amplía** |
| `access: "authenticated"` + `condition` | cualquiera que coincida con `condition` | solo emisores autenticados que coincidan con ella | restringe |
| `access: "authenticated"` + `check`, en `insert` | cualquiera que inserte una fila coincidente | solo emisores autenticados | restringe |

La más habitual es la primera. Escribe `access: "registered"` para admitir únicamente a emisores con una cuenta (no invitados anónimos), o elimina la regla para continuar sin conceder nada. `access` con `roles`, y una `condition` basada en un objeto simple, conservan su significado anterior y no se incluyen en la lista.

El codemod también rechaza cualquier regla que el compilador de 0.31 rechace: una que combine cláusulas que el tipo `SecurityRule` excluye (`access` junto a `ownerField`, `using` o `withCheck`; `ownerField` junto a `using`, `withCheck`, `condition` o `check`; `condition` o `check` junto a `using` o `withCheck`), y una con un valor no válido de `access`, `mode`, `operation(s)` o `roles` (un error tipográfico como `"restrictive"` solía compilarse como permisivo). Consulta [Security rules](/docs/collections/security-rules/).

### Qué más se comporta de forma diferente

- **Lo que `GET /api/schema/tables` responde a un usuario.** Los administradores y quienes posean `schema:read` obtienen todas las tablas. Cualquier otra persona autenticada, incluidos invitados, solo obtiene las tablas a las que sus roles tienen acceso, mostrando únicamente las reglas aplicables a ellos; se descartan las relaciones hacia otras tablas y se retienen los flags de hooks. Un frontend que leía la descripción de otra tabla como usuario regular recibirá menos información; `schemaTables: { persons: "all" }` en las opciones del backend restablece la descripción completa. Consulta [Endpoints](/docs/backend/endpoints/#schema).
- **Los nombres de las relaciones son exactos**, y **las claves foráneas de tipo big-integer son números** ([sección 131](#131-las-filas-en-tránsito-siguen-su-columna)).
- **El historial se sirve enmascarado** ([sección 132](#132-el-historial-se-sirve-como-lecturas)).
- **Los nombres de las herramientas MCP y el payload de vistas** cambian al unísono para el conector alojado y los runtimes a los que accede ([sección 122](#122-las-herramientas-de-mcp-llevan-nombres-de-tablas)).
- **Restricciones deliberadas.** Las marcas de auditoría (columnas `.onCreateNow()` / `.onUpdateNow()`) se ocultan de las columnas de lista del panel de forma predeterminada: una lista migrada que mostraba `created_at` pierde esa columna a menos que especifiques `fields: { created_at: { hidden: false } }` en su `customizeTable`. El codemod rechaza, indicando el motivo, arrays JSON de tuplas, un `vector` / `binary` / `reference` dentro de un mapa, `databaseId` en una colección Postgres, `isId: "cuid"`, una relación solitaria con `isId` y `disableDefaultPolicies: true` sin reglas. Se rechaza una relación de una columna hacia una tabla con clave compuesta (defínela con `rel.via()`). Las etiquetas OpenAPI se derivan del slug, no del display name. `rebase schema introspect` omite tablas sin clave primaria e indica el motivo (un servidor que introspeccione la base de datos la seguirá sirviendo). Una vista básica que declare `roles` produce un error de compilación; el codemod la descarta con una nota.
- **Restauración en otro clúster.** El sello de las políticas de administración por defecto aplica un hash sobre los OID de los roles; por lo tanto, tras un dump o una restauración point-in-time en un clúster distinto, el primer `db push` o arranque volverá a crear esas políticas una sola vez, con los mismos nombres y el mismo SQL.

### Terminología

| Antes | Ahora | Dónde se mantiene "collection" |
|---|---|---|
| una colección en `config/collections/` | una **tabla** en `backend/schema/` (`defineTable`) | — |
| `properties` | `columns` (`col.*`) y `relations` (`rel.*`) | — |
| `securityRules`, `defaultSecurityRules` | `rls` (obligatorio), `defaultRls` | — |
| `callbacks`, `Property.callbacks` | `hooks`, el `.transform()` de una columna | — |
| el bloque `admin` | `customizeTable` en `frontend/src/cms/` | — |
| `data.collection(slug)` | `data.table(slug)` | — |
| lo que muestra el panel de administración | una **colección**: una tabla tal como la dibuja el panel, o una colección de Firestore | el CMS: `CollectionPanel`, el Collection Editor, `externalCollections` |

## 108. Las tablas en `backend/schema` reemplazan a `config/collections` — ejecuta el codemod primero

**A quién afecta:** a todos los proyectos con un directorio `config/collections/`.

**Qué cambió:** el backend solo lee `backend/schema/index.ts` y los resultados exportados de `defineTable`, `defineAuthTable` y `defineView`. Los archivos de `defineCollection` ya no son leídos por nada: el runtime, cada comando de la CLI y la validación de `rebase.json` rechazan cualquier proyecto que conserve `config/collections`, indicando el comando que aparece a continuación. `rls` es obligatorio en cada tabla — una lista de reglas, `"admin-only"`, o `"inherit"` para el `defaultRls` exportado por el index — y `disableDefaultPolicies` pasa a ser `defaultPolicies: false`.

**Qué hacer:**

```bash
rebase migrate collections-to-tables            # or --dry-run first
```

Escribe una tabla por colección, haciendo explícita cada columna física en su posición original (de modo que se escribe la columna de clave de un `belongsTo`), el índice con `defaultRls` derivado de `defaultSecurityRules`, un `customizeTable` para cada colección cuya presentación no fuera la predeterminada, y archivos `defineFirestoreCollection` para colecciones de Firestore. Los callbacks de una colección se convierten en los `hooks` de su tabla y los `.transform()` de sus columnas; los `callbacks` globales que exportaba `config/index.ts` pasan a ser un paso manual (sección 109). Luego vuelve a leer el resultado a través de la nueva canalización: DDL, directivas, búsqueda, vectores, disparadores, vistas y el esquema de Drizzle deben ser byte por byte idénticos a los generados por las colecciones, o de lo contrario se restaura cada archivo y el proceso finaliza con código 1 mostrando el diff.

También traslada lo que antes requería intervención manual:

- **Callbacks construidos mediante un helper** (`callbacks: softDeleteCallbacks(...)` o un objeto de callbacks importado) se convierten en `hooks:` con la misma expresión, y las funciones del helper se transforman en propiedades de table-hooks donde están escritas (el codemod sigue importaciones relativas, `const`, lecturas de propiedades y sentencias de un único `return`). Si no logra seguir el helper, un paso manual listará los hooks que debes revisar.
- **Una función `storagePath`** se migra en dos partes: la función pasa a ser `storage.path` de la personalización, permitiendo que el panel siga eligiendo el destino de la subida, y la plantilla `path` de la columna toma la forma de las claves que devuelve — el texto estático de su template literal reemplazando cada `${…}` por `{path}` (`` `${owner}/cv` `` → `{path}/cv`). Ahora el servidor aplica las directivas `maxBytes` y `accept` de la columna a cualquier subida cuya clave coincida con esa plantilla, no únicamente a la que nombre a la columna, por lo que los límites son más estrictos que en 0.30. Toda función cuyo resultado carezca de texto estático será rechazada: asígnale uno primero.
- **Un `policy.existsIn({ collection })` de 0.30** mantiene su tabla, y se descarta `auth: { collection: usersCollection }` en puntos de entrada personalizados del backend (la tabla definida con `defineAuthTable` es la tabla de auth). La opción de arranque `collections` pasa a ser `schemaDir`.
- **Un generador `dynamicProps`** devuelve una personalización de campo con claves planas en 0.31 (`{ readOnly: true }`, en lugar de `{ admin: { readOnly: true } }`). El codemod reescribe los generadores cuyos retornos sean literales de objeto, en línea o en un módulo compartido, y lista cualquier otro caso.
- **La configuración de presentación propagada (spread) desde un objeto compartido** se transfiere a la personalización (`….dynamicProps`); la presentación calculada por una función envoltorio se registra como un paso a revisar, sin provocar el rechazo del proyecto.

Lo que no se pueda trasladar con exactitud se rechazará indicando archivo y línea, sin escribir nada: una colección construida mediante la invocación de una función, una propagación (spread) o un descriptor de acceso que no se pueda inspeccionar, un motor que no sea Postgres o Firestore, o un archivo de salida existente con contenido diferente (muévelo a otra ubicación, o usa `--force`). Un árbol de git con cambios sin confirmar o un proyecto fuera de git también será rechazado, de modo que la migración resulte en un único diff revisable. `--json` imprime el informe completo para su uso en scripts o agentes. Consulta [`rebase migrate`](/docs/cli/schema/#rebase-migrate) y [Tables](/docs/schema/).

Las tablas generadas definen sus columnas de la misma forma que `pg-core` de Drizzle: `col.varchar({ length: 160 })`, `col.timestamp({ withTimezone: true })`, `col.text().array()`, `pgEnum(...)`, `` .default(sql`…`) ``, `.generatedByDefaultAsIdentity()` — por lo que su salida no requiere nada más; consulta [Columns](/docs/schema/columns/). Una tabla escrita a mano para una versión previa de 0.31 usando la sintaxis antigua (`col.timestamptz()`, `col.varchar(160)`, `col.array(col.text())`, `col.enum(values, { name })`, `.defaultSql()`, `.identity()`, `.column("…")`) ya no compilará: `tooling/scripts/drizzle-sweep.mts` en el repositorio de Rebase la convierte, reescribiendo únicamente las cadenas del constructor, y con `--verify` comprueba que cada tabla convertida compile en el mismo descriptor (`npx tsx drizzle-sweep.mts --verify backend/schema`).

El paso `sdk-calls` posterior también reescribe los orígenes de las reglas: `existsIn({ collection })` y `membership: { collection }` pasan a ser `table` (sección 123); `--skip-sdk-calls` también omite esto. Las tareas pendientes se listan como pasos manuales numerados, y cuando el proyecto contiene agent skills instaladas, el último paso será la línea `rebase skills install` para actualizarlas (sección 128). Ejecutar simplemente `rebase migrate` imprime la ayuda para ambos subcomandos.

## 109. Ya no existe el paquete config

**A quién afecta:** a todos los proyectos — `config/` era un workspace independiente.

0.31 deja de leer `config/collections`; no prohíbe `config/`. El codemod elimina lo que Rebase leía — los archivos de colecciones y el código que se traslada a `backend/` (`resources.ts`, `storage.ts`, `generated/register.ts` y sus reexportaciones en `config/index.ts`) — y deja tus propios módulos en `config/` intactos, importables como siempre: `config/` sigue siendo un paquete del workspace y el backend continúa compilando `../config/**/*`. Solo se reescriben las importaciones de los elementos eliminados: un archivo de colección importado por el backend apuntará al módulo de la tabla (un paso lista los usos que lo leen como un objeto); importado por el frontend, pasa a ser una importación solo de tipos de la tabla donde solo se use como tipo, o genera un paso indicando la personalización; un helper dentro de `config/collections` se copia junto al código que lo requiere.

**Qué cambió:** lo que residía junto a las colecciones se traslada a `backend/`:

| Antes | Ahora |
|---|---|
| `config/resources.ts` | `backend/resources.ts` |
| `config/storage.ts`, `storageAuthorize` de `config/index.ts` | `backend/storage.ts` |
| `callbacks` exportados desde `config/index.ts` | `hooks` exportados desde `backend/hooks.ts` (`TableHooks`: `table` en lugar de `collection`, `values` en lugar de `row`) |
| `config/generated/register.ts` | `backend/generated/register.ts` |
| `config` en `rebase.json`, `usersCollection` | `tables` (por defecto `backend/schema`); la tabla de autenticación es la declarada con `defineAuthTable` |

El runtime lee `storageAuthorize` y `hooks` y nada más de esos módulos; cualquier otra exportación se notificará en el arranque. El frontend importa `backend/**` únicamente como tipos: `pnpm check:frontend-backend-imports` rechaza una importación por valor, ya que enviaría código del servidor al navegador.

**Qué hacer:** el codemod traslada `resources.ts`, `storage.ts` y el registro, y reescribe `rebase.json`, `package.json`, `pnpm-workspace.yaml` y `backend/tsconfig.json`. Los `callbacks` globales se muestran como un paso manual: muévelos a `backend/hooks.ts` a mano y añade `hooks.ts` a la propiedad `include` de `backend/tsconfig.json` para que `tsc` lo verifique. Luego ejecuta la línea `git rm` generada: `git rm -r config/collections …`, o `git rm -r config` si ya no queda nada propio en ese directorio.

## 110. Las opciones de arranque y los hooks hacen referencia a tablas

**A quién afecta:** a backends iniciados manualmente (`initializeRebaseBackend`, `createRebaseBackend`) y código que adjunta hooks tras el arranque.

**Qué cambió:**

| Antes | Ahora |
|---|---|
| `collections`, `collectionsDir` | `tables`, `defaultRls`, `schemaDir` |
| `callbacks` | `hooks` |
| `auth.collection` | eliminado: pasa a ser el `defineAuthTable` en `tables` |
| `backend.setCollectionCallbacks(slug, cb)` | `backend.setTableHooks(slug, hooks)` |
| propiedades de hooks: `collection`, `row` | `table` (el descriptor), `values` |
| `composeCallbacks` | `composeTableHooks` de `@rebasepro/common` |
| `openRebase({ collections, callbacks })` | `openRebase({ tables, hooks })`, `tables` desde `compileSchema([...])` |
| `OpenedRebase.collections`; la variable `collections` en `rebase console` | `.tables`; `tables` |

```diff ts
-await initializeRebaseBackend({ app, server, collectionsDir: "./config/collections", callbacks });
+await initializeRebaseBackend({ app, server, schemaDir: path.resolve(__dirname, "../schema"), hooks });
```

Los hooks asociados a un objeto de colección transferido directamente en el punto de llamada ya no se ejecutan: el driver ejecuta los hooks de las tablas que sirve, por lo que debes asociarlos mediante `setTableHooks`.

**Qué hacer:** `rebase migrate sdk-calls` reescribe `setCollectionCallbacks`, adapta las propiedades de los hooks y genera una lista con cada objeto de opciones del backend a actualizar a mano. Los scripts que lean los datos deben compilar sus tablas:

```diff ts
-const rebase = await openRebase({ databaseUrl, collections, callbacks });
+const rebase = await openRebase({ databaseUrl, tables: compileSchema([products, orders]), hooks });
```

Consulta [Scripts](/docs/backend/scripts/#openrebase), [Backend overview](/docs/backend/) y [Global hooks](/docs/backend/hooks/).

## 111. El panel de administración renderiza las tablas que el servidor sirve

**A quién afecta:** a todo frontend que monte `<RebaseCMS>`.

**Qué cambió:** `<RebaseCMS collections>` desaparece. El panel muestra todas las tablas que el backend expone en `GET /api/schema/tables`, sin necesidad de un archivo por tabla, seguidas de `externalCollections` (Firestore). `tableCustomizations` recibe los objetos `customizeTable` procedentes de `frontend/src/cms/`. Se eliminan el plugin de colecciones de Vite y `virtual:rebase-collections`. `CollectionsProvider` toma las mismas tres entradas (`tableCustomizations`, `externalCollections`, `tables`).

```diff tsx
-import { collections } from "virtual:rebase-collections";
-<RebaseCMS collections={collections}/>
+import { postsCms } from "./cms/posts";
+<RebaseCMS tableCustomizations={[postsCms]}/>
```

**Qué hacer:** el codemod genera `frontend/src/cms/index.ts`, que exporta `tableCustomizations` (y `externalCollections`), y lo monta automáticamente en el `App.tsx` del scaffold; un `App.tsx` no reconocido, el plugin en `vite.config.ts` y la declaración del módulo virtual se registran como pasos manuales en la salida. Consulta [Customizing a table](/docs/frontend/customize-table/).

## 112. Formato de bundle 3; se rechazan los bundles en formato 2

**A quién afecta:** a cualquier despliegue de un bundle compilado — autoalojado con la imagen de runtime, o en Rebase Cloud.

**Qué cambió:** el esquema del bundle es `entry.tables`, junto a `entry.resources`, `entry.storage` y `entry.hooks`; `bundleFormat` pasa a ser 3 y el contrato de runtime a 2. Un bundle en formato 1 o 2 contiene `config/collections`, que el runtime 0.31 no puede interpretar, por lo que se negará a iniciar indicando el comando del codemod en el mensaje, en vez de introspeccionar la base de datos y exponer una API diferente.

**Qué hacer:** migra el código fuente, ejecuta `rebase build` y despliega. En Rebase Cloud, desplegar el repositorio migrado fuerza su recompilación. Consulta [Runtime and bundles](/docs/architecture/runtime-and-bundles/).

## 113. La versión del esquema se calcula a partir de las tablas (`v2:`)

**A quién afecta:** a cualquier base de datos aprovisionada por un runtime anterior a 0.31 y a cada SDK generado.

**Qué cambió:** la versión del esquema aplica un hash a los descriptores de tabla compilados y comienza con `v2:`. Una base de datos marcada con `v1:` reporta el cambio de modelo una única vez — tanto en el registro de inicio como en `rebase doctor`, indicando cómo actualizar el sello — y todo SDK generado se considerará desactualizado una vez.

**Qué hacer:** aprovisiona una vez con el nuevo runtime: inicia el proceso propietario del esquema o ejecuta `rebase db push`. Con `REBASE_REQUIRE_SCHEMA_MATCH=true`, actualiza el sello antes de desplegar el resto de procesos. Vuelve a generar el SDK.

**Qué cambió:**

## 115. El SDK se dirige a una tabla: `data.table(slug)`

**A quién afecta:** a cada cliente, función, cron, hook y script que nombre una tabla por su slug o transfiera el diccionario generado.

**Qué cambió:**

| Antes | Ahora |
|---|---|
| `data.collection(slug)` | `data.table(slug)` |
| `createRebaseClient({ collections: collectionsDictionary })` | `createRebaseClient({ tables: tablesDictionary })` |

**Qué hacer:** el codemod ejecuta `rebase migrate sdk-calls` sobre tu código — ejecútalo de forma aislada en proyectos ya migrados — y luego lanza `rebase generate-sdk`. Una llamada a `.collection(` cuyo receptor no provenga del SDK se conservará tal cual y se mostrará en una lista. Consulta [Typed SDK](/docs/sdk/).

## 116. Indicadores (flags) de la CLI: `--schema-dir`, no `--collections`

**A quién afecta:** scripts y fases de CI que invoquen la CLI con una ruta de esquema.

**Qué cambió:** `--collections` / `-c` son rechazados en cualquier comando que lea el esquema, indicando el comando del codemod en el mensaje (`generate-sdk` ignora un `--collections-dir` suelto); `--schema-dir` especifica un directorio de esquemas distinto a `backend/schema`. `rebase schema introspect` escribe archivos `defineTable` en `backend/schema/` — `--output` ha sido eliminado. `REBASE_STRICT_COLLECTION_CONFIG` ya no se procesa: un esquema que no compile impedirá siempre el arranque.

**Qué hacer:** reemplaza los flags correspondientes. Consulta [CLI](/docs/cli/) y [Schema generation](/docs/cli/schema/).

## 117. El editor de esquemas edita `backend/schema` con `TablePatch`

**A quién afecta:** código que consuma las rutas del editor de esquemas o live-schema, y despliegues con variables de edición en vivo activas.

La capa de presentación no altera el esquema: se almacena como preferencias de UI (`/api/admin/ui-config`). Cualquier edición cuyo archivo haya sido alterado en disco tras prepararse la operación (guardado en el IDE, otro proceso) devolverá 409 `SCHEMA_EDIT_STALE_FILE` sin guardar nada; anteriormente devolvía 400 `SCHEMA_EDIT_REFUSED`.

**Qué hacer:** renombra la variable; adapta las llamadas a estas rutas para enviar parches `TablePatch`, y recarga ante un error `SCHEMA_EDIT_STALE_FILE`. Consulta [Live schema editing](/docs/backend/live-schema-editing/).

## 118. Un slot de componente es un componente

**A quién afecta:** personalizaciones que definían un componente React mediante una ruta de cadena o un thunk diferido `() => import(…)`.

## 119. Las preferencias del panel son preferencias de UI

**A quién afecta:** implementaciones de `UserConfigurationPersistence`.

**Qué cambió:** el redimensionamiento o reordenación de tablas por parte del usuario se gestiona como un delta `UiTablePreferences`: `getTablePreferences` / `saveTablePreferences` sustituyen a `getCollectionConfig` / `onCollectionModified`, y el tipo parcial de configuración de colección que aceptaban ha sido eliminado. El almacenamiento del navegador los guarda bajo `table_preferences::<slug>` e ignora los registros de paneles anteriores, restableciendo una sola vez el ancho de columnas y modos de vista de cada usuario. **Qué hacer:** migra las capas personalizadas de persistencia a los dos nuevos métodos, y adapta implementaciones custom de `StudioSchemaEditing` a `applyTablePatches`.

## 120. MongoDB queda retirado

## 123. El vocabulario de reglas utiliza `table`

**A quién afecta:** reglas que emplean `policy.existsIn` o aislamiento por tenant mediante membership, y reglas que combinan `access` con otras cláusulas.

**Qué cambió:** `policy.existsIn({ collection, where })` pasa a ser `existsIn({ table, where })`, y `tenant.from.membership.collection` pasa a ser `membership.table`; los nombres de las directivas no sufren cambios. **Qué hacer:** el codemod renombra las claves, rechaza directivas inválidas indicando archivo y línea, y enumera las reglas cuyo significado varía bajo "Review before deploying". ## 131. Las filas en tránsito siguen su columna

**A quién afecta:** clientes que consultan claves foráneas o nombran relaciones, y operaciones de escritura que envían columnas generadas u objetos JSON parciales.

**Qué cambió:** los valores se procesan con el codec de su columna durante la salida y bajo las restricciones de la columna durante la entrada.

- Una columna de clave foránea `bigint` o `numeric` creada por una relación, que Postgres entrega como texto, se entrega como **número** en REST, el SDK y el panel de administración. Las claves numéricas declaradas explícitamente ya operaban así.
- Los **elementos de arrays nativos se entregan según su tipo escalar**, tanto en REST, el SDK, sockets y el driver:

  | Columna | 0.30 servía | 0.31 sirve |
  |---|---|---|
  | `timestamptz[]` | `["2026-01-02 11:00:00+01"]` | `["2026-01-02T10:00:00.000Z"]` |
  | `numeric[]` (driver inicializado sin la directiva numérica en el arranque: tests, scripts) | `["1.50", "2.25"]` | `[1.5, 2.25]` |
  | `bigint[]` con un elemento nulo | `[1, 0, 3]` | `[1, null, 3]` |
  | `date[]`, `timestamptz[]` o array de enums con un elemento nulo | `["2026-01-02", "NULL"]` | `["2026-01-02", null]` |

  `date[]`, `time[]`, `text[]`, `uuid[]`, `boolean[]`, `integer[]` y `double precision[]` se entregan como antes. Lo almacenado no cambia: una fila leída y guardada nuevamente conserva el mismo array.
- Una relación indicada en `include`, filtros o criterios de ordenación debe coincidir con su **nombre exacto**. Se eliminan los intentos secundarios que probaban con el slug o la variante en snake_case.
- Cualquier columna calculada/generada se rechaza en operaciones de escritura y se excluye del esquema de entrada OpenAPI.
- Se exige el cumplimiento de campos obligatorios dentro de objetos JSON; las operaciones `$inc` y los elementos de array sobre columnas enteras deben ser números enteros.

**Qué hacer:** procesa las claves foráneas como números allí donde hacías comparaciones de cadenas, parsea elementos de `timestamptz[]` como RFC 3339, maneja elementos nulos de array como `null`, y nombra las relaciones tal como las declara la tabla (las claves dentro de `relations`). Deja de enviar columnas generadas en peticiones de escritura.

## 132. El historial se sirve como lecturas

**A quién afecta:** lectores de instantáneas del historial y desarrolladores que implementen un `DataDriver`.

**Qué cambió:** los registros del historial se entregan como lecturas normales: primero se valida el acceso al campo y luego se ejecutan los hooks `afterRead` (global, tabla, columna). Las columnas enmascaradas por un hook o por `.transform({ afterRead })` quedan enmascaradas en cada instantánea; los campos inaccesibles para el usuario se retienen y se omiten de `changed_fields`; se descartan las claves de columnas borradas, y una restauración jamás escribirá en una columna que el emisor no pueda leer. Si un hook lanza un error sobre una instantánea antigua, la petición fallará. Como 0.30 servía los registros almacenados en crudo, se recomienda actualizar todo proyecto que use historial y hooks de enmascaramiento.

Cada registro refleja la fila tal como la lee `GET /api/data/<table>/<id>` sin `include`: valores simples y un `belongsTo` representado por su clave foránea. Un registro generado por una versión anterior con el modelo de vista del panel se servirá, y se restaurará, con ese mismo formato de fila: un envoltorio `{ "__type": "date", "value" }` como su valor, una referencia `{ "__type": "relation" }` para relaciones de pertenencia como clave foránea bajo el nombre original de la clave, y cualquier otra referencia como la clave de la fila relacionada. La versión 0.30 exponía estas referencias tal como estaban escritas.

El driver expone el historial mediante `DataDriver.serveStoredRows(path, rows)`, ejecutándose dentro de la transacción de solo lectura del cliente; los endpoints de historial devolverán 501 si el driver carece de este método, garantizando que el historial nunca se exponga sin enmascarar.

**Qué hacer:** nada si se utiliza el driver de Postgres integrado. Un driver a medida debe implementar `serveStoredRows`. Consulta [History](/docs/backend/history/).

**Qué hacer:** renombra las referencias. Un wrapper que adapte la implementación a `BackendBootstrapper` debe propagar `ensureTableSchema` y `ensureTablePolicies`. Consulta [Embedding the Postgres driver](/docs/backend/embedding-postgres-driver/).

## 135. `@rebasepro/types` y `@rebasepro/common` eliminan el modelo de colecciones de sus raíces

**A quién afecta:** código que importe tipos de colecciones o propiedades, helpers del panel de administración o utilidades de migración desde `@rebasepro/types` o `@rebasepro/common` — campos y vistas custom, plugins, tests con fixtures de colecciones — y drivers a medida que implementen el registro.

**Qué cambió:** los paquetes base describen únicamente tablas. Lo referente a una colección tal como la representa el panel de administración pasa a `@rebasepro/cms-types`:

- **Tipos** migrados desde `@rebasepro/types`: `CollectionConfig`, `PostgresCollectionConfig`, `FirebaseCollectionConfig`, `AnyCollectionConfig`, todas las variantes `…Property` (`StringProperty`, `NumberProperty`, `ArrayProperty`, …) y `Properties`, `CollectionCallbacks` y sus props de hooks, los modelos de relaciones de 0.30 y sus formas `Resolved…`, `CollectionIndex`, las paletas de etiquetas (`ColorScheme`, `ColorKey`, …), `FieldAccess`, `EnumValues`.
- **Helpers** migrados desde `@rebasepro/common`: los métodos de políticas adaptados a colecciones (`policyToPostgres`, `compileRulePolicies`, `getEffectiveSecurityRules`, `getGeneratedPolicyNames`, …), `CollectionRegistry`, `resolveCollectionRelations`, `resolveRelation`, `getTableName`, `findRelation`, `rowToViewModel`, `resolvePrimaryKeys`, la lectura de accesos de un campo (`effectiveAccess`, `canReadField`, `canWriteField`), `evaluateCondition`, `canEditEntity`, `resolveProperty`, `getDefaultValuesFor`, `getSubcollections`, `getCopyValues`, `enumToObjectEntries`. Las reglas compiladas a partir de una expresión simple deben usar `compilePolicyExpression(expr)` de `@rebasepro/common`.
- **`composeCallbacks`** combina los callbacks de una colección para el panel y pasa a `@rebasepro/cms-types`; `@rebasepro/server` ya no lo reexporta. En el backend, los hooks de tabla se componen mediante `composeTableHooks` de `@rebasepro/common`, y el codemod marcará cualquier importación de `composeCallbacks` en el backend como un paso manual indicándolo.
- **`defineCollection`** se retira de `@rebasepro/common` y `@rebasepro/cms-types`: define la tabla con `defineTable` en `backend/schema` y configúrala mediante `customizeTable` en `frontend/src/cms`; las colecciones Firestore se declaran con `defineFirestoreCollection` de `@rebasepro/firebase`.
- **El accessor del panel de administración y sus tipos asociados**: `Entity`, `EntityValues`, `TableAccessor`, `TableTrashAccessor`, `FindResponse`, `QueryBuilderInterface`, `RebaseData` y `AuthState` salen de `@rebasepro/types`; `buildRebaseData`, `wrapAsEntityData`, `buildRoutedRebaseData`, `EntityDataOptions`, `QueryBuilder`, `RelationRef` y `createRelationRef` salen de `@rebasepro/common`. Todos ellos se importan desde `@rebasepro/cms-types`. La capa de datos propia del SDK — `buildSdkData`, `createDriverTableRows`, `buildRoutedSdkData`, en `@rebasepro/common` — sirve las filas directamente y conserva las respuestas previas.
- **`EntityDataOptions.resolveCollection`** se reemplaza por `primaryKeysOf`, `viewModelOf`, `storedValuesOf` y `viewModelSourceOf`; pueden generarse con `collectionEntityDataOptions(resolveCollection, { resolveDataPath, resolveAccessor })` desde `@rebasepro/cms-types`.
- **La utilidad de migración** (`collectionsToTableDefs`, `collectionToTableDef`, `LiftNote`, `LiftResult`, `LiftOptions`) pasa a `@rebasepro/common/migrate`, junto a una réplica estática del modelo de colecciones 0.30 (tipos `Legacy…`) y `defineLegacyCollection`.
- **Otros elementos eliminados de la raíz de los paquetes base**, listados como pasos manuales por el codemod: la API de parches de colecciones de `@rebasepro/types` (`CollectionPatch`, `CollectionPatchOp`, `applyCollectionPatch`, `collectionPatchProblems`, `isCollectionPatch`, `nestCollectionPatchPaths` → `TablePatch`), sus métodos para JSON de colecciones (`diffCollections`, `diffJsonValues`, `toCollectionJson`, `RUNTIME_ONLY_COLLECTION_KEYS`, `runtimeOnlyKeyIn`), los restos de la época de Mongo `DocumentAdmin`, `isDocumentAdmin` y la capability `supportsDocumentAdmin`, así como `RebaseProjectContract.collectionSlugs` / `.collections` / `.generatedAt` (`/api/meta/contract` entrega `tables`); en `@rebasepro/common`, `buildTenantSecurityRule` → `tenantSecurityRule`, `defaultPoliciesDisabled` → `tableDefaultPoliciesDisabled`, `restoresSoftDeletedRow` → `isSoftDeleteRestore`, `softDeleteFieldOf` → `softDeleteColumn`, `getJunctionConfigForRelation` → `resolveTableJunctions`, y quedan sin equivalente `isRelationRequired`, `relationDeclaringProperty`, `requireCallbackCollection` (debe consultarse el `TableDescriptor`).
- **El registro del driver** implementa `TableRegistryInterface` (anteriormente `CollectionRegistryInterface`): `setGlobalHooks?` y `setTableHooks?` sustituyen a `getGlobalCallbacks` / `setGlobalCallbacks?`. Se eliminan `globalHooksAsCallbacks`, `resolveDriftCheckName` y `PENDING_TABLE_FEATURES`.

**Qué hacer:** `rebase migrate sdk-calls` (integrado en `collections-to-tables`) actualiza las importaciones siguientes a sus nuevos paquetes — fusionándolas si el archivo ya importa de ese paquete, preservando `import type`, `type` en línea y alias `as` — y añade el paquete a las dependencias del módulo correspondiente; ejecuta `pnpm install` después. Si se detecta una importación de un elemento eliminado, un namespace (`import * as`), un `export *`, o un `import()` dinámico o `require()` sobre nombres migrados, se indicará en un paso manual numerado. Las suites de pruebas que mantengan literales de colección como fixtures deben tiparlos con los tipos `Legacy…` y transformarlos mediante `@rebasepro/common/migrate`.

### Importaciones que cambiaron de paquete

Cada elemento reubicado o suprimido en 0.31 está detallado en [Imports that moved in 0.31](/docs/upgrading/0-30-to-0-31-imports/), con las instrucciones pertinentes para cada elemento eliminado. Dicho catálogo se genera desde la misma tabla que consulta el codemod, correspondiendo punto por punto con las modificaciones aplicadas por `rebase migrate sdk-calls`.

## 136. El controlador de Postgres y las lecturas únicas del socket devuelven la fila REST

**A quién afecta:** funciones o plugins que consulten datos mediante `requireDriver(c)` / `getDriver(c)`, implementaciones que transmitan los frames `FETCH_COLLECTION` / `FETCH_ONE` del socket, y código que interprete objetos con estructura `{ __type }` en una respuesta.

**Qué cambió:** el formato de lectura se unifica. `fetchCollection` y `fetchOne` en el driver de Postgres — empleados por `requireDriver(c)` en funciones, extensiones, frames unitarios de sockets, MCP y el simulador de RLS — retornan exactamente la misma estructura que `GET /api/data/<table>`:

| Valor | Lectura en driver 0.30 | 0.31 |
|---|---|---|
| timestamp | `{ "__type": "date", "value": … }` | cadena en formato RFC 3339 |
| relación `belongsTo` | `{ "__type": "relation", "id", "path" }` bajo el nombre de la relación | la clave foránea bajo su propia columna (`authorId`) |
| fila relacionada | todas las relaciones cargadas por `fetchOne` | únicamente las relaciones listadas en `include`, bajo su propia fila |
| vector, `bytea` | `{ "__type": "Vector" }`, data URL | idéntico a cómo los expone REST |

`FetchOneProps` recibe `include` (se elimina `ListenOneTarget`: reemplázalo por `FetchOneProps`). Los métodos `rebase.data`, `context.data` y el SDK ya entregaban este esquema y se mantienen intactos.

`@rebasepro/client` decodifica las respuestas REST y los frames de socket como JSON plano: un nodo con la propiedad `__type` ya no se convierte en una instancia de `Date`, `EntityReference`, `EntityRelation`, `GeoPoint` o `Vector`, y un documento JSON que guarde una clave `__type` se retornará tal como fue almacenado.

**Qué hacer:** procesa los datos como filas planas: convierte fechas desde cadenas, lee las claves foráneas por su propio identificador y añade `include` para cada relación que requieras:

```diff ts
-const article = await requireDriver(c).fetchOne({ path: "articles", id });
-const authorId = article?.author.id;      // a { __type: "relation" } ref
+const article = await requireDriver(c).fetchOne({ path: "articles", id, include: ["author"] });
+const authorId = article?.authorId;
```

## 137. Las interfaces del controlador y del backend utilizan tablas, no colecciones

**A quién afecta:** implementaciones personalizadas de `DataDriver`, adaptadores de base de datos o servidores estructurados directamente sobre los módulos de `@rebasepro/server`.

**Qué cambió:**

| Antes | Ahora |
|---|---|
| la propiedad `collection` en llamadas a `DataDriver` (fetch, save, delete, count, search, listen) | eliminada: el driver localiza la tabla que atiende usando `path` |
| `checkUniqueField(path, name, value, id, collection)` | `checkUniqueField(path, name, value, id?)` |
| `scanStoredRows({ path, collection, pageSize })` | `scanStoredRows({ path, pageSize })` |
| `DataDriver.initTextSearch` | eliminada |
| `DatabaseAdapterInitConfig.collections`, `.collectionRegistry` | eliminadas: el adaptador recibe `CompiledTable[]` |
| `BackendServices.collections()` | `services.tables()` |
| `serializeCollections`, `deserializeCollections`, `isSerializedCollectionRef`, `SerializedCollectionRef` | eliminadas: los descriptores se entregan en `GET /api/schema/tables` |
| `AuthAdapter.prepareUserCreation(values, collectionAuth, options?)`, `describeUserCreationContract(collectionAuth)` | `prepareUserCreation(values, options?)`, `describeUserCreationContract()` |
| `initializeDriver` con retorno `{ driver, collectionRegistry, … }`; `BackendInstance.collectionRegistry` | `{ driver, tableRegistry, … }`; `BackendInstance.tableRegistry` |
| `PolicyEvalContext.entity` (instancia de `Entity`) | `PolicyEvalContext.row` (los valores de la fila) |
| `wrapAsSdkData(…)` | `buildSdkData(driver)`; múltiples fuentes de datos: `buildRoutedSdkData` |
| `FindResponse` en `@rebasepro/client` | `FindResult` |
| `ListenCollectionRequest`, `ListenEntityRequest` en `@rebasepro/server` | `ListenCollectionProps`, `ListenOneProps` |

**Qué hacer:** elimina esos argumentos y procesa las tablas mediante `path`. El codemod registrará cualquier `implements DataDriver` como un paso manual pendiente. Consulta [Embedding the Postgres driver](/docs/backend/embedding-postgres-driver/).

## 138. El backend acepta los valores documentados en la API REST, y nada más

**A quién afecta:** clientes que envían una relación a uno en forma de objeto o un vector como `{ value }`, lógica que filtra relaciones mediante objetos, código que importa las clases de valores del panel y aplicaciones offline con mutaciones en cola generadas en 0.30.

**Qué cambió:** las peticiones de escritura adoptan la misma estructura devuelta en las lecturas — una representación única para REST, sockets, MCP y el SDK en el mismo proceso:

| Valor | Aceptado | Rechazado ahora |
|---|---|---|
| relación a uno (`belongsTo`, `hasOne`, `via` a uno) | la clave del registro vinculado, o `null` (`""` actúa como `null`), bajo el nombre de la relación o el de la clave foránea | un objeto como `{ "id": 5 }`: `400 VALIDATION_INVALID_VALUE`, "'posts.author' links one 'authors' row: write that row's key (a string or a number), or null to unlink — not an object." |
| relación a muchos (`hasMany`, `manyToMany`, `via` modificable a muchos) | un array de claves, o de `{ id, _pivot? }` | — (las demás propiedades del objeto se descartan, como antes) |
| vector | una lista de números | un `Vector`, o `{ "value": [...] }`: `400`, "'embedding' expects a vector as a list of numbers" |
| fecha, hora | texto ISO (`Date` en proceso) | — |
| geopoint | `{ latitude, longitude }` | — |
| `bytea` | una URL `data:application/octet-stream;base64,` (`Buffer` / `Uint8Array` en proceso) | — |
| filtro en relación | la clave | un objeto ya no se descompone: se compara tal cual se envía |

0.30 toleraba la escritura de relaciones a uno mediante un objeto, extrayendo silenciosamente su `id`; ese comportamiento nunca estuvo documentado y pertenecía al modelo de vista del panel. Actualmente, el panel transforma internamente su modelo de vista a valores de transporte en el navegador antes de procesar cualquier escritura o filtrado.

Las clases de valor del panel se reubicaron con el resto de su modelo de vista: `EntityReference`, `EntityRelation`, `GeoPoint`, `Vector` y `EntityReferenceProps` pasan a importarse desde `@rebasepro/cms-types` (salen de `@rebasepro/types`), al igual que `normalizeToEntityRelation` (sale de `@rebasepro/common`); `withRelationReferencesOnly` ha sido suprimido. El historial conserva las filas con la estructura devuelta por las lecturas; las entradas previas se entregarán y restaurarán como datos planos ([sección 132](#132-el-historial-se-sirve-como-lecturas)).

La cola de operaciones offline de `@rebasepro/client` opera con datos directos de red. Cualquier escritura encolada fuera de línea por el SDK de 0.30 se adaptará en el momento de leerse y sincronizarse: no se pierden datos encolados con anterioridad a la migración.

**Qué hacer:** envía la clave directamente: `{ "author": 5 }`, nunca `{ "author": { "id": 5 } }`; entrega los vectores como arrays numéricos y filtra relaciones por su clave. `rebase migrate sdk-calls` actualiza las importaciones de estas clases ([listado completo](/docs/upgrading/0-30-to-0-31-imports/)). Consulta [Writes](/docs/backend/writes/).

## 139. `/api/docs` se sirve a la audiencia del endpoint de esquemas

**A quién afecta:** cualquier usuario o automatización que consuma `/api/docs` o consulte `/api/swagger` — Swagger UI, generadores de clientes API o validaciones en CI.

**Qué cambió:** sin definir `enableSwagger` (o sin configurar `REBASE_ENABLE_SWAGGER`), en cualquier entorno, el esquema OpenAPI se entrega a los mismos emisores que tienen acceso a `GET /api/schema/tables`, aplicando los mismos bloqueos — 401 para peticiones no autenticadas salvo que aplique `schemaTables.public`, y 403 ante credenciales sin permisos de esquema o datos — entregando a cada solicitante la definición exacta de tablas, columnas y relaciones autorizadas para su perfil (los administradores ven todo). Swagger UI ya no se incluye. Un servidor sin mecanismos de autenticación devolverá `404 DOCS_UNAVAILABLE`. En 0.30 se exponía el documento íntegro, con todas las tablas y columnas públicas, a clientes anónimos en desarrollo, limitándolo a administradores en producción.

| `enableSwagger` / `REBASE_ENABLE_SWAGGER` | `/api/docs` | `/api/swagger` |
|---|---|---|
| no configurado (predeterminado) | a los mismos destinatarios del endpoint de esquemas: sus tablas autorizadas | no disponible |
| `true` | el documento completo, accesible a todos | accesible fuera de entornos de producción |
| `false` | el documento completo, restringido a administradores | no disponible |

**Qué hacer:** realiza las peticiones a `/api/docs` con sesión iniciada. Si requieres exponer la totalidad del documento como ocurría en desarrollo en 0.30, define `REBASE_ENABLE_SWAGGER=true` (o `enableSwagger: true`). Consulta [Endpoints](/docs/backend/endpoints/).

## 140. Una columna `pivot` many-to-many no puede declarar `.transform()`

**A quién afecta:** configuraciones `rel.manyToMany(…, { pivot: { … } })` cuya columna pivote declare un `.transform()`.

**Qué cambió:** el compilador abortará el proceso ("the pivot column "x" declares `.transform()` …"). Los transforms en columnas pivote nunca llegaron a ejecutarse en ningún flujo, de modo que cualquier dato que pretendías proteger u ocultar se estaba sirviendo en crudo.

**Qué hacer:** retira la declaración `.transform()` y aplica el enmascaramiento sobre `_pivot` dentro del hook `hooks.afterRead` de la tabla de destino. Consulta [Relations](/docs/collections/relations/).

## 141. Un enlace es exactamente tan legible y escribible como su columna de clave

**A quién afecta:** clientes que registren un `belongsTo` a través de su nombre de relación, filtren o consulten relaciones con restricciones en su columna clave, o dependan del comportamiento de `strictWrites: false`.

**Qué cambió:** toda restricción aplicada a una columna de clave se traslada automáticamente a cualquier identificador o sintaxis que intente leerla o escribirla.

- Escribir un enlace mediante el nombre de su relación (`{ "reviewer": 7 }`) se somete a todas las reglas de la columna clave configurada — `.readOnly()`, `.private()`, `access.write`, marcas temporales de creación, pertenencia a tenant, e inmutabilidad de clave — en REST, modificaciones en masa, `_batch`, sockets y MCP. Enviar el enlace usando ambos identificadores simultáneamente (`{ "reviewer": 7, "reviewerId": 8 }`) con datos contradictorios genera un error 400 `VALIDATION_INVALID_VALUE`. Intentar reasignar un registro a otro tenant mediante su relación devolverá 400 `TENANT_IMMUTABLE` (en versiones previas provocaba un 500).
- Una relación solo será legible si el emisor cuenta con permisos para leer cada columna involucrada en el join, en cada tabla intermedia: la clave del `belongsTo`, la clave foránea en la tabla destino para un `hasMany` / `hasOne`, y cada columna que sirva de puente en los pasos de un `via`. Si falla alguna comprobación, se excluirá de `include` y `_count`, y cualquier filtro, ordenación o recorrido de relación a través de ella responderá con `FIELD_NOT_READABLE` (o como relación inexistente si la columna es `.private()`). Una mutación sobre un `via` hacia un único elemento que intentase propagar una columna no legible para el emisor será rechazada con `FIELD_NOT_READABLE`. Las situaciones inversas y los casos basados en `via` también presentaban esta exposición en versiones 0.30.x.
- Si el usuario carece de lectura sobre la columna clave de un enlace, este se omitirá en `include`, y cualquier filtro, ordenación, entrada en `fields` o navegación a través de él responderá con `FIELD_NOT_READABLE`; un vínculo sujeto a una clave `.private()` figurará como relación inexistente. `GET /api/schema/tables`, OpenAPI y el comando MCP `describe_table` documentan el enlace junto a su clave correspondiente, de forma que una clave cuyo vínculo no esté expuesto tampoco se revelará allí.
- `strictWrites: false` solo rige una única función: delegar las propiedades no declaradas directamente al driver (guardándolas si la base de datos dispone de la columna, o devolviendo 400 `VALIDATION_UNKNOWN_FIELDS` en su defecto). Nunca eludirá la protección de una columna definida, una marca de auditoría, el tenant, la clave primaria, el destino de una relación o una regla configurada en `_pivot`.

**Qué hacer:** define los enlaces utilizando un único identificador, o ambos con idéntico valor; consume relaciones restringidas empleando un rol autorizado para consultar su clave. Consulta [Field access](/docs/collections/field-access/).
