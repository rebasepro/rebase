# Actualización de 0.30 → 0.31

<span class="since-badge" data-since="0.31">Desde 0.31</span>

0.31 convierte el backend en una arquitectura orientada a Postgres (Postgres-first). Las tablas que declara con `defineTable` en `backend/schema/` son lo único que el backend conoce sobre sus datos; lo que el panel de administración muestra sobre ellas reside en el frontend. Casi cada punto a continuación es una consecuencia de esa separación, y casi todo se realiza automáticamente con un solo comando.

### La lista de verificación, por proyecto

1. **Actualice primero cada paquete de `@rebasepro`**, en cada paquete del workspace, para que los tipos que lea el codemod sean los de la versión 0.31: `pnpm -r up "@rebasepro/*@0.31.0"`, luego `pnpm install`. Un proyecto en una versión anterior a 0.30 debe aplicar primero los cambios de código de las guías intermedias ([Actualización](/docs/upgrading/)), y cumplir con los requisitos mínimos de herramientas de 0.31: Node 22.22, TypeScript 6, React 19.2.7, React Router 8, Vite 8 ([la lista](/docs/upgrading/0-30-to-0-31-by-hand/#a-project-on-a-release-before-030)): el codemod carga un `config/` de 0.20–0.29 y su comprobación de SQL pasa, pero esa comprobación compara el compilador de 0.31 consigo mismo; solo el paso 7, contra su base de datos, demuestra que el DDL generado es el que realmente tiene su base de datos.
2. **Haga commit y luego ejecute el codemod como un simulacro (dry run):** `rebase migrate collections-to-tables --dry-run`. Imprime los archivos que escribiría, lo que rechaza (con archivo y línea), las notas y los pasos manuales, sin escribir nada. Corrija primero en `config/` lo que haya sido rechazado.
3. **Ejecútelo de forma definitiva:** `rebase migrate collections-to-tables`. Escribe `backend/schema/`, `frontend/src/cms/` (con `ui-config.json`), los módulos de `backend/` y los archivos del proyecto, añade `rebaseBackendGuard()` al `vite.config.ts` del scaffold, reescribe sus llamadas al SDK, mueve las importaciones de nombres que 0.31 trasladó a otro paquete ([sección 135](#135-rebaseprotypes-y-rebaseprocommon-eliminan-el-modelo-de-colecciones-de-sus-raíces)) y comprueba que el SQL generado sea idéntico byte por byte — o restaura cada archivo a su estado original. Consulte la [sección 108](#108-las-tablas-en-backendschema-reemplazan-a-configcollections-ejecute-el-codemod-primero).
4. **Lea la última sección de su salida, "Revisar antes de desplegar: estas reglas cambian de significado"**, y decida sobre cada regla listada ([más abajo](#revisar-antes-de-desplegar-estas-reglas-cambian-de-significado)).
5. **Realice los pasos manuales que imprime**, en orden. Cada uno indica su archivo y la mayoría incluye el fragmento de código a escribir: el montaje de `<RebaseCMS>` con `tableCustomizations` y `uiConfig` cuando su `App.tsx` no es el del scaffold (o el panel está montado en otro módulo, el cual se indica en el paso), `rebaseBackendGuard()` cuando su `vite.config.ts` no lo es y en cada otra aplicación estática de `rebase.json` ([sección 130](#130-rebase-build-rechaza-un-frontend-sin-rebasebackendguard)), hooks globales, una importación de un nombre que 0.31 eliminó ([sección 135](#135-rebaseprotypes-y-rebaseprocommon-eliminan-el-modelo-de-colecciones-de-sus-raíces)) y `rebase skills install` cuando el proyecto contiene agent skills ([sección 128](#128-la-skill-del-agente-rebase-collections-ahora-es-rebase-tables)). Ejecute `pnpm install` cuando la salida liste "Dependencies added". Luego lea dos listas en la parte del SDK de la salida:
   - **"Rewritten by name — review"**: llamadas `.collection(` en un receptor sin tipo (`any`), reescritas porque el receptor se llama `dataAsAdmin`, o es `.data` con un nombre de tabla literal; el miembro `collection` de un tipo que contiene un slot `data` / `dataAsAdmin`; y dobles de prueba (test doubles). Verifique que cada uno pertenezca al SDK.
   - **"Left unchanged — check each"**: llamadas `.collection(` que el codemod no pudo verificar que pertenecieran al SDK, como una llamada a través de un tipo declarado por su propio proyecto. Una llamada que permanezca aquí y que *sea* del SDK fallará en tiempo de ejecución en 0.31: cámbiele el nombre a `.table(` manualmente. El código que comprueba si `collection` existe (`typeof data.collection === "function"`) es un paso manual: en 0.31 tomará silenciosamente la otra rama.

   Un archivo commiteado como salida de compilación (un `.js` empaquetado o minificado) nunca se edita: se lista para que lo recompile después de migrar, y reemplace cualquier copia vendored del cliente con la compilación de 0.31. Los pasos repetidos de un mismo tipo se imprimen una sola vez, listando cada archivo y línea afectados; `--json` mantiene cada paso por separado. Luego lea [Qué cambiaron los proyectos manualmente](/docs/upgrading/0-30-to-0-31-by-hand/): las modificaciones que proyectos reales tuvieron que hacer tras estos pasos.
6. **`rebase generate-sdk`**: los nombres de los módulos generados han cambiado ([sección 115](#115-el-sdk-referencia-una-tabla-datatableslug)).
7. **Contra su base de datos**, ejecute `rebase db push --dry-run` y espere ver "No changes: the database already matches these tables.", luego ejecute `rebase doctor --policies` y espere que no haya discrepancias en las políticas. La comprobación de SQL del codemod demuestra que la conversión es fiel; estas dos validaciones lo confirman contra la base de datos real, y cualquier diferencia de políticas que cualquiera de ellas liste representa un cambio en quién puede acceder a qué.
8. **`rebase verify`**: ahora también lee `frontend/src/cms`: una personalización que nombre una tabla o campo inexistente, una columna requerida omitida en el formulario, un `rebaseBackendGuard()` faltante o un `ui-config.json` no pasado a `<RebaseCMS>`.
9. **Ejecute la línea `git rm` que imprimió el codemod** una vez revisado el diff: `git rm -r config/collections …` y las conexiones que se movieron a `backend/`, o `git rm -r config` cuando no quede nada propio allí ([sección 109](#109-ya-no-existe-el-paquete-config)).
10. **Recompile y despliegue.** Un bundle compilado antes de 0.31 no arrancará en un runtime de 0.31 ([sección 112](#112-formato-de-bundle-3-se-rechazan-los-bundles-de-formato-2)). El primer arranque actualizará la versión del esquema de la base de datos una sola vez ([sección 113](#113-la-versión-del-esquema-se-calcula-a-partir-de-las-tablas-v2)).

Ejecute `rebase migrate collections-to-tables --check` en CI hasta que `config/` haya sido eliminado: verifica que las tablas migradas sigan generando el mismo SQL que las colecciones de origen, y sale con código 1 si alguna regla listada en "Revisar antes de desplegar" no ha sido confirmada; use `--accept-rule-changes` una vez que las haya revisado.

### Revisar antes de desplegar: estas reglas cambian de significado

El codemod traslada cada regla de seguridad tal como está escrita, y cada una conserva el nombre de su política. Sin embargo, el compilador de 0.30 solo leía la primera opción entre `condition`, `using`, `access: "public"` y `ownerField`, y no reconocía ningún otro valor de `access`, por lo que cuatro variantes de reglas ahora otorgan permisos distintos. Dos de ellas amplían el acceso:

| La regla | 0.30 otorgaba | 0.31 otorga | |
|---|---|---|---|
| un simple `access: "authenticated"` (sin `roles`) | nada | cualquier invocador autenticado, incluidos invitados | **amplía** |
| `access` + `check`, sin `condition`, en `select` / `update` / `delete` / `all` | ninguna fila existente | todas las filas existentes, a los invocadores de `access` | **amplía** |
| `access: "authenticated"` + `condition` | cualquiera que cumpla `condition` | solo invocadores autenticados que la cumplan | restringe |
| `access: "authenticated"` + `check`, en `insert` | cualquiera que inserte una fila coincidente | solo invocadores autenticados | restringe |

La más común es la primera. Escriba `access: "registered"` para admitir únicamente a invocadores con cuenta (no invitados anónimos), o elimine la regla para continuar sin otorgar nada. `access` con `roles`, y un `condition` como objeto simple, significan lo mismo que antes y no se listan.

El codemod también rechaza cualquier regla que el compilador de 0.31 rechace: una que combine cláusulas que el tipo `SecurityRule` excluye (`access` junto a `ownerField`, `using` o `withCheck`; `ownerField` junto a `using`, `withCheck`, `condition` o `check`; `condition` o `check` junto a `using` o `withCheck`), y una con un valor no válido de `access`, `mode`, `operation(s)` o `roles` (un `"restrictive"` mal escrito solía compilarse como permisivo). Consulte [Reglas de seguridad](/docs/collections/security-rules/).

### Qué más se comporta de forma diferente

- **Lo que `GET /api/schema/tables` muestra a un usuario.** Los administradores y quienes posean `schema:read` obtienen todas las tablas. Cualquier otro usuario autenticado, incluidos invitados, solo obtiene las tablas alcanzables por sus roles, con únicamente las reglas aplicables a ellos; las relaciones hacia otras tablas se descartan y los flags de hooks se retienen. Un frontend que leía la descripción de otra tabla como usuario estándar recibirá menos información; `schemaTables: { persons: "all" }` en las opciones del backend restablece la descripción completa. Consulte [Endpoints](/docs/backend/endpoints/#schema).
- **Los nombres de las relaciones son exactos**, y **las claves foráneas de tipo big-integer son números** ([sección 131](#131-las-filas-en-tránsito-siguen-a-su-columna)).
- **El historial se sirve enmascarado** ([sección 132](#132-el-historial-se-sirve-como-lecturas)).
- **Los nombres de herramientas MCP y el payload de la vista** cambian a la par para el conector alojado y los runtimes a los que accede ([sección 122](#122-las-herramientas-mcp-se-nombran-para-tablas)).
- **Restricciones intencionales.** Los sellos de auditoría (columnas `.onCreateNow()` / `.onUpdateNow()`) se ocultan de las columnas de lista del panel de forma predeterminada: una lista migrada que mostraba `created_at` perderá esa columna hasta que defina `fields: { created_at: { hidden: false } }` en su `customizeTable`. El codemod rechaza, indicando el motivo: arrays JSON de tuplas, un `vector` / `binary` / `reference` dentro de un map, `databaseId` en una colección de Postgres, `isId: "cuid"`, una relación única con `isId` y `disableDefaultPolicies: true` sin reglas. Una relación de una columna hacia una tabla con clave compuesta es rechazada (defínala con `rel.via()`). Los tags de OpenAPI provienen del slug, no del nombre para mostrar. `rebase schema introspect` omite tablas sin clave primaria e indica el motivo (un servidor que introspeccione la base de datos la seguirá sirviendo). Una vista simple que declare `roles` es un error de compilación; el codemod la descarta con una nota.
- **Qué cambiaron los proyectos reales manualmente**: requisitos de herramientas, `({ entity })` en código de administración, includes de relaciones renombradas, objetos de colección modificados en runtime, llamadas SDK en receptores sin tipo: [Qué cambiaron los proyectos manualmente](/docs/upgrading/0-30-to-0-31-by-hand/).
- **Restauración en otro clúster.** El sello de las políticas de administración predeterminadas genera un hash a partir de los OID de los roles, por lo que tras un dump o una restauración point-in-time en un clúster diferente, el primer `db push` o arranque recreará esas políticas una sola vez, con los mismos nombres y el mismo SQL.

### Los términos

| Antes | Ahora | Dónde permanece "collection" |
|---|---|---|
| una colección en `config/collections/` | una **tabla** en `backend/schema/` (`defineTable`) | — |
| `properties` | `columns` (`col.*`) y `relations` (`rel.*`) | — |
| `securityRules`, `defaultSecurityRules` | `rls` (requerido), `defaultRls` | — |
| `callbacks`, `Property.callbacks` | `hooks`, el `.transform()` de una columna | — |
| el bloque `admin` | `customizeTable` en `frontend/src/cms/` | — |
| `data.collection(slug)` | `data.table(slug)` | — |
| lo que dibuja el panel de administración | una **colección**: una tabla tal como la muestra el panel, o una colección de Firestore | el CMS: `CollectionPanel`, el Collection Editor, `externalCollections` |

## 108. Las tablas en `backend/schema` reemplazan a `config/collections`: ejecute el codemod primero

**A quién afecta:** a todos los proyectos con un directorio `config/collections/`.

**Qué cambió:** el backend solo lee `backend/schema/index.ts` y los resultados exportados por `defineTable`, `defineAuthTable` y `defineView`. Los archivos de `defineCollection` no son leídos por nada: el runtime, cada comando de CLI y la validación de `rebase.json` rechazan cualquier proyecto que aún conserve `config/collections`, indicando el comando siguiente. `rls` es obligatorio en cada tabla (una lista de reglas, `"admin-only"`, o `"inherit"` para el `defaultRls` que exporta el index), y `disableDefaultPolicies` ahora es `defaultPolicies: false`.

**Qué hacer:**

```bash
rebase migrate collections-to-tables            # o --dry-run primero
```

Escribe una tabla por colección, haciendo explícita cada columna física en su posición original (de modo que la columna de clave de un `belongsTo` queda escrita explícitamente), el index con `defaultRls` a partir de `defaultSecurityRules`, un `customizeTable` para cada colección cuya presentación no fuera la predeterminada y archivos `defineFirestoreCollection` para colecciones de Firestore. Los callbacks de una colección pasan a ser los `hooks` de su tabla y los `.transform()` de sus columnas; los `callbacks` globales que exportaba `config/index.ts` requieren un paso manual (sección 109). A continuación, vuelve a leer el resultado mediante el nuevo pipeline: el DDL, las políticas, la búsqueda, los vectores, los triggers, las vistas y el esquema de Drizzle deben ser idénticos byte por byte a lo que generaban las colecciones, o de lo contrario se restaura cada archivo y el comando termina con código 1 mostrando el diff.

También traslada automáticamente lo que antes requería trabajo manual:

- **Callbacks creados mediante un helper** (`callbacks: softDeleteCallbacks(...)` o un objeto de callbacks importado) pasan a ser `hooks:` con la misma expresión, y las funciones del helper se convierten en props de table-hook donde estén definidas (el codemod sigue importaciones relativas, `const`, accesos a propiedades y sentencias `return` simples). Cuando no puede rastrear el helper, un paso indica los hooks que deben revisarse.
- **Una función en `storagePath`** se migra en dos partes: la función pasa a ser el `storage.path` de la personalización, de modo que el panel sigue decidiendo a dónde va una subida, y la plantilla `path` de la columna toma la forma de las claves que devuelve: el texto estático de su template literal con cada `${…}` reemplazado por `{path}` (`` `${owner}/cv` `` → `{path}/cv`). Ahora el servidor aplica `maxBytes` y `accept` de la columna a cada subida cuya clave coincida con esa plantilla, no solo a la que nombre la columna, por lo que los límites son más estrictos que en 0.30. Una función cuyo resultado no contenga texto estático es rechazada: asígnele uno primero.
- **Un `policy.existsIn({ collection })` de 0.30** mantiene su tabla, y `auth: { collection: usersCollection }` en un entry personalizado del backend se elimina (el `defineAuthTable` pasa a ser la tabla de autenticación). La opción de arranque `collections` se convierte en `schemaDir`.
- **Un builder de `dynamicProps`** devuelve una personalización de campo con claves planas en 0.31 (`{ readOnly: true }`, no `{ admin: { readOnly: true } }`). El codemod reescribe aquellos builders cuyos retornos sean literales de objeto, en línea o en un módulo compartido, y lista cualquier otro caso.
- **La presentación propagada desde un objeto compartido** se traslada a la personalización (`….dynamicProps`); la presentación calculada por una función envoltorio genera un paso a revisar, no el rechazo del proyecto. La ruta de un componente se resuelve contra el módulo que la definió, y cualquier valor calculado cuando se carga `config/` (`new Date()`, `Date.now()`, lecturas de entorno) se preserva como su expresión correspondiente, nunca congelado al valor de la ejecución.
- **Colecciones de Firestore construidas por una función** (un `getAllFirestoreCollections()` propagado al panel) se convierten a `defineFirestoreCollection` una a una donde el archivo de la colección contenga su literal; un paso por cada builder indica los restantes y la estructura requerida, y otro señala cualquier referencia escrita fuera de un literal convertido, que todavía diría `path`.
- **Las importaciones de `config/` mediante alias de ruta** (una entrada en `paths` de tsconfig o un `resolve.alias` de Vite) se reescriben o listan igual que las relativas, y cualquier `storageAuthorize` reexportado por `config/index.ts` se traslada a `backend/storage.ts`.
- **Una relación renombrada a `<key>Relation`** conserva su etiqueta, columna en la lista y título: la personalización referencia la nueva clave. El código que la incluye mediante `include` no se actualiza automáticamente ([qué modificar](/docs/upgrading/0-30-to-0-31-by-hand/#a-belongsto-key-is-a-column-and-a-relation-can-be-renamed)).

Aquello que no pueda trasladarse con exactitud será rechazado indicando archivo y línea, sin escribir nada en disco: una colección creada invocando una función, un spread o accessor que no pueda resolverse, un motor distinto de Postgres o Firestore, o un archivo de salida que ya exista con contenido diferente (muévalo o use `--force`). Un árbol de git con cambios sin commitear o un proyecto fuera de git también serán rechazados, garantizando que la migración sea un único diff revisable. `--json` imprime el informe completo para scripts o agentes. Consulte [`rebase migrate`](/docs/cli/schema/#rebase-migrate) y [Tablas](/docs/schema/).

Las tablas generadas declaran sus columnas siguiendo la sintaxis de `pg-core` de Drizzle: `col.varchar({ length: 160 })`, `col.timestamp({ withTimezone: true })`, `col.text().array()`, `pgEnum(...)`, `` .default(sql`…`) ``, `.generatedByDefaultAsIdentity()`, por lo que su salida no requiere ajustes adicionales; consulte [Columnas](/docs/schema/columns/). Una tabla escrita a mano contra una versión previa de 0.31 con las sintaxis anteriores (`col.timestamptz()`, `col.varchar(160)`, `col.array(col.text())`, `col.enum(values, { name })`, `.defaultSql()`, `.identity()`, `.column("…")`) ya no compilará: `tooling/scripts/drizzle-sweep.mts` en el repositorio de Rebase la convierte reescribiendo únicamente las cadenas de builders, y con `--verify` comprueba que cada tabla convertida compile con el mismo descriptor (`npx tsx drizzle-sweep.mts --verify backend/schema`).

El paso posterior `sdk-calls` también reescribe el origen de las reglas: `existsIn({ collection })` y `membership: { collection }` pasan a ser `table` (sección 123); `--skip-sdk-calls` omite también esta parte. Lo que quede pendiente se imprimirá como pasos manuales numerados, y si el proyecto tiene agent skills instaladas, el último paso será la línea `rebase skills install` para actualizarlas (sección 128). Ejecutar `rebase migrate` sin argumentos muestra la ayuda para ambos subcomandos.

## 109. Ya no existe el paquete config

**A quién afecta:** a todos los proyectos (`config/` constituía un workspace independiente).

0.31 deja de leer `config/collections`; no prohíbe el uso de `config/`. El codemod elimina lo que Rebase leía —los archivos de colección y las conexiones que traslada a `backend/` (`resources.ts`, `storage.ts`, `generated/register.ts`, y las reexportaciones de estos en `config/index.ts`)— y mantiene sus propios módulos en `config/` intactos, importables como siempre: `config/` sigue siendo un paquete del workspace y el backend continúa compilando `../config/**/*`. Solo se reescriben las importaciones de los elementos eliminados: un archivo de colección importado por código de backend apuntará al módulo de la tabla correspondiente (un paso listará los usos que lo leen como un objeto); si es importado por código de frontend, se convertirá en una importación de tipo de la tabla cuando solo se use como tal, o en un paso que indique la personalización; cualquier helper dentro de `config/collections` se copiará junto al código que lo requiera.

**Qué cambió:** los elementos situados junto a las colecciones se trasladan a `backend/`:

| Antes | Ahora |
|---|---|
| `config/resources.ts` | `backend/resources.ts` |
| `config/storage.ts`, `storageAuthorize` desde `config/index.ts` | `backend/storage.ts` |
| `callbacks` exportados desde `config/index.ts` | `hooks` exportados desde `backend/hooks.ts` (`TableHooks`: `table` en lugar de `collection`, `values` en lugar de `row`) |
| `config/generated/register.ts` | `backend/generated/register.ts` |
| `rebase.json` `config`, `usersCollection` | `tables` (por defecto `backend/schema`); la tabla de autenticación es la declarada con `defineAuthTable` |

El runtime lee `storageAuthorize` y `hooks` y nada más de esos módulos; cualquier otra exportación se notificará en el arranque. El frontend solo debe importar `backend/**` como tipos: `pnpm check:frontend-backend-imports` rechazará cualquier importación por valor, ya que incluiría código del servidor en el bundle del navegador.

**Qué hacer:** el codemod mueve `resources.ts`, `storage.ts` y el registro, y reescribe `rebase.json`, `package.json`, `pnpm-workspace.yaml` y `backend/tsconfig.json`. Los `callbacks` globales se presentan como un paso manual impreso: muévalos a `backend/hooks.ts` manualmente y agregue `hooks.ts` al array `include` de `backend/tsconfig.json` para que `tsc` lo verifique. Luego ejecute la línea de `git rm` generada: `git rm -r config/collections …`, o `git rm -r config` cuando no quede nada propio.

## 110. Las opciones de arranque y los hooks nombran tablas

**A quién afecta:** a backends iniciados manualmente (`initializeRebaseBackend`, `createRebaseBackend`) y al código que vincula hooks tras el arranque.

**Qué cambió:**

| Antes | Ahora |
|---|---|
| `collections`, `collectionsDir` | `tables`, `defaultRls`, `schemaDir` |
| `callbacks` | `hooks` |
| `auth.collection` | eliminado: ahora es el `defineAuthTable` en `tables` |
| `backend.setCollectionCallbacks(slug, cb)` | `backend.setTableHooks(slug, hooks)` |
| props del hook: `collection`, `row` | `table` (el descriptor), `values` |
| `composeCallbacks` | `composeTableHooks` desde `@rebasepro/common` |
| `openRebase({ collections, callbacks })` | `openRebase({ tables, hooks })`, `tables` desde `compileSchema([...])` |
| `OpenedRebase.collections`; la variable de `rebase console` `collections` | `.tables`; `tables` |

```diff ts
-await initializeRebaseBackend({ app, server, collectionsDir: "./config/collections", callbacks });
+await initializeRebaseBackend({ app, server, schemaDir: path.resolve(__dirname, "../schema"), hooks });
```

Los hooks asociados a un objeto de colección pasado directamente en una llamada ya no se ejecutan: el driver ejecuta los hooks de las tablas que sirve, por lo que deben asociarse mediante `setTableHooks`.

**Qué hacer:** `rebase migrate sdk-calls` reescribe `setCollectionCallbacks` y adapta las props del hook, listando cada objeto de opciones de backend que deba actualizarse manualmente. Un script que abra los datos compila sus tablas:

```diff ts
-const rebase = await openRebase({ databaseUrl, collections, callbacks });
+const rebase = await openRebase({ databaseUrl, tables: compileSchema([products, orders]), hooks });
```

Consulte [Scripts](/docs/backend/scripts/#openrebase). Consulte [Visión general del backend](/docs/backend/) y [Hooks globales](/docs/backend/hooks/).

## 111. El panel de administración renderiza las tablas que sirve el servidor

**A quién afecta:** a todos los frontends que montan `<RebaseCMS>`.

**Qué cambió:** `<RebaseCMS collections>` ha sido eliminado. El panel muestra cada tabla que el backend sirve en `GET /api/schema/tables`, sin requerir un archivo por tabla, seguido de `externalCollections` (Firestore). `tableCustomizations` recibe los objetos `customizeTable` procedentes de `frontend/src/cms/`. El plugin de colecciones para Vite y `virtual:rebase-collections` han sido eliminados. `CollectionsProvider` acepta las mismas tres entradas (`tableCustomizations`, `externalCollections`, `tables`).

```diff tsx
-import { collections } from "virtual:rebase-collections";
-<RebaseCMS collections={collections}/>
+import { postsCms } from "./cms/posts";
+<RebaseCMS tableCustomizations={[postsCms]}/>
```

**Qué hacer:** el codemod crea `frontend/src/cms/index.ts`, que exporta `tableCustomizations` (y `externalCollections`), y lo monta automáticamente en el `App.tsx` del scaffold; si no reconoce `App.tsx`, el plugin en `vite.config.ts` y la declaración del módulo virtual se presentarán como pasos manuales en la salida. Consulte [Personalizar una tabla](/docs/frontend/customize-table/).

## 112. Formato de bundle 3; se rechazan los bundles de formato 2

**A quién afecta:** a cualquier despliegue de un bundle compilado, ya sea autoalojado con la imagen de runtime o en Rebase Cloud.

**Qué cambió:** el esquema del bundle es `entry.tables`, junto a `entry.resources`, `entry.storage` y `entry.hooks`; `bundleFormat` pasa a ser 3 y el contrato de runtime es 2. Un bundle de formato 1 o 2 incluye `config/collections`, el cual un runtime de 0.31 no puede interpretar, por lo que rechazará el arranque indicando el codemod en el mensaje de error en lugar de introspeccionar la base de datos y servir una API inconsistente.

**Qué hacer:** migre el código fuente, luego ejecute `rebase build` y despliegue. En Rebase Cloud, desplegar el repositorio migrado recompilará la aplicación automáticamente. Consulte [Runtime y bundles](/docs/architecture/runtime-and-bundles/).

## 113. La versión del esquema se calcula a partir de las tablas (`v2:`)

**A quién afecta:** a toda base de datos aprovisionada por un runtime anterior a 0.31 y a cualquier SDK generado.

**Qué cambió:** la versión del esquema genera un hash a partir de los descriptores compilados de las tablas y comienza con el prefijo `v2:`. Una base de datos marcada con `v1:` reportará el cambio de modelo una sola vez —el log de arranque y `rebase doctor` lo indicarán junto con las instrucciones para actualizar el sello— y cada SDK generado será marcado como desactualizado una vez.

**Qué hacer:** aprovisione una vez con el nuevo runtime: inicie el proceso que controla el esquema o ejecute `rebase db push`. Con `REBASE_REQUIRE_SCHEMA_MATCH=true`, actualice el sello antes de desplegar el resto de procesos. Regenere el SDK.

## 114. Los códigos de error nombran tablas

**A quién afecta:** al código que evalúa un `code` de error de forma condicional.

**Qué cambió:**

| Antes | Ahora |
|---|---|
| `NO_COLLECTIONS` (404) | `NO_TABLES` |
| `COLLECTION_READ_ONLY` (405) | `TABLE_READ_ONLY` |
| `UNKNOWN_COLLECTION` (SDK) | `UNKNOWN_TABLE` |
| `INVALID_COLLECTION_PATH` (SDK) | `INVALID_TABLE_PATH` |

**Qué hacer:** `rebase migrate sdk-calls` reescribe los literales de cadena. Consulte [Errores](/docs/backend/errors/).

## 115. El SDK referencia una tabla: `data.table(slug)`

**A quién afecta:** a todo cliente, función, cron, hook y script que referencie una tabla por su slug o pase el diccionario generado.

**Qué cambió:**

| Antes | Ahora |
|---|---|
| `data.collection(slug)` | `data.table(slug)` |
| `createRebaseClient({ collections: collectionsDictionary })` | `createRebaseClient({ tables: tablesDictionary })` |
| generados: `CollectionName`, `CollectionsDictionary` | `TableName`, `TablesDictionary` |
| batch: `{ op, collection }` (SDK y `POST /api/data/_batch`) | `{ op, table }` |
| `CollectionClient`, `SDKCollectionClient`, `CollectionAccessor`, `CollectionTrashAccessor` | `TableClient`, `SDKTableClient`, `TableAccessor`, `TableTrashAccessor` |
| offline: `maxCachedRowsPerCollection`, `maxCachedQueriesPerCollection` | `…PerTable` |
| accessor reservado: `<name>Collection`; `collectionCollection` | `<name>Table`; la tabla `collection` es `collection` |

```diff ts
-const { data } = await client.data.collection("posts").find();
+const { data } = await client.data.table("posts").find();
```

Los accessors tipados (`client.data.posts`) no sufren cambios.

**Qué hacer:** el codemod ejecuta `rebase migrate sdk-calls` sobre su código (ejecútelo individualmente si el proyecto ya fue migrado) y luego `rebase generate-sdk`. Toda llamada `.collection(` cuyo receptor no sea el SDK permanecerá inalterada y será listada. Consulte [SDK tipado](/docs/sdk/).

## 116. Flags de la CLI: `--schema-dir`, no `--collections`

**A quién afecta:** a scripts y pasos de CI que invocan la CLI con una ruta de esquema.

**Qué cambió:** `--collections` / `-c` se rechazan en cualquier comando que lea el esquema, sugiriendo el codemod en el mensaje de error (`generate-sdk` ignora un `--collections-dir` residual); `--schema-dir` permite especificar un directorio de esquema distinto de `backend/schema`. `rebase schema introspect` escribe archivos `defineTable` en `backend/schema/` (`--output` ha sido eliminado). `REBASE_STRICT_COLLECTION_CONFIG` ya no se evalúa: un esquema que no compile impedirá siempre el arranque.

**Qué hacer:** reemplace los flags correspondientes. Consulte [CLI](/docs/cli/) y [Generación de esquemas](/docs/cli/schema/).

## 117. El editor de esquemas edita `backend/schema` con `TablePatch`

**A quién afecta:** al código que invoca las rutas del editor de esquemas o de esquema en vivo, y a los despliegues que configuran variables de edición en vivo.

**Qué cambió:** las rutas `/api/admin/schema-editor/collection/save`, `collection/delete`, `property/save` y `property/delete` han sido eliminadas. El editor ahora sirve `GET /tables`, `POST /preview` y `POST /apply`, y las rutas `/plan` y `/apply` de edición de esquema en vivo reciben `{ patches: TablePatch[] }` en lugar de una colección o un parche de esta. `REBASE_LIVE_SCHEMA_COLLECTIONS_PATH` se rechaza en el arranque: debe usarse `REBASE_LIVE_SCHEMA_PATH` (por defecto `backend/schema`), y `liveSchema.repository.collectionsPath` pasa a ser `schemaPath`. La presentación nunca constituye una edición de esquema: se almacena como preferencias de UI (`/api/admin/ui-config`). Cualquier edición cuyo archivo haya cambiado en disco tras prepararse la modificación (guardado en el IDE, otro proceso) responderá con 409 `SCHEMA_EDIT_STALE_FILE` sin escribir nada (anteriormente devolvía 400 `SCHEMA_EDIT_REFUSED`).

**Qué hacer:** renombre la variable; adapte quien invoque las rutas para enviar modificaciones con `TablePatch` y recargue en caso de recibir `SCHEMA_EDIT_STALE_FILE`. Consulte [Edición de esquema en vivo](/docs/backend/live-schema-editing/).

## 118. Un slot de componente es un componente

**A quién afecta:** a las personalizaciones que definían un componente de React mediante una ruta de texto o una función diferida `() => import(…)`.

**Qué cambió:** los elementos `Field` / `Preview` / `Filter` de un campo, las `Actions` de colección, `entityViews[].Builder`, `collectionViews[].Builder`, `formView.Builder` y las sustituciones de componentes aceptan directamente el componente en sí. `ComponentRef`, `ComponentLike`, `LazyComponentRef` y `isLazyComponentRef` (`@rebasepro/types`), `asComponentRef` y `asReactComponent` (`@rebasepro/cms-types`) y `resolveComponentRef` / `useResolvedComponent` (`@rebasepro/app`) han sido eliminados. `customizeTable` rechaza cadenas de texto o funciones diferidas mostrando el mensaje "imported by value".

**Qué hacer:** importe el componente en el archivo dentro de `frontend/src/cms/` y páselo directamente. Consulte [Campos personalizados](/docs/frontend/custom-fields/).

## 119. Las preferencias del panel son preferencias de UI

**A quién afecta:** al código que implementa `UserConfigurationPersistence`.

**Qué cambió:** la forma en que un usuario redimensiona o reordena una tabla se maneja como un delta de `UiTablePreferences`: `getTablePreferences` / `saveTablePreferences` reemplazan a `getCollectionConfig` / `onCollectionModified`, y el tipo parcial de configuración de colección que recibía ha sido eliminado. El almacenamiento del navegador las guarda bajo `table_preferences::<slug>` e ignora los datos guardados por paneles antiguos, por lo que el ancho de columnas y los modos de visualización de cada usuario se restablecerán una vez. Se eliminó `userSelect` en los campos: una columna `.userId()` actúa como selector de usuario.

El puente de Studio se adapta en consecuencia: `StudioSchemaEditing.updateCollection` pasa a ser `applyTablePatches(slug, patches)`, y el editor de colecciones envía `{ patches }` al editor de esquemas.

**Qué hacer:** adapte cualquier persistencia personalizada a los dos métodos nuevos, y cualquier `StudioSchemaEditing` personalizado a `applyTablePatches`.

## 120. Se retira el soporte para MongoDB

**A quién afecta:** a proyectos que utilicen `@rebasepro/server-mongo` o que declaren `database(…, { engine: "mongodb" })`.

**Qué cambió:** el paquete ha sido eliminado, junto con los tipos de colección de Mongo y el resto de su modelo. Postgres es el único motor de base de datos para el servidor: un origen de transporte de servidor configurado con otro motor impedirá el arranque, señalándolo explícitamente.

**Qué hacer:** migre los datos a Postgres. No existe un mecanismo de migración interno dentro de Rebase.

## 121. Las colecciones de Firestore residen en el frontend

**A quién afecta:** a proyectos híbridos con colecciones que utilizan `engine: "firestore"`.

**Qué cambió:** una colección de Firestore es un origen de CMS que el navegador consulta directamente: se declara con `defineFirestoreCollection` de `@rebasepro/firebase`, dentro de `frontend/src/cms/`, y se pasa a `<RebaseCMS externalCollections>`. Las referencias entre Firestore y una tabla de Postgres se almacenan utilizando el identificador de la entidad de destino, y una referencia de Firestore cuyo `path` coincida con el slug de una tabla de Postgres apuntará a dicha tabla.

**Qué hacer:** el codemod genera los archivos `defineFirestoreCollection`. Apunte las referencias a colecciones de Firestore utilizando el slug de la colección. Consulte [Firebase](/docs/frontend/firebase/).

## 122. Las herramientas MCP se nombran para tablas

**A quién afecta:** a prompts, scripts y listas de permisos que hagan referencia a herramientas MCP.

**Qué cambió:** en `/mcp` remoto: `list_collections`, `describe_collection`, `query_collection`, `show_collection`, `count_documents`, `aggregate_documents`, `get_document`, `create_document`, `update_document`, `delete_document` pasan a llamarse `list_tables`, `describe_table`, `query_table`, `show_table`, `count_rows`, `aggregate_rows`, `get_row`, `create_row`, `update_row`, `delete_row`; el argumento `collection` pasa a ser `table`, y `show_app` / `save_app` aceptan `tables`. En el servidor local: `list_documents` → `query_table`, `get_document` → `get_row`, `create_document` → `create_row`, `update_document` → `update_row`, `delete_document` → `delete_row`; `rebase_schema_plan` recibe `patches`; los recursos son `rebase://tables/{name}`. El payload de vista de MCP Apps utiliza la versión 3: descriptores de tablas filtrados según el invocador, permisos por tabla y preferencias de UI de cada usuario en `preferences` (`file`, `workspace`, `user`; una API key no tiene capa de usuario), con bloques y seeds haciendo referencia a `table`. La vista `collection-table` ha sido eliminada. `list_tables` ya no incluye `title`; `describe_table` añade `primaryKey`, `relations`, el `rls` aplicable al invocador, `title` y `presentation`.

**Qué hacer:** renombre las herramientas. La vista y el servidor deben manejar la misma versión de payload: los conectores alojados y los runtimes a los que se conectan deben actualizarse conjuntamente, y cualquier vista MCP personalizada en el proyecto debe recompilarse con los paquetes de 0.31. Consulte la [Referencia de herramientas MCP](/docs/ai/mcp-tool-reference/) y [MCP remoto](/docs/ai/remote-mcp/).

## 123. El vocabulario de las reglas usa `table`

**A quién afecta:** a las reglas que emplean `policy.existsIn` o un tenant por membresía, así como a las reglas que combinan `access` con otras cláusulas.

**Qué cambió:** `policy.existsIn({ collection, where })` pasa a ser `existsIn({ table, where })`, y `tenant.from.membership.collection` pasa a ser `membership.table`; los nombres de las políticas no se modifican. Cuatro estructuras de reglas otorgan ahora permisos distintos, dos de ellas ampliando el acceso ([la tabla anterior](#revisar-antes-de-desplegar-estas-reglas-cambian-de-significado)): un simple `{ access: "authenticated" }`, que no otorgaba nada, ahora admite a cualquier invocador autenticado, y las tablas intermedias (junctions) de dicha tabla adquieren sus políticas de escritura de relaciones (edge-write). Las reglas que combinen cláusulas excluidas por el tipo `SecurityRule`, o que contengan un valor inválido en `access`, `mode`, `operation` o `roles`, serán rechazadas.

**Qué hacer:** el codemod renombra las claves, rechaza las reglas no válidas indicando archivo y línea, y lista aquellas que cambian de significado bajo "Revisar antes de desplegar". Para cada una: manténgala, defina `access: "registered"` (usuarios autenticados con cuenta) o elimínela. Posteriormente, ejecute y revise `rebase db push --dry-run` y `rebase doctor --policies` contra su base de datos.

## 130. `rebase build` rechaza un frontend sin `rebaseBackendGuard()`

**A quién afecta:** a todos los proyectos con frontend.

**Qué cambió:** el frontend únicamente puede importar contenido de `backend/` como tipos. Una importación por valor incluiría código del servidor (hooks y cualquier secreto asociado) en el bundle del navegador. `rebaseBackendGuard()` de `@rebasepro/app/vitePlugin` interrumpe `vite build` y `vite dev` si algún módulo del frontend resuelve dependencias hacia `backend/`, indicando el módulo importador, la importación y el archivo afectado, tras evaluar alias, rutas de tsconfig, resolución por paquete o absoluta, globs, `?raw`, reexportaciones e importaciones dinámicas. `rebase build`, al igual que la compilación de frontend ejecutada por `rebase cloud deploy`, rechaza frontends cuya configuración de Vite no incluya este guard; `rebase dev` emite una advertencia; `rebase verify` reporta `cms-backend-guard-missing`.

**Qué hacer:** el codemod lo incorpora automáticamente al archivo `frontend/vite.config.ts` del scaffold, e imprime las instrucciones para cualquier otra configuración:

```diff ts
+import { rebaseBackendGuard } from "@rebasepro/app/vitePlugin";

 export default defineConfig({
-    plugins: [react()],
+    plugins: [react(), rebaseBackendGuard()],
 });
```

Posteriormente, convierta cualquier importación por valor de `backend/` en `import type`.

## 131. Las filas en tránsito siguen a su columna

**A quién afecta:** a clientes que consultan claves foráneas o referencian relaciones, y a operaciones de escritura que envían columnas generadas o fragmentos de objetos JSON.

**Qué cambió:** los valores pasan por el codec de su columna al emitirse y se validan con las reglas de la columna al recibirse.

- Una columna de clave foránea de tipo `bigint` o `numeric` generada por una relación, devuelta por Postgres como texto, se entrega como **número** en REST, el SDK y el panel de administración. Las claves numéricas declaradas ya funcionaban de este modo.
- En arrays nativos, **los elementos se sirven según su tipo escalar correspondiente**, en REST, el SDK, websockets y el driver:

  | Columna | 0.30 servía | 0.31 sirve |
  |---|---|---|
  | `timestamptz[]` | `["2026-01-02 11:00:00+01"]` | `["2026-01-02T10:00:00.000Z"]` |
  | `numeric[]` (driver inicializado sin el parámetro numérico de arranque: pruebas, scripts) | `["1.50", "2.25"]` | `[1.5, 2.25]` |
  | `bigint[]` con un elemento nulo | `[1, 0, 3]` | `[1, null, 3]` |
  | `date[]`, `timestamptz[]` o un array de enum con un elemento nulo | `["2026-01-02", "NULL"]` | `["2026-01-02", null]` |

  Las columnas `date[]`, `time[]`, `text[]`, `uuid[]`, `boolean[]`, `integer[]` y `double precision[]` se sirven como hasta ahora. Lo que se almacena no cambia: una fila leída y vuelta a guardar almacena exactamente el mismo array.
- Toda relación especificada en `include`, filtros u ordenamientos debe coincidir con su **nombre exacto**. Los reintentos alternativos usando el slug o la variante en snake_case han sido eliminados.
- Las columnas generadas son rechazadas en operaciones de escritura y se excluyen del esquema de entrada de OpenAPI.
- Se exige el cumplimiento de campos obligatorios dentro de objetos JSON; los modificadores `$inc` y los elementos de un array sobre una columna entera deben ser números enteros.

**Qué hacer:** procese las claves foráneas como números en los lugares donde antes comparaba strings, parsee elementos de `timestamptz[]` bajo la norma RFC 3339 y trate los elementos de array nulos como `null`, escribiendo los nombres de las relaciones tal como los declara la tabla (sus claves en `relations`). Deje de enviar valores para columnas generadas.

## 132. El historial se sirve como lecturas

**A quién afecta:** a consumidores de snapshots históricos y a quienes implementen un `DataDriver`.

**Qué cambió:** las entradas del historial se sirven bajo la semántica de lecturas: primero el acceso a nivel de campo, seguido de `afterRead` (global, tabla, columna). Una columna enmascarada mediante un hook o un `.transform({ afterRead })` aparecerá enmascarada en cada snapshot; una columna que el solicitante no tenga permisos para leer se omitirá y se excluirá de `changed_fields`; las claves de columnas eliminadas se omitirán, y una reversión nunca escribirá en una columna que el usuario no tenga permiso para leer. Si un hook lanza un error al evaluar un snapshot antiguo, la solicitud fallará. Dado que 0.30 servía los valores almacenados en crudo, cualquier proyecto que utilice historial con hooks de enmascaramiento debe actualizarse.

Una entrada contiene la fila en el mismo formato en que `GET /api/data/<table>/<id>` la leería sin `include`: valores simples y un `belongsTo` representado mediante su clave foránea. Una entrada registrada por una versión previa con el modelo de vista del panel de administración se sirve, y se revierte, adaptada a dicha fila: un contenedor `{ "__type": "date", "value" }` como valor, una referencia `{ "__type": "relation" }` de una relación propietaria como clave foránea bajo el nombre propio de la clave, y cualquier otra referencia como la clave de la fila vinculada. 0.30 devolvía dichas referencias tal como estaban guardadas.

Un driver sirve el historial mediante `DataDriver.serveStoredRows(path, rows)`, dentro de la transacción de solo lectura del solicitante; las rutas de historial responden con 501 si el driver no lo implementa, impidiendo que el historial se exponga sin enmascaramiento.

**Qué hacer:** no se requiere ninguna acción si usa el driver de Postgres integrado. Un driver personalizado debe implementar `serveStoredRows`. Consulte [Historial](/docs/backend/history/).

## 135. `@rebasepro/types` y `@rebasepro/common` eliminan el modelo de colecciones de sus raíces

**A quién afecta:** al código que importe tipos de colecciones o propiedades, utilidades del panel de administración o funciones de migración desde `@rebasepro/types` o `@rebasepro/common` (campos personalizados, vistas personalizadas, plugins, tests con fixtures de colecciones) y drivers personalizados que implementen el registro.

**Qué cambió:** los paquetes centrales describen exclusivamente tablas. Lo que describe una colección para su representación en el panel de administración reside en `@rebasepro/cms-types`:

- **Tipos** reubicados desde `@rebasepro/types`: `CollectionConfig`, `PostgresCollectionConfig`, `FirebaseCollectionConfig`, `AnyCollectionConfig`, cada variante de `…Property` (`StringProperty`, `NumberProperty`, `ArrayProperty`, …) y `Properties`, `CollectionCallbacks` y sus props de hook, las variantes de relaciones de 0.30 y sus formas `Resolved…`, `CollectionIndex`, los colores de chips (`ColorScheme`, `ColorKey`, …), `FieldAccess`, `EnumValues`.
- **Helpers** reubicados desde `@rebasepro/common`: los helpers de políticas estructurados para colecciones (`policyToPostgres`, `compileRulePolicies`, `getEffectiveSecurityRules`, `getGeneratedPolicyNames`, …), `CollectionRegistry`, `resolveCollectionRelations`, `resolveRelation`, `getTableName`, `findRelation`, `rowToViewModel`, `resolvePrimaryKeys`, la vista de acceso a campos de una propiedad (`effectiveAccess`, `canReadField`, `canWriteField`), `evaluateCondition`, `canEditEntity`, `resolveProperty`, `getDefaultValuesFor`, `getSubcollections`, `getCopyValues`, `enumToObjectEntries`. Una regla construida desde una expresión simple utiliza `compilePolicyExpression(expr)` de `@rebasepro/common`.
- **`composeCallbacks`** combina los callbacks de una colección para el panel y se trasladó a `@rebasepro/cms-types`; `@rebasepro/server` ya no lo reexporta. En el backend, los hooks de una tabla se componen mediante `composeTableHooks` de `@rebasepro/common`, y el codemod marcará cualquier importación de `composeCallbacks` en el backend como un paso manual informativo.
- **`defineCollection`** ha sido eliminado de `@rebasepro/common` y `@rebasepro/cms-types`: declare la tabla mediante `defineTable` en `backend/schema` y personalícela con `customizeTable` en `frontend/src/cms`; para Firestore use `defineFirestoreCollection` de `@rebasepro/firebase`.
- **El accessor del panel de administración y sus tipos**: `Entity`, `EntityValues`, `TableAccessor`, `TableTrashAccessor`, `FindResponse`, `QueryBuilderInterface`, `RebaseData` y `AuthState` salieron de `@rebasepro/types`; `buildRebaseData`, `wrapAsEntityData`, `buildRoutedRebaseData`, `EntityDataOptions`, `QueryBuilder`, `RelationRef` y `createRelationRef` salieron de `@rebasepro/common`. Todos se importan ahora desde `@rebasepro/cms-types`. La capa de datos propia del SDK (`buildSdkData`, `createDriverTableRows`, `buildRoutedSdkData`, en `@rebasepro/common`) sirve filas directamente y mantiene su valor de retorno previo.
- **`EntityDataOptions.resolveCollection`** se sustituye por `primaryKeysOf`, `viewModelOf`, `storedValuesOf` y `viewModelSourceOf`; la función `collectionEntityDataOptions(resolveCollection, { resolveDataPath, resolveAccessor })` de `@rebasepro/cms-types` se encarga de construirlos.
- **Las herramientas de migración** (`collectionsToTableDefs`, `collectionToTableDef`, `LiftNote`, `LiftResult`, `LiftOptions`) pasaron a `@rebasepro/common/migrate`, junto a una instantánea fija del modelo de colecciones de 0.30 (tipos `Legacy…`) y `defineLegacyCollection`.
- **Otras eliminaciones en los paquetes raíz**, reportadas como pasos manuales por el codemod: la API de parches de colecciones de `@rebasepro/types` (`CollectionPatch`, `CollectionPatchOp`, `applyCollectionPatch`, `collectionPatchProblems`, `isCollectionPatch`, `nestCollectionPatchPaths` → use `TablePatch`), sus utilidades JSON para colecciones (`diffCollections`, `diffJsonValues`, `toCollectionJson`, `RUNTIME_ONLY_COLLECTION_KEYS`, `runtimeOnlyKeyIn`), las capacidades heredadas de Mongo `DocumentAdmin`, `isDocumentAdmin` y `supportsDocumentAdmin`, así como `RebaseProjectContract.collectionSlugs` / `.collections` / `.generatedAt` (`/api/meta/contract` devuelve `tables`); en `@rebasepro/common`: `buildTenantSecurityRule` → `tenantSecurityRule`, `defaultPoliciesDisabled` → `tableDefaultPoliciesDisabled`, `restoresSoftDeletedRow` → `isSoftDeleteRestore`, `softDeleteFieldOf` → `softDeleteColumn`, `getJunctionConfigForRelation` → `resolveTableJunctions`, y quedan sin sustituto directo `isRelationRequired`, `relationDeclaringProperty`, `requireCallbackCollection` (debe consultarse el `TableDescriptor`).
- **El registro de un driver** es ahora un `TableRegistryInterface` (anteriormente `CollectionRegistryInterface`): `setGlobalHooks?` y `setTableHooks?` reemplazan a `getGlobalCallbacks` / `setGlobalCallbacks?`. Se eliminaron `globalHooksAsCallbacks`, `resolveDriftCheckName` y `PENDING_TABLE_FEATURES`.

**Qué hacer:** `rebase migrate sdk-calls` (integrado en `collections-to-tables`) actualiza cada importación detallada abajo hacia su nuevo paquete (combinándola con importaciones existentes en el archivo, preservando `import type`, `type` en línea y alias `as`) y añade el paquete a las dependencias del módulo del workspace correspondiente; ejecute `pnpm install` al finalizar. Las importaciones de identificadores eliminados, importaciones de espacios de nombres (`import * as`), `export *`, importaciones dinámicas `import()` o llamadas a `require()` con nombres trasladados se listarán como pasos manuales numerados. Las pruebas que mantengan literales de colección como fixtures deben tiparse con los tipos `Legacy…` y transformarse con `@rebasepro/common/migrate`.

Dicho listado se genera a partir de la misma tabla que consulta el codemod, por lo que coincide exactamente con lo que `rebase migrate sdk-calls` procesa.

## 136. El driver de Postgres y las lecturas one-shot del socket devuelven la fila REST

**A quién afecta:** a funciones o plugins que consulten a través de `requireDriver(c)` / `getDriver(c)`, código que emita frames `FETCH_COLLECTION` / `FETCH_ONE` por sockets, y código que interprete objetos con la estructura `{ __type }` en la respuesta.

**Qué cambió:** se unifica la estructura de lectura. `fetchCollection` y `fetchOne` en el driver de Postgres —empleados por `requireDriver(c)` en funciones, plugins, frames one-shot de sockets, MCP y el simulador de RLS— devuelven exactamente lo mismo que `GET /api/data/<table>`:

| Valor | Lectura de driver en 0.30 | 0.31 |
|---|---|---|
| una marca de tiempo | `{ "__type": "date", "value": … }` | una cadena RFC 3339 |
| un `belongsTo` | `{ "__type": "relation", "id", "path" }` bajo el nombre de la relación | la clave foránea bajo su propio identificador (`authorId`) |
| una fila vinculada | cada relación cargada automáticamente por `fetchOne` | únicamente las relaciones especificadas en `include`, como la fila propia de la entidad destino |
| un vector, un `bytea` | `{ "__type": "Vector" }`, una URL de datos | tal como los entrega REST |

`FetchOneProps` recibe `include` (se elimina `ListenOneTarget`: utilice `FetchOneProps`). `rebase.data`, `context.data` y el SDK ya devolvían esta estructura y se mantienen sin alteraciones.

`@rebasepro/client` interpreta los cuerpos REST y los frames del socket como JSON plano: un valor que contenga la clave `__type` ya no se convertirá en `Date`, `EntityReference`, `EntityRelation`, `GeoPoint` o `Vector`, y un documento JSON que posea una clave `__type` se entregará tal como fue almacenado.

**Qué hacer:** consuma la fila en plano: convierta las cadenas de fecha a objetos Date, lea las claves foráneas por su propio identificador y pase el parámetro `include` para cada relación que necesite consultar:

```diff ts
-const article = await requireDriver(c).fetchOne({ path: "articles", id });
-const authorId = article?.author.id;      // una referencia { __type: "relation" }
+const article = await requireDriver(c).fetchOne({ path: "articles", id, include: ["author"] });
+const authorId = article?.authorId;
```

## 138. El backend acepta únicamente los valores documentados en la API REST

**A quién afecta:** a clientes que escriban una relación to-one como un objeto o un vector como `{ value }`, código que aplique filtros sobre una relación pasando un objeto, código que importe clases de valores del panel de administración y aplicaciones offline con escrituras pendientes encoladas desde la versión 0.30.

**Qué cambió:** una operación de escritura requiere el mismo formato devuelto por una lectura: una estructura uniforme para REST, websockets, MCP y el SDK en proceso:

| Valor | Aceptado | Rechazado a partir de ahora |
|---|---|---|
| una relación to-one (`belongsTo`, `hasOne`, un `via` de tipo to-one) | la clave de la fila relacionada, o `null` (`""` equivale a `null`), bajo el nombre de la relación o el de la clave foránea | un objeto como `{ "id": 5 }`: `400 VALIDATION_INVALID_VALUE`, "'posts.author' links one 'authors' row: write that row's key (a string or a number), or null to unlink — not an object." |
| una relación to-many (`hasMany`, `manyToMany`, un `via` de tipo to-many editable) | una lista de claves, o de `{ id, _pivot? }` | — (otras claves en el objeto se descartan, como antes) |
| un vector | una lista de números | una instancia de `Vector` o `{ "value": [...] }`: `400`, "'embedding' expects a vector as a list of numbers" |
| una fecha, una hora | texto ISO (`Date` en llamadas en proceso) | — |
| un geopunto | `{ latitude, longitude }` | — |
| un `bytea` | una URL en formato `data:application/octet-stream;base64,` (`Buffer` / `Uint8Array` en llamadas en proceso) | — |
| un filtro sobre una relación | la clave | los objetos ya no se desestructuran: se evalúan exactamente como se envían |

0.30 admitía relaciones to-one enviadas en forma de objeto extrayendo silenciosamente su propiedad `id`; esa variante nunca estuvo documentada y formaba parte del modelo de vista del panel de administración. Ahora, el panel de administración transforma su modelo de vista a valores de transporte directamente en el navegador antes de cualquier escritura o filtro.

Las clases de valores del panel se trasladaron junto al resto de su modelo de vista: `EntityReference`, `EntityRelation`, `GeoPoint`, `Vector` y `EntityReferenceProps` se importan desde `@rebasepro/cms-types` (salieron de `@rebasepro/types`), al igual que `normalizeToEntityRelation` (salió de `@rebasepro/common`); se eliminó `withRelationReferencesOnly`. El historial almacena la fila tal como la devuelve una lectura; las entradas registradas con anterioridad se entregan y revierten como valores planos ([sección 132](#132-el-historial-se-sirve-como-lecturas)).

La cola offline de `@rebasepro/client` almacena valores de transporte. Una operación de escritura encolada sin conexión por el SDK de 0.30 se transforma automáticamente al leerse y reintentarse: ninguna operación encolada antes de la actualización se perderá.

**Qué hacer:** envíe la clave directamente: `{ "author": 5 }`, no `{ "author": { "id": 5 } }`; envíe los vectores como listas de números, y filtre las relaciones usando su clave correspondiente. `rebase migrate sdk-calls` ajusta las importaciones de clases de valores ([el listado](/docs/upgrading/0-30-to-0-31-imports/)). Consulte [Escrituras](/docs/backend/writes/).

## 139. `/api/docs` se sirve a la audiencia del endpoint de esquema

**A quién afecta:** a usuarios o herramientas que consuman `/api/docs` o accedan a `/api/swagger` (Swagger UI, generadores de clientes de API, pasos de CI).

**Qué cambió:** cuando `enableSwagger` no está definido (`REBASE_ENABLE_SWAGGER` sin definir), en cualquier entorno, el documento de OpenAPI se sirve a los mismos usuarios para los que `GET /api/schema/tables` describe tablas, aplicando los mismos controles de rechazo (401 para usuarios anónimos salvo que exista `schemaTables.public`, y 403 para credenciales sin scopes de esquema o datos), y cada cliente obtiene el documento correspondiente de forma exacta a las tablas, columnas y relaciones que dicho endpoint le muestra (un administrador accede a la totalidad). Swagger UI no se incluye. Un servidor sin autenticación configurada responderá `404 DOCS_UNAVAILABLE`. En desarrollo, 0.30 exponía el documento completo con todas las tablas servidas y columnas no privadas a usuarios anónimos, reservándolo exclusivamente para administradores en producción.

| `enableSwagger` / `REBASE_ENABLE_SWAGGER` | `/api/docs` | `/api/swagger` |
|---|---|---|
| sin definir (por defecto) | a cada cliente al que el endpoint de esquema describe tablas: sus tablas | no disponible |
| `true` | el documento completo, para todo el mundo | disponible fuera de producción |
| `false` | el documento completo, protegido bajo acceso de administrador | no disponible |

**Qué hacer:** realice las peticiones a `/api/docs` con una sesión autenticada. Para exponer el documento íntegro tal como hacía 0.30 en desarrollo, configure `REBASE_ENABLE_SWAGGER=true` (o `enableSwagger: true`). Consulte [Endpoints](/docs/backend/endpoints/).

## 140. Una columna `pivot` de tipo many-to-many no puede declarar `.transform()`

**A quién afecta:** a definiciones `rel.manyToMany(…, { pivot: { … } })` cuya columna de pivot contenga un `.transform()`.

**Qué cambió:** el compilador la rechazará ("the pivot column "x" declares `.transform()` …"). La transformación de una columna intermedia de pivot nunca llegaba a ejecutarse, por lo que cualquier valor que intentara enmascararse se devolvía tal como estaba guardado.

**Qué hacer:** elimine el `.transform()` y enmascare `_pivot` dentro del hook `hooks.afterRead` de la tabla de destino. Consulte [Relaciones](/docs/collections/relations/).

## 141. Un enlace es exactamente tan legible y modificable como su columna clave

**A quién afecta:** a clientes que escriban un `belongsTo` mediante el nombre de su relación, lean o filtren relaciones cuya columna clave posea restricciones, o dependan de `strictWrites: false`.

**Qué cambió:** cualquier restricción definida sobre una columna clave aplica a cualquier forma utilizada para leerla o escribirla.

- Escribir un enlace mediante el nombre de su relación (`{ "reviewer": 7 }`) queda sujeto a todas las reglas de la columna clave que modifica (`.readOnly()`, `.private()`, `access.write`, marcas temporales de creación, la columna tenant, inmutabilidad de clave) en REST, bulk, `_batch`, sockets y MCP. Enviar el enlace bajo ambos nombres simultáneamente (`{ "reviewer": 7, "reviewerId": 8 }`) con valores discrepantes producirá un error 400 `VALIDATION_INVALID_VALUE`. Intentar trasladar una fila a otro tenant a través de su enlace responderá 400 `TENANT_IMMUTABLE` (anteriormente generaba un error 500).
- Una relación solo es legible si el solicitante tiene permisos de lectura para todas las columnas involucradas en su join, en todas las tablas por las que transite: la clave del `belongsTo`, la clave foránea de destino en un `hasMany` / `hasOne`, y cada columna unida en los pasos de un `via`. Si alguna falla, se omitirá de `include` y `_count`, y cualquier filtro, ordenamiento o ruta relacional que pase por ella devolverá `FIELD_NOT_READABLE` (o una relación desconocida si la columna es `.private()`). Una escritura to-one via `via` que intente replicar una columna inaccesible para el usuario será rechazada con `FIELD_NOT_READABLE`. Los casos inversos y con `via` ya presentaban este comportamiento en 0.30.x.
- Un enlace cuya columna clave sea inaccesible para el solicitante se omitirá de `include`, y cualquier filtro, ordenamiento, elemento en `fields` o ruta relacional a través de él responderá `FIELD_NOT_READABLE`; un enlace asociado a una clave `.private()` se comportará como una relación desconocida. `GET /api/schema/tables`, OpenAPI y la herramienta `describe_table` de MCP describen los enlaces junto con sus claves, por lo que una columna clave cuyo enlace esté cerrado también se omitirá allí.
- `strictWrites: false` determina una sola cosa: que una clave no declarada pase al driver (se escribirá si la base de datos contiene la columna, de lo contrario devolverá 400 `VALIDATION_UNKNOWN_FIELDS`). En ningún caso desbloqueará una columna declarada, marcas temporales, el tenant, la clave, el destino de una relación o una regla sobre `_pivot`.

**Qué hacer:** especifique un enlace utilizando un único nombre, o ambos con idéntico valor; acceda a enlaces restringidos con un rol que tenga permisos para leer su clave correspondiente. Consulte [Acceso a campos](/docs/collections/field-access/).
