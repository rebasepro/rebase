<span class="since-badge" data-since="0.31">Desde 0.31</span>

Las reglas de una columna se declaran una vez, en la columna, y el servidor las
aplica en cada escritura que llega a la API. El CMS lee las mismas reglas del
descriptor de la tabla y las comprueba en el formulario antes de guardar, de modo
que un operador ve el error en el campo, no como una petición rechazada.

```ts
// backend/schema/events.ts
import { defineTable, col } from "@rebasepro/server/schema";

export const events = defineTable("events", {
    columns: {
        id:      col.uuid().primaryKey().defaultRandom(),
        title:   col.text().notNull().validate({ min: 2, max: 200, requiredMessage: "Every event needs a title" }),
        slug:    col.varchar({ length: 80 }).notNull().unique()
                     .validate({ matches: "^[a-z0-9-]+$", matchesMessage: "Lowercase letters, digits and hyphens only" }),
        isFree:  col.boolean().notNull().default(false),
        price:   col.numeric({ precision: 10, scale: 2 }).validate({ min: 0 }),
        seats:   col.integer().validate({ positive: true }),
    },
    rls: "admin-only",
});
```

:::note[¿Vienes de collections?]
Ya no hay ningún bloque `validation` en el frontend. Las reglas se escriben en
la columna con `.notNull()` y `.validate({ … })`, y el CMS las lee.
:::

## Qué comprueba el formulario

<span class="since-badge" data-since="0.31">Desde 0.31</span>

| En la columna | En el formulario |
|---|---|
| `.notNull()` | Obligatorio, con `requiredMessage` como error cuando se especifique. No es obligatorio donde nadie escribe el valor: una clave generada, una marca de tiempo (stamp), una columna generada o `.readOnly()`. |
| `.unique()` | El valor se comprueba contra la tabla antes de guardar un valor modificado, y se señala el duplicado en su campo correspondiente. |
| `varchar(n)`, `char(n)` | Como máximo `n` caracteres. |
| text `min`, `max`, `length` | Recuento de caracteres, inclusivo. |
| `matches`, `matchesMessage` | Todo el valor debe coincidir con el patrón; el mensaje es el error. |
| `email`, `url` | El valor debe ser un correo electrónico, una URL. |
| `trim`, `lowercase`, `uppercase` | El valor se recorta o se convierte a minúsculas/mayúsculas antes de guardarse. |
| number `min`, `max`, `moreThan`, `lessThan`, `positive`, `negative`, `integer` | Límites, y solo números enteros. Las columnas integer y serial son números enteros independientemente de lo que indique `.validate()`. |
| date `min`, `max` | La fecha más temprana y más tardía aceptada. |
| array `minItems`, `maxItems`, `uniqueItems` | Cuántos elementos, y ningún elemento repetido. |

Cada regla está listada, con su significado exacto, en
[Columnas](/docs/schema/columns/#validation).

## Dónde se ejecuta la validación

<span class="since-badge" data-since="0.31">Desde 0.31</span>

El servidor comprueba las reglas de una columna en el límite de la petición
(REST, el socket en tiempo real y MCP) sobre lo que envió el emisor, antes de que
se ejecute `beforeSave`, y responde a una escritura que incumple una regla con un
error 400 indicando cada campo fallido. El código del servidor que escribe en el
mismo proceso es de confianza y no se comprueba con respecto a estas reglas; lo
que rige allí es lo que aplica la base de datos. Consulta
[Columnas](/docs/schema/columns/#validation).

El CMS comprueba las mismas reglas antes de guardar, tanto en el formulario del
registro como en el editor en línea de la tabla. Una celda de la tabla evalúa un
valor una vez que se edita: un valor almacenado que incumpla una regla añadida
posteriormente no mostrará ningún error hasta que alguien edite esa celda.

## Campos condicionales

<span class="since-badge" data-since="0.31">Desde 0.31</span>

Un campo puede reaccionar a los propios valores del registro: volverse obligatorio,
deshabilitado, de solo lectura u oculto. Hay dos formas, ambas en `customizeTable`:

```tsx
// frontend/src/cms/events.tsx
import { customizeTable } from "@rebasepro/cms";
import type { events } from "../../../backend/schema/events";

export const eventsCms = customizeTable<typeof events>("events", {
    fields: {
        price: {
            conditions: {
                disabled: { "==": [{ "var": "values.isFree" }, true] },
                required: { "!=": [{ "var": "values.isFree" }, true] },
                min: 0,
                disabledMessage: "Free events have no price",
                clearOnDisabled: true,
            },
        },
        seats: {
            dynamicProps: ({ values, authController }) => ({
                disabled: values.isFree === true || !authController.user?.roles?.includes("admin"),
            }),
        },
    },
});
```

### `conditions`: JSON Logic

`conditions` contiene reglas de [JSON Logic](https://jsonlogic.com/) sobre el
registro que se está editando (`values.<key>`). Son datos, por lo que el editor
de esquemas puede leerlas y modificarlas. Una condición puede establecer:

- `disabled`, `disabledMessage`, `clearOnDisabled`, `hidden`, `readOnly`;
- `required`, `requiredMessage`, `min`, `max`;
- `defaultValue`;
- `enumConditions`, `allowedEnumValues`, `excludedEnumValues`;
- `referencePath`, `referenceFilter`;
- `canAddElements`, `sortable`, para arrays.

`disabledMessage` es lo que ve el usuario junto al control deshabilitado en gris.
Sin él, un campo deshabilitado no explica nada.

### `dynamicProps`: una función

A `dynamicProps` se le pasa el registro mientras se está editando (`values`,
incluidas las modificaciones no guardadas, y `previousValues` una vez guardado)
junto con el usuario autenticado en `authController`, y devuelve las opciones de
campo aplicables en ese momento. Lo que devuelve se aplica sobre las demás opciones
del campo cada vez que el formulario lo solicita, por lo que puede devolver
cualquier opción de campo: `disabled`, `hidden`, `readOnly`, `name`,
`description`, `enumLabels`…

:::caution[Las condiciones son comportamiento del formulario]
`conditions` y `dynamicProps` se ejecutan en el navegador y definen lo que ofrece
el CMS. La API acepta una escritura que las ignore. Una regla que deba cumplirse
para cualquier emisor corresponde a la columna (`.notNull()`, `.validate()`) o a
la [seguridad a nivel de fila](/docs/collections/security-rules/) de la tabla,
que la base de datos impone para todos.
:::

## Etiquetas para un conjunto cerrado

<span class="since-badge" data-since="0.31">Desde 0.31</span>

Los valores de un `col.enum([...])` o un `.oneOf([...])` pertenecen a la columna.
Sus etiquetas, colores y orden pertenecen al CMS, definidos con `enumLabels` y
`enumOrder`; consulta [conjuntos cerrados](/docs/collections/properties/#closed-sets-of-values).
