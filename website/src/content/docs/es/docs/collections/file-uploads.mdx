Un campo de archivo es una columna [`col.storage()`](/docs/schema/columns/#storage-columns).
La columna contiene texto, la clave del objeto en el bucket (o su URL, si
la columna así lo especifica), y el CMS lo dibuja como un campo de subida con vista previa.

Lo que hace un campo de almacenamiento se divide en dos, según dónde se ejecute:

| Declarado | Dónde | Opciones |
|---|---|---|
| en la columna, en `backend/schema` | leído por el servidor **y** el CMS | `path`, `source`, `accept`, `maxBytes`, `imageResize`, `public`, `fileName`, `metadata`, `includeBucketUrl`, `storeUrl` |
| en `customizeTable`, en `frontend/src/cms` | solo en el navegador | `storage.path(…)`, `storage.fileName(…)`, `storage.processFile`, `storage.postProcess`, `storage.previewUrl` |

Las opciones de la columna son serializables, por lo que viajan en el descriptor
de la tabla y el servidor aplica las que puede de ellas. Las opciones de
`customizeTable` son funciones: no pueden llegar al servidor, por lo que solo dan
forma a las subidas realizadas desde el CMS.

## Un archivo

<span class="since-badge" data-since="0.31">Desde 0.31</span>

```ts
// backend/schema/listings.ts
import { defineTable, col } from "@rebasepro/server/schema";

export const listings = defineTable("listings", {
    columns: {
        id:     col.uuid().primaryKey().defaultRandom(),
        title:  col.text().notNull(),
        cover:  col.storage({ path: "listings/{id}/", accept: ["image/*"], maxBytes: "10MB",
                              imageResize: { maxWidth: 1600, format: "webp", quality: 80 } }),
        photos: col.storage({ path: "listings/{id}/gallery/", accept: ["image/*"] }).multiple(),
    },
    rls: "admin-only",
});
```

`cover` es un campo de subida que acepta una imagen de un máximo de 10 MB,
redimensionada a un ancho máximo de 1600 píxeles y guardada como WebP. Una columna
cuyo `accept` indique un tipo de imagen ofrece vista previa como imagen, y la primera
columna de este tipo ocupa la ranura de imagen del registro en tarjetas y listas.

## Varios archivos

<span class="since-badge" data-since="0.31">Desde 0.31</span>

`.multiple()` convierte la columna en un `TEXT[]` y el campo en una subida de
múltiples archivos, reordenable arrastrando. Cada opción se aplica a cada archivo.

## Opciones del lado del navegador

<span class="since-badge" data-since="0.31">Desde 0.31</span>

```tsx
// frontend/src/cms/listings.tsx
import { customizeTable } from "@rebasepro/cms";
import type { listings } from "../../../backend/schema/listings";

export const listingsCms = customizeTable<typeof listings>("listings", {
    fields: {
        cover: {
            storage: {
                // A folder per listing title, computed in the browser.
                path: ({ values }) => `listings/${String(values.title ?? "untitled").toLowerCase()}/`,
                fileName: ({ file }) => `${Date.now()}-${file.name}`,
            },
            urlPreview: "image",
        },
        photos: {
            sortable: true,
            storage: { processFile: async (file) => file },
        },
    },
});
```

| `storage.` | Se ejecuta | Efecto |
|---|---|---|
| `path(context)` | antes de una subida | La carpeta a la que va el archivo, reemplazando la plantilla `path` de la columna. |
| `fileName(context)` | antes de una subida | El nombre del archivo almacenado, reemplazando la plantilla `fileName` de la columna. Puede ser asíncrono. |
| `processFile(file)` | antes de una subida | Transforma el archivo (comprimir, eliminar metadatos). |
| `postProcess(pathOrUrl)` | después de una subida | Transforma la ruta o URL antes de que se escriba en la columna. |
| `previewUrl(fileName)` | al dibujar | La URL en la que previsualizar un archivo almacenado, cuando no es el valor del campo. |

`path` y `fileName` reciben el contexto de la subida: el `file`, el `id` del
registro (ausente en un registro nuevo), sus `values` editados, la `propertyKey` y
las reglas de almacenamiento resueltas. En una columna `.multiple()`, las mismas
opciones de `storage` van directamente en el campo y se aplican a cada archivo.

`urlPreview` define cómo se previsualiza el valor almacenado (`"image"`, `"video"`,
`"audio"`, `"file"` o `true` para un enlace), y `clearable` añade un control que
vacía el campo.

## Qué comprueba el servidor

<span class="since-badge" data-since="0.31">Desde 0.31</span>

`accept` y `maxBytes` son aplicados por el servidor en función de **dónde cae el
archivo**. El `path` de una columna es adonde van sus archivos, por lo que también
es donde se aplican sus límites: toda subida cuya clave sea un archivo directamente
bajo esa ruta los cumple, ya sea desde el CMS, `client.storage.putObject`, una subida
reanudable, el explorador de almacenamiento de Studio o `curl`, nombre o no a la
columna, en el propio bucket de la columna. Los marcadores de posición coinciden con
lo que el CMS rellenaría: `{id}`, `{rand}`, `{file}` y similares representan un
segmento de ruta, `{path}` cualquier cantidad. La ruta de una columna con `public: true`
se encuentra bajo `public/`.

- Varias columnas que comparten una ruta: se acepta un archivo que cualquiera de ellas acepte.
- Una subida que también nombra su columna, como hacen las subidas del CMS, se somete
  también a esa columna. Nombrar una columna más permisiva no desbloquea la ruta de una más estricta.
- El servidor no puede leer una función `storage.path` en `customizeTable`,
  por lo que un archivo subido bajo la ruta que esta calcula solo se somete a los límites
  de la columna cuando la subida nombra la columna, lo cual las subidas del CMS siempre hacen.
- Una ruta que ninguna columna reclame se somete únicamente al límite del
  propio bucket (`STORAGE_MAX_FILE_SIZE`).

`imageResize`, `processFile` y `postProcess` ocurren en el navegador, antes de que
los bytes sean enviados: un archivo subido de otra manera se almacena tal como se envió.

## Adónde puede ir un archivo

<span class="since-badge" data-since="0.31">Desde 0.31</span>

`path` es un valor predeterminado, no un límite estricto: nada en el servidor confina
una subida a él. Quién puede escribir en qué lugar es una regla de autorización de
almacenamiento; consulta [Almacenamiento](/docs/backend/storage/).

## Los archivos nunca se eliminan por ti

<span class="since-badge" data-since="0.31">Desde 0.31</span>

Vaciar un campo de archivo, reemplazar su archivo o eliminar la fila deja el
objeto almacenado donde está. Cada subida obtiene su propia clave, por lo que un
reemplazo escribe un nuevo objeto y nada elimina el anterior: dos filas pueden
contener la misma clave, por lo que el CMS no puede saber si un archivo está en desuso.
Los objetos a los que ninguna fila apunta permanecen en el bucket y se facturan
hasta que los elimines desde el explorador de almacenamiento de Studio, con
`client.storage.deleteObject(key)` o con una regla de ciclo de vida en el bucket.
`rebase storage orphans` lista los archivos a los que ninguna fila hace referencia
y los elimina con `--delete`; consulta [la CLI](/docs/cli/#rebase-storage).

## Mover una columna a otro bucket

<span class="since-badge" data-since="0.31">Desde 0.31</span>

Un campo de archivo almacena la clave del objeto, no su bucket. Modificar el `source`
de una columna hace que cada valor existente apunte al nuevo bucket, donde esas
claves no existen, por lo que las vistas previas de archivos más antiguos responderán
"not found". Copia primero los objetos al nuevo bucket con las mismas claves, mediante
`rebase storage move --from <old> --to <new> --prefix <path>` o las herramientas
propias del proveedor, tales como `aws s3 sync` o `gcloud storage cp`, o bien conserva
el bucket anterior para los archivos existentes.
