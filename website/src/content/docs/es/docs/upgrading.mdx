# Actualizar una aplicación existente

Trece saltos, del más reciente al más antiguo. Comienza en el que esté justo por encima de tu versión actual y avanza hacia abajo; o, si vienes de la versión 0.12, comienza desde abajo y avanza hacia arriba.

| Estás en | Lectura | Qué implica |
|---|---|---|
| **0.30** | [0.30 → 0.31](/docs/upgrading/0-30-to-0-31/) | Las tablas en `backend/schema` (`defineTable`) reemplazan a `config/collections`, y ya no existe el paquete config: ejecuta `rebase migrate collections-to-tables`, lo que traslada el proyecto y comprueba que el SQL generado no ha cambiado. El panel de administración renderiza las tablas que sirve el servidor, personalizadas desde `frontend/src/cms`; el SDK utiliza `data.table(slug)` y `tables: tablesDictionary`; los bundles son de formato 3, por lo que debes recompilar antes de desplegar; MongoDB queda descontinuado. |
| **0.29** | [0.29 → 0.30](/docs/upgrading/0-29-to-0-30/) | Un backend iniciado con `initializeRebaseBackend` conserva el token de actualización en una cookie a menos que establezca `cookieAuth: false`, por lo que un cliente que lo lea del cuerpo sin `x-rebase-auth-flow: json` obtendrá `""`. |
| **0.27 – 0.28** | [0.27 → 0.29](/docs/upgrading/0-27-to-0-29/) | Todo lo que el panel de administración entrega a tu código es la fila del servidor con su id al lado: `context.data` y `browserCallbacks` del navegador entregan cadenas ISO y claves foráneas donde antes entregaban `Date`s y objetos de relación, algo que ningún compilador detecta; los hooks de datos de `Entity` pasan a ser internos; y los callbacks, paneles, el panel lateral y la selección reciben `row` e `id` en lugar de `entity` y `entityId`. La versión 0.28 no introduce cambios importantes, por lo que se trata de un único salto desde 0.27. |
| **0.26** | [0.26 → 0.27](/docs/upgrading/0-26-to-0-27/) | Una programación cron que restringe ambos campos de día se ejecuta en cualquiera de ellos, por lo que se ejecuta con mayor frecuencia, y se rechaza cualquier programación con un número mal formado, por lo que ese trabajo dejará de ejecutarse. Una clave cuya estrategia `isId` no pueda ser satisfecha por su tipo detiene el arranque. En Rebase Cloud, un despliegue o preview falla si un archivo de función o de cron no se carga. |
| **0.25** | [0.25 → 0.26](/docs/upgrading/0-25-to-0-26/) | Se rechazan: una escritura que indique una relación `via` de múltiples saltos, un nombre de rol que no sea un rol individual, un token de paginación en almacenamiento local previo a la actualización y un upstream de funciones que no pueda funcionar. El inicio de sesión con OAuth regulariza una cuenta no verificada en lugar de responder `local-account-unverified`, el servidor MCP ya no envía `REBASE_TOKEN` a la aplicación y los tipos generados eliminan la clave de un `belongsTo` con `excludeFromApi`. En Rebase Cloud, `rebase cloud webhooks` y `--scale-to-zero true` quedan descontinuados, y es posible que sea necesario volver a crear los tokens más antiguos. |
| **0.24** | [0.24 → 0.25](/docs/upgrading/0-24-to-0-25/) | `?count=` en una lista REST se convierte en el conmutador para el recuento detrás de `meta.total`, por lo que un filtro en una columna llamada `count` debe ir dentro de `?where=`; `list_collections` del MCP remoto envía su listado solo en el bloque de texto, sin `structuredContent`; y `@rebasepro/app` ya no exporta la tabla de traducción al español `es`. Se rechazan: una petición `OPTIONS` simple a una ruta sin manejador, nombres de tabla en conflicto al arrancar, un upsert en la colección users, `page` con `offset`, una cadena vacía en un campo obligatorio y una contraseña de administrador que no cumpla la política de contraseñas. Las sesiones duran 30 días de inactividad por defecto, `client.cron` llama a `/api/admin/cron`, las lecturas sin conexión que no puedan responderse por completo fallan con `OFFLINE`, y desaparecen algunas exportaciones internas y propiedades no utilizadas. |
| **0.23** | [0.23 → 0.24](/docs/upgrading/0-23-to-0-24/) | El renderizado SQL de `db push` y `db generate` se traslada fuera de `drizzle/` hacia el directorio no versionado `.rebase/sql/`, el flag `--generate` de `rebase dev` desaparece porque `dev` siempre regenera los tipos del SDK, y la edición de esquemas en vivo no confirma ningún SQL. Los permisos se convierten en scopes: las interfaces de administración solicitan un scope en lugar del rol admin, las claves de API contienen scopes en lugar de una lista de permisos y un flag `admin`, y `schema-admin` ya no es administrador. Un flag relativo `--collections` se lee desde donde se ejecuta el comando, se rechazan tanto un upsert en una fila eliminada a la papelera como una actualización que modifique una clave, el endpoint MCP remoto acepta los argumentos del SDK, y los sockets en tiempo real abiertos, enlaces de verificación de correo, `signUp` y códigos de recuperación MFA cambian la forma en que gestionan la sesión. |
| **0.21 – 0.22** | [0.21 → 0.23](/docs/upgrading/0-21-to-0-23/) | Una clave de API en una ruta anidada necesita permisos de `read` en sus elementos principales, las variables numéricas ilegibles y duraciones de sesión no válidas impiden el arranque, un repositorio de autenticación personalizado requiere `unlinkUserIdentity`, y las actualizaciones de invitados requieren el captcha de `register`. La versión 0.22 no introduce cambios importantes, por lo que se trata de un solo salto desde 0.21. |
| **0.18 – 0.20** | [0.18 → 0.21](/docs/upgrading/0-18-to-0-21/) | `context.client.data` deja de compilar en un callback de colección (realiza consultas mediante `context.data`) y `selectedEntities` da paso a una selección que puede representar filas que nadie ha cargado. Las versiones 0.19 y 0.20 no introducen cambios importantes, por lo que es un único salto desde 0.18. |
| **0.17** | [0.17 → 0.18](/docs/upgrading/0-17-to-0-18/) | Once cambios importantes, la mayoría de ellos errores de compilación en lugar de cambios silenciosos de comportamiento. `rebase.data` desaparece en tiempo de ejecución, los rangos de dependencias peer se restringen a intercalaciones (carets) y la versión mínima de Node pasa a 22.22.0. |
| **0.14 – 0.16** | [0.14 → 0.17](/docs/upgrading/0-14-to-0-17/) | Se renombran los paquetes de administración, los recursos se declaran en lugar de configurarse y un bundle compilado anteriormente no arrancará en el entorno de ejecución actual. Las versiones 0.15 y 0.16 no rompen nada, por lo que es un único salto desde 0.14. |
| **0.13** | [0.13 → 0.14](/docs/upgrading/0-13-to-0-14/) | Todas las claves en tránsito utilizan camelCase y el inicio de sesión anónimo pasa a ser opcional (opt-in). |
| **0.12** | [0.12 → 0.13](/docs/upgrading/0-12-to-0-13/) | El salto más grande, y el único que cambia **quién puede leer tus datos**. Elimina el esquema `auth`, renombra paquetes, cambia el significado de `id`, abandona CJS, migra el panel de administración a react-router 8 y corrige tres formas en las que se podía conceder acceso no solicitado. |

Las secciones de cada página están en el orden en que debes abordarlas, y cada una detalla el síntoma que, de otro modo, tendrías que depurar desde el extremo equivocado.

Luego, independientemente del salto realizado:

- [La lista de verificación de actualización](#upgrade-checklist) a continuación: los greps y comandos que vale la pena ejecutar después, agrupados en un solo bloque.

## Upgrade checklist

```
[ ] grep for authenticated() and (auth|rebase).uid() IS NOT NULL in config/collections/
[ ] decide the intent of each rule; rewrite the ones that meant "public"
[ ] replace not(authenticated()) with serverContext()
[ ] if realtime.requireAuth was true with an AuthAdapter, treat the socket as
    having been open — verify RLS on every subscribable collection (section 2)
[ ] SELECT ... FROM pg_policies — record the qual of every policy BEFORE
[ ] update package names and imports
[ ] grep for rebase.data — it is now rebase.dataAsAdmin (section 8)
[ ] grep for the other ten removed deprecated exports (section 8)
[ ] drop react-router-dom; import RouterProvider from "react-router/dom"
[ ] check node >= 22.22.0 and react >= 19.2.7 (react-router 8 requires both)
[ ] move defaultSecurityRules into config/collections/index.ts
[ ] grep for .userId
[ ] grep for row.id on tables not keyed on id
[ ] run db push
[ ] run rebase doctor --policies — expect no Insecure or Orphaned entries
[ ] SELECT ... FROM pg_policies again — confirm every intended change landed
[ ] exercise the app signed OUT, in a private window — watch the websocket too

--- 0.13 → 0.14 (part 2) ---
[ ] re-run rebase generate-sdk, then build — the compiler finds row.author_id
[ ] grep for snake_case where/orderBy keys; a stale one is a 400, not a warning
[ ] grep for raw fetch consumers reading row.<something>_id — these read
    undefined and raise nothing
[ ] if the project was introspected, re-run rebase schema introspect
[ ] decide anonymous sign-in: set auth.allowAnonymous: true, or confirm you
    never used it (grep for signInAnonymously)
[ ] drop @rebasepro/client-postgres from package.json

--- 0.14 → 0.17 (part 3) ---
[ ] rename @rebasepro/admin → @rebasepro/cms and admin-types → cms-types,
    and RebaseAdmin → RebaseCMS
[ ] move dataSources / storageSources out of the backend config into
    rebase.json and config/, then `rebase build` — an old bundle will not boot
[ ] grep collections for admin.titleProperty; it is refused at boot now
[ ] grep crons for ctx.client and for `userId` as an identity key
[ ] rename --legacy to --workspace wherever build/start is scripted
[ ] if you implement EmailService yourself, `send` must return a result

--- 0.30 → 0.31 ---
[ ] bump every @rebasepro package to 0.31 first, then pnpm install
[ ] rebase migrate collections-to-tables on a clean tree; read the manual steps
[ ] move config/index.ts `callbacks` to backend/hooks.ts by hand, if you had them
[ ] rebase generate-sdk; rebase db push --dry-run plans no change
[ ] run the git rm line the codemod printed (your own config/ modules may stay)
[ ] send a to-one relation as its key, not { id } — that is a 400 now
[ ] call /api/docs signed in, or set REBASE_ENABLE_SWAGGER=true to publish it
[ ] rename the MCP tools in prompts and allow-lists (list_tables, query_table, …)
[ ] rebuild the bundle and deploy — a format-2 bundle is refused
```

`rebase doctor --policies` es el comando que conviene conectar a CI: devuelve un código de salida distinto de cero si una política aún contiene la tautología permisiva o si un push anterior la reemplazó. Vale la pena dedicar un minuto a las lecturas de `pg_policies` de antes y después: muestran las expresiones en sí mismas, que es la única manera de detectar una política que falla permitiendo el acceso (fail-open) escrita con una sintaxis que el detector no reconoce. Ni los paquetes ni el sistema de tipos te lo advertirán: el cambio reside en la base de datos, y `db push` es lo único que lo aplica allí.

## Revertir una versión

Antes de revertir a una versión anterior a la que introdujo los compañeros de solicitudes de administración (admin-request companions; consulta el [registro de cambios](/docs/changelog/)), debes desactivarlos. Un entorno de ejecución antiguo nunca elimina un compañero, por lo que una regla modificada tras la reversión seguiría permitiendo el acceso de cualquier administrador a todas las filas. Ejecuta `REVOKE rebase_admin_request FROM rebase_user_admin;` una vez por cada rol de solicitud de administrador, o elimina las políticas `_ar_`. En [Las lecturas de administración utilizan los índices del propietario](/docs/deployment/existing-database/#admin-reads-use-the-owners-indexes) se explica su funcionamiento.
