# Upgrade von 0.30 → 0.31

<span class="since-badge" data-since="0.31">Seit 0.31</span>

0.31 macht das Backend „Postgres-first“. Die Tabellen, die Sie mit `defineTable` in `backend/schema/` deklarieren, sind das Einzige, was das Backend über Ihre Daten weiß; was das Admin-Panel darüber anzeigt, befindet sich im Frontend. Fast jeder unten aufgeführte Eintrag ist eine Konsequenz dieser Aufteilung, und fast alles wird durch einen einzigen Befehl für Sie erledigt.

### Die Checkliste pro Projekt

1. **Aktualisieren Sie zuerst jedes `@rebasepro`-Paket** in jedem Workspace-Paket, damit die vom Codemod gelesenen Typen diejenigen von 0.31 sind: `pnpm -r up "@rebasepro/*@0.31.0"`, danach `pnpm install`. Ein Projekt auf einer Version vor 0.30 wendet zuerst die Codeänderungen der dazwischen liegenden Leitfäden an ([Upgrading](/docs/upgrading/)) und erfüllt die Toolchain-Mindestanforderungen von 0.31 – Node 22.22, TypeScript 6, React 19.2.7, React Router 8, Vite 8 ([die Liste](/docs/upgrading/0-30-to-0-31-by-hand/#a-project-on-a-release-before-030)): Der Codemod lädt eine 0.20–0.29 `config/` und seine SQL-Prüfung besteht, aber diese Prüfung vergleicht den 0.31-Compiler mit sich selbst – erst Schritt 7 gegen Ihre Datenbank beweist, dass das generierte DDL dem entspricht, was Ihre Datenbank enthält.
2. **Commiten Sie und führen Sie den Codemod als Dry-Run aus:** `rebase migrate collections-to-tables --dry-run`. Dies gibt die Dateien aus, die geschrieben würden, was abgelehnt wird (mit Datei und Zeile), die Hinweise und die manuellen Schritte, und schreibt nichts. Beheben Sie zuerst in `config/`, was abgelehnt wird.
3. **Führen Sie ihn tatsächlich aus:** `rebase migrate collections-to-tables`. Er schreibt `backend/schema/`, `frontend/src/cms/` (mit `ui-config.json`), die `backend/`-Module und die Projektdateien, fügt `rebaseBackendGuard()` zur `vite.config.ts` des Scaffolds hinzu, schreibt Ihre SDK-Aufrufe um, verschiebt die Importe von Namen, die 0.31 in ein anderes Paket verschoben hat ([Abschnitt 135](#135-rebaseprotypes-und-rebaseprocommon-entfernen-das-collection-modell-aus-ihren-roots)), und beweist, dass das generierte SQL Byte für Byte identisch ist – oder setzt jede Datei zurück. Siehe [Abschnitt 108](#108-tabellen-in-backendschema-ersetzen-configcollections--führen-sie-zuerst-den-codemod-aus).
4. **Lesen Sie den letzten Abschnitt der Ausgabe: „Review before deploying: these rules change meaning“**, und entscheiden Sie über jede aufgeführte Regel ([unten](#review-vor-dem-deployment-diese-regeln-ändern-ihre-bedeutung)).
5. **Führen Sie die ausgegebenen manuellen Schritte der Reihe nach durch.** Jeder nennt seine Datei, und die meisten enthalten das zu schreibende Snippet: das Einbinden von `<RebaseCMS>` mit `tableCustomizations` und `uiConfig`, wenn Ihre `App.tsx` nicht die des Scaffolds ist (oder das Panel in einem anderen Modul gemountet ist, das der Schritt benennt), `rebaseBackendGuard()`, wenn Ihre `vite.config.ts` nicht die Standarddatei ist sowie in jeder anderen statischen App von `rebase.json` ([Abschnitt 130](#130-rebase-build-verweigert-ein-frontend-ohne-rebasebackendguard)), globale Hooks, ein Import eines von 0.31 entfernten Namens ([Abschnitt 135](#135-rebaseprotypes-und-rebaseprocommon-entfernen-das-collection-modell-aus-ihren-roots)) und `rebase skills install`, wenn das Projekt Agent-Skills enthält ([Abschnitt 128](#128-der-agent-skill-rebase-collections-heißt-rebase-tables)). Führen Sie `pnpm install` aus, wenn die Ausgabe „Dependencies added“ auflistet. Lesen Sie dann zwei Listen im SDK-Teil der Ausgabe:
   - **„Rewritten by name — review“**: `.collection(`-Aufrufe auf einem Receiver ohne Typ (`any`), die umgeschrieben wurden, weil der Receiver `dataAsAdmin` heißt oder `.data` mit einem literalen Tabellennamen ist; das `collection`-Member eines Typs, den ein `data` / `dataAsAdmin`-Slot hält; sowie Test-Doubles. Überprüfen Sie bei jedem Aufruf, ob es sich um das SDK handelt.
   - **„Left unchanged — check each“**: `.collection(`-Aufrufe, bei denen der Codemod nicht nachweisen konnte, dass es sich um das SDK handelt, wie z. B. ein Aufruf über einen Typ, den Ihr Projekt selbst deklariert. Ein Aufruf, der hier belassen wurde und *tatsächlich* das SDK ist, schlägt unter 0.31 zur Laufzeit fehl: Benennen Sie ihn manuell in `.table(` um. Code, der prüft, ob `collection` existiert (`typeof data.collection === "function"`), ist ein manueller Schritt: Unter 0.31 nimmt er stillschweigend den anderen Zweig.

   Eine Datei, die als Build-Output committet wurde (ein gebündeltes oder minifiziertes `.js`), wird niemals bearbeitet: Sie wird aufgelistet, also bauen Sie sie nach der Migration neu und ersetzen Sie eine vendored Kopie des Clients durch den 0.31-Build. Wiederholte Schritte derselben Art werden einmal ausgegeben und listen jede betroffene Datei und Zeile auf; `--json` gibt jeden Schritt separat aus. Lesen Sie dann [Was reale Projekte manuell geändert haben](/docs/upgrading/0-30-to-0-31-by-hand/): die Anpassungen, die reale Projekte nach diesen Schritten noch vorgenommen haben.
6. **Führen Sie die vom Codemod ausgegebene `git rm`-Zeile aus**, sobald das Diff überprüft wurde und `rebase migrate collections-to-tables --check` erfolgreich durchläuft: `git rm -r config/collections …` und die Verdrahtung, die nach `backend/` verschoben wurde, oder `git rm -r config`, wenn dort nichts Eigenes mehr übrig ist ([Abschnitt 109](#109-es-gibt-kein-config-paket-mehr)). Die nächsten drei Schritte setzen dies voraus: `generate-sdk`, `db push`, `doctor` und `verify` verweigern ein Projekt, das noch `config/collections` enthält.
7. **`rebase generate-sdk`** – die Namen des generierten Moduls haben sich geändert ([Abschnitt 115](#115-das-sdk-adressiert-eine-tabelle-datatableslug)).
8. **Führen Sie an Ihrer Datenbank** `rebase db push --dry-run` aus und erwarten Sie „No changes: the database already matches these tables.“, dann `rebase doctor --policies` und erwarten Sie keinen Policy-Drift. Die SQL-Prüfung des Codemods beweist die Korrektheit der Konvertierung; diese beiden Befehle beweisen sie gegen die reale Datenbank, und jeder Policy-Unterschied, den einer von beiden auflistet, bedeutet eine Änderung daran, wer auf was zugreifen kann.
9. **`rebase verify`** – liest jetzt auch `frontend/src/cms`: eine Anpassung, die eine nicht existierende Tabelle oder ein nicht existierendes Feld benennt, eine erforderliche Spalte, die vom Formular ausgeschlossen wurde, ein fehlendes `rebaseBackendGuard()`, eine `ui-config.json`, die nicht an `<RebaseCMS>` übergeben wurde.
10. **Erneut bauen und deployen.** Ein vor 0.31 erstelltes Bundle startet auf einer 0.31-Laufzeitumgebung nicht ([Abschnitt 112](#112-bundle-format-3-format-2-bundles-werden-abgelehnt)). Der erste Start aktualisiert den Schema-Versionsstempel der Datenbank einmalig ([Abschnitt 113](#113-die-schema-version-wird-aus-tabellen-berechnet-v2)).

Führen Sie `rebase migrate collections-to-tables --check` in der CI aus, bis `config/` entfernt ist: Es verifiziert, dass die migrierten Tabellen immer noch dasselbe SQL rendern wie die Collections, von denen sie stammen, und bricht mit Exit-Code 1 ab, solange eine unter „Review before deploying“ aufgeführte Regel nicht bestätigt wurde – übergeben Sie `--accept-rule-changes`, sobald Sie diese überprüft haben.

### Review vor dem Deployment: Diese Regeln ändern ihre Bedeutung

Der Codemod übernimmt jede Sicherheitsregel unverändert, und jede behält ihren Policy-Namen. Aber der 0.30-Compiler las nur das erste von `condition`, `using`, `access: "public"` und `ownerField`, und kannte keinen anderen `access`-Wert, weshalb vier Ausprägungen von Regeln nun andere Berechtigungen erteilen. Zwei davon erweitern den Zugriff:

| Die Regel | 0.30 gewährte | 0.31 gewährt | |
|---|---|---|---|
| ein einfaches `access: "authenticated"` (ohne `roles`) | nichts | jedem angemeldeten Aufrufer, einschließlich Gästen | **erweitert** |
| `access` + `check`, keine `condition`, auf `select` / `update` / `delete` / `all` | keine vorhandene Zeile | jede vorhandene Zeile für Aufrufer mit `access` | **erweitert** |
| `access: "authenticated"` + `condition` | jedem, der die `condition` erfüllt | nur angemeldeten Aufrufern, die sie erfüllen | schränkt ein |
| `access: "authenticated"` + `check`, auf `insert` | jedem, der eine passende Zeile einfügt | nur angemeldeten Aufrufern | schränkt ein |

Am häufigsten kommt der erste Fall vor. Schreiben Sie `access: "registered"`, um nur Aufrufern mit einem Konto (keine anonymen Gäste) Zugriff zu gewähren, oder entfernen Sie die Regel, um weiterhin nichts zu gewähren. `access` mit `roles` und eine `condition` als Plain Object behalten ihre bisherige Bedeutung und werden nicht aufgelistet.

Der Codemod verweigert außerdem Regeln, die auch der 0.31-Compiler ablehnt: solche, die Klauseln kombinieren, die der Typ `SecurityRule` ausschließt (`access` neben `ownerField`, `using` oder `withCheck`; `ownerField` neben `using`, `withCheck`, `condition` oder `check`; `condition` oder `check` neben `using` oder `withCheck`), sowie solche mit einem ungültigen Wert für `access`, `mode`, `operation(s)` oder `roles` – ein falsch geschriebenes `"restrictive"` wurde früher fälschlicherweise als permissive kompiliert. Siehe [Sicherheitsregeln](/docs/collections/security-rules/).

### Was sich sonst noch anders verhält

- **Was `GET /api/schema/tables` einer Person mitteilt.** Administratoren und Inhaber von `schema:read` erhalten jede Tabelle. Jeder andere angemeldete Benutzer, einschließlich Gästen, erhält nur die Tabellen, die seine Rollen erreichen können, und nur mit den Regeln, die für ihn gelten können; Relationen zu anderen Tabellen werden weggelassen und Hook-Flags zurückgehalten. Ein Frontend, das die Beschreibung einer anderen Tabelle als regulärer Benutzer gelesen hat, erhält weniger; `schemaTables: { persons: "all" }` in den Backend-Optionen stellt die vollständige Beschreibung wieder her. Siehe [Endpunkte](/docs/backend/endpoints/#schema).
- **Relationsnamen sind exakt**, und **Big-Integer-Fremdschlüssel sind Zahlen** ([Abschnitt 131](#131-zeilen-auf-der-leitung-folgen-ihrer-spalte)).
- **Die Historie wird maskiert ausgeliefert** ([Abschnitt 132](#132-die-historie-wird-als-lesevorgänge-ausgeliefert)).
- **MCP-Tool-Namen und die View-Payload** ändern sich gemeinsam für den gehosteten Konnektor und die von ihm erreichten Laufzeiten ([Abschnitt 122](#122-mcp-tools-sind-nach-tabellen-benannt)).
- **Absichtlich eingeschränkt.** Audit-Stamps (`.onCreateNow()` / `.onUpdateNow()`-Spalten) sind in den Listenspalten des Panels standardmäßig ausgeblendet: Eine migrierte Liste, die `created_at` angezeigt hat, verliert diese Spalte, bis Sie `fields: { created_at: { hidden: false } }` in deren `customizeTable` schreiben. Der Codemod verweigert unter Angabe des Grundes Tuple-JSON-Arrays, `vector` / `binary` / `reference` innerhalb einer Map, `databaseId` auf einer Postgres-Collection, `isId: "cuid"`, eine einzelne `isId`-Relation und `disableDefaultPolicies: true` ohne Regeln. Eine einspaltige Relation zu einer Tabelle mit zusammengesetztem Primärschlüssel wird abgelehnt (schreiben Sie sie mit `rel.via()`). OpenAPI-Tags stammen aus dem Slug, nicht aus dem Anzeigenamen. `rebase schema introspect` lässt Tabellen ohne Primärschlüssel aus und gibt den Grund an (ein Server, der die Datenbank introspektiert, liefert sie dennoch aus). Eine einfache View, die `roles` deklariert, führt zu einem Compiler-Fehler; der Codemod entfernt dies mit einem Hinweis.
- **Was reale Projekte dennoch manuell geändert haben** – minimale Toolchain-Versionen, `({ entity })` im Admin-Code, Includes einer umbenannten Relation, zur Laufzeit geänderte Collection-Objekte, SDK-Aufrufe auf untypisierten Receivern: [Was reale Projekte von Hand geändert haben](/docs/upgrading/0-30-to-0-31-by-hand/).
- **Wiederherstellung auf einem anderen Cluster.** Der Stempel der Standard-Admin-Policies hasht Rollen-OIDs; nach einem Dump oder Point-in-Time-Restore auf einem anderen Cluster erstellt der erste `db push` oder Boot diese Policies einmalig neu – mit denselben Namen und demselben SQL.

### Die Begriffe

| Vorher | Jetzt | Wo „Collection“ bleibt |
|---|---|---|
| eine Collection in `config/collections/` | eine **Tabelle** in `backend/schema/` (`defineTable`) | — |
| `properties` | `columns` (`col.*`) und `relations` (`rel.*`) | — |
| `securityRules`, `defaultSecurityRules` | `rls` (erforderlich), `defaultRls` | — |
| `callbacks`, `Property.callbacks` | `hooks`, das `.transform()` einer Spalte | — |
| der `admin`-Block | `customizeTable` in `frontend/src/cms/` | — |
| `data.collection(slug)` | `data.table(slug)` | — |
| was das Admin-Panel darstellt | eine **Collection**: eine Tabelle, wie das Panel sie anzeigt, oder eine Firestore-Collection | das CMS: `CollectionPanel`, der Collection Editor, `externalCollections` |

## 108. Tabellen in `backend/schema` ersetzen `config/collections` — führen Sie zuerst den Codemod aus

**Wen das betrifft:** jedes Projekt mit einem `config/collections/`-Verzeichnis.

**Was sich geändert hat:** Das Backend liest nur noch `backend/schema/index.ts` und die darin exportierten `defineTable`-, `defineAuthTable`- und `defineView`-Ergebnisse. `defineCollection`-Dateien werden von nichts mehr gelesen: Die Runtime, jeder CLI-Befehl und die `rebase.json`-Validierung verweigern ein Projekt, das noch `config/collections` enthält, unter Nennung des folgenden Befehls. `rls` ist für jede Tabelle erforderlich – eine Liste von Regeln, `"admin-only"`, oder `"inherit"` für das vom Index exportierte `defaultRls` – und `disableDefaultPolicies` heißt jetzt `defaultPolicies: false`.

**Was zu tun ist:**

```bash
rebase migrate collections-to-tables            # or --dry-run first
```

Es wird eine Tabelle pro Collection geschrieben, jede physische Spalte explizit an ihrer ursprünglichen Position (sodass die Schlüsselspalte eines `belongsTo` ausgeschrieben wird), der Index mit `defaultRls` aus `defaultSecurityRules`, ein `customizeTable` für jede Collection, deren Darstellung nicht dem Standard entsprach, und `defineFirestoreCollection`-Dateien für Firestore-Collections. Die Callbacks einer Collection werden zu den `hooks` ihrer Tabelle und den `.transform()`-Methoden ihrer Spalten; die globalen `callbacks`, die `config/index.ts` exportiert hat, sind ein manueller Schritt (Abschnitt 109). Anschließend liest er das Ergebnis über die neue Pipeline zurück: DDL, Policies, Search, Vector, Triggers, Views und das Drizzle-Schema müssen Byte für Byte identisch mit dem sein, was die Collections generiert haben, andernfalls wird jede Datei zurückgesetzt und der Durchlauf bricht mit Exit-Code 1 und dem Diff ab.

Außerdem übernimmt er Dinge, die bisher manuelle Arbeit erforderten:

- **Callbacks, die von einem Helper erstellt wurden** (`callbacks: softDeleteCallbacks(...)` oder ein importiertes Callbacks-Objekt), werden zu `hooks:` mit demselben Ausdruck, und die Funktionen des Helpers werden dort, wo sie geschrieben sind, in Tabellen-Hook-Props konvertiert (der Codemod folgt relativen Importen, `const`s, Eigenschaftszugriffen und einem einzelnen `return`). Wenn er dem Helper nicht folgen kann, benennt ein Schritt die zu prüfenden Hooks.
- **Ein Funktions-`storagePath`** migriert in zwei Hälften: Die Funktion wird zum `storage.path` der Anpassung, sodass das Panel weiterhin bestimmt, wohin ein Upload geht, und das `path`-Template der Spalte entspricht dem Muster der Keys, die sie zurückgibt – der statische Text ihres Template-Literals mit jedem `${…}` als `{path}` (`` `${owner}/cv` `` → `{path}/cv`). Der Server wendet nun `maxBytes` und `accept` der Spalte auf jeden Upload an, dessen Key diesem Template entspricht, nicht nur auf solche, die die Spalte explizit benennen; die Limits sind also strenger als in 0.30. Eine Funktion, deren Ergebnis keinen statischen Text enthält, wird abgelehnt: Vergeben Sie vorher einen solchen.
- **Ein 0.30 `policy.existsIn({ collection })`** behält seine Tabelle, und `auth: { collection: usersCollection }` in einem benutzerdefinierten Backend-Einstiegspunkt wird entfernt (das `defineAuthTable` ist die Auth-Tabelle). Eine `collections`-Boot-Option wird zu `schemaDir`.
- **Ein `dynamicProps`-Builder** gibt unter 0.31 eine Feldanpassung mit flachen Keys zurück (`{ readOnly: true }`, nicht `{ admin: { readOnly: true } }`). Der Codemod schreibt Builder um, deren Rückgaben Objektliterale sind (inline oder in einem gemeinsam genutzten Modul), und listet alle anderen auf.
- **Darstellungseigenschaften, die aus einem gemeinsamen Objekt per Spread eingefügt wurden**, werden in die Anpassung übernommen (`….dynamicProps`); Darstellungseigenschaften, die eine Wrapper-Funktion berechnet, sind ein zu prüfender Schritt, keine Verweigerung des Projekts. Ein Komponentenpfad wird relativ zu dem Modul aufgelöst, das ihn geschrieben hat, und ein Wert, der beim Laden von `config/` berechnet wird (`new Date()`, `Date.now()`, ein Umgebungsvariablenzugriff), wird als sein Ausdruck übernommen und niemals auf den Wert des Migrationslaufs festgeschrieben.
- **Firestore-Collections, die von einer Funktion erstellt werden** (ein `getAllFirestoreCollections()`, das die App per Spread in das Panel einfügt), werden einzeln in `defineFirestoreCollection` konvertiert, wenn die Datei einer Collection ihr Literal enthält; ein Schritt pro Builder benennt den Rest und das zu schreibende Format, und ein weiterer benennt eine Referenz außerhalb eines konvertierten Literals, die noch `path` lauten würde.
- **Importe von `config/` über einen Pfad-Alias** (ein tsconfig-`paths`-Eintrag, ein Vite-`resolve.alias`) werden wie relative Pfade umgeschrieben oder aufgelistet, und ein von `config/index.ts` re-exportiertes `storageAuthorize` wird nach `backend/storage.ts` verschoben.
- **Eine Relation, die in `<key>Relation` umbenannt wurde**, behält ihr Label, ihre Listenspalte und ihren Titel: Die Anpassung benennt den neuen Key. Code, der sie per Include einbindet, wird nicht automatisch angepasst ([was zu ändern ist](/docs/upgrading/0-30-to-0-31-by-hand/#a-belongsto-key-is-a-column-and-a-relation-can-be-renamed)).

Was nicht exakt übernommen werden kann, wird unter Angabe von Datei und Zeile abgelehnt, und es wird nichts geschrieben: eine Collection, die durch den Aufruf einer Funktion erstellt wird, ein Spread oder Accessor, durch den nicht hindurchgelesen werden kann, eine andere Engine als Postgres oder Firestore, eine Ausgabedatei, die bereits mit anderem Inhalt existiert (verschieben Sie sie beiseite oder verwenden Sie `--force`). Ein unsauberer Git-Tree oder ein Projekt außerhalb von Git wird ebenfalls abgelehnt, damit die Migration ein einziges, überprüfbares Diff darstellt. `--json` gibt den gesamten Bericht für ein Skript oder einen Agenten aus. Siehe [`rebase migrate`](/docs/cli/schema/#rebase-migrate) und [Tabellen](/docs/schema/).

Die geschriebenen Tabellen formulieren ihre Spalten so, wie es Drizzles `pg-core` tut – `col.varchar({ length: 160 })`, `col.timestamp({ withTimezone: true })`, `col.text().array()`, `pgEnum(...)`, `` .default(sql`…`) ``, `.generatedByDefaultAsIdentity()` – sodass die Ausgabe keine weiteren Anpassungen benötigt; siehe [Spalten](/docs/schema/columns/). Eine Tabelle, die manuell gegen ein 0.31-Pre-Release in den früheren Schreibweisen verfasst wurde (`col.timestamptz()`, `col.varchar(160)`, `col.array(col.text())`, `col.enum(values, { name })`, `.defaultSql()`, `.identity()`, `.column("…")`), kompiliert nicht mehr: `tooling/scripts/drizzle-sweep.mts` im Rebase-Repository konvertiert sie, indem es nur die Builder-Chains umschreibt, und weist mit `--verify` nach, dass jede konvertierte Tabelle zum selben Deskriptor kompiliert (`npx tsx drizzle-sweep.mts --verify backend/schema`).

Der darauffolgende `sdk-calls`-Durchlauf schreibt auch Regelquellen um: `existsIn({ collection })` und `membership: { collection }` werden zu `table` (Abschnitt 123); `--skip-sdk-calls` überspringt auch das. Was Ihnen überlassen bleibt, wird als nummerierte manuelle Schritte ausgegeben. Wenn das Projekt installierte Agent-Skills enthält, ist der letzte Schritt die Zeile `rebase skills install`, die diese aktualisiert (Abschnitt 128). Ein einfaches `rebase migrate` gibt die Hilfe für beide Unterbefehle aus.

## 109. Es gibt kein Config-Paket mehr

**Wen das betrifft:** jedes Projekt – `config/` war ein eigener Workspace.

0.31 liest `config/collections` nicht mehr; es verbietet `config/` jedoch nicht. Der Codemod entfernt, was Rebase gelesen hat – die Collection-Dateien und die Verdrahtung, die nach `backend/` umzieht (`resources.ts`, `storage.ts`, `generated/register.ts` und die Re-Exporte davon in `config/index.ts`) – und belässt Ihre eigenen Module in `config/` dort, wo sie sind, importierbar wie zuvor: `config/` bleibt ein Workspace-Paket, und das Backend kompiliert weiterhin `../config/**/*`. Nur Importe von entferntem Code werden umgeschrieben: Eine von Backend-Code importierte Collection-Datei verweist nun auf das Tabellenmodul (ein Schritt listet Verwendungen auf, die sie als Objekt lesen); wird sie von Frontend-Code importiert, wird sie zu einem reinen Typ-Import der Tabelle, sofern sie nur als Typ verwendet wird, oder zu einem Schritt, der die Anpassung benennt; ein Helper innerhalb von `config/collections` wird neben den Code kopiert, der ihn benötigt.

**Was sich geändert hat:** Was neben den Collections lag, zieht nach `backend/` um:

| Vorher | Jetzt |
|---|---|
| `config/resources.ts` | `backend/resources.ts` |
| `config/storage.ts`, `storageAuthorize` aus `config/index.ts` | `backend/storage.ts` |
| aus `config/index.ts` exportierte `callbacks` | aus `backend/hooks.ts` exportierte `hooks` (`TableHooks`: `table` statt `collection`, `values` statt `row`) |
| `config/generated/register.ts` | `backend/generated/register.ts` |
| `rebase.json` `config`, `usersCollection` | `tables` (Standard `backend/schema`); die Auth-Tabelle ist diejenige, die mit `defineAuthTable` deklariert wurde |

Die Runtime liest `storageAuthorize` und `hooks` und nichts anderes aus diesen Modulen; jeder andere Export wird beim Boot gemeldet. Das Frontend importiert `backend/**` ausschließlich als Typen – `pnpm check:frontend-backend-imports` verweigert Wert-Importe, da diese Server-Code an den Browser ausliefern würden.

**Was zu tun ist:** Der Codemod verschiebt `resources.ts`, `storage.ts` sowie die Registrierung und schreibt `rebase.json`, `package.json`, `pnpm-workspace.yaml` und `backend/tsconfig.json` um. Die globalen `callbacks` sind ein manueller Schritt, der ausgegeben wird: Verschieben Sie sie manuell nach `backend/hooks.ts` und fügen Sie `hooks.ts` zum `include` von `backend/tsconfig.json` hinzu, damit `tsc` sie überprüft. Führen Sie danach die ausgegebene `git rm`-Zeile aus: `git rm -r config/collections …`, oder `git rm -r config`, wenn nichts Eigenes mehr übrig ist.

## 110. Boot-Optionen und Hooks benennen Tabellen

**Wen das betrifft:** ein Backend, das Sie selbst booten (`initializeRebaseBackend`, `createRebaseBackend`), und Code, der Hooks nach dem Boot anhängt.

**Was sich geändert hat:**

| Vorher | Jetzt |
|---|---|
| `collections`, `collectionsDir` | `tables`, `defaultRls`, `schemaDir` |
| `callbacks` | `hooks` |
| `auth.collection` | entfernt: das `defineAuthTable` in `tables` |
| `backend.setCollectionCallbacks(slug, cb)` | `backend.setTableHooks(slug, hooks)` |
| Hook-Props `collection`, `row` | `table` (der Deskriptor), `values` |
| `composeCallbacks` | `composeTableHooks` aus `@rebasepro/common` |
| `openRebase({ collections, callbacks })` | `openRebase({ tables, hooks })`, `tables` aus `compileSchema([...])` |
| `OpenedRebase.collections`; die `rebase console`-Variable `collections` | `.tables`; `tables` |

```diff ts
-await initializeRebaseBackend({ app, server, collectionsDir: "./config/collections", callbacks });
+await initializeRebaseBackend({ app, server, schemaDir: path.resolve(__dirname, "../schema"), hooks });
```

Hooks, die an ein an einer Aufrufstelle übergebenes Collection-Objekt angehängt wurden, werden nicht mehr ausgeführt: Der Treiber führt die Hooks der von ihm bedienten Tabellen aus; hängen Sie sie daher mit `setTableHooks` an.

**Was zu tun ist:** `rebase migrate sdk-calls` schreibt `setCollectionCallbacks` um, passt die Hook-Props an und listet jedes manuell zu aktualisierende Backend-Optionsobjekt auf. Ein Skript, das die Daten öffnet, kompiliert seine Tabellen:

```diff ts
-const rebase = await openRebase({ databaseUrl, collections, callbacks });
+const rebase = await openRebase({ databaseUrl, tables: compileSchema([products, orders]), hooks });
```

Siehe [Skripte](/docs/backend/scripts/#openrebase). Siehe [Backend-Übersicht](/docs/backend/) und [Globale Hooks](/docs/backend/hooks/).

## 111. Das Admin-Panel rendert die vom Server bereitgestellten Tabellen

**Wen das betrifft:** jedes Frontend, das `<RebaseCMS>` einbindet.

**Was sich geändert hat:** `<RebaseCMS collections>` gibt es nicht mehr. Das Panel zeigt jede Tabelle an, die das Backend unter `GET /api/schema/tables` bereitstellt (ohne Datei pro Tabelle), gefolgt von `externalCollections` (Firestore). `tableCustomizations` nimmt die `customizeTable`-Objekte aus `frontend/src/cms/` entgegen. Das Vite-Collections-Plugin und `virtual:rebase-collections` wurden entfernt. `CollectionsProvider` nimmt dieselben drei Eingaben entgegen (`tableCustomizations`, `externalCollections`, `tables`).

```diff tsx
-import { collections } from "virtual:rebase-collections";
-<RebaseCMS collections={collections}/>
+import { postsCms } from "./cms/posts";
+<RebaseCMS tableCustomizations={[postsCms]}/>
```

**Was zu tun ist:** Der Codemod schreibt `frontend/src/cms/index.ts`, welches `tableCustomizations` (und `externalCollections`) exportiert, und bindet es in der `App.tsx` eines Scaffolds direkt ein; eine `App.tsx`, die er nicht erkennt, das Plugin in `vite.config.ts` und die Deklaration des virtuellen Moduls werden als manuelle Schritte ausgegeben. Siehe [Eine Tabelle anpassen](/docs/frontend/customize-table/).

## 112. Bundle-Format 3; Format-2-Bundles werden abgelehnt

**Wen das betrifft:** jedes Deployment eines gebauten Bundles – selbst gehostet mit dem Runtime-Image oder auf Rebase Cloud.

**Was sich geändert hat:** Das Schema eines Bundles ist `entry.tables`, neben `entry.resources`, `entry.storage` und `entry.hooks`; `bundleFormat` ist 3 und der Laufzeitvertrag 2. Ein Bundle im Format 1 oder 2 enthält `config/collections`, wofür eine 0.31-Runtime keine Lesemöglichkeit mehr besitzt. Sie verweigert daher den Start mit einem Verweis auf den Codemod in der Fehlermeldung, anstatt die Datenbank zu introspektieren und eine abweichende API bereitzustellen.

**Was zu tun ist:** Migrieren Sie den Quellcode, führen Sie dann `rebase build` aus und deployen Sie. Auf Rebase Cloud baut das erneute Deployment des migrierten Repositorys dieses neu. Siehe [Runtime und Bundles](/docs/architecture/runtime-and-bundles/).

## 113. Die Schema-Version wird aus Tabellen berechnet (`v2:`)

**Wen das betrifft:** jede Datenbank, die von einer Runtime vor 0.31 initialisiert wurde, und jedes generierte SDK.

**Was sich geändert hat:** Die Schema-Version hasht die kompilierten Tabellendeskriptoren und beginnt mit `v2:`. Eine mit `v1:` gestempelte Datenbank meldet die Modelländerung einmalig – das Boot-Log und `rebase doctor` weisen darauf hin und erklären, wie neu gestempelt wird – und jedes generierte SDK wird einmalig als veraltet gemeldet.

**Was zu tun ist:** Einmalig mit der neuen Laufzeitumgebung bereitstellen: Starten Sie den Prozess, der das Schema besitzt, oder führen Sie `rebase db push` aus. Mit `REBASE_REQUIRE_SCHEMA_MATCH=true` stempeln Sie neu, bevor die anderen Prozesse schrittweise aktualisiert werden. Generieren Sie das SDK neu.

## 115. Das SDK adressiert eine Tabelle: `data.table(slug)`

**Wen das betrifft:** jeden Client, jede Funktion, jeden Cron, jeden Hook und jedes Skript, das eine Tabelle über ihren Slug anspricht oder das generierte Dictionary übergibt.

**Was sich geändert hat:**

| Vorher | Jetzt |
|---|---|
| `data.collection(slug)` | `data.table(slug)` |
| `createRebaseClient({ collections: collectionsDictionary })` | `createRebaseClient({ tables: tablesDictionary })` |
| generiertes `CollectionName`, `CollectionsDictionary` | `TableName`, `TablesDictionary` |
| Batch `{ op, collection }` (SDK und `POST /api/data/_batch`) | `{ op, table }` |
| `CollectionClient`, `SDKCollectionClient`, `CollectionAccessor`, `CollectionTrashAccessor` | `TableClient`, `SDKTableClient`, `TableAccessor`, `TableTrashAccessor` |
| Offline `maxCachedRowsPerCollection`, `maxCachedQueriesPerCollection` | `…PerTable` |
| reservierter Accessor `<name>Collection`; `collectionCollection` | `<name>Table`; die `collection`-Tabelle heißt `collection` |

```diff ts
-const { data } = await client.data.collection("posts").find();
+const { data } = await client.data.table("posts").find();
```

Typisierte Accessoren (`client.data.posts`) bleiben unverändert.

**Was zu tun ist:** Der Codemod führt `rebase migrate sdk-calls` über Ihren Code aus – führen Sie dies bei einem bereits migrierten Projekt separat aus – und danach `rebase generate-sdk`. Ein `.collection(`-Aufruf, dessen Receiver nicht das SDK ist, bleibt unverändert erhalten und wird aufgelistet. Siehe [Typisiertes SDK](/docs/sdk/).

## 116. CLI-Flags: `--schema-dir` statt `--collections`

**Wen das betrifft:** Skripte und CI-Schritte, die das CLI mit einem Schema-Pfad aufrufen.

**Was sich geändert hat:** `--collections` / `-c` werden bei jedem Befehl, der das Schema liest, abgelehnt (mit einem Hinweis auf den Codemod in der Meldung; `generate-sdk` ignoriert ein überflüssiges `--collections-dir`); `--schema-dir` gibt ein anderes Schema-Verzeichnis als `backend/schema` an. `rebase schema introspect` schreibt `defineTable`-Dateien nach `backend/schema/` – `--output` existiert nicht mehr. `REBASE_STRICT_COLLECTION_CONFIG` wird nicht mehr ausgewertet: Ein Schema, das nicht kompiliert, verhindert stets den Start.

**Was zu tun ist:** Ersetzen Sie die Flags. Siehe [CLI](/docs/cli/) und [Schema-Generierung](/docs/cli/schema/).

## 117. Der Schema-Editor bearbeitet `backend/schema` mit `TablePatch`

**Wen das betrifft:** Code, der Routen des Schema-Editors oder des Live-Schemas aufruft, sowie Deployments, die Variablen für Live-Editing setzen.

**Was sich geändert hat:** `/api/admin/schema-editor/collection/save`, `collection/delete`, `property/save` und `property/delete` wurden entfernt. Der Editor bedient `GET /tables`, `POST /preview` und `POST /apply`, und die Endpunkte `/plan` und `/apply` des Live-Schema-Editings akzeptieren `{ patches: TablePatch[] }` anstelle einer Collection oder eines Patches dafür. `REBASE_LIVE_SCHEMA_COLLECTIONS_PATH` wird beim Start abgewiesen: Die Variable heißt nun `REBASE_LIVE_SCHEMA_PATH` (Standard `backend/schema`), und `liveSchema.repository.collectionsPath` heißt `schemaPath`. Darstellungseinstellungen sind niemals Schema-Edits: Sie werden als UI-Präferenzen gespeichert (`/api/admin/ui-config`). Ein Edit, dessen Datei auf der Festplatte geändert wurde, nachdem der Edit vorbereitet wurde (durch Speichern in der IDE oder einen anderen Prozess), antwortet mit 409 `SCHEMA_EDIT_STALE_FILE` und schreibt nichts; zuvor war dies ein 400 `SCHEMA_EDIT_REFUSED`.

**Was zu tun ist:** Benennen Sie die Variable um; passen Sie Aufrufer der Routen so an, dass sie `TablePatch`-Edits senden, und laden Sie bei `SCHEMA_EDIT_STALE_FILE` neu. Siehe [Live-Schema-Bearbeitung](/docs/backend/live-schema-editing/).

## 118. Ein Komponenten-Slot ist eine Komponente

**Wen das betrifft:** Anpassungen, die eine React-Komponente über einen String-Pfad oder einen Lazy-Thunk `() => import(…)` angegeben haben.

**Was sich geändert hat:** `Field` / `Preview` / `Filter` eines Feldes, Collection-`Actions`, `entityViews[].Builder`, `collectionViews[].Builder`, `formView.Builder` und Komponenten-Overrides akzeptieren die Komponente direkt. `ComponentRef`, `ComponentLike`, `LazyComponentRef` und `isLazyComponentRef` (`@rebasepro/types`), `asComponentRef` und `asReactComponent` (`@rebasepro/cms-types`) sowie `resolveComponentRef` / `useResolvedComponent` (`@rebasepro/app`) wurden entfernt. `customizeTable` verweigert Strings oder Thunks mit der Meldung „imported by value“.

**Was zu tun ist:** Importieren Sie die Komponente in der Datei `frontend/src/cms/` und übergeben Sie sie direkt. Siehe [Benutzerdefinierte Felder](/docs/frontend/custom-fields/).

## 119. Panel-Einstellungen sind UI-Einstellungen

**Wen das betrifft:** Code, der `UserConfigurationPersistence` implementiert.

**Was sich geändert hat:** Wie ein Benutzer eine Tabelle in der Größe angepasst oder neu angeordnet hat, ist ein `UiTablePreferences`-Delta: `getTablePreferences` / `saveTablePreferences` ersetzen `getCollectionConfig` / `onCollectionModified`, und der partielle Collection-Config-Typ, den sie entgegennahmen, wurde entfernt. Der Browser-Store speichert diese unter `table_preferences::<slug>` und ignoriert, was ein älteres Panel gespeichert hat, sodass die Spaltenbreiten und Ansichtsmodi jedes Benutzers einmalig zurückgesetzt werden. `userSelect` auf einem Feld existiert nicht mehr: Eine `.userId()`-Spalte dient als Benutzerauswahl.

Die Studio-Bridge folgt diesem Schema: `StudioSchemaEditing.updateCollection` heißt `applyTablePatches(slug, patches)`, und der Collection Editor sendet `{ patches }` an den Schema-Editor.

**Was zu tun ist:** Portieren Sie eine eigene Persistenz auf die beiden Methoden und ein eigenes `StudioSchemaEditing` auf `applyTablePatches`.

## 120. MongoDB wird nicht mehr unterstützt

**Wen das betrifft:** ein Projekt mit `@rebasepro/server-mongo` oder eines, das `database(…, { engine: "mongodb" })` deklariert.

**Was sich geändert hat:** Das Paket wurde entfernt, ebenso wie die Mongo-Collection-Typen und der Rest des Mongo-Modells. Postgres ist die einzige Server-Engine: Eine Server-Transport-Quelle auf einer anderen Engine verweigert den Boot unter Nennung der Engine.

**Was zu tun ist:** Migrieren Sie die Daten nach Postgres. Es gibt keinen migrationsinternen Pfad innerhalb von Rebase.

## 121. Firestore-Collections befinden sich im Frontend

**Wen das betrifft:** ein hybrides Projekt mit `engine: "firestore"`-Collections.

**Was sich geändert hat:** Eine Firestore-Collection ist eine CMS-Quelle, die der Browser direkt liest: `defineFirestoreCollection` aus `@rebasepro/firebase` in `frontend/src/cms/`, übergeben an `<RebaseCMS externalCollections>`. Eine Referenz zwischen Firestore und einer Postgres-Tabelle wird als ID des Ziels gespeichert, und eine Firestore-Referenz, deren `path` auch ein Postgres-Slug ist, zielt nun auf die Postgres-Tabelle.

**Was zu tun ist:** Der Codemod schreibt die `defineFirestoreCollection`-Dateien. Verweisen Sie auf eine Firestore-Collection über den Slug dieser Collection. Siehe [Firebase](/docs/frontend/firebase/).

## 122. MCP-Tools sind nach Tabellen benannt

**Wen das betrifft:** Prompts, Skripte und Allow-Lists, die MCP-Tools benennen.

**Was sich geändert hat:** Remote `/mcp`: `list_collections`, `describe_collection`, `query_collection`, `show_collection`, `count_documents`, `aggregate_documents`, `get_document`, `create_document`, `update_document`, `delete_document` → `list_tables`, `describe_table`, `query_table`, `show_table`, `count_rows`, `aggregate_rows`, `get_row`, `create_row`, `update_row`, `delete_row`; das Argument `collection` heißt `table`, und `show_app` / `save_app` erwarten `tables`. Der lokale Server: `list_documents` → `query_table`, `get_document` → `get_row`, `create_document` → `create_row`, `update_document` → `update_row`, `delete_document` → `delete_row`; `rebase_schema_plan` nimmt `patches` entgegen; Ressourcen lauten `rebase://tables/{name}`. Die MCP Apps View-Payload hat Version 3: für den Aufrufer redigierte Tabellendeskriptoren, Pro-Tabelle-Berechtigungen und die UI-Präferenzen jedes Aufrufers unter `preferences` (`file`, `workspace`, `user`; ein API-Key hat keine User-Ebene), wobei Blöcke und Seeds `table` benennen. Die Ansicht `collection-table` wurde entfernt. `list_tables` hat keinen `title`; `describe_table` ergänzt `primaryKey`, `relations`, das `rls` des Aufrufers, `title` und `presentation`.

**Was zu tun ist:** Benennen Sie die Aufrufe um. View und Server müssen dieselbe Payload-Version verwenden: Ein gehosteter Konnektor und die von ihm erreichten Runtimes werden zusammen aktualisiert, und eine projektbezogene MCP-View wird mit den 0.31-Paketen neu gebaut. Siehe [MCP-Tool-Referenz](/docs/ai/mcp-tool-reference/) und [Remote-MCP](/docs/ai/remote-mcp/).

## 123. Das Regel-Vokabular nutzt `table`

**Wen das betrifft:** Regeln, die `policy.existsIn` oder einen Membership-Tenant verwenden, sowie Regeln, die `access` mit anderen Klauseln kombinieren.

**Was sich geändert hat:** `policy.existsIn({ collection, where })` heißt `existsIn({ table, where })`, und `tenant.from.membership.collection` heißt `membership.table`; Policy-Namen ändern sich nicht. Vier Regelvarianten gewähren nun andere Rechte, zwei davon mehr ([die Tabelle oben](#review-vor-dem-deployment-diese-regeln-ändern-ihre-bedeutung)): Ein einfaches `{ access: "authenticated" }`, das früher nichts gewährte, lässt nun jeden angemeldeten Aufrufer zu, und die Zwischentabellen (Junctions) einer solchen Tabelle erhalten ihre Schreib-Policies für Kanten. Regeln, die Klauseln kombinieren, die der Typ `SecurityRule` ausschließt, oder die einen ungültigen Wert für `access`, `mode`, `operation` oder `roles` enthalten, werden abgewiesen.

**Was zu tun ist:** Der Codemod benennt die Keys um, lehnt ungültige Regeln unter Angabe von Datei und Zeile ab und listet die Regeln mit geänderter Bedeutung unter „Review before deploying“ auf. Entscheiden Sie für jede Regel: Beibehalten, `access: "registered"` verwenden (angemeldete Aufrufer mit Konto) oder entfernen. Führen Sie anschließend `rebase db push --dry-run` und `rebase doctor --policies` an Ihrer Datenbank aus.

## 124. Studio liest die Tabellen vom Server

**Wen das betrifft:** Studio, das auf ein Backend vor Version 0.31 zeigt, und Studio-JS-Konsolenskripte.

**Was sich geändert hat:** Jedes schemabezogene Werkzeug liest `GET /api/schema/tables`; bei einer Laufzeitumgebung ohne diesen Endpunkt wird ein Upgrade-Hinweis angezeigt. Die deklarierte Seite des RLS-Editors entspricht dem, was der Server kompiliert hat. Ein JS-Konsolenskript empfängt `context.tables` (zuvor `context.collections`).

**Was zu tun ist:** Aktualisieren Sie die Runtime zusammen mit dem Panel. Siehe [Studio](/docs/studio/).

## 128. Der Agent-Skill `rebase-collections` heißt `rebase-tables`

## 130. `rebase build` verweigert ein Frontend ohne `rebaseBackendGuard()`

**Wen das betrifft:** jedes Projekt mit einem Frontend.

**Was sich geändert hat:** Das Frontend darf `backend/` ausschließlich als Typen importieren. Ein
Wert-Import würde Server-Code – Hooks und alle von ihnen gelesenen Secrets – in das
Browser-Bundle einbinden. `rebaseBackendGuard()` aus `@rebasepro/app/vitePlugin` lässt `vite build` und `vite dev` fehlschlagen, wenn ein Frontend-Modul nach `backend/` auflöst, und benennt Importeur, Import und Datei – unter Berücksichtigung von Aliasen, tsconfig-Pfaden, Package- und absoluter Auflösung, Globs, `?raw`, Re-Exporten und dynamischen Imports. `rebase build` und der Frontend-Build, den `rebase cloud deploy` ausführt, verweigern ein Frontend, dessen Vite-Konfiguration dies nicht nutzt; `rebase dev` gibt eine Warnung aus; `rebase verify` meldet `cms-backend-guard-missing`.

**Was zu tun ist:** Der Codemod fügt dies zur `frontend/vite.config.ts` eines Scaffolds hinzu und gibt die Zeilen für jede andere Konfiguration aus:

```diff ts
+import { rebaseBackendGuard } from "@rebasepro/app/vitePlugin";

 export default defineConfig({
-    plugins: [react()],
+    plugins: [react(), rebaseBackendGuard()],
 });
```

Wandeln Sie anschließend jeden Wert-Import von `backend/` in ein `import type` um.

## 131. Zeilen auf der Leitung folgen ihrer Spalte

**Wen das betrifft:** Clients, die Fremdschlüssel lesen oder Relationen benennen, sowie Schreiboperationen, die generierte Spalten oder unvollständige JSON-Objekte senden.

**Was sich geändert hat:** Werte durchlaufen den Codec ihrer Spalte beim Senden und die Regeln der Spalte beim Empfangen.

- Eine durch eine Relation generierte `bigint`- oder `numeric`-Fremdschlüsselspalte, die Postgres als Text zurückgibt, wird in REST, im SDK und im Admin-Panel als **Zahl** ausgeliefert. Deklarierte Zahlenschlüssel waren dies bereits.
- Die **Elemente eines nativen Arrays werden so ausgeliefert wie ihr skalarer Typ**, in REST, im SDK, im Socket und im Treiber:

  | Spalte | 0.30 lieferte | 0.31 liefert |
  |---|---|---|
  | `timestamptz[]` | `["2026-01-02 11:00:00+01"]` | `["2026-01-02T10:00:00.000Z"]` |
  | `numeric[]` (Treiber ohne die boot-zeitige Numeric-Einstellung geöffnet: Tests, Skripte) | `["1.50", "2.25"]` | `[1.5, 2.25]` |
  | `bigint[]` mit einem Null-Element | `[1, 0, 3]` | `[1, null, 3]` |
  | `date[]`, `timestamptz[]` oder ein Enum-Array mit einem Null-Element | `["2026-01-02", "NULL"]` | `["2026-01-02", null]` |

  `date[]`, `time[]`, `text[]`, `uuid[]`, `boolean[]`, `integer[]` und `double precision[]` werden wie bisher ausgeliefert. Was gespeichert wird, ändert sich nicht: Eine gelesene und wieder gespeicherte Zeile speichert dasselbe Array.
- Eine in `include`, einem Filter oder einem Sort angegebene Relation muss ihren **exakten Namen** tragen. Fallbacks über den Slug und die snake_case-Schreibweise wurden entfernt.
- Eine generierte Spalte wird beim Schreiben abgelehnt und aus dem OpenAPI-Eingabeschema weggelassen.
- Ein Pflichtfeld innerhalb eines JSON-Objekts wird erzwungen; `$inc` und Array-Elemente bei einer Integer-Spalte müssen ganze Zahlen sein.

**Was zu tun ist:** Lesen Sie Fremdschlüssel als Zahlen dort, wo Sie Strings verglichen haben, parsen Sie `timestamptz[]`-Elemente als RFC 3339, behandeln Sie ein Null-Array-Element als `null` und schreiben Sie Relationsnamen exakt so, wie die Tabelle sie deklariert (ihre `relations`-Keys). Hören Sie auf, generierte Spalten beim Schreiben zu übermitteln.

## 132. Die Historie wird als Lesevorgänge ausgeliefert

**Wen das betrifft:** Leser von Verlaufs-Snapshots und alle, die einen `DataDriver` implementieren.

**Was sich geändert hat:** Verlaufseinträge werden als Lesevorgänge ausgeliefert: Feldzugriff zuerst, dann `afterRead` (global, Tabelle, Spalte). Eine durch einen Hook oder ein `.transform({ afterRead })` maskierte Spalte ist in jedem Snapshot maskiert; eine Spalte, die der Aufrufer nicht lesen darf, wird zurückgehalten und aus `changed_fields` weggelassen; Keys entfernter Spalten werden zurückgehalten, und ein Revert schreibt niemals eine Spalte, die der Aufrufer nicht lesen darf. Ein Hook, der bei einem alten Snapshot einen Fehler wirft, lässt die Anfrage fehlschlagen. 0.30 lieferte die gespeicherten Rohwerte aus; ein Projekt mit Verlauf und Maskierungs-Hooks sollte daher zwingend aktualisiert werden.

Ein Eintrag enthält die Zeile so, wie `GET /api/data/<table>/<id>` sie ohne `include` liest: reine Werte, ein `belongsTo` als dessen Fremdschlüssel. Ein Eintrag, den eine ältere Version mit dem View-Model des Admin-Panels aufgezeichnet hat, wird als diese Zeile ausgeliefert und zurückgesetzt: eine `{ "__type": "date", "value" }`-Hülle als Wert, eine `{ "__type": "relation" }`-Referenz einer besitzenden Relation als Fremdschlüssel unter dem Eigennamen des Schlüssels und jede andere Referenz als Schlüssel der verknüpften Zeile. 0.30 lieferte diese Referenzen wie gespeichert aus.

Ein Treiber stellt die Historie über `DataDriver.serveStoredRows(path, rows)` innerhalb der schreibgeschützten Transaktion des Aufrufers bereit; die Verlaufsrouten antworten mit 501 für Treiber ohne diese Methode, sodass die Historie niemals unmaskiert ausgeliefert wird.

**Was zu tun ist:** Für den mitgelieferten Postgres-Treiber ist nichts zu tun. Ein benutzerdefinierter Treiber implementiert `serveStoredRows`. Siehe [Historie](/docs/backend/history/).

## 135. `@rebasepro/types` und `@rebasepro/common` entfernen das Collection-Modell aus ihren Roots

**Wen das betrifft:** Code, der Collection- oder Property-Typen, Admin-Panel-Helper oder den Lift aus `@rebasepro/types` oder `@rebasepro/common` importiert – benutzerdefinierte Felder, benutzerdefinierte Views, Plugins, Tests mit Collection-Fixtures – und benutzerdefinierte Treiber, die die Registry implementieren.

**Was sich geändert hat:** Die Kernel-Pakete beschreiben ausschließlich Tabellen. Was eine Collection beschreibt, wie das Admin-Panel sie darstellt, befindet sich in `@rebasepro/cms-types`:

- **Typen**, die aus `@rebasepro/types` verschoben wurden: `CollectionConfig`, `PostgresCollectionConfig`, `FirebaseCollectionConfig`, `AnyCollectionConfig`, jedes `…Property` (`StringProperty`, `NumberProperty`, `ArrayProperty`, …) und `Properties`, `CollectionCallbacks` und deren Hook-Props, die Relationsarten aus 0.30 und deren `Resolved…`-Formen, `CollectionIndex`, die Chip-Farben (`ColorScheme`, `ColorKey`, …), `FieldAccess`, `EnumValues`.
- **Helper**, die aus `@rebasepro/common` verschoben wurden: die auf Collections ausgerichteten Policy-Helper (`policyToPostgres`, `compileRulePolicies`, `getEffectiveSecurityRules`, `getGeneratedPolicyNames`, …), `CollectionRegistry`, `resolveCollectionRelations`, `resolveRelation`, `getTableName`, `findRelation`, `rowToViewModel`, `resolvePrimaryKeys`, die Feldzugriffssicht einer Eigenschaft (`effectiveAccess`, `canReadField`, `canWriteField`), `evaluateCondition`, `canEditEntity`, `resolveProperty`, `getDefaultValuesFor`, `getSubcollections`, `getCopyValues`, `enumToObjectEntries`. Eine aus einem einfachen Ausdruck kompilierte Regel verwendet `compilePolicyExpression(expr)` aus `@rebasepro/common`.
- **`composeCallbacks`** komponiert die Callbacks einer Collection für das Panel und wurde nach `@rebasepro/cms-types` verschoben; `@rebasepro/server` re-exportiert dies nicht mehr. Backend-Code setzt die Hooks einer Tabelle mit `composeTableHooks` aus `@rebasepro/common` zusammen, und der Codemod listet einen Backend-Import von `composeCallbacks` als manuellen Schritt auf, der darauf hinweist.
- **`defineCollection`** wurde aus `@rebasepro/common` und `@rebasepro/cms-types` entfernt: Deklarieren Sie die Tabelle mit `defineTable` in `backend/schema` und passen Sie sie mit `customizeTable` in `frontend/src/cms` an; eine Firestore-Collection ist `defineFirestoreCollection` aus `@rebasepro/firebase`.
- **Der Accessor des Admin-Panels und seine Typen**: `Entity`, `EntityValues`, `TableAccessor`, `TableTrashAccessor`, `FindResponse`, `QueryBuilderInterface`, `RebaseData` und `AuthState` haben `@rebasepro/types` verlassen; `buildRebaseData`, `wrapAsEntityData`, `buildRoutedRebaseData`, `EntityDataOptions`, `QueryBuilder`, `RelationRef` und `createRelationRef` haben `@rebasepro/common` verlassen. Alle werden nun aus `@rebasepro/cms-types` importiert. Die eigene Datenschicht des SDKs – `buildSdkData`, `createDriverTableRows`, `buildRoutedSdkData` in `@rebasepro/common` – liefert Zeilen direkt aus und gibt zurück, was sie zuvor zurückgegeben hat.
- **`EntityDataOptions.resolveCollection`** wird durch `primaryKeysOf`, `viewModelOf`, `storedValuesOf` und `viewModelSourceOf` ersetzt; `collectionEntityDataOptions(resolveCollection, { resolveDataPath, resolveAccessor })` aus `@rebasepro/cms-types` erstellt diese.
- **Der Migrations-Lift** (`collectionsToTableDefs`, `collectionToTableDef`, `LiftNote`, `LiftResult`, `LiftOptions`) wurde nach `@rebasepro/common/migrate` verschoben, neben eine eingefrorene Kopie des Collection-Modells aus 0.30 (`Legacy…`-Typen) und `defineLegacyCollection`.
- **Ebenfalls aus den Kernel-Roots entfernt** und vom Codemod jeweils als manueller Schritt aufgeführt: die Collection-Patch-API von `@rebasepro/types` (`CollectionPatch`, `CollectionPatchOp`, `applyCollectionPatch`, `collectionPatchProblems`, `isCollectionPatch`, `nestCollectionPatchPaths` → `TablePatch`), dessen Collection-JSON-Helper (`diffCollections`, `diffJsonValues`, `toCollectionJson`, `RUNTIME_ONLY_COLLECTION_KEYS`, `runtimeOnlyKeyIn`), der aus der Mongo-Ära stammende `DocumentAdmin`, die Fähigkeiten `isDocumentAdmin` und `supportsDocumentAdmin` sowie `RebaseProjectContract.collectionSlugs` / `.collections` / `.generatedAt` (`/api/meta/contract` stellt `tables` bereit); aus `@rebasepro/common`: `buildTenantSecurityRule` → `tenantSecurityRule`, `defaultPoliciesDisabled` → `tableDefaultPoliciesDisabled`, `restoresSoftDeletedRow` → `isSoftDeleteRestore`, `softDeleteFieldOf` → `softDeleteColumn`, `getJunctionConfigForRelation` → `resolveTableJunctions`, und `isRelationRequired`, `relationDeclaringProperty`, `requireCallbackCollection` ersatzlos entfernt (lesen Sie den `TableDescriptor`).
- **Die Registry eines Treibers** ist ein `TableRegistryInterface` (zuvor `CollectionRegistryInterface`): `setGlobalHooks?` und `setTableHooks?` ersetzen `getGlobalCallbacks` / `setGlobalCallbacks?`. `globalHooksAsCallbacks`, `resolveDriftCheckName` und `PENDING_TABLE_FEATURES` wurden entfernt.

**Was zu tun ist:** `rebase migrate sdk-calls` (Teil von `collections-to-tables`) verschiebt jeden unten stehenden Import in sein neues Paket – zusammengeführt in einen bereits bestehenden Import dieses Pakets in der Datei, wobei `import type`, Inline-`type` und `as`-Aliase erhalten bleiben – und fügt das Paket zu den Abhängigkeiten des importierenden Workspace-Pakets hinzu; führen Sie danach `pnpm install` aus. Ein Import eines entfernten Namens, ein Namespace-Import (`import * as`), ein `export *`, ein dynamisches `import()` oder ein `require()`, das einen verschobenen Namen verwendet, wird als nummerierter manueller Schritt aufgeführt. Ein Test, der Collection-Literale als Fixtures behält, typisiert diese mit den `Legacy…`-Typen und überführt sie mittels `@rebasepro/common/migrate`.

## 136. Der Postgres-Treiber und die One-Shot-Reads des Sockets liefern die REST-Zeile zurück

**Wen das betrifft:** Funktionen oder Plugins, die über `requireDriver(c)` / `getDriver(c)` lesen, Code, der die Socket-Frames `FETCH_COLLECTION` / `FETCH_ONE` sendet, sowie Code, der `{ __type }`-Objekte aus einer Antwort gelesen hat.

**Was sich geändert hat:** Es gibt nur noch ein einheitliches Leseformat. `fetchCollection` und `fetchOne` auf dem Postgres-Treiber – worüber das `requireDriver(c)` einer Funktion, Plugins, die One-Shot-Frames des Sockets, MCP und der RLS-Simulator lesen – geben zurück, was `GET /api/data/<table>` zurückgibt:

| Wert | 0.30 Treiber-Lesevorgang | 0.31 |
|---|---|---|
| ein Zeitstempel | `{ "__type": "date", "value": … }` | ein RFC-3339-String |
| ein `belongsTo` | `{ "__type": "relation", "id", "path" }` unter dem Namen der Relation | der Fremdschlüssel unter seinem eigenen Key (`authorId`) |
| eine verknüpfte Zeile | jede von `fetchOne` geladene Relation | nur eine von `include` benannte Relation als eigene Zeile des Ziels |
| ein Vektor, ein `bytea` | `{ "__type": "Vector" }`, eine Data-URL | so wie REST sie bereitstellt |

`FetchOneProps` nimmt `include` entgegen (`ListenOneTarget` wurde entfernt: verwenden Sie `FetchOneProps`). `rebase.data`, `context.data` und das SDK gaben dieses Format bereits zurück und bleiben unverändert.

`@rebasepro/client` liest REST-Bodys und Socket-Frames als einfaches JSON: Ein Wert mit einem `__type`-Key wird nicht mehr in ein `Date`, `EntityReference`, `EntityRelation`, `GeoPoint` oder `Vector` umgewandelt, und ein JSON-Dokument, das einen `__type`-Key enthält, wird genau so zurückgegeben, wie es gespeichert ist.

**Was zu tun ist:** Lesen Sie die Plain-Zeile: Parsen Sie Daten aus ihren Strings, lesen Sie einen Fremdschlüssel aus seinem eigenen Key aus und übergeben Sie `include` für jede Relation, die Sie lesen möchten:

```diff ts
-const article = await requireDriver(c).fetchOne({ path: "articles", id });
-const authorId = article?.author.id;      // a { __type: "relation" } ref
+const article = await requireDriver(c).fetchOne({ path: "articles", id, include: ["author"] });
+const authorId = article?.authorId;
```

## 138. Das Backend akzeptiert die von der REST-API dokumentierten Werte und nichts anderes

**Wen das betrifft:** Clients, die eine To-One-Relation als Objekt oder einen Vektor als `{ value }` schreiben, Code, der eine Relation mit einem Objekt filtert, Code, der die Werteklassen des Admins importiert, sowie Offline-Apps mit Schreibvorgängen, die von 0.30 in die Queue gestellt wurden.

**Was sich geändert hat:** Ein Schreibvorgang akzeptiert genau das Format, das ein Lesevorgang zurückgibt – ein einheitliches Schreibformat für REST, den Socket, MCP und das prozessinterne SDK:

| Wert | Akzeptiert | Jetzt abgelehnt |
|---|---|---|
| eine To-One-Relation (`belongsTo`, `hasOne`, ein To-One-`via`) | der Schlüssel der verknüpften Zeile oder `null` (`""` ist `null`), unter dem Namen der Relation oder des Fremdschlüssels | ein Objekt wie `{ "id": 5 }`: `400 VALIDATION_INVALID_VALUE`, „'posts.author' links one 'authors' row: write that row's key (a string or a number), or null to unlink — not an object.“ |
| eine To-Many-Relation (`hasMany`, `manyToMany`, ein beschreibbares To-Many-`via`) | eine Liste von Schlüsseln oder von `{ id, _pivot? }` | — (andere Keys des Objekts werden wie bisher ignoriert) |
| ein Vektor | eine Liste von Zahlen | ein `Vector` oder `{ "value": [...] }`: `400`, „'embedding' expects a vector as a list of numbers“ |
| ein Datum, eine Uhrzeit | ISO-Text (`Date` prozessintern) | — |
| ein Geopoint | `{ latitude, longitude }` | — |
| ein `bytea` | eine `data:application/octet-stream;base64,`-URL (`Buffer` / `Uint8Array` prozessintern) | — |
| ein Filter auf einer Relation | der Schlüssel | ein Objekt wird nicht mehr entpackt: Es wird exakt wie übergeben verglichen |

0.30 akzeptierte eine als Objekt geschriebene To-One-Relation und übernahm stillschweigend deren `id`; dieses Format war nie dokumentiert und entsprach dem View-Model des Admin-Panels. Das Admin-Panel wandelt sein View-Model nun im Browser vor jedem Schreibvorgang und Filter in Übertragungswerte (Wire Values) um.

Die Werteklassen des Admins wurden zusammen mit dem Rest seines View-Models verschoben: `EntityReference`, `EntityRelation`, `GeoPoint`, `Vector` und `EntityReferenceProps` werden aus `@rebasepro/cms-types` importiert (sie haben `@rebasepro/types` verlassen), ebenso wie `normalizeToEntityRelation` (hat `@rebasepro/common` verlassen); `withRelationReferencesOnly` wurde entfernt. Die Historie speichert die Zeile so, wie ein Lesevorgang sie zurückgibt; zuvor aufgezeichnete Einträge werden als einfache Werte ausgeliefert und zurückgesetzt ([Abschnitt 132](#132-die-historie-wird-als-lesevorgänge-ausgeliefert)).

Die Offline-Queue von `@rebasepro/client` speichert Wire Values. Ein durch das 0.30-SDK offline in die Warteschlange gestellter Schreibvorgang wird beim Zurücklesen und erneuten Abspielen konvertiert: Nichts, was vor dem Upgrade in der Warteschlange gelandet ist, geht verloren.

**Was zu tun ist:** Senden Sie den Schlüssel: `{ "author": 5 }`, nicht `{ "author": { "id": 5 } }`; senden Sie einen Vektor als Liste von Zahlen und filtern Sie eine Relation über ihren Schlüssel. `rebase migrate sdk-calls` verschiebt die Importe der Werteklassen ([die Liste](/docs/upgrading/0-30-to-0-31-imports/)). Siehe [Schreibvorgänge](/docs/backend/writes/).

## 139. `/api/docs` wird für die Zielgruppe des Schema-Endpunkts ausgeliefert

**Wen das betrifft:** Personen oder Tools, die `/api/docs` lesen oder `/api/swagger` aufrufen – Swagger UI, API-Client-Generatoren, CI-Schritte.

**Was sich geändert hat:** Wenn `enableSwagger` nicht gesetzt ist (`REBASE_ENABLE_SWAGGER` nicht gesetzt), wird das OpenAPI-Dokument in jeder Umgebung denselben Aufrufern bereitgestellt, für die `GET /api/schema/tables` Tabellen beschreibt, und mit denselben Verweigerungen – 401 für anonyme Aufrufer, sofern nicht `schemaTables.public`, 403 für Credentials ohne Schema- oder Daten-Scope – und jeder Aufrufer erhält das Dokument über exakt die Tabellen, Spalten und Relationen, die dieser Endpunkt für ihn beschreibt (ein Administrator erhält alles). Es gibt keine Swagger-UI. Ein Server ohne konfigurierte Authentifizierung antwortet mit `404 DOCS_UNAVAILABLE`. 0.30 veröffentlichte in der Entwicklungsumgebung das gesamte Dokument, jede bediente Tabelle und nicht-private Spalte für anonyme Aufrufer und hielt es in der Produktion nur für Administratoren zugänglich.

| `enableSwagger` / `REBASE_ENABLE_SWAGGER` | `/api/docs` | `/api/swagger` |
|---|---|---|
| nicht gesetzt (Standard) | jeder Aufrufer, für den der Schema-Endpunkt Tabellen beschreibt: seine Tabellen | wird nicht ausgeliefert |
| `true` | das gesamte Dokument für jeden | wird außerhalb der Produktion ausgeliefert |
| `false` | das gesamte Dokument hinter dem Admin-Gate | wird nicht ausgeliefert |

**Was zu tun ist:** Rufen Sie `/api/docs` im angemeldeten Zustand auf. Um das gesamte Dokument wie unter 0.30 in der Entwicklung öffentlich bereitzustellen, setzen Sie `REBASE_ENABLE_SWAGGER=true` (oder `enableSwagger: true`). Siehe [Endpunkte](/docs/backend/endpoints/).

## 140. Eine Many-to-Many-`pivot`-Spalte darf kein `.transform()` deklarieren

**Wen das betrifft:** ein `rel.manyToMany(…, { pivot: { … } })`, dessen Pivot-Spalte ein `.transform()` besitzt.

**Was sich geändert hat:** Der Compiler verweigert dies („the pivot column "x" declares `.transform()` …“). Die Transformation einer Pivot-Spalte wurde an keiner Stelle ausgeführt, sodass ein Wert, den Sie maskieren wollten, unmaskiert so wie gespeichert ausgeliefert wurde.

**Was zu tun ist:** Entfernen Sie das `.transform()` und maskieren Sie `_pivot` im `hooks.afterRead` der Zieltabelle. Siehe [Relationen](/docs/collections/relations/).

## 141. Eine Verknüpfung ist exakt so lesbar und beschreibbar wie ihre Schlüsselspalte

**Wen das betrifft:** Clients, die ein `belongsTo` über seinen Relationsnamen schreiben, eine Relation lesen oder filtern, deren Schlüsselspalte eingeschränkt ist, oder sich auf `strictWrites: false` verlassen.

**Was sich geändert hat:** Eine Einschränkung einer Schlüsselspalte gilt gleichermaßen für jede Schreibweise, die sie liest oder beschreibt.

- Das Schreiben einer Verknüpfung über ihren Relationsnamen (`{ "reviewer": 7 }`) unterliegt jeder Regel der Schlüsselspalte, die sie setzt – `.readOnly()`, `.private()`, `access.write`, Erstellungszeitstempel, Tenant-Spalte, Schlüssel-Unveränderlichkeit – über REST, Bulk, `_batch`, den Socket und MCP. Das Schreiben der Verknüpfung unter beiden Namen (`{ "reviewer": 7, "reviewerId": 8 }`) mit unterschiedlichen Werten führt zu einem 400 `VALIDATION_INVALID_VALUE`. Das Verschieben einer Zeile zu einem anderen Tenant über ihre Verknüpfung antwortet mit 400 `TENANT_IMMUTABLE` (zuvor ein 500).
- Eine Relation ist nur dann lesbar, wenn der Aufrufer jede Spalte lesen darf, die ihr Join liest, und zwar auf jeder Tabelle, die er durchläuft: der Schlüssel eines `belongsTo`, der Fremdschlüssel des Ziels bei einem `hasMany` / `hasOne`, jede Spalte, über die die Schritte eines `via` joinen. Eine Relation, bei der dies fehlschlägt, wird aus `include` und `_count` weggelassen, und ein Filter, Sort oder Relationspfad über sie antwortet mit `FIELD_NOT_READABLE` (bzw. unbekannte Relation, wenn die Spalte `.private()` ist). Ein To-One-`via`-Schreibvorgang, der eine Spalte kopieren würde, die der Aufrufer nicht lesen darf, wird mit `FIELD_NOT_READABLE` abgelehnt. Die inversen und `via`-Fälle waren auch in 0.30.x offen.
- Eine Verknüpfung, deren Schlüsselspalte der Aufrufer nicht lesen darf, wird aus `include` weggelassen, und ein Filter, Sort, `fields`-Eintrag oder Relationspfad über sie antwortet mit `FIELD_NOT_READABLE`; eine an einen `.private()`-Schlüssel gebundene Verknüpfung gilt als unbekannte Relation. `GET /api/schema/tables`, OpenAPI und MCP `describe_table` beschreiben eine Verknüpfung und ihren Schlüssel zusammen, sodass eine Schlüsselspalte, deren Verknüpfung gesperrt ist, auch dort zurückgehalten wird.
- `strictWrites: false` entscheidet über genau eine Sache: Ein nicht deklarierter Key wird an den Treiber weitergeleitet (geschrieben, wenn die Datenbank die Spalte besitzt, andernfalls 400 `VALIDATION_UNKNOWN_FIELDS`). Es hebt niemals die Beschränkungen einer deklarierten Spalte, eines Stamps, des Tenants, des Schlüssels, eines Relationsziels oder einer `_pivot`-Regel auf.

**Was zu tun ist:** Schreiben Sie eine Verknüpfung über genau einen Namen oder über beide mit demselben Wert; lesen Sie eingeschränkte Verknüpfungen mit einer Rolle, die deren Schlüssel lesen darf. Siehe [Feldzugriff](/docs/collections/field-access/).
