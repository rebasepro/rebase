# Upgrade von 0.30 → 0.31

<span class="since-badge" data-since="0.31">Seit 0.31</span>

0.31 macht das Backend Postgres-first. Die Tabellen, die Sie mit `defineTable` in `backend/schema/` deklarieren, sind das Einzige, was das Backend über Ihre Daten weiß; was das Admin-Panel darüber hinaus anzeigt, befindet sich im Frontend. Fast jeder unten stehende Eintrag ist eine Konsequenz dieser Trennung, und fast alles davon wird durch einen einzigen Befehl für Sie erledigt.

### Die Checkliste, pro Projekt

1. **Aktualisieren Sie zuerst jedes `@rebasepro`-Paket** in jedem Workspace-Paket, damit die Typen, die der Codemod liest, denen von 0.31 entsprechen: `pnpm -r up "@rebasepro/*@0.31.0"`, dann `pnpm install`. Ein Projekt auf einem Release vor 0.30 wendet zuerst die Codeänderungen der dazwischenliegenden Anleitungen an ([Upgrade](/docs/upgrading/)) und erfüllt die Toolchain-Mindestanforderungen von 0.31 – Node 22.22, TypeScript 6, React 19.2.7, React Router 8, Vite 8 ([die Liste](/docs/upgrading/0-30-to-0-31-by-hand/#a-project-on-a-release-before-030)): Der Codemod lädt eine 0.20–0.29 `config/` und seine SQL-Prüfung ist erfolgreich, aber diese Prüfung vergleicht den 0.31-Compiler mit sich selbst – erst Schritt 7, gegenüber Ihrer Datenbank, beweist, dass das generierte DDL dem entspricht, was Ihre Datenbank enthält.
2. **Commiten Sie, und führen Sie den Codemod dann als Testlauf aus:** `rebase migrate collections-to-tables --dry-run`. Er gibt die Dateien aus, die er schreiben würde, was er ablehnt (mit Datei und Zeile), die Hinweise und die manuellen Schritte, und schreibt nichts. Beheben Sie zuerst das, was er ablehnt, in `config/`.
3. **Führen Sie ihn tatsächlich aus:** `rebase migrate collections-to-tables`. Er schreibt `backend/schema/`, `frontend/src/cms/` (mit `ui-config.json`), die `backend/`-Module und die Projektdateien, fügt `rebaseBackendGuard()` zur `vite.config.ts` des Scaffolds hinzu, schreibt Ihre SDK-Aufrufe um, verschiebt die Imports von Namen, die 0.31 in ein anderes Paket verschoben hat ([Abschnitt 135](#135-rebaseprotypes-and-rebaseprocommon-drop-the-collection-model-from-their-roots)), und beweist, dass das generierte SQL byte-identisch ist – oder stellt jede Datei wieder her. Siehe [Abschnitt 108](#108-tables-in-backendschema-replace-configcollections--run-the-codemod-first).
4. **Lesen Sie den letzten Abschnitt seiner Ausgabe, „Review before deploying: these rules change meaning“**, und entscheiden Sie über jede dort aufgeführte Regel ([unten](#vor-dem-deployment-prüfen-diese-regeln-ändern-ihre-bedeutung)).
5. **Führen Sie die manuellen Schritte, die ausgegeben werden, der Reihe nach aus.** Jeder nennt seine Datei, und die meisten enthalten das zu schreibende Snippet: den `<RebaseCMS>`-Mount mit `tableCustomizations` und `uiConfig`, wenn Ihre `App.tsx` nicht die des Scaffolds ist (oder das Panel in einem anderen Modul gemountet ist, das der Schritt benennt), `rebaseBackendGuard()`, wenn Ihre `vite.config.ts` nicht die des Scaffolds ist, sowie in jeder anderen statischen App aus `rebase.json` ([Abschnitt 130](#130-rebase-build-refuses-a-frontend-without-rebasebackendguard)), globale Hooks, einen Import eines Namens, den 0.31 entfernt hat ([Abschnitt 135](#135-rebaseprotypes-and-rebaseprocommon-drop-the-collection-model-from-their-roots)), und `rebase skills install`, wenn das Projekt Agent Skills enthält ([Abschnitt 128](#128-the-agent-skill-rebase-collections-is-rebase-tables)). Führen Sie `pnpm install` aus, wenn die Ausgabe „Dependencies added“ auflistet. Lesen Sie dann zwei Listen im SDK-Teil der Ausgabe:
   - **„Rewritten by name — review“**: `.collection(`-Aufrufe auf einem Empfänger ohne Typ (`any`), umgeschrieben, weil der Empfänger `dataAsAdmin` heißt oder `.data` mit einem literalen Tabellennamen ist; das `collection`-Member eines Typs, den ein `data`- / `dataAsAdmin`-Slot hält; und Test-Doubles. Überprüfen Sie bei jedem, ob es sich um das SDK handelt.
   - **„Left unchanged — check each“**: `.collection(`-Aufrufe, bei denen der Codemod nicht nachweisen konnte, dass es sich um das SDK handelt, wie etwa ein Aufruf über einen Typ, den Ihr Projekt selbst deklariert. Ein hier verbliebener Aufruf, der tatsächlich das SDK *ist*, schlägt unter 0.31 zur Laufzeit fehl: Benennen Sie ihn manuell in `.table(` um. Code, der prüft, ob `collection` existiert (`typeof data.collection === "function"`), ist ein manueller Schritt: Unter 0.31 wird stillschweigend der andere Zweig genommen.

   Eine Datei, die als Build-Output (ein gebündeltes oder minifiziertes `.js`) committet wurde, wird niemals bearbeitet: Sie wird aufgelistet; bauen Sie sie daher nach der Migration neu und ersetzen Sie eine vendorte Kopie des Clients durch den 0.31-Build. Wiederholte Schritte derselben Art werden einmal ausgegeben und listen jede betroffene Datei und Zeile auf; `--json` gibt jeden Schritt separat aus. Lesen Sie dann [Was Projekte manuell geändert haben](/docs/upgrading/0-30-to-0-31-by-hand/): die Anpassungen, die reale Projekte nach diesen Schritten noch vorgenommen haben.
6. **`rebase generate-sdk`** — die Namen des generierten Moduls haben sich geändert ([Abschnitt 115](#115-the-sdk-addresses-a-table-datatableslug)).
7. **Gegenüber Ihrer Datenbank**: Führen Sie `rebase db push --dry-run` aus und erwarten Sie „No changes: the database already matches these tables.“, dann `rebase doctor --policies` und erwarten Sie keinen Policy-Drift. Die SQL-Prüfung des Codemods beweist, dass die Konvertierung getreu erfolgt ist; diese beiden prüfen es gegenüber der echten Datenbank, und jeder Policy-Unterschied, den einer von beiden auflistet, ist eine Änderung daran, wer worauf zugreifen kann.
8. **`rebase verify`** — liest nun auch `frontend/src/cms`: eine Anpassung, die eine nicht existierende Tabelle oder ein nicht existierendes Feld benennt, eine erforderliche Spalte, die vom Formular ausgeschlossen wurde, ein fehlender `rebaseBackendGuard()`, ein nicht an `<RebaseCMS>` übergebenes `ui-config.json`.
9. **Führen Sie die vom Codemod ausgegebene `git rm`-Zeile aus**, sobald das Diff überprüft wurde: `git rm -r config/collections …` und die Verdrahtung, die nach `backend/` verschoben wurde, oder `git rm -r config`, wenn dort nichts Eigenes mehr übrig ist ([Abschnitt 109](#109-there-is-no-config-package)).
10. **Neu bauen und deployen.** Ein vor 0.31 erstelltes Bundle startet nicht auf einer 0.31-Runtime ([Abschnitt 112](#112-bundle-format-3-format-2-bundles-are-refused)). Der erste Start stempelt die Schema-Version der Datenbank einmalig neu ab ([Abschnitt 113](#113-the-schema-version-is-computed-from-tables-v2)).

Führen Sie `rebase migrate collections-to-tables --check` in CI aus, bis `config/` entfernt ist: Es verifiziert, dass die migrierten Tabellen immer noch dasselbe SQL rendern wie die Collections, von denen sie stammten, und beendet mit Exit-Code 1, solange eine unter „Review before deploying“ aufgelistete Regel nicht bestätigt wurde – übergeben Sie `--accept-rule-changes`, sobald Sie diese überprüft haben.

### Vor dem Deployment prüfen: Diese Regeln ändern ihre Bedeutung

Der Codemod übernimmt jede Sicherheitsregel unverändert, und jede behält ihren Policy-Namen. Aber der 0.30-Compiler las nur das erste Vorkommen von `condition`, `using`, `access: "public"` und `ownerField` und kannte keinen anderen `access`-Wert, sodass vier Regelformen nun etwas anderes gewähren. Zwei davon erweitern den Zugriff:

| Die Regel | 0.30 gewährte | 0.31 gewährt | |
|---|---|---|---|
| ein reines `access: "authenticated"` (keine `roles`) | nichts | jedem angemeldeten Aufrufer, Gäste eingeschlossen | **erweitert** |
| `access` + `check`, kein `condition`, bei `select` / `update` / `delete` / `all` | keine bestehende Zeile | jede bestehende Zeile für die `access`-Aufrufer | **erweitert** |
| `access: "authenticated"` + `condition` | jedem, der `condition` erfüllt | nur angemeldeten Aufrufern, die dies erfüllen | schränkt ein |
| `access: "authenticated"` + `check`, bei `insert` | jedem, der eine passende Zeile einfügt | nur angemeldeten Aufrufern | schränkt ein |

Am häufigsten tritt die erste auf. Schreiben Sie `access: "registered"`, um nur Aufrufer mit einem Konto (keine anonymen Gäste) zuzulassen, oder entfernen Sie die Regel, um weiterhin nichts zu gewähren. `access` mit `roles` und ein Plain-Object-`condition` bedeuten dasselbe wie zuvor und werden nicht aufgeführt.

Der Codemod lehnt außerdem eine Regel ab, die der 0.31-Compiler ablehnt: eine Regel, die Klauseln kombiniert, die der Typ `SecurityRule` ausschließt (`access` neben `ownerField`, `using` oder `withCheck`; `ownerField` neben `using`, `withCheck`, `condition` oder `check`; `condition` oder `check` neben `using` oder `withCheck`), sowie eine mit einem ungültigen Wert für `access`, `mode`, `operation(s)` oder `roles` – ein falsch geschriebenes `"restrictive"` wurde früher fälschlicherweise als permissiv kompiliert. Siehe [Sicherheitsregeln](/docs/collections/security-rules/).

### Was sich sonst noch anders verhält

- **Was `GET /api/schema/tables` einer Person mitteilt.** Administratoren und Inhaber von `schema:read` erhalten jede Tabelle. Jede andere angemeldete Person, Gäste eingeschlossen, erhält nur die Tabellen, die ihre Rollen erreichen können, und nur mit den Regeln, die auf sie zutreffen können; Relationen zu anderen Tabellen werden verworfen und Hook-Flags vorenthalten. Ein Frontend, das die Beschreibung einer anderen Tabelle als regulärer Benutzer gelesen hat, erhält weniger; `schemaTables: { persons: "all" }` in den Backend-Optionen stellt die vollständige Beschreibung wieder her. Siehe [Endpunkte](/docs/backend/endpoints/#schema).
- **Relationsnamen sind exakt**, und **Big-Integer-Fremdschlüssel sind Zahlen** ([Abschnitt 131](#131-rows-on-the-wire-follow-their-column)).
- **Die Historie wird maskiert ausgeliefert** ([Abschnitt 132](#132-history-is-served-as-reads)).
- **MCP-Tool-Namen und das View-Payload** ändern sich gemeinsam für den gehosteten Connector und die Runtimes, die er erreicht ([Abschnitt 122](#122-mcp-tools-are-named-for-tables)).
- **Gezielt eingeschränkt.** Audit-Stamps (`.onCreateNow()`- / `.onUpdateNow()`-Spalten) werden standardmäßig aus den Listenspalten des Panels ausgeblendet: Eine migrierte Liste, die `created_at` angezeigt hat, verliert diese Spalte, bis Sie `fields: { created_at: { hidden: false } }` in deren `customizeTable` eintragen. Der Codemod lehnt unter Angabe des Grundes Tuple-JSON-Arrays, ein `vector` / `binary` / `reference` innerhalb einer Map, `databaseId` auf einer Postgres-Collection, `isId: "cuid"`, eine alleinige `isId`-Relation und `disableDefaultPolicies: true` ohne Regeln ab. Eine einspaltige Relation zu einer Tabelle mit zusammengesetztem Primärschlüssel wird abgelehnt (schreiben Sie diese mit `rel.via()`). OpenAPI-Tags stammen aus dem Slug, nicht aus dem Anzeigenamen. `rebase schema introspect` lässt Tabellen ohne Primärschlüssel aus und gibt den Grund an (ein Server, der die Datenbank introspektiert, bedient sie weiterhin). Eine einfache View, die `roles` deklariert, ist ein Kompilierungsfehler; der Codemod entfernt sie mit einem Hinweis.
- **Was reale Projekte dennoch manuell geändert haben** – Toolchain-Mindestanforderungen, `({ entity })` in Admin-Code, Includes einer umbenannten Relation, zur Laufzeit geänderte Collection-Objekte, SDK-Aufrufe auf untypisierten Empfängern: [Was Projekte manuell geändert haben](/docs/upgrading/0-30-to-0-31-by-hand/).
- **Wiederherstellung auf einem anderen Cluster.** Der Stempel der Standard-Admin-Policies hasht Rollen-OIDs; nach einem Dump oder Point-in-Time-Restore auf einem anderen Cluster erstellt der erste `db push` oder Boot diese Policies einmalig neu – mit denselben Namen und demselben SQL.

### Die Begriffe

| Vorher | Jetzt | Wo „Collection“ bleibt |
|---|---|---|
| eine Collection in `config/collections/` | eine **Tabelle** in `backend/schema/` (`defineTable`) | — |
| `properties` | `columns` (`col.*`) und `relations` (`rel.*`) | — |
| `securityRules`, `defaultSecurityRules` | `rls` (erforderlich), `defaultRls` | — |
| `callbacks`, `Property.callbacks` | `hooks`, das `.transform()` einer Spalte | — |
| der `admin`-Block | `customizeTable` in `frontend/src/cms/` | — |
| `data.collection(slug)` | `data.table(slug)` | — |
| was das Admin-Panel darstellt | eine **Collection**: eine Tabelle, wie das Panel sie anzeigt, oder eine Firestore-Collection | das CMS: `CollectionPanel`, der Collection Editor, `externalCollections` |

## 108. Tables in `backend/schema` replace `config/collections` — run the codemod first

**Wen dies betrifft:** jedes Projekt mit einem `config/collections/`-Verzeichnis.

**Was sich geändert hat:** Das Backend liest nur `backend/schema/index.ts` und die von dort exportierten Ergebnisse von `defineTable`, `defineAuthTable` und `defineView`. `defineCollection`-Dateien werden von nichts mehr gelesen: Die Runtime, jeder CLI-Befehl und die Validierung von `rebase.json` verweigern ein Projekt, das immer noch `config/collections` enthält, und nennen dabei den unten stehenden Befehl. `rls` ist für jede Tabelle erforderlich – eine Liste von Regeln, `"admin-only"` oder `"inherit"` für das vom Index exportierte `defaultRls` – und `disableDefaultPolicies` heißt nun `defaultPolicies: false`.

**Was zu tun ist:**

```bash
rebase migrate collections-to-tables            # or --dry-run first
```

Er schreibt eine Tabelle pro Collection, jede physische Spalte explizit an ihrer ursprünglichen Position (sodass die Schlüsselspalte eines `belongsTo` ausgeschrieben wird), den Index mit `defaultRls` aus `defaultSecurityRules`, ein `customizeTable` für jede Collection, deren Darstellung nicht dem Standard entsprach, und `defineFirestoreCollection`-Dateien für Firestore-Collections. Die Callbacks einer Collection werden zu den `hooks` ihrer Tabelle und den `.transform()`s ihrer Spalten; die von `config/index.ts` exportierten globalen `callbacks` sind ein manueller Schritt (Abschnitt 109). Anschließend liest er das Ergebnis durch die neue Pipeline zurück: DDL, Policies, Search, Vector, Trigger, Views und das Drizzle-Schema müssen byte-identisch mit dem sein, was die Collections generiert haben, andernfalls wird jede Datei zurückgesetzt und der Lauf bricht mit Exit-Code 1 und dem Diff ab.

Er übernimmt auch das, was früher manuelle Arbeit erforderte:

- **Callbacks, die von einem Helper erstellt wurden** (`callbacks: softDeleteCallbacks(...)` oder ein importiertes Callbacks-Objekt), werden zu `hooks:` mit demselben Ausdruck, und die Funktionen des Helpers werden dort, wo sie geschrieben sind, in Tabellen-Hook-Props konvertiert (der Codemod folgt relativen Imports, `const`-Deklarationen, Property-Zugriffen und einem einzelnen `return`). Wenn er dem Helper nicht folgen kann, nennt ein Schritt die zu überprüfenden Hooks.
- **Eine Funktion `storagePath`** migriert in zwei Hälften: Die Funktion wird zum `storage.path` der Anpassung, sodass das Panel weiterhin bestimmt, wohin ein Upload gelangt, und das `path`-Template der Spalte entspricht der Form der Keys, die sie zurückgibt – dem statischen Text ihres Template-Literals mit jedem `${…}` als `{path}` (`` `${owner}/cv` `` → `{path}/cv`). Der Server wendet nun `maxBytes` und `accept` der Spalte auf jeden Upload an, dessen Key diesem Template entspricht, nicht nur auf solche, die die Spalte benennen; die Limits sind daher strenger als unter 0.30. Eine Funktion, deren Ergebnis keinen statischen Text enthält, wird abgelehnt: Geben Sie ihr zuerst einen statischen Text.
- **Ein 0.30 `policy.existsIn({ collection })`** behält seine Tabelle, und `auth: { collection: usersCollection }` in einem benutzerdefinierten Backend-Eintrag wird entfernt (die `defineAuthTable` ist die Auth-Tabelle). Eine `collections`-Boot-Option wird zu `schemaDir`.
- **Ein `dynamicProps`-Builder** gibt unter 0.31 eine Feldanpassung mit flachen Keys zurück (`{ readOnly: true }`, nicht `{ admin: { readOnly: true } }`). Der Codemod schreibt einen Builder um, dessen Rückgaben Objektliterale sind (inline oder in einem gemeinsam genutzten Modul), und listet alle anderen auf.
- **Darstellung, die über ein einzelnes geteiltes Objekt per Spread hineingebracht wurde**, wird in die Anpassung übernommen (`….dynamicProps`); Darstellung, die eine Wrapper-Funktion berechnet, ist ein zu überprüfender Schritt, keine Ablehnung des Projekts. Ein Komponentenpfad wird relativ zu dem Modul aufgelöst, das ihn geschrieben hat, und ein Wert, der beim Laden von `config/` berechnet wird (`new Date()`, `Date.now()`, ein Lesen von Umgebungsvariablen), wird als sein Ausdruck übernommen und niemals auf den Wert des Migrationslaufs eingefroren.
- **Firestore-Collections, die von einer Funktion erzeugt werden** (ein `getAllFirestoreCollections()`, das die App in das Panel einbindet), werden einzeln in `defineFirestoreCollection` konvertiert, sofern die Datei einer Collection ihr Literal enthält; ein Schritt pro Builder nennt den Rest und die zu schreibende Form, und ein weiterer nennt eine Referenz, die außerhalb eines konvertierten Literals geschrieben wurde und immer noch `path` lauten würde.
- **Imports von `config/` über einen Pfad-Alias** (ein tsconfig-`paths`-Eintrag, ein Vite-`resolve.alias`) werden wie relative Imports umgeschrieben oder aufgelistet, und ein `storageAuthorize`, das `config/index.ts` re-exportiert, wird nach `backend/storage.ts` übertragen.
- **Eine in `<key>Relation` umbenannte Relation** behält ihr Label, ihre Listenspalte und ihren Titel: Die Anpassung nennt den neuen Key. Code, der sie per Include einbindet, folgt dem nicht automatisch ([was zu ändern ist](/docs/upgrading/0-30-to-0-31-by-hand/#a-belongsto-key-is-a-column-and-a-relation-can-be-renamed)).

Was nicht exakt übertragen werden kann, wird unter Angabe von Datei und Zeile abgelehnt, und es wird nichts geschrieben: eine Collection, die durch den Aufruf einer Funktion erstellt wurde, ein Spread oder Accessor, den er nicht durchschauen kann, eine andere Engine als Postgres oder Firestore, eine Ausgabedatei, die bereits mit anderem Inhalt existiert (beiseite verschieben oder `--force`). Ein unsauberer Git-Tree oder ein Projekt außerhalb von Git wird ebenfalls abgelehnt, sodass die Migration ein einziges, überprüfbares Diff darstellt. `--json` gibt den vollständigen Bericht für ein Skript oder einen Agenten aus. Siehe [`rebase migrate`](/docs/cli/schema/#rebase-migrate) und [Tabellen](/docs/schema/).

Die geschriebenen Tabellen formulieren ihre Spalten so, wie es `pg-core` von Drizzle tut – `col.varchar({ length: 160 })`, `col.timestamp({ withTimezone: true })`, `col.text().array()`, `pgEnum(...)`, `` .default(sql`…`) ``, `.generatedByDefaultAsIdentity()` – sodass die Ausgabe nichts weiter benötigt; siehe [Spalten](/docs/schema/columns/). Eine Tabelle, die manuell gegen ein 0.31-Pre-Release in den früheren Schreibweisen verfasst wurde (`col.timestamptz()`, `col.varchar(160)`, `col.array(col.text())`, `col.enum(values, { name })`, `.defaultSql()`, `.identity()`, `.column("…")`), kompiliert nicht mehr: `tooling/scripts/drizzle-sweep.mts` im Rebase-Repository konvertiert sie, indem es nur die Builder-Chains umschreibt, und weist mit `--verify` nach, dass jede konvertierte Tabelle zum selben Deskriptor kompiliert (`npx tsx drizzle-sweep.mts --verify backend/schema`).

Der anschließende `sdk-calls`-Durchlauf schreibt auch Regelquellen um: `existsIn({ collection })` und `membership: { collection }` werden zu `table` (Abschnitt 123); `--skip-sdk-calls` überspringt auch das. Was für Sie übrig bleibt, wird als nummerierte manuelle Schritte ausgegeben, und wenn das Projekt installierte Agent Skills enthält, ist der letzte Schritt die Zeile `rebase skills install`, die diese aktualisiert (Abschnitt 128). Ein einfacher Aufruf von `rebase migrate` gibt die Hilfe für beide Unterbefehle aus.

## 109. There is no config package

**Wen dies betrifft:** jedes Projekt – `config/` war ein eigener Workspace.

0.31 hört auf, `config/collections` zu lesen; es verbietet `config/` nicht. Der Codemod entfernt das, was Rebase gelesen hat – die Collection-Dateien und die Verdrahtung, die er nach `backend/` verschiebt (`resources.ts`, `storage.ts`, `generated/register.ts` und die Re-Exporte davon in `config/index.ts`) – und belässt Ihre eigenen Module in `config/` an Ort und Stelle, weiterhin importierbar wie zuvor: `config/` bleibt ein Workspace-Paket und das Backend kompiliert weiterhin `../config/**/*`. Nur Imports von Dingen, die entfallen, werden umgeschrieben: Eine von Backend-Code importierte Collection-Datei verweist auf das Tabellenmodul (ein Schritt listet Verwendungen auf, die sie als Objekt lesen); wird sie von Frontend-Code importiert, wird sie zu einem Type-Import der Tabelle, sofern sie nur als Typ verwendet wird, oder zu einem Schritt, der die Anpassung benennt; ein Helper innerhalb von `config/collections` wird neben den Code kopiert, der ihn benötigt.

**Was sich geändert hat:** Was sich neben den Collections befand, wandert nach `backend/`:

| Vorher | Jetzt |
|---|---|
| `config/resources.ts` | `backend/resources.ts` |
| `config/storage.ts`, `storageAuthorize` aus `config/index.ts` | `backend/storage.ts` |
| `callbacks`, exportiert aus `config/index.ts` | `hooks`, exportiert aus `backend/hooks.ts` (`TableHooks`: `table` statt `collection`, `values` statt `row`) |
| `config/generated/register.ts` | `backend/generated/register.ts` |
| `rebase.json` `config`, `usersCollection` | `tables` (Standard `backend/schema`); die Auth-Tabelle ist diejenige, die mit `defineAuthTable` deklariert wurde |

Die Runtime liest `storageAuthorize` und `hooks` und nichts anderes aus diesen Modulen; jeder andere Export wird beim Booten gemeldet. Das Frontend importiert `backend/**` ausschließlich als Typen – `pnpm check:frontend-backend-imports` lehnt einen Value-Import ab, der Server-Code an den Browser ausliefern würde.

**Was zu tun ist:** Der Codemod verschiebt `resources.ts`, `storage.ts` und die Registrierung und schreibt `rebase.json`, `package.json`, `pnpm-workspace.yaml` und `backend/tsconfig.json` um. Die globalen `callbacks` sind ein manueller Schritt, den er ausgibt: Verschieben Sie sie manuell nach `backend/hooks.ts` und fügen Sie `hooks.ts` zum `include` von `backend/tsconfig.json` hinzu, damit `tsc` dies überprüft. Führen Sie dann die ausgegebene `git rm`-Zeile aus: `git rm -r config/collections …` oder `git rm -r config`, wenn nichts Eigenes mehr übrig ist.

## 110. Boot options and hooks name tables

**Wen dies betrifft:** ein Backend, das Sie selbst booten (`initializeRebaseBackend`, `createRebaseBackend`), und Code, der Hooks nach dem Booten anhängt.

**Was sich geändert hat:**

| Vorher | Jetzt |
|---|---|
| `collections`, `collectionsDir` | `tables`, `defaultRls`, `schemaDir` |
| `callbacks` | `hooks` |
| `auth.collection` | entfallen: das `defineAuthTable` in `tables` |
| `backend.setCollectionCallbacks(slug, cb)` | `backend.setTableHooks(slug, hooks)` |
| Hook-Props `collection`, `row` | `table` (der Deskriptor), `values` |
| `composeCallbacks` | `composeTableHooks` aus `@rebasepro/common` |
| `openRebase({ collections, callbacks })` | `openRebase({ tables, hooks })`, `tables` aus `compileSchema([...])` |
| `OpenedRebase.collections`; die `rebase console`-Variable `collections` | `.tables`; `tables` |

```diff ts
-await initializeRebaseBackend({ app, server, collectionsDir: "./config/collections", callbacks });
+await initializeRebaseBackend({ app, server, schemaDir: path.resolve(__dirname, "../schema"), hooks });
```

Hooks, die an ein an einer Aufrufstelle übergebenes Collection-Objekt angehängt wurden, werden nicht mehr ausgeführt: Der Treiber führt die Hooks der Tabellen aus, die er bedient; hängen Sie sie daher mit `setTableHooks` an.

**Was zu tun ist:** `rebase migrate sdk-calls` schreibt `setCollectionCallbacks` um, passt die Hook-Props an und listet jedes Backend-Optionsobjekt auf, das manuell aktualisiert werden muss. Ein Skript, das die Daten öffnet, kompiliert seine Tabellen:

```diff ts
-const rebase = await openRebase({ databaseUrl, collections, callbacks });
+const rebase = await openRebase({ databaseUrl, tables: compileSchema([products, orders]), hooks });
```

Siehe [Skripte](/docs/backend/scripts/#openrebase). Siehe [Backend-Übersicht](/docs/backend/) und [Globale Hooks](/docs/backend/hooks/).

## 111. The admin panel renders the tables the server serves

**Wen dies betrifft:** jedes Frontend, das `<RebaseCMS>` mountet.

**Was sich geändert hat:** `<RebaseCMS collections>` ist entfallen. Das Panel zeigt jede Tabelle an, die das Backend unter `GET /api/schema/tables` bereitstellt, ohne Datei pro Tabelle, gefolgt von `externalCollections` (Firestore). `tableCustomizations` nimmt die `customizeTable`-Objekte aus `frontend/src/cms/` entgegen. Das Vite-Collections-Plugin und `virtual:rebase-collections` wurden entfernt. `CollectionsProvider` nimmt dieselben drei Eingaben entgegen (`tableCustomizations`, `externalCollections`, `tables`).

```diff tsx
-import { collections } from "virtual:rebase-collections";
-<RebaseCMS collections={collections}/>
+import { postsCms } from "./cms/posts";
+<RebaseCMS tableCustomizations={[postsCms]}/>
```

**Was zu tun ist:** Der Codemod schreibt `frontend/src/cms/index.ts`, welches `tableCustomizations` (und `externalCollections`) exportiert, und mountet es selbst in der `App.tsx` eines Scaffolds; eine `App.tsx`, die er nicht erkennt, das Plugin in `vite.config.ts` und die virtuelle Moduldeklaration sind manuelle Schritte, die er ausgibt. Siehe [Anpassen einer Tabelle](/docs/frontend/customize-table/).

## 112. Bundle format 3; format-2 bundles are refused

**Wen dies betrifft:** jedes Deployment eines gebauten Bundles – selbst gehostet mit dem Runtime-Image oder auf Rebase Cloud.

**Was sich geändert hat:** Das Schema eines Bundles ist `entry.tables` neben `entry.resources`, `entry.storage` und `entry.hooks`; `bundleFormat` ist 3 und der Runtime-Contract 2. Ein Bundle im Format 1 oder 2 enthält `config/collections`, wofür eine 0.31-Runtime keine Lesemöglichkeit mehr hat. Daher verweigert sie den Start mit dem Codemod in der Fehlermeldung, anstatt die Datenbank zu introspektieren und eine abweichende API bereitzustellen.

**Was zu tun ist:** Migrieren Sie den Quellcode, führen Sie dann `rebase build` aus und deployen Sie. Auf Rebase Cloud führt das Deployment des migrierten Repositorys zu einem Rebuild. Siehe [Runtime und Bundles](/docs/architecture/runtime-and-bundles/).

## 113. The schema version is computed from tables (`v2:`)

**Wen dies betrifft:** jede Datenbank, die von einer Runtime vor 0.31 provisioniert wurde, und jedes generierte SDK.

**Was sich geändert hat:** Die Schema-Version hasht die kompilierten Tabellendeskriptoren und beginnt mit `v2:`. Eine mit `v1:` gestempelte Datenbank meldet die Modelländerung einmalig – das Boot-Log und `rebase doctor` weisen darauf hin und erklären, wie neu gestempelt wird – und jedes generierte SDK wird einmalig als veraltet gemeldet.

**Was zu tun ist:** Provisionieren Sie einmalig mit der neuen Runtime: Starten Sie den Prozess, der das Schema besitzt, oder führen Sie `rebase db push` aus. Bei gesetztem `REBASE_REQUIRE_SCHEMA_MATCH=true` stempeln Sie vor dem Rollout der anderen Prozesse neu ab. Generieren Sie das SDK neu.

**Was sich geändert hat:**

| Vorher | Jetzt |
|---|---|
| `NO_COLLECTIONS` (404) | `NO_TABLES` |
| `COLLECTION_READ_ONLY` (405) | `TABLE_READ_ONLY` |

## 115. The SDK addresses a table: `data.table(slug)`

**Wen dies betrifft:** jeden Client, jede Funktion, jeden Cron, jeden Hook und jedes Skript, das eine Tabelle über ihren Slug anspricht oder das generierte Wörterbuch übergibt.

**Was sich geändert hat:**

| Vorher | Jetzt |
|---|---|
| `data.collection(slug)` | `data.table(slug)` |
| `createRebaseClient({ collections: collectionsDictionary })` | `createRebaseClient({ tables: tablesDictionary })` |
| generiertes `CollectionName`, `CollectionsDictionary` | `TableName`, `TablesDictionary` |
| Batch `{ op, collection }` (SDK und `POST /api/data/_batch`) | `{ op, table }` |
| `CollectionClient`, `SDKCollectionClient`, `CollectionAccessor`, `CollectionTrashAccessor` | `TableClient`, `SDKTableClient`, `TableAccessor`, `TableTrashAccessor` |
| Offline `maxCachedRowsPerCollection`, `maxCachedQueriesPerCollection` | `…PerTable` |
| reservierter Accessor `<name>Collection`; `collectionCollection` | `<name>Table`; die Tabelle `collection` heißt `collection` |

```diff ts
-const { data } = await client.data.collection("posts").find();
+const { data } = await client.data.table("posts").find();
```

Typisierte Accessoren (`client.data.posts`) bleiben unverändert.

**Was zu tun ist:** Der Codemod führt `rebase migrate sdk-calls` über Ihren Code aus – führen Sie ihn bei einem bereits migrierten Projekt separat aus – und anschließend `rebase generate-sdk`. Ein `.collection(`-Aufruf, dessen Empfänger nicht das SDK ist, bleibt wie geschrieben bestehen und wird aufgelistet. Siehe [Typisiertes SDK](/docs/sdk/).

## 116. CLI flags: `--schema-dir`, not `--collections`

**Wen dies betrifft:** Skripte und CI-Schritte, die die CLI mit einem Schema-Pfad aufrufen.

**Was sich geändert hat:** `--collections` / `-c` werden bei jedem Befehl, der das Schema liest, abgelehnt, wobei die Fehlermeldung auf den Codemod verweist (`generate-sdk` ignoriert ein überflüssiges `--collections-dir`); `--schema-dir` gibt ein anderes Schema-Verzeichnis als `backend/schema` an. `rebase schema introspect` schreibt `defineTable`-Dateien nach `backend/schema/` – `--output` ist entfallen. `REBASE_STRICT_COLLECTION_CONFIG` wird nicht mehr gelesen: Ein Schema, das nicht kompiliert, verweigert stets den Start.

**Was zu tun ist:** Ersetzen Sie die Flags. Siehe [CLI](/docs/cli/) und [Schema-Generierung](/docs/cli/schema/).

## 117. The schema editor edits `backend/schema` with `TablePatch`

**Wen dies betrifft:** Code, der die Schema-Editor- oder Live-Schema-Routen aufruft, sowie Deployments, die die Variablen für Live-Editing setzen.

**Was sich geändert hat:** `/api/admin/schema-editor/collection/save`, `collection/delete`, `property/save` und `property/delete` sind entfallen. Der Editor bedient `GET /tables`, `POST /preview` und `POST /apply`, und die Endpunkte `/plan` und `/apply` des Live-Schema-Editings nehmen `{ patches: TablePatch[] }` statt einer Collection oder eines Patches davon entgegen. `REBASE_LIVE_SCHEMA_COLLECTIONS_PATH` wird beim Start abgelehnt: Die Variable heißt nun `REBASE_LIVE_SCHEMA_PATH` (Standard `backend/schema`), und `liveSchema.repository.collectionsPath` heißt `schemaPath`. Die Darstellung ist niemals eine Schema-Bearbeitung: Sie wird als UI-Präferenzen gespeichert (`/api/admin/ui-config`). Eine Bearbeitung, deren Datei auf der Festplatte geändert wurde, nachdem die Bearbeitung vorbereitet wurde (durch Speichern in der IDE, einen anderen Prozess), antwortet mit 409 `SCHEMA_EDIT_STALE_FILE` und schreibt nichts; zuvor war dies ein 400 `SCHEMA_EDIT_REFUSED`.

**Was zu tun ist:** Benennen Sie die Variable um; schreiben Sie Aufrufer der Routen um, sodass sie `TablePatch`-Edits senden, und laden Sie bei `SCHEMA_EDIT_STALE_FILE` neu. Siehe [Live-Schema-Editing](/docs/backend/live-schema-editing/).

## 118. A component slot is a component

**Wen dies betrifft:** Anpassungen, die eine React-Komponente über einen String-Pfad oder einen Lazy-Thunk `() => import(…)` benannt haben.

**Was sich geändert hat:** `Field` / `Preview` / `Filter` eines Felds, Collection-`Actions`, `entityViews[].Builder`, `collectionViews[].Builder`, `formView.Builder` und Komponenten-Overrides nehmen die Komponente selbst entgegen. `ComponentRef`, `ComponentLike`, `LazyComponentRef` und `isLazyComponentRef` (`@rebasepro/types`), `asComponentRef` und `asReactComponent` (`@rebasepro/cms-types`) sowie `resolveComponentRef` / `useResolvedComponent` (`@rebasepro/app`) wurden entfernt. `customizeTable` lehnt einen String oder Thunk mit der Meldung „imported by value“ ab.

**Was zu tun ist:** Importieren Sie die Komponente in der Datei in `frontend/src/cms/` und übergeben Sie sie direkt. Siehe [Benutzerdefinierte Felder](/docs/frontend/custom-fields/).

## 119. Panel preferences are UI preferences

**Wen dies betrifft:** Code, der `UserConfigurationPersistence` implementiert.

**Was sich geändert hat:** Wie ein Benutzer die Größe oder Reihenfolge einer Tabelle geändert hat, ist ein `UiTablePreferences`-Delta: `getTablePreferences` / `saveTablePreferences` ersetzen `getCollectionConfig` / `onCollectionModified`, und der partielle Collection-Config-Typ, den dies entgegennahm, wurde entfernt. Der Browser-Store hält diese unter `table_preferences::<slug>` und ignoriert, was ein älteres Panel gespeichert hat, sodass die Spaltenbreiten und Ansichtsmodi jedes Benutzers einmalig zurückgesetzt werden. `userSelect` auf einem Feld ist entfallen: Eine `.userId()`-Spalte dient als User-Picker.

Die Bridge von Studio folgt diesem Muster: `StudioSchemaEditing.updateCollection` heißt `applyTablePatches(slug, patches)`, und der Collection Editor sendet `{ patches }` an den Schema-Editor.

**Was zu tun ist:** Portieren Sie eine benutzerdefinierte Persistenz auf die beiden Methoden und ein benutzerdefiniertes `StudioSchemaEditing` auf `applyTablePatches`.

## 120. MongoDB is retired

**Wen dies betrifft:** Projekte, die `@rebasepro/server-mongo` nutzen oder `database(…, { engine: "mongodb" })` deklarieren.

**Was sich geändert hat:** Das Paket ist entfallen, ebenso wie die Mongo-Collection-Typen und der Rest des Mongo-Modells. Postgres ist die einzige Server-Engine: Eine Server-Transport-Quelle auf einer anderen Engine verweigert den Start unter Nennung der Engine.

**Was zu tun ist:** Migrieren Sie die Daten nach Postgres. Es gibt innerhalb von Rebase keinen Migrationspfad.

## 121. Firestore collections live in the frontend

**Wen dies betrifft:** ein Hybridprojekt mit `engine: "firestore"`-Collections.

**Was sich geändert hat:** Eine Firestore-Collection ist eine CMS-Quelle, die der Browser direkt liest: `defineFirestoreCollection` aus `@rebasepro/firebase`, in `frontend/src/cms/`, übergeben an `<RebaseCMS externalCollections>`. Eine Referenz zwischen Firestore und einer Postgres-Tabelle wird als ID des Ziels gespeichert, und eine Firestore-Referenz, deren `path` zugleich ein Postgres-Slug ist, zielt nun auf die Postgres-Tabelle.

**Was zu tun ist:** Der Codemod schreibt die `defineFirestoreCollection`-Dateien. Verweisen Sie auf eine Firestore-Collection über den Slug dieser Collection. Siehe [Firebase](/docs/frontend/firebase/).

## 122. MCP tools are named for tables

**Wen dies betrifft:** Prompts, Skripte und Allow-Lists, die MCP-Tools benennen.

**Was sich geändert hat:** Remote `/mcp`: `list_collections`, `describe_collection`, `query_collection`, `show_collection`, `count_documents`, `aggregate_documents`, `get_document`, `create_document`, `update_document`, `delete_document` → `list_tables`, `describe_table`, `query_table`, `show_table`, `count_rows`, `aggregate_rows`, `get_row`, `create_row`, `update_row`, `delete_row`; das Argument `collection` heißt nun `table`, und `show_app` / `save_app` akzeptieren `tables`. Der lokale Server: `list_documents` → `query_table`, `get_document` → `get_row`, `create_document` → `create_row`, `update_document` → `update_row`, `delete_document` → `delete_row`; `rebase_schema_plan` nimmt `patches` entgegen; Ressourcen lauten `rebase://tables/{name}`. Die MCP Apps View-Payload hat Version 3: für den Aufrufer bereinigte Tabellendeskriptoren, Pro-Tabelle-Berechtigungen und die UI-Präferenzen jedes Aufrufers unter `preferences` (`file`, `workspace`, `user`; ein API-Key hat keinen User-Layer), wobei Blöcke und Seeds `table` benennen. Die `collection-table`-View wurde entfernt. `list_tables` besitzt kein `title`; `describe_table` ergänzt `primaryKey`, `relations`, das `rls` des Aufrufers, `title` und `presentation`.

**Was zu tun ist:** Umbenennen. Die View und der Server müssen dieselbe Payload-Version sprechen: Ein gehosteter Connector und die von ihm erreichten Runtimes werden gemeinsam aktualisiert, und eine vom Projekt erstellte MCP-View wird mit den 0.31-Paketen neu gebaut. Siehe [MCP-Tool-Referenz](/docs/ai/mcp-tool-reference/) und [Remote-MCP](/docs/ai/remote-mcp/).

## 123. The rule vocabulary says `table`

**Wen dies betrifft:** Regeln, die `policy.existsIn` oder einen Membership-Mandanten verwenden, sowie Regeln, die `access` mit anderen Klauseln kombinieren.

**Was sich geändert hat:** `policy.existsIn({ collection, where })` heißt `existsIn({ table, where })`, und `tenant.from.membership.collection` heißt `membership.table`; Policy-Namen ändern sich nicht. Vier Regelformen gewähren nun etwas anderes, zwei davon mehr ([die Tabelle oben](#vor-dem-deployment-prüfen-diese-regeln-ändern-ihre-bedeutung)): Ein einfaches `{ access: "authenticated" }`, das zuvor nichts gewährte, lässt nun jeden angemeldeten Aufrufer zu, und die Junctions einer solchen Tabelle erhalten ihre Edge-Write-Policies. Regeln, die Klauseln kombinieren, die der Typ `SecurityRule` ausschließt, oder die einen ungültigen Wert für `access`, `mode`, `operation` oder `roles` enthalten, werden abgelehnt.

**Was zu tun ist:** Der Codemod benennt die Keys um, lehnt ungültige Regeln unter Angabe von Datei und Zeile ab und listet die Regeln, deren Bedeutung sich ändert, unter „Review before deploying“ auf. Behalten Sie diese für jeden Fall bei, tragen Sie `access: "registered"` ein (angemeldete Aufrufer mit Konto) oder entfernen Sie die Regel. Führen Sie anschließend `rebase db push --dry-run` und `rebase doctor --policies` gegenüber Ihrer Datenbank aus.

## 124. Studio reads the tables from the server

**Wen dies betrifft:** Studio, das auf ein Backend vor 0.31 gerichtet ist, sowie Studio-JS-Konsolenskripte.

**Was sich geändert hat:** Jedes schema-bewusste Tool liest `GET /api/schema/tables`; gegenüber einer Runtime, die dies nicht bereitstellt, zeigen sie einen Upgrade-Hinweis an. Die deklarierte Seite des RLS-Editors entspricht dem, was der Server kompiliert hat. Ein JS-Konsolenskript erhält `context.tables` (zuvor `context.collections`).

**Was zu tun ist:** Aktualisieren Sie die Runtime zusammen mit dem Panel. Siehe [Studio](/docs/studio/).

**Was sich geändert hat:** `remediation.rebase.securityRules` heißt nun `remediation.rebase.rls`, der Auszug ist ein `defineTable(…, { rls })`, und die Formatversion des Dokuments ist 2. `--json` bleibt unverändert. Siehe [rls-check](/docs/rls-check/).

## 128. The agent skill `rebase-collections` is `rebase-tables`

**Was sich geändert hat:** Der Skill, der das Datenmodell vermittelt, heißt `rebase-tables`: Erstellung von Tabellen, Spalten, Relationen, `rls`, Hooks und der darauf aufbauenden CMS-Schicht. `rebase skills install` entfernt die alte `rebase-collections`-Kopie, auch aus Installationen, die vor der Existenz des Skills-Manifests vorgenommen wurden, und behält jedes Verzeichnis dieses Namens bei, das Sie selbst erstellt haben.

## 129. `useJsonCollectionsConfigController` is removed

**Wen dies betrifft:** Projekte, die Collection-Definitionen über `@rebasepro/cms` als JSON gespeichert haben.

**Was sich geändert hat:** `useJsonCollectionsConfigController` ist entfallen, zusammen mit seinem Optionstyp und der dahinterliegenden JSON-Store-Klasse. Das Schema einer Tabelle liegt in `backend/schema`, und wie das Panel sie anzeigt, liegt in UI-Präferenzen: `frontend/src/cms/ui-config.json` in der Entwicklung, die Tabelle `rebase.ui_preferences` in einem Deployment.

**Was zu tun ist:** Deklarieren Sie die Tabellen mit `defineTable` (`rebase migrate collections-to-tables` erzeugt sie aus Collection-Definitionen) und übergeben Sie das `uiConfig` des Scaffolds an `<RebaseCMS>`. Siehe [Anpassen einer Tabelle](/docs/frontend/customize-table/#customizations-ui-configjson-and-preferences).

## 130. `rebase build` refuses a frontend without `rebaseBackendGuard()`

**Wen dies betrifft:** jedes Projekt mit einem Frontend.

**Was sich geändert hat:** Das Frontend darf `backend/` ausschließlich als Typen importieren. Ein Value-Import würde Server-Code – Hooks und alle darin gelesenen Secrets – in das Browser-Bundle einbringen. `rebaseBackendGuard()` aus `@rebasepro/app/vitePlugin` lässt `vite build` und `vite dev` fehlschlagen, wenn ein Frontend-Modul nach `backend/` aufgelöst wird, und nennt dabei den Importer, den Import und die Datei – unter Berücksichtigung von Aliasen, tsconfig-Pfaden, Package- und absoluter Auflösung, Globs, `?raw`, Re-Exporten und dynamischen Imports. `rebase build` sowie der Frontend-Build, den `rebase cloud deploy` ausführt, verweigern ein Frontend, dessen Vite-Konfiguration dies nicht nutzt; `rebase dev` gibt eine Warnung aus; `rebase verify` meldet `cms-backend-guard-missing`.

**Was zu tun ist:** Der Codemod fügt dies zur `frontend/vite.config.ts` eines Scaffolds hinzu und gibt die Zeilen für jede andere Konfiguration aus:

```diff ts
+import { rebaseBackendGuard } from "@rebasepro/app/vitePlugin";

 export default defineConfig({
-    plugins: [react()],
+    plugins: [react(), rebaseBackendGuard()],
 });
```

Ändern Sie anschließend jeden Value-Import von `backend/` in `import type`.

## 131. Rows on the wire follow their column

**Wen dies betrifft:** Clients, die Fremdschlüssel lesen oder Relationen benennen, sowie Schreiboperationen, die generierte Spalten oder partielle JSON-Objekte senden.

**Was sich geändert hat:** Werte durchlaufen beim Senden den Codec ihrer Spalte und beim Empfangen die Regeln der Spalte.

- Eine von einer Relation generierte `bigint`- oder `numeric`-Fremdschlüsselspalte, die Postgres als Text zurückgibt, wird in REST, dem SDK und dem Admin-Panel als **Zahl** ausgeliefert. Deklarierte Zahlenschlüssel waren dies bereits.
- Die **Elemente eines nativen Arrays werden als ihr Skalartyp ausgeliefert**, in REST, dem SDK, dem Socket und dem Treiber:

  | Spalte | 0.30 lieferte | 0.31 liefert |
  |---|---|---|
  | `timestamptz[]` | `["2026-01-02 11:00:00+01"]` | `["2026-01-02T10:00:00.000Z"]` |
  | `numeric[]` (ein Treiber, der ohne die numerische Boot-Einstellung geöffnet wurde: Tests, Skripte) | `["1.50", "2.25"]` | `[1.5, 2.25]` |
  | `bigint[]` mit einem Null-Element | `[1, 0, 3]` | `[1, null, 3]` |
  | `date[]`, `timestamptz[]` oder ein Enum-Array mit einem Null-Element | `["2026-01-02", "NULL"]` | `["2026-01-02", null]` |

  `date[]`, `time[]`, `text[]`, `uuid[]`, `boolean[]`, `integer[]` und `double precision[]` werden wie zuvor ausgeliefert. Was gespeichert wird, ändert sich nicht: Eine Zeile, die gelesen und wieder gespeichert wird, speichert dasselbe Array.
- Eine in `include`, einem Filter oder einer Sortierung benannte Relation muss mit ihrem **exakten Namen** angegeben werden. Die erneuten Versuche mit dem Slug und der snake_case-Schreibweise sind entfallen.
- Eine generierte Spalte wird beim Schreiben abgelehnt und aus dem OpenAPI-Eingabeschema weggelassen.
- Ein erforderliches Feld innerhalb eines JSON-Objekts wird erzwungen; `$inc` und Array-Elemente bei einer Integer-Spalte müssen ganze Zahlen sein.

**Was zu tun ist:** Lesen Sie Fremdschlüssel als Zahlen dort, wo Sie zuvor Strings verglichen haben, parsen Sie `timestamptz[]`-Elemente als RFC 3339, behandeln Sie ein Null-Array-Element als `null` und schreiben Sie Relationsnamen genau so, wie die Tabelle sie deklariert (ihre `relations`-Keys). Senden Sie keine generierten Spalten mehr.

## 132. History is served as reads

**Wen dies betrifft:** Leser von Verlaufs-Snapshots und jeden, der einen `DataDriver` implementiert.

**Was sich geändert hat:** Verlaufseinträge werden wie Lesezugriffe ausgeliefert: zuerst Feldzugriff, dann `afterRead` (global, Tabelle, Spalte). Eine durch einen Hook oder ein `.transform({ afterRead })` maskierte Spalte ist in jedem Snapshot maskiert; eine Spalte, die der Aufrufer nicht lesen darf, wird vorenthalten und aus `changed_fields` weggelassen; Keys entfernter Spalten werden vorenthalten, und ein Revert schreibt niemals eine Spalte, die der Aufrufer nicht lesen darf. Ein Hook, der bei einem alten Snapshot einen Fehler wirft, lässt die Anfrage fehlschlagen. 0.30 lieferte die gespeicherten Werte im Rohzustand aus, daher sollte ein Projekt mit Historie und Maskierungs-Hooks ein Upgrade durchführen.

Ein Eintrag enthält die Zeile so, wie `GET /api/data/<table>/<id>` sie ohne `include` liest: einfache Werte, ein `belongsTo` als dessen Fremdschlüssel. Ein Eintrag, den eine ältere Version mit dem View-Modell des Admin-Panels aufgezeichnet hat, wird als diese Zeile ausgeliefert und zurückgesetzt: eine `{ "__type": "date", "value" }`-Hülle als Wert, eine `{ "__type": "relation" }`-Referenz einer besitzenden Relation als Fremdschlüssel unter dem eigenen Namen des Keys und jede andere Referenz als Schlüssel der zugehörigen Zeile. 0.30 lieferte diese Referenzen wie geschrieben aus.

Ein Treiber liefert die Historie über `DataDriver.serveStoredRows(path, rows)` innerhalb der schreibgeschützten Transaktion des Aufrufers aus; die Verlaufsrouten antworten mit 501 bei einem Treiber, der dies nicht unterstützt, sodass die Historie niemals unmaskiert ausgeliefert wird.

**Was zu tun ist:** Für den mitgelieferten Postgres-Treiber ist nichts zu tun. Ein benutzerdefinierter Treiber implementiert `serveStoredRows`. Siehe [Historie](/docs/backend/history/).

## 133. `@rebasepro/server` exports name tables

**Wen dies betrifft:** einen Server, den Sie aus Teilen von `@rebasepro/server` anstelle von `initializeRebaseBackend` / `createRebaseBackend` zusammenbauen.

**Was sich geändert hat:**

| Vorher | Jetzt |
|---|---|
| `new RestApiGenerator(collections, …)` | `new RestApiGenerator(tables, …)` (`RestTables`) |
| `mountOpenApiDocs({ collections })`, `createHistoryRoutes({ collections })` | `mountOpenApiDocs({ serverTables })`, `createHistoryRoutes({ tables })` |

## 135. `@rebasepro/types` and `@rebasepro/common` drop the collection model from their roots

**Wen dies betrifft:** Code, der Collection- oder Property-Typen, Admin-Panel-Helper oder das Lift aus `@rebasepro/types` oder `@rebasepro/common` importiert – benutzerdefinierte Felder, benutzerdefinierte Views, Plugins, Tests mit Collection-Fixtures – sowie benutzerdefinierte Treiber, die die Registry implementieren.

**Was sich geändert hat:** Die Kernel-Pakete beschreiben nur noch Tabellen. Was eine Collection beschreibt, wie das Admin-Panel sie darstellt, befindet sich in `@rebasepro/cms-types`:

- **Typen**, die aus `@rebasepro/types` verschoben wurden: `CollectionConfig`, `PostgresCollectionConfig`, `FirebaseCollectionConfig`, `AnyCollectionConfig`, jedes `…Property` (`StringProperty`, `NumberProperty`, `ArrayProperty`, …) und `Properties`, `CollectionCallbacks` und deren Hook-Props, die Relationsarten aus 0.30 und deren `Resolved…`-Formen, `CollectionIndex`, die Chip-Farben (`ColorScheme`, `ColorKey`, …), `FieldAccess`, `EnumValues`.
- **Helper**, die aus `@rebasepro/common` verschoben wurden: die collection-spezifischen Policy-Helper (`policyToPostgres`, `compileRulePolicies`, `getEffectiveSecurityRules`, `getGeneratedPolicyNames`, …), `CollectionRegistry`, `resolveCollectionRelations`, `resolveRelation`, `getTableName`, `findRelation`, `rowToViewModel`, `resolvePrimaryKeys`, die Field-Access-Sicht einer Property (`effectiveAccess`, `canReadField`, `canWriteField`), `evaluateCondition`, `canEditEntity`, `resolveProperty`, `getDefaultValuesFor`, `getSubcollections`, `getCopyValues`, `enumToObjectEntries`. Eine aus einem reinen Ausdruck kompilierte Regel nutzt `compilePolicyExpression(expr)` aus `@rebasepro/common`.
- **`composeCallbacks`** komponiert die Callbacks einer Collection für das Panel und wurde nach `@rebasepro/cms-types` verschoben; `@rebasepro/server` re-exportiert dies nicht mehr. Backend-Code komponiert die Hooks einer Tabelle mit `composeTableHooks` aus `@rebasepro/common`, und der Codemod listet einen Backend-Import von `composeCallbacks` als manuellen Schritt auf, der darauf hinweist.
- **`defineCollection`** wurde aus `@rebasepro/common` und `@rebasepro/cms-types` entfernt: Deklarieren Sie die Tabelle mit `defineTable` in `backend/schema` und passen Sie sie mit `customizeTable` in `frontend/src/cms` an; eine Firestore-Collection ist `defineFirestoreCollection` aus `@rebasepro/firebase`.
- **Der Accessor des Admin-Panels und seine Typen**: `Entity`, `EntityValues`, `TableAccessor`, `TableTrashAccessor`, `FindResponse`, `QueryBuilderInterface`, `RebaseData` und `AuthState` haben `@rebasepro/types` verlassen; `buildRebaseData`, `wrapAsEntityData`, `buildRoutedRebaseData`, `EntityDataOptions`, `QueryBuilder`, `RelationRef` und `createRelationRef` haben `@rebasepro/common` verlassen. Alle werden aus `@rebasepro/cms-types` importiert. Die eigene Datenschicht des SDKs – `buildSdkData`, `createDriverTableRows`, `buildRoutedSdkData` in `@rebasepro/common` – liefert Zeilen direkt aus und gibt zurück, was sie zuvor zurückgegeben hat.
- **`EntityDataOptions.resolveCollection`** wird durch `primaryKeysOf`, `viewModelOf`, `storedValuesOf` und `viewModelSourceOf` ersetzt; `collectionEntityDataOptions(resolveCollection, { resolveDataPath, resolveAccessor })` aus `@rebasepro/cms-types` baut diese auf.
- **Der Migrations-Lift** (`collectionsToTableDefs`, `collectionToTableDef`, `LiftNote`, `LiftResult`, `LiftOptions`) wurde nach `@rebasepro/common/migrate` verschoben, neben eine eingefrorene Kopie des 0.30-Collection-Modells (`Legacy…`-Typen) und `defineLegacyCollection`.
- **Ebenfalls aus den Kernel-Roots entfernt**, jeweils vom Codemod als manueller Schritt aufgelistet: die Collection-Patch-API von `@rebasepro/types` (`CollectionPatch`, `CollectionPatchOp`, `applyCollectionPatch`, `collectionPatchProblems`, `isCollectionPatch`, `nestCollectionPatchPaths` → `TablePatch`), dessen Collection-JSON-Helper (`diffCollections`, `diffJsonValues`, `toCollectionJson`, `RUNTIME_ONLY_COLLECTION_KEYS`, `runtimeOnlyKeyIn`), die aus der Mongo-Ära stammende Fähigkeit `DocumentAdmin`, `isDocumentAdmin` und `supportsDocumentAdmin` sowie `RebaseProjectContract.collectionSlugs` / `.collections` / `.generatedAt` (`/api/meta/contract` liefert `tables`); aus `@rebasepro/common`: `buildTenantSecurityRule` → `tenantSecurityRule`, `defaultPoliciesDisabled` → `tableDefaultPoliciesDisabled`, `restoresSoftDeletedRow` → `isSoftDeleteRestore`, `softDeleteFieldOf` → `softDeleteColumn`, `getJunctionConfigForRelation` → `resolveTableJunctions` sowie `isRelationRequired`, `relationDeclaringProperty`, `requireCallbackCollection` ohne Nachfolger (lesen Sie den `TableDescriptor`).
- **Die Registry eines Treibers** ist ein `TableRegistryInterface` (zuvor `CollectionRegistryInterface`): `setGlobalHooks?` und `setTableHooks?` ersetzen `getGlobalCallbacks` / `setGlobalCallbacks?`. `globalHooksAsCallbacks`, `resolveDriftCheckName` und `PENDING_TABLE_FEATURES` wurden entfernt.

**Was zu tun ist:** `rebase migrate sdk-calls` (Teil von `collections-to-tables`) verschiebt jeden unten stehenden Import in sein neues Paket – zusammengeführt in einen bereits in der Datei vorhandenen Import dieses Pakets, wobei `import type`, Inline-`type` und `as`-Aliase beibehalten werden – und fügt das Paket zu den Abhängigkeiten des importierenden Workspace-Pakets hinzu; führen Sie anschließend `pnpm install` aus. Ein Import eines entfernten Namens, ein Namespace-Import (`import * as`), ein `export *`, ein dynamisches `import()` oder ein `require()`, das einen verschobenen Namen verwendet, ist ein nummerierter manueller Schritt. Ein Test, der Collection-Literale als Fixtures verwendet, typisiert diese mit den `Legacy…`-Typen und transformiert sie über `@rebasepro/common/migrate`.

## 136. The Postgres driver and the socket's one-shot reads return the REST row

**Wen dies betrifft:** Funktionen oder Plugins, die über `requireDriver(c)` / `getDriver(c)` lesen, Code, der die Socket-Frames `FETCH_COLLECTION` / `FETCH_ONE` sendet, und Code, der `{ __type }`-Objekte aus einer Antwort gelesen hat.

**Was sich geändert hat:** Es gibt nur noch ein Ausgabeformat. `fetchCollection` und `fetchOne` auf dem Postgres-Treiber – worüber `requireDriver(c)` einer Funktion, Plugins, die One-Shot-Frames des Sockets, MCP und der RLS-Simulator lesen – geben das zurück, was `GET /api/data/<table>` zurückgibt:

| Wert | 0.30 Treiber-Lesevorgang | 0.31 |
|---|---|---|
| ein Timestamp | `{ "__type": "date", "value": … }` | ein RFC-3339-String |
| ein `belongsTo` | `{ "__type": "relation", "id", "path" }` unter dem Namen der Relation | der Fremdschlüssel unter seinem eigenen Key (`authorId`) |
| eine zugehörige Zeile | jede von `fetchOne` geladene Relation | nur eine von `include` benannte Relation, als eigene Zeile des Ziels |
| ein Vector, ein `bytea` | `{ "__type": "Vector" }`, eine Data-URL | wie von REST ausgeliefert |

`FetchOneProps` nimmt `include` entgegen (`ListenOneTarget` ist entfernt: nutzen Sie `FetchOneProps`). `rebase.data`, `context.data` und das SDK gaben dieses Format bereits zurück und bleiben unverändert.

`@rebasepro/client` liest REST-Bodies und Socket-Frames als einfaches JSON: Ein Wert mit einem `__type`-Key wird nicht mehr in ein `Date`, `EntityReference`, `EntityRelation`, `GeoPoint` oder `Vector` umgewandelt, und ein JSON-Dokument, das einen `__type`-Key enthält, wird so zurückgegeben, wie es gespeichert ist.

**Was zu tun ist:** Lesen Sie die einfache Zeile aus: Parsen Sie Daten aus ihren Strings, lesen Sie einen Fremdschlüssel über seinen eigenen Key und übergeben Sie `include` für jede Relation, die Sie lesen:

```diff ts
-const article = await requireDriver(c).fetchOne({ path: "articles", id });
-const authorId = article?.author.id;      // a { __type: "relation" } ref
+const article = await requireDriver(c).fetchOne({ path: "articles", id, include: ["author"] });
+const authorId = article?.authorId;
```

## 138. The backend accepts the values the REST API documents, and nothing else

**Wen dies betrifft:** Clients, die eine To-One-Relation als Objekt oder einen Vektor als `{ value }` schreiben, Code, der bei einer Relation mit einem Objekt filtert, Code, der die Werteklassen des Admins importiert, und Offline-Apps mit Schreiboperationen, die von 0.30 in die Warteschlange gestellt wurden.

**Was sich geändert hat:** Ein Schreibvorgang akzeptiert das Format, das ein Lesevorgang zurückgibt – ein einheitliches Schreibformat für REST, den Socket, MCP und das prozessinterne SDK:

| Wert | Akzeptiert | Jetzt abgelehnt |
|---|---|---|
| eine To-One-Relation (`belongsTo`, `hasOne`, ein To-One-`via`) | der Schlüssel der verknüpften Zeile oder `null` (`""` ist `null`), unter dem Namen der Relation oder des Fremdschlüssels | ein Objekt wie `{ "id": 5 }`: `400 VALIDATION_INVALID_VALUE`, "'posts.author' links one 'authors' row: write that row's key (a string or a number), or null to unlink — not an object." |
| eine To-Many-Relation (`hasMany`, `manyToMany`, ein schreibbares To-Many-`via`) | eine Liste von Schlüsseln oder von `{ id, _pivot? }` | — (andere Keys auf dem Objekt werden wie zuvor ignoriert) |
| ein Vektor | eine Liste von Zahlen | ein `Vector` oder `{ "value": [...] }`: `400`, "'embedding' expects a vector as a list of numbers" |
| ein Datum, eine Uhrzeit | ISO-Text (`Date` prozessintern) | — |
| ein GeoPoint | `{ latitude, longitude }` | — |
| ein `bytea` | eine `data:application/octet-stream;base64,`-URL (`Buffer` / `Uint8Array` prozessintern) | — |
| ein Filter auf einer Relation | der Schlüssel | ein Objekt wird nicht mehr ausgepackt: Es wird unverändert verglichen |

0.30 akzeptierte eine als Objekt geschriebene To-One-Relation und übernahm stillschweigend deren `id`; dieses Format war nie dokumentiert und ist das View-Modell des Admin-Panels. Das Admin-Panel konvertiert sein View-Modell nun vor jedem Schreib- und Filtervorgang im Browser in Wire-Werte.

Die Werteklassen des Admins wurden zusammen mit dem Rest seines View-Modells verschoben: `EntityReference`, `EntityRelation`, `GeoPoint`, `Vector` und `EntityReferenceProps` werden aus `@rebasepro/cms-types` importiert (sie haben `@rebasepro/types` verlassen), und `normalizeToEntityRelation` ebenfalls (aus `@rebasepro/common` entfernt); `withRelationReferencesOnly` wurde entfernt. Die Historie speichert die Zeile so, wie ein Lesevorgang sie zurückgibt; zuvor aufgezeichnete Einträge werden als einfache Werte ausgeliefert und zurückgesetzt ([Abschnitt 132](#132-history-is-served-as-reads)).

Die Offline-Queue von `@rebasepro/client` speichert Wire-Werte. Eine offline durch das 0.30-SDK eingereihte Schreiboperation wird konvertiert, wenn sie zurückgelesen und wiederholt wird: Nichts, was vor dem Upgrade in die Queue gestellt wurde, geht verloren.

**Was zu tun ist:** Senden Sie den Schlüssel: `{ "author": 5 }`, nicht `{ "author": { "id": 5 } }`; senden Sie einen Vektor als Liste von Zahlen und filtern Sie eine Relation über ihren Schlüssel. `rebase migrate sdk-calls` verschiebt die Imports der Werteklassen ([die Liste](/docs/upgrading/0-30-to-0-31-imports/)). Siehe [Schreiboperationen](/docs/backend/writes/).

## 139. `/api/docs` is served to the schema endpoint's audience

**Wen dies betrifft:** Personen oder Tools, die `/api/docs` lesen oder `/api/swagger` aufrufen – Swagger UI, ein API-Client-Generator, ein CI-Schritt.

**Was sich geändert hat:** Wenn `enableSwagger` nicht gesetzt ist (`REBASE_ENABLE_SWAGGER` nicht gesetzt), wird das OpenAPI-Dokument in jeder Umgebung den Aufrufern ausgeliefert, denen `GET /api/schema/tables` Tabellen beschreibt, mit denselben Ablehnungen – 401 für einen anonymen Aufrufer, außer bei `schemaTables.public`, 403 für Zugangsdaten ohne Schema- oder Data-Scope – und jeder Aufrufer erhält das Dokument genau der Tabellen, Spalten und Relationen, die dieser Endpunkt für ihn beschreibt (ein Administrator erhält alles). Es gibt kein Swagger UI. Ein Server ohne konfigurierte Authentifizierung antwortet mit `404 DOCS_UNAVAILABLE`. 0.30 veröffentlichte das gesamte Dokument, jede bereitgestellte Tabelle und nicht-private Spalte in der Entwicklung für anonyme Aufrufer und beschränkte es in der Produktion auf Administratoren.

| `enableSwagger` / `REBASE_ENABLE_SWAGGER` | `/api/docs` | `/api/swagger` |
|---|---|---|
| nicht gesetzt (Standard) | jedem Aufrufer, dem der Schema-Endpunkt Tabellen beschreibt: seine Tabellen | wird nicht bereitgestellt |
| `true` | das gesamte Dokument, für alle | wird außerhalb der Produktion bereitgestellt |
| `false` | das gesamte Dokument, hinter dem Admin-Gate | wird nicht bereitgestellt |

**Was zu tun ist:** Rufen Sie `/api/docs` angemeldet auf. Um das gesamte Dokument wie unter 0.30 in der Entwicklung zu veröffentlichen, setzen Sie `REBASE_ENABLE_SWAGGER=true` (oder `enableSwagger: true`). Siehe [Endpunkte](/docs/backend/endpoints/).

## 140. A many-to-many `pivot` column may not declare `.transform()`

**Wen dies betrifft:** ein `rel.manyToMany(…, { pivot: { … } })`, dessen Pivot-Spalte ein `.transform()` besitzt.

**Was sich geändert hat:** Der Compiler lehnt dies ab („the pivot column "x" declares `.transform()` …“). Das Transform einer Pivot-Spalte wurde nirgendwo ausgeführt, sodass ein Wert, den Sie maskieren wollten, unmaskiert wie gespeichert ausgeliefert wurde.

**Was zu tun ist:** Entfernen Sie das `.transform()` und maskieren Sie `_pivot` in `hooks.afterRead` der Zieltabelle. Siehe [Relationen](/docs/collections/relations/).

## 141. A link is exactly as readable and writable as its key column

**Wen dies betrifft:** Clients, die ein `belongsTo` über seinen Relationsnamen schreiben, eine Relation lesen oder filtern, deren Schlüsselspalte eingeschränkt ist, oder sich auf `strictWrites: false` verlassen.

**Was sich geändert hat:** Eine Einschränkung einer Schlüsselspalte ist eine Einschränkung für jede Schreibweise, die sie liest oder schreibt.

- Das Schreiben eines Links über seinen Relationsnamen (`{ "reviewer": 7 }`) unterliegt jeder Regel der von ihm gesetzten Schlüsselspalte – `.readOnly()`, `.private()`, `access.write`, Erstellungsstempeln, der Tenant-Spalte, Schlüssel-Unveränderlichkeit – bei REST, Bulk, `_batch`, dem Socket und MCP. Das Schreiben des Links unter beiden Namen (`{ "reviewer": 7, "reviewerId": 8 }`) mit unterschiedlichen Werten führt zu einem 400 `VALIDATION_INVALID_VALUE`. Das Verschieben einer Zeile zu einem anderen Mandanten über ihren Link antwortet mit 400 `TENANT_IMMUTABLE` (zuvor war dies ein 500).
- Eine Relation ist nur lesbar, wenn der Aufrufer jede Spalte lesen darf, die ihr Join liest, auf jeder Tabelle, die sie durchläuft: den Schlüssel eines `belongsTo`, den Fremdschlüssel des Ziels bei einem `hasMany` / `hasOne`, jede Spalte, über die die Schritte eines `via` joinen. Eine Relation, bei der dies fehlschlägt, wird aus `include` und `_count` weggelassen, und ein Filter, eine Sortierung oder ein Relationspfad darüber antwortet mit `FIELD_NOT_READABLE` (bzw. eine unbekannte Relation, wenn die Spalte `.private()` ist). Ein To-One-`via`-Schreibvorgang, der eine Spalte kopieren würde, die der Aufrufer nicht lesen darf, wird mit `FIELD_NOT_READABLE` abgelehnt. Die inversen und `via`-Fälle waren auch in 0.30.x offen.
- Ein Link, dessen Schlüsselspalte der Aufrufer nicht lesen darf, wird aus `include` weggelassen, und ein Filter, eine Sortierung, ein `fields`-Eintrag oder ein Relationspfad darüber antwortet mit `FIELD_NOT_READABLE`; ein an einen `.private()`-Schlüssel gebundener Link ist eine unbekannte Relation. `GET /api/schema/tables`, OpenAPI und MCP `describe_table` beschreiben einen Link und seinen Schlüssel zusammen, sodass eine Schlüsselspalte, deren Link geschlossen ist, auch dort vorenthalten wird.
- `strictWrites: false` entscheidet über genau eine Sache: Ein nicht deklarierter Key wird an den Treiber weitergeleitet (geschrieben, wenn die Datenbank die Spalte besitzt, andernfalls 400 `VALIDATION_UNKNOWN_FIELDS`). Es öffnet niemals eine deklarierte Spalte, einen Stempel, den Mandanten, den Schlüssel, ein Relationsziel oder eine `_pivot`-Regel.

**Was zu tun ist:** Schreiben Sie einen Link unter einem Namen oder unter beiden mit demselben Wert; lesen Sie eingeschränkte Links mit einer Rolle, die deren Schlüssel lesen darf. Siehe [Feldzugriff](/docs/collections/field-access/).
