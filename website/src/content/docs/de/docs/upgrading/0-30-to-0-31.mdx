# Upgrade von 0.30 → 0.31

<span class="since-badge" data-since="0.31">Seit 0.31</span>

0.31 macht das Backend Postgres-first. Die Tabellen, die Sie mit `defineTable` in `backend/schema/` deklarieren, sind das Einzige, was das Backend über Ihre Daten weiß; was das Admin-Panel darüber hinaus anzeigt, liegt im Frontend. Fast jeder Eintrag unten ist eine Folge dieser Trennung, und fast alles wird durch einen einzigen Befehl für Sie erledigt.

### Die Checkliste pro Projekt

1. **Aktualisieren Sie zuerst jedes `@rebasepro`-Paket** in jedem Workspace-Paket, damit die Typen, die der Codemod liest, denen von 0.31 entsprechen: `pnpm -r up "@rebasepro/*@0.31.0"`, dann `pnpm install`. Ein Projekt auf einer Version vor 0.30 wendet zuerst die Codeänderungen der Leitfäden dazwischen an ([Upgrades](/docs/upgrading/)) und erfüllt die Mindestanforderungen der Toolchain von 0.31 – Node 22.22, TypeScript 6, React 19.2.7, React Router 8, Vite 8 ([die Liste](/docs/upgrading/0-30-to-0-31-by-hand/#a-project-on-a-release-before-030)): Der Codemod lädt ein `config/` aus 0.20–0.29 und seine SQL-Prüfung besteht, aber diese Prüfung vergleicht den 0.31-Compiler mit sich selbst – erst Schritt 7 gegen Ihre Datenbank beweist, dass das generierte DDL dem entspricht, was Ihre Datenbank enthält.
2. **Committen Sie, führen Sie dann den Codemod als Testlauf aus:** `rebase migrate collections-to-tables --dry-run`. Er gibt die Dateien aus, die er schreiben würde, was er ablehnt (mit Datei und Zeile), die Hinweise und die manuellen Schritte und schreibt nichts. Beheben Sie zuerst in `config/`, was er ablehnt.
3. **Führen Sie ihn echt aus:** `rebase migrate collections-to-tables`. Er schreibt `backend/schema/`, `frontend/src/cms/` (mit `ui-config.json`), die `backend/`-Module und die Projektdateien, fügt `rebaseBackendGuard()` zur `vite.config.ts` des Scaffolds hinzu, schreibt Ihre SDK-Aufrufe um, verschiebt die Importe von Namen, die 0.31 in ein anderes Paket verschoben hat ([Abschnitt 135](#135-rebaseprotypes-and-rebaseprocommon-drop-the-collection-model-from-their-roots)), und beweist, dass das generierte SQL Byte für Byte identisch ist – oder stellt jede Datei wieder her. Siehe [Abschnitt 108](#108-tables-in-backendschema-replace-configcollections--run-the-codemod-first).
4. **Lesen Sie den letzten Abschnitt seiner Ausgabe, „Review before deploying: these rules change meaning“**, und entscheiden Sie über jede dort aufgeführte Regel ([unten](#review-before-deploying-these-rules-change-meaning)).
5. **Führen Sie die ausgegebenen manuellen Schritte der Reihe nach durch.** Jeder nennt seine Datei, und die meisten enthalten das zu schreibende Snippet: den `<RebaseCMS>`-Mount mit `tableCustomizations` und `uiConfig`, wenn Ihre `App.tsx` nicht die des Scaffolds ist (oder das Panel in einem anderen Modul gemountet ist, das der Schritt nennt), `rebaseBackendGuard()`, wenn es Ihre `vite.config.ts` nicht ist und in jeder anderen statischen App aus `rebase.json` ([Abschnitt 130](#130-rebase-build-refuses-a-frontend-without-rebasebackendguard)), globale Hooks, einen Import eines von 0.31 entfernten Namens ([Abschnitt 135](#135-rebaseprotypes-and-rebaseprocommon-drop-the-collection-model-from-their-roots)) und `rebase skills install`, wenn das Projekt Agent-Skills enthält ([Abschnitt 128](#128-the-agent-skill-rebase-collections-is-rebase-tables)). Führen Sie `pnpm install` aus, wenn die Ausgabe „Dependencies added“ auflistet. Lesen Sie dann zwei Listen im SDK-Teil der Ausgabe:
   - **„Rewritten by name — review“**: `.collection(`-Aufrufe auf einem Receiver ohne Typ (`any`), umgeschrieben, weil der Receiver `dataAsAdmin` heißt oder `.data` mit einem literalen Tabellennamen ist; das `collection`-Member eines Typs, den ein `data`- / `dataAsAdmin`-Slot enthält; und Test-Doubles. Prüfen Sie bei jedem, ob es sich um das SDK handelt.
   - **„Left unchanged — check each“**: `.collection(`-Aufrufe, bei denen der Codemod nicht nachweisen konnte, dass es sich um das SDK handelt, wie etwa ein Aufruf über einen Typ, den Ihr Projekt selbst deklariert. Ein Aufruf, der hier verbleibt und das SDK *ist*, schlägt unter 0.31 zur Laufzeit fehl: Benennen Sie ihn manuell in `.table(` um. Code, der prüft, ob `collection` existiert (`typeof data.collection === "function"`), ist ein manueller Schritt: Unter 0.31 nimmt er stillschweigend den anderen Zweig.

   Eine als Build-Ausgabe committete Datei (ein gebündeltes oder minifiziertes `.js`) wird niemals bearbeitet: Sie wird aufgelistet, also bauen Sie sie nach der Migration neu und ersetzen Sie eine vendorte Kopie des Clients durch den 0.31-Build. Wiederholte Schritte gleicher Art werden einmal ausgegeben und listen jede betroffene Datei und Zeile auf; `--json` gibt jeden Schritt separat aus. Lesen Sie dann [Was Projekte manuell geändert haben](/docs/upgrading/0-30-to-0-31-by-hand/): die Anpassungen, die reale Projekte nach diesen Schritten noch manuell vorgenommen haben.
6. **Führen Sie die vom Codemod ausgegebene `git rm`-Zeile aus**, sobald das Diff überprüft wurde und `rebase migrate collections-to-tables --check` erfolgreich durchläuft: `git rm -r config/collections …` und die Verdrahtung, die nach `backend/` verschoben wurde, oder `git rm -r config`, wenn dort nichts Eigenes mehr verbleibt ([Abschnitt 109](#109-there-is-no-config-package)). Die nächsten drei Schritte setzen dies voraus: `generate-sdk`, `db push`, `doctor` und `verify` verweigern die Ausführung bei einem Projekt, das noch `config/collections` enthält.
7. **`rebase generate-sdk`** – die Namen des generierten Moduls haben sich geändert ([Abschnitt 115](#115-the-sdk-addresses-a-table-datatableslug)).
8. **Führen Sie gegen Ihre Datenbank** `rebase db push --dry-run` aus und erwarten Sie „No changes: the database already matches these tables.“, dann `rebase doctor --policies` und erwarten Sie keinen Policy-Drift. Die SQL-Prüfung des Codemods beweist die Korrektheit der Konvertierung; diese beiden Befehle prüfen sie gegen die reale Datenbank, und jeder aufgelistete Policy-Unterschied ist eine Änderung daran, wer worauf zugreifen kann.
9. **`rebase verify`** – liest nun auch `frontend/src/cms`: eine Anpassung, die eine nicht existierende Tabelle oder ein nicht existierendes Feld benennt, eine erforderliche Spalte, die im Formular weggelassen wurde, ein fehlender `rebaseBackendGuard()`, eine nicht an `<RebaseCMS>` übergebene `ui-config.json`.
10. **Neu bauen und deployen.** Ein vor 0.31 erstelltes Bundle startet auf einer 0.31-Runtime nicht ([Abschnitt 112](#112-bundle-format-3-format-2-bundles-are-refused)). Der erste Start aktualisiert den Schema-Versionsstempel der Datenbank einmalig ([Abschnitt 113](#113-the-schema-version-is-computed-from-tables-v2)).

Führen Sie `rebase migrate collections-to-tables --check` in der CI aus, bis `config/` entfernt ist: Dies verifiziert, dass die migrierten Tabellen immer noch dasselbe SQL rendern wie die Collections, aus denen sie hervorgegangen sind, und beendet mit Exit-Code 1, solange eine unter „Review before deploying“ aufgeführte Regel nicht bestätigt wurde – übergeben Sie `--accept-rule-changes`, sobald Sie diese überprüft haben.

### Vor dem Deployment prüfen: Diese Regeln ändern ihre Bedeutung

Der Codemod übernimmt jede Sicherheitsregel unverändert, und jede behält ihren Policy-Namen. Da der 0.30-Compiler jedoch nur die erste gefundene Klausel aus `condition`, `using`, `access: "public"` und `ownerField` gelesen und keinen anderen `access`-Wert gekannt hat, gewähren vier Formen von Regeln nun andere Rechte. Zwei davon erweitern den Zugriff:

| Die Regel | 0.30 gewährte | 0.31 gewährt | |
|---|---|---|---|
| ein reines `access: "authenticated"` (ohne `roles`) | nichts | jedem angemeldeten Aufrufer, einschließlich Gästen | **erweitert** |
| `access` + `check`, keine `condition`, auf `select` / `update` / `delete` / `all` | keine vorhandene Zeile | jede vorhandene Zeile für die `access`-Aufrufer | **erweitert** |
| `access: "authenticated"` + `condition` | jedem, der `condition` erfüllt | nur angemeldeten Aufrufern, die sie erfüllen | schränkt ein |
| `access: "authenticated"` + `check`, auf `insert` | jedem, der eine passende Zeile einfügt | nur angemeldeten Aufrufern | schränkt ein |

Am häufigsten ist die erste. Schreiben Sie `access: "registered"`, um nur Aufrufern mit einem Konto (keinen anonymen Gästen) Zugriff zu gewähren, oder entfernen Sie die Regel, um weiterhin nichts zu gewähren. `access` mit `roles` und eine `condition` als reines Objekt bedeuten weiterhin dasselbe wie zuvor und werden nicht aufgeführt.

Der Codemod verweigert auch Regeln, die der 0.31-Compiler ablehnt: solche, die Klauseln kombinieren, die der Typ `SecurityRule` ausschließt (`access` neben `ownerField`, `using` oder `withCheck`; `ownerField` neben `using`, `withCheck`, `condition` oder `check`; `condition` oder `check` neben `using` oder `withCheck`), sowie solche mit einem ungültigen Wert für `access`, `mode`, `operation(s)` oder `roles` – ein falsch geschriebenes `"restrictive"` wurde früher fälschlicherweise als permissiv kompiliert. Siehe [Sicherheitsregeln](/docs/collections/security-rules/).

### Was sich sonst noch anders verhält

- **Was `GET /api/schema/tables` einer Person mitteilt.** Administratoren und Inhaber von `schema:read` erhalten jede Tabelle. Jeder andere angemeldete Benutzer, einschließlich Gästen, erhält nur die Tabellen, die seine Rollen erreichen können, mit ausschließlich den Regeln, die auf ihn zutreffen können; Relationen zu anderen Tabellen werden verworfen und Hook-Flags vorenthalten. Ein Frontend, das die Beschreibung einer anderen Tabelle als regulärer Benutzer gelesen hat, erhält weniger; `schemaTables: { persons: "all" }` in den Backend-Optionen stellt die vollständige Beschreibung wieder her. Siehe [Endpunkte](/docs/backend/endpoints/#schema).
- **Relationsnamen sind exakt**, und **Big-Integer-Fremdschlüssel sind Zahlen** ([Abschnitt 131](#131-rows-on-the-wire-follow-their-column)).
- **Die Historie wird maskiert ausgeliefert** ([Abschnitt 132](#132-history-is-served-as-reads)).
- **MCP-Tool-Namen und die View-Payload** ändern sich gemeinsam für den gehosteten Konnektor und die Runtimes, die er erreicht ([Abschnitt 122](#122-mcp-tools-are-named-for-tables)).
- **Gezielt eingeschränkt.** Audit-Stamps (`.onCreateNow()`- / `.onUpdateNow()`-Spalten) werden standardmäßig aus den Spalten der Listenansicht des Panels ausgeblendet: Eine migrierte Liste, die `created_at` angezeigt hat, verliert diese Spalte, bis Sie `fields: { created_at: { hidden: false } }` in dessen `customizeTable` schreiben. Der Codemod verweigert mit Begründung Tupel-JSON-Arrays, ein `vector` / `binary` / `reference` innerhalb einer Map, `databaseId` auf einer Postgres-Collection, `isId: "cuid"`, eine alleinige `isId`-Relation und `disableDefaultPolicies: true` ohne Regeln. Eine einspaltige Relation zu einer Tabelle mit einem zusammengesetzten Primärschlüssel wird abgelehnt (schreiben Sie sie mit `rel.via()`). OpenAPI-Tags stammen aus dem Slug, nicht aus dem Anzeigenamen. `rebase schema introspect` lässt Tabellen ohne Primärschlüssel aus und gibt den Grund an (ein Server, der die Datenbank introspektiert, liefert sie weiterhin aus). Ein Plain-View, der `roles` deklariert, führt zu einem Compiler-Fehler; der Codemod entfernt ihn mit einem Hinweis.
- **Was reale Projekte dennoch manuell geändert haben** – Mindestanforderungen an die Toolchain, `({ entity })` in Admin-Code, Includes einer umbenannten Relation, zur Laufzeit geänderte Collection-Objekte, SDK-Aufrufe auf untypisierten Receivern: [Was Projekte manuell geändert haben](/docs/upgrading/0-30-to-0-31-by-hand/).
- **Eine Wiederherstellung in einem anderen Cluster.** Der Stempel der Standard-Admin-Policies hasht Rollen-OIDs; nach einem Dump oder Point-in-Time-Restore in einen anderen Cluster erstellt das erste `db push` oder der erste Start diese Policies einmalig neu – mit denselben Namen und demselben SQL.

### Die Begrifflichkeiten

| Vorher | Jetzt | Wo „collection“ bleibt |
|---|---|---|
| eine Collection in `config/collections/` | eine **Tabelle** (Table) in `backend/schema/` (`defineTable`) | — |
| `properties` | `columns` (`col.*`) und `relations` (`rel.*`) | — |
| `securityRules`, `defaultSecurityRules` | `rls` (erforderlich), `defaultRls` | — |
| `callbacks`, `Property.callbacks` | `hooks`, das `.transform()` einer Spalte | — |
| der `admin`-Block | `customizeTable` in `frontend/src/cms/` | — |
| `data.collection(slug)` | `data.table(slug)` | — |
| was das Admin-Panel darstellt | eine **Collection**: eine Tabelle in der Darstellung des Panels oder eine Firestore-Collection | das CMS: `CollectionPanel`, der Collection Editor, `externalCollections` |

## 108. Tables in `backend/schema` replace `config/collections` — run the codemod first

**Wen dies betrifft:** jedes Projekt mit einem `config/collections/`-Verzeichnis.

**Was sich geändert hat:** Das Backend liest nur noch `backend/schema/index.ts` und die von dort exportierten Ergebnisse von `defineTable`, `defineAuthTable` und `defineView`. `defineCollection`-Dateien werden von nichts mehr gelesen: Die Runtime, jeder CLI-Befehl und die Validierung von `rebase.json` verweigern die Ausführung bei einem Projekt, das noch `config/collections` enthält, und verweisen auf den unten stehenden Befehl. `rls` ist für jede Tabelle erforderlich – eine Liste von Regeln, `"admin-only"` oder `"inherit"` für das vom Index exportierte `defaultRls` – und `disableDefaultPolicies` heißt nun `defaultPolicies: false`.

**Was zu tun ist:**

```bash
rebase migrate collections-to-tables            # or --dry-run first
```

Es wird eine Tabelle pro Collection geschrieben, jede physische Spalte explizit an ihrer ursprünglichen Position (sodass die Schlüsselspalte eines `belongsTo` ausgeschrieben wird), der Index mit `defaultRls` aus `defaultSecurityRules`, ein `customizeTable` für jede Collection, deren Darstellung nicht dem Standard entsprach, und `defineFirestoreCollection`-Dateien für Firestore-Collections. Die Callbacks einer Collection werden zu den `hooks` ihrer Tabelle und den `.transform()`-Methoden ihrer Spalten; die globalen `callbacks`, die `config/index.ts` exportiert hat, sind ein manueller Schritt (Abschnitt 109). Anschließend liest der Befehl das Ergebnis über die neue Pipeline ein: DDL, Policies, Search, Vector, Trigger, Views und das Drizzle-Schema müssen Byte für Byte identisch mit dem sein, was die Collections generiert haben, andernfalls wird jede Datei zurückgesetzt und der Durchlauf bricht mit Exit-Code 1 und dem Diff ab.

Er übernimmt auch Dinge, die früher manuelle Arbeit erforderten:

- **Callbacks, die durch einen Helper erstellt wurden** (`callbacks: softDeleteCallbacks(...)` oder ein importiertes Callbacks-Objekt), werden zu `hooks:` mit demselben Ausdruck, und die Funktionen des Helpers werden dort, wo sie geschrieben sind, in Tabellen-Hook-Props umgewandelt (der Codemod folgt relativen Importen, `const`s, Eigenschaftszugriffen und einem einzelnen `return`). Wenn er dem Helper nicht folgen kann, nennt ein Schritt die zu prüfenden Hooks.
- **Ein Funktions-`storagePath`** migriert zweigeteilt: Die Funktion wird zum `storage.path` der Anpassung, sodass das Panel weiterhin bestimmt, wohin ein Upload geht, und das `path`-Template der Spalte entspricht der Form der Schlüssel, die sie zurückgibt – dem statischen Text ihres Template-Literals mit jedem `${…}` als `{path}` (`` `${owner}/cv` `` → `{path}/cv`). Der Server wendet nun die Limits `maxBytes` und `accept` der Spalte auf jeden Upload an, dessen Schlüssel zu diesem Template passt, nicht nur auf solche, die die Spalte explizit benennen; die Limits sind somit strikter als unter 0.30. Eine Funktion, deren Ergebnis keinen statischen Text enthält, wird abgelehnt: Vergeben Sie vorher einen.
- **Ein 0.30 `policy.existsIn({ collection })`** behält seine Tabelle, und `auth: { collection: usersCollection }` in einem benutzerdefinierten Backend-Einstiegspunkt wird verworfen (das `defineAuthTable` ist die Auth-Tabelle). Eine `collections`-Boot-Option wird zu `schemaDir`.
- **Ein `dynamicProps`-Builder** gibt unter 0.31 eine Feldanpassung mit flachen Schlüsseln zurück (`{ readOnly: true }`, nicht `{ admin: { readOnly: true } }`). Der Codemod schreibt Builder um, deren Rückgaben Objektliterale sind, inline oder in einem geteilten Modul, und listet alle anderen auf.
- **Darstellungslogik, die aus einem geteilten Objekt per Spread eingefügt wurde**, wird in die Anpassung übernommen (`….dynamicProps`); Darstellung, die eine Wrapper-Funktion berechnet, ist ein zu überprüfender Schritt, führt aber nicht zur Ablehnung des Projekts. Ein Komponentenpfad wird relativ zu dem Modul aufgelöst, das ihn geschrieben hat, und ein Wert, der beim Laden von `config/` berechnet wird (`new Date()`, `Date.now()`, ein Auslesen von Umgebungsvariablen), wird als dessen Ausdruck übernommen und niemals auf den Wert des Durchlaufs festgeschrieben.
- **Firestore-Collections, die von einer Funktion erzeugt werden** (ein `getAllFirestoreCollections()`, das die App in das Panel einfügt), werden einzeln in `defineFirestoreCollection` konvertiert, sofern die Datei einer Collection ihr Literal enthält; ein Schritt pro Builder nennt die restlichen und die zu schreibende Form, und ein weiterer nennt Referenzen außerhalb eines konvertierten Literals, die noch `path` verwenden würden.
- **Importe von `config/` über einen Pfad-Alias** (ein `paths`-Eintrag in der tsconfig, ein `resolve.alias` in Vite) werden wie relative Importe umgeschrieben oder aufgelistet, und ein `storageAuthorize`, das `config/index.ts` reexportiert, wird nach `backend/storage.ts` übertragen.
- **Eine zu `<key>Relation` umbenannte Relation** behält ihr Label, ihre Listenspalte und ihren Titel: Die Anpassung benennt den neuen Schlüssel. Code, der sie per Include einbindet, wird nicht automatisch angepasst ([was zu ändern ist](/docs/upgrading/0-30-to-0-31-by-hand/#a-belongsto-key-is-a-column-and-a-relation-can-be-renamed)).

Was nicht exakt übertragen werden kann, wird unter Angabe von Datei und Zeile abgelehnt und es wird nichts geschrieben: eine Collection, die durch Aufruf einer Funktion erstellt wurde, ein Spread oder Accessor, der nicht durchleuchtet werden kann, eine andere Engine als Postgres oder Firestore, eine Ausgabedatei, die bereits mit anderem Inhalt existiert (beiseite schieben oder `--force` nutzen). Ein unsauberer Git-Tree oder ein Projekt außerhalb von Git wird ebenfalls abgelehnt, damit die Migration ein einziges, überprüfbares Diff darstellt. `--json` gibt den vollständigen Bericht für ein Skript oder einen Agenten aus. Siehe [`rebase migrate`](/docs/cli/schema/#rebase-migrate) und [Tabellen](/docs/schema/).

Die generierten Tabellen definieren ihre Spalten so, wie es Drizzles `pg-core` tut – `col.varchar({ length: 160 })`, `col.timestamp({ withTimezone: true })`, `col.text().array()`, `pgEnum(...)`, `` .default(sql`…`) ``, `.generatedByDefaultAsIdentity()` – sodass die Ausgabe keine weiteren Anpassungen benötigt; siehe [Spalten](/docs/schema/columns/). Eine manuell gegen ein 0.31-Pre-Release in der früheren Schreibweise verfasste Tabelle (`col.timestamptz()`, `col.varchar(160)`, `col.array(col.text())`, `col.enum(values, { name })`, `.defaultSql()`, `.identity()`, `.column("…")`) kompiliert nicht mehr: `tooling/scripts/drizzle-sweep.mts` im Rebase-Repository konvertiert sie, indem es nur die Builder-Chains umschreibt, und beweist mit `--verify`, dass jede konvertierte Tabelle zum selben Deskriptor kompiliert (`npx tsx drizzle-sweep.mts --verify backend/schema`).

Der darauffolgende Durchlauf `sdk-calls` schreibt auch Regelquellen um: `existsIn({ collection })` und `membership: { collection }` werden zu `table` (Abschnitt 123); `--skip-sdk-calls` überspringt auch das. Was noch manuell zu tun ist, wird als nummerierte manuelle Schritte ausgegeben, und wenn das Projekt installierte Agent-Skills enthält, ist der letzte Schritt die `rebase skills install`-Zeile, die diese aktualisiert (Abschnitt 128). Ein einfaches `rebase migrate` gibt die Hilfe für beide Unterbefehle aus.

## 109. There is no config package

**Wen dies betrifft:** jedes Projekt – `config/` war ein eigener Workspace.

0.31 liest `config/collections` nicht mehr; es verbietet `config/` jedoch nicht. Der Codemod entfernt, was Rebase gelesen hat – die Collection-Dateien und die Verdrahtung, die nach `backend/` verschoben wird (`resources.ts`, `storage.ts`, `generated/register.ts` und deren Re-Exporte in `config/index.ts`) – und belässt Ihre eigenen Module in `config/` an Ort und Stelle, importierbar wie zuvor: `config/` bleibt ein Workspace-Paket, und das Backend kompiliert weiterhin `../config/**/*`. Nur Importe von Elementen, die entfallen, werden umgeschrieben: Eine von Backend-Code importierte Collection-Datei verweist auf das Tabellenmodul (ein Schritt listet Verwendungen auf, die sie als Objekt lesen); wird sie von Frontend-Code importiert, wird sie zu einem reinen Typ-Import der Tabelle, sofern sie nur als Typ verwendet wird, oder zu einem Schritt, der die Anpassung benennt; ein Helper innerhalb von `config/collections` wird neben den Code kopiert, der ihn benötigt.

**Was sich geändert hat:** Was neben den Collections lag, wandert nach `backend/`:

| Vorher | Jetzt |
|---|---|
| `config/resources.ts` | `backend/resources.ts` |
| `config/storage.ts`, `storageAuthorize` aus `config/index.ts` | `backend/storage.ts` |
| `callbacks` exportiert aus `config/index.ts` | `hooks` exportiert aus `backend/hooks.ts` (`TableHooks`: `table` statt `collection`, `values` statt `row`) |
| `config/generated/register.ts` | `backend/generated/register.ts` |
| `rebase.json` `config`, `usersCollection` | `tables` (Standard `backend/schema`); die Auth-Tabelle ist die mit `defineAuthTable` deklarierte |

Die Runtime liest `storageAuthorize` und `hooks` und nichts anderes aus diesen Modulen; jeder andere Export wird beim Start gemeldet. Das Frontend importiert `backend/**` ausschließlich als Typen – `pnpm check:frontend-backend-imports` verweigert Wert-Importe, die Server-Code an den Browser ausliefern würden.

**Was zu tun ist:** Der Codemod verschiebt `resources.ts`, `storage.ts` sowie die Registrierung und schreibt `rebase.json`, `package.json`, `pnpm-workspace.yaml` und `backend/tsconfig.json` um. Die globalen `callbacks` sind ein ausgegebener manueller Schritt: Verschieben Sie sie manuell nach `backend/hooks.ts` und fügen Sie `hooks.ts` zum `include` von `backend/tsconfig.json` hinzu, damit `tsc` sie überprüft. Führen Sie danach die ausgegebene `git rm`-Zeile aus: `git rm -r config/collections …`, oder `git rm -r config`, falls nichts Eigenes mehr übrig ist.

## 110. Boot options and hooks name tables

**Wen dies betrifft:** ein Backend, das Sie selbst starten (`initializeRebaseBackend`, `createRebaseBackend`), und Code, der Hooks nach dem Start anhängt.

**Was sich geändert hat:**

| Vorher | Jetzt |
|---|---|
| `collections`, `collectionsDir` | `tables`, `defaultRls`, `schemaDir` |
| `callbacks` | `hooks` |
| `auth.collection` | entfernt: das `defineAuthTable` in `tables` |
| `backend.setCollectionCallbacks(slug, cb)` | `backend.setTableHooks(slug, hooks)` |
| Hook-Props `collection`, `row` | `table` (der Deskriptor), `values` |
| `composeCallbacks` | `composeTableHooks` aus `@rebasepro/common` |
| `openRebase({ collections, callbacks })` | `openRebase({ tables, hooks })`, `tables` aus `compileSchema([...])` |
| `OpenedRebase.collections`; die Variable `collections` in `rebase console` | `.tables`; `tables` |

```diff ts
-await initializeRebaseBackend({ app, server, collectionsDir: "./config/collections", callbacks });
+await initializeRebaseBackend({ app, server, schemaDir: path.resolve(__dirname, "../schema"), hooks });
```

Hooks, die an ein an einer Aufrufstelle übergebenes Collection-Objekt angehängt wurden, werden nicht mehr ausgeführt: Der Treiber führt die Hooks der Tabellen aus, die er bedient; hängen Sie sie daher mit `setTableHooks` an.

**Was zu tun ist:** `rebase migrate sdk-calls` schreibt `setCollectionCallbacks` um, passt die Hook-Props an und listet jedes Backend-Optionsobjekt auf, das manuell aktualisiert werden muss. Ein Skript, das die Daten öffnet, kompiliert seine Tabellen:

```diff ts
-const rebase = await openRebase({ databaseUrl, collections, callbacks });
+const rebase = await openRebase({ databaseUrl, tables: compileSchema([products, orders]), hooks });
```

Siehe [Skripte](/docs/backend/scripts/#openrebase). Siehe [Backend-Übersicht](/docs/backend/) und [Globale Hooks](/docs/backend/hooks/).

## 111. The admin panel renders the tables the server serves

**Wen dies betrifft:** jedes Frontend, das `<RebaseCMS>` einbindet.

**Was sich geändert hat:** `<RebaseCMS collections>` gibt es nicht mehr. Das Panel zeigt jede Tabelle an, die das Backend unter `GET /api/schema/tables` bereitstellt, ohne eine Datei pro Tabelle, gefolgt von `externalCollections` (Firestore). `tableCustomizations` nimmt die `customizeTable`-Objekte aus `frontend/src/cms/` entgegen. Das Vite-Collections-Plugin und `virtual:rebase-collections` wurden entfernt. `CollectionsProvider` nimmt dieselben drei Eingaben entgegen (`tableCustomizations`, `externalCollections`, `tables`).

```diff tsx
-import { collections } from "virtual:rebase-collections";
-<RebaseCMS collections={collections}/>
+import { postsCms } from "./cms/posts";
+<RebaseCMS tableCustomizations={[postsCms]}/>
```

**Was zu tun ist:** Der Codemod schreibt `frontend/src/cms/index.ts`, das `tableCustomizations` (und `externalCollections`) exportiert, und bindet es in der `App.tsx` eines Scaffolds selbst ein; eine nicht erkannte `App.tsx`, das Plugin in `vite.config.ts` und die virtuelle Moduldeklaration werden als manuelle Schritte ausgegeben. Siehe [Eine Tabelle anpassen](/docs/frontend/customize-table/).

## 112. Bundle format 3; format-2 bundles are refused

**Wen dies betrifft:** jedes Deployment eines gebauten Bundles – selbst gehostet mit dem Runtime-Image oder auf Rebase Cloud.

**Was sich geändert hat:** Das Schema eines Bundles ist `entry.tables`, neben `entry.resources`, `entry.storage` und `entry.hooks`; `bundleFormat` ist 3 und der Runtime-Vertrag 2. Ein Format-1- oder Format-2-Bundle enthält `config/collections`, wofür eine 0.31-Runtime keine Leselogik mehr besitzt. Daher verweigert sie den Start mit dem Hinweis auf den Codemod in der Fehlermeldung, anstatt die Datenbank zu introspektieren und eine abweichende API bereitzustellen.

**Was zu tun ist:** Migrieren Sie den Quellcode, führen Sie dann `rebase build` aus und deployen Sie. Auf Rebase Cloud baut das Deployment des migrierten Repositorys dieses neu. Siehe [Runtime und Bundles](/docs/architecture/runtime-and-bundles/).

**Auf Rebase Cloud läuft ein Projekt auf 0.30 weiter, kann jedoch nicht deployt werden.** Die Plattform liefert weiterhin das vorhandene Bundle aus, und ihre Runtime-Updates stoppen dort (die Konsole weist darauf hin), sie akzeptiert jedoch nur noch Format 3: Ein Deploy über eine 0.30-CLI lädt das gesamte Bundle hoch und wird dann mit `BUNDLE_FORMAT_TOO_OLD` abgelehnt. Der Weg nach vorn besteht bei jedem Projekt aus denselben drei Befehlen:

```bash
pnpm exec rebase upgrade --to latest
rebase migrate collections-to-tables
rebase cloud deploy
```

Eine CLI nach 0.32.0 bricht früher ab, bevor sie etwas baut oder hochlädt: `rebase build` und `rebase cloud deploy` bei einem Projekt, dessen Tabellen noch in `config/collections` liegen, stoppen mit der Nennung des Codemods; ein `--bundle-dir`, das ein Format-2-Bundle enthält, wird mit „Nothing was uploaded“ abgelehnt, und `rebase upgrade` nennt den Codemod als nächsten Schritt anstelle von `rebase build`. (Das eigene `rebase upgrade` von 0.30 endet noch mit dem Hinweis „Run `rebase build`“; der Build, auf den es verweist, ist derjenige, der stoppt.)

## 113. The schema version is computed from tables (`v2:`)

**Wen dies betrifft:** jede Datenbank, die von einer Runtime vor 0.31 bereitgestellt wurde, und jedes generierte SDK.

**Was sich geändert hat:** Die Schema-Version hasht die kompilierten Tabellendeskriptoren und beginnt mit `v2:`. Eine mit `v1:` gestempelte Datenbank meldet die Modelländerung einmalig – das Boot-Log und `rebase doctor` weisen darauf hin und erklären, wie neu gestempelt wird – und jedes generierte SDK wird einmalig als veraltet gemeldet.

**Was zu tun ist:** Einmalig mit der neuen Runtime provisionieren: Starten Sie den Prozess, der das Schema verwaltet, oder führen Sie `rebase db push` aus. Stempeln Sie bei gesetztem `REBASE_REQUIRE_SCHEMA_MATCH=true` neu, bevor Sie die anderen Prozesse aktualisieren. Generieren Sie das SDK neu.

**Was sich geändert hat:**

| Vorher | Jetzt |
|---|---|
| `NO_COLLECTIONS` (404) | `NO_TABLES` |
| `COLLECTION_READ_ONLY` (405) | `TABLE_READ_ONLY` |

## 115. The SDK addresses a table: `data.table(slug)`

**Wen dies betrifft:** jeden Client, jede Funktion, jeden Cron-Job, jeden Hook und jedes Skript, das eine Tabelle über ihren Slug anspricht oder das generierte Dictionary übergibt.

**Was sich geändert hat:**

| Vorher | Jetzt |
|---|---|
| `data.collection(slug)` | `data.table(slug)` |
| `createRebaseClient({ collections: collectionsDictionary })` | `createRebaseClient({ tables: tablesDictionary })` |
| generiertes `CollectionName`, `CollectionsDictionary` | `TableName`, `TablesDictionary` |
| Batch `{ op, collection }` (SDK und `POST /api/data/_batch`) | `{ op, table }` |
| `CollectionClient`, `SDKCollectionClient`, `CollectionAccessor`, `CollectionTrashAccessor` | `TableClient`, `SDKTableClient`, `TableAccessor`, `TableTrashAccessor` |
| Offline `maxCachedRowsPerCollection`, `maxCachedQueriesPerCollection` | `…PerTable` |
| reservierter Accessor `<name>Collection`; `collectionCollection` | `<name>Table`; die Tabelle `collection` heißt `collection` |

```diff ts
-const { data } = await client.data.collection("posts").find();
+const { data } = await client.data.table("posts").find();
```

Typisierte Accessoren (`client.data.posts`) bleiben unverändert.

**Was zu tun ist:** Der Codemod führt `rebase migrate sdk-calls` über Ihren Code aus – führen Sie ihn bei einem bereits migrierten Projekt separat aus – und anschließend `rebase generate-sdk`. Ein `.collection(`-Aufruf, dessen Receiver nicht das SDK ist, wird unverändert belassen und aufgelistet. Siehe [Typisiertes SDK](/docs/sdk/).

## 116. CLI flags: `--schema-dir`, not `--collections`

**Wen dies betrifft:** Skripte und CI-Schritte, die die CLI mit einem Schema-Pfad aufrufen.

**Was sich geändert hat:** `--collections` / `-c` werden bei jedem Befehl, der das Schema liest, mit einem Hinweis auf den Codemod in der Fehlermeldung abgelehnt (`generate-sdk` ignoriert ein überflüssiges `--collections-dir`); `--schema-dir` gibt ein anderes Schema-Verzeichnis als `backend/schema` an. `rebase schema introspect` schreibt `defineTable`-Dateien nach `backend/schema/` – `--output` existiert nicht mehr. `REBASE_STRICT_COLLECTION_CONFIG` wird nicht mehr ausgewertet: Ein Schema, das nicht kompiliert, verhindert immer den Start.

**Was zu tun ist:** Ersetzen Sie die Flags. Siehe [CLI](/docs/cli/) und [Schema-Generierung](/docs/cli/schema/).

## 117. The schema editor edits `backend/schema` with `TablePatch`

**Wen dies betrifft:** Code, der die Schema-Editor- oder Live-Schema-Routen aufruft, sowie Deployments, die Variablen für die Live-Bearbeitung setzen.

**Was sich geändert hat:** `/api/admin/schema-editor/collection/save`, `collection/delete`, `property/save` und `property/delete` sind entfernt. Der Editor bedient `GET /tables`, `POST /preview` und `POST /apply`, und das `/plan` sowie `/apply` der Live-Schema-Bearbeitung nehmen `{ patches: TablePatch[] }` anstelle einer Collection oder eines Patches davon entgegen. `REBASE_LIVE_SCHEMA_COLLECTIONS_PATH` wird beim Start abgewiesen: Es heißt nun `REBASE_LIVE_SCHEMA_PATH` (Standard `backend/schema`), und `liveSchema.repository.collectionsPath` heißt `schemaPath`. Darstellungseinstellungen sind niemals Schema-Änderungen: Sie werden als UI-Präferenzen gespeichert (`/api/admin/ui-config`). Eine Bearbeitung, deren Datei sich auf der Festplatte geändert hat, nachdem der Edit vorbereitet wurde (Speichern in der IDE, ein anderer Prozess), antwortet mit 409 `SCHEMA_EDIT_STALE_FILE` und schreibt nichts; zuvor war dies ein 400 `SCHEMA_EDIT_REFUSED`.

**Was zu tun ist:** Benennen Sie die Variable um; schreiben Sie Aufrufer der Routen so um, dass sie `TablePatch`-Edits senden, und laden Sie bei `SCHEMA_EDIT_STALE_FILE` neu. Siehe [Live-Schema-Bearbeitung](/docs/backend/live-schema-editing/).

## 118. A component slot is a component

**Wen dies betrifft:** Anpassungen, die eine React-Komponente über einen String-Pfad oder einen Lazy-Thunk `() => import(…)` angegeben haben.

**Was sich geändert hat:** Das `Field` / `Preview` / `Filter` eines Feldes, Collection-`Actions`, `entityViews[].Builder`, `collectionViews[].Builder`, `formView.Builder` und Komponenten-Overrides nehmen die Komponente selbst entgegen. `ComponentRef`, `ComponentLike`, `LazyComponentRef` und `isLazyComponentRef` (`@rebasepro/types`), `asComponentRef` und `asReactComponent` (`@rebasepro/cms-types`) sowie `resolveComponentRef` / `useResolvedComponent` (`@rebasepro/app`) wurden entfernt. `customizeTable` lehnt Strings oder Thunks mit der Meldung „imported by value“ ab.

**Was zu tun ist:** Importieren Sie die Komponente in der Datei `frontend/src/cms/` und übergeben Sie sie direkt. Siehe [Benutzerdefinierte Felder](/docs/frontend/custom-fields/).

Der Codemod führt dies für jeden String-Pfad durch und vermerkt jeden einzelnen, da eine importierte Komponente nun typgeprüft an ihren Slot übergeben wird, wo vorher nie eine Typprüfung für Pfade stattfand. Ein `Preview`, das `customProps?: MyProps` deklariert, schlägt im `tsc` Ihres Frontends fehl: Der Slot übergibt `customProps` als `unknown`, da nichts die `customProps` eines Feldes an die Komponente koppelt, die sie liest. Verwenden Sie `customProps?: unknown` und grenzen Sie den Typ innerhalb der Komponente ein.

## 119. Panel preferences are UI preferences

**Wen dies betrifft:** Code, der `UserConfigurationPersistence` implementiert.

**Was sich geändert hat:** Wie ein Benutzer eine Tabelle in der Größe angepasst oder neu angeordnet hat, ist ein `UiTablePreferences`-Delta: `getTablePreferences` / `saveTablePreferences` ersetzen `getCollectionConfig` / `onCollectionModified`, und der partielle Collection-Config-Typ, den dies entgegennahm, wurde entfernt. Der Browser-Store hält diese unter `table_preferences::<slug>` vor und ignoriert, was ein älteres Panel gespeichert hat, sodass die Spaltenbreiten und Ansichtsmodi jedes Benutzers einmalig zurückgesetzt werden. `userSelect` auf einem Feld ist entfallen: Eine `.userId()`-Spalte dient als Benutzerauswahl.

Die Studio-Bridge folgt diesem Schema: `StudioSchemaEditing.updateCollection` heißt `applyTablePatches(slug, patches)`, und der Collection Editor sendet `{ patches }` an den Schema-Editor.

**Was zu tun ist:** Portieren Sie eine eigene Persistenz auf die beiden Methoden und ein eigenes `StudioSchemaEditing` auf `applyTablePatches`.

## 120. MongoDB is retired

**Wen dies betrifft:** ein Projekt, das auf `@rebasepro/server-mongo` basiert oder `database(…, { engine: "mongodb" })` deklariert.

**Was sich geändert hat:** Das Paket wurde entfernt, ebenso wie die Mongo-Collection-Typen und der Rest des Mongo-Modells. Postgres ist die einzige Server-Engine: Eine Server-Transportquelle auf einer anderen Engine verweigert den Start unter Nennung der Engine.

**Was zu tun ist:** Migrieren Sie die Daten nach Postgres. Es gibt keinen migrationsinternen Pfad innerhalb von Rebase.

## 121. Firestore collections live in the frontend

**Wen dies betrifft:** ein Hybrid-Projekt mit `engine: "firestore"`-Collections.

**Was sich geändert hat:** Eine Firestore-Collection ist eine CMS-Quelle, die der Browser direkt liest: `defineFirestoreCollection` aus `@rebasepro/firebase` in `frontend/src/cms/`, übergeben an `<RebaseCMS externalCollections>`. Eine Referenz zwischen Firestore und einer Postgres-Tabelle wird als ID des Ziels gespeichert, und eine Firestore-Referenz, deren `path` gleichzeitig ein Postgres-Slug ist, zielt nun auf die Postgres-Tabelle ab.

**Was zu tun ist:** Der Codemod schreibt die `defineFirestoreCollection`-Dateien. Verweisen Sie auf eine Firestore-Collection über den Slug dieser Collection. Siehe [Firebase](/docs/frontend/firebase/).

## 122. MCP tools are named for tables

**Wen dies betrifft:** Prompts, Skripte und Allowlisten, die MCP-Tools benennen.

**Was sich geändert hat:** Remote-`/mcp`: `list_collections`, `describe_collection`, `query_collection`, `show_collection`, `count_documents`, `aggregate_documents`, `get_document`, `create_document`, `update_document`, `delete_document` → `list_tables`, `describe_table`, `query_table`, `show_table`, `count_rows`, `aggregate_rows`, `get_row`, `create_row`, `update_row`, `delete_row`; das Argument `collection` heißt `table`, und `show_app` / `save_app` akzeptieren `tables`. Der lokale Server: `list_documents` → `query_table`, `get_document` → `get_row`, `create_document` → `create_row`, `update_document` → `update_row`, `delete_document` → `delete_row`; `rebase_schema_plan` nimmt `patches` entgegen; Ressourcen lauten `rebase://tables/{name}`. Die MCP-Apps-View-Payload hat die Version 3: für den Aufrufer geschwärzte Tabellendeskriptoren, Pro-Tabelle-Berechtigungen und die UI-Präferenzen jedes Aufrufers unter `preferences` (`file`, `workspace`, `user`; ein API-Key hat keine User-Ebene), wobei Blöcke und Seeds `table` benennen. Die View `collection-table` wurde entfernt. `list_tables` besitzt keinen `title`; `describe_table` fügt `primaryKey`, `relations`, das `rls` des Aufrufers, `title` und `presentation` hinzu.

**Was zu tun ist:** Benennen Sie diese um. Die View und der Server müssen dieselbe Payload-Version sprechen: Ein gehosteter Konnektor und die von ihm erreichten Runtimes werden gemeinsam aktualisiert, und eine im Projekt gebaute MCP-View wird mit den 0.31-Paketen neu gebaut. Siehe [MCP-Tool-Referenz](/docs/ai/mcp-tool-reference/) und [Remote-MCP](/docs/ai/remote-mcp/).

## 123. The rule vocabulary says `table`

**Wen dies betrifft:** Regeln, die `policy.existsIn` oder einen Membership-Tenanten verwenden, sowie Regeln, die `access` mit anderen Klauseln kombinieren.

**Was sich geändert hat:** `policy.existsIn({ collection, where })` heißt `existsIn({ table, where })`, und `tenant.from.membership.collection` heißt `membership.table`; Policy-Namen ändern sich nicht. Vier Regelformen gewähren nun andere Berechtigungen, zwei davon mehr ([die Tabelle oben](#review-before-deploying-these-rules-change-meaning)): Ein reines `{ access: "authenticated" }`, das früher nichts gewährte, lässt nun jeden angemeldeten Aufrufer zu, und die Verbindungstabellen (Junctions) einer solchen Tabelle erhalten ihre Edge-Write-Policies. Regeln, die Klauseln kombinieren, die der Typ `SecurityRule` ausschließt, oder die ungültige Werte für `access`, `mode`, `operation` oder `roles` enthalten, werden abgelehnt.

**Was zu tun ist:** Der Codemod benennt die Schlüssel um, lehnt ungültige Regeln unter Angabe von Datei und Zeile ab und listet die Regeln, die ihre Bedeutung ändern, unter „Review before deploying“ auf. Behalten Sie jede einzelne bei, ändern Sie sie in `access: "registered"` (angemeldete Aufrufer mit Konto) oder entfernen Sie sie. Prüfen Sie anschließend `rebase db push --dry-run` und `rebase doctor --policies` gegen Ihre Datenbank.

## 124. Studio reads the tables from the server

**Wen dies betrifft:** Studio, das auf ein Backend vor 0.31 gerichtet ist, sowie Studio-JS-Konsolenskripte.

**Was sich geändert hat:** Jedes schema-bewusste Tool liest `GET /api/schema/tables`; bei einer Runtime ohne diesen Endpunkt wird ein Upgrade-Hinweis angezeigt. Die deklarierte Seite des RLS-Editors entspricht dem, was der Server kompiliert hat. Ein JS-Konsolenskript erhält `context.tables` (zuvor `context.collections`).

**Was zu tun ist:** Aktualisieren Sie die Runtime zusammen mit dem Panel. Siehe [Studio](/docs/studio/).

## 128. The agent skill `rebase-collections` is `rebase-tables`

**Was sich geändert hat:** Der Skill, der das Datenmodell vermittelt, heißt nun `rebase-tables`: Erstellung von Tabellen, Spalten, Relationen, `rls`, Hooks und der CMS-Schicht darüber. `rebase skills install` entfernt die alte `rebase-collections`-Kopie, auch aus Installationen vor der Einführung des Skills-Manifests, und behält jedes selbst erstellte Verzeichnis dieses Namens bei.

## 129. `useJsonCollectionsConfigController` is removed

**Wen dies betrifft:** ein Projekt, das Collection-Definitionen über `@rebasepro/cms` als JSON gespeichert hat.

**Was sich geändert hat:** `useJsonCollectionsConfigController` wurde entfernt, zusammen mit seinem Optionstyp und der dahinterliegenden JSON-Store-Klasse. Das Schema einer Tabelle liegt in `backend/schema`, und wie das Panel sie darstellt, wird in UI-Präferenzen gespeichert: `frontend/src/cms/ui-config.json` in der Entwicklung, die Tabelle `rebase.ui_preferences` in einem Deployment.

**Was zu tun ist:** Deklarieren Sie die Tabellen mit `defineTable` (`rebase migrate collections-to-tables` schreibt sie anhand der Collection-Definitionen) und übergeben Sie die `uiConfig` des Scaffolds an `<RebaseCMS>`. Siehe [Eine Tabelle anpassen](/docs/frontend/customize-table/#customizations-ui-configjson-and-preferences).

## 130. `rebase build` refuses a frontend without `rebaseBackendGuard()`

**Wen dies betrifft:** jedes Projekt mit einem Frontend.

**Was sich geändert hat:** Das Frontend darf `backend/` ausschließlich als Typen importieren. Ein Wert-Import würde Server-Code – Hooks und alle darin gelesenen Secrets – in das Browser-Bundle einbringen. `rebaseBackendGuard()` aus `@rebasepro/app/vitePlugin` lässt `vite build` und `vite dev` fehlschlagen, wenn ein Frontend-Modul nach `backend/` auflöst, und nennt den Importer, den Import und die Datei nach Auflösung von Aliasen, tsconfig-Pfaden, Paket- und absoluten Auflösungen, Globs, `?raw`, Re-Exporten und dynamischen Importen. `rebase build` sowie der Frontend-Build, den `rebase cloud deploy` ausführt, verweigern die Ausführung bei einem Frontend, dessen Vite-Konfiguration dies nicht nutzt; `rebase dev` gibt eine Warnung aus; `rebase verify` meldet `cms-backend-guard-missing`.

**Was zu tun ist:** Der Codemod fügt dies zur `frontend/vite.config.ts` eines Scaffolds hinzu und gibt die Zeilen für jede andere Konfiguration aus:

```diff ts
+import { rebaseBackendGuard } from "@rebasepro/app/vitePlugin";

 export default defineConfig({
-    plugins: [react()],
+    plugins: [react(), rebaseBackendGuard()],
 });
```

Wandeln Sie anschließend jeden Wert-Import von `backend/` in ein `import type` um.

## 131. Rows on the wire follow their column

**Wen dies betrifft:** Clients, die Fremdschlüssel auslesen oder Relationen benennen, sowie Schreibvorgänge, die generierte Spalten oder partielle JSON-Objekte senden.

**Was sich geändert hat:** Werte durchlaufen beim Senden den Codec ihrer Spalte und beim Empfangen die Regeln der Spalte.

- Eine von einer Relation generierte `bigint`- oder `numeric`-Fremdschlüsselspalte, die Postgres als Text zurückgibt, wird in REST, im SDK und im Admin-Panel als **Zahl** ausgeliefert. Explizit deklarierte numerische Schlüssel waren dies bereits.
- Die **Elemente eines nativen Arrays werden entsprechend ihrem Skalartyp ausgeliefert**, in REST, im SDK, über Sockets und im Treiber:

  | Spalte | 0.30 lieferte | 0.31 liefert |
  |---|---|---|
  | `timestamptz[]` | `["2026-01-02 11:00:00+01"]` | `["2026-01-02T10:00:00.000Z"]` |
  | `numeric[]` (ein Treiber, der ohne die Boot-Zeit-Einstellung für Numerics geöffnet wurde: Tests, Skripte) | `["1.50", "2.25"]` | `[1.5, 2.25]` |
  | `bigint[]` mit einem Null-Element | `[1, 0, 3]` | `[1, null, 3]` |
  | `date[]`, `timestamptz[]` oder ein Enum-Array mit einem Null-Element | `["2026-01-02", "NULL"]` | `["2026-01-02", null]` |

  `date[]`, `time[]`, `text[]`, `uuid[]`, `boolean[]`, `integer[]` und `double precision[]` werden wie bisher ausgeliefert. Was gespeichert wird, ändert sich nicht: Eine gelesene und wieder zurückgespeicherte Zeile speichert dasselbe Array.
- Eine in `include`, einem Filter oder einer Sortierung angegebene Relation muss ihren **exakten Namen** tragen. Die Fallbacks mit dem Slug und der snake_case-Schreibweise wurden entfernt.
- Eine generierte Spalte wird beim Schreiben abgelehnt und aus dem OpenAPI-Eingabeschema weggelassen.
- Ein Pflichtfeld innerhalb eines JSON-Objekts wird erzwungen; `$inc` und Array-Elemente auf einer Integer-Spalte müssen ganze Zahlen sein.

**Was zu tun ist:** Lesen Sie Fremdschlüssel als Zahlen aus, wo Sie bisher Strings verglichen haben, parsen Sie `timestamptz[]`-Elemente als RFC 3339, behandeln Sie ein Null-Array-Element als `null` und schreiben Sie Relationsnamen genau so, wie die Tabelle sie deklariert (ihre `relations`-Schlüssel). Senden Sie keine generierten Spalten mehr.

## 132. History is served as reads

**Wen dies betrifft:** Leser von Verlaufs-Snapshots und jeden, der einen `DataDriver` implementiert.

**Was sich geändert hat:** Verlaufseinträge werden wie reguläre Lesevorgänge ausgeliefert: zuerst Feldzugriff, dann `afterRead` (global, Tabelle, Spalte). Eine durch einen Hook oder ein `.transform({ afterRead })` maskierte Spalte ist in jedem Snapshot maskiert; eine Spalte, die der Aufrufer nicht lesen darf, wird vorenthalten und aus `changed_fields` weggelassen; Schlüssel gelöschter Spalten werden vorenthalten, und ein Revert schreibt niemals eine Spalte, die der Aufrufer nicht lesen darf. Ein Hook, der bei einem alten Snapshot einen Fehler wirft, lässt die Anfrage fehlschlagen. 0.30 lieferte die gespeicherten Rohwerte aus, daher sollte jedes Projekt mit Verlauf und Maskierungs-Hooks aktualisiert werden.

Ein Eintrag enthält die Zeile so, wie `GET /api/data/<table>/<id>` sie ohne `include` liest: einfache Werte, ein `belongsTo` als dessen Fremdschlüssel. Ein Eintrag, den eine ältere Version mit dem ViewModel des Admin-Panels aufgezeichnet hat, wird als diese Zeile ausgeliefert und zurückgerollt: eine `{ "__type": "date", "value" }`-Hülle als Wert, eine `{ "__type": "relation" }`-Referenz einer besitzenden Relation als Fremdschlüssel unter dem Eigennamen des Schlüssels und jede andere Referenz als Schlüssel der verknüpften Zeile. 0.30 lieferte diese Referenzen wie gespeichert aus.

Ein Treiber stellt den Verlauf über `DataDriver.serveStoredRows(path, rows)` innerhalb der schreibgeschützten Transaktion des Aufrufers bereit; die Verlaufsrouten antworten mit 501 bei einem Treiber, der dies nicht unterstützt, sodass der Verlauf niemals unmaskiert ausgeliefert wird.

**Was zu tun ist:** Für den mitgelieferten Postgres-Treiber ist nichts zu tun. Ein benutzerdefinierter Treiber implementiert `serveStoredRows`. Siehe [Verlauf](/docs/backend/history/).

## 135. `@rebasepro/types` and `@rebasepro/common` drop the collection model from their roots

**Wen dies betrifft:** Code, der Collection- oder Eigenschaftstypen, Admin-Panel-Helper oder den Lift aus `@rebasepro/types` oder `@rebasepro/common` importiert – benutzerdefinierte Felder, Custom Views, Plugins, Tests mit Collection-Fixtures – sowie benutzerdefinierte Treiber, die die Registry implementieren.

**Was sich geändert hat:** Die Kernel-Pakete beschreiben ausschließlich Tabellen. Was eine Collection in der Darstellung des Admin-Panels beschreibt, liegt in `@rebasepro/cms-types`:

- **Typen**, die aus `@rebasepro/types` verschoben wurden: `CollectionConfig`, `PostgresCollectionConfig`, `FirebaseCollectionConfig`, `AnyCollectionConfig`, jedes `…Property` (`StringProperty`, `NumberProperty`, `ArrayProperty`, …) und `Properties`, `CollectionCallbacks` und deren Hook-Props, die Relationsarten aus 0.30 und ihre `Resolved…`-Formen, `CollectionIndex`, die Chip-Farben (`ColorScheme`, `ColorKey`, …), `FieldAccess`, `EnumValues`.
- **Helper**, die aus `@rebasepro/common` verschoben wurden: die collection-spezifischen Policy-Helper (`policyToPostgres`, `compileRulePolicies`, `getEffectiveSecurityRules`, `getGeneratedPolicyNames`, …), `CollectionRegistry`, `resolveCollectionRelations`, `resolveRelation`, `getTableName`, `findRelation`, `rowToViewModel`, `resolvePrimaryKeys`, die Feldzugriffsansicht einer Eigenschaft (`effectiveAccess`, `canReadField`, `canWriteField`), `evaluateCondition`, `canEditEntity`, `resolveProperty`, `getDefaultValuesFor`, `getSubcollections`, `getCopyValues`, `enumToObjectEntries`. Eine aus einem einfachen Ausdruck kompilierte Regel verwendet `compilePolicyExpression(expr)` aus `@rebasepro/common`.
- **`composeCallbacks`** komponiert die Callbacks einer Collection für das Panel und wurde nach `@rebasepro/cms-types` verschoben; `@rebasepro/server` reexportiert dies nicht mehr. Backend-Code komponiert die Hooks einer Tabelle mit `composeTableHooks` aus `@rebasepro/common`, und der Codemod führt einen Backend-Import von `composeCallbacks` als entsprechenden manuellen Schritt auf.
- **`defineCollection`** wurde aus `@rebasepro/common` und `@rebasepro/cms-types` entfernt: Deklarieren Sie die Tabelle mit `defineTable` in `backend/schema` und passen Sie sie mit `customizeTable` in `frontend/src/cms` an; eine Firestore-Collection ist `defineFirestoreCollection` aus `@rebasepro/firebase`.
- **Der Accessor des Admin-Panels und seine Typen**: `Entity`, `EntityValues`, `TableAccessor`, `TableTrashAccessor`, `FindResponse`, `QueryBuilderInterface`, `RebaseData` und `AuthState` haben `@rebasepro/types` verlassen; `buildRebaseData`, `wrapAsEntityData`, `buildRoutedRebaseData`, `EntityDataOptions`, `QueryBuilder`, `RelationRef` und `createRelationRef` haben `@rebasepro/common` verlassen. Alle werden nun aus `@rebasepro/cms-types` importiert. Die eigene Datenschicht des SDK – `buildSdkData`, `createDriverTableRows`, `buildRoutedSdkData`, in `@rebasepro/common` – liefert Zeilen direkt aus und gibt zurück, was sie zuvor zurückgegeben hat.
- **`EntityDataOptions.resolveCollection`** wird durch `primaryKeysOf`, `viewModelOf`, `storedValuesOf` und `viewModelSourceOf` ersetzt; `collectionEntityDataOptions(resolveCollection, { resolveDataPath, resolveAccessor })` aus `@rebasepro/cms-types` baut diese auf.
- **Der Migrations-Lift** (`collectionsToTableDefs`, `collectionToTableDef`, `LiftNote`, `LiftResult`, `LiftOptions`) wurde nach `@rebasepro/common/migrate` verschoben, neben eine eingefrorene Kopie des Collection-Modells aus 0.30 (`Legacy…`-Typen) und `defineLegacyCollection`.
- **Ebenfalls aus den Kernel-Roots entfernt** und vom Codemod jeweils als manueller Schritt aufgelistet: die Collection-Patch-API von `@rebasepro/types` (`CollectionPatch`, `CollectionPatchOp`, `applyCollectionPatch`, `collectionPatchProblems`, `isCollectionPatch`, `nestCollectionPatchPaths` → `TablePatch`), deren Collection-JSON-Helper (`diffCollections`, `diffJsonValues`, `toCollectionJson`, `RUNTIME_ONLY_COLLECTION_KEYS`, `runtimeOnlyKeyIn`), die aus der Mongo-Ära stammenden `DocumentAdmin`, `isDocumentAdmin` und die Fähigkeit `supportsDocumentAdmin`, sowie `RebaseProjectContract.collectionSlugs` / `.collections` / `.generatedAt` (`/api/meta/contract` liefert `tables` aus); aus `@rebasepro/common`: `buildTenantSecurityRule` → `tenantSecurityRule`, `defaultPoliciesDisabled` → `tableDefaultPoliciesDisabled`, `restoresSoftDeletedRow` → `isSoftDeleteRestore`, `softDeleteFieldOf` → `softDeleteColumn`, `getJunctionConfigForRelation` → `resolveTableJunctions`, und `isRelationRequired`, `relationDeclaringProperty`, `requireCallbackCollection` ohne Nachfolger (lesen Sie den `TableDescriptor` aus).
- **Die Registry eines Treibers** ist ein `TableRegistryInterface` (zuvor `CollectionRegistryInterface`): `setGlobalHooks?` und `setTableHooks?` ersetzen `getGlobalCallbacks` / `setGlobalCallbacks?`. `globalHooksAsCallbacks`, `resolveDriftCheckName` und `PENDING_TABLE_FEATURES` wurden entfernt.

**Was zu tun ist:** `rebase migrate sdk-calls` (Teil von `collections-to-tables`) verschiebt jeden unten stehenden Import in sein neues Paket – zusammengeführt in einen bereits bestehenden Import dieses Pakets in der Datei, wobei `import type`, Inline-`type` und `as`-Aliase beibehalten werden – und fügt das Paket zu den Abhängigkeiten des importierenden Workspace-Pakets hinzu; führen Sie danach `pnpm install` aus. Ein Import eines entfernten Namens, ein Namespace-Import (`import * as`), ein `export *`, ein dynamisches `import()` oder ein `require()`, das einen verschobenen Namen verwendet, wird als nummerierter manueller Schritt ausgegeben. Ein Test, der Collection-Literale als Fixtures vorhält, typisiert diese mit den `Legacy…`-Typen und führt den Lift über `@rebasepro/common/migrate` durch.

### Verschobene Importe

Jeder Name, den 0.31 in ein anderes Paket verschoben oder entfernt hat, ist unter [In 0.31 verschobene Importe](/docs/upgrading/0-30-to-0-31-imports/) aufgeführt, inklusive Hinweisen, was für die einzelnen entfernten Namen zu schreiben ist. ## 136. The Postgres driver and the socket's one-shot reads return the REST row

**Wen dies betrifft:** Funktionen oder Plugins, die über `requireDriver(c)` / `getDriver(c)` lesen, Code, der die `FETCH_COLLECTION`- / `FETCH_ONE`-Frames des Sockets sendet, und Code, der `{ __type }`-Objekte aus einer Antwort ausliest.

**Was sich geändert hat:** Es gibt nur noch eine einzige Rückgabeform beim Lesen. `fetchCollection` und `fetchOne` auf dem Postgres-Treiber – worüber `requireDriver(c)` einer Funktion, Plugins, die One-Shot-Frames des Sockets, MCP und der RLS-Simulator lesen – geben das zurück, was `GET /api/data/<table>` zurückgibt:

| Wert | 0.30 Treiber-Lesevorgang | 0.31 |
|---|---|---|
| ein Zeitstempel | `{ "__type": "date", "value": … }` | ein RFC 3339-String |
| ein `belongsTo` | `{ "__type": "relation", "id", "path" }` unter dem Namen der Relation | der Fremdschlüssel unter seinem eigenen Schlüssel (`authorId`) |
| eine verknüpfte Zeile | jede von `fetchOne` geladene Relation | nur eine Relation, die `include` benennt, als eigene Zeile des Ziels |
| ein Vektor, ein `bytea` | `{ "__type": "Vector" }`, eine Data-URL | wie von REST ausgeliefert |

`FetchOneProps` nimmt `include` entgegen (`ListenOneTarget` wurde entfernt: verwenden Sie `FetchOneProps`). `rebase.data`, `context.data` und das SDK gaben diese Form bereits zurück und bleiben unverändert.

`@rebasepro/client` liest REST-Bodies und Socket-Frames als einfaches JSON: Ein Wert mit einem `__type`-Schlüssel wird nicht mehr in ein `Date`, `EntityReference`, `EntityRelation`, `GeoPoint` oder `Vector` umgewandelt, und ein JSON-Dokument, das einen `__type`-Schlüssel enthält, wird wie gespeichert zurückgegeben.

**Was zu tun ist:** Lesen Sie die reine Zeile aus: Parsen Sie Daten aus ihren Strings, lesen Sie einen Fremdschlüssel über seinen eigenen Schlüssel aus und übergeben Sie `include` für jede Relation, die Sie auslesen:

```diff ts
-const article = await requireDriver(c).fetchOne({ path: "articles", id });
-const authorId = article?.author.id;      // a { __type: "relation" } ref
+const article = await requireDriver(c).fetchOne({ path: "articles", id, include: ["author"] });
+const authorId = article?.authorId;
```

## 138. The backend accepts the values the REST API documents, and nothing else

**Wen dies betrifft:** Clients, die eine To-One-Relation als Objekt oder einen Vektor als `{ value }` schreiben, Code, der bei einer Relation mit einem Objekt filtert, Code, der die Wertklassen des Admins importiert, und Offline-Apps mit Schreiboperationen, die von 0.30 in die Warteschlange gestellt wurden.

**Was sich geändert hat:** Ein Schreibvorgang erwartet dieselbe Form, die ein Lesevorgang zurückgibt – ein einheitliches Schreibformat für REST, den Socket, MCP und das prozessinterne SDK:

| Wert | Akzeptiert | Jetzt abgelehnt |
|---|---|---|
| eine To-One-Relation (`belongsTo`, `hasOne`, ein To-One `via`) | der Schlüssel der verknüpften Zeile oder `null` (`""` ist `null`), unter dem Namen der Relation oder des Fremdschlüssels | ein Objekt wie etwa `{ "id": 5 }`: `400 VALIDATION_INVALID_VALUE`, "'posts.author' links one 'authors' row: write that row's key (a string or a number), or null to unlink — not an object." |
| eine To-Many-Relation (`hasMany`, `manyToMany`, ein beschreibbares To-Many `via`) | eine Liste von Schlüsseln oder von `{ id, _pivot? }` | — (weitere Schlüssel am Objekt werden wie bisher ignoriert) |
| ein Vektor | eine Liste von Zahlen | ein `Vector` oder `{ "value": [...] }`: `400`, "'embedding' expects a vector as a list of numbers" |
| ein Datum, eine Uhrzeit | ISO-Text (`Date` prozessintern) | — |
| ein Geopoint | `{ latitude, longitude }` | — |
| ein `bytea` | eine `data:application/octet-stream;base64,`-URL (`Buffer` / `Uint8Array` prozessintern) | — |
| ein Filter auf einer Relation | der Schlüssel | ein Objekt wird nicht mehr aufgelöst: Es wird exakt wie angegeben verglichen |

0.30 akzeptierte eine als Objekt geschriebene To-One-Relation und extrahierte stillschweigend deren `id`; dieses Format war nie dokumentiert und entsprach dem ViewModel des Admin-Panels. Das Admin-Panel wandelt sein ViewModel nun vor jedem Schreib- und Filtervorgang im Browser in die Werte der Übertragungsschicht um.

Die Wertklassen des Admins wurden zusammen mit dem Rest seines ViewModels verschoben: `EntityReference`, `EntityRelation`, `GeoPoint`, `Vector` und `EntityReferenceProps` werden aus `@rebasepro/cms-types` importiert (sie haben `@rebasepro/types` verlassen), ebenso wie `normalizeToEntityRelation` (hat `@rebasepro/common` verlassen); `withRelationReferencesOnly` wurde entfernt. Der Verlauf speichert die Zeile so, wie ein Lesevorgang sie zurückgibt; zuvor aufgezeichnete Einträge werden als einfache Werte ausgeliefert und zurückgerollt ([Abschnitt 132](#132-history-is-served-as-reads)).

Die Offline-Queue von `@rebasepro/client` speichert Werte im Übertragungsformat. Ein vom 0.30-SDK offline in die Warteschlange gestellter Schreibvorgang wird beim Zurücklesen und erneuten Abspielen konvertiert: Nichts, was vor dem Upgrade in der Warteschlange lag, geht verloren.

**Was zu tun ist:** Senden Sie den Schlüssel: `{ "author": 5 }`, nicht `{ "author": { "id": 5 } }`; senden Sie einen Vektor als Liste von Zahlen und filtern Sie eine Relation nach ihrem Schlüssel. `rebase migrate sdk-calls` verschiebt die Importe der Wertklassen ([die Liste](/docs/upgrading/0-30-to-0-31-imports/)). Siehe [Schreibvorgänge](/docs/backend/writes/).

## 139. `/api/docs` is served to the schema endpoint's audience

**Wen dies betrifft:** Personen oder Tools, die `/api/docs` lesen oder `/api/swagger` öffnen – Swagger UI, API-Client-Generatoren, CI-Schritte.

**Was sich geändert hat:** Wenn `enableSwagger` nicht gesetzt ist (`REBASE_ENABLE_SWAGGER` nicht gesetzt), wird das OpenAPI-Dokument in jeder Umgebung denselben Aufrufern ausgeliefert, denen auch `GET /api/schema/tables` Tabellen beschreibt, mit denselben Ablehnungen – 401 für anonyme Aufrufer, sofern nicht `schemaTables.public` gilt, 403 für Credentials ohne Schema- oder Daten-Scope – und jeder Aufrufer erhält das Dokument exakt für die Tabellen, Spalten und Relationen, die dieser Endpunkt ihm beschreibt (ein Administrator erhält alles). Es gibt kein Swagger UI. Ein Server ohne konfigurierte Authentifizierung antwortet mit `404 DOCS_UNAVAILABLE`. 0.30 stellte in der Entwicklungsumgebung das gesamte Dokument mit jeder bereitgestellten Tabelle und nicht-privaten Spalte anonymen Aufrufern zur Verfügung und beschränkte es in der Produktion auf Administratoren.

| `enableSwagger` / `REBASE_ENABLE_SWAGGER` | `/api/docs` | `/api/swagger` |
|---|---|---|
| nicht gesetzt (Standard) | jeder Aufrufer, dem der Schema-Endpunkt Tabellen beschreibt: seine jeweiligen Tabellen | wird nicht ausgeliefert |
| `true` | das vollständige Dokument für jeden | wird außerhalb der Produktionsumgebung ausgeliefert |
| `false` | das vollständige Dokument, geschützt hinter dem Admin-Zugang | wird nicht ausgeliefert |

**Was zu tun ist:** Rufen Sie `/api/docs` im angemeldeten Zustand auf. Um das gesamte Dokument wie unter 0.30 in der Entwicklung öffentlich bereitzustellen, setzen Sie `REBASE_ENABLE_SWAGGER=true` (oder `enableSwagger: true`). Siehe [Endpunkte](/docs/backend/endpoints/).

## 140. A many-to-many `pivot` column may not declare `.transform()`

**Wen dies betrifft:** ein `rel.manyToMany(…, { pivot: { … } })`, dessen Pivot-Spalte ein `.transform()` deklariert.

**Was sich geändert hat:** Der Compiler verweigert dies („the pivot column "x" declares `.transform()` …“). Die Transformation einer Pivot-Spalte wurde an keiner Stelle ausgeführt, sodass ein Wert, den Sie maskieren wollten, unmaskiert wie gespeichert ausgeliefert wurde.

**Was zu tun ist:** Entfernen Sie das `.transform()` und maskieren Sie `_pivot` im `hooks.afterRead` der Zieltabelle. Siehe [Relationen](/docs/collections/relations/).

## 141. A link is exactly as readable and writable as its key column

**Wen dies betrifft:** Clients, die ein `belongsTo` über seinen Relationsnamen schreiben, Relationen lesen oder filtern, deren Schlüsselspalte beschränkt ist, oder sich auf `strictWrites: false` verlassen.

**Was sich geändert hat:** Eine Einschränkung auf einer Schlüsselspalte ist eine Einschränkung für jede Schreibweise, die sie liest oder beschreibt.

- Das Schreiben einer Verknüpfung über ihren Relationsnamen (`{ "reviewer": 7 }`) unterliegt jeder Regel der Schlüsselspalte, die sie setzt – `.readOnly()`, `.private()`, `access.write`, Erstellungs-Zeitstempeln, der Tenant-Spalte, Schlüssel-Unveränderlichkeit – in REST, Bulk, `_batch`, dem Socket und MCP. Das Schreiben der Verknüpfung unter beiden Namen (`{ "reviewer": 7, "reviewerId": 8 }`) mit unterschiedlichen Werten führt zu einem 400 `VALIDATION_INVALID_VALUE`. Das Verschieben einer Zeile zu einem anderen Tenanten über deren Verknüpfung beantwortet der Server mit 400 `TENANT_IMMUTABLE` (zuvor war dies ein 500).
- Eine Relation ist nur lesbar, wenn der Aufrufer jede Spalte lesen darf, die ihr Join liest, und zwar auf jeder Tabelle, die sie durchläuft: den Schlüssel eines `belongsTo`, den Fremdschlüssel des Ziels bei einem `hasMany` / `hasOne`, jede Spalte, über die die Schritte eines `via` joinen. Schlägt eine davon fehl, wird sie aus `include` und `_count` weggelassen, und ein Filter, eine Sortierung oder ein Relationspfad darüber antwortet mit `FIELD_NOT_READABLE` (eine unbekannte Relation, wenn die Spalte `.private()` ist). Ein To-One-`via`-Schreibvorgang, der eine Spalte kopieren würde, die der Aufrufer nicht lesen darf, wird mit `FIELD_NOT_READABLE` abgelehnt. Die inversen und `via`-Fälle waren auch in 0.30.x bereits offen.
- Eine Verknüpfung, deren Schlüsselspalte der Aufrufer nicht lesen darf, wird aus `include` weggelassen, und ein Filter, eine Sortierung, ein `fields`-Eintrag oder ein Relationspfad darüber antwortet mit `FIELD_NOT_READABLE`; eine an einen `.private()`-Schlüssel gebundene Verknüpfung gilt als unbekannte Relation. `GET /api/schema/tables`, OpenAPI und das MCP-`describe_table` beschreiben eine Verknüpfung und ihren Schlüssel zusammen, sodass eine Schlüsselspalte, deren Verknüpfung gesperrt ist, auch dort vorenthalten wird.
- `strictWrites: false` entscheidet über genau eine Sache: Ein nicht deklarierter Schlüssel wird an den Treiber weitergegeben (geschrieben, wenn die Datenbank die Spalte besitzt, andernfalls 400 `VALIDATION_UNKNOWN_FIELDS`). Es hebt niemals eine deklarierte Spalte, einen Zeitstempel, den Tenanten, den Schlüssel, ein Relationsziel oder eine `_pivot`-Regel auf.

**Was zu tun ist:** Schreiben Sie eine Verknüpfung über einen Namen oder über beide mit demselben Wert; lesen Sie eingeschränkte Verknüpfungen mit einer Rolle aus, die deren Schlüssel lesen darf. Siehe [Feldzugriff](/docs/collections/field-access/).
