# Upgrade von 0.26 → 0.27

Dies sind die `### Breaking`-Einträge, die 0.27 für eine App auf Version 0.26 mit sich bringt.

Die beiden Cron-Änderungen sollten Sie zuerst lesen, da keine von beiden das Starten verhindert: Ein Job wird häufiger ausgeführt und der andere überhaupt nicht mehr. Die dritte Änderung betrifft nur eine Tabelle, die bereits existierte. Die vierte betrifft Rebase Cloud und begegnet Ihnen bei Ihrem nächsten Deployment. Die letzte betrifft das Client-SDK im Browser.

---

## 97. Ein Cron-Zeitplan, der beide Tagesfelder einschränkt, greift bei jedem von beiden

`0 9 1 * 1` wurde früher nur an einem Montag ausgeführt, der auf den 1. fiel. Jetzt wird er an jedem 1. und an jedem Montag ausgeführt, wie es bei Standard-Cron der Fall ist. Dies gilt, wenn keines der beiden Tagesfelder mit `*` beginnt. Ein Zeitplan mit `*` oder `*/n` in einem der beiden Felder behält seine bisherige Bedeutung.

Der Zeitplan, der sich dadurch am stärksten ändert, ist das Idiom „erster Montag des Monats“: `0 9 1-7 * 1` wurde früher einmal im Monat ausgeführt und wird jetzt an jedem der ersten sieben Tage sowie an jedem Montag ausgeführt.

**Was zu ändern ist:** Finden Sie die Zeitpläne mit einer Zahl in beiden Tagesfeldern:

```bash
grep -rnE "schedule:.*[\"'\`][^ ]+ +[^ ]+ +[0-9][^ ]* +[^ ]+ +[0-9]" backend/
```

Wenn Sie einen der beiden Tage meinten (ODER-Bedingung), belassen Sie es so. Wenn Sie beide meinten (UND-Bedingung), tragen Sie ein Tagesfeld in den Zeitplan ein und prüfen Sie das andere im Handler:

```typescript
// backend/crons/first-monday.ts
import { defineCron } from "@rebasepro/server";

export default defineCron({
    schedule: "0 9 * * 1",
    timezone: "UTC",

    async handler(ctx) {
        if (ctx.scheduledAt.getUTCDate() > 7) return;
        ctx.log("First Monday of the month");
    },
});
```

Siehe [Zeitplansyntax](/docs/backend/cron-jobs/#schedule-syntax).

## 98. Ein Cron-Zeitplan mit einer fehlerhaften Zahl wird abgelehnt

`5abc`, `*/5x`, `1.5` und ein Bereich, der rückwärts läuft, wie etwa `5-1`, passierten früher die Validierung. Eine Zahl wurde bis zum ersten Zeichen gelesen, das keine Ziffer war, sodass `5abc` als `5` ausgeführt wurde und ein rückwärts verlaufender Bereich gar nichts beitrug. Jeder dieser Fälle wird nun unter Nennung des Feldes und des Grundes abgelehnt.

Ein abgelehnter Job wird nicht registriert und nicht ausgeführt; der Rest des Backends startet normal. Sie erhalten darüber hinaus keinen Hinweis: Ein Deploy geht live, da die Datei selbst geladen werden konnte.

**Was zu ändern ist:** Suchen Sie nach dem Upgrade im Server-Log nach `[cron] Rejecting job` oder prüfen Sie `rejected` über `GET /api/admin/cron`, was auch das Cron-Jobs-Tool des Studios anzeigt. Korrigieren Sie die Zahl, damit der Job beim nächsten Start registriert wird. Siehe [Jobs, die nicht vorhanden sind](/docs/backend/cron-jobs-api/#jobs-that-are-not-there).

## 99. Ein Schlüssel, dessen Strategie von seinem Typ nicht erfüllt werden kann, stoppt den Boot-Vorgang

`isId: "increment"` bei einem Schlüssel, der keine `number` ist, und `isId: "uuid"` bei einem, der kein `string` ist, werden beim Laden der Konfiguration mit einer Meldung abgelehnt, die die entsprechende Eigenschaft benennt. Beide wurden früher als rohes SQL-Default interpretiert. Postgres lehnte `DEFAULT increment` beim ersten `CREATE TABLE` ab, daher betrifft dies nur eine bereits existierende Tabelle, bei der diese Anweisung nicht ausgeführt wurde.

**Was zu ändern ist:** Deklarieren Sie den Schlüssel passend zum Typ der Spalte. Ein numerischer Schlüssel erhält `type: "number"` mit `"increment"`, und ein String-Schlüssel erhält `"uuid"` oder `true`, wenn der Aufrufer den Wert übergibt. Siehe [Schlüssel, Identity und Serials](/docs/schema/columns/#keys-identity-and-serials).

## 100. Ein verwaltetes Deployment oder eine Vorschau schlägt fehl, wenn eine Funktions- oder Cron-Datei nicht geladen werden kann

Eine Funktions- oder Cron-Datei, die beim Importieren einen Fehler auslöste oder nicht geparst werden konnte, wurde früher übersprungen. Dadurch meldete ein Deploy `✓ Live` und bestand seine Probes, obwohl jede Route dieser Datei mit 404 antwortete. Pods auf Rebase Cloud laufen jetzt mit `REBASE_REQUIRE_FILES_LOADED` auf einer Laufzeitumgebung, die dies unterstützt. Die neue Version geht daher niemals in den Status „ready“, die alte Version bedient weiterhin Anfragen und das Deployment bricht unter Nennung der Datei und des Grundes ab.

Ein Projekt, das bisher mit einer solchen Datei im Betrieb war, stößt bei seinem nächsten Deploy darauf. Fleet-Rollouts und Rollbacks sind davon nicht betroffen. Eine Datei, die sich fehlerfrei importieren lässt und keine Funktion oder keinen Job exportiert (wie z. B. ein Helper), wird weiterhin übersprungen.

**Was zu ändern ist:** Führen Sie das Deployment durch und beheben oder löschen Sie anschließend die im Deploy genannte Datei. Außerhalb von Rebase Cloud ändert sich nichts, es sei denn, Sie setzen `REBASE_REQUIRE_FILES_LOADED=true` selbst. Siehe [Umgebung & Konfiguration](/docs/getting-started/configuration/).

## 101. Ein Browser-Client verwendet standardmäßig Cookie-Auth

`createRebaseClient` ohne `auth.authFlowMode` nutzte bisher überall den JSON-Modus. Ein Backend, das von der Rebase-Laufzeitumgebung betrieben wird, behält das Refresh-Token immer in einem HttpOnly-Cookie und liefert im Response-Body `""` zurück. Ein Browser-Client mit diesem Standardwert hatte somit nichts, womit er die Session erneuern konnte, und wurde etwa eine Stunde nach dem Login wortlos abgemeldet. Im Browser ist der Standard jetzt der Cookie-Modus. Außerhalb des Browsers sowie bei einem Browser-Client, dem ein eigenes `auth.storage` übergeben wurde, bleibt es weiterhin JSON.

**Was zu ändern ist:** Nichts, wenn Ihr Backend auf der Rebase-Laufzeitumgebung läuft oder `auth.cookieAuth` setzt: Eine Browser-App, die zuvor nach einer Stunde abgemeldet wurde, bleibt nun angemeldet. Ein Backend ohne `auth.cookieAuth` benötigt `auth: { authFlowMode: "json" }` an seinem Browser-Client. Der Client gibt beim ersten Login, bei dem beide Seiten nicht übereinstimmen, einen Fehler im Log aus und nennt den zu verwendenden Modus. Im Cookie-Modus wird die Session nicht mehr im `localStorage` gespeichert; ein Neuladen der Seite stellt sie über eine einzelne `/auth/refresh`-Anfrage wieder her. Lesen Sie die Session daher erst nach `auth.isInitialized()` aus. Siehe [Wo die Session gespeichert wird](/docs/sdk/authentication/#where-the-session-lives-authflowmode).
