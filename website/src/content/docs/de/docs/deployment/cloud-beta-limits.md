[Rebase Cloud](/docs/deployment/cloud/) befindet sich in der Private Beta. Klar ausgedrückt, da es schlimmer ist, es erst später herauszufinden:

- **Keine freie Wahl der Region.** Aktuell läuft alles in einer einzigen Region. Das Placement-Modell existiert in der Plattform, ein Projekt kann sich eine Region jedoch nicht aussuchen. `projects create --provider` und `--region` sind keine Ausnahmen, auch wenn es so aussieht: Sie halten fest, zu welchem der registrierten Deploy-Ziele der Control Plane ein Projekt gehört. Da es nur eines gibt, fallen beide standardmäßig darauf zurück, und keines von beiden verschiebt ein Projekt an einen anderen Ort. `rebase cloud projects create --help` besagt dasselbe.
- **Kein Self-Service.** Der Zugriff wird schubweise gewährt; es gibt keine Registrierung mit direkter Bezahlung.
- **Kein veröffentlichtes SLA** und kein SOC 2. Wenn Sie eines von beiden benötigen, geben Sie dies bitte direkt bei der Zugriffsanfrage an, anstatt davon auszugehen.
- **Keine Branch-Deployments** und keine native GitHub-App. Deploy-Hooks – geheime URLs, auf die Sie einen Repository-Webhook richten – sind die unterstützte Automatisierungsmethode. [Preview-Deployments](/docs/deployment/cloud/#preview-a-change) werden schrittweise eingeführt und über die CLI gestartet.
- **Tokens agieren als Person.** Ein [Token](/docs/deployment/cloud-agents/#ci-and-agents) wird von einem Account generiert und agiert als dieser; es gibt bisher keine organisationsweiten Maschinenidentitäten. Wenn Sie sich stattdessen über CI anmelden, übergeben Sie `REBASE_CLOUD_EMAIL` und `REBASE_CLOUD_PASSWORD` aus einem Secret-Speicher – `--password` schreibt das Passwort in Ihre Shell-Historie und in die Prozesstabelle und weist Sie darauf hin, bevor Sie angemeldet werden. Falls die Datei `.rebase/cloud.json` des Repositorys eine andere Control Plane als die plattformeigene angibt, übergeben Sie diese ebenfalls als `--url`: Ohne Terminal weigert sich `login`, ein Passwort an einen Host zu senden, der lediglich in der ausgecheckten Datei benannt wurde.
- **Kein öffentlicher Datenbank-Endpunkt.** Eine verwaltete Datenbank ist nicht für das Internet freigegeben. Der in der Konsole angezeigte Host ist daher die Adresse, unter der Ihr Backend sie erreicht, und löst auf Ihrem lokalen Rechner zu nichts auf. `rebase cloud db connect` öffnet einen lokalen Port, der dieser Datenbank entspricht – getunnelt über die Control Plane –, solange Sie den Befehl laufen lassen; es gibt jedoch keinen permanenten Hostnamen, mit dem sich ein Drittanbieterdienst verbinden kann. Um SQL ohne lokalen Postgres-Client auszuführen, öffnet `rebase cloud db query "<sql>"` oder `rebase cloud db query --file file.sql` denselben Tunnel für eine einzelne Abfrage, führt den Text als ein Skript aus (bricht beim ersten Fehler ab) und gibt die Antwort jeder Anweisung aus (`--json` für ein Skript). Sowohl dieser Tunnel als auch das Passwort hinter `rebase cloud db info --reveal` erfordern die Rolle „Owner“ oder „Admin“ der Organisation: dieselbe, die auch der SQL-Editor von Studio verlangt, da alle drei in einer Session auf Ihren Produktionsdaten enden.
- **Deployen bedeutet, Code mit den Produktions-Secrets auszuführen.** Die Umgebung der App enthält `REBASE_SERVICE_KEY` (Admin auf der eigenen API), `DATABASE_URL` und `JWT_SECRET`. Code, den ein Mitglied deployt, kann diese Werte also auslesen, auch wenn nur Owner und Admins sie in der Konsole einsehen können. Laden Sie nur Personen als Mitglieder ein, denen Sie diese Werte anvertrauen würden.
- **Der Service-Key kann ersetzt werden.** Über die **Settings** des Projekts (oder `rebase cloud service-key rotate`) wird ein neuer `REBASE_SERVICE_KEY` ausgestellt und die App damit neu gestartet. Der alte Schlüssel funktioniert noch, bis der Neustart abgeschlossen ist, danach jedoch nicht mehr – alles, was ihn kopiert hat, wird ab diesem Zeitpunkt abgewiesen. Das Beanspruchen eines Projekts (Claiming) bewirkt dasselbe.
