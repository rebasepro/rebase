Jeder Fehler, den ein Rebase-Backend zurückgibt, verwendet ein einheitliches Envelope
und enthält einen stabilen `code`. Der Code ist das Element, auf das im Code verzweigt
werden sollte: Die Nachricht ist für Menschen geschrieben und kann umformuliert werden,
der Status wird von einem Dutzend verschiedener Probleme geteilt, und der Code ist keines
von beidem.

## Der Envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — menschenlesbar. Bei einem `4xx` ist es die eigene Nachricht des
  Servers; bei einem `5xx` ist sie bewusst generisch gehalten, da der zugrunde liegende
  Text einen Host, eine Rolle oder einen Spaltennamen zitieren kann.
- **`code`** — einer der unten aufgeführten Werte. Stabil über Minor-Versionen hinweg.
- **`details`** — optional und niemals garantiert. Siehe die Regeln unten.
- **`requestId`** — vorhanden, wann immer die Anfrage die Request-ID-Middleware
  durchlaufen hat, was auf jede Route unter `basePath` zutrifft.

### `X-Request-ID`

Jede Anfrage unter `basePath` erhält eine ID: den `X-Request-ID`-Header des Aufrufers,
wenn es sich um eine UUID handelt, andernfalls eine neu generierte. Sie wird in der
Antwort als `X-Request-ID` zurückgegeben, im Fehler-Envelope als `requestId` eingefügt
und an die Server-Protokollzeile für diese Anfrage angehängt.

Das ist der Verknüpfungsschlüssel. Geben Sie ihn in einem Fehlerbericht an, und ein
Operator kann genau die eine Protokollzeile finden, die den Fehler erklärt – einschließlich
des Grundes, der dem Client niemals angezeigt wurde.

Das Senden einer eigenen ID sorgt dafür, dass ein Trace einen Hop übersteht: Ein Gateway
oder ein Job-Runner, der den Header weiterleitet, behält eine einheitliche ID über jeden
Dienst hinweg, der die Anfrage verarbeitet hat. Ein ungültiger Wert wird ignoriert statt
abgewiesen – ein fehlerhafter Header eines Aufrufers ist es nicht wert, eine Anfrage
fehlschlagen zu lassen. Gehen Sie daher nicht davon aus, dass die von Ihnen gesendete
ID genau der empfangenen ID entspricht. Lesen Sie den Response-Header aus.

### Was in `details` enthalten ist

`details` dient Diagnosezwecken und ist nicht vertraglich zugesichert. Drei Regeln bestimmen den Inhalt:

1. **Alles, was eine Route explizit festlegt, wird immer zurückgegeben.** Dies sind die
   eigenen Fehler des Aufrufers, die präzise beschrieben werden: welches Filterfeld
   unbekannt war, welche Relation nicht schreibbar ist, welcher Wert nicht zu seinem
   Typ passte.
2. **Datenbankdiagnosen werden in der Produktion gekürzt.** Wenn der Fehler von
   Postgres stammt, ist `details.dbCode` – der SQLSTATE – immer vorhanden: Er benennt
   die Problemklasse und gibt nichts über die Daten preis. `dbMessage`, `detail` und
   `hint` werden nur hinzugefügt, wenn `NODE_ENV` nicht `production` ist, da Postgres
   Zeileninhalte darin platziert. `23505` meldet `Key (email)=(a@b.c) already exists.`,
   was für jede beliebige Adresse die Frage „Ist diese Person registriert?“ beantwortet.
3. **Niemals auf Basis von `details` verzweigen.** Verzweigen Sie anhand von `code`.
   Was unter `details` steht, war lediglich an der jeweiligen Aufrufstelle für eine
   Person nützlich und kann sich ändern.

## Einen Status interpretieren

| Status | Was er über die Anfrage aussagt |
| --- | --- |
| `400` | Fehlerhaft aufgebaut (malformed) oder fragt nach etwas, das im Schema nicht existiert. Korrigieren Sie die Anfrage. |
| `401` | Nicht authentifiziert oder die Anmeldeinformationen sind abgelaufen. Anmelden oder aktualisieren. |
| `403` | Authentifiziert, aber nicht berechtigt. Ein erneuter Versuch mit derselben Identität hilft nicht. |
| `404` | Keine solche Route, Tabelle oder Zeile – oder eine Zeile, die durch Row-Level Security verborgen wird. |
| `409` | Ein Konflikt mit dem bestehenden Zustand: ein Duplikat oder ein konkurrierender Schreibvorgang. |
| `413` `415` `422` | Der Body ist zu groß, hat den falschen Medientyp oder wurde semantisch abgelehnt. |
| `429` | Rate-Limit erreicht. Warten Sie; die Nachricht gibt an, wie lange. |
| `500` | Der Server oder seine Datenbank hat einen Fehler, nicht der Aufrufer. Prüfen Sie die Logs. |
| `501` | Die Route existiert, aber diese Bereitstellung kann sie nicht bedienen – eine Funktion ist deaktiviert oder unkonfiguriert. |
| `502` `503` `504` | Eine Abhängigkeit war nicht erreichbar, nicht konfiguriert oder zu langsam. |

## `PG_<SQLSTATE>` — ein von der Datenbank abgelehnter Constraint

Ein Schreibvorgang, den Postgres aus einem Grund ablehnt, der in den *Daten des Aufrufers*
liegt, antwortet mit dem SQLSTATE im Code: `PG_23505`, `PG_23503` usw. Dabei handelt es sich
um eine Familie, nicht um eine feste Liste – Postgres definiert Hunderte von SQLSTATEs –,
aber nur zwei Klassen erreichen diesen Zustand, da nur diese beiden auf Fehler des
Aufrufers zurückzuführen sind:

- **Klasse 23**, Verletzung von Integritäts-Constraints: ein Duplikat, ein Fremdschlüssel,
  der ins Leere zeigt, eine leere NOT NULL-Spalte;
- **Klasse 22**, Daten-Ausnahme (Data Exception): ein Wert, den der Typ der Spalte nicht
  aufnehmen kann.

Alles andere – eine unterbrochene Verbindung, eine fehlende Spalte, ein Berechtigungsproblem –
liegt in der Verantwortung des Servers und bleibt ein `500`. Daher ist `code.startsWith("PG_")`
eine verlässliche Prüfung auf „Die von mir gesendete Zeile war fehlerhaft“, und die vier
unten aufgeführten Fehler sind diejenigen, denen ein Client in der Praxis begegnet.
`details.dbCode` enthält bei allen denselben SQLSTATE, und die Nachricht nennt den Constraint.

| Code | Status | Bedeutung | Behebung |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Ein Wert konnte nicht als Typ der Spalte gelesen werden – das schreibseitige Pendant zu `INVALID_FILTER_VALUE`. | Senden Sie einen Wert vom Typ der Spalte. |
| `PG_23502` | 400 | Eine `NOT NULL`-Spalte wurde leer gelassen. | Senden Sie das Feld oder weisen Sie der Spalte einen Standardwert zu. |
| `PG_23503` | 400 / 409 | Beim Speichern zeigt ein Fremdschlüssel auf eine Zeile, die nicht existiert (400). Beim Löschen verweisen noch andere Zeilen auf diese Zeile (409; ein `RESTRICT`-Schlüssel löst `PG_23001` aus, ebenfalls 409). | Erstellen Sie zuerst die Zielzeile oder korrigieren Sie die ID; entfernen oder verweisen Sie beim Löschen zuerst die referenzierenden Zeilen um. |
| `PG_23505` | 409 | Ein Unique-Constraint wurde verletzt. Die Nachricht nennt den Constraint. | Verwenden Sie einen anderen Wert oder aktualisieren Sie die bestehende Zeile. |

### Warum die Tabelle eines Branches nicht gemergt werden kann

`BRANCH_MERGE_BLOCKED` nennt jede abgelehnte Tabelle in `details.tables` mit einem
dieser Codes. Derselbe Code befindet sich auf dem `blocked` der Tabelle im Diff
selbst, sodass Studio dies anzeigen kann, bevor jemand auf **Merge** klickt.
Keiner dieser Codes stellt eine eigenständige API-Antwort dar.

| Code | Status | Bedeutung | Behebung |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Die Spalten der Tabelle unterscheiden sich zwischen dem Branch und seinem übergeordneten Element. Zeilen werden anhand der gemeinsamen Spalten verglichen. | Fügen Sie die fehlenden Spalten mit Ihren Migrationen (`rebase db push`) zum übergeordneten Element hinzu und führen Sie dann den Merge durch. Eine Migration, die die Tabelle neu schreibt – eine Änderung des Spaltentyps –, wandelt dies in `TABLE_REWRITTEN` um: Führen Sie den Merge vor einer solchen Änderung durch oder erstellen Sie den Branch danach neu. |
| `NO_PRIMARY_KEY` | — | Die Tabelle besitzt keinen Primärschlüssel, sodass Zeilen nicht einzeln abgeglichen werden können; das Diff gibt nur deren Zeilenzahl an. | Versehen Sie die Tabelle mit einem Primärschlüssel oder verschieben Sie deren Zeilen manuell. |
| `PRIMARY_KEY_DIFFERS` | — | Die Spalten des Primärschlüssels oder deren Typen unterscheiden sich zwischen beiden. | Wenden Sie das Schema zuerst auf das übergeordnete Element an. |
| `TABLE_ADDED` | — | Der Branch hat die Tabelle erstellt. Ein Merge erstellt niemals Tabellen. | Erstellen Sie sie auf dem übergeordneten Element mit Ihren Migrationen und mergen Sie dann deren Zeilen. |
| `TABLE_DROPPED` | — | Der Branch hat die Tabelle gelöscht. Ein Merge löscht niemals Tabellen. | Löschen Sie sie mit Ihren Migrationen. |
| `TABLE_REWRITTEN` | — | Eine Seite hat jede Zeile der Tabelle nach Erstellung des Branches neu geschrieben – eine Änderung des Spaltentyps, ein `ADD COLUMN` mit flüchtigem Standardwert, `VACUUM FULL`, `CLUSTER` –, sodass jede Zeile als seitdem geschrieben gilt und nicht mehr ermittelt werden kann, welche Seite welche Zeile geändert hat. | Mergen Sie den Branch vor einer solchen Migration oder erstellen Sie den Branch danach neu aus dem übergeordneten Element. |
| `TOO_LARGE` | — | Die Tabelle enthält auf einer Seite mehr Zeilen, als ein Diff einzeln abgleicht (standardmäßig 100.000, `maxRowsPerTable`). | Erhöhen Sie `maxRowsPerTable` sowohl für das Diff als auch für den Merge, oder verschieben Sie die Zeilen auf andere Weise. |

## Diese Seite aktuell halten

`pnpm verify:docs` schlägt fehl, wenn ein Code, den der Server auslösen kann, in
diesen Tabellen fehlt, wenn eine Tabelle einen Code auflistet, den nichts auslösen
kann, wenn die Statuswerte einer Zeile nicht exakt denen entsprechen, mit denen der
Quellcode den Code auslöst, oder wenn eine Code-Familie wie `PG_<SQLSTATE>` keine Zeile
für einen SQLSTATE enthält, dem Aufrufer begegnen. Der Prüfschritt ist
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Er prüft sich zunächst selbst. Der Scan liest Codes aus TypeScript und nicht von
einem laufenden Server aus, sodass seine toten Winkel konstruktionsbedingt unbemerkt
bleiben: Einmal konnte er keinen Code erkennen, der über einen Einzeiler-Wrapper
übergeben wurde, oder einen, der nach einer Nachricht mit einer `)` stand, und
meldete „Jeder Code, den der Server auslösen kann, ist dokumentiert“ für eine Seite,
