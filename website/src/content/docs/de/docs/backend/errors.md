Jeder Fehler, den ein Rebase-Backend zurückgibt, verwendet einen einheitlichen Envelope und enthält einen stabilen `code`. Auf diesen Code sollte im Programmablauf verzweigt werden: Die Nachricht ist für Menschen verfasst und kann umformuliert werden, der Status wird von einem Dutzend verschiedener Probleme geteilt – der Code hingegen ist weder vage noch unbeständig.

## Der Envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — menschenlesbar. Bei einem `4xx`-Fehler ist es die eigene Nachricht des Servers; bei einem `5xx`-Fehler ist sie bewusst generisch gehalten, da der zugrunde liegende Text einen Host, eine Rolle oder einen Spaltennamen enthalten kann.
- **`code`** — einer der unten aufgeführten Werte. Stabil über Minor-Versionen hinweg.
- **`details`** — optional und niemals garantiert. Siehe die unten stehenden Regeln.
- **`requestId`** — vorhanden, wann immer die Anfrage die Request-ID-Middleware durchlaufen hat, was für jede Route unter `basePath` gilt.

### `X-Request-ID`

Jede Anfrage unter `basePath` erhält eine ID: den `X-Request-ID`-Header des Aufrufers, sofern es sich um eine UUID handelt, andernfalls eine neu generierte. Sie wird in der Antwort als `X-Request-ID` zurückgegeben, im Fehler-Envelope als `requestId` aufgeführt und an die Server-Logzeile für diese Anfrage angehängt.

Das ist der Join-Schlüssel. Geben Sie ihn in einem Fehlerbericht an, und ein Administrator kann genau die eine Logzeile finden, die den Fehler erklärt und den Grund enthält, der dem Client nie angezeigt wurde.

Das Senden einer eigenen ID ermöglicht es einem Trace, Hops zu überstehen: Ein Gateway oder ein Job-Runner, der den Header weiterleitet, behält eine einheitliche ID über alle Dienste hinweg bei, die die Anfrage verarbeitet haben. Ein ungültiger Wert wird ignoriert statt abgelehnt – wegen eines fehlerhaften Headers eines Aufrufers sollte keine Anfrage fehlschlagen. Gehen Sie daher nicht davon aus, dass die von Ihnen gesendete ID der empfangenen entspricht. Lesen Sie den Response-Header aus.

### Was in `details` enthalten ist

`details` dient Diagnosezwecken und ist nicht vertraglich zugesichert. Drei Regeln bestimmen den Inhalt:

1. **Alles, was eine Route explizit setzt, wird immer zurückgegeben.** Dies sind die präzise beschriebenen Fehler des Aufrufers selbst: welches Filterfeld unbekannt war, welche Relation nicht beschreibbar ist, welcher Wert nicht zu seinem Typ passte.
2. **Datenbankdiagnosen werden in Produktionsumgebungen gekürzt.** Wenn der Fehler von Postgres stammt, ist `details.dbCode` – der SQLSTATE – immer vorhanden: Er benennt die Problemklasse und verrät nichts über die Daten. `dbMessage`, `detail` und `hint` werden nur hinzugefügt, wenn `NODE_ENV` nicht `production` ist, da Postgres Zeileninhalte darin platziert. `23505` meldet `Key (email)=(a@b.c) already exists.`, was für jede beliebige Adresse die Frage „Ist diese Person registriert?“ beantworten würde.
3. **Verzweigen Sie im Code niemals auf Basis von `details`.** Verzweigen Sie anhand von `code`. Was unter `details` steht, ist das, was für einen Menschen an dieser Aufrufstelle nützlich war, und es kann sich ändern.

## Einen Status interpretieren

| Status | Was er über die Anfrage aussagt |
| --- | --- |
| `400` | Fehlerhaft aufgebaut oder fordert etwas an, das im Schema nicht existiert. Beheben Sie die Anfrage. |
| `401` | Nicht authentifiziert oder die Anmeldedaten sind abgelaufen. Melden Sie sich an oder aktualisieren Sie das Token. |
| `403` | Authentifiziert, aber nicht autorisiert. Ein erneuter Versuch mit derselben Identität wird nicht helfen. |
| `404` | Keine solche Route, Tabelle oder Zeile – oder eine Zeile, die durch Row-Level Security verborgen wird. |
| `409` | Ein Konflikt mit dem bestehenden Zustand: ein Duplikat oder ein konkurrierender Schreibvorgang. |
| `413` `415` `422` | Der Body ist zu groß, hat den falschen Medientyp oder wurde semantisch abgelehnt. |
| `429` | Rate-Limit erreicht. Warten Sie; die Nachricht gibt an, wie lange. |
| `500` | Der Server oder seine Datenbank weist einen Fehler auf, nicht der Aufrufer. Überprüfen Sie die Logs. |
| `501` | Die Route existiert, aber dieses Deployment kann sie nicht bedienen – eine Funktion ist deaktiviert oder unkonfiguriert. |
| `502` `503` `504` | Eine Abhängigkeit war nicht erreichbar, unkonfiguriert oder zu langsam. |

## `PG_<SQLSTATE>` — ein von der Datenbank abgelehnter Constraint

Ein Schreibvorgang, den Postgres aus einem Grund ablehnt, der in den *Daten des Aufrufers* liegt, antwortet mit dem SQLSTATE im Code: `PG_23505`, `PG_23503` usw. Dabei handelt es sich um eine Code-Familie, nicht um eine feste Liste – Postgres definiert Hunderte von SQLSTATEs –, aber nur zwei Klassen treten hier jemals auf, da nur diese beiden vom Aufrufer zu verantworten sind:

- **Klasse 23**, Integritätsverletzung (Integrity Constraint Violation): ein Duplikat, ein Fremdschlüssel, der ins Leere zeigt, eine leere NOT NULL-Spalte;
- **Klasse 22**, Daten-Ausnahme (Data Exception): ein Wert, den der Typ der Spalte nicht aufnehmen kann.

Alles andere – eine unterbrochene Verbindung, eine fehlende Spalte, ein Rechteproblem – liegt in der Verantwortung des Servers und bleibt ein `500`. Daher ist `code.startsWith("PG_")` eine zuverlässige Prüfung für „Die von mir gesendete Zeile war fehlerhaft“, und die vier unten aufgeführten sind diejenigen, denen ein Client in der Praxis begegnet. `details.dbCode` enthält bei allen denselben SQLSTATE, und die Nachricht nennt den Constraint.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Ein Wert konnte nicht als Typ der Spalte interpretiert werden – das Gegenstück zu `INVALID_FILTER_VALUE` auf Schreibseite. | Senden Sie einen Wert des passenden Spaltentyps. |
| `PG_23502` | 400 | Eine `NOT NULL`-Spalte wurde leer gelassen. | Senden Sie das Feld mit oder versehen Sie die Spalte mit einem Standardwert. |
| `PG_23503` | 400 / 409 | Beim Speichern verweist ein Fremdschlüssel auf eine Zeile, die nicht existiert (400). Beim Löschen referenzieren andere Zeilen noch diese Zeile (409; ein `RESTRICT`-Schlüssel löst `PG_23001` aus, ebenfalls 409). | Erstellen Sie zuerst die Zielzeile oder korrigieren Sie die ID; entfernen Sie beim Löschen zuerst die referenzierenden Zeilen oder passen Sie deren Referenz an. |
| `PG_23505` | 409 | Ein Eindeutigkeits-Constraint (Unique Constraint) wurde verletzt. Die Nachricht nennt den Constraint. | Verwenden Sie einen anderen Wert oder aktualisieren Sie die bestehende Zeile. |

### Warum die Tabelle eines Branches nicht zusammengeführt werden kann

`BRANCH_MERGE_BLOCKED` listet jede abgewiesene Tabelle in `details.tables` mit einem der folgenden Codes auf. Derselbe Code findet sich im Diff selbst unter `blocked` der jeweiligen Tabelle, sodass Studio dies anzeigen kann, bevor jemand auf **Merge** klickt. Keiner davon ist eine eigenständige HTTP-Antwort.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Die Spalten der Tabelle unterscheiden sich zwischen dem Branch und seinem Parent. Zeilen werden anhand der gemeinsamen Spalten verglichen. | Fügen Sie die fehlenden Spalten über Ihre Migrationen zum Parent hinzu (`rebase db push`) und führen Sie anschließend den Merge durch. Eine Migration, die die Tabelle neu schreibt – etwa eine Änderung des Spaltentyps –, führt zu `TABLE_REWRITTEN`: Führen Sie den Merge vor einer solchen Änderung durch oder erstellen Sie den Branch danach neu. |
| `NO_PRIMARY_KEY` | — | Die Tabelle besitzt keinen Primärschlüssel, sodass Zeilen nicht einzeln abgeglichen werden können; das Diff gibt lediglich Zeilenanzahlen aus. | Versehen Sie die Tabelle mit einem Primärschlüssel oder übertragen Sie die Zeilen manuell. |
| `PRIMARY_KEY_DIFFERS` | — | Die Spalten des Primärschlüssels oder deren Datentypen unterscheiden sich zwischen beiden Seiten. | Wenden Sie das Schema zuerst auf dem Parent an. |
| `TABLE_ADDED` | — | Der Branch hat die Tabelle neu erstellt. Ein Merge erstellt niemals Tabellen. | Erstellen Sie die Tabelle über Ihre Migrationen auf dem Parent und führen Sie danach die Zeilen zusammen. |
| `TABLE_DROPPED` | — | Der Branch hat die Tabelle gelöscht. Ein Merge löscht niemals Tabellen. | Löschen Sie die Tabelle über Ihre Migrationen. |
| `TABLE_REWRITTEN` | — | Eine Seite hat nach Erstellung des Branches jede Zeile der Tabelle neu geschrieben – Änderung eines Spaltentyps, ein `ADD COLUMN` mit volatilem Default, `VACUUM FULL`, `CLUSTER` – sodass jede Zeile als nachträglich geschrieben gilt und nicht mehr ermittelt werden kann, welche Seite welche Zeile geändert hat. | Führen Sie den Merge vor einer solchen Migration durch oder erstellen Sie den Branch vom Parent danach neu. |
| `TOO_LARGE` | — | Die Tabelle enthält auf einer Seite mehr Zeilen, als ein Diff einzeln abgleicht (standardmäßig 100.000, `maxRowsPerTable`). | Erhöhen Sie `maxRowsPerTable` sowohl für das Diff als auch für den Merge oder übertragen Sie die Zeilen auf anderem Wege. |

## Diese Seite aktuell und korrekt halten

`pnpm verify:docs` schlägt fehl, wenn ein Code, den der Server werfen kann, in diesen Tabellen fehlt, wenn eine Tabelle einen Code auflistet, den nichts auslösen kann, wenn die Statusangaben einer Zeile nicht exakt denen entsprechen, mit denen die Codebasis den Fehler auslöst, oder wenn eine Code-Familie wie `PG_<SQLSTATE>` keine Zeile für einen SQLSTATE enthält, dem Aufrufer in der Praxis begegnen. Der entsprechende Prüfschritt ist `tooling/scripts/docs-verify/check-error-codes.mjs`.

Das Skript prüft sich zunächst selbst: Der Scan liest Codes direkt aus dem TypeScript-Quellcode statt von einem laufenden Server aus, weshalb tote Winkel konstruktionsbedingt unbemerkt bleiben könnten – früher konnte es beispielsweise keinen Code erkennen, der über einen einzeiligen Wrapper übergeben wurde, oder einen, der hinter einer Nachricht mit einer `)` stand, und meldete „Jeder Code, den der Server werfen kann, ist dokumentiert“, obwohl auf der Seite siebzehn Codes fehlten. Daher führt der Schritt eine Test-Fixture genau dieser Konstrukte aus, bevor er diese Seite liest, und verweigert die Validierung, falls er diese nicht erfassen kann.
