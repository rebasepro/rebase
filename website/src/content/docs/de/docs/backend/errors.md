Jeder Fehler, den ein Rebase-Backend zurückgibt, verwendet denselben Envelope und enthält einen stabilen
`code`. Der Code ist das Element, auf dem Verzweigungen basieren sollten: Die Nachricht ist für Menschen
geschrieben und kann umformuliert werden, der Status wird von einem Dutzend verschiedener Probleme geteilt,
und der Code ist beides nicht.

## Der Envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — menschenlesbar. Bei einem `4xx` ist es die serverspezifische Nachricht; bei einem
  `5xx` ist sie bewusst allgemein gehalten, da der zugrunde liegende Text einen Host, eine Rolle oder einen
  Spaltennamen enthalten kann.
- **`code`** — einer der unten aufgeführten Werte. Stabil über Minor-Versionen hinweg.
- **`details`** — optional und niemals garantiert. Siehe die nachfolgenden Regeln.
- **`requestId`** — vorhanden, sobald die Anfrage die Request-ID-Middleware durchlaufen hat, was auf
  jede Route unter `basePath` zutrifft.

### `X-Request-ID`

Jede Anfrage unter `basePath` erhält eine ID: den `X-Request-ID`-Header des Aufrufers, wenn es
sich um eine UUID handelt, andernfalls eine neu generierte. Sie wird in der Antwort als
`X-Request-ID` zurückgegeben, im Fehler-Envelope als `requestId` enthalten und an die Logzeile
des Servers für diese Anfrage angehängt.

Das ist der Verknüpfungsschlüssel (Join Key). Geben Sie ihn in einem Fehlerbericht an, und ein Operator kann die
eine Logzeile finden, die den Fehler erklärt und den Grund enthält, der dem Client niemals
angezeigt wurde.

Das Senden einer eigenen ID ermöglicht es einem Trace, Hops zu überstehen: Ein Gateway oder ein Job-Runner,
der den Header weiterleitet, erhält eine einheitliche ID über jeden Dienst hinweg, der die Anfrage verarbeitet hat.
Ein ungültiger Wert wird ignoriert und nicht abgelehnt – wegen eines fehlerhaften Headers eines Aufrufers
sollte eine Anfrage nicht fehlschlagen. Gehen Sie daher nicht davon aus, dass die gesendete ID der empfangenen
entspricht. Prüfen Sie den Response-Header.

### Was in `details` enthalten ist

`details` dient der Diagnose, nicht als Vertrag. Drei Regeln bestimmen den Inhalt:

1. **Alles, was eine Route explizit setzt, wird immer zurückgegeben.** Dies sind präzise
   beschriebene Fehler des Aufrufers: welches Filterfeld unbekannt war, welche Relation
   nicht schreibbar ist, welcher Wert nicht zu seinem Typ passte.
2. **Datenbankdiagnosen werden in der Produktionsumgebung gekürzt.** Wenn der Fehler von
   Postgres stammt, ist `details.dbCode` – der SQLSTATE – immer vorhanden: Er benennt die
   Problemklasse und gibt nichts über die Daten preis. `dbMessage`, `detail` und `hint` werden
   nur hinzugefügt, wenn `NODE_ENV` nicht `production` ist, da Postgres Zeileninhalte darin platziert.
   `23505` meldet `Key (email)=(a@b.c) already exists.`, was für jede beliebige Adresse die Frage
   "Ist diese Person registriert?" beantwortet.
3. **Verzweigen Sie niemals anhand von `details`.** Verzweigen Sie anhand von `code`. Was unter
   `details` steht, ist das, was für einen Menschen an dieser Aufrufstelle nützlich war, und kann sich ändern.

## Einen Status interpretieren

| Status | Was er über die Anfrage aussagt |
| --- | --- |
| `400` | Fehlerhaft aufgebaut oder fragt nach etwas, das im Schema nicht existiert. Beheben Sie die Anfrage. |
| `401` | Nicht authentifiziert oder die Anmeldeinformationen sind abgelaufen. Melden Sie sich an oder aktualisieren Sie das Token. |
| `403` | Authentifiziert, aber nicht autorisiert. Ein erneuter Versuch mit derselben Identität nützt nichts. |
| `404` | Keine solche Route, Tabelle oder Zeile – oder eine Zeile, die durch Row-Level Security verborgen wird. |
| `409` | Ein Konflikt mit dem bestehenden Status: ein Duplikat oder ein gleichzeitiger Schreibvorgang. |
| `413` `415` `422` | Der Body ist zu groß, hat den falschen Medientyp oder wurde semantisch abgelehnt. |
| `429` | Rate-Limit erreicht. Warten Sie; die Nachricht gibt an, wie lange. |
| `500` | Der Server oder seine Datenbank hat einen Fehler, nicht der Aufrufer. Prüfen Sie die Logs. |
| `501` | Die Route existiert, aber dieses Deployment kann sie nicht bereitstellen – ein Feature ist deaktiviert oder unkonfiguriert. |
| `502` `503` `504` | Eine Abhängigkeit war nicht erreichbar, unkonfiguriert oder zu langsam. |

## `PG_<SQLSTATE>` — ein von der Datenbank abgelehnter Constraint

Ein Schreibvorgang, den Postgres aus einem Grund ablehnt, der in den *Daten des Aufrufers* liegt,
antwortet mit dem SQLSTATE im Code: `PG_23505`, `PG_23503` usw. Dabei handelt es sich um
eine Familie, nicht um eine feste Liste – Postgres definiert Hunderte von SQLSTATEs –, aber nur
zwei Klassen erreichen jemals diesen Punkt, da nur diese beiden vom Aufrufer verschuldet sind:

- **Klasse 23**, Integritäts-Constraint-Verletzung: ein Duplikat, ein Fremdschlüssel, der ins
  Leere zeigt, eine leere NOT-NULL-Spalte;
- **Klasse 22**, Daten-Ausnahme: ein Wert, den der Spaltentyp nicht aufnehmen kann.

Alles andere – ein Verbindungsabbruch, eine fehlende Spalte, ein Berechtigungsproblem – liegt in der
Verantwortung des Servers und bleibt ein `500`. Somit ist `code.startsWith("PG_")` eine verlässliche
Prüfung für "die von mir gesendete Zeile war fehlerhaft", und die vier folgenden Codes sind diejenigen,
denen ein Client in der Praxis begegnet. `details.dbCode` enthält bei allen denselben SQLSTATE, und
die Nachricht nennt den Constraint.

| Code | Status | Bedeutung | Was zu tun ist |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Ein Wert konnte nicht als Typ der Spalte interpretiert werden – das schreibseitige Gegenstück zu `INVALID_FILTER_VALUE`. | Senden Sie einen Wert, der dem Spaltentyp entspricht. |
| `PG_23502` | 400 | Eine `NOT NULL`-Spalte wurde leer gelassen. | Senden Sie das Feld mit oder versehen Sie die Spalte mit einem Standardwert. |
| `PG_23503` | 400 / 409 | Beim Speichern: Ein Fremdschlüssel verweist auf eine nicht existierende Zeile (400). Beim Löschen: Andere Zeilen referenzieren diese Zeile noch (409; ein `RESTRICT`-Schlüssel löst `PG_23001` aus, ebenfalls 409). | Erstellen Sie zuerst die Zielzeile oder korrigieren Sie die ID; entfernen Sie beim Löschen zuerst die referenzierenden Zeilen oder biegen Sie sie um. |
| `PG_23505` | 409 | Ein Unique-Constraint wurde verletzt. Die Nachricht nennt den Constraint. | Verwenden Sie einen anderen Wert oder aktualisieren Sie die bestehende Zeile. |

### Warum die Tabelle eines Branches nicht zusammengeführt werden kann

`BRANCH_MERGE_BLOCKED` nennt jede abgelehnte Tabelle in `details.tables` mit einem
dieser Codes. Derselbe Code befindet sich auf dem `blocked` der Tabelle im Diff selbst,
sodass Studio dies anzeigen kann, bevor jemand auf **Merge** klickt. Keiner davon ist eine
eigenständige Serverantwort.

| Code | Status | Bedeutung | Was zu tun ist |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Die Spalten der Tabelle unterscheiden sich zwischen dem Branch und seinem übergeordneten Element. Zeilen werden anhand der gemeinsamen Spalten verglichen. | Fügen Sie die fehlenden Spalten mit Ihren Migrationen dem übergeordneten Element hinzu (`rebase db push`), und führen Sie den Merge dann durch. Eine Migration, die die Tabelle umschreibt – eine Änderung des Spaltentyps –, führt zu `TABLE_REWRITTEN`: Führen Sie den Merge vor einer solchen Änderung durch oder erstellen Sie den Branch danach neu. |
| `NO_PRIMARY_KEY` | — | Die Tabelle besitzt keinen Primärschlüssel, sodass Zeilen nicht einzeln abgeglichen werden können; der Diff liefert nur deren Zeilenzahlen. | Versehen Sie die Tabelle mit einem Primärschlüssel oder verschieben Sie ihre Zeilen manuell. |
| `PRIMARY_KEY_DIFFERS` | — | Die Spalten des Primärschlüssels oder deren Typen unterscheiden sich zwischen beiden. | Wenden Sie das Schema zuerst auf das übergeordnete Element an. |
| `TABLE_ADDED` | — | Der Branch hat die Tabelle erstellt. Ein Merge erstellt niemals eine Tabelle. | Erstellen Sie sie mit Ihren Migrationen auf dem übergeordneten Element und führen Sie dann die Zeilen zusammen. |
| `TABLE_DROPPED` | — | Der Branch hat die Tabelle gelöscht. Ein Merge löscht niemals eine Tabelle. | Löschen Sie sie mit Ihren Migrationen. |
| `TABLE_REWRITTEN` | — | Eine Seite hat nach der Erstellung des Branches jede Zeile der Tabelle neu geschrieben – eine Änderung des Spaltentyps, ein `ADD COLUMN` mit flüchtigem Default-Wert, `VACUUM FULL`, `CLUSTER` –, sodass jede Zeile als seitdem geschrieben gilt und nicht mehr ermittelt werden kann, welche Seite welche Zeile geändert hat. | Führen Sie den Merge des Branches vor einer solchen Migration durch oder erstellen Sie den Branch nach der Migration neu aus dem übergeordneten Element. |
| `TOO_LARGE` | — | Die Tabelle enthält auf einer Seite mehr Zeilen, als ein Diff einzeln abgleicht (standardmäßig 100.000, `maxRowsPerTable`). | Erhöhen Sie `maxRowsPerTable` sowohl für den Diff als auch für den Merge, oder verschieben Sie die Zeilen auf andere Weise. |

## Diese Seite aktuell halten

`pnpm verify:docs` schlägt fehl, wenn ein Code, den der Server ausgeben kann, in diesen
Tabellen fehlt, wenn eine Tabelle einen Code auflistet, den nichts auslösen kann, wenn die Statuswerte einer
Zeile nicht exakt denjenigen entsprechen, mit denen die Quelle den Code auslöst, oder wenn eine Code-Familie wie `PG_<SQLSTATE>` keine Zeile
für einen SQLSTATE enthält, auf den Aufrufer stoßen. Der entsprechende Prüfschritt ist
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Er prüft sich zuerst selbst. Der Scan liest Codes aus TypeScript statt aus
einem laufenden Server aus, weshalb seine toten Winkel konstruktionsbedingt unbemerkt bleiben: Er konnte einst
keinen Code erkennen, der über einen Einzeiler-Wrapper übergeben wurde, oder einen, der nach einer Nachricht mit
einer `)` geschrieben war, und meldete "jeder Code, den der Server ausgeben kann, ist dokumentiert"
auf einer Seite, auf der siebzehn davon fehlten. Daher führt der Prüfschritt eine Test-Fixture genau
dieser Formen aus, bevor er diese Seite liest, und verweigert jede Meldung, wenn
er diese nicht erkennen kann.
