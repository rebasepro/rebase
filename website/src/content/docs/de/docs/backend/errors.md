Jeder Fehler, den ein Rebase-Backend zurückgibt, verwendet denselben Envelope und enthält einen stabilen
`code`. Der Code ist das Kriterium, nach dem im Client verzweigt werden sollte: Die Meldung (`message`) ist für Menschen
geschrieben und kann umformuliert werden, der Status wird von einem Dutzend verschiedener Probleme geteilt,
und auf den Code trifft beides nicht zu.

## Der Envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — menschenlesbar. Bei einem `4xx`-Fehler ist dies die spezifische Meldung des Servers;
  bei einem `5xx`-Fehler ist sie bewusst generisch gehalten, da der zugrunde liegende Text
  Hostnamen, Rollen oder Spaltennamen enthalten kann.
- **`code`** — einer der unten aufgeführten Werte. Stabil über Minor-Versionen hinweg.
- **`details`** — optional und niemals garantiert. Siehe die nachfolgenden Regeln.
- **`requestId`** — immer vorhanden, wenn der Request die Request-ID-Middleware
  durchlaufen hat, was auf jede Route unter `basePath` zutrifft.

### `X-Request-ID`

Jeder Request unter `basePath` erhält eine ID: den `X-Request-ID`-Header des Aufrufers,
sofern es sich um eine UUID handelt, andernfalls eine neu erzeugte. Sie wird in der
Response als `X-Request-ID` zurückgegeben, im Fehler-Envelope als `requestId` aufgeführt und
an die Log-Zeile des Servers für diesen Request angehängt.

Das ist der Join-Key. Geben Sie ihn in einem Bugreport an, damit Administratoren genau die
eine Log-Zeile finden können, die den Fehler erklärt – einschließlich des Grundes, der dem
Client aus Sicherheitsgründen verborgen blieb.

Das Senden einer eigenen ID ermöglicht es einem Trace, Netzwerksprünge (Hops) zu überstehen: Ein Gateway oder Job-Runner,
der den Header weiterleitet, erhält so eine einheitliche ID über jeden Dienst hinweg, der den Request verarbeitet hat.
Ein ungültiger Wert wird ignoriert und nicht abgewiesen – wegen eines fehlerhaften Headers eines
Aufrufers soll kein Request scheitern. Gehen Sie daher nicht davon aus, dass die gesendete ID der
empfangenen ID entspricht. Prüfen Sie den Response-Header.

### Was in `details` enthalten ist

`details` dient Diagnosezwecken und stellt keinen Vertrag dar. Drei Regeln bestimmen den Inhalt:

1. **Alles, was eine Route explizit festlegt, wird immer zurückgegeben.** Dies sind die
   präzise beschriebenen Fehler des Aufrufers: welches Filterfeld unbekannt war,
   welche Relation schreibgeschützt ist, welcher Wert nicht zum Datentyp passte.
2. **Datenbankdiagnosen werden in Produktionsumgebungen gekürzt.** Wenn der Fehler von
   Postgres stammt, ist `details.dbCode` – der SQLSTATE – immer vorhanden: Er benennt
   die Problemklasse, verrät aber nichts über die Daten. `dbMessage`,
   `detail` und `hint` werden nur hinzugefügt, wenn `NODE_ENV` nicht `production` ist,
   da Postgres Zeileninhalte in diese Felder einbettet. `23505` meldet
   `Key (email)=(a@b.c) already exists.`, was für jede beliebige Adresse die Frage "Ist diese Person
   registriert?" beantworten würde.
3. **Verzweigen Sie im Code niemals anhand von `details`.** Verzweigen Sie anhand von `code`. Der Inhalt von
   `details` ist das, was für eine Person an dieser Aufrufstelle nützlich war, und kann sich ändern.

## Statuscodes interpretieren

| Status | Bedeutung für den Request |
| --- | --- |
| `400` | Fehlerhaft aufgebaut (malformed) oder fragt etwas an, das im Schema nicht existiert. Korrigieren Sie den Request. |
| `401` | Nicht authentifiziert oder die Anmeldedaten sind abgelaufen. Anmelden oder Token erneuern. |
| `403` | Authentifiziert, aber nicht berechtigt. Ein erneuter Versuch mit derselben Identität wird nicht helfen. |
| `404` | Keine solche Route, Tabelle oder Zeile – oder eine Zeile, die durch Row-Level Security ausgeblendet wird. |
| `409` | Konflikt mit dem bestehenden Zustand: ein Duplikat oder ein konkurrierender Schreibvorgang. |
| `413` `415` `422` | Der Body ist zu groß, hat den falschen Medientyp oder wurde semantisch abgelehnt. |
| `429` | Rate-Limit erreicht. Anfragen drosseln; die Nachricht gibt an, wie lange gewartet werden muss. |
| `500` | Fehler beim Server oder seiner Datenbank, nicht beim Aufrufer. Prüfen Sie die Logs. |
| `501` | Die Route existiert, aber dieses Deployment kann sie nicht bedienen – ein Feature ist deaktiviert oder unkonfiguriert. |
| `502` `503` `504` | Eine Abhängigkeit war nicht erreichbar, nicht konfiguriert oder zu langsam. |

## `PG_<SQLSTATE>` — ein von der Datenbank abgelehnter Constraint

Schlägt ein Schreibvorgang in Postgres aus Gründen fehl, die in den *Daten des Aufrufers* liegen,
antwortet das Backend mit dem SQLSTATE im Code: `PG_23505`, `PG_23503` usw. Das ist eine
Familie von Codes, keine feste Liste – Postgres definiert hunderte von SQLSTATEs. Jedoch
erreichen nur zwei Klassen diese Stelle, da nur diese beiden auf Fehler des Aufrufers zurückzuführen sind:

- **Klasse 23**, Integritätsverletzung (Integrity Constraint Violation): ein Duplikat, ein Fremdschlüssel auf ein
  nicht existentes Ziel, eine leere NOT-NULL-Spalte;
- **Klasse 22**, Daten-Ausnahme (Data Exception): ein Wert, der vom Datentyp der Spalte nicht aufgenommen werden kann.

Alles andere – Verbindungsabbruch, fehlende Spalte, Berechtigungsproblem –
liegt in der Verantwortung des Servers und bleibt ein `500`. `code.startsWith("PG_")` ist daher eine verlässliche Prüfung
für "die gesendete Zeile war ungültig". Die vier unten genannten Codes sind diejenigen,
auf die ein Client in der Praxis trifft. `details.dbCode` enthält bei allen denselben SQLSTATE, und
die Meldung nennt den verletzten Constraint.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Ein Wert konnte nicht als Spaltentyp interpretiert werden – das schreibende Pendant zu `INVALID_FILTER_VALUE`. | Senden Sie einen Wert, der dem Spaltentyp entspricht. |
| `PG_23502` | 400 | Eine `NOT NULL`-Spalte wurde leer gelassen. | Senden Sie das Feld mit oder definieren Sie einen Default-Wert für die Spalte. |
| `PG_23503` | 400 / 409 | Beim Speichern: Ein Fremdschlüssel verweist auf eine nicht existierende Zeile (400). Beim Löschen: Andere Zeilen verweisen noch auf diese Zeile (409; ein `RESTRICT`-Schlüssel löst `PG_23001` aus, ebenfalls 409). | Erstellen Sie zuerst die Zielzeile oder korrigieren Sie die ID; beim Löschen: entfernen oder verweisen Sie abhängige Zeilen zuerst um. |
| `PG_23505` | 409 | Ein Unique Constraint wurde verletzt. Die Meldung benennt den Constraint. | Verwenden Sie einen anderen Wert oder aktualisieren Sie die bestehende Zeile. |

### Gründe, warum Tabellen eines Branches nicht gemergt werden können

`BRANCH_MERGE_BLOCKED` listet jede abgewiesene Tabelle in `details.tables` mit einem
dieser Codes auf. Derselbe Code steht im `blocked`-Feld der Tabelle im Diff selbst,
sodass Studio dies anzeigen kann, noch bevor **Merge** geklickt wird. Keiner dieser Codes
stellt eine eigenständige HTTP-Response dar.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Die Spalten der Tabelle unterscheiden sich zwischen Branch und Parent. Zeilen werden nur über gemeinsame Spalten verglichen. | Fehlende Spalten per Migration (`rebase db push`) zum Parent hinzufügen, dann mergen. Eine Migration, die die Tabelle umschreibt (z. B. Spaltentypänderung), führt zu `TABLE_REWRITTEN`: Vor einer solchen Änderung mergen oder den Branch danach neu anlegen. |
| `NO_PRIMARY_KEY` | — | Die Tabelle besitzt keinen Primärschlüssel, weshalb Zeilen nicht einzeln verglichen werden können; der Diff weist nur die Zeilenanzahl aus. | Definieren Sie einen Primärschlüssel oder übertragen Sie Zeilen manuell. |
| `PRIMARY_KEY_DIFFERS` | — | Die Spalten des Primärschlüssels oder deren Datentypen weichen voneinander ab. | Schema zuerst auf den Parent anwenden. |
| `TABLE_ADDED` | — | Der Branch hat die Tabelle neu erstellt. Ein Merge erstellt niemals neue Tabellen. | Erstellen Sie die Tabelle per Migration auf dem Parent und mergen Sie anschließend deren Zeilen. |
| `TABLE_DROPPED` | — | Der Branch hat die Tabelle gelöscht. Ein Merge löscht niemals Tabellen. | Löschen Sie die Tabelle per Migration. |
| `TABLE_REWRITTEN` | — | Eine Seite hat alle Zeilen der Tabelle nach Branch-Erstellung neu geschrieben – Spaltentypänderung, `ADD COLUMN` mit volatilem Default, `VACUUM FULL`, `CLUSTER` – sodass jede Zeile als neu modifiziert gilt und Ursprünge nicht mehr zugeordnet werden können. | Den Branch vor einer solchen Migration mergen oder ihn danach neu vom Parent abzweigen. |
| `TOO_LARGE` | — | Die Tabelle enthält auf einer Seite mehr Zeilen, als ein Diff einzeln abgleicht (standardmäßig 100.000, `maxRowsPerTable`). | Erhöhen Sie `maxRowsPerTable` für Diff und Merge oder migrieren Sie die Zeilen auf anderem Wege. |

## Richtigkeit dieser Seite gewährleisten

`pnpm verify:docs` schlägt fehl, wenn ein vom Server werfbarer Code in diesen
Tabellen fehlt, wenn eine Tabelle einen Code auflistet, der nirgends geworfen werden kann,
wenn die Statuswerte einer Zeile nicht exakt denen des Quellcodes entsprechen, oder wenn eine Code-Familie wie `PG_<SQLSTATE>` keine Zeile
für einen SQLSTATE enthält, dem Aufrufer in der Praxis begegnen. Der entsprechende Prüfschritt ist
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Das Skript überprüft sich zunächst selbst: Der Scan extrahiert Codes aus dem TypeScript-Code und nicht aus
einem laufenden Server. Seine blinden Flecken sind daher konstruktionsbedingt lautlos: Es übersah
früher Codes, die über Einzeilen-Wrapper übergeben wurden oder nach Meldungen mit einer schließenden
Klammer `)` standen, und meldete fälschlicherweise "alle Servercodes sind dokumentiert"
auf einer Seite, auf der siebzehn Codes fehlten. Der Prüfschritt führt daher ein Fixture
genau dieser Syntaxformen aus, bevor er diese Seite prüft, und verweigert die Validierung,
wenn er diese Testfälle nicht erkennt.
