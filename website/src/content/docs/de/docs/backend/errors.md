Jeder Fehler, den ein Rebase-Backend zurückgibt, verwendet dieselbe Envelope-Struktur und enthält einen stabilen `code`. Der Code ist das Kriterium für Fallunterscheidungen: Die Nachricht ist für Menschen verfasst und kann umformuliert werden, der Status wird von dutzenden verschiedenen Problemen geteilt – der Code ist keines von beidem.

## Der Envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — menschenlesbar. Bei einem `4xx` ist es die serverspezifische Meldung; bei einem `5xx` ist sie bewusst generisch gehalten, da der zugrunde liegende Text Hostnamen, Rollen oder Spaltennamen zitieren kann.
- **`code`** — einer der unten aufgeführten Werte. Stabil über Minor-Versionen hinweg.
- **`details`** — optional und nie garantiert. Siehe die Regeln unten.
- **`requestId`** — vorhanden, wann immer die Anfrage die Request-ID-Middleware durchlaufen hat, was für jede Route unter `basePath` gilt.

### `X-Request-ID`

Jede Anfrage unter `basePath` erhält eine ID: den `X-Request-ID`-Header des Aufrufers, wenn es sich um eine UUID handelt, andernfalls eine neu generierte. Sie wird im Response-Header als `X-Request-ID` zurückgegeben, im Fehler-Envelope als `requestId` eingefügt und an die Server-Logzeile für diese Anfrage angehängt.

Das ist der Join-Key. Geben Sie ihn in einem Fehlerbericht an, und ein Administrator kann genau die eine Logzeile finden, die den Fehler erklärt und den Grund enthält, der dem Client niemals angezeigt wurde.

Das Senden einer eigenen ID ermöglicht es einem Trace, Netzwerkhops zu überstehen: Ein Gateway oder Job-Runner, der den Header weiterleitet, sorgt für eine einheitliche ID über alle Dienste hinweg, die die Anfrage verarbeitet haben. Ein ungültiger Wert wird ignoriert und nicht abgelehnt – ein fehlerhafter Header eines Aufrufers ist es nicht wert, eine Anfrage fehlschlagen zu lassen –, gehen Sie also nicht davon aus, dass die gesendete ID der empfangenen entspricht. Lesen Sie den Response-Header.

### Was in `details` enthalten ist

`details` dient der Diagnose und ist nicht vertraglich zugesichert. Drei Regeln bestimmen den Inhalt:

1. **Alles, was eine Route explizit festlegt, wird immer zurückgegeben.** Dies sind die präzise beschriebenen eigenen Fehler des Aufrufers: welches Filterfeld unbekannt war, welche Relation nicht schreibbar ist, welcher Wert nicht zu seinem Typ passte.
2. **Datenbankdiagnosen werden in der Produktion gekürzt.** Wenn der Fehler von Postgres stammte, ist `details.dbCode` – der SQLSTATE – immer vorhanden: Er benennt die Problemklasse und gibt nichts über die Daten preis. `dbMessage`, `detail` und `hint` werden nur hinzugefügt, wenn `NODE_ENV` nicht `production` ist, da Postgres Zeileninhalte darin platziert. `23505` meldet `Key (email)=(a@b.c) already exists.`, was für jede beliebige Adresse die Frage "Ist diese Person registriert?" beantworten würde.
3. **Führen Sie Verzweigungen niemals anhand von `details` durch.** Verzweigen Sie anhand von `code`. Was unter `details` steht, ist das, was an dieser Aufrufstelle für einen Menschen nützlich war, und das kann sich ändern.

## Einen Status interpretieren

| Status | Was er über die Anfrage aussagt |
| --- | --- |
| `400` | Fehlerhafter Aufbau oder Anforderung von Daten, die im Schema nicht existieren. Beheben Sie die Anfrage. |
| `401` | Nicht authentifiziert oder die Zugangsdaten sind abgelaufen. Melden Sie sich an oder aktualisieren Sie das Token. |
| `403` | Authentifiziert, aber nicht autorisiert. Ein erneuter Versuch mit derselben Identität wird nicht helfen. |
| `404` | Keine solche Route, Tabelle oder Zeile – oder eine Zeile, die durch Row-Level Security verborgen wird. |
| `409` | Ein Konflikt mit dem bestehenden Zustand: ein Duplikat oder ein gleichzeitiger Schreibvorgang. |
| `413` `415` `422` | Der Body ist zu groß, hat den falschen Medientyp oder wurde semantisch abgelehnt. |
| `429` | Rate-Limit erreicht. Anfragen drosseln; die Nachricht gibt an, wie lange gewartet werden muss. |
| `500` | Der Server oder seine Datenbank ist fehlerhaft, nicht der Aufrufer. Prüfen Sie die Logs. |
| `501` | Die Route existiert, aber dieses Deployment kann sie nicht bedienen – eine Funktion ist deaktiviert oder unkonfiguriert. |
| `502` `503` `504` | Eine Abhängigkeit war nicht erreichbar, nicht konfiguriert oder zu langsam. |

## `PG_<SQLSTATE>` — ein von der Datenbank abgelehnter Constraint

Ein Schreibvorgang, den Postgres aus Gründen ablehnt, die in den *Daten des Aufrufers* liegen, antwortet mit dem SQLSTATE im Code: `PG_23505`, `PG_23503` usw. Das ist eine Familie, keine feste Liste – Postgres definiert Hunderte von SQLSTATEs –, aber nur zwei Klassen erreichen diesen Zustand, da nur diese beiden vom Aufrufer verschuldet sind:

- **Klasse 23**, Verletzung von Integritäts-Constraints: ein Duplikat, ein Fremdschlüssel, der ins Leere zeigt, eine leere `NOT NULL`-Spalte;
- **Klasse 22**, Daten-Ausnahme (Data Exception): ein Wert, der vom Spaltentyp nicht aufgenommen werden kann.

Alles andere – eine abgebrochene Verbindung, eine fehlende Spalte, ein Berechtigungsproblem – liegt auf Serverseite und bleibt ein `500`. Daher ist `code.startsWith("PG_")` eine zuverlässige Prüfung für "die von mir gesendete Zeile war fehlerhaft", und die vier folgenden Codes sind diejenigen, denen Clients tatsächlich begegnen. `details.dbCode` enthält bei allen denselben SQLSTATE, und die Nachricht benennt den Constraint.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Ein Wert konnte nicht als Spaltentyp interpretiert werden – das schreibseitige Gegenstück zu `INVALID_FILTER_VALUE`. | Senden Sie einen Wert passend zum Spaltentyp. |
| `PG_23502` | 400 | Eine `NOT NULL`-Spalte wurde leer gelassen. | Senden Sie das Feld mit oder versehen Sie die Spalte mit einem Standardwert. |
| `PG_23503` | 400 / 409 | Beim Speichern: Ein Fremdschlüssel verweist auf eine nicht existierende Zeile (400). Beim Löschen: Andere Zeilen referenzieren diese noch (409; ein `RESTRICT`-Schlüssel löst `PG_23001` aus, ebenfalls 409). | Erstellen Sie zuerst die Zielzeile oder korrigieren Sie die ID; beim Löschen müssen referenzierende Zeilen zuerst entfernt oder umgebogen werden. |
| `PG_23505` | 409 | Ein Unique-Constraint wurde verletzt. Die Meldung benennt den Constraint. | Verwenden Sie einen anderen Wert oder aktualisieren Sie die bestehende Zeile. |

Eine deklarierte Spalte wird gelöscht, indem sie aus `defineTable` entfernt, deployt und anschließend reconcilt wird. |
| `SCHEMA_RECONCILE_STALE` | 409 | Die Datenbank oder die Tabellen wurden seit dem bestätigten Plan geändert. `details.plan` zeigt den neuen Plan. | Prüfen Sie den neuen Plan und bestätigen Sie dessen `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | An `/reconcile/apply` wurde kein `confirm` übermittelt. | Führen Sie zuerst den Plan-Schritt aus und senden Sie den `digest` des Plans als `confirm`. Das CLI erledigt dies nach Eingabe von `yes`. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | Der Treiber dieses Backends kann keinen Reconcile planen oder kein SQL ausführen. | Reconcile funktioniert auf Postgres. |

### Warum die Tabelle eines Branches nicht zusammengeführt werden kann

`BRANCH_MERGE_BLOCKED` listet jede abgewiesene Tabelle in `details.tables` mit einem
dieser Codes auf. Derselbe Code steht auch an `blocked` der Tabelle im Diff selbst,
sodass Studio dies anzeigen kann, bevor jemand auf **Merge** klickt. Keiner davon ist eine eigenständige
HTTP-Antwort.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Die Spalten der Tabelle unterscheiden sich zwischen dem Branch und seinem Parent. Zeilen werden anhand der gemeinsamen Spalten verglichen. | Fügen Sie dem Parent die fehlenden Spalten über Ihre Migrationen hinzu (`rebase db push`), dann mergen. Eine Migration, die die Tabelle umschreibt (z. B. Spaltentypänderung), führt zu `TABLE_REWRITTEN`: Führen Sie den Merge vor einer solchen Änderung durch oder erstellen Sie den Branch danach neu. |
| `NO_PRIMARY_KEY` | — | Die Tabelle besitzt keinen Primärschlüssel, sodass Zeilen nicht einzeln abgeglichen werden können; das Diff liefert lediglich die Zeilenanzahl. | Versehen Sie die Tabelle mit einem Primärschlüssel oder übertragen Sie deren Zeilen manuell. |
| `PRIMARY_KEY_DIFFERS` | — | Die Primärschlüssel-Spalten oder deren Typen unterscheiden sich zwischen beiden Seiten. | Wenden Sie das Schema zuerst auf dem Parent an. |
| `TABLE_ADDED` | — | Der Branch hat die Tabelle neu erstellt. Ein Merge erstellt niemals Tabellen. | Erstellen Sie sie auf dem Parent über Ihre Migrationen und mergen Sie danach deren Zeilen. |
| `TABLE_DROPPED` | — | Der Branch hat die Tabelle gelöscht. Ein Merge löscht niemals Tabellen. | Löschen Sie sie über Ihre Migrationen. |
| `TABLE_REWRITTEN` | — | Eine Seite hat nach der Branch-Erstellung jede Zeile der Tabelle neu geschrieben – eine Spaltentypänderung, ein `ADD COLUMN` mit volatilem Standardwert, `VACUUM FULL`, `CLUSTER` –, sodass jede Zeile als seitdem geändert gilt und nicht mehr ermittelt werden kann, welche Seite welche Zeile modifiziert hat. | Mergen Sie den Branch vor einer solchen Migration oder erstellen Sie den Branch vom Parent danach neu. |
| `TOO_LARGE` | — | Die Tabelle enthält auf einer Seite mehr Zeilen, als ein Diff einzeln abgleicht (standardmäßig 100.000, `maxRowsPerTable`). | Erhöhen Sie `maxRowsPerTable` sowohl für das Diff als auch für den Merge, oder verschieben Sie die Zeilen auf anderem Weg. |

## Generische Codes

Eine Route verwendet einen dieser Codes, wenn kein spezifischerer zutrifft.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Fehlerhafter Aufbau der Anfrage, und kein spezifischerer Code trifft zu. | Siehe Fehlermeldung. |
| `UNAUTHORIZED` | 401 | Nicht authentifiziert oder Zugangsdaten wurden abgelehnt. | Melden Sie sich an oder aktualisieren Sie das Token. |
| `FORBIDDEN` | 403 | Authentifiziert, aber nicht autorisiert. | Ein erneuter Versuch mit derselben Identität wird nicht helfen. |
| `CONFLICT` | 409 | Ein Konflikt mit dem bestehenden Zustand. | Siehe Fehlermeldung. |
| `INTERNAL_ERROR` | 500 | Auf dem Server ist ein Fehler aufgetreten. Die Nachricht ist bewusst generisch gehalten. | Geben Sie die `requestId` an; die Ursache befindet sich in den Server-Logs. |
| `NOT_CONFIGURED` | 503 | Eine für diese Route erforderliche Abhängigkeit ist auf diesem Server nicht konfiguriert. | Siehe Fehlermeldung. |
| `SERVICE_UNAVAILABLE` | 503 | Ein Dienst, von dem die Anfrage abhängt, konnte nicht erreicht werden: ein S3- oder MinIO-Bucket oder ein Host, den eine Funktion per `fetch()` aufruft, der die Verbindung verweigert oder nicht aufgelöst werden kann. Das Server-Log nennt den Host; die Antwort tut dies nicht. Eine nicht erreichbare Datenbank liefert `DATABASE_UNAVAILABLE`. Eine fehlschlagende Verbindung zu einem solchen Dienst antwortet hiermit. | Erneut versuchen; Logs prüfen. |

## Diese Seite aktuell halten

`pnpm verify:docs` schlägt fehl, wenn ein Code, den der Server auslösen kann, in diesen
Tabellen fehlt, wenn eine Tabelle einen Code auflistet, den nichts auslösen kann, wenn die Statuswerte
einer Zeile nicht exakt denen entsprechen, mit denen der Quellcode den Code auslöst, oder wenn für eine Code-Familie wie `PG_<SQLSTATE>`
eine Zeile für einen SQLSTATE fehlt, dem Aufrufer begegnen können. Die Prüfstufe ist
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Sie prüft sich zuerst selbst. Der Scan liest Codes aus dem TypeScript-Code und nicht aus
einem laufenden Server aus, weshalb tote Winkel konstruktionsbedingt unbemerkt blieben: Einst
konnte ein Code nicht erkannt werden, der durch einen einzeiligen Wrapper übergeben wurde, oder einer, der nach einer Nachricht mit einer `)`
stand, und meldete "jeder Code, den der Server werfen kann, ist dokumentiert"
für eine Seite, auf der siebzehn Codes fehlten. Daher führt diese Stufe ein Fixture mit genau
diesen Mustern aus, bevor sie diese Seite liest, und verweigert die Ausgabe eines Ergebnisses, wenn
sie diese nicht erkennen kann.
