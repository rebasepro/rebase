Jeder Fehler, den ein Rebase-Backend zurückgibt, verwendet denselben Envelope und enthält einen stabilen `code`. Der Code ist der Wert, auf den verzweigt werden sollte: Die Nachricht ist für Menschen formuliert und kann sich im Wortlaut ändern, der Status wird von einem Dutzend verschiedener Probleme geteilt, und der Code ist keines von beidem.

## Der Envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — menschenlesbar. Bei einem `4xx` ist es die servereigene Meldung; bei einem `5xx` ist sie bewusst generisch gehalten, da der zugrunde liegende Text Hosts, Rollen oder Spaltennamen zitieren kann.
- **`code`** — einer der unten aufgeführten Werte. Stabil über Minor-Versionen hinweg.
- **`details`** — optional und niemals garantiert. Siehe die unten stehenden Regeln.
- **`requestId`** — vorhanden, wann immer die Anfrage die Request-ID-Middleware durchlaufen hat, was auf jede Route unter `basePath` zutrifft.

### `X-Request-ID`

Jede Anfrage unter `basePath` erhält eine ID: den `X-Request-ID`-Header des Aufrufers, sofern es sich um eine UUID handelt, andernfalls eine neu generierte. Sie wird in der Antwort als `X-Request-ID` zurückgegeben, im Fehler-Envelope als `requestId` aufgeführt und an die Log-Zeile des Servers für diese Anfrage angehängt.

Das ist der Join-Key. Geben Sie ihn in einem Fehlerbericht an, und ein Operator kann genau die eine Log-Zeile finden, die den Fehler erklärt und den Grund enthält, der dem Client nie angezeigt wurde.

Einen eigenen Header zu senden stellt sicher, dass ein Trace Hops übersteht: Ein Gateway oder ein Job-Runner, der den Header weiterleitet, sorgt für eine einheitliche ID über alle Dienste hinweg, die die Anfrage verarbeitet haben. Ein ungültiger Wert wird ignoriert statt abgewiesen — wegen eines fehlerhaften Headers eines Aufrufers sollte eine Anfrage nicht fehlschlagen —, gehen Sie also nicht davon aus, dass die gesendete ID der empfangenen ID entspricht. Lesen Sie den Response-Header.

### Was in `details` steht

`details` dient der Diagnose und ist nicht vertraglich bindend. Drei Regeln bestimmen den Inhalt:

1. **Alles, was eine Route explizit setzt, wird immer zurückgegeben.** Dies sind die präzise beschriebenen Fehler des Aufrufers selbst: welches Filterfeld unbekannt war, welche Relation nicht schreibbar ist, welcher Wert nicht zu seinem Typ passte.
2. **Datenbankdiagnosen werden in der Produktion gekürzt.** Wenn der Fehler von Postgres stammt, ist `details.dbCode` — der SQLSTATE — immer vorhanden: Er benennt die Problemklasse und gibt nichts über die Daten preis. `dbMessage`, `detail` und `hint` werden nur hinzugefügt, wenn `NODE_ENV` nicht `production` ist, da Postgres Zeileninhalte darin platziert. `23505` meldet `Key (email)=(a@b.c) already exists.`, was für jede beliebige Adresse, die jemand ausprobieren möchte, die Frage „Ist diese Person registriert?“ beantwortet.
3. **Verzweigen Sie niemals auf `details`.** Verzweigen Sie auf `code`. Was unter `details` steht, ist das, was an dieser Aufrufstelle für Menschen nützlich war, und es kann sich ändern.

## Einen Status interpretieren

| Status | Was er über die Anfrage aussagt |
| --- | --- |
| `400` | Fehlerhaft aufgebaut oder fordert etwas an, das im Schema nicht existiert. Korrigieren Sie die Anfrage. |
| `401` | Nicht authentifiziert oder die Anmeldeinformationen sind abgelaufen. Melden Sie sich an oder aktualisieren Sie das Token. |
| `403` | Authentifiziert, aber nicht berechtigt. Ein erneuter Versuch mit derselben Identität hilft nicht. |
| `404` | Keine solche Route, Collection oder Zeile — oder eine Zeile, die durch Row-Level Security verborgen wird. |
| `409` | Ein Konflikt mit dem bestehenden Zustand: ein Duplikat oder ein gleichzeitiger Schreibvorgang. |
| `413` `415` `422` | Der Body ist zu groß, hat den falschen Medientyp oder wurde semantisch abgelehnt. |
| `429` | Rate-Limit erreicht. Warten Sie; die Meldung gibt an, wie lange. |
| `500` | Der Server oder seine Datenbank ist fehlerhaft, nicht der Aufrufer. Überprüfen Sie die Logs. |
| `501` | Die Route existiert, aber dieses Deployment kann sie nicht bedienen — ein Feature ist deaktiviert oder unkonfiguriert. |
| `502` `503` `504` | Eine Abhängigkeit war nicht erreichbar, unkonfiguriert oder zu langsam. |

## `PG_<SQLSTATE>` — eine von der Datenbank abgelehnte Bedingung

Ein Schreibvorgang, den Postgres aus einem Grund ablehnt, der *in den Daten des Aufrufers* liegt, antwortet mit dem SQLSTATE im Code: `PG_23505`, `PG_23503` usw. Das ist eine Familie, keine feste Liste — Postgres definiert Hunderte von SQLSTATEs —, aber nur zwei Klassen erreichen diesen Zustand je, da nur diese beiden vom Aufrufer verschuldet sind:

- **Klasse 23**, Verletzung von Integritätsbedingungen (Integrity Constraint Violation): ein Duplikat, ein Fremdschlüssel, der ins Leere zeigt, eine leer gelassene NOT NULL-Spalte;
- **Klasse 22**, Daten-Ausnahme (Data Exception): ein Wert, den der Typ der Spalte nicht aufnehmen kann.

Alles andere — eine abgebrochene Verbindung, eine fehlende Spalte, ein Berechtigungsproblem — liegt beim Server und bleibt ein `500`. Daher ist `code.startsWith("PG_")` eine verlässliche Prüfung auf „Die von mir gesendete Zeile war fehlerhaft“, und die vier unten aufgeführten sind diejenigen, denen ein Client tatsächlich begegnet. `details.dbCode` enthält bei allen denselben SQLSTATE, und die Nachricht nennt das Constraint.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Ein Wert konnte nicht als Typ der Spalte gelesen werden — das schreibseitige Gegenstück zu `INVALID_FILTER_VALUE`. | Senden Sie einen Wert, der dem Spaltentyp entspricht. |
| `PG_23502` | 400 | Eine `NOT NULL`-Spalte wurde leer gelassen. | Senden Sie das Feld mit oder versehen Sie die Spalte mit einem Standardwert. |
| `PG_23503` | 400 / 409 | Beim Speichern verweist ein Fremdschlüssel auf eine Zeile, die nicht existiert (400). Beim Löschen verweisen andere Zeilen noch auf diese (409; ein `RESTRICT`-Schlüssel wirft `PG_23001`, ebenfalls 409). | Erstellen Sie zuerst die Zielzeile oder korrigieren Sie die ID; entfernen Sie beim Löschen zuerst die referenzierenden Zeilen oder biegen Sie sie um. |
| `PG_23505` | 409 | Ein Eindeutigkeits-Constraint (Unique Constraint) wurde verletzt. Die Nachricht nennt das Constraint. | Verwenden Sie einen anderen Wert oder aktualisieren Sie die bestehende Zeile. |

Diese Codes besagen, dass ein Feature deaktiviert oder unkonfiguriert ist, und nicht, dass die Anfrage falsch war. Jeder dieser Fehler wird auch auf der entsprechenden `/status`-Route mit `200` gemeldet, sodass ein Panel das Feature ausgrauen kann, anstatt einen Fehler anzuzeigen.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `ADMIN_SURFACE_UNAVAILABLE` | 501 | Eine reine Admin-Oberfläche wurde auf einem Server ohne konfigurierte Authentifizierung aufgerufen, sodass nichts einen Administrator von einem Fremden unterscheiden kann. | Setzen Sie `auth.jwtSecret` oder übergeben Sie einen `AuthAdapter`. |
| `BRANCH_DIFF_STALE` | 409 | `POST /api/admin/branches/:name/merge` wurde der Fingerprint eines Diffs gesendet, der nicht mehr zutrifft: Der Branch oder sein Parent hat sich seitdem geändert. Es wurde nichts geschrieben. | Lesen Sie das Diff erneut, überprüfen Sie es und führen Sie den Merge mit dem neuen `fingerprint` durch. |
| `BRANCH_DIFF_UNSUPPORTED` | 501 | Die Datenquelle kann Branches nicht vergleichen: Sie besitzt kein SQL oder kein Branching (keine Admin-Verbindung). | Verwenden Sie ein Postgres-Backend mit gesetztem `adminConnectionString`. |
| `BRANCH_MERGE_BLOCKED` | 409 | Eine Tabelle mit Abweichungen kann nicht gemergt werden — durch den Branch hinzugefügt oder entfernt, abweichende Spalten oder Primärschlüssel, kein Primärschlüssel, zu viele Zeilen zum Abgleichen oder seit der Erstellung des Branches neu geschrieben (`TABLE_REWRITTEN`). Eine Tabelle, deren Zeilen nicht abgeglichen werden konnten, blockiert selbst dann, wenn ihre Zähler 0 anzeigen: Sie sind unbekannt, nicht null. `details.tables` nennt jede Tabelle mit Begründung. Es wurde nichts geschrieben. | Wenden Sie das Schema zuerst mit Ihren Migrationen an, oder führen Sie den Merge mit `skipBlocked: true` durch, um diese Tabellen unverändert zu lassen. |
| `BRANCH_MERGE_CONFLICT` | 409 | Zeilen wurden sowohl auf dem Branch als auch auf seinem Parent geändert, und `onConflict` war `"abort"` (Standard); oder der Parent hat einen Teil des Merges abgelehnt — eine Zeile hat sich zwischenzeitlich geändert, ein Trigger hat sie übersprungen, eine Policy hat sie verborgen. Es wurde nichts geschrieben. | Wählen Sie mit `onConflict: "branch"` oder `"target"`, welche Seite gewinnt, oder lesen Sie das Diff erneut. |
| `BRANCH_MERGE_FAILED` | 409 | Der Parent hat die Zeilen des Branches innerhalb des Merge-Statements abgelehnt — ein Constraint, ein Enum-Label oder ein Fremdschlüssel, den er besitzt und den die Zeilen des Branches verletzen, meist weil sich die beiden Schemas unterscheiden. `details` enthält `sqlState`, `table`, `constraint` und `detail`. Es wurde nichts geschrieben. | Lesen Sie die Schema-Änderungen des Diffs, bringen Sie das Schema des Parents mit Ihren Migrationen in Einklang oder korrigieren Sie die Zeilen des Branches und führen Sie den Merge erneut durch. |
| `BRANCH_NOT_FOUND` | 404 | Kein Branch mit diesem Namen in der Registry. | `rebase db branch list` oder der Bereich „Branches“ listet die vorhandenen auf. |
| `CONTRACT_UNAVAILABLE` | 404 | Der Projekt-Contract wird nur bereitgestellt, wenn Authentifizierung konfiguriert ist — er beschreibt jede Tabelle und Relation. | Konfigurieren Sie Auth. `/meta/schema-version` wird immer bereitgestellt. |
| `DEV_MAILBOX_UNAVAILABLE` | 501 | Kein Entwicklungs-Postfach aktiv. E-Mails werden nur abgefangen, wenn `SMTP_HOST` nicht gesetzt und `NODE_ENV` nicht `production` ist. | Entfernen Sie `SMTP_HOST` in der Entwicklungsumgebung oder lesen Sie das echte Postfach. |
| `INVALID_CHANGE` | 400 | Die vorgeschlagene Schemaänderung ist nicht wohlgeformt. | Siehe die Nachricht. |
| `SCHEMA_CHANGE_FAILED` | 400 | Das Anwenden einer geplanten Schemaänderung ist aus einem Grund fehlgeschlagen, den spezifischere Codes nicht abdecken. | Siehe die Nachricht; sie gibt den zugrunde liegenden Fehler wortwörtlich wieder. |
| `SCHEMA_CHANGE_UNAPPLICABLE` | 400 | Die Änderung ist gültig, kann aber auf das Schema in seinem aktuellen Zustand nicht angewendet werden. | Siehe die Nachricht. |
| `SCHEMA_EDIT_DIRTY_TREE` | 409 | Das Repository enthält nicht committete Änderungen, sodass die Bearbeitung nicht sicher angewendet werden konnte. | Committen oder stashen Sie und versuchen Sie es erneut. |
| `SCHEMA_EDIT_REFUSED` | 400 | Der Schema-Editor hat die Bearbeitung abgelehnt. | Siehe die Nachricht; es ist die eigene Ablehnung des Editors. |
| `SCHEMA_EDIT_REQUIRES_A_PERSON` | 403 | Ein API-Schlüssel oder ein anderer maschineller Principal hat versucht, eine Schemaänderung anzuwenden. | Melden Sie sich als Benutzer an oder setzen Sie `liveSchema.allowMachineApply`. |
| `SCHEMA_EDITING_NO_COLLECTIONS_DIR` | 501 | Live-Schema-Editing erfordert `collectionsDir` oder `liveSchema.repository`, und dieser Server wurde mit keinem von beiden gestartet. | Konfigurieren Sie eines davon. |
| `SCHEMA_EDITING_NO_REPOSITORY` | 503 | Das Planen funktioniert; es gibt kein Repository, in das die Änderung committet werden könnte. | Konfigurieren Sie `liveSchema.repository`. |
| `SCHEMA_EDITING_PROVISIONING_OFF` | 409 | Dieses Deployment ändert nichts an seiner Datenbank (`REBASE_PROVISION=false`), sodass eine Änderung nicht über das Panel angewendet werden kann. | Committen Sie sie nur als Quellcode und lassen Sie sie von dem Prozess anwenden, der Änderungen an der Datenbank durchführt. |
| `SCHEMA_EDITING_UNSUPPORTED` | 503 | Dieser Treiber kann Schemaänderungen nicht planen. | Live-Editing ist unter Postgres verfügbar. |

| `SCHEMA_EDITOR_NO_COLLECTIONS_DIR` | 501 | Der Server besitzt kein `collectionsDir`, sodass der Editor kein Ziel zum Schreiben hat. | Setzen Sie `collectionsDir`. |
| `SCHEMA_EDITOR_PRODUCTION` | 501 | Der Editor ist unter `NODE_ENV=production` deaktiviert: Die Dateien eines bereitgestellten Servers werden bei jedem Deployment aus Ihrem Repository neu gebaut, sodass eine Bearbeitung hier verworfen würde. | Bearbeiten Sie Collections in der Entwicklungsumgebung und deployen Sie, oder konfigurieren Sie `liveSchema.repository`, um sie dort zu committen. |

### Schemaabgleich (Schema reconcile)

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) plant
über `POST /api/admin/schema/reconcile/plan` und wendet Änderungen über
`/reconcile/apply` an. Eine Ablehnung ändert nichts; nur `SCHEMA_RECONCILE_FAILED`
hinterlässt einen Plan teilweise angewendet.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | Der Body ist kein JSON-Objekt, oder `drop` ist keine Liste von `"<collection>.<column>"`-Strings. | Senden Sie `{ "drop": ["voice_cache.wav"] }` oder lassen Sie `drop` weg. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Ein Statement ist mittendrin fehlgeschlagen. Die Statements davor wurden ausgeführt und bleiben angewendet; `details.applied` listet sie auf. | Beheben Sie, was die Nachricht benennt, und planen Sie dann erneut: Der neue Plan lässt aus, was bereits ausgeführt wurde. |
| `SCHEMA_RECONCILE_INVALID` | 400 | Der Plan kann nicht angewendet werden, und die Nachricht listet die Gründe auf: ein `drop`, das nicht `<collection>.<column>` ist, keine Collection oder Spalte nennt, oder eine Spalte nennt, die die Collection weiterhin deklariert. `details.plan` ist der Plan. | Korrigieren Sie die `drop`-Liste. Eine deklarierte Spalte wird gelöscht, indem ihre Eigenschaft entfernt, deployt und anschließend abgeglichen wird. |
| `SCHEMA_RECONCILE_STALE` | 409 | Die Datenbank oder die Collections haben sich seit dem von Ihnen bestätigten Plan geändert. `details.plan` ist der neue Plan. | Überprüfen Sie den neuen Plan und bestätigen Sie seinen `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | An `/reconcile/apply` wurde kein `confirm` gesendet. | Planen Sie zuerst und senden Sie den `digest` des Plans als `confirm`. Die CLI tut dies, sobald Sie `yes` eingeben. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | Der Treiber dieses Backends kann keinen Reconcile planen oder kein SQL ausführen. | Reconcile funktioniert unter Postgres. |

### Warum die Tabelle eines Branches nicht gemergt werden kann

`BRANCH_MERGE_BLOCKED` nennt jede abgelehnte Tabelle in `details.tables` mit einem
dieser Codes. Derselbe Code befindet sich auf dem `blocked` der Tabelle im Diff selbst,
sodass Studio dies anzeigen kann, bevor jemand auf **Merge** klickt. Keiner davon ist eine eigenständige
Response.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Die Spalten der Tabelle unterscheiden sich zwischen dem Branch und seinem Parent. Zeilen werden anhand der gemeinsamen Spalten verglichen. | Fügen Sie die fehlenden Spalten mit Ihren Migrationen (`rebase db push`) zum Parent hinzu und führen Sie dann den Merge durch. Eine Migration, die die Tabelle neu schreibt — eine Änderung des Spaltentyps —, verwandelt dies in `TABLE_REWRITTEN`: Führen Sie den Merge vor einer solchen Änderung durch oder erstellen Sie den Branch danach neu. |
| `NO_PRIMARY_KEY` | — | Die Tabelle besitzt keinen Primärschlüssel, sodass Zeilen nicht einzeln abgeglichen werden können; das Diff gibt nur deren Zeilenanzahl an. | Versehen Sie die Tabelle mit einem Primärschlüssel oder verschieben Sie ihre Zeilen manuell. |
| `PRIMARY_KEY_DIFFERS` | — | Die Spalten des Primärschlüssels oder deren Typen unterscheiden sich zwischen den beiden. | Wenden Sie das Schema zuerst auf den Parent an. |
| `TABLE_ADDED` | — | Der Branch hat die Tabelle erstellt. Ein Merge erstellt niemals eine Tabelle. | Erstellen Sie sie auf dem Parent mit Ihren Migrationen und mergen Sie dann deren Zeilen. |
| `TABLE_DROPPED` | — | Der Branch hat die Tabelle gelöscht. Ein Merge löscht niemals eine Tabelle. | Löschen Sie sie mit Ihren Migrationen. |
| `TABLE_REWRITTEN` | — | Eine Seite hat nach der Erstellung des Branches jede Zeile der Tabelle neu geschrieben — eine Spaltentypänderung, ein `ADD COLUMN` mit flüchtigem Standardwert, `VACUUM FULL`, `CLUSTER` —, sodass jede Zeile als seitdem geschrieben gilt und nicht mehr festgestellt werden kann, welche Seite welche Zeile geändert hat. | Führen Sie den Merge des Branches vor einer solchen Migration durch oder erstellen Sie den Branch danach neu aus dem Parent. |
| `TOO_LARGE` | — | Die Tabelle enthält auf einer Seite mehr Zeilen, als ein Diff einzeln abgleicht (standardmäßig 100.000, `maxRowsPerTable`). | Erhöhen Sie `maxRowsPerTable` sowohl beim Diff als auch beim Merge, oder verschieben Sie die Zeilen auf andere Weise. |

## Generische Codes

Eine Route verwendet einen dieser Codes, wenn nichts Spezifischeres zutrifft.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Fehlerhaft, und nichts Spezifischeres trifft zu. | Siehe die Nachricht. |
| `UNAUTHORIZED` | 401 | Nicht authentifiziert oder die Anmeldeinformationen wurden abgelehnt. | Melden Sie sich an oder aktualisieren Sie das Token. |
| `FORBIDDEN` | 403 | Authentifiziert, aber nicht berechtigt. | Ein erneuter Versuch mit derselben Identität hilft nicht. |
| `CONFLICT` | 409 | Ein Konflikt mit dem bestehenden Zustand. | Siehe die Nachricht. |
| `INTERNAL_ERROR` | 500 | Etwas auf dem Server ist fehlgeschlagen. Die Nachricht ist bewusst generisch gehalten. | Geben Sie die `requestId` an; die Ursache befindet sich in den Logs. |
| `NOT_CONFIGURED` | 503 | Eine Abhängigkeit, die diese Route benötigt, ist auf diesem Server nicht konfiguriert. | Siehe die Nachricht. |
| `SERVICE_UNAVAILABLE` | 503 | Ein Dienst, von dem die Anfrage abhängt, konnte nicht erreicht werden: ein S3- oder MinIO-Bucket oder ein Host, den eine Funktion per `fetch()` aufruft und der die Verbindung verweigert oder nicht auflöst. Das Server-Log nennt den Host; die Response tut dies nicht. Eine nicht erreichbare Datenbank ist `DATABASE_UNAVAILABLE`. Eine fehlschlagende Verbindung zu einem solchen Dienst liefert diese Antwort. | Versuchen Sie es erneut; prüfen Sie die Logs. |

## Diese Seite aktuell halten

`pnpm verify:docs` schlägt fehl, wenn ein Code, den der Server auslösen kann, in diesen
Tabellen fehlt, wenn eine Tabelle einen Code auflistet, den nichts auslösen kann, wenn die Statuswerte einer Zeile nicht
exakt denen entsprechen, mit denen der Quellcode den Code auslöst, oder wenn eine Code-Familie wie `PG_<SQLSTATE>` keine Zeile
für einen SQLSTATE hat, dem Aufrufer begegnen. Die Prüfstufe ist
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Sie prüft sich zuerst selbst. Der Scan liest Codes aus TypeScript statt aus
einem laufenden Server aus, weshalb seine blinden Flecken konstruktionsbedingt lautlos sind: Einst konnte
er einen Code nicht erkennen, der durch einen einzeiligen Wrapper übergeben wurde, oder einen, der nach einer Nachricht
mit einer `)` geschrieben stand, und meldete „Jeder Code, den der Server auslösen kann, ist dokumentiert“
für eine Seite, auf der siebzehn davon fehlten. Daher führt die Prüfstufe eine Fixture aus genau
diesen Formen aus, bevor sie diese Seite liest, und verweigert jeden Bericht, wenn
sie diese nicht erkennen kann.
