Jeder Fehler, den ein Rebase-Backend zurückgibt, verwendet einen einheitlichen Envelope und enthält einen stabilen `code`. Der Code ist der Wert, auf den verzweigt werden sollte: Die Nachricht ist für Menschen geschrieben und kann umformuliert werden, der Status wird von einem Dutzend verschiedener Probleme geteilt, und der Code ist keines von beidem.

## Der Envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — für Menschen lesbar. Bei einem `4xx` ist es die serverspezifische Nachricht; bei einem `5xx` ist sie bewusst generisch gehalten, da der zugrunde liegende Text einen Host, eine Rolle oder einen Spaltennamen enthalten kann.
- **`code`** — einer der unten aufgeführten Werte. Stabil über Minor-Versionen hinweg.
- **`details`** — optional und nie garantiert. Siehe die unten stehenden Regeln.
- **`requestId`** — vorhanden, wann immer die Anfrage die Request-ID-Middleware durchlaufen hat, was auf jede Route unter `basePath` zutrifft.

### `X-Request-ID`

Jede Anfrage unter `basePath` erhält eine ID: den `X-Request-ID`-Header des Aufrufers, wenn es sich um eine UUID handelt, andernfalls eine neu generierte. Sie wird in der Antwort als `X-Request-ID` zurückgegeben, im Fehler-Envelope als `requestId` eingefügt und an die Protokollzeile des Servers für diese Anfrage angehängt.

Das ist der Verknüpfungsschlüssel. Geben Sie ihn in einem Fehlerbericht an, und ein Operator kann genau die eine Protokollzeile finden, die den Fehler erklärt und den Grund enthält, der dem Client nie angezeigt wurde.

Das Senden einer eigenen ID sorgt dafür, dass ein Trace über Hops hinweg erhalten bleibt: Ein Gateway oder ein Job-Runner, der den Header weiterleitet, erhält eine einheitliche ID über alle Dienste hinweg, die die Anfrage verarbeitet haben. Ein ungültiger Wert wird ignoriert und nicht abgelehnt – wegen eines fehlerhaften Headers eines Aufrufers lohnt es sich nicht, eine Anfrage fehlschlagen zu lassen. Gehen Sie also nicht davon aus, dass die gesendete ID der empfangenen entspricht. Lesen Sie den Antwort-Header.

### Was in `details` steht

`details` dient Diagnosezwecken und ist nicht verbindlich. Drei Regeln bestimmen den Inhalt:

1. **Alles, was eine Route explizit setzt, wird immer zurückgegeben.** Dies sind die Fehler des Aufrufers selbst, präzise beschrieben: welches Filterfeld unbekannt war, welche Relation nicht beschreibbar ist, welcher Wert nicht zu seinem Typ passte.
2. **Datenbankdiagnosen werden in der Produktion gekürzt.** Wenn der Fehler von Postgres stammt, ist `details.dbCode` – der SQLSTATE – immer vorhanden: Er benennt die Problemklasse und gibt nichts über die Daten preis. `dbMessage`, `detail` und `hint` werden nur hinzugefügt, wenn `NODE_ENV` nicht `production` ist, da Postgres Zeileninhalte darin platziert. `23505` meldet `Key (email)=(a@b.c) already exists.`, was für jede beliebige Adresse die Frage „Ist diese Person registriert?“ beantwortet.
3. **Verzweigen Sie niemals auf `details`.** Verzweigen Sie auf `code`. Was unter `details` steht, ist das, was für eine Person an diesem Aufrufpunkt nützlich war, und es kann sich ändern.

## Statuscodes verstehen

| Status | Was er über die Anfrage aussagt |
| --- | --- |
| `400` | Fehlerhaft aufgebaut oder fordert etwas an, das im Schema nicht existiert. Korrigieren Sie die Anfrage. |
| `401` | Nicht authentifiziert oder die Anmeldeinformationen sind abgelaufen. Anmelden oder aktualisieren. |
| `403` | Authentifiziert, aber nicht berechtigt. Ein erneuter Versuch mit derselben Identität hilft nicht. |
| `404` | Keine solche Route, Tabelle oder Zeile – oder eine Zeile, die durch Row-Level Security verborgen wird. |
| `409` | Ein Konflikt mit dem bestehenden Zustand: ein Duplikat oder ein gleichzeitiger Schreibzugriff. |
| `413` `415` `422` | Der Body ist zu groß, hat den falschen Medientyp oder wurde semantisch abgelehnt. |
| `429` | Ratenbegrenzung überschritten. Warten Sie ab; die Nachricht gibt an, wie lange. |
| `500` | Der Server oder seine Datenbank ist fehlerhaft, nicht der Aufrufer. Prüfen Sie die Logs. |
| `501` | Die Route existiert, aber dieses Deployment kann sie nicht bedienen – eine Funktion, die deaktiviert oder unkonfiguriert ist. |
| `502` `503` `504` | Eine Abhängigkeit war nicht erreichbar, unkonfiguriert oder zu langsam. |

## `PG_<SQLSTATE>` — Ein von der Datenbank abgelehnter Constraint

Ein Schreibvorgang, den Postgres aus Gründen ablehnt, die in den *Daten des Aufrufers* liegen, antwortet mit dem SQLSTATE im Code: `PG_23505`, `PG_23503` usw. Das ist eine Familie, keine feste Liste – Postgres definiert Hunderte von SQLSTATEs –, aber nur zwei Klassen erreichen diesen Status je, da nur diese beiden auf Fehler des Aufrufers zurückzuführen sind:

- **Klasse 23**, Verletzung von Integritäts-Constraints: ein Duplikat, ein Fremdschlüssel, der ins Leere weist, eine leere NOT NULL-Spalte;
- **Klasse 22**, Daten-Ausnahme: ein Wert, den der Spaltentyp nicht aufnehmen kann.

Alles andere – eine unterbrochene Verbindung, eine fehlende Spalte, ein Rechteproblem – liegt auf Serverseite und bleibt ein `500`. Daher ist `code.startsWith("PG_")` eine zuverlässige Prüfung für „Die von mir gesendete Zeile war fehlerhaft“, und die vier unten stehenden sind diejenigen, auf die ein Client in der Praxis trifft. `details.dbCode` trägt bei allen denselben SQLSTATE, und die Nachricht nennt den Constraint.

| Code | Status | Bedeutung | Was zu tun ist |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Ein Wert konnte nicht als Typ der Spalte gelesen werden – das schreibseitige Pendant zu `INVALID_FILTER_VALUE`. | Senden Sie einen Wert, der dem Typ der Spalte entspricht. |
| `PG_23502` | 400 | Eine `NOT NULL`-Spalte wurde leer gelassen. | Senden Sie das Feld mit oder geben Sie der Spalte einen Standardwert. |
| `PG_23503` | 400 / 409 | Beim Speichern verweist ein Fremdschlüssel auf eine nicht existierende Zeile (400). Beim Löschen verweisen andere Zeilen noch auf diese (409; ein `RESTRICT`-Schlüssel wirft `PG_23001`, ebenfalls 409). | Erstellen Sie zuerst die Zielzeile oder korrigieren Sie die ID; entfernen Sie beim Löschen zuerst die verweisenden Zeilen oder biegen Sie sie um. |
| `PG_23505` | 409 | Ein Unique-Constraint wurde verletzt. Die Nachricht nennt den Constraint. | Verwenden Sie einen anderen Wert oder aktualisieren Sie die bestehende Zeile. |

## Benutzerdefinierte Funktionen

| Code | Status | Bedeutung | Was zu tun ist |
| --- | --- | --- | --- |
| `FUNCTION_NOT_FOUND` | 404 | Es wird keine Funktion dieses Namens bereitgestellt – oder eine existiert, deren eigene Routen den Pfad dahinter jedoch nicht abdecken. ## SQL-Funktionen als RPC

`POST /api/rpc/<name>` – siehe [SQL-Funktionen als RPC](/docs/backend/rpc/). Ein fehlerhaftes Argument führt zu `VALIDATION_CONSTRAINT` (400), wobei `details.violations` jedes Feld benennt (wie bei der Daten-API); Zugangsdaten ohne `data:read` führen zu `SCOPE_MISSING` (403); ein öffentlicher RPC über seinem Limit führt zu `RATE_LIMITED` (429).

| Code | Status | Bedeutung | Was zu tun ist |
| --- | --- | --- | --- |
| `RPC_NOT_FOUND` | 404 | Kein `defineRpc` dieses Namens wird aus `backend/schema/index.ts` exportiert. Nur deklarierte Funktionen sind aufrufbar; eine Funktion, die die Datenbank besitzt, die aber niemand deklariert hat, antwortet ebenfalls damit. | Deklarieren Sie sie mit `defineRpc` oder überprüfen Sie den Namen. |
| `METHOD_NOT_ALLOWED` | 405 | Der RPC existiert, wird jedoch mit einer anderen Methode als `POST` aufgerufen. Die Antwort enthält `Allow: POST`. | Senden Sie per `POST` einen JSON-Body mit benannten Argumenten. |
| `INVALID_RPC_BODY` | 400 | Der Body ist JSON, aber kein Objekt benannter Argumente (sondern ein Array oder ein String). | Senden Sie `{ "argument": value }` oder keinen Body bei Funktionen ohne Argumente. |
| `RPC_ARGUMENTS_MISMATCH` | 400 | Keine Überladung der SQL-Funktion akzeptiert die gesendeten Argumente: Ein Parameter ohne `DEFAULT` wurde weggelassen oder es wurde ein Parameter benannt, den die Funktion nicht hat. Die Nachricht listet die erwarteten Parameter auf. | Senden Sie die von der Funktion erwarteten Parameter und markieren Sie sie in `args` als `.required()`. |
| `RPC_INVALID_ARGUMENT` | 400 | Postgres hat einen Wert für den Parametertyp der Funktion abgelehnt (ein SQLSTATE der Klasse 22): `"abc"` für eine `uuid`, ein Label außerhalb eines Enums. | Senden Sie einen Wert, der dem Typ des Parameters entspricht. |
| `RPC_EXCEPTION` | 400, oder der durch einen `PTnnn`-SQLSTATE angegebene Status | Die Funktion hat eine Exception ausgelöst: `RAISE EXCEPTION '…'` antwortet mit 400 und der entsprechenden Nachricht; `details` enthält `sqlState`, `detail` und `hint`; `RAISE SQLSTATE 'PT404'` antwortet mit 404, analog zu PostgREST. | Die Nachricht stammt von der Funktion selbst. |
| `RPC_READ_ONLY` | 500 | Die Funktion hat Schreiboperationen ausgeführt, ein RPC läuft jedoch in einer schreibgeschützten Transaktion, sofern er nicht mit `write: true` deklariert ist. | Fügen Sie `write: true` zu dessen `defineRpc` hinzu. |
| `RPC_FUNCTION_MISSING` | 500 | Der RPC ist deklariert, aber die Datenbank besitzt keine Funktion mit diesem Schema und Namen. Postgres speichert unquoted Namen in Kleinbuchstaben. | Erstellen Sie die Funktion oder korrigieren Sie den Namen bzw. das `schema` in `defineRpc`. |
| `RPC_AMBIGUOUS` | 500 | Mehrere Überladungen der Funktion akzeptieren die gesendeten Argumente. | Entfernen Sie die Überladungen, die der RPC nicht erreichen soll, oder benennen Sie sie um. |

| `SQL_EXPORT_UNSUPPORTED` | 501 | `POST /api/admin/sql/csv` kann hier kein Streaming eines Ergebnisses durchführen: Die prozessinterne Entwicklungsdatenbank (PGlite) besitzt nur eine einzige Verbindung, und ein während eines Downloads gehaltener Cursor würde jede andere Abfrage dahinter blockieren; oder die Datenquelle besitzt keinen SQL-Cursor. | Richten Sie `DATABASE_URL` auf ein eigenes Postgres (`rebase dev --docker` startet eines) oder fügen Sie ein `LIMIT` hinzu und exportieren Sie die Zeilen über die Oberfläche. |

### Schema-Reconcile

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) plant über `POST /api/admin/schema/reconcile/plan` und wendet Änderungen über `/reconcile/apply` an. Eine Ablehnung ändert nichts; lediglich `SCHEMA_RECONCILE_FAILED` hinterlässt einen teilweise angewendeten Plan.

| Code | Status | Bedeutung | Was zu tun ist |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | Der Body ist kein JSON-Objekt oder `drop` ist keine Liste von `"<table>.<column>"`-Strings. | Senden Sie `{ "drop": ["voice_cache.wav"] }` oder lassen Sie `drop` weg. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Eine Anweisung schlug mittendrin fehl. Die davor liegenden Anweisungen wurden ausgeführt und bleiben wirksam; `details.applied` listet sie auf. | Beheben Sie die in der Nachricht genannte Ursache und planen Sie erneut: Der neue Plan spart das bereits Ausgeführte aus. |
| `SCHEMA_RECONCILE_INVALID` | 400 | Der Plan kann nicht angewendet werden; die Nachricht nennt die Gründe: ein `drop`, das nicht `<table>.<column>` entspricht, keine Tabelle bzw. Spalte benennt oder eine Spalte benennt, die von der Tabelle noch deklariert wird. `details.plan` enthält den Plan. | Korrigieren Sie die `drop`-Liste. Eine deklarierte Spalte wird gelöscht, indem sie aus ihrem `defineTable` entfernt, deployed und anschließend abgeglichen (reconciled) wird. |
| `SCHEMA_RECONCILE_STALE` | 409 | Die Datenbank oder die Tabellen haben sich seit dem von Ihnen bestätigten Plan geändert. `details.plan` enthält den neuen Plan. | Prüfen Sie den neuen Plan und bestätigen Sie dessen `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | An `/reconcile/apply` wurde kein `confirm` übergeben. | Führen Sie zuerst die Planung durch und senden Sie den `digest` des Plans als `confirm`. Das CLI erledigt dies, sobald Sie `yes` eingeben. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | Der Treiber dieses Backends kann keinen Abgleich planen oder kein SQL ausführen. | Reconcile funktioniert auf Postgres. |

### Warum die Tabelle eines Branches nicht zusammengeführt werden kann

`BRANCH_MERGE_BLOCKED` benennt jede abgelehnte Tabelle in `details.tables` mit einem dieser Codes. Derselbe Code steht im Diff selbst auf `blocked` der Tabelle, sodass Studio dies anzeigen kann, bevor jemand auf **Merge** klickt. Keiner davon ist eine eigenständige Response.

| Code | Status | Bedeutung | Was zu tun ist |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Die Spalten der Tabelle weichen zwischen Branch und Parent voneinander ab. Zeilen werden anhand der gemeinsamen Spalten verglichen. | Fügen Sie die fehlenden Spalten mit Ihren Migrationen (`rebase db push`) zum Parent hinzu und führen Sie den Merge dann durch. Eine Migration, die die Tabelle umschreibt (z. B. Änderung eines Spaltentyps), führt zu `TABLE_REWRITTEN`: Führen Sie den Merge vor einer solchen Änderung durch oder erstellen Sie den Branch danach neu. |
| `NO_PRIMARY_KEY` | — | Die Tabelle besitzt keinen Primärschlüssel, sodass Zeilen nicht einzeln abgeglichen werden können; das Diff liefert lediglich die Zeilenanzahl. | Vergeben Sie einen Primärschlüssel für die Tabelle oder übertragen Sie die Zeilen manuell. |
| `PRIMARY_KEY_DIFFERS` | — | Die Spalten des Primärschlüssels oder deren Typen unterscheiden sich zwischen beiden Seiten. | Wenden Sie das Schema zuerst auf den Parent an. |
| `TABLE_ADDED` | — | Der Branch hat die Tabelle erstellt. Ein Merge erstellt niemals Tabellen. | Erstellen Sie sie mit Ihren Migrationen auf dem Parent und führen Sie die Zeilen anschließend zusammen. |
| `TABLE_DROPPED` | — | Der Branch hat die Tabelle gelöscht. Ein Merge löscht niemals Tabellen. | Löschen Sie sie über Ihre Migrationen. |
| `TABLE_REWRITTEN` | — | Eine Seite hat nach Erstellung des Branches jede Zeile der Tabelle neu geschrieben – eine Änderung des Spaltentyps, ein `ADD COLUMN` mit flüchtigem Default-Wert, `VACUUM FULL`, `CLUSTER` –, sodass jede Zeile als seitdem modifiziert gilt und nicht mehr ermittelt werden kann, welche Seite welche Zeile geändert hat. | Mergen Sie den Branch vor einer solchen Migration oder erstellen Sie den Branch nach der Migration erneut vom Parent. |
| `TOO_LARGE` | — | Die Tabelle enthält auf einer Seite mehr Zeilen, als ein Diff einzeln abgleicht (standardmäßig 100.000, `maxRowsPerTable`). | Erhöhen Sie `maxRowsPerTable` sowohl für das Diff als auch für den Merge, oder verschieben Sie die Zeilen auf anderem Wege. |

## Generische Codes

Eine Route verwendet einen dieser Codes, wenn kein spezifischerer zutrifft.

| Code | Status | Bedeutung | Was zu tun ist |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Fehlerhaft aufgebaut und kein spezifischerer Code trifft zu. | Siehe die Nachricht. |
| `UNAUTHORIZED` | 401 | Nicht authentifiziert oder die Anmeldeinformationen wurden abgelehnt. | Anmelden oder aktualisieren. |
| `FORBIDDEN` | 403 | Authentifiziert, aber nicht berechtigt. | Ein erneuter Versuch mit derselben Identität hilft nicht. |
| `CONFLICT` | 409 | Ein Konflikt mit dem bestehenden Zustand. | Siehe die Nachricht. |
| `INTERNAL_ERROR` | 500 | Auf dem Server ist ein interner Fehler aufgetreten. Die Nachricht ist bewusst generisch gehalten. | Geben Sie die `requestId` an; die Ursache steht in den Protokollen. |
| `NOT_CONFIGURED` | 503 | Eine von dieser Route benötigte Abhängigkeit ist auf diesem Server nicht konfiguriert. | Siehe die Nachricht. |
| `SERVICE_UNAVAILABLE` | 503 | Ein Dienst, von dem die Anfrage abhängt, konnte nicht erreicht werden: ein S3- oder MinIO-Bucket oder ein Host, den eine Funktion per `fetch()` aufruft, der die Verbindung verweigert oder nicht aufgelöst werden kann. Das Server-Log nennt den Host; die Response tut dies nicht. Eine nicht erreichbare Datenbank führt zu `DATABASE_UNAVAILABLE`. Eine fehlschlagende Verbindung zu einem solchen Dienst antwortet mit diesem Code. | Wiederholen Sie den Vorgang; prüfen Sie die Logs. |

## Diese Seite aktuell halten

`pnpm verify:docs` schlägt fehl, wenn ein Code, den der Server auslösen kann, in diesen Tabellen fehlt, wenn eine Tabelle einen Code auflistet, den nichts auslösen kann, wenn die Statuswerte einer Zeile nicht exakt denen entsprechen, mit denen der Quellcode den Code auslöst, oder wenn eine Code-Familie wie `PG_<SQLSTATE>` keine Zeile für einen SQLSTATE enthält, auf den Aufrufer treffen können. Der Prüfschritt ist `tooling/scripts/docs-verify/check-error-codes.mjs`.

Er prüft sich zunächst selbst. Der Scan liest Codes aus TypeScript statt aus einem laufenden Server aus, weshalb tote Winkel konstruktionsbedingt unbemerkt blieben: Früher konnte er einen Code nicht erkennen, der über einen einzeiligen Wrapper übergeben wurde, oder einen, der nach einer Nachricht mit einer `)` geschrieben stand, und meldete „Jeder Code, den der Server auslösen kann, ist dokumentiert“ für eine Seite, auf der siebzehn davon fehlten. Daher führt der Schritt eine Fixture mit exakt diesen Mustern aus, bevor er diese Seite liest, und verweigert jeden Bericht, wenn er diese nicht erkennen kann.
