Jeder Fehler, den ein Rebase-Backend zurückgibt, verwendet denselben Envelope und enthält einen stabilen
`code`. Der Code ist das Kriterium, nach dem verzweigt werden sollte: Die Meldung ist für Menschen
verfasst und kann sich im Wortlaut ändern, der Status wird von einem Dutzend verschiedener Probleme
geteilt – der Code ist keines von beidem.

## Der Envelope

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — menschenlesbar. Bei einem `4xx` ist es die eigene Meldung des Servers;
  bei einem `5xx` ist sie bewusst generisch gehalten, da der zugrunde liegende Text
  einen Host, eine Rolle oder einen Spaltennamen zitieren kann.
- **`code`** — einer der unten aufgeführten Werte. Stabil über Minor-Versionen hinweg.
- **`details`** — optional und niemals garantiert. Siehe die nachfolgenden Regeln.
- **`requestId`** — vorhanden, wann immer die Anfrage die Request-ID-Middleware
  durchlaufen hat, was auf jede Route unter `basePath` zutrifft.

### `X-Request-ID`

Jede Anfrage unter `basePath` erhält eine ID: den `X-Request-ID`-Header des Aufrufers,
wenn es sich um eine UUID handelt, andernfalls eine neu generierte. Sie wird in der
Antwort als `X-Request-ID` zurückgegeben, im Fehler-Envelope als `requestId` eingefügt
und an die Server-Protokollzeile für diese Anfrage angehängt.

Das ist der Verknüpfungsschlüssel. Geben Sie ihn in einem Fehlerbericht an, und ein
Administrator kann genau die eine Protokollzeile finden, die den Fehler erklärt und
den Grund enthält, der dem Client niemals angezeigt wurde.

Das Senden einer eigenen ID ermöglicht es, einen Trace über Zwischenstationen hinweg
aufrechtzuerhalten: Ein Gateway oder Job-Runner, der den Header weiterleitet, erhält
eine einheitliche ID über alle Dienste hinweg, die die Anfrage verarbeitet haben.
Ein ungültiger Wert wird ignoriert statt abgelehnt – wegen eines fehlerhaften Headers
eines Aufrufers sollte eine Anfrage nicht fehlschlagen. Gehen Sie daher nicht davon aus,
dass die gesendete ID der erhaltenen ID entspricht. Lesen Sie den Response-Header aus.

### Was in `details` enthalten ist

`details` dient der Diagnose und ist nicht vertraglich bindend. Es gelten drei Regeln:

1. **Alles, was eine Route explizit setzt, wird immer zurückgegeben.** Dies sind die
   präzise beschriebenen Fehler des Aufrufers: welches Filterfeld unbekannt war,
   welche Relation nicht beschreibbar ist, welcher Wert nicht zu seinem Typ passte.
2. **Datenbank-Diagnosedaten werden in der Produktion gekürzt.** Wenn der Fehler von
   Postgres stammt, ist `details.dbCode` – der SQLSTATE – immer vorhanden: Er benennt
   die Problemklasse und verrät nichts über die Daten. `dbMessage`, `detail` und `hint`
   werden nur hinzugefügt, wenn `NODE_ENV` nicht `production` ist, da Postgres Zeileninhalte
   darin platziert. `23505` meldet `Key (email)=(a@b.c) already exists.`, was für jede
   beliebige Adresse die Frage „Ist diese Person registriert?“ beantwortet.
3. **Verzweigen Sie niemals auf Basis von `details`.** Verzweigen Sie nach `code`. Was
   unter `details` steht, ist das, was für eine Person an diesem Aufrufpunkt nützlich
   war, und kann sich ändern.

## Einen Status interpretieren

| Status | Was er über die Anfrage aussagt |
| --- | --- |
| `400` | Fehlerhaft aufgebaut oder fordert etwas an, das im Schema nicht existiert. Korrigieren Sie die Anfrage. |
| `401` | Nicht authentifiziert oder die Anmeldedaten sind abgelaufen. Melden Sie sich an oder erneuern Sie die Sitzung. |
| `403` | Authentifiziert, aber nicht autorisiert. Ein erneuter Versuch mit derselben Identität hilft nicht. |
| `404` | Keine solche Route, Tabelle oder Zeile – oder eine Zeile, die durch Row-Level Security verborgen wird. |
| `409` | Ein Konflikt mit dem bestehenden Zustand: ein Duplikat oder ein gleichzeitiger Schreibvorgang. |
| `413` `415` `422` | Der Body ist zu groß, hat den falschen Medientyp oder wurde semantisch abgelehnt. |
| `429` | Rate-Limit erreicht. Warten Sie; die Meldung gibt an, wie lange. |
| `500` | Der Fehler liegt beim Server oder seiner Datenbank, nicht beim Aufrufer. Überprüfen Sie die Logs. |
| `501` | Die Route existiert, aber dieses Deployment kann sie nicht bedienen – ein Feature, das deaktiviert oder nicht konfiguriert ist. |
| `502` `503` `504` | Eine Abhängigkeit war nicht erreichbar, nicht konfiguriert oder zu langsam. |

## `PG_<SQLSTATE>` — ein von der Datenbank abgelehnter Constraint

Ein Schreibvorgang, den Postgres aus einem Grund ablehnt, der in den *Daten des Aufrufers*
liegt, antwortet mit dem SQLSTATE im Code: `PG_23505`, `PG_23503` usw. Dabei handelt es
sich um eine Familie, nicht um eine feste Liste – Postgres definiert Hunderte von SQLSTATEs –,
aber nur zwei Klassen erreichen diesen Punkt jemals, da nur diese beiden dem Aufrufer
anzulasten sind:

- **Klasse 23**, Verletzung von Integritäts-Constraints: ein Duplikat, ein Fremdschlüssel,
  der ins Leere zeigt, eine leere NOT-NULL-Spalte;
- **Klasse 22**, Daten-Ausnahme (Data Exception): ein Wert, den der Typ der Spalte nicht
  aufnehmen kann.

Alles andere – eine getrennte Verbindung, eine fehlende Spalte, ein Berechtigungsproblem –
liegt in der Verantwortung des Servers und bleibt ein `500`. Daher ist `code.startsWith("PG_")`
eine verlässliche Prüfung auf „die von mir gesendete Zeile war fehlerhaft“, und die vier
unten aufgeführten Codes sind diejenigen, denen ein Client in der Praxis begegnet.
`details.dbCode` enthält für alle denselben SQLSTATE, und die Meldung benennt den Constraint.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Ein Wert konnte nicht als Typ der Spalte gelesen werden – das schreibseitige Pendant zu `INVALID_FILTER_VALUE`. | Senden Sie einen Wert des Spaltentyps. |
| `PG_23502` | 400 | Eine `NOT NULL`-Spalte wurde leer gelassen. | Senden Sie das Feld mit oder versehen Sie die Spalte mit einem Standardwert. |
| `PG_23503` | 400 / 409 | Beim Speichern: Ein Fremdschlüssel verweist auf eine nicht existierende Zeile (400). Beim Löschen: Andere Zeilen referenzieren diese noch (409; ein `RESTRICT`-Schlüssel löst `PG_23001` aus, ebenfalls 409). | Erstellen Sie zuerst die Zielzeile oder korrigieren Sie die ID; entfernen Sie beim Löschen zuerst die referenzierenden Zeilen oder passen Sie deren Referenz an. |
| `PG_23505` | 409 | Ein Unique-Constraint wurde verletzt. Die Meldung benennt den Constraint. | Verwenden Sie einen anderen Wert oder aktualisieren Sie die bestehende Zeile. |

## Benutzerdefinierte Funktionen

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `FUNCTION_NOT_FOUND` | 404 | Es wird keine Funktion dieses Namens bereitgestellt – oder eine existiert, deren eigene Routen den darauffolgenden Pfad jedoch nicht abdecken. Einem angemeldeten Aufrufer wird auch mitgeteilt, was *tatsächlich* bereitgestellt wird; einem anonymen nicht, da diese Liste ein Inventar jedes benutzerdefinierten Endpunkts darstellt. Wenn eine Datei dieses Namens nicht geladen werden konnte, teilt die Meldung dies einem angemeldeten Aufrufer unter Nennung der Datei mit: Das ist der Unterschied zwischen einem Tippfehler und einem fehlerhaften Deployment. Ein anonymer Aufrufer erhält die einfache Antwort für unbekannte Namen, genau wie bei einem Namen, der auf nichts zutrifft. | Gleichen Sie den Namen mit `GET /api/functions` ab oder prüfen Sie das Boot-Log auf Dateien, die nicht geladen werden konnten. |
| `FUNCTION_TIMEOUT` | 504 | Der Handler hat sein Timeout überschritten. Er läuft weiterhin; er kann von hier aus nicht abgebrochen werden. Die Meldung und `details` (`{ timeoutMs, source }`) geben an, welches Limit gegriffen hat und wo es gesetzt wurde. | Versehen Sie ausgehende Aufrufe mit einem `AbortSignal`, deklarieren Sie das eigene `timeoutMs` der Funktion (`defineFunction(…, { timeoutMs })`, maximal `REBASE_FUNCTIONS_MAX_TIMEOUT_MS`) oder erhöhen Sie `REBASE_FUNCTIONS_TIMEOUT_MS`. |
| `FUNCTIONS_UPSTREAM_UNREACHABLE` | 502 | Dieser Prozess leitet Funktionen per Proxy an einen anderen weiter, der nicht geantwortet hat. | Prüfen Sie, ob die Functions-Einheit ausgeführt wird. |

## SQL-Funktionen als RPC

`POST /api/rpc/<name>` — siehe [SQL-Funktionen als RPC](/docs/backend/rpc/). Ein fehlerhaftes Argument führt zu `VALIDATION_CONSTRAINT` (400), wobei `details.violations` jedes Feld benennt, genau wie bei der Daten-API; Zugangsdaten ohne `data:read` führen zu `SCOPE_MISSING` (403); ein öffentlicher RPC über seinem Limit führt zu `RATE_LIMITED` (429).

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `RPC_NOT_FOUND` | 404 | Kein `defineRpc` dieses Namens wird aus `backend/schema/index.ts` exportiert. Nur deklarierte Funktionen sind aufrufbar; eine Funktion, die die Datenbank besitzt, aber niemand deklariert hat, antwortet daher ebenfalls hiermit. | Deklarieren Sie sie mit `defineRpc` oder überprüfen Sie den Namen. |
| `METHOD_NOT_ALLOWED` | 405 | Der RPC existiert und wird mit einer anderen Methode als `POST` aufgerufen. Die Antwort enthält `Allow: POST`. | Senden Sie ein `POST` mit einem JSON-Body benannter Argumente. |
| `INVALID_RPC_BODY` | 400 | Der Body ist zwar JSON, aber kein Objekt benannter Argumente (z. B. ein Array, ein String). | Senden Sie `{ "argument": value }` oder keinen Body für aufrufe ohne Argumente. |
| `RPC_ARGUMENTS_MISMATCH` | 400 | Keine Überladung der SQL-Funktion akzeptiert die gesendeten Argumente: Ein Parameter ohne `DEFAULT` wurde weggelassen oder ein nicht vorhandener Parameter wurde angegeben. Die Meldung listet auf, was sie akzeptiert. | Senden Sie, was die Funktion erwartet, und markieren Sie es in `args` als `.required()`. |
| `RPC_INVALID_ARGUMENT` | 400 | Postgres hat einen Wert für den Parametertyp der Funktion abgelehnt (ein SQLSTATE der Klasse 22): `"abc"` für eine `uuid`, ein Label außerhalb eines Enums. | Senden Sie einen Wert des Parametertyps. |
| `RPC_EXCEPTION` | 400, oder der Status, den ein `PTnnn`-SQLSTATE angibt | Die Funktion hat eine Ausnahme ausgelöst: `RAISE EXCEPTION '…'` antwortet mit 400 und ihrer Meldung, und `details` enthält `sqlState`, `detail` und `hint`; `RAISE SQLSTATE 'PT404'` antwortet mit 404, wie es PostgREST tut. | Die Meldung stammt von der Funktion selbst. |
| `RPC_READ_ONLY` | 500 | Die Funktion hat geschrieben, und ein RPC läuft in einer schreibgeschützten Transaktion, sofern er nicht als `write: true` deklariert ist. | Fügen Sie `write: true` zu seinem `defineRpc` hinzu. |
| `RPC_FUNCTION_MISSING` | 500 | Der RPC ist deklariert, aber die Datenbank besitzt keine Funktion mit diesem Schema und Namen. Postgres speichert unquotierte Namen in Kleinbuchstaben. | Erstellen Sie die Funktion oder korrigieren Sie den Namen bzw. das `schema` in `defineRpc`. |
| `RPC_AMBIGUOUS` | 500 | Mehrere Überladungen der Funktion akzeptieren die gesendeten Argumente. | Entfernen Sie die Überladungen, die der RPC nicht erreichen soll, oder benennen Sie sie um. |

| `UI_CONFIG_FILE_INVALID` | 500 | `frontend/src/cms/ui-config.json`, worin die UI-Einstellungen des Workspace in der Entwicklung geschrieben werden, ist kein valides JSON. | Korrigieren oder löschen Sie die Datei; das Panel schreibt sie beim nächsten Speichern neu. |
| `SQL_EXPORT_UNSUPPORTED` | 501 | `POST /api/admin/sql/csv` kann hier kein Ergebnis streamen: Die prozessinterne Entwicklungsdatenbank (PGlite) besitzt nur eine Verbindung, und ein über einen Download gehaltener Cursor würde jede andere Abfrage dahinter blockieren; oder die Datenquelle besitzt keinen SQL-Cursor. | Richten Sie `DATABASE_URL` auf ein eigenes Postgres (`rebase dev --docker` startet eines) oder fügen Sie ein `LIMIT` hinzu und exportieren Sie die Zeilen über die Bildschirmanzeige. |

### Schema-Abgleich (Reconcile)

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) plant
über `POST /api/admin/schema/reconcile/plan` und wendet Änderungen über
`/reconcile/apply` an. Eine Ablehnung ändert nichts; lediglich `SCHEMA_RECONCILE_FAILED`
hinterlässt einen Plan in teilweise angewendetem Zustand.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | Der Body ist kein JSON-Objekt oder `drop` ist keine Liste von `"<table>.<column>"`-Strings. | Senden Sie `{ "drop": ["voice_cache.wav"] }` oder lassen Sie `drop` weg. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Eine Anweisung ist während der Ausführung fehlgeschlagen. Die vorherigen Anweisungen wurden ausgeführt und bleiben angewendet; `details.applied` listet sie auf. | Beheben Sie die in der Meldung genannte Ursache und planen Sie erneut: Der neue Plan lässt bereits ausgeführte Schritte aus. |
| `SCHEMA_RECONCILE_INVALID` | 400 | Der Plan kann nicht angewendet werden, und die Meldung listet die Gründe auf: ein `drop`, das nicht `<table>.<column>` entspricht, keine Tabelle oder Spalte benennt oder eine Spalte benennt, die die Tabelle weiterhin deklariert. `details.plan` enthält den Plan. | Korrigieren Sie die `drop`-Liste. Eine deklarierte Spalte wird gelöscht, indem sie aus ihrem `defineTable` entfernt, deployt und anschließend abgeglichen wird. |
| `SCHEMA_RECONCILE_STALE` | 409 | Die Datenbank oder die Tabellen haben sich seit dem von Ihnen bestätigten Plan geändert. `details.plan` ist der neue Plan. | Prüfen Sie den neuen Plan und bestätigen Sie dessen `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | `/reconcile/apply` wurde ohne `confirm` aufgerufen. | Planen Sie zuerst und senden Sie den `digest` des Plans als `confirm`. Das CLI erledigt dies, sobald Sie `yes` eingeben. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | Der Treiber dieses Backends kann keinen Reconcile planen oder kein SQL ausführen. | Reconcile funktioniert unter Postgres. |

### Warum die Tabelle eines Branches nicht zusammengeführt werden kann

`BRANCH_MERGE_BLOCKED` benennt jede abgelehnte Tabelle in `details.tables` mit einem
dieser Codes. Derselbe Code steht im Diff selbst auf dem Feld `blocked` der Tabelle,
sodass Studio dies anzeigen kann, bevor jemand auf **Merge** klickt. Keiner davon
ist eine eigenständige HTTP-Antwort.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Die Spalten der Tabelle unterscheiden sich zwischen dem Branch und seinem übergeordneten Element. Zeilen werden anhand der gemeinsamen Spalten verglichen. | Fügen Sie die fehlenden Spalten mit Ihren Migrationen (`rebase db push`) zum übergeordneten Element hinzu und führen Sie den Merge dann durch. Eine Migration, die die Tabelle umschreibt – eine Änderung des Spaltentyps –, führt zu `TABLE_REWRITTEN`: Führen Sie den Merge vor einer solchen Änderung durch oder erstellen Sie den Branch danach neu. |
| `NO_PRIMARY_KEY` | — | Die Tabelle besitzt keinen Primärschlüssel, sodass Zeilen nicht einzeln abgeglichen werden können; das Diff liefert lediglich die Zeilenanzahl. | Versehen Sie die Tabelle mit einem Primärschlüssel oder übertragen Sie die Zeilen manuell. |
| `PRIMARY_KEY_DIFFERS` | — | Die Spalten des Primärschlüssels oder deren Typen unterscheiden sich zwischen beiden. | Wenden Sie das Schema zuerst auf das übergeordnete Element an. |
| `TABLE_ADDED` | — | Der Branch hat die Tabelle erstellt. Ein Merge erstellt niemals eine Tabelle. | Erstellen Sie sie auf dem übergeordneten Element mit Ihren Migrationen und führen Sie dann die Zeilen zusammen. |
| `TABLE_DROPPED` | — | Der Branch hat die Tabelle gelöscht. Ein Merge löscht niemals eine Tabelle. | Löschen Sie sie über Ihre Migrationen. |
| `TABLE_REWRITTEN` | — | Eine Seite hat nach Erstellung des Branches jede Zeile der Tabelle neu geschrieben – eine Änderung des Spaltentyps, ein `ADD COLUMN` mit flüchtigem Standardwert, `VACUUM FULL`, `CLUSTER` –, sodass jede Zeile als seitdem geschrieben gilt und nicht mehr ermittelt werden kann, welche Seite welche Zeile geändert hat. | Führen Sie den Merge des Branches vor einer solchen Migration durch oder erstellen Sie den Branch nach der Migration neu aus dem übergeordneten Element. |
| `TOO_LARGE` | — | Die Tabelle enthält auf einer Seite mehr Zeilen, als ein Diff einzeln abgleicht (standardmäßig 100.000, `maxRowsPerTable`). | Erhöhen Sie `maxRowsPerTable` sowohl für das Diff als auch für den Merge, oder verschieben Sie die Zeilen auf anderem Wege. |

## Allgemeine Codes

Eine Route verwendet einen dieser Codes, wenn kein spezifischerer zutrifft.

| Code | Status | Bedeutung | Maßnahme |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Fehlerhafte Anfrage, und kein spezifischerer Code trifft zu. | Siehe die Meldung. |
| `UNAUTHORIZED` | 401 | Nicht authentifiziert oder die Anmeldedaten wurden abgelehnt. | Melden Sie sich an oder erneuern Sie die Sitzung. |
| `FORBIDDEN` | 403 | Authentifiziert, aber nicht autorisiert. | Ein erneuter Versuch mit derselben Identität hilft nicht. |
| `CONFLICT` | 409 | Ein Konflikt mit dem bestehenden Zustand. | Siehe die Meldung. |
| `INTERNAL_ERROR` | 500 | Auf dem Server ist ein interner Fehler aufgetreten. Die Meldung ist bewusst generisch. | Geben Sie die `requestId` an; die Ursache befindet sich in den Protokollen. |
| `NOT_CONFIGURED` | 503 | Eine Abhängigkeit, die diese Route benötigt, ist auf diesem Server nicht konfiguriert. | Siehe die Meldung. |
| `SERVICE_UNAVAILABLE` | 503 | Ein Dienst, von dem die Anfrage abhängt, konnte nicht erreicht werden: ein S3- oder MinIO-Bucket oder ein Host, den eine Funktion per `fetch()` aufruft und der die Verbindung verweigert oder nicht auflöst. Das Server-Log nennt den Host; die Antwort tut dies nicht. Eine nicht erreichbare Datenbank führt zu `DATABASE_UNAVAILABLE`. Eine fehlschlagende Verbindung zu einem solchen Dienst antwortet hiermit. | Versuchen Sie es erneut; prüfen Sie die Protokolle. |

## Diese Seite aktuell halten

`pnpm verify:docs` schlägt fehl, wenn ein Code, den der Server auslösen kann,
in diesen Tabellen fehlt, wenn eine Tabelle einen Code auflistet, den nichts
auslösen kann, wenn die Statuswerte einer Zeile nicht exakt denen entsprechen,
mit denen der Quellcode den Code auslöst, oder wenn eine Code-Familie wie
`PG_<SQLSTATE>` keine Zeile für einen SQLSTATE enthält, dem Aufrufer begegnen.
Der zuständige Prüfschritt ist `tooling/scripts/docs-verify/check-error-codes.mjs`.

Er prüft sich zunächst selbst. Der Scan liest Codes aus TypeScript-Dateien statt
aus einem laufenden Server aus, sodass tote Winkel konstruktionsbedingt unbemerkt
bleiben könnten: Früher konnte er einen Code nicht erkennen, der über einen
einzeiligen Wrapper übergeben wurde, oder einen, der nach einer Meldung mit einer `)`
stand, und meldete „jeder Code, den der Server auslösen kann, ist dokumentiert“
für eine Seite, auf der siebzehn Codes fehlten. Daher führt dieser Schritt eine
Fixture genau dieser Muster aus, bevor er diese Seite liest, und verweigert
jegliche Erfolgsmeldung, wenn er diese nicht erkennen kann.
