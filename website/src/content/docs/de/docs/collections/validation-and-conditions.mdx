<span class="since-badge" data-since="0.31">Seit 0.31</span>

Die Regeln einer Spalte werden einmalig an der Spalte deklariert und vom Server
bei jedem Schreibvorgang erzwungen, der die API erreicht. Das CMS liest dieselben
Regeln aus dem Deskriptor der Tabelle und überprüft sie im Formular vor dem
Speichern, sodass ein Operator den Fehler direkt am Feld sieht und nicht als
abgelehnte Anfrage.

```ts
// backend/schema/events.ts
import { defineTable, col } from "@rebasepro/server/schema";

export const events = defineTable("events", {
    columns: {
        id:      col.uuid().primaryKey().defaultRandom(),
        title:   col.text().notNull().validate({ min: 2, max: 200, requiredMessage: "Every event needs a title" }),
        slug:    col.varchar({ length: 80 }).notNull().unique()
                     .validate({ matches: "^[a-z0-9-]+$", matchesMessage: "Lowercase letters, digits and hyphens only" }),
        isFree:  col.boolean().notNull().default(false),
        price:   col.numeric({ precision: 10, scale: 2 }).validate({ min: 0 }),
        seats:   col.integer().validate({ positive: true }),
    },
    rls: "admin-only",
});
```

:::note[Umstieg von Collections?]
Im Frontend gibt es keinen `validation`-Block mehr. Regeln werden mit
`.notNull()` und `.validate({ … })` an der Spalte definiert, und das CMS liest
sie aus.
:::

## Was das Formular überprüft

<span class="since-badge" data-since="0.31">Seit 0.31</span>

| An der Spalte | Im Formular |
|---|---|
| `.notNull()` | Erforderlich, mit `requiredMessage` als Fehlermeldung, sofern angegeben. Nicht erforderlich, wenn niemand den Wert eingibt: ein generierter Schlüssel, ein Zeitstempel, eine generierte oder `.readOnly()`-Spalte. |
| `.unique()` | Der Wert wird vor dem Speichern eines geänderten Werts anhand der Tabelle überprüft, und ein Duplikat wird direkt am Feld gemeldet. |
| `varchar(n)`, `char(n)` | Maximal `n` Zeichen. |
| text `min`, `max`, `length` | Zeichenanzahl, inklusive. |
| `matches`, `matchesMessage` | Der gesamte Wert muss mit dem Muster übereinstimmen; die Meldung ist der Fehler. |
| `email`, `url` | Der Wert muss eine E-Mail-Adresse bzw. eine URL sein. |
| `trim`, `lowercase`, `uppercase` | Der Wert wird vor dem Speichern getrimmt oder in Klein-/Großschreibung umgewandelt. |
| number `min`, `max`, `moreThan`, `lessThan`, `positive`, `negative`, `integer` | Grenzwerte und nur ganze Zahlen. Integer- und Serial-Spalten sind immer ganze Zahlen, unabhängig davon, was `.validate()` angibt. |
| date `min`, `max` | Das früheste und späteste akzeptierte Datum. |
| array `minItems`, `maxItems`, `uniqueItems` | Anzahl der Elemente und keine doppelten Elemente. |

Jede Regel ist mit ihrer genauen Bedeutung unter
[Spalten](/docs/schema/columns/#validation) aufgeführt.

## Wo die Validierung stattfindet

<span class="since-badge" data-since="0.31">Seit 0.31</span>

Der Server überprüft die Regeln einer Spalte an der Schnittstelle der Anfrage
(REST, der Realtime-Socket und MCP) anhand der vom Aufrufer gesendeten Daten,
bevor `beforeSave` ausgeführt wird. Er beantwortet Schreibvorgänge, die gegen
eine Regel verstoßen, mit dem Statuscode 400 und benennt jedes fehlerhafte Feld.
Servercode, der In-Process schreibt, gilt als vertrauenswürdig und wird nicht
anhand dieser Regeln überprüft; dort gilt das, was die Datenbank erzwingt. Siehe
[Spalten](/docs/schema/columns/#validation).

Das CMS überprüft dieselben Regeln vor dem Speichern – sowohl im
Datensatzformular als auch im Inline-Editor der Tabelle. Eine Tabellenzelle
bewertet einen Wert, sobald Sie ihn bearbeiten: Ein gespeicherter Wert, der
gegen eine später hinzugefügte Regel verstößt, zeigt so lange keinen Fehler an,
bis jemand diese Zelle bearbeitet.

## Bedingte Felder

<span class="since-badge" data-since="0.31">Seit 0.31</span>

Ein Feld kann auf die eigenen Werte des Datensatzes reagieren: als erforderlich,
deaktiviert, schreibgeschützt oder ausgeblendet definiert werden. Es gibt zwei
Möglichkeiten, beide in `customizeTable`:

```tsx
// frontend/src/cms/events.tsx
import { customizeTable } from "@rebasepro/cms";
import type { events } from "../../../backend/schema/events";

export const eventsCms = customizeTable<typeof events>("events", {
    fields: {
        price: {
            conditions: {
                disabled: { "==": [{ "var": "values.isFree" }, true] },
                required: { "!=": [{ "var": "values.isFree" }, true] },
                min: 0,
                disabledMessage: "Free events have no price",
                clearOnDisabled: true,
            },
        },
        seats: {
            dynamicProps: ({ values, authController }) => ({
                disabled: values.isFree === true || !authController.user?.roles?.includes("admin"),
            }),
        },
    },
});
```

### `conditions`: JSON Logic

`conditions` enthält [JSON Logic](https://jsonlogic.com/)-Regeln für den
Datensatz, der gerade bearbeitet wird (`values.<key>`). Da es sich um Daten
handelt, kann der Schema-Editor sie lesen und ändern. Eine Bedingung kann
Folgendes festlegen:

- `disabled`, `disabledMessage`, `clearOnDisabled`, `hidden`, `readOnly`;
- `required`, `requiredMessage`, `min`, `max`;
- `defaultValue`;
- `enumConditions`, `allowedEnumValues`, `excludedEnumValues`;
- `referencePath`, `referenceFilter`;
- `canAddElements`, `sortable` für Arrays.

`disabledMessage` ist der Hinweis, den der Benutzer neben dem ausgegrauten
Steuerelement sieht. Ohne diesen Hinweis liefert ein deaktiviertes Feld keine
Erklärung.

### `dynamicProps`: Eine Funktion

An `dynamicProps` wird der Datensatz übergeben, während er bearbeitet wird
(`values`, einschließlich ungespeicherter Änderungen, sowie `previousValues` nach
dem Speichern), zusammen mit dem angemeldeten Benutzer über `authController`. Die
Funktion gibt die Feldoptionen zurück, die aktuell gelten. Die Rückgabewerte
überschreiben bei jeder Formularabfrage die anderen Optionen des Feldes, sodass
jede Feldoption zurückgegeben werden kann: `disabled`, `hidden`, `readOnly`,
`name`, `description`, `enumLabels`…

:::caution[Bedingungen betreffen das Formularverhalten]
`conditions` und `dynamicProps` werden im Browser ausgeführt und steuern das
Verhalten des CMS. Die API akzeptiert Schreibvorgänge, die diese Regeln
ignorieren. Eine Regel, die für jeden Aufrufer gelten muss, gehört an die Spalte
(`.notNull()`, `.validate()`) oder in die [Row-Level
Security](/docs/collections/security-rules/) der Tabelle, welche die Datenbank
für jedermann erzwingt.
:::

## Labels für ein geschlossenes Set

<span class="since-badge" data-since="0.31">Seit 0.31</span>

Die Werte eines `col.enum([...])` oder eines `.oneOf([...])` gehören zur Spalte.
Ihre Labels, Farben und Reihenfolge gehören zum CMS und werden mit `enumLabels`
und `enumOrder` festgelegt; siehe [geschlossene
Wertemengen](/docs/collections/properties/#closed-sets-of-values).
