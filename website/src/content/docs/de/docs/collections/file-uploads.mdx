Ein Dateifeld ist eine gewöhnliche **String**-Property mit einem `storage`-Block. Die
Spalte enthält Text — den Key des Objekts im Bucket oder dessen URL, falls Sie
diese anfordern — und der Block legt fest, wohin die Bytes übertragen werden und was das Formular akzeptiert.

Diese Trennung ist wichtiger, als es zunächst scheint. Der Großteil von `storage` wird vom Uploader des
Admin-Panels auf dem Weg zur API gelesen, sodass ein Schreibvorgang, der nicht aus einem
Formular stammt, diesen nicht durchläuft — diese Optionen tragen die untenstehende Kennzeichnung. Die beiden
Optionen, die bestimmen, was eine Datei sein *darf*, `maxSize` und `acceptedFiles`, bilden die Ausnahme:
Der Server prüft sie bei jedem Upload in den `storagePath` der Property.

## Eine Datei

```typescript
avatar: {
    type: "string",
    name: "Main image",
    storage: {
        storagePath: "avatars",
        acceptedFiles: ["image/*"],
        maxSize: 2 * 1024 * 1024
    }
}
```

## Mehrere Dateien

Ein Array desselben Typs. Der `storage`-Block wandert nach `of`, da er
jedes einzelne Element und nicht die Liste beschreibt:

```typescript
images: {
    type: "array",
    name: "Images",
    of: {
        type: "string",
        storage: { storagePath: "images", acceptedFiles: ["image/*"] }
    }
}
```

## Storage-Optionen

Alles innerhalb von `storage`.

| Property | Typ | Beschreibung |
|----------|------|-------------|
| `storagePath` | `string \| function` | **Erforderlich.** Gibt an, wohin die Datei im Bucket abgelegt wird. Ein String mit Platzhaltern — `{file}`, `{file.name}`, `{file.ext}`, `{rand}`, `{id}` (die ID des Datensatzes; `{entityId}` wird identisch interpretiert), `{propertyKey}`, `{path}` — oder eine Funktion des Upload-Kontexts, welche die ID des Datensatzes `id` nennt. **Nur im Admin-Formular — wird von der API oder der Datenbank nicht erzwungen:** Der Uploader des Panels löst dies auf, und `client.storage.upload()` vergibt seinen eigenen Key. Ein String-Pfad ist auch der Ort, an dem der Server jeden Upload an die `maxSize` und `acceptedFiles` dieser Property bindet |
| `fileName` | `string \| function` | Der Dateiname des hochgeladenen Objekts mit denselben Platzhaltern. **Nur im Admin-Formular — wird von der API oder der Datenbank nicht erzwungen.** |
| `storageSource` | `string` | Welcher registrierte Bucket verwendet wird, wenn ein Projekt mehr als einen hat. Das Handle `bucket("media")` funktioniert hier ebenfalls |
| `public` | `boolean` | Unter dem öffentlichen Präfix speichern und über eine stabile, tokenlose, cachebare URL bereitstellen. Standardmäßig `false`, was private Objekte und kurzlebige signierte URLs bedeutet |
| `acceptedFiles` | `FileType[]` | MIME-Types, die diese Property akzeptiert. Die Sternchen-Form funktioniert — `image/*`. **Vom Server erzwungen** für jeden Upload in den `storagePath` der Property — siehe [Was der Server prüft](#was-der-server-prüft) |
| `maxSize` | `number` | Größte zulässige Datei in Bytes. **Vom Server erzwungen**, genau wie `acceptedFiles`, sowohl für reguläre als auch für fortsetzbare (resumable) Upload-Pfade |
| `metadata` | `Record<string, unknown>` | Objekt-Metadaten, die zusammen mit der Datei gespeichert werden sollen |
| `includeBucketUrl` | `boolean` | Schreibt `s3://my-bucket/path/to/file.png` anstelle von `path/to/file.png` in die Spalte. Standardmäßig `false` |
| `storeUrl` | `boolean` | Schreibt die Download-URL anstelle des Keys in die Spalte. Standardmäßig `false` und es empfiehlt sich, dies so zu belassen: Eine URL mit Token funktioniert nicht mehr, sobald das Token abläuft, und die ursprüngliche Referenz ist dann verloren |
| `imageResize` | `ImageResize` | Größenänderung und Zuschnitt vor dem Upload für `image/jpeg`, `image/png` und `image/webp`. **Nur im Admin-Formular — wird von der API oder der Datenbank nicht erzwungen.** |
| `processFile` | `(file: File) => Promise<File>` | Transformiert die Datei vor dem Upload. Läuft im Browser. **Nur im Admin-Formular — wird von der API oder der Datenbank nicht erzwungen.** |
| `postProcess` | `(pathOrUrl: string) => Promise<string>` | Transformiert den aufgelösten Pfad oder die URL vor dem Speichern. Läuft im Browser. **Nur im Admin-Formular — wird von der API oder der Datenbank nicht erzwungen.** |
| `previewUrl` | `(fileName: string) => string` | Erstellt die Vorschau-URL für Fälle, in denen die tatsächliche Adresse der Datei nicht der Wert des Feldes ist. **Nur im Admin-Formular — wird von der API oder der Datenbank nicht erzwungen.** |

### Größenänderung

`imageResize` akzeptiert `maxWidth` und `maxHeight` in Pixeln, einen `mode` von
`"contain"` (herunterskalieren zum Einpassen, der Standard) oder `"cover"` (den Bereich füllen und
beschneiden), ein `format` von `"original"`, `"jpeg"`, `"png"` oder `"webp"` sowie eine
`quality` zwischen 0 und 100 für die verlustbehafteten Formate — standardmäßig 80. Dies geschieht im
Browser, bevor die Bytes gesendet werden, sodass ein Upload, der nicht über das
Panel erfolgte, in seiner Originalgröße gespeichert wird.

### Was der Server prüft

`maxSize` und `acceptedFiles` wurden früher von genau einer Stelle durchgesetzt: dem
Browser. Die Upload-Route kannte lediglich eine globale Größenbegrenzung und wusste nichts über die
Property, für die eine Datei bestimmt war. So konnte `curl -F file=@payload.exe` am Dateiauswahldialog
vorbei eine 40 MB große ausführbare Datei in den Avatar-Bucket laden, ohne dass die Konfiguration,
die anderes vorschrieb, jemals herangezogen wurde.

Beide werden nun vom Server anhand dessen geprüft, **wo die Datei abgelegt wird**. Der
`storagePath` einer Property ist der Ort, an den ihre Dateien gelangen, daher gelten dort auch
ihre Beschränkungen: Jeder Upload, dessen Key eine Datei direkt unter diesem Pfad ist — sei es über das
Panel, `client.storage.putObject`, einen fortsetzbaren Upload, den Storage-Browser von Studio
oder `curl` — unterliegt diesen Beschränkungen auf der eigenen Storage-Quelle der Property,
unabhängig davon, ob er die Property benennt oder nicht. Platzhalter stimmen mit dem überein, was das Panel
einsetzen würde: `{id}`, `{rand}`, `{file}` und Ähnliche stehen für ein einzelnes Pfadsegment,
`{path}` für eine beliebige Anzahl. Der Pfad einer Property mit `public: true` liegt unter `public/`.

- Mehrere Properties, die sich einen Pfad teilen: Eine Datei, die von einer davon akzeptiert wird, wird akzeptiert.
- Ein Upload, der zusätzlich seine Property angibt (`collection` + `property`, wie
  sie von `putObject({ context })` übermittelt werden), wird ebenfalls an diese Property gebunden. Die Angabe einer
  weniger restriktiven Property schaltet nicht den Pfad einer strikteren Property frei.
  Uploads über das Panel (Dateifelder, Tabellenzellen und Markdown-Bilder)
  geben diese immer an.
- Ein als Funktion geschriebener `storagePath` kann nicht ausgelesen werden, ohne ihn auszuführen, weshalb
  für ihn keine serverseitige Regel existiert: Diese Limits gelten nur für Uploads, die die
  Property angeben, was bei Uploads über das Panel der Fall ist.
- Ein Pfad, der von keiner Property beansprucht wird, unterliegt allein dem Limit der Quelle
  (`STORAGE_MAX_FILE_SIZE`).

### Bilder in einem Markdown-Feld

Eine Markdown-Property (`admin.markdown: true`) mit einem `storage`-Block nimmt im
Editor Bild-Uploads entgegen. Der Text speichert jedes Bild als **Storage-Referenz** —
`![](rebase-storage:posts/abc_cover.png)` — und nicht als URL: Die URL einer privaten Datei
enthält ein Download-Token, das nach wenigen Minuten abläuft, während der Text dauerhaft gespeichert wird. Der
Editor und die Vorschau des Admin-Panels tauschen jede Referenz gegen eine frische URL aus, wenn
sie sie anzeigen; eine Website, die das Feld rendert, tut dasselbe mit
`resolveStorageReferences(text, client)` — siehe
[Files inside text](/docs/sdk/storage#files-inside-text).

Text, der vor Einführung der Referenzen gespeichert wurde, enthält die Download-URLs selbst mit abgelaufenen
Tokens. Der Editor, die Vorschauen und `resolveStorageReferences` erneuern diese beim
Anzeigen des Textes, da ein Token weiterhin sein Objekt benennt; erneutes Einfügen des Bildes
oder das Umschreiben des Textes mit `storageReferencesForDownloadUrls(text)` speichert eine
Referenz.

### Wohin die Datei abgelegt werden darf

`storagePath` ist ein Standardwert, keine feste Grenze: Serverseitig schränkt nichts einen
Upload auf dieses Präfix ein. Die Entscheidung darüber, wer wohin schreiben darf, ist
Aufgabe von Storage-Autorisierungsregeln — siehe [Storage](/docs/backend/storage).

### Dateien werden niemals automatisch gelöscht

Das Leeren eines Dateifeldes, das Ersetzen seiner Datei oder das Löschen der zugehörigen Zeile
belässt das gespeicherte Objekt an Ort und Stelle. Jeder Upload erhält einen eigenen Key, sodass ein
Ersetzen ein neues Objekt schreibt, anstatt das alte zu überschreiben, und
nichts entfernt das vorherige: Zwei Zeilen können denselben Key enthalten, sodass das
Panel nicht wissen kann, ob eine Datei ungenutzt ist. Objekte, auf die keine Zeile verweist, verbleiben im
Bucket und werden abgerechnet, bis Sie sie löschen — über den Storage-Browser von Studio,
mit `client.storage.deleteObject(key)` oder über eine Lifecycle-Regel für den
Bucket. `rebase storage orphans` listet die Dateien auf, die von keiner Zeile referenziert werden, und löscht sie
mit `--delete` — siehe [the CLI](/docs/cli/#rebase-storage).

### Eine Property zu einer anderen Storage-Quelle verschieben

Ein Dateifeld speichert den Key des Objekts, nicht dessen Quelle. Das Ändern der
`storageSource` einer Property verweist jeden vorhandenen Wert auf die neue Quelle, in der diese
Keys nicht existieren, sodass Vorschaubilder von Dateien, die vor der Änderung hochgeladen wurden, mit
"nicht gefunden" antworten. Kopieren Sie die Objekte unter denselben Keys in die neue Quelle, bevor Sie
die Property ändern — `rebase storage move --from <old> --to <new> --prefix <storagePath>` oder
die bordeigenen Tools des Anbieters wie `aws s3 sync` oder
`gcloud storage cp` — oder behalten Sie die alte Quelle für die bestehenden Dateien bei.
