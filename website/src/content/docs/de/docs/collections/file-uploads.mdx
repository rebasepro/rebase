<span class="since-badge" data-since="0.31">Seit 0.31</span>

Ein Dateifeld ist eine [`col.storage()`](/docs/schema/columns/#storage-columns)-Spalte.
Die Spalte enthält Text, den Schlüssel des Objekts im Bucket (oder dessen URL,
falls die Spalte dies vorgibt), und das CMS stellt sie als Upload-Feld mit einer
Vorschau dar.

Die Funktionsweise eines Storage-Feldes ist zweigeteilt, je nachdem, wo sie ausgeführt wird:

| Deklariert | Wo | Optionen |
|---|---|---|
| an der Spalte, in `backend/schema` | vom Server **und** dem CMS gelesen | `path`, `source`, `accept`, `maxBytes`, `imageResize`, `public`, `fileName`, `metadata`, `includeBucketUrl`, `storeUrl` |
| in `customizeTable`, in `frontend/src/cms` | nur im Browser | `storage.path(…)`, `storage.fileName(…)`, `storage.processFile`, `storage.postProcess`, `storage.previewUrl` |

Die Optionen der Spalte sind serialisierbar, sodass sie im Deskriptor der Tabelle
übertragen werden und der Server erzwingt, was er davon durchsetzen kann. Die
`customizeTable`-Optionen sind Funktionen: Sie können den Server nicht erreichen,
daher wirken sie sich nur auf Uploads aus, die über das CMS getätigt werden.

## Eine Datei

<span class="since-badge" data-since="0.31">Seit 0.31</span>

```ts
// backend/schema/listings.ts
import { defineTable, col } from "@rebasepro/server/schema";

export const listings = defineTable("listings", {
    columns: {
        id:     col.uuid().primaryKey().defaultRandom(),
        title:  col.text().notNull(),
        cover:  col.storage({ path: "listings/{id}/", accept: ["image/*"], maxBytes: "10MB",
                              imageResize: { maxWidth: 1600, format: "webp", quality: 80 } }),
        photos: col.storage({ path: "listings/{id}/gallery/", accept: ["image/*"] }).multiple(),
    },
    rls: "admin-only",
});
```

`cover` ist ein Upload-Feld, das ein Bild von maximal 10 MB akzeptiert, auf maximal
1600 Pixel Breite skaliert und als WebP gespeichert wird. Eine Spalte, deren `accept`
einen Bildtyp angibt, wird als Bild in der Vorschau angezeigt, und die erste dieser
Spalten füllt den Bild-Slot des Datensatzes in Karten und Listen.

## Mehrere Dateien

<span class="since-badge" data-since="0.31">Seit 0.31</span>

`.multiple()` macht die Spalte zu einem `TEXT[]` und das Feld zu einem Multi-Datei-Upload,
dessen Reihenfolge per Drag & Drop geändert werden kann. Jede Option gilt für jede Datei.

## Browserseitige Optionen

<span class="since-badge" data-since="0.31">Seit 0.31</span>

```tsx
// frontend/src/cms/listings.tsx
import { customizeTable } from "@rebasepro/cms";
import type { listings } from "../../../backend/schema/listings";

export const listingsCms = customizeTable<typeof listings>("listings", {
    fields: {
        cover: {
            storage: {
                // A folder per listing title, computed in the browser.
                path: ({ values }) => `listings/${String(values.title ?? "untitled").toLowerCase()}/`,
                fileName: ({ file }) => `${Date.now()}-${file.name}`,
            },
            urlPreview: "image",
        },
        photos: {
            sortable: true,
            storage: { processFile: async (file) => file },
        },
    },
});
```

| `storage.` | Ausführung | Auswirkung |
|---|---|---|
| `path(context)` | vor einem Upload | Der Ordner, in den die Datei gelangt, ersetzt die `path`-Vorlage der Spalte. |
| `fileName(context)` | vor einem Upload | Der gespeicherte Dateiname, ersetzt die `fileName`-Vorlage der Spalte. Kann asynchron sein. |
| `processFile(file)` | vor einem Upload | Transformiert die Datei (komprimieren, Metadaten entfernen). |
| `postProcess(pathOrUrl)` | nach einem Upload | Transformiert den Pfad oder die URL, bevor er/sie in die Spalte geschrieben wird. |
| `previewUrl(fileName)` | beim Rendern | Die URL zur Vorschau einer gespeicherten Datei, wenn sie nicht der Wert des Feldes ist. |

`path` und `fileName` erhalten den Kontext des Uploads: das `file`, die `id` des
Datensatzes (fehlt bei einem neuen Datensatz), seine bearbeiteten `values`, den
`propertyKey` und die aufgelösten Storage-Regeln. Bei einer `.multiple()`-Spalte
werden dieselben `storage`-Optionen direkt auf das Feld angewendet und gelten für
jede Datei.

`urlPreview` legt fest, wie der gespeicherte Wert in der Vorschau angezeigt wird
(`"image"`, `"video"`, `"audio"`, `"file"` oder `true` für einen Link), und `clearable`
fügt ein Steuerelement hinzu, das das Feld leert.

## Was der Server prüft

<span class="since-badge" data-since="0.31">Seit 0.31</span>

`accept` und `maxBytes` werden vom Server anhand dessen erzwungen, **wo die Datei
abgelegt wird**. Der `path` einer Spalte ist der Ort, an den ihre Dateien gelangen,
daher gelten dort auch ihre Beschränkungen: Jeder Upload, dessen Schlüssel eine Datei
direkt unter diesem Pfad ist, muss diese erfüllen – sei es über das CMS,
`client.storage.putObject`, einen fortsetzbaren Upload, den Storage-Browser des
Studios oder `curl`, unabhängig davon, ob die Spalte angegeben wird oder nicht, im
Bucket der Spalte selbst. Platzhalter entsprechen dem, was das CMS einsetzen würde:
`{id}`, `{rand}`, `{file}` und Ähnliches stehen für ein einzelnes Pfadsegment, `{path}`
für eine beliebige Anzahl. Der Pfad einer Spalte mit `public: true` liegt unter `public/`.

- Mehrere Spalten, die denselben Pfad teilen: Eine Datei, die von einer davon akzeptiert wird, wird akzeptiert.
- Ein Upload, der auch seine Spalte benennt (wie es die Uploads des CMS tun), wird
  auch an dieser Spalte gemessen. Die Angabe einer weniger restriktiven Spalte schaltet
  nicht den Pfad einer strikteren Spalte frei.
- Eine `storage.path`-Funktion in `customizeTable` kann vom Server nicht gelesen
  werden; daher wird eine Datei, die unter dem von ihr berechneten Pfad hochgeladen
  wird, nur dann an den Limits der Spalte gemessen, wenn der Upload die Spalte benennt
  (was bei Uploads des CMS immer der Fall ist).
- Ein Pfad, den keine Spalte beansprucht, unterliegt ausschließlich dem eigenen Limit
  des Buckets (`STORAGE_MAX_FILE_SIZE`).

`imageResize`, `processFile` und `postProcess` finden im Browser statt, bevor die
Bytes gesendet werden: Eine Datei, die auf andere Weise hochgeladen wird, wird so
gespeichert, wie sie gesendet wurde.

## Wo eine Datei abgelegt werden darf

<span class="since-badge" data-since="0.31">Seit 0.31</span>

`path` ist ein Standardwert, keine feste Grenze: Nichts auf dem Server beschränkt
einen Upload zwingend darauf. Wer wohin schreiben darf, ist eine Autorisierungsregel
für den Speicher; siehe [Storage](/docs/backend/storage/).

## Dateien werden nie automatisch gelöscht

<span class="since-badge" data-since="0.31">Seit 0.31</span>

Das Leeren eines Dateifelds, das Ersetzen seiner Datei oder das Löschen der Zeile
belässt das gespeicherte Objekt dort, wo es ist. Jeder Upload erhält einen eigenen
Schlüssel, sodass ein Ersetzen ein neues Objekt schreibt und nichts das vorherige
entfernt: Zwei Zeilen können denselben Schlüssel enthalten, daher kann das CMS
nicht wissen, ob eine Datei ungenutzt ist. Objekte, auf die keine Zeile verweist,
verbleiben im Bucket und werden in Rechnung gestellt, bis Sie sie über den
Storage-Browser des Studios, mit `client.storage.deleteObject(key)` oder über eine
Lebenszyklusregel für den Bucket löschen. `rebase storage orphans` listet die
Dateien auf, die von keiner Zeile referenziert werden, und löscht sie mit `--delete`;
siehe [die CLI](/docs/cli/#rebase-storage).

## Eine Spalte in einen anderen Bucket verschieben

<span class="since-badge" data-since="0.31">Seit 0.31</span>

Ein Dateifeld speichert den Schlüssel des Objekts, nicht dessen Bucket. Das Ändern
der `source` einer Spalte verweist alle vorhandenen Werte auf den neuen Bucket, in
dem diese Schlüssel nicht existieren, sodass die Vorschau älterer Dateien mit „not found“
antwortet. Kopieren Sie die Objekte zunächst unter denselben Schlüsseln in den neuen
Bucket – entweder mit `rebase storage move --from <old> --to <new> --prefix <path>`
oder mit den eigenen Werkzeugen des Anbieters wie `aws s3 sync` oder `gcloud storage cp` –
oder behalten Sie den alten Bucket für die bestehenden Dateien bei.
