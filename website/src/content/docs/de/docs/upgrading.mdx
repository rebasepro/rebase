# Upgrade einer bestehenden App

Dreizehn Schritte, die neuesten zuerst. Beginnen Sie bei dem Schritt direkt über Ihrer aktuellen Version und arbeiten Sie sich nach unten durch — oder fangen Sie, wenn Sie von 0.12 kommen, ganz unten an und arbeiten sich nach oben vor.

| Aktuelle Version | Lesen | Was sich für Sie ändert |
|---|---|---|
| **0.31** | [das 0.32.0-Changelog](/docs/changelog/) | 0.32 deklariert keine Breaking Changes: Aktualisieren Sie jedes `@rebasepro`-Paket. Zwei Dinge fallen Skripten auf: Ein destruktiver CLI-Befehl (`api-keys revoke`, `db branch delete`, `cloud env unset`, `cloud compute set`, …) verlangt zuerst eine Bestätigung und verweigert ohne Terminal oder unter `--json` die Ausführung mit `confirmation_required`, bis Sie `--yes` übergeben; und die Befehle `rebase_cloud_deploy`, `rebase_cloud_env_set`, `rebase_cloud_rollback` sowie `rebase_cloud_provision` des lokalen MCP-Servers werden nur mit `confirm: true` ausgeführt. `REALTIME_CDC=auto` liest jetzt das Write-Ahead-Log, sofern die Datenbank dies erlaubt; setzen Sie `REALTIME_CDC=trigger`, um die Erfassung über Trigger beizubehalten. |
| **0.30** | [0.30 → 0.31](/docs/upgrading/0-30-to-0-31/) | Tabellen in `backend/schema` (`defineTable`) ersetzen `config/collections`, und es gibt kein Config-Paket mehr: Führen Sie `rebase migrate collections-to-tables` aus, was das Projekt migriert und nachweist, dass das generierte SQL unverändert bleibt. Das Admin-Panel rendert die Tabellen, die der Server bereitstellt, angepasst über `frontend/src/cms`; das SDK nutzt `data.table(slug)` und `tables: tablesDictionary`; Bundles haben das Format 3, daher vor dem Deployment neu bauen; MongoDB wird eingestellt. |
| **0.29** | [0.29 → 0.30](/docs/upgrading/0-29-to-0-30/) | Ein Backend, das mit `initializeRebaseBackend` gestartet wird, speichert das Refresh-Token in einem Cookie, sofern nicht `cookieAuth: false` gesetzt ist. Ein Aufrufer, der es ohne `x-rebase-auth-flow: json` aus dem Body liest, erhält daher `""`. |
| **0.27 – 0.28** | [0.27 → 0.29](/docs/upgrading/0-27-to-0-29/) | Alles, was der Admin an Ihren Code übergibt, ist die Zeile des Servers mit der zugehörigen ID: `context.data` und `browserCallbacks` des Browsers übergeben ISO-Strings und Fremdschlüssel anstelle von `Date`-Objekten und Beziehungsobjekten, was kein Compiler erkennt; die `Entity`-Daten-Hooks werden intern; und Callbacks, Panels, das Seitenpanel sowie die Auswahl erwarten `row` und `id` anstelle von `entity` und `entityId`. 0.28 enthält keine Breaking Changes, daher ist dies ein einzelner Schritt von 0.27. |
| **0.26** | [0.26 → 0.27](/docs/upgrading/0-26-to-0-27/) | Ein Cron-Zeitplan, der beide Tagesfelder einschränkt, greift bei jedem der beiden und läuft daher häufiger; ein Zeitplan mit einer fehlerhaften Zahl wird abgelehnt, sodass dieser Job nicht mehr ausgeführt wird. Ein Schlüssel, dessen `isId`-Strategie vom Typ nicht erfüllt werden kann, verhindert den Start. Auf Rebase Cloud schlägt ein Deploy oder Preview fehl, wenn eine Funktions- oder Cron-Datei nicht geladen werden kann. |
| **0.25** | [0.25 → 0.26](/docs/upgrading/0-25-to-0-26/) | Ein Schreibvorgang, der eine Multi-Hop-`via`-Relation benennt, ein Rollenname, der keine einzelne Rolle darstellt, ein Local-Storage-Page-Token von vor dem Upgrade und ein nicht funktionsfähiger Functions-Upstream werden abgewiesen. OAuth-Sign-in bestätigt ein nicht verifiziertes Konto, anstatt mit `local-account-unverified` zu antworten, der MCP-Server sendet `REBASE_TOKEN` nicht mehr an die App, und generierte Typen verwerfen den Schlüssel eines `excludeFromApi`-belongsTo. Auf Rebase Cloud wurden `rebase cloud webhooks` und `--scale-to-zero true` eingestellt, und ältere Tokens müssen möglicherweise neu erstellt werden. |
| **0.24** | [0.24 → 0.25](/docs/upgrading/0-24-to-0-25/) | `?count=` bei einer REST-Liste wird zum Schalter für die Anzahl hinter `meta.total`, sodass ein Filter auf eine Spalte namens `count` in `?where=` gehört; `list_collections` des Remote-MCP sendet seine Auflistung nur im Textblock ohne `structuredContent`; und `@rebasepro/app` exportiert die spanische Übersetzungstabelle `es` nicht mehr. Ein einfaches `OPTIONS` auf eine Route ohne Handler, kollidierende Tabellennamen beim Start, ein Upsert auf die Users-Collection, `page` zusammen mit `offset`, ein leerer String bei einem Pflichtfeld und ein Administrator-Passwort, das die Passwortrichtlinie verletzt, werden abgewiesen. Sitzungen bleiben standardmäßig 30 Tage bei Inaktivität gültig, `client.cron` ruft `/api/admin/cron` auf, Offline-Lesezugriffe, die nicht vollständig beantwortet werden können, schlagen mit `OFFLINE` fehl, und einige interne Exporte sowie ungenutzte Props wurden entfernt. |
| **0.23** | [0.23 → 0.24](/docs/upgrading/0-23-to-0-24/) | Das von `db push` und `db generate` erzeugte SQL wandert aus `drizzle/` in das nicht versionierte `.rebase/sql/`, das Flag `--generate` von `rebase dev` entfällt, da `dev` die SDK-Typen immer neu generiert, und eine Live-Schemaänderung committet kein SQL. Berechtigungen werden zu Scopes: Admin-Oberflächen verlangen nach einem Scope statt der Admin-Rolle, API-Schlüssel enthalten Scopes statt einer Berechtigungsliste und eines `admin`-Flags, und `schema-admin` ist kein Administrator mehr. Ein relatives `--collections` wird von dem Verzeichnis aus gelesen, in dem der Befehl ausgeführt wird; ein Upsert in eine gelöschte Zeile (Papierkorb) sowie ein Update, das einen Schlüssel ändert, werden abgelehnt; der Remote-MCP-Endpunkt akzeptiert die Argumente des SDKs; und offene Realtime-Sockets, E-Mail-Verifizierungslinks, `signUp` und MFA-Wiederherstellungscodes ändern ihren Umgang mit Sitzungen. |
| **0.21 – 0.22** | [0.21 → 0.23](/docs/upgrading/0-21-to-0-23/) | Ein API-Schlüssel auf einem verschachtelten Pfad benötigt `read` auf übergeordneten Pfaden, unlesbare numerische Variablen und Sitzungsdauern verhindern den Start, ein benutzerdefiniertes Auth-Repository benötigt `unlinkUserIdentity`, und Gast-Upgrades verwenden das `register`-Captcha. 0.22 enthält keine Breaking Changes, daher ist dies ein einzelner Schritt von 0.21. |
| **0.18 – 0.20** | [0.18 → 0.21](/docs/upgrading/0-18-to-0-21/) | `context.client.data` kompiliert in einem Collection-Callback nicht mehr — fragen Sie Daten stattdessen über `context.data` ab — und `selectedEntities` weicht einer Selektion, die auch für Zeilen stehen kann, die noch niemand geladen hat. 0.19 und 0.20 deklarieren keine Breaking Changes, daher ist dies ein einzelner Schritt von 0.18. |
| **0.17** | [0.17 → 0.18](/docs/upgrading/0-17-to-0-18/) | Elf Breaking Changes, die meisten davon Compiler-Fehler statt stiller Verhaltensänderungen. `rebase.data` verschwindet zur Laufzeit, Peer-Dependency-Bereiche werden auf Carets (`^`) eingeschränkt und die Mindestanforderung für Node steigt auf 22.22.0. |
| **0.14 – 0.16** | [0.14 → 0.17](/docs/upgrading/0-14-to-0-17/) | Die Admin-Pakete wurden umbenannt, Ressourcen werden deklariert statt konfiguriert, und ein zuvor erstelltes Bundle lässt sich auf einer aktuellen Runtime nicht mehr starten. 0.15 und 0.16 ändern nichts Grundlegendes, daher ist dies ein einzelner Schritt von 0.14. |
| **0.13** | [0.13 → 0.14](/docs/upgrading/0-13-to-0-14/) | Jeder Wire-Key ist in camelCase gehalten, und die anonyme Anmeldung ist opt-in. |
| **0.12** | [0.12 → 0.13](/docs/upgrading/0-12-to-0-13/) | Der größte Schritt und der einzige, der ändert, **wer Ihre Daten lesen kann**. Er entfernt das `auth`-Schema, benennt Pakete um, ändert die Bedeutung von `id`, entfernt CJS, migriert das Admin-Panel auf react-router 8 und behebt drei Fälle, in denen unabsichtlich Zugriff gewährt werden konnte. |

Die Abschnitte jeder Seite sind in der Reihenfolge angeordnet, in der Sie die Änderungen durchführen müssen, und jeder nennt das Symptom, das Sie sonst vom falschen Ende her debuggen würden.

Danach, unabhängig davon, welchen Schritt Sie gemacht haben:

- [Die Upgrade-Checkliste](#upgrade-checklist) unten — die Suchmuster (greps) und Befehle, die Sie im Anschluss ausführen sollten, zusammengefasst in einem Block.

## Upgrade checklist

```
[ ] grep for authenticated() and (auth|rebase).uid() IS NOT NULL in config/collections/
[ ] decide the intent of each rule; rewrite the ones that meant "public"
[ ] replace not(authenticated()) with serverContext()
[ ] if realtime.requireAuth was true with an AuthAdapter, treat the socket as
    having been open — verify RLS on every subscribable collection (section 2)
[ ] SELECT ... FROM pg_policies — record the qual of every policy BEFORE
[ ] update package names and imports
[ ] grep for rebase.data — it is now rebase.dataAsAdmin (section 8)
[ ] grep for the other ten removed deprecated exports (section 8)
[ ] drop react-router-dom; import RouterProvider from "react-router/dom"
[ ] check node >= 22.22.0 and react >= 19.2.7 (react-router 8 requires both)
[ ] move defaultSecurityRules into config/collections/index.ts
[ ] grep for .userId
[ ] grep for row.id on tables not keyed on id
[ ] run db push
[ ] run rebase doctor --policies — expect no Insecure or Orphaned entries
[ ] SELECT ... FROM pg_policies again — confirm every intended change landed
[ ] exercise the app signed OUT, in a private window — watch the websocket too

--- 0.13 → 0.14 (part 2) ---
[ ] re-run rebase generate-sdk, then build — the compiler finds row.author_id
[ ] grep for snake_case where/orderBy keys; a stale one is a 400, not a warning
[ ] grep for raw fetch consumers reading row.<something>_id — these read
    undefined and raise nothing
[ ] if the project was introspected, re-run rebase schema introspect
[ ] decide anonymous sign-in: set auth.allowAnonymous: true, or confirm you
    never used it (grep for signInAnonymously)
[ ] drop @rebasepro/client-postgres from package.json

--- 0.14 → 0.17 (part 3) ---
[ ] rename @rebasepro/admin → @rebasepro/cms and admin-types → cms-types,
    and RebaseAdmin → RebaseCMS
[ ] move dataSources / storageSources out of the backend config into
    rebase.json and config/, then `rebase build` — an old bundle will not boot
[ ] grep collections for admin.titleProperty; it is refused at boot now
[ ] grep crons for ctx.client and for `userId` as an identity key
[ ] rename --legacy to --workspace wherever build/start is scripted
[ ] if you implement EmailService yourself, `send` must return a result

--- 0.30 → 0.31 ---
[ ] bump every @rebasepro package to 0.31 first, then pnpm install
[ ] rebase migrate collections-to-tables on a clean tree; read the manual steps
[ ] move config/index.ts `callbacks` to backend/hooks.ts by hand, if you had them
[ ] rebase generate-sdk; rebase db push --dry-run plans no change
[ ] run the git rm line the codemod printed (your own config/ modules may stay)
[ ] send a to-one relation as its key, not { id } — that is a 400 now
[ ] call /api/docs signed in, or set REBASE_ENABLE_SWAGGER=true to publish it
[ ] rename the MCP tools in prompts and allow-lists (list_tables, query_table, …)
[ ] rebuild the bundle and deploy — a format-2 bundle is refused

--- 0.31 → 0.32 ---
[ ] bump every @rebasepro package to 0.32, then pnpm install
[ ] add --yes to scripted destructive CLI commands (they refuse with confirmation_required)
[ ] rebase verify — fix any rls-policy-recursion it reports
[ ] rebase build — it warns when config/index.ts still exports storageAuthorize
```

`rebase doctor --policies` ist der Befehl, den Sie in Ihre CI einbinden sollten: Er bricht mit einem Exit-Code ungleich null ab, wenn eine Richtlinie noch die freizügige Tautologie enthält oder durch einen früheren Push ersetzt wurde. Die Leseabfragen von `pg_policies` davor und danach lohnen sich dennoch — sie zeigen Ihnen die Ausdrücke selbst, was die einzige Möglichkeit ist, eine Fail-Open-Richtlinie zu erkennen, die in einer Schreibweise verfasst ist, die der Detektor nicht erkennt. Weder die Pakete noch das Typsystem weisen Sie darauf hin: Die Änderung befindet sich in der Datenbank, und `db push` ist das Einzige, was sie dorthin bringt.

## Rollback eines Releases

Bevor Sie ein Rollback auf ein Release durchführen, das älter ist als jenes, das Admin-Request-Companions eingeführt hat (siehe [Changelog](/docs/changelog/)), machen Sie diese unwirksam. Eine ältere Runtime löscht Companions niemals, sodass eine Regel, die Sie nach dem Rollback ändern, weiterhin jedem Admin Zugriff auf jede Zeile gewähren würde. Führen Sie `REVOKE rebase_admin_request FROM rebase_user_admin;` einmal pro Admin-Request-Rolle aus oder löschen Sie die `_ar_`-Policies. [Admin-Lesezugriffe nutzen die Indizes des Eigentümers](/docs/deployment/existing-database/#admin-reads-use-the-owners-indexes) erklärt die Hintergründe.
