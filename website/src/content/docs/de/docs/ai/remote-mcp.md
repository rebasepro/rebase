:::tip[Verbinden Sie Claude mit Ihren eigenen Projekten?]
Das ist der [Rebase-Connector](/docs/ai/rebase-connector/): ein Connector für alle, und ein selbst gehosteter Server tritt ihm mit `rebase cloud connect` bei. Diese Seite richtet sich an Personen, die Ihre App **nutzen**.
:::

Der [MCP-Server](/docs/ai/mcp/) ist ein Entwickler-Tool: Er läuft auf Ihrem Rechner und enthält einen Service-Key oder einen API-Schlüssel. Ein bereitgestelltes Backend kann MCP auch selbst unter `/mcp` für die Personen bereitstellen, die Ihre Anwendung nutzen. Ein Assistent, den ein Nutzer verbindet, liest und schreibt das Projekt **als diese Person**, und jeder Aufruf läuft unter dessen eigener Row-Level-Security (RLS).

Er ist standardmäßig deaktiviert, und beide Variablen sind erforderlich:

```bash
REBASE_MCP_ENABLED=true
REBASE_PUBLIC_URL=https://app.example.com   # this deployment's real origin
```

Ohne `REBASE_PUBLIC_URL`, ein JWT-Secret oder einen Datentreiber, der eine Abfrage auf einen einzelnen Benutzer beschränken kann, verweigert der Endpunkt die Bereitstellung und gibt den Grund im Boot-Log an. Keine `REBASE_ROLE` schaltet ihn ein.

`rebase dev` ist die einzige Ausnahme: Es aktiviert `/mcp` für den Server, den es startet, und dieser Server gibt seine eigene Adresse, `http://localhost:<port>`, als öffentliche URL an, sodass nichts konfiguriert werden muss. Eine `REBASE_MCP_ENABLED`-Zeile in der Shell oder in `.env` entscheidet weiterhin, einschließlich `false`. Das Dev-Banner gibt den Endpunkt auf einer `MCP:`-Zeile aus, sobald er eingebunden ist.

## Einen Client verbinden

```bash
rebase mcp connect            # pick the clients to connect, from a list
rebase mcp connect --client claude-code,cursor
rebase mcp connect --print    # the URL, the command and the install links; changes nothing
rebase mcp url                # the URL alone
```

`rebase mcp connect` fragt den Server, wo sich `/mcp` befindet, indem es das Dokument liest, das dieser unter `/.well-known/oauth-protected-resource/mcp` veröffentlicht. So stimmt die URL hinter einem Proxy, unter `REBASE_PUBLIC_URL` und auf einem Dev-Port, der sich geändert hat. Anschließend verbindet es jeden ausgewählten Client:

| Client | `--client` | Was passiert |
|---|---|---|
| Claude Code | `claude-code` | Führt `claude mcp add --transport http <name> <url>` aus |
| Cursor | `cursor` | Öffnet den Installationslink für Cursor |
| VS Code | `vscode` | Öffnet den Installationslink für VS Code |
| Claude (claude.ai, Desktop, Mobilgeräte) | `claude` | Gibt die Schritte für Settings → Connectors mit der einzufügenden URL aus |
| ChatGPT | `chatgpt` | Gibt die Schritte für dessen Connector-Einstellungen aus |

Clients, die als installiert erkannt werden, sind bereits vorausgewählt. Claude und ChatGPT verbinden sich von ihren eigenen Servern aus, die `localhost` nicht erreichen können; gegenüber einem Dev-Server werden sie daher als Server aufgeführt, die ein bereitgestelltes Projekt erfordern. `--client all` wählt alle aus. Ohne Terminal oder unter `--json` und ohne `--client` gibt der Befehl dasselbe wie `--print` aus und verbindet nichts.

Der abgefragte Server ist der des Projekts selbst: `REBASE_BASE_URL`, andernfalls das laufende `rebase dev`. `--cloud` fragt das Rebase-Cloud-Projekt ab, mit dem das Verzeichnis verknüpft ist, und `--url <server>` jedes beliebige Backend. Ein Server mit deaktiviertem `/mcp` antwortet dort nicht, und der Befehl erklärt, wie man es aktiviert.

Der Server wird unter dem Namen des Projekts registriert, mit `-local` für eine Instanz auf diesem Rechner, sodass sowohl ein lokales als auch ein bereitgestelltes Projekt verbunden werden können; `--name` ändert dies. Er heißt niemals `rebase`, der Name des [Entwickler-MCP-Servers](/docs/ai/mcp/) in der `.mcp.json` eines Projekts, den ein zweiter Server desselben Namens verdecken würde.

Das Admin-Panel bietet dieselben Schritte. Seine Seitenleiste enthält eine Schaltfläche **Connect AI**, die die vom Server veröffentlichte URL, den Befehl `claude mcp add`, die Installationslinks für Cursor und VS Code sowie bei einem bereitgestellten Projekt die Connector-Schritte für Claude und ChatGPT anzeigt. Darunter werden die Agenten aufgelistet, die die angemeldete Person verbunden hat, jeweils mit einer Option zum Trennen der Verbindung. Jeder angemeldete Benutzer sieht die Schaltfläche, solange `/mcp` aktiviert ist. Wenn es deaktiviert ist, sieht sie nur ein Administrator, zusammen mit Hinweisen zur Aktivierung.

## Was eine Verbindung erhält

- **OAuth mit einem Genehmigungsbildschirm.** Ein Client findet den Autorisierungsserver über `/.well-known/oauth-protected-resource`, registriert sich selbst (dynamische Registrierung ist standardmäßig aktiviert; `REBASE_MCP_OPEN_REGISTRATION=false` beschränkt sie auf von Ihnen registrierte Clients) und leitet die Person zu einem Genehmigungsbildschirm weiter, der sie über Ihr bestehendes `/auth/login` anmeldet. Ein Konto mit Zwei-Faktor-Authentifizierung wird anschließend über die bestehenden `/auth/mfa/challenge`-Routen nach seinem Authenticator-Code oder einem Wiederherstellungscode gefragt. Wenn das eigene Frontend Ihrer App eine Sitzung im selben Browser hält, bietet der Bildschirm dieses Konto an, und "Allow" erteilt die Zustimmung ohne Passwort; so verbindet sich jemand, der sich ausschließlich mit Google, GitHub oder einem E-Mail-Link anmeldet. Andernfalls meldet sich der Nutzer mit einem Passwort an, und wer keines hat, legt zuerst eines über `/auth/forgot-password` fest (das "Passwort vergessen" Ihrer App); der Bildschirm weist darauf hin. Er nennt auch den Host, an den der Autorisierungscode gesendet wird, und weist darauf hin, dass dieser Host nicht verifiziert ist: Da jeder einen Client unter einem beliebigen Namen registrieren kann, ist der Host der Teil, den ein Nutzer überprüfen kann.
- **Siebzehn Tools, drei Scopes.** Dieselben [Scopes](/docs/backend/roles-and-scopes/), die jede Anmeldeinformation verwendet. `data:read` bietet `list_tables`, `describe_table`, `query_table`, `count_rows`, `aggregate_rows`, `get_row`, die drei Ansichten `show_table`, `show_record` und `show_app`, `show_app_guide` sowie die experimentellen `list_apps` und `open_app`; `data:write` fügt `create_row`, `update_row` und die experimentellen `save_app` und `delete_app` hinzu; `data:delete` fügt `delete_row` hinzu. Ein Client, der nichts anfordert, erhält `data:read`. Jeder Scope lässt sich auf eine Tabelle eingrenzen: `data:read:posts` listet, beschreibt und liest `posts` und sonst nichts. Ein Scope bestimmt, welche Tools angeboten werden und welche Tabellen sie erreichen, nicht welche Zeilen: Eine leere Liste kann auf greifendes RLS zurückzuführen sein, und `data:write` kann weiterhin keine Zeile schreiben, auf die die Person keinen Zugriff hat.
- **Drei Tools bringen Ihr Admin-Panel direkt zum Nutzer.** In einem Client, der MCP Apps rendert (wie Claude), öffnen sie die Ansichten des Admin-Panels direkt in der Konversation, basierend auf den Tabellendeskriptoren, die das Backend für diese Person bereitstellt – Spalten, Enums, Validierung, Relationen – zusammen mit den UI-Präferenzen, die das Panel zusammensetzt: die im Bundle enthaltene `ui-config.json`, die des Workspaces und die der Person selbst (ein API-Schlüssel hat keine), sodass Bezeichnungen, Spaltenreihenfolge, ausgeblendete Spalten und Enum-Labels mit dem Panel übereinstimmen. Die individuellen Anpassungen des Panels Ihres Projekts werden dort angezeigt, wo das Backend seine MCP-Ansicht bereitstellt.
  - `show_table` nimmt die Argumente von `query_table` entgegen, plus `view` (`table`, `list`, `cards` oder `kanban`), und öffnet die Ansicht der Tabelle: Die Person kann suchen, filtern, sortieren, paginieren, das Formular einer Zeile öffnen und neue Zeilen hinzufügen.
  - `show_record` öffnet das Formular einer einzelnen Zeile (`id`) oder ein Formular für eine neue Zeile, das mit den vom Modell ausgefüllten `values` vorbefüllt ist, sodass die Person diese selbst prüfen und speichern kann.
  - `show_app` führt eine App aus, die das Modell für die jeweilige Aufgabe schreibt: eine React-Komponente (`code`) und die `tables`, die sie liest. Sie importiert die eigenen Pakete von Rebase, sodass derselbe Code in Ihrem Projekt funktioniert:
    - `@rebasepro/app`: `useRows`, `useRow`, `useRowCount`, `useAggregate` und `useRowWrites` über die Zeilen des Projekts;
    - `@rebasepro/cms`: das `CollectionPanel` des Admin-Panels (mit `CollectionToolbar` und deren Komponenten sowie `onRowClick`, das der App die angeklickte Zeile übergibt, wie `useRows` sie liest), `RecordForm` und `FormField`, `RecordDetail`, `FieldValue` und `useSidePanel`, die jeweils ihre Tabelle über den Pfad benennen, mit Ihren benutzerdefinierten Feldern, Ansichten und Aktionen;
    - `@rebasepro/ui`, das gesamte UI-Kit, einschließlich `SplitView` sowie KPI-Kacheln und Diagrammen.

    Der Server kompiliert den Code vorab, sodass ein Syntaxfehler, ein Modul, das die Ansicht nicht bereitstellt, oder ein Name, den sie nicht aus `@rebasepro/cms` oder `@rebasepro/app` anbietet, als Fehler des Aufrufs inklusive Zeilenangabe zurückgegeben wird. Ein Fehler während der Ausführung wird anstelle der App angezeigt und dem Modell mit der nächsten Nachricht der Person mitgeteilt. Eine App darf nur die Tabellen verwenden, die sie auflistet. Ihre Stile sind die Standard-Utilities von Tailwind, die vor dem Eintreffen einer App mit der Ansicht gebaut wurden: Ein beliebiger Wert wie `h-[560px]` bewirkt dort nichts, eine exakte Größe muss daher als `style` angegeben werden.

    Die Beschreibung von `show_app` enthält nur das Wesentliche, da ein Client eine lange Tool-Beschreibung möglicherweise abschneidet (claude.ai tut dies bei etwa 4.000 Zeichen). Sie weist das Modell an, zuerst `show_app_guide` aufzurufen, das alle Hooks, Komponenten und Props zurückgibt, die eine App verwenden darf, einschließlich eines ausgearbeiteten Beispiels. `show_app_guide` wird überall dort angeboten, wo auch `show_app` verfügbar ist.

  Jeder Lese- und Speichervorgang in der Ansicht ist ein Aufruf der Lese- und Schreib-Tools, der als die jeweilige Person unter deren RLS ausgeführt wird. Ein Formular bietet daher nur das an, was der Verbindung gewährt wurde: Ohne `data:write` ist es schreibgeschützt, und ein Feld, das die Rollen der Person nicht lesen dürfen, ist nicht enthalten. Das ist auch die Grenze, innerhalb derer der Code einer App arbeitet: Er läuft in der Ansicht, sodass jeder Aufruf eines dieser Tools im Namen der Person erfolgt und nichts tun kann, was das Modell nicht auch mit denselben Tools tun könnte. Auf dem gehosteten Connector wird jeder Schreibvorgang zudem vom Server geplant und bestätigt. Innerhalb dieses Rahmens bittet `useRowWrites` die Person vor dem Schreiben um Bestätigung, sodass eine App nicht ohne deren Klick schreibt; die eigenen Steuerelemente des Admins (das Speichern eines Formulars, ein Löschvorgang, eine Tabellenbearbeitung) verhalten sich wie auf einem `show_table`-Bildschirm. Dem Modell wird mitgeteilt, was geändert wurde. Es liest die Zeilen, die jedes Tool zurückgibt, nicht die Deskriptoren, mit denen die Ansicht gerendert wird. Ein Client ohne MCP Apps, wie Claude Code oder Cursor, zeigt nichts an, und das Modell liest dieselben Zeilen, die es von `query_table` erhalten würde.
- **Experimentell: Im Projekt gespeicherte Apps.** `save_app` speichert eine App, die das Modell mit `show_app` erstellt hat, damit sie erneut geöffnet werden kann: Es kompiliert den Code wie `show_app` und speichert ihn mit `title`, `tables` und `visibility`, welche `personal` (der Eigentümer, Standard), `roles` (jeder mit einer der angegebenen `roles`) oder `team` (jeder, der sich anmeldet) sein kann. Das Speichern für mehr als sich selbst erfordert die Admin-Rolle, da eine geteilte App von einer KI geschriebener Code ist, der für andere Personen ausgeführt wird. Nur der Eigentümer oder ein Admin kann eine App ersetzen (`id`) oder löschen, und eine Person kann maximal 200 Apps behalten. `list_apps` listet die Apps auf, die der Aufrufer öffnen darf, `open_app` öffnet eine App wie `show_app`, und `delete_app` entfernt eine. Eine App sehen zu können bedeutet nicht, auf ihre Daten zugreifen zu können: Eine geöffnete App liest und schreibt über die oben genannten Tools als diejenige Person, die sie öffnet, unter deren RLS. Die Apps befinden sich in `rebase.saved_apps`, das das Backend beim ersten Zugriff eines Tools erstellt und für keinen Endbenutzer freigibt.
  Das Admin-Panel öffnet dieselben Apps: Fügen Sie `savedAppsView` aus `@rebasepro/cms` zu Ihren `views` hinzu. Es führt eine App in einem Iframe aus, der ohne `allow-same-origin` und ohne eigenes Netzwerk isoliert ist, und leitet seine Tool-Aufrufe an `POST /api/admin/apps/mcp` weiter – dieselben Tools für die Sitzung des Admin-Panels, die mit den Admin-Routen eingebunden wird, unabhängig davon, ob `REBASE_MCP_ENABLED` gesetzt ist. Die Namen und Signaturen der Tools können sich noch ändern.
- **Vor 0.24 erteilte Berechtigungen behalten ihren Umfang.** `mcp:read` wird bei gespeicherten Berechtigungen und bereits ausgestellten Tokens als `data:read` interpretiert, und `mcp:write` als `data:write data:delete`.
- **Ein API-Schlüssel funktioniert ebenfalls.** `/mcp` akzeptiert auch `Authorization: Bearer rk_…` für Clients, die über einen Header statt über einen OAuth-Flow konfiguriert sind. Der Schlüssel erreicht die Tools, die seine `data:*`-Scopes abdecken, und agiert als die jeweilige Entität: ein [persönlicher Schlüssel](/docs/backend/api-keys/#personal-keys) als sein Eigentümer, ein Service-Key als `api-key:<id>`.
- **Das Vokabular des SDKs, die Antworten von REST.** Die Tools akzeptieren dieselben Parameter wie das SDK – `where` (`{"status": ["==", "paid"]}`), `orderBy` (`["created_at", "desc"]` oder `"created_at:desc"`), `limit`, `offset`, `searchString` und `data` für Schreibvorgänge – und lesen über den Pfad `GET /api/data/<table>`, sodass eine Zeile so zurückgegeben wird, wie REST sie ausliefert (ISO-Datumsangaben, ein `belongsTo` als Fremdschlüssel, z. B. `authorId`), und in einem Update unverändert zurückgesendet werden kann. `query_table` antwortet mit `{ data, meta }` inklusive `meta.total` und `meta.hasMore`, und `count_rows` mit `{ count }`; `tools/list` stellt sowohl für diese als auch für `aggregate_rows` und `get_row` ein `outputSchema` bereit, das dort flexibel gehalten ist, wo Antworten variieren können. `aggregate_rows` entspricht `GET /api/data/<table>/aggregate`: `select` ist eine Liste in der REST-Grammatik (`["count()", "sum(total)"]`), `groupBy` eine Liste von Feldern, und es antwortet mit `{ data }` mit einer Zeile pro Gruppe, plus `meta.hasMore` bei einem gruppierten Aufruf, dessen Gruppen mit `limit` und `offset` paginiert und mit `orderBy` sortiert werden können. Bei einer Tabelle, die durch einen `afterRead`-Hook umgeschrieben wird, liefert es nur `count()`, wie es auch REST tut. Wie bei REST werden ein `limit` über 1000, ein nicht deklariertes Argument sowie das Bearbeiten oder Löschen einer im Papierkorb befindlichen Zeile (404) abgelehnt; das Setzen des Soft-Delete-Feldes auf `null` stellt sie wieder her. `deleted: "only"` (oder `"include"`) bei `query_table`, `count_rows` und `aggregate_rows` liest den Papierkorb, genau wie RESTs `?deleted=`, sodass eine durch `delete_row` in den Papierkorb verschobene Zeile wiedergefunden und wiederhergestellt werden kann. Seine Beschreibung teilt dem Modell mit, dass das Löschen nur dann dauerhaft ist, wenn die Tabelle kein Soft-Delete-Feld besitzt.
- **Die Auflistung nennt die Tabellen; `describe_table` liefert das Schema einer Tabelle.** `list_tables` antwortet mit `{ tables: [{ name, description, kind? }] }` – ohne Label – und `describe_table { table }` mit den OpenAPI-Schemas `row` (die Spalten, die diesem Aufrufer bereitgestellt werden) und `create` (die beschreibbaren Spalten) dieser Tabelle, ihrem `primaryKey`, bereitgestellten `relations` und `rls` (rohes SQL ohne `schema:read` unkenntlich gemacht), plus `softDeleteField`, falls Zeilen in einen Papierkorb verschoben werden, sowie der Darstellung gemäß den UI-Präferenzen des Aufrufers: `title` und pro Spalte `label`, `valueLabels`, `hidden`, `hiddenInForm`, `readOnly`. Was eine Verbindung über das Schema erfahren darf, wird durch denselben Serializer bestimmt, den auch `GET /api/schema/tables` verwendet. Die Tool-Beschreibungen weisen das Modell an, eine Tabelle vor dem Schreiben zu beschreiben. Die Auflistung eines Projekts mit 200 Tabellen umfasst etwa 5.000 Tokens, und jede Beschreibung liegt unter 1.000 Tokens; mit allen Schemas in der Auflistung waren es etwa 150.000 Tokens.
- **Ein Token ausschließlich für diesen Endpunkt.** Ein MCP-Access-Token wird von `/api/data`, `/api/admin` und dem WebSocket abgelehnt, sodass die Verbindung eines Assistenten diesem keine allgemeine Sitzung übergibt.

Jede Anfrage an `/mcp` liest das Konto der Person erneut aus. Ein gelöschtes oder deaktiviertes Konto, eine Aktion wie "Überall abmelden" oder eine Passwortänderung nach Ausstellung des Tokens stoppt einen verbundenen Client sofort mit einem 401-Fehler. Ein Entzug von Rechten greift beim nächsten Tool-Aufruf. Jeder Refresh führt dieselben Prüfungen durch und verweigert eine solche Autorisierung dauerhaft. Eine Gastsitzung kann überhaupt keine Zustimmung erteilen.

Eine Einschränkung: Das Trennen eines Clients (`DELETE /api/oauth/grants/:clientId` mit der eigenen Sitzung der Person) widerruft dessen Refresh-Tokens sofort, ein bereits ausgestelltes Access-Token funktioniert jedoch weiter, bis es abläuft (innerhalb einer Stunde).

## Skills

Der Endpunkt kann auch [Agent Skills](https://agentskills.io/specification) über MCP bereitstellen: Anweisungen, die ein Assistent lädt, wenn die Aufgabe dies erfordert, wie etwa die Art und Weise, wie Ihr Team eine Bestellung aufgibt oder was ein bestimmtes Feld bedeutet. Legen Sie jeden Skill in einem eigenen Ordner ab, mit einer `SKILL.md`, deren Frontmatter ein `name` (passend zum Ordner) und eine `description` enthält, zusammen mit allen Dateien, auf die sie verweist. Geben Sie dann den übergeordneten Ordner in der Backend-Konfiguration an:

```ts
// skills/order-intake/SKILL.md, skills/order-intake/references/fields.md, …
createRebaseBackend({
    ...options, // the rest of your backend config
    mcp: { skills: "./skills" }
});
```

Der Pfad ist relativ zum Arbeitsverzeichnis. Die Daten-Tools bleiben unverändert, und `skills` steht neben `tools`, wenn ein Backend eigene mitbringt.

- **Was ein Client sieht.** Clients mit Protokollrevision 2026-07-28 oder neuer (Claude Code, Claude) listen die Skills auf und laden einen Skill, wenn er relevant ist. Claude Code benennt jeden einzelnen als `<connector>:<skill>`. Diese werden über die MCP-Skills-Erweiterung (`io.modelcontextprotocol/skills`) bereitgestellt: `skills/list`, `skills/get` und `resources/read` von `skill://<name>/…`. Jeder Skill wird mit einem SHA-256-Manifest seiner Dateien ausgeliefert. Der Client gleicht jede Datei mit diesem Manifest ab, und die Genehmigung der Person ist daran gebunden.
- **Wer sie lesen kann.** Jede authentifizierte Verbindung, unabhängig von ihren Scopes. Platzieren Sie nichts in einem Skill, das nicht für jeden bestimmt ist, der eine Verbindung herstellt.
- **Wann sie sich ändern.** Der Ordner wird bei der ersten Anfrage gelesen, die ihn benötigt, sodass eine Bearbeitung beim nächsten Deployment oder Neustart wirksam wird. Eine Datei, die sich vorher auf der Festplatte ändert, wird abgelehnt und nicht anhand eines Manifests ausgeliefert, zu dem sie nicht mehr passt.
- **Was ausgelassen wird.** Ein Skill, der gegen eine Regel verstößt, wird übersprungen, und das Boot-Log nennt den Grund. Die Regeln: kein Frontmatter, ein Name, der sich von dem seines Ordners unterscheidet, ein Symlink im Ordner oder mehr als 512 Dateien bzw. 16 MiB. Versteckte Dateien wie `.gitkeep` werden niemals ausgeliefert. Ein Skill, der die Limits von Claude Code überschreitet (100 KB pro Datei, insgesamt 400 KB), wird mit einer Warnung ausgeliefert, da Claude Code ihn nicht laden wird.

Der Endpunkt unterstützt beide Protokoll-Ären. Ein Client der 2025er-Ära beginnt wie bisher mit `initialize`. Ein Client nach 2026-07-28 sendet keinen Handshake. Jede Anfrage überträgt ihre Protokollversion und Fähigkeiten in `params._meta`, zusätzlich zu den Headern `MCP-Protocol-Version`, `Mcp-Method` und `Mcp-Name`, die mit dem Body übereinstimmen müssen. Seine Fähigkeiten stammen aus `server/discover`. Skills werden ausschließlich dort deklariert.

Die Routen finden Sie unter [Endpunkte](/docs/backend/endpoints/#mcp-surface) und die Variablen unter [Konfiguration](/docs/getting-started/configuration/#mcp-surface).
