Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. C'est sur ce code qu'il convient d'effectuer vos branchements conditionnels : le message est rédigé pour un humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, alors que le code ne présente aucun de ces deux inconvénients.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par un humain. Pour un code `4xx`, il s'agit du propre message du serveur ; pour un `5xx`, il est délibérément générique, car le texte sous-jacent peut citer un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable d'une version mineure à l'autre.
- **`details`** — optionnel, et jamais garanti. Voir les règles ci-dessous.
- **`requestId`** — présent dès lors que la requête a traversé le middleware de request-ID, ce qui est le cas de chaque route sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un identifiant : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, ou un nouvel identifiant dans le cas contraire. Il est renvoyé dans la réponse sous la forme `X-Request-ID`, inclus dans l'enveloppe d'erreur en tant que `requestId`, et associé à la ligne de journal (log) du serveur pour cette requête.

C'est la clé de jointure. Citez-le dans un rapport de bug et un opérateur pourra retrouver l'unique ligne de log expliquant l'échec, contenant la raison qui n'a jamais été montrée au client.

Envoyer le vôtre permet à une trace de survivre à un saut : une passerelle ou un exécuteur de tâches qui transmet l'en-tête conserve un ID unique à travers tous les services ayant traité la requête. Une valeur invalide est ignorée plutôt que rejetée — un en-tête malformé provenant d'un appelant ne mérite pas de faire échouer une requête — ne partez donc pas du principe que l'ID que vous avez envoyé est celui que vous avez reçu. Lisez l'en-tête de réponse.

### Contenu de `details`

`details` est diagnostique, non contractuel. Trois règles le régissent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des erreurs propres à l'appelant décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas accessible en écriture, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont tronqués en production.** Lorsque l'échec provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il nomme la classe de problème et ne révèle rien sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y inclut le contenu des lignes. `23505` rapporte `Key (email)=(a@b.c) already exists.`, ce qui répond à la question « cette personne est-elle inscrite ? » pour toute adresse que quiconque souhaiterait tester.
3. **Ne basez jamais vos branchements sur `details`.** Basez-les sur `code`. Ce qui se trouve sous `details` correspond à ce qui était utile à un humain à cet endroit précis de l'appel, et cela est sujet à changement.

## Comprendre un statut

| Statut | Ce qu'il indique sur la requête |
| --- | --- |
| `400` | Malformée, ou demandant quelque chose qui n'existe pas dans le schéma. Corrigez la requête. |
| `401` | Non authentifié, ou identifiant expiré. Connectez-vous ou actualisez le jeton. |
| `403` | Authentifié, mais non autorisé. Réessayer avec la même identité n'aidera pas. |
| `404` | Route, table ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Conflit avec l'état existant : un doublon, ou une écriture concurrente. |
| `413` `415` `422` | Corps trop volumineux, mauvais type de média, ou rejet sémantique. |
| `429` | Limite de débit atteinte (rate limited). Temporisez ; le message indique pendant combien de temps. |
| `500` | Le serveur ou sa base de données est en faute, pas l'appelant. Vérifiez les logs. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — fonctionnalité désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était injoignable, non configurée ou trop lente. |

| `DEVICE_LOGIN_DECIDED` | 409 | La connexion de l'appareil a déjà été approuvée ou refusée. Une connexion ne peut être tranchée qu'une seule fois. | Démarrez-en une nouvelle sur l'appareil. |

| `EMAIL_EXISTS` | 409 | Un compte avec cette adresse existe déjà — lors de l'inscription, d'un changement d'adresse, ou en suivant un lien de changement d'adresse lorsqu'un autre compte a récupéré l'adresse pendant l'attente. | Connectez-vous, ou démarrez une réinitialisation de mot de passe ; pour un changement d'adresse, choisissez une autre adresse. |
| `EMAIL_NOT_CONFIGURED` | 503 | Des liens magiques ou des OTP ont été demandés et le serveur ne dispose d'aucun transport d'e-mails. | Configurez SMTP, ou utilisez une autre méthode de connexion. |

| `IDENTITY_ALREADY_LINKED` | 409 | Cette identité OAuth appartient à un autre compte. | Connectez-vous avec cette dernière, ou dissociez-la d'abord sur l'autre compte. |

| `IMPERSONATION_UNSUPPORTED` | 400 | `x-rebase-impersonate` a été envoyé à une route ne pouvant pas s'exécuter sous une autre identité. | `SIMULATION_FORBIDDEN` | 403 | Une requête a envoyé un en-tête `x-rebase-simulate-*` (simulateur RLS), ou interrogé `/api/admin/rls-simulator`, et son appelant n'est pas autorisé à simuler des accès. Seule la session propre d'un administrateur connecté le peut, jamais une clé API ou la clé de service. | Envoyez-la avec la session d'un administrateur, ou omettez les en-têtes. |
| `SIMULATION_INVALID` | 400 | La simulation était malformée : un en-tête envoyé vide, `x-rebase-simulate-api-key-id` combiné avec un rôle ou un ID utilisateur, ou une simulation combinée avec `x-rebase-impersonate`. | Spécifiez un seul rôle (avec éventuellement un UID), un seul ID utilisateur, ou un seul ID de clé API. |
| `SIMULATION_READ_ONLY` | 403 | Une écriture, suppression, `_batch`, annulation d'historique, ou une fonction personnalisée appelée avec un verbe autre que `GET`/`HEAD`/`OPTIONS`, comportait un en-tête `x-rebase-simulate-*`. | `SIMULATION_TARGET_NOT_FOUND` | 404 | La simulation ne désigne aucun utilisateur actif (un ID utilisateur envoyé sans rôle) ou aucune clé API active. | Vérifiez l'ID, ou envoyez un rôle avec l'UID pour simuler un UID n'ayant pas de compte. |
| `SIMULATION_UNAVAILABLE` | 501 | Ce backend ne peut pas simuler d'accès : son `AuthAdapter` n'a pas de méthode `resolveUser` pour confirmer un administrateur, ou une clé a été mentionnée sur un backend sans clés API. | Implémentez `resolveUser`, ou omettez les en-têtes. |

| `GUEST_REFERENCED` | 409 | Un invité n'a pas pu être supprimé car une ligne propre au projet l'exige, via une clé étrangère avec `ON DELETE RESTRICT` ou `NO ACTION`. `DELETE /api/admin/guests` le signale par invité dans `skipped` et poursuit l'exécution. | Supprimez la ligne, ou conservez l'invité. |
| `INVALID_ACCOUNT` | 400 | Le compte se trouve dans un état qui ne permet pas cette opération. | Consultez le message. |

## `PG_<SQLSTATE>` — une contrainte rejetée par la base de données

Une écriture que Postgres rejette pour une raison liée aux *données de l'appelant* répond avec le SQLSTATE dans le code : `PG_23505`, `PG_23503`, etc. Il s'agit d'une famille et non d'une liste finie — Postgres définit des centaines de SQLSTATE — mais seules deux classes l'atteignent, car seules ces deux-là relèvent de la responsabilité de l'appelant :

- **classe 23**, violation de contrainte d'intégrité : un doublon, une clé étrangère pointant dans le vide, une colonne NOT NULL laissée vide ;
- **classe 22**, exception de données : une valeur incompatible avec le type de la colonne.

Tout le reste — connexion interrompue, colonne manquante, problème de privilèges — relève du serveur et produit une erreur `500`. Le test `code.startsWith("PG_")` est donc un moyen sûr de vérifier que « la ligne envoyée était incorrecte », et les quatre codes ci-dessous sont ceux qu'un client rencontre concrètement. `details.dbCode` contient le même SQLSTATE pour chacun d'eux, et le message nomme la contrainte.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Une valeur n'a pas pu être convertie dans le type de la colonne — pendant d'écriture de `INVALID_FILTER_VALUE`. | Envoyez une valeur correspondant au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` a été laissée vide. | Fournissez le champ, ou attribuez une valeur par défaut à la colonne. |
| `PG_23503` | 400 / 409 | Lors d'un enregistrement, une clé étrangère pointe vers une ligne inexistante (400). Lors d'une suppression, d'autres lignes référencent encore celle-ci (409 ; une clé `RESTRICT` lève `PG_23001`, également une 409). | Créez d'abord la ligne cible, ou corrigez l'identifiant ; pour une suppression, retirez ou réorientez d'abord les lignes qui la référencent. |
| `PG_23505` | 409 | Violation d'une contrainte d'unicité. Le message indique la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

### Pourquoi la table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` liste chaque table refusée dans `details.tables`, avec l'un de ces codes. Le même code apparaît sur la propriété `blocked` de la table dans le diff lui-même, permettant à Studio de l'indiquer avant que quiconque ne clique sur **Merge**. Aucun de ces codes ne constitue une réponse HTTP autonome.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table diffèrent entre la branche et son parent. Les lignes sont comparées sur la base des colonnes communes. | Ajoutez les colonnes manquantes au parent via vos migrations (`rebase db push`), puis fusionnez. Une migration qui réécrit la table — changement de type de colonne — la transforme en `TABLE_REWRITTEN` : fusionnez avant un tel changement, ou recréez la branche après coup. |
| `NO_PRIMARY_KEY` | — | La table n'a pas de clé primaire, empêchant d'apparier les lignes une à une ; le diff ne fournit que le nombre de lignes. | Attribuez une clé primaire à la table, ou déplacez ses lignes manuellement. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes de la clé primaire, ou leurs types, diffèrent entre les deux. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La table a été créée par la branche. Une fusion ne crée jamais de table. | Créez-la sur le parent à l'aide de vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La table a été supprimée par la branche. Une fusion ne supprime jamais de table. | Supprimez-la à l'aide de vos migrations. |
| `TABLE_REWRITTEN` | — | L'un des côtés a réécrit intégralement chaque ligne de la table après la création de la branche — changement de type de colonne, `ADD COLUMN` avec valeur par défaut volatile, `VACUUM FULL`, `CLUSTER` — de sorte que chaque ligne apparaît comme modifiée depuis lors, rendant impossible d'identifier qui a modifié quelle ligne. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après celle-ci. |
| `TOO_LARGE` | — | La table contient plus de lignes d'un côté que ce qu'un diff peut apparier une par une (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` sur le diff et la fusion, ou déplacez les lignes par un autre moyen. |

## Garantir l'exactitude de cette page

La commande `pnpm verify:docs` échoue si un code pouvant être émis par le serveur est absent de ces tableaux, si un tableau liste un code qui ne peut jamais être émis, si les statuts d'une ligne ne correspondent pas exactement à ceux avec lesquels la source émet le code, ou si une famille de codes telle que `PG_<SQLSTATE>` ne comporte pas de ligne pour un SQLSTATE que les appelants peuvent rencontrer. Cette étape est assurée par `tooling/scripts/docs-verify/check-error-codes.mjs`.

Elle s'auto-contrôle au préalable. L'analyse extrait les codes directement du code TypeScript plutôt que d'un serveur en cours d'exécution, de sorte que ses angles morts sont silencieux par conception : il lui est arrivé de ne pas détecter un code transmis via un wrapper d'une ligne, ou un code placé après un message contenant une parenthèse `)`, affirmant alors que « tous les codes pouvant être émis par le serveur sont documentés » sur une page à laquelle il en manquait dix-sept. Par conséquent, cette vérification exécute d'abord un jeu de test reproduisant fidèlement ces cas de figure avant de lire la présente page, et refuse de rendre son rapport si elle ne parvient pas à les détecter.
