Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. C'est sur ce code qu'il faut effectuer vos branchements logiques : le message est rédigé pour un être humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, tandis que le code n'est sujet à aucun de ces deux travers.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par un être humain. Pour un statut `4xx`, il s'agit du propre message du serveur ; pour un `5xx`, il est délibérément générique, car le texte sous-jacent peut citer un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable à travers les versions mineures.
- **`details`** — optionnel, et jamais garanti. Consultez les règles ci-dessous.
- **`requestId`** — présent dès lors que la requête a traversé le middleware de request-ID, c'est-à-dire pour chaque route sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un identifiant : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, ou un nouvel identifiant dans le cas contraire. Il est renvoyé en écho dans la réponse sous la forme de l'en-tête `X-Request-ID`, inclus dans l'enveloppe d'erreur sous le nom `requestId`, et attaché à la ligne de log du serveur correspondant à cette requête.

Il s'agit de la clé de jointure. Mentionnez-la dans un rapport de bogue et un opérateur pourra retrouver l'unique ligne de log expliquant la défaillance, indiquant la raison qui n'a jamais été montrée au client.

Envoyer votre propre identifiant est le moyen de préserver une trace à travers les sauts de réseau : une passerelle ou un exécuteur de tâches qui transmet l'en-tête conserve un ID unique à travers chaque service ayant traité la requête. Une valeur invalide est ignorée plutôt que rejetée — un en-tête malformé provenant d'un appelant ne mérite pas de faire échouer une requête — ne présumez donc pas que l'ID envoyé est celui que vous avez reçu. Lisez l'en-tête de réponse.

### Ce que contient `details`

`details` a une vocation diagnostique et non contractuelle. Trois règles l'encadrent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des erreurs propres à l'appelant décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas modifiable, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont épurés en production.** Lorsque la défaillance provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il désigne la catégorie de problème et ne divulgue rien sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y insère le contenu des lignes. `23505` rapporte `Key (email)=(a@b.c) already exists.`, ce qui répond à la question « cette personne est-elle inscrite ? » pour toute adresse qu'un tiers souhaiterait tester.
3. **N'effectuez jamais de branchements logiques sur `details`.** Basez-vous sur `code`. Le contenu de `details` correspond à ce qui était utile à un humain à cet endroit du code, et il est sujet à changement.

## Interpréter un statut

| Statut | Ce qu'il indique sur la requête |
| --- | --- |
| `400` | Malformée, ou demandant un élément qui n'existe pas dans le schéma. Corrigez la requête. |
| `401` | Non authentifié, ou identifiant expiré. Connectez-vous ou actualisez le jeton. |
| `403` | Authentifié, mais non autorisé. Réessayer avec la même identité ne changera rien. |
| `404` | Route, table ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Conflit avec l'état existant : un doublon, ou une écriture concurrente. |
| `413` `415` `422` | Corps trop volumineux, mauvais type de média, ou rejet sémantique. |
| `429` | Limite de débit atteinte (Rate limited). Patientez ; le message indique pendant combien de temps. |
| `500` | Le problème vient du serveur ou de sa base de données, pas de l'appelant. Consultez les logs. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — une fonctionnalité désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était inaccessible, non configurée ou trop lente. |

## `PG_<SQLSTATE>` — une contrainte refusée par la base de données

Une écriture rejetée par Postgres pour une cause liée aux *données de l'appelant* répond avec le SQLSTATE dans le code d'erreur : `PG_23505`, `PG_23503`, etc. Il s'agit d'une famille d'erreurs et non d'une liste figée — Postgres définissant des centaines de SQLSTATE — mais seules deux classes peuvent parvenir jusqu'ici, car seules ces deux-là relèvent de la responsabilité de l'appelant :

- **classe 23**, violation de contrainte d'intégrité : un doublon, une clé étrangère pointant vers le vide, une colonne NOT NULL laissée vide ;
- **classe 22**, exception de données : une valeur que le type de colonne ne peut pas contenir.

Toutes les autres causes — perte de connexion, colonne inexistante, problème de droits — incombent au serveur et conservent un statut `500`. Dès lors, tester `code.startsWith("PG_")` constitue un moyen fiable de déterminer si « la ligne transmise était invalide », et les quatre erreurs ci-dessous sont celles qu'un client rencontre en pratique. `details.dbCode` contient le même SQLSTATE pour chacune d'elles, et le message précise la contrainte en cause.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Une valeur n'a pas pu être convertie dans le type de la colonne — pendant de `INVALID_FILTER_VALUE` côté écriture. | Transmettez une valeur correspondant au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` est restée vide. | Fournissez le champ, ou affectez une valeur par défaut à la colonne. |
| `PG_23503` | 400 / 409 | Lors d'un enregistrement, une clé étrangère référence une ligne inexistante (400). Lors d'une suppression, d'autres lignes référencent encore celle-ci (409 ; une clé `RESTRICT` déclenche `PG_23001`, également une 409). | Créez d'abord la ligne cible, ou corrigez l'id ; pour une suppression, supprimez ou réassignez au préalable les lignes qui la référencent. |
| `PG_23505` | 409 | Une contrainte d'unicité a été violée. Le message précise la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

### Réconciliation de schéma

<span class="since-badge" data-since="0.31">Depuis 0.31</span>

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) planifie les actions via `POST /api/admin/schema/reconcile/plan` et les applique via `/reconcile/apply`. Un refus ne modifie rien ; seul `SCHEMA_RECONCILE_FAILED` peut laisser une portion de plan appliquée.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | Le corps n'est pas un objet JSON, ou `drop` n'est pas une liste de chaînes `"<table>.<column>"`. | Envoyez `{ "drop": ["voice_cache.wav"] }`, ou omettez `drop`. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Une instruction a échoué en cours d'exécution. ### Pourquoi la table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` liste chaque table refusée dans `details.tables`, accompagnée de l'un de ces codes. Ce même code figure sur l'attribut `blocked` de la table dans le diff lui-même, permettant au Studio d'en avertir l'utilisateur avant qu'il ne clique sur **Merge**. Aucun de ces éléments ne constitue une réponse HTTP autonome.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table diffèrent entre la branche et son parent. Les lignes sont comparées sur la base de leurs colonnes communes. | Ajoutez les colonnes manquantes sur le parent avec vos migrations (`rebase db push`), puis fusionnez. Une migration réécrivant la table — un changement de type de colonne — transforme ce statut en `TABLE_REWRITTEN` : fusionnez avant un tel changement, ou recréez la branche après coup. |
| `NO_PRIMARY_KEY` | — | La table ne possède pas de clé primaire, empêchant la comparaison des lignes une par une ; le diff n'affiche que ses totaux de lignes. | Attribuez une clé primaire à la table, ou déplacez ses lignes à la main. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes de la clé primaire, ou leurs types, diffèrent entre les deux. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La table a été créée sur la branche. Une fusion ne crée jamais de table. | Créez-la sur le parent via vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La table a été supprimée sur la branche. Une fusion ne supprime jamais de table. | Supprimez-la via vos migrations. |
| `TABLE_REWRITTEN` | — | L'une des deux parties a réécrit intégralement les lignes de la table après la création de la branche — changement de type de colonne, `ADD COLUMN` avec valeur par défaut volatile, `VACUUM FULL`, `CLUSTER` — de sorte que chaque ligne apparaît comme réécrite depuis, rendant impossible l'attribution des modifications. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après celle-ci. |
| `TOO_LARGE` | — | La table contient sur un côté plus de lignes que le seuil de comparaison ligne à ligne d'un diff (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` à la fois pour le diff et la fusion, ou transférez les lignes par un autre moyen. |

## Maintien de l'exactitude de cette page

La commande `pnpm verify:docs` échoue lorsqu'un code susceptible d'être émis par le serveur est absent de ces tableaux, lorsqu'un tableau répertorie un code qu'aucun composant ne peut émettre, lorsque les statuts d'une ligne ne correspondent pas exactement à ceux avec lesquels le code source émet le code, ou lorsqu'une famille de codes comme `PG_<SQLSTATE>` ne comporte aucune ligne pour un SQLSTATE que les appelants peuvent rencontrer. Ce test est géré par `tooling/scripts/docs-verify/check-error-codes.mjs`.

Ce script se vérifie lui-même en priorité. L'analyse extrait les codes du code TypeScript plutôt que d'un serveur en cours d'exécution, ses angles morts sont donc silencieux par nature : il lui est arrivé de ne pas détecter un code encapsulé dans un wrapper d'une ligne, ou placé après un message contenant une parenthèse `)`, tout en affirmant que « chaque code susceptible d'être émis par le serveur est documenté » sur une page où il en manquait dix-sept. Par conséquent, l'étape de vérification exécute d'abord un jeu de test reproduisant précisément ces motifs avant de lire cette page, et refuse de rendre le moindre rapport si elle ne parvient pas à les détecter.
