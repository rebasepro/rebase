Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. Le code est l'élément sur lequel baser vos conditions : le message est rédigé pour un humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, et le code n'est ni l'un ni l'autre.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par un humain. Pour une erreur `4xx`, il s'agit du propre message du serveur ; pour une `5xx`, il est délibérément générique, car le texte sous-jacent peut mentionner un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable d'une version mineure à l'autre.
- **`details`** — optionnel et jamais garanti. Voir les règles ci-dessous.
- **`requestId`** — présent chaque fois que la requête est passée par le middleware de request-ID, c'est-à-dire toutes les routes sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un identifiant : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, sinon un nouvel identifiant généré. Il est renvoyé dans la réponse sous le nom `X-Request-ID`, inclus dans l'enveloppe d'erreur sous `requestId`, et rattaché à la ligne de log du serveur correspondant à cette requête.

C'est la clé de jointure. Mentionnez-la dans un rapport de bogue et un opérateur pourra trouver la ligne de log exacte qui explique l'échec, contenant la raison qui n'a jamais été montrée au client.

Envoyer le vôtre permet à une trace de survivre à un saut (hop) : une passerelle ou un exécuteur de tâches qui transfère l'en-tête conserve un ID unique à travers tous les services ayant traité la requête. Une valeur invalide est ignorée plutôt que rejetée — un en-tête malformé provenant d'un appelant ne mérite pas de faire échouer une requête — ne supposez donc pas que l'ID envoyé correspond à l'ID reçu. Lisez l'en-tête de la réponse.

### Que contient `details`

`details` est diagnostique, non contractuel. Trois règles le régissent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des erreurs propres à l'appelant décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas accessible en écriture, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont tronqués en production.** Lorsque l'échec provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il désigne la classe du problème et ne révèle rien sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y inclut le contenu des lignes. `23505` indique `Key (email)=(a@b.c) already exists.`, ce qui répond à « cette personne est-elle enregistrée ? » pour n'importe quelle adresse testée.
3. **Ne basez jamais vos conditions sur `details`.** Basez-les sur `code`. Le contenu de `details` correspond à ce qui était utile à un humain à cet endroit du code, et cela change.

## Interpréter un statut

| Statut | Ce qu'il indique sur la requête |
| --- | --- |
| `400` | Malformée, ou demandant quelque chose qui n'existe pas dans le schéma. Corrigez la requête. |
| `401` | Non authentifié, ou identifiant expiré. Connectez-vous ou actualisez la session. |
| `403` | Authentifié, mais non autorisé. Réessayer avec la même identité ne servira à rien. |
| `404` | Route, collection ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Conflit avec l'état existant : doublon ou écriture concurrente. |
| `413` `415` `422` | Le corps est trop volumineux, le type de média est incorrect ou la requête est rejetée sémantiquement. |
| `429` | Limite de débit atteinte (rate limit). Ralentissez ; le message indique pendant combien de temps. |
| `500` | Le serveur ou sa base de données est en faute, pas l'appelant. Consultez les logs. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — fonctionnalité désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était inaccessible, non configurée ou trop lente. |

## `PG_<SQLSTATE>` — une contrainte refusée par la base de données

Une écriture que Postgres rejette pour une raison liée aux *données de l'appelant* répond avec le SQLSTATE dans le code : `PG_23505`, `PG_23503`, etc. Il s'agit d'une famille et non d'une liste exhaustive — Postgres définissant des centaines de SQLSTATE — mais seules deux classes y parviennent, car seules ces deux sont imputables à l'appelant :

- **classe 23**, violation de contrainte d'intégrité : doublon, clé étrangère pointant vers le vide, colonne NOT NULL laissée vide ;
- **classe 22**, exception de données : valeur que le type de colonne ne peut pas contenir.

Tout le reste — connexion interrompue, colonne manquante, problème de privilèges — relève du serveur et reste une `500`. Le test `code.startsWith("PG_")` est donc un moyen sûr de vérifier que « la ligne envoyée était incorrecte », et les quatre ci-dessous sont celles qu'un client rencontre concrètement. `details.dbCode` renvoie le même SQLSTATE pour chacune d'elles, et le message mentionne la contrainte en cause.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Une valeur n'a pas pu être lue dans le type de la colonne — le pendant côté écriture de `INVALID_FILTER_VALUE`. | Envoyez une valeur correspondant au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` a été laissée vide. | Envoyez le champ ou définissez une valeur par défaut pour la colonne. |
| `PG_23503` | 400 / 409 | Lors d'un enregistrement, une clé étrangère pointe vers une ligne inexistante (400). Lors d'une suppression, d'autres lignes référencent toujours celle-ci (409 ; une clé `RESTRICT` lève `PG_23001`, également une 409). | Créez d'abord la ligne cible, ou corrigez l'identifiant ; pour une suppression, retirez ou réorientez d'abord les lignes qui la référencent. |
| `PG_23505` | 409 | Une contrainte d'unicité a été enfreinte. Le message précise la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

Ces erreurs indiquent qu'une fonctionnalité est désactivée ou non configurée, plutôt que la requête était incorrecte. Une table dont les lignes n'ont pas pu être comparées bloque même si ses compteurs affichent 0 : ils sont inconnus, pas à zéro. `details.tables` liste chacune d'elles avec la raison. Rien n'a été écrit. | Appliquez d'abord le schéma avec vos migrations, ou fusionnez avec `skipBlocked: true` pour laisser ces tables intactes. |
| `BRANCH_MERGE_CONFLICT` | 409 | Des lignes ont été modifiées à la fois sur la branche et sur son parent, et `onConflict` valait `"abort"` (par défaut) ; ou le parent a refusé une partie de la fusion — ligne modifiée entre-temps, déclencheur l'ayant ignorée, politique l'ayant masquée. Rien n'a été écrit. | Choisissez le côté prioritaire avec `onConflict: "branch"` ou `"target"`, ou relisez le diff. |
| `BRANCH_MERGE_FAILED` | 409 | Le parent a refusé les lignes de la branche au sein de l'instruction de fusion — une contrainte, un libellé d'énumération ou une clé étrangère qu'il applique et que les lignes de la branche enfreignent, généralement parce que les deux schémas diffèrent. `details` contient `sqlState`, `table`, `constraint` et `detail`. Rien n'a été écrit. | Consultez les modifications de schéma du diff, alignez le schéma parent avec vos migrations, ou corrigez les lignes de la branche, puis relancez la fusion. |
| `BRANCH_NOT_FOUND` | 404 | Aucune branche ne porte ce nom dans le registre. | `rebase db branch list`, ou le volet Branches, liste celles qui existent. |
| `CONTRACT_UNAVAILABLE` | 404 | Le contrat du projet n'est servi que lorsque l'authentification est configurée — il décrit l'intégralité des tables et relations. | Configurez l'authentification. `/meta/schema-version` est toujours servi. |
| `DEV_MAILBOX_UNAVAILABLE` | 501 | Aucune boîte aux lettres de développement n'est active. Les e-mails ne sont capturés que lorsque `SMTP_HOST` n'est pas défini et que `NODE_ENV` n'est pas en production. | Supprimez `SMTP_HOST` en développement, ou consultez la vraie boîte de réception. |
| `INVALID_CHANGE` | 400 | La modification de schéma proposée n'est pas bien formée. | Consultez le message. |
| `SCHEMA_CHANGE_FAILED` | 400 | L'application d'une modification de schéma planifiée a échoué pour une raison non couverte par des codes plus précis. | Consultez le message ; il reprend mot pour mot l'échec sous-jacent. |
| `SCHEMA_CHANGE_UNAPPLICABLE` | 400 | La modification est valide mais ne peut pas être appliquée au schéma dans son état actuel. | Consultez le message. |
| `SCHEMA_EDIT_DIRTY_TREE` | 409 | Le dépôt contient des modifications non validées, la modification n'a donc pas pu être appliquée en toute sécurité. | Effectuez un commit ou un stash, puis réessayez. |
| `SCHEMA_EDIT_REFUSED` | 400 | L'éditeur de schéma a refusé la modification. | Consultez le message ; il s'agit du propre refus de l'éditeur. |
| `SCHEMA_EDIT_REQUIRES_A_PERSON` | 403 | Une clé d'API ou une autre entité machine a tenté d'appliquer une modification de schéma. | Connectez-vous en tant qu'utilisateur, ou définissez `liveSchema.allowMachineApply`. |
| `SCHEMA_EDITING_NO_COLLECTIONS_DIR` | 501 | La modification de schéma à chaud nécessite `collectionsDir` ou `liveSchema.repository`, et ce serveur a démarré sans aucun des deux. | Configurez l'un d'eux. |
| `SCHEMA_EDITING_NO_REPOSITORY` | 503 | La planification fonctionne ; aucun dépôt n'est disponible pour y enregistrer la modification. | Configurez `liveSchema.repository`. |
| `SCHEMA_EDITING_PROVISIONING_OFF` | 409 | Ce déploiement ne modifie rien dans sa base de données (`REBASE_PROVISION=false`), une modification ne peut donc pas être appliquée depuis le panneau. | Validez-la uniquement dans le code source et laissez le processus qui modifie la base de données l'appliquer. |
| `SCHEMA_EDITING_UNSUPPORTED` | 503 | Ce pilote ne peut pas planifier de modifications de schéma. | L'édition en direct est disponible sur Postgres. |
| `SCHEMA_EDITOR_BAAS_MODE` | 501 | Les collections sont ici introspectées depuis la base de données, il n'y a donc aucun fichier source à modifier. | Modifiez le schéma à l'aide d'une migration. |
| `SCHEMA_EDITOR_DISABLED` | 501 | L'éditeur de schéma est désactivé sur ce serveur. Un bundle compilé répond toujours cela. | Activez-le avec `schemaEditor`. Sur un bundle, définissez `REBASE_LIVE_SCHEMA_REPOSITORY` pour modifier les collections via un dépôt — voir [Édition de schéma en direct](/docs/backend/live-schema-editing#from-a-built-bundle). |
| `SCHEMA_EDITOR_MISSING_DEPENDENCY` | 501 | L'éditeur de schéma nécessite `ts-morph`, qui n'est pas installé. | Installez-le dans le package exécutant le backend, puis redémarrez-le : `pnpm --dir backend add -D ts-morph@28.0.0` depuis la racine d'un projet échafaudé, ou `pnpm add -D ts-morph@28.0.0` si le backend constitue le projet lui-même. Le message indique la commande adaptée à votre projet. |
| `SCHEMA_EDITOR_NO_COLLECTIONS_DIR` | 501 | Le serveur n'a pas de `collectionsDir`, l'éditeur n'a donc aucun endroit où écrire. | Définissez `collectionsDir`. |
| `SCHEMA_EDITOR_PRODUCTION` | 501 | L'éditeur est désactivé avec `NODE_ENV=production` : les fichiers d'un serveur déployé sont reconstruits depuis votre dépôt à chaque déploiement, toute modification apportée ici serait donc perdue. | Modifiez les collections en développement et déployez-les, ou configurez `liveSchema.repository` pour les y enregistrer. |
| `SQL_EXPORT_UNSUPPORTED` | 501 | `POST /api/admin/sql/csv` ne peut pas diffuser de résultat ici : la base de données de développement intégrée (PGlite) ne dispose que d'une seule connexion, et un curseur maintenu pendant un téléchargement bloquerait toutes les autres requêtes derrière lui ; ou la source de données n'a pas de curseur SQL. | Pointez `DATABASE_URL` vers votre propre instance Postgres (`rebase dev --docker` en lance une), ou ajoutez un `LIMIT` et exportez les lignes affichées à l'écran. |

### Réconciliation de schéma

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) planifie
via `POST /api/admin/schema/reconcile/plan` et applique via
`/reconcile/apply`. Un refus ne change rien ; seul `SCHEMA_RECONCILE_FAILED`
laisse une partie du plan appliquée.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | Le corps n'est pas un objet JSON, ou `drop` n'est pas une liste de chaînes `"<collection>.<column>"`. | Envoyez `{ "drop": ["voice_cache.wav"] }`, ou omettez `drop`. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Une instruction a échoué en cours d'exécution. Les instructions précédentes ont été exécutées et restent appliquées ; `details.applied` les énumère. | Corrigez ce que le message indique, puis replanifiez : le nouveau plan exclut ce qui a déjà été exécuté. |
| `SCHEMA_RECONCILE_INVALID` | 400 | Le plan ne peut pas être appliqué, et le message en détaille les raisons : un `drop` qui n'est pas sous la forme `<collection>.<column>`, ne nomme aucune collection ou colonne, ou nomme une colonne toujours déclarée par la collection. `details.plan` correspond au plan. | Corrigez la liste `drop`. Une colonne déclarée est supprimée en retirant sa propriété, en déployant, puis en procédant à la réconciliation. |
| `SCHEMA_RECONCILE_STALE` | 409 | La base de données ou les collections ont changé depuis le plan que vous avez confirmé. `details.plan` correspond au nouveau plan. | Examinez le nouveau plan et confirmez son `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | `/reconcile/apply` n'a reçu aucune confirmation (`confirm`). | Planifiez d'abord et envoyez le `digest` du plan en tant que `confirm`. Le CLI le fait dès que vous tapez `yes`. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | Le pilote de ce backend ne peut pas planifier de réconciliation, ou ne peut pas exécuter de SQL. | La réconciliation fonctionne sur Postgres. |

### Pourquoi une table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` énumère chaque table refusée dans `details.tables`, avec
l'un de ces codes. Ce même code figure dans le champ `blocked` de la table au
sein du diff lui-même, afin que Studio puisse l'indiquer avant que quiconque ne
clique sur **Merge**. Aucun ne constitue une réponse indépendante.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table diffèrent entre la branche et son parent. Les lignes sont comparées sur la base des colonnes qu'elles partagent. | Ajoutez les colonnes manquantes au parent avec vos migrations (`rebase db push`), puis fusionnez. Une migration réécrivant la table — modification de type de colonne — la transforme en `TABLE_REWRITTEN` : fusionnez avant un tel changement, ou recréez la branche après. |
| `NO_PRIMARY_KEY` | — | La table n'a pas de clé primaire, les lignes ne peuvent donc pas être comparées une à une ; le diff n'indique que ses décomptes de lignes. | Attribuez une clé primaire à la table, ou déplacez ses lignes à la main. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes de la clé primaire, ou leurs types, diffèrent entre les deux. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La branche a créé la table. Une fusion n'en crée jamais. | Créez-la sur le parent avec vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La branche a supprimé la table. Une fusion n'en supprime jamais. | Supprimez-la avec vos migrations. |
| `TABLE_REWRITTEN` | — | L'un des côtés a réécrit chaque ligne de la table après la création de la branche — modification de type de colonne, `ADD COLUMN` avec une valeur par défaut volatile, `VACUUM FULL`, `CLUSTER` — chaque ligne apparaît donc comme modifiée depuis lors et il n'est plus possible de savoir quel côté a modifié quelle ligne. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après coup. |
| `TOO_LARGE` | — | La table contient plus de lignes sur un côté que ce qu'un diff compare une par une (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` à la fois pour le diff et la fusion, ou transférez les lignes autrement. |

## Codes génériques

Une route utilise l'un de ceux-ci lorsqu'aucun code plus précis ne s'applique.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Malformée, et aucun code plus spécifique ne s'applique. | Consultez le message. |
| `UNAUTHORIZED` | 401 | Non authentifié, ou identifiant rejeté. | Connectez-vous ou actualisez la session. |
| `FORBIDDEN` | 403 | Authentifié, mais non autorisé. | Réessayer avec la même identité ne servira à rien. |
| `CONFLICT` | 409 | Conflit avec l'état existant. | Consultez le message. |
| `INTERNAL_ERROR` | 500 | Un problème est survenu sur le serveur. Le message est délibérément générique. | Mentionnez le `requestId` ; la raison figure dans les logs. |
| `NOT_CONFIGURED` | 503 | Une dépendance nécessaire à cette route n'est pas configurée sur ce serveur. | Consultez le message. |
| `SERVICE_UNAVAILABLE` | 503 | Un service dont dépend la requête n'a pas pu être atteint : un bucket S3 ou MinIO, ou un hôte qu'une fonction tente de `fetch()` qui refuse la connexion ou n'est pas résolu. Le log du serveur nomme l'hôte ; la réponse ne le mentionne pas. Une base de données inaccessible renvoie `DATABASE_UNAVAILABLE`. Une connexion défaillante vers un tel service renvoie ce code. | Réessayez ; consultez les logs. |

## Maintenir cette page à jour

`pnpm verify:docs` échoue lorsqu'un code que le serveur peut lever est absent de
ces tableaux, lorsqu'un tableau liste un code que rien ne peut lever, lorsque les
statuts d'une ligne ne correspondent pas exactement à ceux avec lesquels le code
source lève le code, ou lorsqu'une famille de codes telle que `PG_<SQLSTATE>` ne
contient pas de ligne pour un SQLSTATE rencontré par les appelants. L'étape est
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Elle se vérifie d'abord elle-même. L'analyse lit les codes depuis TypeScript
plutôt que depuis un serveur en cours d'exécution, ses angles morts sont donc
silencieux par conception : elle a par le passé été incapable de détecter un code
passé par un wrapper d'une ligne, ou écrit après un message contenant une `)`, et
indiquait « chaque code que le serveur peut lever est documenté » sur une page où
il en manquait dix-sept. Cette étape exécute donc une fixture reproduisant
exactement ces cas de figure avant de lire cette page, et refuse de générer le
moindre rapport si elle ne parvient pas à les détecter.
