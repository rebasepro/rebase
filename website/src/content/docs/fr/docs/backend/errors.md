Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. Le code est l'élément sur lequel baser vos branchements conditionnels : le message est rédigé pour un humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, alors que le code n'est ni l'un ni l'autre.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par un humain. Pour une `4xx`, il s'agit du message propre au serveur ; pour une `5xx`, il est délibérément générique, car le texte sous-jacent peut citer un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable d'une version mineure à l'autre.
- **`details`** — optionnel et jamais garanti. Voir les règles ci-dessous.
- **`requestId`** — présent dès que la requête est passée par le middleware de request-ID, c'est-à-dire pour chaque route sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un identifiant : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, ou un nouvel identifiant dans le cas contraire. Il est renvoyé en écho dans la réponse sous le nom `X-Request-ID`, inclus dans l'enveloppe d'erreur sous le nom `requestId`, et joint à la ligne de log du serveur correspondant à cette requête.

Il s'agit de la clé de jointure. Mentionnez-le dans un rapport de bug et un opérateur pourra retrouver l'unique ligne de log expliquant l'échec, contenant la raison qui n'a jamais été montrée au client.

Envoyer votre propre identifiant permet à une trace de traverser un saut réseau : une passerelle ou un exécuteur de tâches qui transmet l'en-tête conserve un ID unique à travers tous les services qui ont traité la requête. Une valeur invalide est ignorée plutôt que rejetée — un en-tête malformé provenant d'un appelant ne justifie pas l'échec d'une requête — ne présumez donc pas que l'ID envoyé est celui que vous avez reçu. Lisez l'en-tête de réponse.

### Ce que contient `details`

Le champ `details` est diagnostique, non contractuel. Trois règles le régissent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des erreurs propres à l'appelant décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas accessible en écriture, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont purgés en production.** Lorsque l'échec provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il indique la classe du problème et ne révèle rien sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y inclut le contenu des lignes. Le code `23505` rapporte `Key (email)=(a@b.c) already exists.`, ce qui permet de répondre à « cette personne est-elle enregistrée ? » pour n'importe quelle adresse testée.
3. **Ne faites jamais de branchement conditionnel sur `details`.** Basez vos branchements sur `code`. Le contenu de `details` correspond à ce qui était utile à un humain à cet endroit du code au moment de l'appel, et il est sujet à changement.

## Comprendre un statut

| Statut | Ce que cela indique sur la requête |
| --- | --- |
| `400` | Malformée, ou demandant quelque chose qui n'existe pas dans le schéma. Corrigez la requête. |
| `401` | Non authentifié, ou l'identifiant a expiré. Connectez-vous ou actualisez le jeton. |
| `403` | Authentifié, mais non autorisé. Réessayer avec la même identité ne changera rien. |
| `404` | Route, table ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Conflit avec l'état existant : doublon ou écriture concurrente. |
| `413` `415` `422` | Corps trop volumineux, mauvais type de média ou rejet sémantique. |
| `429` | Limite de débit atteinte (Rate limited). Ralentissez ; le message indique pendant combien de temps. |
| `500` | L'erreur vient du serveur ou de sa base de données, pas de l'appelant. Consultez les logs. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — fonctionnalité désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était inaccessible, non configurée ou trop lente. |

## `PG_<SQLSTATE>` — une contrainte refusée par la base de données

Une écriture rejetée par Postgres en raison des *données de l'appelant* répond
avec le SQLSTATE dans le code : `PG_23505`, `PG_23503`, et ainsi de suite. Il s'agit
d'une famille de codes et non d'une liste finie — Postgres définit des centaines
de SQLSTATEs — mais seules deux classes sont concernées ici, car seules ces deux-là
relèvent de la responsabilité de l'appelant :

- **classe 23**, violation de contrainte d'intégrité : doublon, clé étrangère
  pointant vers une cible inexistante, colonne NOT NULL laissée vide ;
- **classe 22**, exception de données : valeur impossible à stocker dans le type de la colonne.

Tout le reste — coupure de connexion, colonne manquante, problème de droits —
relève du serveur et conserve un statut `500`. Le test `code.startsWith("PG_")`
est donc un moyen fiable de vérifier que « la ligne envoyée était incorrecte »,
et les quatre codes ci-dessous sont ceux réellement rencontrés par un client.
`details.dbCode` contient le même SQLSTATE pour chacun d'eux, et le message
nomme la contrainte.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Impossible de lire une valeur selon le type de la colonne — le pendant côté écriture de `INVALID_FILTER_VALUE`. | Envoyez une valeur correspondant au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` a été laissée vide. | Transmettez le champ, ou attribuez une valeur par défaut à la colonne. |
| `PG_23503` | 400 / 409 | Lors d'un enregistrement, une clé étrangère pointe vers une ligne inexistante (400). Lors d'une suppression, d'autres lignes référencent toujours celle-ci (409 ; une clé `RESTRICT` lève `PG_23001`, également une 409). | Créez d'abord la ligne cible, ou corrigez l'identifiant ; pour une suppression, retirez d'abord les lignes dépendantes ou mettez à jour leur référence. |
| `PG_23505` | 409 | Violation d'une contrainte d'unicité. Le message précise la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

### Réconciliation de schéma

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) planifie
via `POST /api/admin/schema/reconcile/plan` et applique via
`/reconcile/apply`. Un refus ne modifie rien ; seul `SCHEMA_RECONCILE_FAILED`
laisse un plan partiellement appliqué.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | Le corps n'est pas un objet JSON, ou `drop` n'est pas une liste de chaînes `"<table>.<column>"`. | Envoyez `{ "drop": ["voice_cache.wav"] }`, ou omettez `drop`. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Une instruction a échoué en cours d'exécution. Les instructions précédentes ont été exécutées et restent appliquées ; `details.applied` les liste. | Corrigez ce que le message indique, puis relancez la planification : le nouveau plan exclura ce qui a déjà été appliqué. |
| `SCHEMA_RECONCILE_INVALID` | 400 | Le plan ne peut pas être appliqué, et le message en liste les raisons : un `drop` qui n'est pas au format `<table>.<column>`, ne désigne aucune table ou colonne, ou désigne une colonne toujours déclarée dans la table. `details.plan` contient le plan. | Corrigez la liste `drop`. Pour supprimer une colonne déclarée, retirez-la de son `defineTable`, déployez, puis effectuez la réconciliation. |
| `SCHEMA_RECONCILE_STALE` | 409 | La base de données ou les tables ont changé depuis le plan que vous avez validé. `details.plan` contient le nouveau plan. | Examinez le nouveau plan et confirmez son `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | `/reconcile/apply` a été appelé sans `confirm`. | Planifiez d'abord et transmettez le `digest` du plan dans `confirm`. La CLI s'en charge dès que vous saisissez `yes`. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | Le pilote de ce backend ne sait pas planifier de réconciliation, ou ne peut pas exécuter de SQL. | La réconciliation fonctionne sur Postgres. |

### Pourquoi la table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` énumère chaque table refusée dans `details.tables`, avec l'un
de ces codes. Ce même code figure sous la propriété `blocked` de la table dans le
diff lui-même, permettant à Studio de l'indiquer avant que quiconque ne clique sur
**Fusionner**. Aucun de ces codes ne constitue une réponse autonome.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table diffèrent entre la branche et son parent. Les lignes sont comparées sur la base des colonnes communes. | Ajoutez les colonnes manquantes au parent avec vos migrations (`rebase db push`), puis fusionnez. Une migration qui réécrit la table — changement de type de colonne — transforme ce statut en `TABLE_REWRITTEN` : fusionnez avant un tel changement, ou recréez la branche après. |
| `NO_PRIMARY_KEY` | — | La table n'a pas de clé primaire, les lignes ne peuvent donc pas être comparées une par une ; le diff n'indique que ses totaux de lignes. | Attribuez une clé primaire à la table, ou déplacez ses lignes manuellement. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes de la clé primaire, ou leurs types, diffèrent entre les deux. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La branche a créé la table. Une fusion ne crée jamais de table. | Créez-la sur le parent via vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La branche a supprimé la table. Une fusion ne supprime jamais de table. | Supprimez-la via vos migrations. |
| `TABLE_REWRITTEN` | — | L'un des côtés a réécrit toutes les lignes de la table après la création de la branche — changement de type de colonne, `ADD COLUMN` avec valeur par défaut volatile, `VACUUM FULL`, `CLUSTER` — chaque ligne apparaît donc comme modifiée depuis, rendant impossible l'identification du côté ayant modifié chaque ligne. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après celle-ci. |
| `TOO_LARGE` | — | La table compte plus de lignes sur un côté que ce qu'un diff peut comparer individuellement (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` pour le diff et la fusion, ou déplacez les lignes par un autre moyen. |

## Garantir l'exactitude de cette page

`pnpm verify:docs` échoue lorsqu'un code que le serveur peut lever est absent de
ces tableaux, lorsqu'un tableau liste un code que rien ne peut lever, lorsque les
statuts d'une ligne ne correspondent pas exactement à ceux avec lesquels le code
source lève le code, ou lorsqu'une famille de codes comme `PG_<SQLSTATE>` ne contient pas
de ligne pour un SQLSTATE rencontré par les appelants. L'étape de validation est
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Elle s'auto-contrôle d'abord. L'analyse extrait les codes directement depuis le code
TypeScript plutôt que depuis un serveur en cours d'exécution, ses angles morts sont
donc silencieux par nature : il lui est déjà arrivé d'ignorer un code encapsulé
dans un wrapper d'une ligne, ou placé après un message contenant une parenthèse `)`,
concluant que « chaque code que le serveur peut lever est documenté » sur une page
où il en manquait dix-sept. Cette étape exécute donc d'abord un jeu de test
reproduisant exactement ces cas de figure avant de lire cette page, et refuse de
valider quoi que ce soit si elle ne parvient pas à les détecter.
