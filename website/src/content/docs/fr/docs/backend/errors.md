Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. Le code est l'élément sur lequel baser vos branchements conditionnels : le message est rédigé pour un humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, alors que le code n'est ni l'un ni l'autre.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par un humain. Pour un code `4xx`, il s'agit du propre message du serveur ; pour un `5xx`, il est délibérément générique, car le texte sous-jacent peut citer un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable d'une version mineure à l'autre.
- **`details`** — optionnel et jamais garanti. Voir les règles ci-dessous.
- **`requestId`** — présent dès lors que la requête est passée par le middleware de request-ID, c'est-à-dire chaque route sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un identifiant : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, ou un nouvel identifiant dans le cas contraire. Il est renvoyé en écho dans la réponse sous le nom de `X-Request-ID`, inclus dans l'enveloppe d'erreur sous `requestId`, et joint à la ligne de journal (log) du serveur pour cette requête.

C'est la clé de jointure. Citez-la dans un rapport de bug et un opérateur pourra retrouver l'unique ligne de log expliquant l'échec, contenant la raison qui n'a jamais été montrée au client.

Envoyer votre propre identifiant permet à une trace de survivre d'un saut à l'autre : une passerelle ou un exécuteur de tâches qui transfère l'en-tête conserve un ID unique à travers tous les services ayant traité la requête. Une valeur invalide est ignorée plutôt que rejetée — un en-tête malformé provenant d'un appelant ne mérite pas de faire échouer une requête — ne présumez donc pas que l'ID envoyé est celui que vous avez reçu. Lisez l'en-tête de réponse.

### Contenu de `details`

`details` a une vocation diagnostique et non contractuelle. Trois règles l'encadrent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des erreurs propres à l'appelant, décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas modifiable en écriture, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont épurés en production.** Lorsque l'erreur provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il nomme la classe du problème sans rien révéler sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y inclut le contenu des lignes. `23505` indique `Key (email)=(a@b.c) already exists.`, ce qui permettrait à quiconque de vérifier « cette personne est-elle inscrite ? » pour n'importe quelle adresse testée.
3. **Ne basez jamais vos branchements sur `details`.** Basez-les sur `code`. Le contenu de `details` correspond à ce qui était utile à un humain à cet endroit précis du code, et il est sujet à changement.

## Interpréter un statut

| Statut | Ce qu'il indique sur la requête |
| --- | --- |
| `400` | Malformée, ou demandant un élément qui n'existe pas dans le schéma. Corrigez la requête. |
| `401` | Non authentifié, ou identifiant expiré. Connectez-vous ou actualisez le jeton. |
| `403` | Authentifié, mais non autorisé. Réessayer avec la même identité ne servira à rien. |
| `404` | Route, table ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Un conflit avec l'état existant : un doublon ou une écriture concurrente. |
| `413` `415` `422` | Le corps est trop volumineux, le type de média est incorrect ou la requête est sémantiquement rejetée. |
| `429` | Limite de débit atteinte (rate limit). Ralentissez la cadence ; le message indique pendant combien de temps. |
| `500` | L'erreur provient du serveur ou de sa base de données, pas de l'appelant. Consultez les logs. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — une fonctionnalité désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était inaccessible, non configurée ou trop lente. |

## `PG_<SQLSTATE>` — une contrainte refusée par la base de données

Une écriture que Postgres rejette pour une raison liée aux *données de l'appelant* répond avec le SQLSTATE directement intégré au code d'erreur : `PG_23505`, `PG_23503`, etc. Il s'agit d'une famille d'erreurs et non d'une liste finie — Postgres définit des centaines de codes SQLSTATE — mais seules deux classes sont susceptibles de vous parvenir, car elles sont les seules imputables à l'appelant :

- **classe 23**, violation de contrainte d'intégrité : un doublon, une clé étrangère pointant vers le vide, une colonne NOT NULL laissée vide ;
- **classe 22**, exception sur les données : une valeur incompatible avec le type de la colonne.

Tout le reste — une connexion interrompue, une colonne manquante, un défaut de privilèges — incombe au serveur et demeure sous forme d'erreur `500`. Dès lors, tester `code.startsWith("PG_")` est une méthode fiable pour détecter que « la ligne envoyée était incorrecte », les quatre codes ci-dessous étant ceux réellement rencontrés par un client. `details.dbCode` transporte le même SQLSTATE pour chacun d'eux, et le message précise la contrainte en cause.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Une valeur n'a pas pu être interprétée selon le type de la colonne — le pendant côté écriture de `INVALID_FILTER_VALUE`. | Envoyez une valeur correspondant au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` a été laissée vide. | Renseignez le champ, ou affectez une valeur par défaut à la colonne. |
| `PG_23503` | 400 / 409 | À l'enregistrement, une clé étrangère pointe vers une ligne inexistante (400). À la suppression, d'autres lignes dépendent encore de celle-ci (409 ; une clé en `RESTRICT` produit `PG_23001`, également en 409). | Créez d'abord la ligne cible ou corrigez l'identifiant ; pour une suppression, supprimez ou réassociez d'abord les lignes dépendantes. |
| `PG_23505` | 409 | Violation d'une contrainte d'unicité. Le message précise la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

| `FUNCTION_TIMEOUT` | 504 | Le gestionnaire a dépassé son délai d'exécution imparti. Il tourne toujours en arrière-plan et ne peut pas être interrompu depuis ce point. | Associez un `AbortSignal` aux appels externes, ou augmentez `REBASE_FUNCTIONS_TIMEOUT_MS`. |
| `FUNCTIONS_UPSTREAM_UNREACHABLE` | 502 | Ce processus relaie les fonctions vers un autre processus qui n'a pas répondu. | Assurez-vous que l'unité exécutant les fonctions est bien démarrée. |

Ces erreurs indiquent qu'une fonctionnalité est désactivée ou mal configurée, et non que la requête était incorrecte. Chacune est également renvoyée sur la route `/status` associée avec un code `200`, permettant à une interface de griser l'option plutôt que d'afficher une erreur.

| `BRANCH_DIFF_STALE` | 409 | `POST /api/admin/branches/:name/merge` a reçu l'empreinte d'un diff qui n'est plus valide : la branche ou son parent a changé depuis. Rien n'a été écrit. | Relisez le diff, inspectez-le, puis effectuez la fusion avec son nouveau `fingerprint`. |
| `BRANCH_DIFF_UNSUPPORTED` | 501 | La source de données ne peut pas comparer les branches : absence de support SQL, ou pas de gestion des branches (pas de connexion admin). | Utilisez un backend Postgres configuré avec `adminConnectionString`. |

### Réconciliation de schéma

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) planifie
via `POST /api/admin/schema/reconcile/plan` et applique via
`/reconcile/apply`. Un refus ne modifie rien ; seul `SCHEMA_RECONCILE_FAILED`
laisse un plan partiellement appliqué.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | Le corps n'est pas un objet JSON, ou `drop` n'est pas une liste de chaînes `"<table>.<column>"`. | Envoyez `{ "drop": ["voice_cache.wav"] }`, ou omettez le paramètre `drop`. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Une instruction a échoué en cours d'exécution. Les instructions antérieures ont été exécutées et restent appliquées ; `details.applied` les énumère. | Corrigez ce que le message indique, puis planifiez à nouveau : le nouveau plan ignorera ce qui a déjà été appliqué. |
| `SCHEMA_RECONCILE_INVALID` | 400 | Le plan ne peut pas être appliqué, et le message en liste les raisons : un élément de `drop` ne respecte pas le format `<table>.<column>`, ne correspond à aucune table ou colonne, ou désigne une colonne toujours déclarée dans la table. `details.plan` contient le plan. | Corrigez la liste `drop`. Pour supprimer une colonne déclarée, retirez-la de son `defineTable`, déployez, puis lancez la réconciliation. |
| `SCHEMA_RECONCILE_STALE` | 409 | La base de données ou les tables ont été modifiées depuis le plan que vous avez confirmé. `details.plan` présente le nouveau plan. | Passez en revue le nouveau plan et confirmez son `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | `/reconcile/apply` a été appelé sans argument `confirm`. | Générez d'abord le plan et envoyez son `digest` sous l'argument `confirm`. La CLI s'en charge automatiquement après la saisie de `yes`. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | Le pilote de ce backend ne peut pas planifier de réconciliation, ou ne peut pas exécuter de SQL. | La réconciliation fonctionne sur Postgres. |

### Pourquoi la table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` énumère chaque table refusée dans `details.tables`, associée à l'un de ces codes. Ce même code figure sous la propriété `blocked` de la table dans le diff lui-même, permettant au Studio de prévenir l'utilisateur avant même qu'il ne clique sur **Merge**. Aucun ne constitue une réponse d'erreur autonome.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table diffèrent entre la branche et son parent. Les lignes sont comparées sur la base de leurs colonnes communes. | Ajoutez les colonnes manquantes au parent via vos migrations (`rebase db push`), puis lancez la fusion. Une migration réécrivant la table — comme un changement de type de colonne — transforme ce statut en `TABLE_REWRITTEN` : fusionnez avant une telle opération, ou recréez la branche après celle-ci. |
| `NO_PRIMARY_KEY` | — | La table n'a pas de clé primaire, empêchant toute comparaison ligne par ligne ; le diff indique uniquement les nombres de lignes. | Définissez une clé primaire sur la table, ou transférez ses lignes manuellement. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes constituant la clé primaire, ou leurs types, diffèrent entre les deux versions. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La branche a créé la table. Une fusion ne crée jamais de table. | Créez-la sur le parent à l'aide de vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La branche a supprimé la table. Une fusion ne supprime jamais de table. | Supprimez-la à l'aide de vos migrations. |
| `TABLE_REWRITTEN` | — | L'un des côtés a réécrit l'intégralité des lignes de la table après la création de la branche — changement de type de colonne, `ADD COLUMN` avec valeur par défaut volatile, `VACUUM FULL`, `CLUSTER` — de sorte que chaque ligne apparaît comme modifiée depuis, rendant impossible la distinction des changements respectifs. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après celle-ci. |
| `TOO_LARGE` | — | La table contient sur l'un des côtés plus de lignes qu'un diff n'en compare une par une (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` tant pour le diff que pour la fusion, ou déplacez les lignes par un autre moyen. |

## Maintenir l'exactitude de cette page

La commande `pnpm verify:docs` échoue si un code susceptible d'être levé par le serveur manque dans ces tableaux, si un tableau mentionne un code qu'aucun composant ne peut lever, si les statuts d'une ligne ne reflètent pas exactement ceux levés par le code source, ou si une famille de codes comme `PG_<SQLSTATE>` ne comporte pas de ligne pour un SQLSTATE que les appelants peuvent rencontrer. L'étape correspondante est `tooling/scripts/docs-verify/check-error-codes.mjs`.

Elle s'auto-contrôle au préalable. L'analyse extrait les codes depuis l'arbre TypeScript plutôt que depuis un serveur en cours d'exécution, ses angles morts sont donc silencieux par nature : elle a par exemple été incapable par le passé de détecter un code transmis au travers d'un wrapper d'une ligne, ou placé après un message contenant une parenthèse `)`, et affirmait que « chaque code levé par le serveur est documenté » alors que la page en omettait dix-sept. Désormais, cette vérification exécute d'abord un jeu de test reproduisant précisément ces motifs avant de lire la présente page, et refuse de rendre son verdict si elle ne parvient pas à les repérer.
