Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. Le code est l'élément sur lequel baser vos branchements logiques : le message est écrit pour un être humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, alors que le code n'est ni l'un ni l'autre.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par un être humain. Pour un statut `4xx`, il s'agit du propre message du serveur ; pour un statut `5xx`, il est délibérément générique, car le texte sous-jacent peut citer un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable d'une version mineure à l'autre.
- **`details`** — optionnel, et jamais garanti. Voir les règles ci-dessous.
- **`requestId`** — présent chaque fois que la requête est passée par le middleware de request-ID, ce qui correspond à toutes les routes sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un identifiant : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, ou un nouvel identifiant dans le cas contraire. Il est renvoyé dans la réponse sous la forme `X-Request-ID`, inclus dans l'enveloppe d'erreur sous `requestId`, et attaché à la ligne de log du serveur correspondant à cette requête.

C'est la clé de jointure. Mentionnez-la dans un rapport de bug et un opérateur pourra retrouver l'unique ligne de log qui explique l'échec, contenant la raison qui n'a jamais été montrée au client.

Envoyer votre propre identifiant permet à une trace de traverser les différents sauts de réseau : une passerelle ou un exécuteur de tâches qui transmet l'en-tête conserve un ID unique à travers tous les services ayant traité la requête. Une valeur invalide est ignorée plutôt que rejetée — un en-tête malformé provenant d'un appelant ne mérite pas de faire échouer une requête — ne présumez donc pas que l'ID envoyé est celui obtenu. Lisez l'en-tête de réponse.

### Que contient `details`

`details` est diagnostique, non contractuel. Trois règles le régissent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des erreurs propres à l'appelant décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas accessible en écriture, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont tronqués en production.** Lorsque l'échec provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il désigne la classe du problème et ne révèle rien sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y insère le contenu des lignes. `23505` signale `Key (email)=(a@b.c) already exists.`, ce qui répond à la question « cette personne est-elle inscrite ? » pour toute adresse qu'un tiers voudrait tester.
3. **Ne branchez jamais votre logique sur `details`.** Branchez-vous sur `code`. Ce qui se trouve sous `details` est ce qui était utile à un humain au point d'appel concerné, et cela est sujet à changement.

## Interpréter un statut

| Statut | Ce que cela indique sur la requête |
| --- | --- |
| `400` | Malformée, ou demandant un élément inexistant dans le schéma. Corrigez la requête. |
| `401` | Non authentifié, ou identifiant expiré. Connectez-vous ou actualisez le jeton. |
| `403` | Authentifié, mais non autorisé. Réessayer avec la même identité ne servira à rien. |
| `404` | Route, table ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Conflit avec l'état existant : un doublon ou une écriture concurrente. |
| `413` `415` `422` | Le corps est trop volumineux, le type de média est incorrect ou rejeté sémantiquement. |
| `429` | Limite de débit atteinte. Ralentissez la cadence ; le message indique pendant combien de temps. |
| `500` | Le problème vient du serveur ou de sa base de données, pas de l'appelant. Consultez les logs. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — une fonctionnalité désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était inaccessible, non configurée ou trop lente. |

## Authentification et comptes

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `AAL2_REQUIRED` | 403 | La route requiert un second facteur et la session n'en possède qu'un. | Répondez au challenge MFA, puis réessayez. |
| `ALREADY_VERIFIED` | 400 | L'adresse ou le facteur est déjà vérifié. | Rien — l'état souhaité est déjà atteint. |
| `ACCOUNT_OUTRANKS_CALLER` | 403 | Le compte en cours de modification, réinitialisation ou suppression possède un rôle ou une portée que l'appelant n'a pas. `details.beyond` les énumère. | Demandez à une personne détenant ces privilèges d'effectuer la modification. |
| `ANONYMOUS_AUTH_DISABLED` | 403 | La connexion anonyme est désactivée sur ce serveur. | Activez-la, ou connectez-vous avec une véritable identité. |
| `ANONYMOUS_NOT_ALLOWED` | 403 | Une session invité a tenté d'approuver une connexion d'appareil. Un invité n'a pas de compte à prêter à un appareil. | Connectez-vous avec un compte, puis approuvez la connexion. |
| `API_KEY_SELF_MANAGEMENT_FORBIDDEN` | 403 | Une clé d'API a tenté de lister, créer, modifier ou révoquer des clés d'API, qu'il s'agisse de clés de son propre type ou de clés personnelles. | Gérez les clés en tant que personne détenant `keys:write`, ou avec la clé de service. |
| `AUTH_MIDDLEWARE_MISSING` | 500 | Une route protégée a été exécutée sans aucun middleware d'authentification Rebase en amont, de sorte que les identifiants de l'appelant n'ont jamais été examinés. | Montez l'application via le routeur de fonctions plutôt que directement sur votre propre serveur. |
| `BOOTSTRAP_ANONYMOUS` | 403 | L'initialisation du premier administrateur a été tentée par un appelant anonyme. | Connectez-vous d'abord. |
| `BOOTSTRAP_COMPLETED` | 403 | Le premier administrateur existe déjà. | Demandez à un administrateur existant d'accorder le rôle. |
| `BOOTSTRAP_NOT_FIRST_USER` | 403 | L'initialisation est réservée au tout premier utilisateur, et il ne s'agit pas de celui-ci. | Demandez à un administrateur existant d'accorder le rôle. |
| `CAPTCHA_FAILED` | 400 | Le fournisseur a rejeté le jeton CAPTCHA. | Résolvez un nouveau test. |
| `CAPTCHA_REQUIRED` | 400 | La route requiert un jeton CAPTCHA et aucun n'a été envoyé. | Incluez le jeton. |
| `CHALLENGE_EXHAUSTED` | 401 | Trop de codes erronés saisis pour ce challenge MFA. | Lancez un nouveau challenge. |

| `DDL_REJECTED` | 400, ou 409 quand l'objet existe déjà | PostgreSQL a refusé une instruction exécutée pour vous par `/api/admin/db/*` — un type, une valeur par défaut, une condition de politique, un nom déjà pris. Le message est celui de Postgres, et `details.dbCode` son SQLSTATE. | Modifiez l'élément mentionné dans le message et renvoyez la requête ; `dryRun: true` affiche d'abord le SQL. |
| `DEVICE_LOGIN_DECIDED` | 409 | La connexion de l'appareil a déjà été approuvée ou refusée. Une connexion n'est tranchée qu'une seule fois. | Lancez-en une nouvelle sur l'appareil. |
| `DEVICE_LOGIN_EXPIRED` | 410 | La connexion de l'appareil a dépassé ses dix minutes avant d'avoir été tranchée. | Lancez-en une nouvelle sur l'appareil. |
| `DEVICE_LOGIN_NOT_FOUND` | 404 | Aucune connexion d'appareil ne correspond à ce code utilisateur. L'interrogation de l'appareil elle-même renvoie les codes minuscules de la RFC 8628 : `authorization_pending`, `slow_down`, `access_denied`, `expired_token`, `invalid_grant`. | Vérifiez le code par rapport à celui affiché par l'appareil. |
| `EMAIL_EXISTS` | 409 | Un compte avec cette adresse existe déjà — lors de l'inscription, d'un changement d'adresse, ou en suivant un lien de changement d'adresse alors qu'un autre compte a pris l'adresse pendant l'attente. | Connectez-vous, ou lancez une réinitialisation de mot de passe ; pour un changement d'adresse, choisissez une autre adresse. |
| `EMAIL_NOT_CONFIGURED` | 503 | Des liens magiques (magic links) ou OTP ont été demandés et le serveur ne dispose d'aucun transport d'e-mails. | Configurez SMTP, ou utilisez une autre méthode de connexion. |
| `EMAIL_NOT_VERIFIED` | 403 | Une connexion OAuth a trouvé un compte avec la même adresse, mais le fournisseur n'a pas vérifié cette adresse, elle n'est donc pas liée. | Connectez-vous avec la méthode existante, puis `POST /auth/link/<provider>`. |
| `CSRF_REFUSED` | 403 | La protection CSRF est activée (`csrf: { origin }`) et une requête sans en-tête `Authorization` provient d'une origine hors liste : une soumission de formulaire authentifiée par cookie depuis un autre site, ou une requête sans corps et sans `Origin`. | Envoyez-la depuis une origine autorisée, avec un corps JSON, ou avec un en-tête `Authorization`. |
| `FACTOR_NOT_VERIFIED` | 400 | Le facteur MFA a été enregistré mais jamais confirmé. | Confirmez le facteur. |
| `ID_EXISTS` | 409 | Un compte possède déjà l'ID qu'un import de comptes souhaite conserver (`POST /api/admin/users/import`). L'import le signale comme `skipped` et laisse le compte tel quel. | Rien, si le compte avait déjà été importé auparavant. Sinon, omettez `id`, ou choisissez-en un autre. |
| `IDENTITY_ALREADY_LINKED` | 409 | Cette identité OAuth appartient à un autre compte. | Connectez-vous avec celle-ci, ou déliez-la d'abord de l'autre compte. |
| `IMPERSONATION_FORBIDDEN` | 403 | Une requête a envoyé `x-rebase-impersonate` et son appelant n'est pas autorisé à exécuter une requête au nom d'un autre utilisateur. Seule la session propre d'un administrateur connecté le peut, jamais une clé d'API ou la clé de service. | Envoyez-la avec la session d'un administrateur, ou omettez l'en-tête. |
| `IMPERSONATION_INVALID` | 400 | `x-rebase-impersonate` a été envoyé vide. | Envoyez l'UID de l'utilisateur sous l'identité duquel agir, ou omettez l'en-tête. |
| `IMPERSONATION_TARGET_NOT_FOUND` | 404 | `x-rebase-impersonate` ne désigne aucun utilisateur actif : aucun compte ne possède cet UID, ou il est désactivé. | Vérifiez l'UID. |
| `IMPERSONATION_UNAVAILABLE` | 501 | L'authentification de ce backend ne peut pas exécuter une requête sous l'identité d'un autre utilisateur, car son `AuthAdapter` ne possède pas de méthode `resolveUser`. | Implémentez `resolveUser` dans l'adaptateur, ou omettez l'en-tête. |
| `IMPERSONATION_UNSUPPORTED` | 400 | `x-rebase-impersonate` a été envoyé à une route qui ne peut pas s'exécuter sous l'identité d'un autre utilisateur. Seules l'API de données et les fonctions personnalisées le prennent en charge, et la socket temps réel prend en charge `impersonate` lors de `AUTHENTICATE`. | Envoyez la requête sans l'en-tête. |
| `SIMULATION_FORBIDDEN` | 403 | Une requête a envoyé un en-tête `x-rebase-simulate-*` (le simulateur RLS), ou a interrogé `/api/admin/rls-simulator`, et son appelant n'est pas autorisé à simuler des accès. Seule la propre session d'un administrateur connecté le peut, jamais une clé d'API ou la clé de service. | Envoyez-la avec la session d'un administrateur, ou omettez les en-têtes. |
| `SIMULATION_INVALID` | 400 | La simulation était malformée : un en-tête envoyé vide, `x-rebase-simulate-api-key-id` combiné à un rôle ou un ID utilisateur, ou une simulation combinée à `x-rebase-impersonate`. | Indiquez un seul rôle (optionnellement avec un UID), un seul ID utilisateur, ou un seul ID de clé d'API. |
| `SIMULATION_READ_ONLY` | 403 | Une écriture, suppression, `_batch`, annulation d'historique, ou une fonction personnalisée appelée avec un verbe autre que `GET`/`HEAD`/`OPTIONS`, comportait un en-tête `x-rebase-simulate-*`. L'accès simulé est en lecture seule : l'écriture s'exécuterait sous l'identité simulée, non sous celle de l'administrateur. Les lectures, y compris `POST …/query` et `…/count`, s'exécutent toujours. | Cessez la simulation pour effectuer des modifications. |
| `SIMULATION_TARGET_NOT_FOUND` | 404 | La simulation ne désigne aucun utilisateur actif (un ID utilisateur envoyé sans rôle) ou aucune clé d'API valide. | Vérifiez l'ID, ou envoyez un rôle avec l'UID pour simuler un UID qui ne possède pas de compte. |
| `SIMULATION_UNAVAILABLE` | 501 | Ce backend ne peut pas simuler d'accès : son `AuthAdapter` n'a pas de méthode `resolveUser` pour confirmer un administrateur, ou une clé a été spécifiée sur un backend sans clés d'API. | Implémentez `resolveUser`, ou omettez les en-têtes. |
| `SIMULATION_UNSUPPORTED` | 400 | Un en-tête `x-rebase-simulate-*` a été envoyé à une route qui ne peut pas s'exécuter avec un accès simulé. Seules l'API de données et les fonctions personnalisées les prennent en compte. | Envoyez la requête sans les en-têtes. |
| `GUEST_REFERENCED` | 409 | Un invité n'a pas pu être supprimé car une ligne propre au projet l'exige, via une clé étrangère avec `ON DELETE RESTRICT` ou `NO ACTION`. `DELETE /api/admin/guests` le signale pour chaque invité dans `skipped` et continue son traitement. | Supprimez la ligne, ou conservez l'invité. |
| `INVALID_ACCOUNT` | 400 | Le compte est dans un état sur lequel cette opération ne peut pas agir. | Voir le message. |
| `INVALID_CHALLENGE` | 400 | Le challenge MFA est inconnu ou expiré. | Lancez-en un nouveau. |
| `INVALID_CODE` | 400 / 401 | Le code OTP ou MFA est incorrect : 400 pour la connexion par code e-mail (`/auth/otp/verify`), 401 pour un enrôlement ou challenge MFA. | Réessayez avec le code actuel. |
| `INVALID_CREDENTIALS` | 401 | E-mail ou mot de passe erroné — sans préciser délibérément lequel. | Réessayez, ou réinitialisez le mot de passe. |
| `INVALID_PLATFORM_TOKEN` | 401 | Un jeton de plateforme `rpt_` a été refusé : signature invalide, mauvaise audience, expiré ou durée de vie dépassant le plafond. Le message précise la cause. | Demandez à la plateforme d'en générer un nouveau — sur Rebase Cloud, réexécutez la commande. |
| `INVALID_SCOPES` | 400 | Une clé a été demandée pour un élément qui n'est pas une portée valide : malformée, inconnue ou avec une cible non prise en charge par la portée. `details.problems` indique laquelle et pourquoi ; `details.validScopes` liste les portées qu'une clé peut détenir. Il exclut `keys:read` et `keys:write`, qu'aucune clé ne peut détenir. | Utilisez un nom de la liste. Voir [Rôles et portées](/docs/backend/roles-and-scopes/). |
| `INVALID_TOKEN` | 400 / 401 | Un jeton de vérification, de réinitialisation, de lien magique ou de changement d'adresse est malformé, inconnu, déjà consommé ou expiré (400). Un identifiant de fournisseur OAuth ou un jeton d'actualisation non vérifiable renvoie un 401. | Demandez un nouveau lien, ou reconnectez-vous. |
| `INVALID_USER_CODE` | 400 | La valeur envoyée comme code de connexion d'appareil n'en est pas un : huit lettres, comme `BCDF-GHJK`. | Copiez le code affiché par l'appareil. |
| `INVALID_ID` | 400 | L'identifiant `id` d'un compte importé n'est pas valide pour un compte : vide, plus de 128 caractères, contient un caractère en dehors des lettres, chiffres et `_ - . : \|`, un identifiant réservé (`service`, `anonymous`), ou une valeur que la colonne id de la table des utilisateurs ne peut pas contenir (par exemple pas un uuid pour une colonne `uuid`). | Corrigez l'ID, ou omettez-le pour laisser la table en générer un. |
| `INVALID_ROLE` | 400 | Le nom de rôle écrit n'est pas une chaîne, est vide, ou contient `,` `{` `}` `"` `\` ou un caractère de contrôle. Tout autre nom est accepté. |
| `KEY_MANAGEMENT_SCOPE` | 400 | Une clé a demandé `keys:read` ou `keys:write`. Aucune clé ne peut gérer des clés. `details.scopes` les énumère. | Omettez-les. |

| `LAST_ADMIN` | 403 | La modification laisserait le projet sans aucun administrateur. | Promouvez quelqu'un d'autre d'abord. |
| `MFA_REQUIRED` | 401 | Le mot de passe était correct et le compte possède un second facteur vérifié, la connexion n'est donc qu'à moitié achevée. `details` contient un jeton à courte durée de vie restreint au challenge MFA — ce n'est pas une session. | Ouvrez un challenge et validez-le ; la réponse au challenge délivre la session. |
| `NO_SESSION` | 401 | Aucun cookie de session ni jeton d'actualisation n'a été présenté. Normal lors du premier chargement d'une page. | Connectez-vous. |
| `NOT_ANONYMOUS` | 400 | Une route de mise à niveau depuis le statut anonyme a été appelée par un vrai compte, ou `DELETE /api/admin/guests/:uid` en a désigné un. | Rien à mettre à niveau. Pour supprimer un compte, utilisez `DELETE /api/admin/users/:uid`. |

| `ROLE_LOOKUP_FAILED` | 503 | Les rôles de l'appelant n'ont pas pu être lus — sur une route d'administration ou lors d'une requête de données sur un backend avec `config.auth`. ## `PG_<SQLSTATE>` — une contrainte refusée par la base de données

Une écriture que Postgres rejette pour une raison liée *aux données de l'appelant* répond avec le SQLSTATE dans le code : `PG_23505`, `PG_23503`, etc. Il s'agit d'une famille de codes, pas d'une liste exhaustive — Postgres définissant des centaines de SQLSTATE — mais seules deux classes parviennent jusqu'ici, car seules ces deux-là relèvent de la responsabilité de l'appelant :

- **classe 23**, violation de contrainte d'intégrité : un doublon, une clé étrangère pointant vers le vide, une colonne NOT NULL laissée vide ;
- **classe 22**, exception sur les données : une valeur que le type de colonne ne peut pas contenir.

Tout le reste — une connexion perdue, une colonne manquante, un problème de privilèges — incombe au serveur et reste une `500`. Le test `code.startsWith("PG_")` est donc un moyen sûr de vérifier que « la ligne envoyée était incorrecte », et les quatre ci-dessous sont ceux qu'un client rencontre concrètement. `details.dbCode` contient le même SQLSTATE pour chacun d'eux, et le message nomme la contrainte.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Une valeur n'a pas pu être convertie dans le type de la colonne — le pendant côté écriture de `INVALID_FILTER_VALUE`. | Envoyez une valeur conforme au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` a été laissée vide. | Envoyez le champ, ou attribuez une valeur par défaut à la colonne. |
| `PG_23503` | 400 / 409 | Lors d'une sauvegarde, une clé étrangère pointe vers une ligne inexistante (400). Lors d'une suppression, d'autres lignes référencent toujours celle-ci (409 ; une contrainte `RESTRICT` renvoie `PG_23001`, également 409). | Créez d'abord la ligne ciblée, ou corrigez l'identifiant ; pour une suppression, retirez ou réorientez d'abord les lignes qui la référencent. |
| `PG_23505` | 409 | Une contrainte d'unicité a été enfreinte. Le message nomme la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

### Pourquoi la table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` nomme chaque table refusée dans `details.tables`, avec l'un
de ces codes. Le même code apparaît sur le `blocked` de la table dans le diff lui-même,
permettant à Studio de l'indiquer avant que quiconque ne clique sur **Fusionner**. Aucun de ces codes ne constitue une réponse en soi.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table divergent entre la branche et son parent. Les lignes sont comparées sur les colonnes qu'elles ont en commun. | Ajoutez les colonnes manquantes au parent avec vos migrations (`rebase db push`), puis fusionnez. Une migration réécrivant la table — modification de type de colonne — transforme ce cas en `TABLE_REWRITTEN` : fusionnez avant un tel changement, ou recréez la branche après celui-ci. |
| `NO_PRIMARY_KEY` | — | La table n'a pas de clé primaire, les lignes ne peuvent donc pas être comparées une par une ; le diff n'indique que ses totaux de lignes. | Donnez une clé primaire à la table, ou déplacez ses lignes manuellement. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes de la clé primaire, ou leurs types, divergent entre les deux côtés. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La branche a créé la table. Une fusion n'en crée jamais. | Créez-la sur le parent avec vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La branche a supprimé la table. Une fusion n'en supprime jamais. | Supprimez-la avec vos migrations. |
| `TABLE_REWRITTEN` | — | L'un des côtés a réécrit toutes les lignes de la table après la création de la branche — changement de type de colonne, `ADD COLUMN` avec valeur par défaut volatile, `VACUUM FULL`, `CLUSTER` — de sorte que chaque ligne apparaît comme modifiée depuis, empêchant d'identifier quel côté a changé quelle ligne. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après celle-ci. |
| `TOO_LARGE` | — | La table contient sur un côté plus de lignes qu'un diff ne peut en comparer individuellement (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` à la fois sur le diff et la fusion, ou déplacez les lignes par un autre moyen. |

## Codes génériques

Une route utilise l'un de ces codes lorsque rien de plus spécifique ne s'applique.

| Code | Statut | Signification | Que faire |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Requête malformée, sans code plus spécifique applicable. | Voir le message. |
| `UNAUTHORIZED` | 401 | Non authentifié, ou identifiant rejeté. | Connectez-vous ou actualisez le jeton. |
| `FORBIDDEN` | 403 | Authentifié, mais non autorisé. | Réessayer avec la même identité ne servira à rien. |
| `CONFLICT` | 409 | Conflit avec l'état existant. | Voir le message. |
| `INTERNAL_ERROR` | 500 | Une erreur est survenue sur le serveur. Le message est délibérément générique. | Mentionnez le `requestId` ; la cause se trouve dans les logs. |
| `NOT_CONFIGURED` | 503 | Une dépendance requise par cette route n'est pas configurée sur ce serveur. | Voir le message. |
| `SERVICE_UNAVAILABLE` | 503 | Un service dont dépend la requête n'a pas pu être joint : bucket S3 ou MinIO, ou hôte appelé via `fetch()` par une fonction qui refuse la connexion ou ne se résout pas. Le journal du serveur nomme l'hôte ; la réponse ne le nomme pas. Une base de données inaccessible renvoie `DATABASE_UNAVAILABLE`. Une tentative de connexion infructueuse vers un tel service renvoie ce code. | Réessayez ; consultez les logs. |

## Maintenir cette page à jour

`pnpm verify:docs` échoue lorsqu'un code que le serveur peut renvoyer est absent de ces
tableaux, lorsqu'un tableau liste un code que rien ne peut déclencher, lorsque les statuts d'une ligne ne sont pas
exactement ceux avec lesquels le code source le déclenche, ou lorsqu'une famille de codes comme `PG_<SQLSTATE>` ne possède pas de ligne
pour un SQLSTATE rencontré par les appelants. L'étape correspondante est
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Elle commence par s'autovérifier. L'analyse extrait les codes directement de TypeScript plutôt que depuis
un serveur en cours d'exécution, de sorte que ses angles morts sont silencieux par construction : il lui est arrivé
de ne pas voir un code transmis par un wrapper d'une ligne, ou un code écrit après un message
contenant une parenthèse `)`, et de signaler que « chaque code que le serveur peut déclencher est documenté »
sur une page où il en manquait dix-sept. Cette étape exécute donc un jeu d'essai contenant précisément
ces cas de figure avant de lire cette page, et refuse de produire un résultat si elle
ne parvient pas à les détecter.
