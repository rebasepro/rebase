Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. Le code est l'élément sur lequel baser vos branchements conditionnels : le message est rédigé pour un humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, alors que le code n'est ni l'un ni l'autre.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par l'humain. Pour une erreur `4xx`, il s'agit du propre message du serveur ; pour une `5xx`, il est délibérément générique, car le texte sous-jacent peut citer un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable d'une version mineure à l'autre.
- **`details`** — optionnel et jamais garanti. Voir les règles ci-dessous.
- **`requestId`** — présent dès lors que la requête a traversé le middleware de request-ID, c'est-à-dire chaque route sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un identifiant : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, sinon un identifiant tout neuf. Il est renvoyé en écho dans la réponse sous la forme `X-Request-ID`, inclus dans l'enveloppe d'erreur sous `requestId`, et attaché à la ligne de log du serveur pour cette requête.

C'est la clé de jointure. Mentionnez-le dans un rapport de bogue et un opérateur pourra retrouver l'unique ligne de journal expliquant l'échec, révélant la raison qui n'a jamais été montrée au client.

Envoyer le vôtre permet à une trace de survivre à un saut (hop) : une passerelle ou un exécuteur de tâches qui transmet l'en-tête conserve un identifiant unique à travers chaque service ayant traité la requête. Une valeur invalide est ignorée plutôt que rejetée — un en-tête malformé provenant d'un appelant ne mérite pas de faire échouer une requête — ne présumez donc pas que l'identifiant envoyé est celui que vous avez reçu. Lisez l'en-tête de réponse.

### Ce que contient `details`

`details` a une valeur diagnostique, non contractuelle. Trois règles l'encadrent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des erreurs propres à l'appelant décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas modifiable, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont purgés en production.** Lorsque l'échec provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il désigne la classe du problème et ne révèle rien sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y intègre le contenu des lignes. `23505` rapporte `Key (email)=(a@b.c) already exists.`, ce qui répond à la question « cette personne est-elle inscrite ? » pour n'importe quelle adresse qu'un tiers voudrait tester.
3. **Ne basez jamais vos branchements conditionnels sur `details`.** Basez-vous sur `code`. Le contenu de `details` correspond simplement à ce qui était utile à un humain à cet endroit du code, et cela peut changer.

## Interpréter un statut

| Statut | Ce qu'il indique sur la requête |
| --- | --- |
| `400` | Malformée, ou demandant quelque chose qui n'existe pas dans le schéma. Corrigez la requête. |
| `401` | Non authentifié, ou l'identifiant a expiré. Connectez-vous ou actualisez le jeton. |
| `403` | Authentifié, mais non autorisé. Réessayer avec la même identité n'aidera pas. |
| `404` | Route, collection ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Conflit avec l'état existant : un doublon ou une écriture concurrente. |
| `413` `415` `422` | Corps trop volumineux, mauvais type de média ou rejet sémantique. |
| `429` | Limite de débit atteinte (rate limit). Ralentissez ; le message indique pendant combien de temps. |
| `500` | Le serveur ou sa base de données est en faute, pas l'appelant. Consultez les logs. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — fonctionnalité désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était inaccessible, non configurée ou trop lente. |

| `IDENTITY_ALREADY_LINKED` | 409 | Cette identité OAuth appartient à un autre compte. | Connectez-vous avec celle-ci, ou dissociez-la d'abord de l'autre compte. |
| `IMPERSONATION_FORBIDDEN` | 403 | Une requête a envoyé `x-rebase-impersonate` et son appelant n'est pas autorisé à agir au nom d'un autre utilisateur. | `IMPERSONATION_INVALID` | 400 | `x-rebase-impersonate` a été envoyé vide. | Envoyez l'uid de l'utilisateur à usurper, ou omettez l'en-tête. |
| `IMPERSONATION_TARGET_NOT_FOUND` | 404 | `x-rebase-impersonate` ne désigne aucun utilisateur actif : aucun compte ne possède cet uid, ou il est désactivé. | Vérifiez l'uid. |

| `IMPERSONATION_UNSUPPORTED` | 400 | `x-rebase-impersonate` a été envoyé à une route qui ne peut pas s'exécuter sous une autre identité. | `SIMULATION_READ_ONLY` | 403 | Une écriture, suppression, `_batch`, retour en arrière d'historique ou une fonction personnalisée appelée par un verbe autre que `GET`/`HEAD`/`OPTIONS` comportait un en-tête `x-rebase-simulate-*`. | `SIMULATION_UNSUPPORTED` | 400 | Un en-tête `x-rebase-simulate-*` a été envoyé à une route qui ne peut pas s'exécuter avec un accès simulé. Seules l'API de données et les fonctions personnalisées les prennent en compte. | Envoyez la requête sans les en-têtes. |
| `GUEST_REFERENCED` | 409 | Un invité n'a pas pu être supprimé car une ligne propre au projet l'exige, via une clé étrangère avec `ON DELETE RESTRICT` ou `NO ACTION`. `DELETE /api/admin/guests` le signale pour chaque invité dans `skipped` et poursuit son exécution. | Supprimez la ligne, ou conservez l'invité. |
| `INVALID_ACCOUNT` | 400 | Le compte est dans un état qui ne permet pas cette opération. | Consultez le message. |
| `INVALID_CHALLENGE` | 400 | Le défi MFA est inconnu ou expiré. | Démarrez-en un nouveau. |
| `INVALID_CODE` | 400 / 401 | Le code OTP ou MFA est incorrect : 400 pour la connexion par code reçu par e-mail (`/auth/otp/verify`), 401 pour un enrôlement ou un défi MFA. | Réessayez avec le code actuel. |
| `INVALID_CREDENTIALS` | 401 | Mauvaise adresse e-mail ou mauvais mot de passe — sans préciser lequel, délibérément. | Réessayez ou réinitialisez le mot de passe. |
| `INVALID_PLATFORM_TOKEN` | 401 | Un jeton de plateforme `rpt_` a été refusé : signature invalide, mauvaise audience, expiré, ou durée de vie dépassant le plafond. Le message précise la cause. | Demandez à la plateforme d'en émettre un nouveau — sur Rebase Cloud, réexécutez la commande. |
| `INVALID_SCOPES` | 400 | Une clé a demandé quelque chose qui n'est pas une portée (scope) : malformée, inconnue, ou avec une cible non prise en charge par la portée. `details.problems` indique quoi et pourquoi ; `details.validScopes` liste les portées qu'une clé peut détenir. | `INVALID_TOKEN` | 400 / 401 | Un jeton de vérification, de réinitialisation, de magic-link ou de changement d'adresse est malformé, inconnu, consommé ou expiré (400). ## `PG_<SQLSTATE>` — une contrainte refusée par la base de données

Une écriture rejetée par Postgres pour une raison liée aux *données de l'appelant* renvoie le SQLSTATE dans le code : `PG_23505`, `PG_23503`, et ainsi de suite. Il s'agit d'une famille de codes, pas d'une liste exhaustive — Postgres définissant des centaines de SQLSTATE — mais seules deux classes parviennent jusqu'ici, car seules ces deux-là relèvent de la responsabilité de l'appelant :

- **classe 23**, violation de contrainte d'intégrité : un doublon, une clé étrangère pointant dans le vide, une colonne NOT NULL laissée vide ;
- **classe 22**, exception sur les données : une valeur que le type de la colonne ne peut pas contenir.

Tout le reste — connexion interrompue, colonne manquante, problème de privilèges — relève du serveur et demeure une `500`. Dès lors, `code.startsWith("PG_")` constitue un test fiable pour déterminer si « la ligne envoyée était incorrecte », et les quatre codes ci-dessous sont ceux qu'un client rencontre concrètement. `details.dbCode` transporte le même SQLSTATE pour chacun d'entre eux, et le message nomme la contrainte.

| Code | Statut | Signification | Action à mener |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Une valeur n'a pas pu être interprétée dans le type de la colonne — le pendant côté écriture de `INVALID_FILTER_VALUE`. | Envoyez une valeur correspondant au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` a été laissée vide. | Envoyez le champ, ou attribuez une valeur par défaut à la colonne. |
| `PG_23503` | 400 / 409 | Lors d'un enregistrement, une clé étrangère pointe vers une ligne inexistante (400). Lors d'une suppression, d'autres lignes référencent encore celle-ci (409 ; une clé en `RESTRICT` lève `PG_23001`, également une 409). | Créez d'abord la ligne cible, ou corrigez l'identifiant ; pour une suppression, supprimez ou redirigez d'abord les lignes qui la référencent. |
| `PG_23505` | 409 | Une contrainte d'unicité a été enfreinte. Le message nomme la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

### Réconciliation de schéma

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) planifie
via `POST /api/admin/schema/reconcile/plan` et applique via
`/reconcile/apply`. Un refus ne modifie rien ; seul `SCHEMA_RECONCILE_FAILED`
laisse une portion de plan appliquée.

| Code | Statut | Signification | Action à mener |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | Le corps n'est pas un objet JSON, ou `drop` n'est pas une liste de chaînes au format `"<collection>.<column>"`. | Envoyez `{ "drop": ["voice_cache.wav"] }`, ou omettez `drop`. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Une instruction a échoué en cours de route. Les instructions précédentes ont été exécutées et restent appliquées ; `details.applied` les liste. | Corrigez ce que le message indique, puis replanifiez : le nouveau plan omettra ce qui a déjà été appliqué. |
| `SCHEMA_RECONCILE_INVALID` | 400 | Le plan ne peut pas être appliqué, et le message liste pourquoi : un `drop` qui n'est pas sous la forme `<collection>.<column>`, ne désigne aucune collection ou colonne, ou désigne une colonne que la collection déclare toujours. `details.plan` contient le plan. | Corrigez la liste `drop`. Une colonne déclarée est supprimée en retirant sa propriété, en déployant, puis en procédant à la réconciliation. |
| `SCHEMA_RECONCILE_STALE` | 409 | La base de données ou les collections ont changé depuis le plan que vous aviez confirmé. `details.plan` contient le nouveau plan. | Examinez le nouveau plan et confirmez son `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | `/reconcile/apply` n'a reçu aucun champ `confirm`. | Planifiez d'abord et transmettez le `digest` du plan en tant que `confirm`. La CLI s'en charge dès que vous saisissez `yes`. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | Le pilote de ce backend ne peut pas planifier de réconciliation, ou ne peut pas exécuter de SQL. | La réconciliation fonctionne sur Postgres. |

### Pourquoi la table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` énumère chaque table refusée dans `details.tables`, avec l'un
de ces codes. Le même code apparaît sur la propriété `blocked` de la table dans le diff lui-même,
ce qui permet au Studio de le signaler avant que quiconque ne clique sur **Merge**. Aucun ne constitue une réponse HTTP autonome.

| Code | Statut | Signification | Action à mener |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table diffèrent entre la branche et son parent. Les lignes sont comparées sur la base des colonnes qu'elles ont en commun. | Ajoutez les colonnes manquantes au parent via vos migrations (`rebase db push`), puis fusionnez. Une migration qui réécrit la table — modification de type de colonne — transforme cela en `TABLE_REWRITTEN` : fusionnez avant une telle opération, ou recréez la branche après celle-ci. |
| `NO_PRIMARY_KEY` | — | La table n'a pas de clé primaire, les lignes ne peuvent donc pas être appariées une à une ; le diff n'indique que le nombre de lignes. | Définissez une clé primaire sur la table, ou déplacez ses lignes à la main. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes de la clé primaire, ou leurs types, diffèrent entre les deux. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La branche a créé la table. Une fusion ne crée jamais de table. | Créez-la sur le parent via vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La branche a supprimé la table. Une fusion ne supprime jamais de table. | Supprimez-la via vos migrations. |
| `TABLE_REWRITTEN` | — | L'un des côtés a réécrit l'intégralité des lignes de la table après la création de la branche — changement de type de colonne, `ADD COLUMN` avec une valeur par défaut volatile, `VACUUM FULL`, `CLUSTER` — chaque ligne apparaît donc comme modifiée depuis lors, rendant impossible de déterminer qui a modifié quelle ligne. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après celle-ci. |
| `TOO_LARGE` | — | La table contient plus de lignes sur un côté que ce qu'un diff peut comparer ligne par ligne (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` à la fois pour le diff et pour la fusion, ou déplacez les lignes d'une autre façon. |

## Codes génériques

Une route utilise l'un de ceux-ci lorsqu'aucun code plus précis ne s'applique.

| Code | Statut | Signification | Action à mener |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Malformée, et rien de plus spécifique ne s'applique. | Consultez le message. |
| `UNAUTHORIZED` | 401 | Non authentifié, ou l'identifiant a été rejeté. | Connectez-vous ou actualisez le jeton. |
| `FORBIDDEN` | 403 | Authentifié, mais non autorisé. | Réessayer avec la même identité ne servira à rien. |
| `CONFLICT` | 409 | Conflit avec l'état existant. | Consultez le message. |
| `INTERNAL_ERROR` | 500 | Un problème est survenu sur le serveur. Le message est délibérément générique. | Citez le `requestId` ; la cause détaillée se trouve dans les logs. |
| `NOT_CONFIGURED` | 503 | Une dépendance requise par cette route n'est pas configurée sur ce serveur. | Consultez le message. |
| `SERVICE_UNAVAILABLE` | 503 | Un service dont dépend la requête n'a pas pu être joint : un bucket S3 ou MinIO, ou un hôte qu'une fonction `fetch()` et qui refuse la connexion ou ne se résout pas. Le log du serveur indique le nom d'hôte ; la réponse HTTP ne le précise pas. Une base de données inaccessible renvoie `DATABASE_UNAVAILABLE`. Une tentative de connexion échouée vers un tel service renvoie ceci. | Réessayez ; consultez les logs. |

## Maintenir l'exactitude de cette page

`pnpm verify:docs` échoue si un code que le serveur peut émettre est absent de ces
tableaux, si un tableau liste un code que rien ne peut émettre, si les statuts d'une ligne ne sont pas
exactement ceux avec lesquels la source émet le code, ou lorsqu'une famille de codes comme `PG_<SQLSTATE>` ne comporte aucune ligne
pour un SQLSTATE que les appelants rencontrent. L'étape est gérée par
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Elle commence par s'autovérifier. L'analyse extrait les codes directement depuis TypeScript plutôt que depuis
un serveur en cours d'exécution, ses angles morts sont donc invisibles par conception : il lui est arrivé autrefois
de ne pas voir un code encapsulé dans un wrapper d'une ligne, ou placé après un message
contenant une `)`, et d'affirmer « tous les codes que le serveur peut émettre sont documentés »
sur une page à laquelle il en manquait dix-sept. Désormais, l'étape exécute un test de référence présentant précisément
ces structures avant de lire cette page, et refuse de rendre le moindre rapport si elle ne parvient pas à les détecter.
