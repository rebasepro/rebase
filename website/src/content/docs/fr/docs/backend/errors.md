Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. Le code est l'élément sur lequel baser vos branchements conditionnels : le message est rédigé pour un être humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, tandis que le code n'est ni l'un ni l'autre.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par un humain. Pour une `4xx`, il s'agit du propre message du serveur ; pour une `5xx`, il est délibérément générique, car le texte sous-jacent peut citer un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable à travers les versions mineures.
- **`details`** — facultatif, et jamais garanti. Voir les règles ci-dessous.
- **`requestId`** — présent dès lors que la requête est passée par le middleware de request-ID, ce qui est le cas de chaque route sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un identifiant : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, ou un nouvel identifiant dans le cas contraire. Il est renvoyé dans la réponse sous la forme `X-Request-ID`, inclus dans l'enveloppe d'erreur sous `requestId`, et rattaché à la ligne de log du serveur pour cette requête.

C'est la clé de jointure. Mentionnez-la dans un rapport de bug et un opérateur pourra retrouver l'unique ligne de log qui explique l'échec, contenant la raison qui n'a jamais été montrée au client.

Envoyer votre propre identifiant permet à une trace de survivre à un saut : une passerelle ou un exécuteur de tâches qui transmet l'en-tête conserve le même ID à travers chaque service ayant traité la requête. Une valeur invalide est ignorée plutôt que rejetée — un en-tête mal formé de la part d'un appelant ne mérite pas de faire échouer une requête — ne présumez donc pas que l'ID envoyé est l'ID obtenu. Lisez l'en-tête de réponse.

### Ce que contient `details`

`details` a une vocation diagnostique, pas contractuelle. Trois règles le régissent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des propres erreurs de l'appelant décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas accessible en écriture, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont tronqués en production.** Lorsque l'échec provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il désigne la catégorie du problème et ne révèle rien sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y insère le contenu des lignes. `23505` renvoie `Key (email)=(a@b.c) already exists.`, ce qui répond à « cette personne est-elle inscrite ? » pour n'importe quelle adresse testée.
3. **Ne faites jamais de branchement conditionnel sur `details`.** Basez-vous sur `code`. Ce qui se trouve sous `details` correspond à ce qui était utile pour un humain à cet endroit du code, et cela peut changer.

## Comprendre un statut

| Statut | Ce que cela indique sur la requête |
| --- | --- |
| `400` | Mal formée, ou demandant quelque chose qui n'existe pas dans le schéma. Corrigez la requête. |
| `401` | Non authentifiée, ou l'identifiant a expiré. Connectez-vous ou actualisez la session. |
| `403` | Authentifiée, mais non autorisée. Réessayer avec la même identité ne servira à rien. |
| `404` | Route, table ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Un conflit avec l'état existant : un doublon, ou une écriture concurrente. |
| `413` `415` `422` | Le corps est trop volumineux, le type de média est incorrect, ou rejeté sémantiquement. |
| `429` | Limite de débit atteinte (rate limit). Patientez ; le message indique pendant combien de temps. |
| `500` | Le problème vient du serveur ou de sa base de données, pas de l'appelant. Consultez les logs. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — une fonctionnalité désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était inaccessible, non configurée ou trop lente. |

## `PG_<SQLSTATE>` — une contrainte refusée par la base de données

Une écriture rejetée par Postgres pour une raison liée aux *données de l'appelant* renvoie le SQLSTATE dans le code : `PG_23505`, `PG_23503`, etc. C'est une famille et non une liste figée — Postgres définissant des centaines de SQLSTATE — mais seules deux classes y parviennent, car seules ces deux-là relèvent de la responsabilité de l'appelant :

- **classe 23**, violation de contrainte d'intégrité : un doublon, une clé étrangère pointant vers le vide, une colonne NOT NULL laissée vide ;
- **classe 22**, exception sur les données : une valeur hors limites pour le type de la colonne.

Tout le reste — coupure de connexion, colonne manquante, défaut de privilèges — relève du serveur et conserve un statut `500`. Le test `code.startsWith("PG_")` permet ainsi de vérifier de façon sûre si « la ligne transmise était invalide » ; les quatre codes ci-dessous sont ceux qu'un client rencontre concrètement. `details.dbCode` contient le même SQLSTATE pour chacun d'eux, et le message cite la contrainte incriminée.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Une valeur n'a pas pu être interprétée dans le type de la colonne — le pendant côté écriture de `INVALID_FILTER_VALUE`. | Envoyez une valeur conforme au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` est restée vide. | Transmettez le champ, ou attribuez une valeur par défaut à la colonne. |
| `PG_23503` | 400 / 409 | À l'enregistrement, une clé étrangère pointe vers une ligne inexistante (400). À la suppression, d'autres lignes référencent toujours celle-ci (409 ; une clé `RESTRICT` lève `PG_23001`, également 409). | Créez d'abord la ligne cible, ou corrigez l'identifiant ; pour une suppression, supprimez ou réorientez d'abord les lignes qui la référencent. |
| `PG_23505` | 409 | Une contrainte d'unicité a été enfreinte. Le message nomme la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

## Interfaces d'administration et modification de schéma

Ces erreurs indiquent qu'une fonctionnalité est désactivée ou non configurée, et non que la requête était erronée. Chacune est également renvoyée sur la route `/status` correspondante avec un statut `200`, afin qu'un panneau d'administration puisse griser la fonctionnalité au lieu d'afficher une erreur.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `ADMIN_SURFACE_UNAVAILABLE` | 501 | Une interface réservée aux administrateurs a été appelée sur un serveur sans authentification configurée ; rien ne permet de distinguer un administrateur d'un inconnu. | Configurez `auth.jwtSecret`, ou passez un `AuthAdapter`. |
| `BRANCH_DIFF_STALE` | 409 | `POST /api/admin/branches/:name/merge` a reçu l'empreinte (fingerprint) d'un diff qui n'est plus valable : la branche ou son parent a changé entre-temps. Rien n'a été écrit. | Relisez le diff, examinez-le, et fusionnez avec sa nouvelle `fingerprint`. |
| `BRANCH_DIFF_UNSUPPORTED` | 501 | La source de données ne peut pas comparer les branches : pas de support SQL, ou pas de gestion des branches (pas de connexion d'administration). | Utilisez un backend Postgres avec `adminConnectionString` défini. |
| `BRANCH_MERGE_BLOCKED` | 409 | Une table présentant des différences ne peut pas être fusionnée — ajoutée ou supprimée par la branche, colonnes ou clé primaire divergentes, absence de clé primaire, trop de lignes à comparer, ou réécrite depuis la création de la branche (`TABLE_REWRITTEN`). Une table dont les lignes n'ont pas pu être comparées bloque la fusion même si ses décomptes indiquent 0 : ils sont inconnus, pas nuls. `details.tables` cite chaque table concernée avec la raison. Rien n'a été écrit. | Appliquez d'abord le schéma avec vos migrations, ou fusionnez avec `skipBlocked: true` pour ignorer ces tables. |
| `BRANCH_MERGE_CONFLICT` | 409 | Des lignes ont été modifiées à la fois sur la branche et sur son parent, et `onConflict` était positionné à `"abort"` (par défaut) ; ou le parent a refusé une partie de la fusion — ligne modifiée entre-temps, trigger l'ayant ignorée, politique l'ayant masquée. Rien n'a été écrit. | Choisissez le côté prioritaire avec `onConflict: "branch"` ou `"target"`, ou relisez le diff. |
| `BRANCH_MERGE_FAILED` | 409 | Le parent a rejeté les lignes de la branche au sein de l'instruction de fusion — une contrainte, une valeur d'enum ou une clé étrangère qu'il applique et que les lignes de la branche enfreignent, généralement parce que les deux schémas divergent. `details` contient `sqlState`, `table`, `constraint` et `detail`. Rien n'a été écrit. | Consultez les modifications de schéma dans le diff, alignez le schéma du parent via vos migrations, ou corrigez les lignes de la branche, puis relancez la fusion. |
| `BRANCH_NOT_FOUND` | 404 | Aucune branche ne porte ce nom dans le registre. | `rebase db branch list`, ou le panneau Branches, liste celles qui existent. |
| `CONTRACT_UNAVAILABLE` | 404 | Le contrat du projet n'est servi que lorsque l'authentification est configurée — il décrit l'intégralité des tables et relations. | Configurez l'authentification. `/meta/schema-version` est toujours servi. |
| `DEV_MAILBOX_UNAVAILABLE` | 501 | Aucune boîte aux lettres de développement n'est active. Les e-mails ne sont capturés que si `SMTP_HOST` n'est pas défini et que `NODE_ENV` n'est pas en production. | Supprimez `SMTP_HOST` en développement, ou consultez la véritable boîte de réception. |
| `DOCS_UNAVAILABLE` | 404 | `GET /api/docs` est servi aux appelants auxquels `GET /api/schema/tables` décrit les tables ; ce serveur n'ayant pas d'authentification configurée, il n'y a personne à qui les décrire. | Configurez l'authentification, ou publiez l'intégralité de la documentation pour tous avec `enableSwagger: true` (`REBASE_ENABLE_SWAGGER=true`). |
| `INVALID_CHANGE` | 400 | La modification de schéma proposée n'est pas bien formée. | Consultez le message. |
| `SCHEMA_CHANGE_FAILED` | 400 | L'application d'un changement de schéma planifié a échoué pour une raison non couverte par des codes plus spécifiques. | Consultez le message ; il contient textuellement l'échec sous-jacent. |
| `SCHEMA_CHANGE_UNAPPLICABLE` | 400 | La modification est valide mais ne peut pas être appliquée au schéma en l'état. | Consultez le message. |
| `SCHEMA_EDIT_DIRTY_TREE` | 409 | Le dépôt contient des modifications non commitées ; l'édition n'a donc pas pu être appliquée en toute sécurité. | Committez ou utilisez stash, puis réessayez. |
| `SCHEMA_EDIT_REFUSED` | 400 | L'éditeur de schéma a refusé la modification : ce qu'il devrait modifier est écrit dans un code qu'il ne réécrit pas (un spread, un helper, une clé calculée), ou la modification fait partie de celles qu'il ne réalise jamais (renommer une table, supprimer la dernière règle). `details.problems` énumère chaque point. Rien n'a été écrit. | Consultez le message. Effectuez la modification manuellement dans `backend/schema`. |
| `SCHEMA_EDIT_DOES_NOT_COMPILE` | 400 | La modification peut être effectuée, mais le schéma résultant ne compilerait pas — relation vers une table supprimée, règle ciblant une colonne retirée. `details.problems` détaille les erreurs du compilateur, chacune avec sa table et sa colonne. ### Réconciliation de schéma

[`rebase schema reconcile`](/docs/cli/schema/#rebase-schema-reconcile) planifie via `POST /api/admin/schema/reconcile/plan` et applique via `/reconcile/apply`. Un refus ne modifie rien ; seul `SCHEMA_RECONCILE_FAILED` laisse une partie d'un plan appliquée.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `INVALID_RECONCILE` | 400 | Le corps n'est pas un objet JSON, ou `drop` n'est pas une liste de chaînes `"<table>.<column>"`. | Envoyez `{ "drop": ["voice_cache.wav"] }`, ou omettez `drop`. |
| `SCHEMA_RECONCILE_FAILED` | 400 | Une instruction a échoué en cours de traitement. Les instructions qui la précédaient ont été exécutées et restent appliquées ; `details.applied` les énumère. | Corrigez ce que le message indique, puis replanifiez : le nouveau plan ignorera ce qui a déjà été appliqué. |
| `SCHEMA_RECONCILE_INVALID` | 400 | Le plan ne peut pas être appliqué, et le message en énumère les raisons : un `drop` qui n'est pas sous la forme `<table>.<column>`, ne cite aucune table ou colonne, ou désigne une colonne toujours déclarée par la table. `details.plan` contient le plan. | Corrigez la liste `drop`. Pour supprimer une colonne déclarée, retirez-la de son `defineTable`, déployez, puis lancez la réconciliation. |
| `SCHEMA_RECONCILE_STALE` | 409 | La base de données ou les tables ont changé depuis le plan que vous avez confirmé. `details.plan` contient le nouveau plan. | Examinez le nouveau plan et confirmez son `digest`. |
| `SCHEMA_RECONCILE_UNCONFIRMED` | 400 | `/reconcile/apply` a été appelé sans `confirm`. | Planifiez d'abord et transmettez le `digest` du plan dans `confirm`. La CLI effectue cette étape lorsque vous tapez `yes`. |
| `SCHEMA_RECONCILE_UNSUPPORTED` | 503 | Le pilote de ce backend ne peut pas planifier de réconciliation, ou ne peut pas exécuter de SQL. | La réconciliation fonctionne sur Postgres. |

### Pourquoi la table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` énumère chaque table refusée dans `details.tables`, avec l'un de ces codes. Ce même code figure dans la propriété `blocked` de la table au sein du diff lui-même, ce qui permet à Studio de l'indiquer avant que quiconque ne clique sur **Merge**. Aucun d'eux ne constitue une réponse HTTP indépendante.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table diffèrent entre la branche et son parent. Les lignes sont comparées sur la base des colonnes communes. | Ajoutez les colonnes manquantes au parent avec vos migrations (`rebase db push`), puis fusionnez. Une migration réécrivant la table — modification du type d'une colonne — transforme l'état en `TABLE_REWRITTEN` : fusionnez avant une telle opération, ou recréez la branche après. |
| `NO_PRIMARY_KEY` | — | La table n'a pas de clé primaire, les lignes ne peuvent donc pas être comparées une à une ; le diff ne fournit que ses volumes de lignes. | Attribuez une clé primaire à la table, ou déplacez ses lignes manuellement. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes composant la clé primaire, ou leurs types, diffèrent entre les deux. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La branche a créé la table. Une fusion ne crée jamais de table. | Créez-la sur le parent à l'aide de vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La branche a supprimé la table. Une fusion ne supprime jamais de table. | Supprimez-la via vos migrations. |
| `TABLE_REWRITTEN` | — | L'un des côtés a réécrit intégralement chaque ligne de la table après la création de la branche — modification du type d'une colonne, `ADD COLUMN` avec une valeur par défaut volatile, `VACUUM FULL`, `CLUSTER` — de sorte que chaque ligne apparaît comme modifiée depuis, rendant impossible l'identification du côté ayant modifié chaque ligne. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après coup. |
| `TOO_LARGE` | — | La table contient plus de lignes d'un côté que ce qu'un diff compare élément par élément (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` pour le diff et la fusion, ou déplacez les lignes par un autre moyen. |

## Codes génériques

Une route utilise l'un de ces codes lorsqu'aucun autre plus spécifique ne s'applique.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Mal formée, et aucun code plus spécifique ne s'applique. | Consultez le message. |
| `UNAUTHORIZED` | 401 | Non authentifiée, ou identifiant rejeté. | Connectez-vous ou actualisez la session. |
| `FORBIDDEN` | 403 | Authentifiée, mais non autorisée. | Réessayer avec la même identité ne changera rien. |
| `CONFLICT` | 409 | Conflit avec l'état existant. | Consultez le message. |
| `INTERNAL_ERROR` | 500 | Un problème interne est survenu sur le serveur. Le message est délibérément générique. | Mentionnez le `requestId` ; la raison figure dans les logs. |
| `NOT_CONFIGURED` | 503 | Une dépendance requise par cette route n'est pas configurée sur ce serveur. | Consultez le message. |
| `SERVICE_UNAVAILABLE` | 503 | Un service tiers dont dépend la requête n'a pas pu être joint : bucket S3 ou MinIO, ou hôte contacté par `fetch()` dans une fonction qui refuse la connexion ou ne se résout pas. Les logs du serveur citent l'hôte ; la réponse HTTP ne le fait pas. Une base inaccessible renvoie `DATABASE_UNAVAILABLE`. Une tentative de connexion infructueuse vers un tel service renvoie ce code. | Réessayez ; consultez les logs. |

## Garantir l'exactitude de cette page

`pnpm verify:docs` échoue lorsqu'un code que le serveur peut renvoyer est absent de ces tableaux, lorsqu'un tableau liste un code que rien ne peut émettre, lorsque les statuts d'une ligne ne correspondent pas exactement à ceux avec lesquels le code source le déclenche, ou lorsqu'une famille de codes comme `PG_<SQLSTATE>` ne comporte aucune ligne pour un SQLSTATE rencontré par les appelants. L'étape est assurée par `tooling/scripts/docs-verify/check-error-codes.mjs`.

Le script commence par s'auto-tester. L'analyse extrait les codes directement depuis TypeScript plutôt que depuis un serveur en cours d'exécution ; ses angles morts sont donc silencieux par nature : il ne voyait pas autrefois un code transmis via un wrapper d'une ligne, ni un code écrit après un message contenant un `)`, et concluait que « chaque code que le serveur peut renvoyer est documenté » sur une page où il en manquait dix-sept. Désormais, l'étape exécute un fixture reproduisant exactement ces structures avant de lire cette page, et refuse de valider quoi que ce soit si elle ne parvient pas à les détecter.
