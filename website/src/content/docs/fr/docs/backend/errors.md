Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. Le code est l'élément sur lequel baser votre logique conditionnelle : le message est rédigé pour un être humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, alors que le code n'est ni l'un ni l'autre.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par un être humain. Pour un `4xx`, il s'agit du propre message du serveur ; pour un `5xx`, il est délibérément générique, car le texte sous-jacent peut citer un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable d'une version mineure à l'autre.
- **`details`** — facultatif, et jamais garanti. Voir les règles ci-dessous.
- **`requestId`** — présent chaque fois que la requête est passée par le middleware d'ID de requête, c'est-à-dire toutes les routes sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un ID : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, ou un nouvel identifiant sinon. Il est renvoyé en écho dans la réponse sous la forme `X-Request-ID`, inclus dans l'enveloppe d'erreur en tant que `requestId`, et associé à la ligne de journal du serveur pour cette requête.

C'est la clé de jointure. Citez-la dans un rapport de bug et un opérateur pourra retrouver l'unique ligne de journal qui explique l'échec, contenant la raison qui n'a jamais été montrée au client.

Envoyer votre propre identifiant permet à une trace de survivre à un saut intermédiaire : une passerelle ou un exécuteur de tâches qui transmet l'en-tête conserve un ID unique à travers chaque service ayant traité la requête. Une valeur non valide est ignorée plutôt que rejetée — un en-tête malformé provenant d'un appelant ne justifie pas de faire échouer une requête — ne supposez donc pas que l'ID que vous avez envoyé est l'ID que vous avez reçu. Lisez l'en-tête de réponse.

### Que contient `details`

`details` a une vocation diagnostique et non contractuelle. Trois règles le régissent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des propres erreurs de l'appelant décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas accessible en écriture, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont tronqués en production.** Lorsque l'échec provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il indique la classe du problème et ne révèle rien sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y inclut le contenu des lignes. `23505` rapporte `Key (email)=(a@b.c) already exists.`, ce qui répond à « cette personne est-elle inscrite ? » pour n'importe quelle adresse que quelqu'un souhaiterait tester.
3. **Ne basez jamais votre logique conditionnelle sur `details`.** Basez-la sur `code`. Ce qui se trouve sous `details` correspond à ce qui était utile à un développeur à cet endroit de l'appel, et cela change.

## Interpréter un statut

| Statut | Ce qu'il indique sur la requête |
| --- | --- |
| `400` | Malformée, ou demandant quelque chose qui n'existe pas dans le schéma. Corrigez la requête. |
| `401` | Non authentifié, ou identifiant expiré. Connectez-vous ou actualisez le jeton. |
| `403` | Authentifié, mais non autorisé. Réessayer avec la même identité n'aidera pas. |
| `404` | Route, table ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Un conflit avec l'état existant : un doublon ou une écriture concurrente. |
| `413` `415` `422` | Le corps est trop volumineux, le type de média est incorrect, ou la requête est sémantiquement rejetée. |
| `429` | Limite de débit atteinte. Ralentissez ; le message indique pendant combien de temps. |
| `500` | Le serveur ou sa base de données est en faute, pas l'appelant. Consultez les logs. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — une fonctionnalité désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était inaccessible, non configurée ou trop lente. |

## `PG_<SQLSTATE>` — une contrainte refusée par la base de données

Une écriture rejetée par Postgres pour une raison liée aux *données de l'appelant* répond avec le SQLSTATE dans le code : `PG_23505`, `PG_23503`, et ainsi de suite. Il s'agit d'une famille de codes et non d'une liste exhaustive — Postgres définissant des centaines de SQLSTATE — mais seules deux classes lui parviennent, car seules ces deux-là relèvent de la responsabilité de l'appelant :

- **classe 23**, violation de contrainte d'intégrité : un doublon, une clé étrangère pointant vers le vide, une colonne NOT NULL laissée vide ;
- **classe 22**, exception de données : une valeur que le type de colonne ne peut pas contenir.

Tout le reste — une connexion interrompue, une colonne manquante, un problème de privilège — relève du serveur et reste un `500`. Ainsi, `code.startsWith("PG_")` constitue un test fiable pour déterminer si « la ligne envoyée était incorrecte », et les quatre ci-dessous sont ceux qu'un client rencontre concrètement. `details.dbCode` contient le même SQLSTATE pour chacun d'eux, et le message nomme la contrainte.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Une valeur n'a pas pu être lue dans le type de la colonne — le pendant côté écriture de `INVALID_FILTER_VALUE`. | Envoyez une valeur correspondant au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` a été laissée vide. | Envoyez le champ, ou attribuez une valeur par défaut à la colonne. |
| `PG_23503` | 400 / 409 | Lors d'un enregistrement, une clé étrangère pointe vers une ligne inexistante (400). Lors d'une suppression, d'autres lignes référencent encore celle-ci (409 ; une clé `RESTRICT` lève `PG_23001`, également 409). | Créez d'abord la ligne cible ou corrigez l'identifiant ; pour une suppression, supprimez ou redirigez d'abord les lignes qui y font référence. |
| `PG_23505` | 409 | Une contrainte d'unicité a été violée. Le message nomme la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

| `FUNCTIONS_UPSTREAM_UNREACHABLE` | 502 | Ce processus relaie les fonctions vers un autre processus qui n'a pas répondu. | Vérifiez que l'unité de fonctions est bien en cours d'exécution. |

Ces erreurs indiquent qu'une fonctionnalité est désactivée ou non configurée, plutôt que la requête était incorrecte. Chacune est également signalée sur la route `/status` correspondante avec un statut `200`, afin qu'un panneau d'administration puisse griser la fonctionnalité au lieu d'afficher une erreur.

### Pourquoi la table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` nomme chaque table refusée dans `details.tables`, avec l'un
de ces codes. Le même code apparaît sur l'attribut `blocked` de la table dans le diff lui-même,
afin que Studio puisse l'indiquer avant que quiconque n'appuie sur **Merge**. Aucun ne constitue une réponse
à part entière.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table diffèrent entre la branche et son parent. Les lignes sont comparées sur les colonnes qu'elles partagent. | Ajoutez les colonnes manquantes au parent avec vos migrations (`rebase db push`), puis fusionnez. Une migration qui réécrit la table — un changement de type de colonne — transforme cela en `TABLE_REWRITTEN` : fusionnez avant un tel changement, ou recréez la branche après. |
| `NO_PRIMARY_KEY` | — | La table n'a pas de clé primaire, les lignes ne peuvent donc pas être comparées une par une ; le diff n'indique que ses totaux de lignes. | Donnez une clé primaire à la table, ou déplacez ses lignes à la main. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes de la clé primaire, ou leurs types, diffèrent entre les deux. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La branche a créé la table. Une fusion n'en crée jamais. | Créez-la sur le parent avec vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La branche a supprimé la table. Une fusion n'en supprime jamais. | Supprimez-la avec vos migrations. |
| `TABLE_REWRITTEN` | — | L'un des côtés a réécrit chaque ligne de la table après la création de la branche — un changement de type de colonne, un `ADD COLUMN` avec une valeur par défaut volatile, un `VACUUM FULL`, un `CLUSTER` — de sorte que chaque ligne apparaît comme modifiée depuis, rendant impossible de savoir quel côté a modifié quelle ligne. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après celle-ci. |
| `TOO_LARGE` | — | La table contient plus de lignes sur un côté que ce qu'un diff peut comparer une à une (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` à la fois pour le diff et la fusion, ou transférez les lignes autrement. |

## Maintenir l'exactitude de cette page

`pnpm verify:docs` échoue lorsqu'un code que le serveur peut lever est absent de ces
tables, lorsqu'une table liste un code que rien ne peut lever, lorsque les statuts d'une ligne ne sont pas
exactement ceux avec lesquels le code source déclenche l'erreur, ou lorsqu'une famille de codes telle que `PG_<SQLSTATE>` ne comporte aucune ligne
pour un SQLSTATE rencontré par les appelants. Cette étape correspond à
`tooling/scripts/docs-verify/check-error-codes.mjs`.

Elle effectue d'abord une auto-vérification. L'analyse extrait les codes depuis TypeScript plutôt que depuis
un serveur en cours d'exécution, de sorte que ses angles morts sont silencieux par construction : il lui est arrivé de ne pas
voir un code passé à travers un wrapper d'une ligne, ou écrit après un message
contenant une `)`, et d'affirmer « tous les codes que le serveur peut lever sont documentés »
sur une page à laquelle il en manquait dix-sept. L'étape exécute donc un jeu de test reproduisant exactement
ces structures syntaxiques avant de lire cette page, et refuse de rendre un verdict si elle ne
parvient pas à les détecter.
