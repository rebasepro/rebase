Chaque échec renvoyé par un backend Rebase utilise une enveloppe unique et comporte un `code` stable. C'est sur ce code qu'il faut baser vos conditions : le message est rédigé pour un être humain et peut être reformulé, le statut est partagé par une douzaine de problèmes différents, alors que le code ne subit ni l'un ni l'autre.

## L'enveloppe

```json
{
  "error": {
    "message": "Schema drift: table \"posts\" does not exist.",
    "code": "SCHEMA_DRIFT",
    "details": { "dbCode": "42P01" },
    "requestId": "6f1b2f3e-8a0c-4d1b-9c3e-2a5b7c9d1e0f"
  }
}
```

- **`message`** — lisible par un être humain. Pour un `4xx`, il s'agit du propre message du serveur ; pour un `5xx`, il est délibérément générique, car le texte sous-jacent peut mentionner un hôte, un rôle ou un nom de colonne.
- **`code`** — l'une des valeurs ci-dessous. Stable d'une version mineure à l'autre.
- **`details`** — optionnel et jamais garanti. Voir les règles ci-dessous.
- **`requestId`** — présent chaque fois que la requête a traversé le middleware d'ID de requête, ce qui est le cas de chaque route sous `basePath`.

### `X-Request-ID`

Chaque requête sous `basePath` reçoit un identifiant : l'en-tête `X-Request-ID` de l'appelant lorsqu'il s'agit d'un UUID, sinon un nouvel identifiant généré pour l'occasion. Il est renvoyé en écho dans la réponse sous la forme `X-Request-ID`, inclus dans l'enveloppe d'erreur en tant que `requestId`, et attaché à la ligne de journalisation (log) du serveur pour cette requête.

Il s'agit de la clé de corrélation. Mentionnez-la dans un rapport de bogue et un opérateur pourra retrouver l'unique ligne de journal expliquant l'échec, contenant la raison qui n'a jamais été montrée au client.

Envoyer votre propre identifiant permet à une trace de survivre d'un saut à l'autre : une passerelle ou un exécuteur de tâches qui transfère l'en-tête conserve un ID unique à travers tous les services ayant traité la requête. Une valeur invalide est ignorée plutôt que rejetée — un en-tête malformé provenant d'un appelant ne justifie pas l'échec d'une requête — ne présumez donc pas que l'ID envoyé est l'ID reçu. Lisez l'en-tête de réponse.

### Ce que contient `details`

`details` a une vocation diagnostique, pas contractuelle. Trois règles le régissent :

1. **Tout ce qu'une route définit explicitement est toujours renvoyé.** Il s'agit des erreurs propres à l'appelant décrites avec précision : quel champ de filtre était inconnu, quelle relation n'est pas accessible en écriture, quelle valeur ne correspondait pas à son type.
2. **Les diagnostics de base de données sont épurés en production.** Lorsque l'échec provient de Postgres, `details.dbCode` — le SQLSTATE — est toujours présent : il nomme la catégorie du problème et ne divulgue rien sur les données. `dbMessage`, `detail` et `hint` ne sont ajoutés que lorsque `NODE_ENV` n'est pas `production`, car Postgres y intègre le contenu des lignes. `23505` indique `Key (email)=(a@b.c) already exists.`, ce qui permettrait de répondre à « cette personne est-elle inscrite ? » pour n'importe quelle adresse testée.
3. **Ne basez jamais votre logique de branchement sur `details`.** Basez-la sur `code`. Le contenu de `details` correspond à ce qui était utile à une personne à cet endroit précis du code, et cela change.

## Comprendre un statut

| Statut | Ce qu'il indique sur la requête |
| --- | --- |
| `400` | Requête malformée, ou demandant un élément inexistant dans le schéma. Corrigez la requête. |
| `401` | Non authentifié, ou identifiant expiré. Connectez-vous ou actualisez le jeton. |
| `403` | Authentifié, mais non autorisé. Réessayer avec la même identité ne servira à rien. |
| `404` | Route, collection ou ligne inexistante — ou ligne masquée par la sécurité au niveau des lignes (RLS). |
| `409` | Conflit avec l'état existant : un doublon ou une écriture concurrente. |
| `413` `415` `422` | Le corps est trop volumineux, le type de média est incorrect, ou la requête est sémantiquement rejetée. |
| `429` | Limite de débit atteinte (Rate limited). Ralentissez la cadence ; le message indique pour combien de temps. |
| `500` | L'erreur vient du serveur ou de sa base de données, pas de l'appelant. Consultez les journaux. |
| `501` | La route existe, mais ce déploiement ne peut pas la servir — une fonctionnalité est désactivée ou non configurée. |
| `502` `503` `504` | Une dépendance était inaccessible, non configurée ou trop lente. |

## `PG_<SQLSTATE>` — une contrainte rejetée par la base de données

Une écriture rejetée par Postgres pour une cause liée aux *données fournies par l'appelant* répond avec le SQLSTATE dans le code : `PG_23505`, `PG_23503`, etc. Il s'agit d'une famille d'erreurs et non d'une liste finie — Postgres définit des centaines de SQLSTATE — mais seules deux classes parviennent jusqu'ici, car seules ces deux-là relèvent de la responsabilité de l'appelant :

- **classe 23**, violation de contrainte d'intégrité : un doublon, une clé étrangère pointant vers le vide, une colonne NOT NULL laissée vide ;
- **classe 22**, exception sur les données : une valeur que le type de colonne ne peut pas stocker.

Tout le reste — connexion coupée, colonne manquante, problème de privilèges — relève du serveur et conserve un code `500`. Le test `code.startsWith("PG_")` est donc un moyen sûr de vérifier si « la ligne envoyée était incorrecte », et les quatre entrées ci-dessous sont celles qu'un client rencontre concrètement. `details.dbCode` contient ce même SQLSTATE pour chacune d'elles, et le message cite la contrainte en cause.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `PG_22P02` | 400 | Une valeur n'a pas pu être interprétée dans le type de la colonne — le pendant côté écriture de `INVALID_FILTER_VALUE`. | Envoyez une valeur conforme au type de la colonne. |
| `PG_23502` | 400 | Une colonne `NOT NULL` a été laissée vide. | Fournissez le champ, ou définissez une valeur par défaut sur la colonne. |
| `PG_23503` | 400 / 409 | À l'enregistrement, une clé étrangère cible une ligne inexistante (400). À la suppression, d'autres lignes référencent toujours celle-ci (409 ; une clé en `RESTRICT` lève `PG_23001`, également une 409). | Créez d'abord la ligne cible ou corrigez l'identifiant ; pour une suppression, supprimez ou redirigez d'abord les lignes qui y font référence. |
| `PG_23505` | 409 | Violation d'une contrainte d'unicité. Le message précise la contrainte. | Utilisez une valeur différente, ou mettez à jour la ligne existante. |

| `SCHEMA_EDITOR_NO_COLLECTIONS_DIR` | 501 | Le serveur n'a pas de `collectionsDir`, l'éditeur n'a donc nulle part où écrire. | Définissez `collectionsDir`. |
| `SCHEMA_EDITOR_PRODUCTION` | 501 | L'éditeur est inactif sous `NODE_ENV=production` : les fichiers d'un serveur déployé sont reconstruits depuis votre dépôt à chaque déploiement, une modification effectuée ici serait donc perdue. | Modifiez les collections en développement puis déployez, ou configurez `liveSchema.repository` pour y enregistrer les commits. |
| `SQL_EXPORT_UNSUPPORTED` | 501 | `POST /api/admin/sql/csv` ne peut pas diffuser de résultat ici : la base de développement intégrée au processus (PGlite) ne gère qu'une seule connexion, et un curseur maintenu pendant un téléchargement bloquerait toutes les autres requêtes en attente ; ou bien la source de données ne prend pas en charge les curseurs SQL. | Pointez `DATABASE_URL` vers votre propre instance Postgres (`rebase dev --docker` en démarre une), ou ajoutez un `LIMIT` et exportez les lignes affichées à l'écran. |

### Pourquoi la table d'une branche ne peut pas être fusionnée

`BRANCH_MERGE_BLOCKED` énumère chaque table refusée dans `details.tables`, avec l'un des codes suivants. Ce même code est attribué au champ `blocked` de la table au sein du diff lui-même, afin que Studio puisse le signaler avant même que l'utilisateur ne clique sur **Merge**. Aucun de ces codes ne constitue une réponse isolée.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `COLUMNS_DIFFER` | — | Les colonnes de la table divergent entre la branche et son parent. Les lignes sont comparées sur la base des seules colonnes communes. | Ajoutez les colonnes manquantes sur le parent avec vos migrations (`rebase db push`), puis fusionnez. Une migration réécrivant la table — modification de type de colonne — transforme cela en `TABLE_REWRITTEN` : fusionnez avant une telle opération, ou recréez la branche après coup. |
| `NO_PRIMARY_KEY` | — | La table n'a pas de clé primaire, les lignes ne peuvent donc pas être comparées une à une ; le diff n'indique que le nombre de lignes. | Attribuez une clé primaire à la table, ou déplacez ses lignes à la main. |
| `PRIMARY_KEY_DIFFERS` | — | Les colonnes de la clé primaire ou leurs types diffèrent d'un côté à l'autre. | Appliquez d'abord le schéma sur le parent. |
| `TABLE_ADDED` | — | La table a été créée par la branche. Une fusion ne crée jamais de table. | Créez-la sur le parent via vos migrations, puis fusionnez ses lignes. |
| `TABLE_DROPPED` | — | La table a été supprimée par la branche. Une fusion ne supprime jamais de table. | Supprimez-la à l'aide de vos migrations. |
| `TABLE_REWRITTEN` | — | L'un des côtés a réécrit l'intégralité des lignes de la table après la création de la branche — changement de type de colonne, `ADD COLUMN` avec valeur par défaut volatile, `VACUUM FULL`, `CLUSTER` — chaque ligne apparaît donc comme modifiée depuis lors et il est impossible de déterminer qui a modifié quoi. | Fusionnez la branche avant une telle migration, ou recréez la branche depuis le parent après celle-ci. |
| `TOO_LARGE` | — | La table contient sur l'un des côtés plus de lignes que ce qu'un diff compare individuellement (100 000 par défaut, `maxRowsPerTable`). | Augmentez `maxRowsPerTable` à la fois pour le diff et pour la fusion, ou transférez les lignes autrement. |

## Codes génériques

Une route utilise l'un de ces codes lorsqu'aucun autre plus spécifique ne s'applique.

| Code | Statut | Signification | Action |
| --- | --- | --- | --- |
| `BAD_REQUEST` | 400 | Requête malformée, sans code plus précis applicable. | Voir le message. |
| `UNAUTHORIZED` | 401 | Non authentifié, ou identifiant rejeté. | Connectez-vous ou actualisez le jeton. |
| `FORBIDDEN` | 403 | Authentifié, mais non autorisé. | Réessayer avec la même identité ne servira à rien. |
| `CONFLICT` | 409 | Conflit avec l'état existant. | Voir le message. |
| `INTERNAL_ERROR` | 500 | Un problème est survenu sur le serveur. Le message est volontairement générique. | Mentionnez le `requestId` ; la raison figure dans les journaux. |
| `NOT_CONFIGURED` | 503 | Une dépendance requise par cette route n'est pas configurée sur ce serveur. | Voir le message. |
| `SERVICE_UNAVAILABLE` | 503 | Un service dont dépend la requête n'a pas pu être joint : un bucket S3 ou MinIO, ou un hôte qu'une fonction tente de joindre via `fetch()` qui refuse la connexion ou ne se résout pas. Les journaux du serveur indiquent le nom de l'hôte ; la réponse HTTP ne le précise pas. Une base de données inaccessible produit `DATABASE_UNAVAILABLE`. Une connexion défaillante vers un tel service renvoie ce code ; sur la 0.24, elle renvoyait une `500` dont le code était l'erreur de socket (`ECONNREFUSED`), ou `INTERNAL_ERROR`. | Réessayez ; vérifiez les journaux. |

## Garantir l'exactitude de cette page

`pnpm verify:docs` échoue lorsqu'un code que le serveur peut lever est absent de ces tableaux, lorsqu'un tableau liste un code qui ne peut jamais être déclenché, lorsque les statuts d'une ligne ne correspondent pas exactement à ceux générés dans le code source, ou lorsqu'une famille de codes comme `PG_<SQLSTATE>` ne comporte pas de ligne pour un SQLSTATE que les appelants peuvent rencontrer. L'étape de contrôle se trouve dans `tooling/scripts/docs-verify/check-error-codes.mjs`.

Ce script se vérifie d'abord lui-même. L'analyse extrait les codes directement du code TypeScript plutôt que d'un serveur en cours d'exécution, ses angles morts sont donc silencieux par nature : il lui est arrivé de ne pas détecter un code encapsulé dans un wrapper d'une ligne, ou un code écrit après un message contenant une parenthèse `)`, tout en affirmant que « tous les codes pouvant être levés par le serveur sont documentés » sur une page où il en manquait dix-sept. Désormais, cette étape exécute une fixture contenant précisément ces cas de figure avant de lire cette page, et refuse de produire un rapport si elle ne parvient pas à les repérer.
