<span class="since-badge" data-since="0.31">Depuis 0.31</span>

Les règles d'une colonne sont déclarées une seule fois, sur la colonne, et appliquées
par le serveur lors de chaque écriture atteignant l'API. Le CMS lit ces mêmes
règles à partir du descripteur de la table et les vérifie dans le formulaire avant
l'enregistrement, afin qu'un opérateur voie l'erreur directement sur le champ et
non sous la forme d'une requête refusée.

```ts
// backend/schema/events.ts
import { defineTable, col } from "@rebasepro/server/schema";

export const events = defineTable("events", {
    columns: {
        id:      col.uuid().primaryKey().defaultRandom(),
        title:   col.text().notNull().validate({ min: 2, max: 200, requiredMessage: "Every event needs a title" }),
        slug:    col.varchar({ length: 80 }).notNull().unique()
                     .validate({ matches: "^[a-z0-9-]+$", matchesMessage: "Lowercase letters, digits and hyphens only" }),
        isFree:  col.boolean().notNull().default(false),
        price:   col.numeric({ precision: 10, scale: 2 }).validate({ min: 0 }),
        seats:   col.integer().validate({ positive: true }),
    },
    rls: "admin-only",
});
```

:::note[Vous venez des collections ?]
Il n'y a plus de bloc `validation` dans le frontend. Les règles sont écrites sur
la colonne avec `.notNull()` et `.validate({ … })`, et le CMS les lit.
:::

## Ce que le formulaire vérifie

<span class="since-badge" data-since="0.31">Depuis 0.31</span>

| Sur la colonne | Dans le formulaire |
|---|---|
| `.notNull()` | Requis, avec `requiredMessage` comme message d'erreur lorsqu'il est défini. Non requis lorsque personne ne saisit la valeur : une clé générée, un horodatage (stamp), une colonne générée ou `.readOnly()`. |
| `.unique()` | La valeur est vérifiée par rapport à la table avant qu'une valeur modifiée ne soit enregistrée, et un doublon est signalé sur son champ. |
| `varchar(n)`, `char(n)` | Au maximum `n` caractères. |
| text `min`, `max`, `length` | Nombre de caractères, bornes incluses. |
| `matches`, `matchesMessage` | La valeur entière doit correspondre au motif ; le message constitue l'erreur. |
| `email`, `url` | La valeur doit être une adresse e-mail, une URL. |
| `trim`, `lowercase`, `uppercase` | La valeur est nettoyée de ses espaces ou convertie en minuscules/majuscules avant d'être enregistrée. |
| number `min`, `max`, `moreThan`, `lessThan`, `positive`, `negative`, `integer` | Bornes et nombres entiers uniquement. Les colonnes integer et serial sont des nombres entiers, peu importe ce que stipule `.validate()`. |
| date `min`, `max` | La date la plus ancienne et la plus récente acceptées. |
| array `minItems`, `maxItems`, `uniqueItems` | Nombre d'éléments, et aucun élément en double. |

Chaque règle est répertoriée, avec sa signification exacte, sur la page
[Colonnes](/docs/schema/columns/#validation).

## Où s'exécute la validation

<span class="since-badge" data-since="0.31">Depuis 0.31</span>

Le serveur vérifie les règles d'une colonne au niveau de la frontière de requête
(REST, le socket temps réel et MCP) sur ce que l'appelant a envoyé, avant
l'exécution de `beforeSave`, et répond à une écriture enfreignant une règle par une
erreur 400 identifiant chaque champ en échec. Le code serveur qui écrit
en interne (in-process) est considéré comme fiable et n'est pas vérifié par rapport
à ces règles ; ce qui s'applique alors est ce que la base de données impose. Voir
[Colonnes](/docs/schema/columns/#validation).

Le CMS vérifie les mêmes règles avant d'enregistrer, dans le formulaire de
l'enregistrement et dans l'éditeur en ligne de la table. Une cellule de tableau
évalue une valeur dès que vous la modifiez : une valeur stockée qui enfreint une
règle ajoutée ultérieurement n'affiche aucune erreur tant que personne ne modifie
cette cellule.

## Champs conditionnels

<span class="since-badge" data-since="0.31">Depuis 0.31</span>

Un champ peut réagir aux valeurs de l'enregistrement lui-même : devenir
obligatoire, désactivé, en lecture seule ou masqué. Il existe deux façons de
procéder, toutes deux dans `customizeTable` :

```tsx
// frontend/src/cms/events.tsx
import { customizeTable } from "@rebasepro/cms";
import type { events } from "../../../backend/schema/events";

export const eventsCms = customizeTable<typeof events>("events", {
    fields: {
        price: {
            conditions: {
                disabled: { "==": [{ "var": "values.isFree" }, true] },
                required: { "!=": [{ "var": "values.isFree" }, true] },
                min: 0,
                disabledMessage: "Free events have no price",
                clearOnDisabled: true,
            },
        },
        seats: {
            dynamicProps: ({ values, authController }) => ({
                disabled: values.isFree === true || !authController.user?.roles?.includes("admin"),
            }),
        },
    },
});
```

### `conditions` : JSON Logic

`conditions` contient des règles [JSON Logic](https://jsonlogic.com/) portant sur
l'enregistrement en cours de modification (`values.<key>`). Il s'agit de données,
l'éditeur de schéma peut donc les lire et les modifier. Une condition peut définir :

- `disabled`, `disabledMessage`, `clearOnDisabled`, `hidden`, `readOnly` ;
- `required`, `requiredMessage`, `min`, `max` ;
- `defaultValue` ;
- `enumConditions`, `allowedEnumValues`, `excludedEnumValues` ;
- `referencePath`, `referenceFilter` ;
- `canAddElements`, `sortable`, pour les tableaux.

`disabledMessage` est ce que l'utilisateur voit à côté du contrôle grisé. Sans
lui, un champ désactivé ne fournit aucune explication.

### `dynamicProps` : une fonction

`dynamicProps` reçoit l'enregistrement tel qu'il est en cours de modification
(`values`, modifications non enregistrées comprises, et `previousValues` une fois
qu'il est enregistré) ainsi que l'utilisateur connecté via `authController`, puis
renvoie les options de champ qui s'appliquent actuellement. Ce qu'elle renvoie
est appliqué par-dessus les autres options du champ à chaque sollicitation du
formulaire, de sorte qu'elle peut renvoyer n'importe quelle option de champ :
`disabled`, `hidden`, `readOnly`, `name`, `description`, `enumLabels`…

:::caution[Les conditions relèvent du comportement du formulaire]
`conditions` et `dynamicProps` s'exécutent dans le navigateur et définissent ce
que le CMS propose. L'API accepte une écriture qui les ignore. Une règle qui doit
s'appliquer à chaque appelant doit figurer sur la colonne (`.notNull()`,
`.validate()`), ou dans la [sécurité au niveau des lignes](/docs/collections/security-rules/)
de la table, que la base de données applique pour tout le monde.
:::

## Libellés pour un ensemble fermé

<span class="since-badge" data-since="0.31">Depuis 0.31</span>

Les valeurs d'un `col.enum([...])` ou d'un `.oneOf([...])` appartiennent à la
colonne. Leurs libellés, couleurs et ordre appartiennent au CMS, définis avec
`enumLabels` et `enumOrder` ; voir les
[ensembles fermés de valeurs](/docs/collections/properties/#closed-sets-of-values).
