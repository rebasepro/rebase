# Mettre à niveau une application existante

Treize étapes, de la plus récente à la plus ancienne. Commencez par celle qui se situe juste au-dessus de votre version actuelle et descendez — ou, si vous venez de la version 0.12, commencez par le bas et remontez.

| Votre version | À lire | Ce que cela implique |
|---|---|---|
| **0.31** | [le changelog de la 0.32.0](/docs/changelog/) | La 0.32 ne déclare aucun changement cassant : mettez à niveau chaque paquet `@rebasepro`. Deux points perceptibles par un script : une commande CLI destructive (`api-keys revoke`, `db branch delete`, `cloud env unset`, `cloud compute set`, …) demande désormais confirmation et, en l'absence de terminal ou avec `--json`, refuse de s'exécuter avec `confirmation_required` tant que `--yes` n'est pas passé ; et les commandes du serveur MCP local `rebase_cloud_deploy`, `rebase_cloud_env_set`, `rebase_cloud_rollback` et `rebase_cloud_provision` n'agissent qu'avec `confirm: true`. `REALTIME_CDC=auto` lit désormais le journal des transactions (write-ahead log) lorsque la base de données le permet ; définissez `REALTIME_CDC=trigger` pour conserver la capture par déclencheurs. |
| **0.30** | [0.30 → 0.31](/docs/upgrading/0-30-to-0-31/) | Les tables dans `backend/schema` (`defineTable`) remplacent `config/collections`, et il n'y a plus de paquet config : exécutez `rebase migrate collections-to-tables`, qui déplace le projet et vérifie que le SQL généré reste inchangé. Le panneau d'administration affiche les tables servies par le serveur, personnalisées depuis `frontend/src/cms` ; le SDK utilise `data.table(slug)` et `tables: tablesDictionary` ; les bundles passent au format 3, recompilez donc avant de déployer ; MongoDB est retiré. |
| **0.29** | [0.29 → 0.30](/docs/upgrading/0-29-to-0-30/) | Un backend démarré avec `initializeRebaseBackend` conserve le jeton de rafraîchissement dans un cookie à moins de définir `cookieAuth: false`, de sorte qu'un appelant le lisant depuis le corps de la requête sans `x-rebase-auth-flow: json` reçoit `""`. |
| **0.27 – 0.28** | [0.27 → 0.29](/docs/upgrading/0-27-to-0-29/) | Tout ce que l'administration transmet à votre code correspond à la ligne du serveur accompagnée de son identifiant : le `context.data` et les `browserCallbacks` du navigateur renvoient des chaînes ISO et des clés étrangères là où ils transmettaient des `Date` et des objets de relation, ce qu'aucun compilateur ne détecte ; les hooks de données `Entity` deviennent internes ; et les callbacks, les panneaux, le panneau latéral ainsi que la sélection acceptent `row` et `id` au lieu de `entity` et `entityId`. La 0.28 ne déclarant aucun changement cassant, il s'agit d'une seule étape depuis la 0.27. |
| **0.26** | [0.26 → 0.27](/docs/upgrading/0-26-to-0-27/) | Une planification cron restreignant les deux champs de jour s'exécute sur l'un ou l'autre, donc plus fréquemment, et une planification contenant un nombre mal formé est refusée, ce qui arrête l'exécution de la tâche. Une clé dont le type ne peut honorer la stratégie `isId` bloque le démarrage. Sur Rebase Cloud, un déploiement ou une prévisualisation échoue lorsqu'un fichier de fonction ou de cron ne parvient pas à se charger. |
| **0.25** | [0.25 → 0.26](/docs/upgrading/0-25-to-0-26/) | Une écriture ciblant une relation `via` multi-sauts, un nom de rôle qui ne correspond pas à un rôle unique, un jeton de pagination du stockage local antérieur à la mise à niveau et un upstream de fonctions non opérationnel sont refusés. La connexion OAuth valide un compte non vérifié au lieu de renvoyer `local-account-unverified`, le serveur MCP n'envoie plus `REBASE_TOKEN` à l'application, et les types générés retirent la clé d'une relation belongsTo marquée `excludeFromApi`. Sur Rebase Cloud, `rebase cloud webhooks` et `--scale-to-zero true` sont retirés, et les anciens jetons peuvent nécessiter une recréation. |
| **0.24** | [0.24 → 0.25](/docs/upgrading/0-24-to-0-25/) | `?count=` sur une liste REST devient l'interrupteur pour le décompte derrière `meta.total`, un filtre sur une colonne nommée `count` doit donc être placé dans `?where=` ; la méthode `list_collections` du MCP distant envoie sa liste uniquement dans le bloc de texte, sans `structuredContent` ; et `@rebasepro/app` n'exporte plus la table de traduction espagnole `es`. Une simple requête `OPTIONS` vers une route sans gestionnaire, des collisions de noms de table au démarrage, un upsert sur la collection des utilisateurs, l'usage combiné de `page` avec `offset`, une chaîne vide sur un champ obligatoire et un mot de passe administrateur non conforme à la politique de mot de passe sont refusés. Les sessions durent 30 jours d'inactivité par défaut, `client.cron` appelle `/api/admin/cron`, les lectures hors ligne qui ne peuvent être honorées en totalité échouent avec `OFFLINE`, et plusieurs exports internes ainsi que des props inutilisées ont disparu. |
| **0.23** | [0.23 → 0.24](/docs/upgrading/0-23-to-0-24/) | Le rendu SQL de `db push` et `db generate` quitte `drizzle/` pour le répertoire non versionné `.rebase/sql/`, l'option `--generate` de `rebase dev` est supprimée car `dev` régénère toujours les types du SDK, et une modification de schéma en direct ne valide aucun SQL. Les permissions deviennent des scopes : les interfaces d'administration demandent un scope plutôt que le rôle admin, les clés d'API détiennent des scopes au lieu d'une liste de permissions et d'un indicateur `admin`, et `schema-admin` n'est plus un administrateur. Un chemin relatif pour `--collections` est résolu à partir de l'emplacement d'exécution de la commande, un upsert sur une ligne supprimée et une mise à jour modifiant une clé sont refusés, le point de terminaison MCP distant accepte les arguments du SDK, et les sockets temps réel ouvertes, les liens de vérification d'e-mail, `signUp` et les codes de récupération MFA changent leur façon de gérer une session. |
| **0.21 – 0.22** | [0.21 → 0.23](/docs/upgrading/0-21-to-0-23/) | Une clé d'API sur un chemin imbriqué nécessite la permission `read` sur ses parents, les variables numériques illisibles et les durées de session invalides empêchent le démarrage, un dépôt d'authentification personnalisé requiert `unlinkUserIdentity`, et les conversions d'invités (guest upgrades) exigent le captcha `register`. La 0.22 ne déclare aucun changement cassant, il s'agit donc d'une seule étape depuis la 0.21. |
| **0.18 – 0.20** | [0.18 → 0.21](/docs/upgrading/0-18-to-0-21/) | `context.client.data` ne compile plus dans un callback de collection — effectuez vos requêtes via `context.data` — et `selectedEntities` cède la place à une sélection pouvant représenter des lignes que personne n'a chargées. La 0.19 et la 0.20 ne déclarent aucun changement cassant, il s'agit donc d'une seule étape depuis la 0.18. |
| **0.17** | [0.17 → 0.18](/docs/upgrading/0-17-to-0-18/) | Onze changements cassants, la plupart étant des erreurs de compilation plutôt que des modifications silencieuses de comportement. `rebase.data` disparaît au runtime, les plages de versions des dépendances paires (peer dependencies) sont resserrées aux carets (^), et la version minimale de Node passe à 22.22.0. |
| **0.14 – 0.16** | [0.14 → 0.17](/docs/upgrading/0-14-to-0-17/) | Les paquets d'administration sont renommés, les ressources sont déclarées plutôt que configurées, et un bundle généré auparavant ne démarrera pas sur un runtime actuel. La 0.15 et la 0.16 ne cassent rien, il s'agit donc d'une seule étape depuis la 0.14. |
| **0.13** | [0.13 → 0.14](/docs/upgrading/0-13-to-0-14/) | Toutes les clés réseau sont en camelCase, et la connexion anonyme est soumise à une activation explicite (opt-in). |
| **0.12** | [0.12 → 0.13](/docs/upgrading/0-12-to-0-13/) | L'étape la plus importante, et la seule qui modifie **qui peut lire vos données**. Elle supprime le schéma `auth`, renomme des paquets, change la signification de `id`, abandonne CJS, migre le panneau d'administration vers react-router 8 et corrige trois manières par lesquelles un accès pouvait être accordé sans que vous ne l'ayez demandé. |

Les sections de chaque page sont présentées dans l'ordre où vous devez effectuer les étapes, et chacune mentionne le symptôme que vous risqueriez autrement de déboguer à l'envers.

Ensuite, quelle que soit l'étape franchie :

- [La checklist de mise à niveau](#upgrade-checklist) ci-dessous — les commandes et greps utiles à exécuter par la suite, regroupés en un seul bloc.

## Upgrade checklist

```
[ ] grep for authenticated() and (auth|rebase).uid() IS NOT NULL in config/collections/
[ ] decide the intent of each rule; rewrite the ones that meant "public"
[ ] replace not(authenticated()) with serverContext()
[ ] if realtime.requireAuth was true with an AuthAdapter, treat the socket as
    having been open — verify RLS on every subscribable collection (section 2)
[ ] SELECT ... FROM pg_policies — record the qual of every policy BEFORE
[ ] update package names and imports
[ ] grep for rebase.data — it is now rebase.dataAsAdmin (section 8)
[ ] grep for the other ten removed deprecated exports (section 8)
[ ] drop react-router-dom; import RouterProvider from "react-router/dom"
[ ] check node >= 22.22.0 and react >= 19.2.7 (react-router 8 requires both)
[ ] move defaultSecurityRules into config/collections/index.ts
[ ] grep for .userId
[ ] grep for row.id on tables not keyed on id
[ ] run db push
[ ] run rebase doctor --policies — expect no Insecure or Orphaned entries
[ ] SELECT ... FROM pg_policies again — confirm every intended change landed
[ ] exercise the app signed OUT, in a private window — watch the websocket too

--- 0.13 → 0.14 (part 2) ---
[ ] re-run rebase generate-sdk, then build — the compiler finds row.author_id
[ ] grep for snake_case where/orderBy keys; a stale one is a 400, not a warning
[ ] grep for raw fetch consumers reading row.<something>_id — these read
    undefined and raise nothing
[ ] if the project was introspected, re-run rebase schema introspect
[ ] decide anonymous sign-in: set auth.allowAnonymous: true, or confirm you
    never used it (grep for signInAnonymously)
[ ] drop @rebasepro/client-postgres from package.json

--- 0.14 → 0.17 (part 3) ---
[ ] rename @rebasepro/admin → @rebasepro/cms and admin-types → cms-types,
    and RebaseAdmin → RebaseCMS
[ ] move dataSources / storageSources out of the backend config into
    rebase.json and config/, then `rebase build` — an old bundle will not boot
[ ] grep collections for admin.titleProperty; it is refused at boot now
[ ] grep crons for ctx.client and for `userId` as an identity key
[ ] rename --legacy to --workspace wherever build/start is scripted
[ ] if you implement EmailService yourself, `send` must return a result

--- 0.30 → 0.31 ---
[ ] bump every @rebasepro package to 0.31 first, then pnpm install
[ ] rebase migrate collections-to-tables on a clean tree; read the manual steps
[ ] move config/index.ts `callbacks` to backend/hooks.ts by hand, if you had them
[ ] rebase generate-sdk; rebase db push --dry-run plans no change
[ ] run the git rm line the codemod printed (your own config/ modules may stay)
[ ] send a to-one relation as its key, not { id } — that is a 400 now
[ ] call /api/docs signed in, or set REBASE_ENABLE_SWAGGER=true to publish it
[ ] rename the MCP tools in prompts and allow-lists (list_tables, query_table, …)
[ ] rebuild the bundle and deploy — a format-2 bundle is refused

--- 0.31 → 0.32 ---
[ ] bump every @rebasepro package to 0.32, then pnpm install
[ ] add --yes to scripted destructive CLI commands (they refuse with confirmation_required)
[ ] rebase verify — fix any rls-policy-recursion it reports
[ ] rebase build — it warns when config/index.ts still exports storageAuthorize
```

`rebase doctor --policies` est la commande à intégrer dans votre CI : elle retourne un code d'erreur non nul pour toute stratégie comportant encore une tautologie permissive ou ayant été remplacée par un push précédent. La lecture de `pg_policies` avant et après vaut largement cette minute consacrée — elle vous montre les expressions elles-mêmes, ce qui est le seul moyen de repérer une stratégie ouverte par défaut (« fail-open ») rédigée sous une forme que le détecteur ne reconnaît pas. Ni les paquets ni le système de types ne vous avertiront : le changement réside dans la base de données, et `db push` est la seule commande qui l'y applique.

## Revenir à une version antérieure

Avant de revenir à une version plus ancienne que celle qui a introduit les compagnons d'admin-request (voir le [journal des modifications](/docs/changelog/)), rendez-les inactifs. Un runtime plus ancien ne supprime jamais un compagnon ; une règle modifiée après le retour en arrière continuerait donc d'accorder à chaque administrateur l'accès à chaque ligne. Exécutez `REVOKE rebase_admin_request FROM rebase_user_admin;` une fois par rôle admin request, ou supprimez les stratégies `_ar_`. La section [Admin reads use the owner's indexes](/docs/deployment/existing-database/#admin-reads-use-the-owners-indexes) fournit plus de détails à ce sujet.
