# Mettre à niveau une application existante

Douze étapes, de la plus récente à la plus ancienne. Commencez par celle qui se situe juste au-dessus de votre version actuelle et progressez vers le bas — ou, si vous venez de la 0.12, commencez par le bas et remontez.

| Votre version actuelle | À lire | Ce que cela implique |
|---|---|---|
| **0.29** | [0.29 → 0.30](/docs/upgrading/0-29-to-0-30/) | Un backend démarré avec `initializeRebaseBackend` garde le jeton de rafraîchissement dans un cookie, sauf s'il définit `cookieAuth: false` : un appelant qui le lit dans le corps sans `x-rebase-auth-flow: json` reçoit `""`. |
| **0.27 – 0.28** | [0.27 → 0.29](/docs/upgrading/0-27-to-0-29/) | Tout ce que l'admin transmet à votre code est la ligne du serveur avec son id à côté : les `context.data` et `browserCallbacks` du navigateur fournissent des chaînes ISO et des clés étrangères là où ils transmettaient des `Date` et des objets de relation, ce qu'aucun compilateur ne détecte ; les hooks de données `Entity` deviennent internes ; et les callbacks, les panneaux, le panneau latéral et la sélection prennent `row` et `id` à la place d'`entity` et `entityId`. La version 0.28 ne déclare aucun changement cassant, il s'agit donc d'une seule étape depuis la 0.27. |
| **0.26** | [0.26 → 0.27](/docs/upgrading/0-26-to-0-27/) | Une planification cron restreignant les deux champs de jour s'exécute sur l'un ou l'autre, donc plus fréquemment, et une planification contenant un nombre mal formé est refusée, ce qui arrête l'exécution de cette tâche. Une clé dont la stratégie `isId` ne peut pas être respectée par son type bloque le démarrage. Sur Rebase Cloud, un déploiement ou une prévisualisation échoue lorsqu'un fichier de fonction ou de cron ne se charge pas. |
| **0.25** | [0.25 → 0.26](/docs/upgrading/0-25-to-0-26/) | Une écriture désignant une relation `via` multi-sauts, un nom de rôle qui ne correspond pas à un rôle unique, un jeton de pagination du stockage local antérieur à la mise à niveau et un upstream de fonctions non fonctionnel sont refusés. La connexion OAuth valide un compte non vérifié au lieu de renvoyer `local-account-unverified`, le serveur MCP n'envoie plus `REBASE_TOKEN` à l'application, et les types générés suppriment la clé d'un belongsTo annoté `excludeFromApi`. Sur Rebase Cloud, `rebase cloud webhooks` et `--scale-to-zero true` sont abandonnés, et les anciens jetons peuvent nécessiter d'être recréés. |
| **0.24** | [0.24 → 0.25](/docs/upgrading/0-24-to-0-25/) | `?count=` sur une liste REST devient l'indicateur pour le comptage sous-jacent à `meta.total`, donc un filtre sur une colonne nommée `count` se place dans `?where=` ; la commande `list_collections` du MCP distant envoie sa liste uniquement dans le bloc de texte, sans `structuredContent` ; et `@rebasepro/app` n'exporte plus la table de traduction espagnole `es`. Une requête `OPTIONS` simple vers une route sans gestionnaire, des collisions de noms de tables au démarrage, un upsert sur la collection `users`, `page` avec `offset`, une chaîne vide sur un champ requis et un mot de passe administrateur non conforme à la politique de mot de passe sont refusés. Les sessions durent 30 jours d'inactivité par défaut, `client.cron` appelle `/api/admin/cron`, les lectures hors ligne qui ne peuvent être totalement honorées échouent avec `OFFLINE`, et quelques exports internes ainsi que des props inutilisées ont disparu. |
| **0.23** | [0.23 → 0.24](/docs/upgrading/0-23-to-0-24/) | Le rendu SQL de `db push` et `db generate` quitte `drizzle/` pour le répertoire non versionné `.rebase/sql/`, le flag `--generate` de `rebase dev` est supprimé car `dev` régénère toujours les types du SDK, et une modification de schéma à chaud ne committe aucun SQL. Les permissions deviennent des scopes : les interfaces admin requièrent un scope plutôt que le rôle admin, les clés d'API contiennent des scopes au lieu d'une liste de permissions et d'un flag `admin`, et `schema-admin` n'est plus administrateur. Un chemin relatif `--collections` est lu depuis l'emplacement où la commande est exécutée, un upsert sur une ligne mise à la corbeille et une mise à jour modifiant une clé sont refusés, le point de terminaison MCP distant accepte les arguments du SDK, et les sockets temps réel ouvertes, les liens de vérification d'e-mail, `signUp` et les codes de récupération MFA modifient leur gestion de la session. |
| **0.21 – 0.22** | [0.21 → 0.23](/docs/upgrading/0-21-to-0-23/) | Une clé d'API sur un chemin imbriqué nécessite `read` sur ses parents, des variables numériques et des durées de vie de session illisibles bloquent le démarrage, un dépôt d'authentification personnalisé requiert `unlinkUserIdentity`, et les conversions d'invités utilisent le captcha `register`. La version 0.22 ne déclare aucun changement cassant, il s'agit donc d'une seule étape depuis la 0.21. |
| **0.18 – 0.20** | [0.18 → 0.21](/docs/upgrading/0-18-to-0-21/) | `context.client.data` ne compile plus dans un callback de collection — effectuez vos requêtes via `context.data` — et `selectedEntities` cède sa place à une sélection pouvant représenter des lignes que personne n'a chargées. Les versions 0.19 et 0.20 ne déclarent aucun changement cassant, il s'agit donc d'une seule étape depuis la 0.18. |
| **0.17** | [0.17 → 0.18](/docs/upgrading/0-17-to-0-18/) | Onze changements cassants, la plupart étant des erreurs de compilation plutôt que des changements de comportement silencieux. `rebase.data` disparaît au runtime, les plages de peer dependencies se resserrent aux carets (`^`), et la version minimale de Node passe à 22.22.0. |
| **0.14 – 0.16** | [0.14 → 0.17](/docs/upgrading/0-14-to-0-17/) | Les packages d'administration sont renommés, les ressources sont déclarées plutôt que configurées, et un bundle généré antérieurement ne démarrera pas sur un runtime actuel. Les versions 0.15 et 0.16 ne cassent rien, il s'agit donc d'une seule étape depuis la 0.14. |
| **0.13** | [0.13 → 0.14](/docs/upgrading/0-13-to-0-14/) | Toutes les clés réseau sont en camelCase, et la connexion anonyme devient opt-in. |
| **0.12** | [0.12 → 0.13](/docs/upgrading/0-12-to-0-13/) | L'étape la plus importante, et la seule qui modifie **qui peut lire vos données**. Elle supprime le schéma `auth`, renomme des packages, change la signification d'`id`, abandonne CJS, migre le panneau d'administration vers react-router 8 et corrige trois manières dont des accès pouvaient être accordés sans que vous ne l'ayez demandé. |

Les sections de chaque page sont présentées dans l'ordre dans lequel vous devez procéder, et chacune indique le symptôme que vous risqueriez sinon de déboguer par le mauvais bout.

Ensuite, quelle que soit l'étape franchie :

- [La checklist de mise à niveau](#upgrade-checklist) ci-dessous — les commandes grep et les instructions utiles à exécuter ensuite, réunies en un seul bloc.

## Upgrade checklist

```
[ ] grep for authenticated() and (auth|rebase).uid() IS NOT NULL in config/collections/
[ ] decide the intent of each rule; rewrite the ones that meant "public"
[ ] replace not(authenticated()) with serverContext()
[ ] if realtime.requireAuth was true with an AuthAdapter, treat the socket as
    having been open — verify RLS on every subscribable collection (section 2)
[ ] SELECT ... FROM pg_policies — record the qual of every policy BEFORE
[ ] update package names and imports
[ ] grep for rebase.data — it is now rebase.dataAsAdmin (section 8)
[ ] grep for the other ten removed deprecated exports (section 8)
[ ] drop react-router-dom; import RouterProvider from "react-router/dom"
[ ] check node >= 22.22.0 and react >= 19.2.7 (react-router 8 requires both)
[ ] move defaultSecurityRules into config/collections/index.ts
[ ] grep for .userId
[ ] grep for row.id on tables not keyed on id
[ ] run db push
[ ] run rebase doctor --policies — expect no Insecure or Orphaned entries
[ ] SELECT ... FROM pg_policies again — confirm every intended change landed
[ ] exercise the app signed OUT, in a private window — watch the websocket too

--- 0.13 → 0.14 (part 2) ---
[ ] re-run rebase generate-sdk, then build — the compiler finds row.author_id
[ ] grep for snake_case where/orderBy keys; a stale one is a 400, not a warning
[ ] grep for raw fetch consumers reading row.<something>_id — these read
    undefined and raise nothing
[ ] if the project was introspected, re-run rebase schema introspect
[ ] decide anonymous sign-in: set auth.allowAnonymous: true, or confirm you
    never used it (grep for signInAnonymously)
[ ] drop @rebasepro/client-postgres from package.json

--- 0.14 → 0.17 (part 3) ---
[ ] rename @rebasepro/admin → @rebasepro/cms and admin-types → cms-types,
    and RebaseAdmin → RebaseCMS
[ ] move dataSources / storageSources out of the backend config into
    rebase.json and config/, then `rebase build` — an old bundle will not boot
[ ] grep collections for admin.titleProperty; it is refused at boot now
[ ] grep crons for ctx.client and for `userId` as an identity key
[ ] rename --legacy to --workspace wherever build/start is scripted
[ ] if you implement EmailService yourself, `send` must return a result
```

`rebase doctor --policies` est la commande à intégrer dans votre CI : elle renvoie un code de sortie non nul si une stratégie comporte encore la tautologie permissive, ou si une stratégie a été remplacée par un push antérieur. La consultation de `pg_policies` avant et après vaut largement la minute consacrée — elle vous montre les expressions elles-mêmes, ce qui constitue le seul moyen de repérer une stratégie permissive ("fail-open") rédigée selon une syntaxe non reconnue par le détecteur. Ni les packages ni le système de types ne vous avertiront : le changement réside dans la base de données, et `db push` est la seule commande qui l'y applique.

## Revenir à une version antérieure

Avant de revenir à une version plus ancienne que celle qui a introduit les politiques compagnes des requêtes d'administration (voir le [journal des modifications](/docs/changelog/)), rendez-les inertes. Un runtime plus ancien ne supprime jamais une politique compagne : une règle modifiée après le retour en arrière continuerait d'ouvrir toutes les lignes à tous les administrateurs. Exécutez `REVOKE rebase_admin_request FROM rebase_user_admin;` une fois par rôle de requête d'administration, ou supprimez les politiques `_ar_`. [Les lectures d'administration utilisent les index du propriétaire](/docs/deployment/existing-database/#admin-reads-use-the-owners-indexes) les explique.
