:::tip[Vous connectez Claude à vos propres projets ?]
C'est le rôle du [connecteur Rebase](/docs/ai/rebase-connector/) : un seul connecteur pour
tous vos projets, et un serveur auto-hébergé le rejoint avec `rebase cloud connect`. Cette
page s'adresse aux personnes qui **utilisent** votre application.
:::

Le [serveur MCP](/docs/ai/mcp/) est un outil de développement : il s'exécute sur votre machine et détient une clé de service ou une clé d'API. Un backend déployé peut également servir MCP lui-même, à l'adresse `/mcp`, pour les personnes qui utilisent votre application. Un assistant connecté par l'une d'elles lit et écrit dans le projet **en tant que cette personne**, et chaque appel s'exécute sous sa propre sécurité au niveau des lignes.

Il est désactivé par défaut, et les deux variables sont obligatoires :

```bash
REBASE_MCP_ENABLED=true
REBASE_PUBLIC_URL=https://app.example.com   # this deployment's real origin
```

Sans `REBASE_PUBLIC_URL`, sans secret JWT ou sans pilote de données capable de restreindre une requête à un utilisateur, le point de terminaison refuse de se monter et en explique la raison dans le journal de démarrage. Aucun `REBASE_ROLE` ne l'active.

- **OAuth, avec un écran de consentement.** Un client trouve le serveur d'autorisation via `/.well-known/oauth-protected-resource`, s'enregistre (l'enregistrement dynamique est activé par défaut ; `REBASE_MCP_OPEN_REGISTRATION=false` le limite aux clients que vous enregistrez) et redirige l'utilisateur vers un écran de consentement qui le connecte via votre `/auth/login` existant. Un compte avec double facteur doit ensuite fournir son code d'authentification ou un code de récupération, via les routes `/auth/mfa/challenge` existantes. Lorsque le propre frontend de votre application conserve une session dans le même navigateur, l'écran propose ce compte, et le bouton Autoriser donne son accord sous cette identité sans mot de passe ; c'est ainsi qu'une personne se connectant uniquement avec Google, GitHub ou un lien par e-mail se connecte. Sinon, elle se connecte avec un mot de passe, et une personne qui n'en a pas en définit d'abord un avec `/auth/forgot-password` (« Mot de passe oublié » de votre application) ; l'écran le lui indique. Il mentionne également l'hôte auquel le code d'autorisation est envoyé et précise que cet hôte n'est pas vérifié : n'importe qui pouvant enregistrer un client sous n'importe quel nom, l'hôte est l'élément que l'utilisateur peut vérifier.
- **Douze outils, trois portées.** <span class="since-badge" data-since="0.29">Depuis 0.29</span> Les mêmes [portées](/docs/backend/roles-and-scopes/) que chaque identifiant utilise. `data:read` propose `list_collections`, `describe_collection`, `query_collection`, `count_documents`, `aggregate_documents`, `get_document` et les trois vues, `show_collection`, `show_record` et `show_app` ; `data:write` ajoute `create_document` et `update_document` ; `data:delete` ajoute `delete_document`. Un client qui ne demande rien obtient `data:read`. Chacune se restreint à une collection : `data:read:posts` liste, décrit et lit `posts` et rien d'autre. Une portée détermine quels outils sont proposés et quelles collections ils atteignent, pas quelles lignes : une liste vide peut simplement signifier que le RLS fonctionne, et `data:write` ne peut toujours pas écrire une ligne à laquelle la personne n'a pas accès.
- **Trois outils placent votre panneau d'administration devant l'utilisateur.** Dans un client qui prend en charge le rendu des applications MCP, tel que Claude, ils ouvrent les propres vues du panneau d'administration dans la conversation, générées à partir de vos collections : leurs champs, énumérations, validations, relations, sections de formulaire et paramètres de vue.
  - `show_collection` prend les arguments de `query_collection`, plus `view` (`table`, `list`, `cards` ou `kanban`), et ouvre la vue de la collection : l'utilisateur peut rechercher, filtrer, trier et paginer, ouvrir le formulaire d'une ligne et ajouter des lignes.
  - `show_record` ouvre le formulaire d'une ligne (`id`), ou un formulaire pour une nouvelle ligne pré-remplie avec les `values` fournies par le modèle, afin que la personne puisse les vérifier et les enregistrer elle-même.
  - `show_app` exécute une application écrite par le modèle pour la tâche en cours : un composant React (`code`) et les `collections` qu'il lit. Il importe les propres packages de Rebase, de sorte que le même code fonctionne dans votre projet :
    - `@rebasepro/app` : `useRows`, `useRow`, `useRowCount`, `useAggregate` et `useRowWrites` sur les lignes du projet ;
    - `@rebasepro/cms` : le `CollectionPanel` du panneau d'administration (avec `CollectionToolbar` et ses éléments, ainsi que `onRowClick`, qui transmet à l'application la ligne cliquée telle que lue par `useRows`), `RecordForm` et `FormField`, `RecordDetail`, `FieldValue` et `useSidePanel`, chacun nommant sa collection par son chemin, avec vos champs, vues et actions personnalisés ;
    - `@rebasepro/ui`, l'ensemble du kit UI, `SplitView` ainsi que les tuiles KPI et graphiques inclus.

    Le serveur la compile d'abord, de sorte qu'une erreur de syntaxe, un module non fourni par la vue ou un nom non exposé depuis `@rebasepro/cms` ou `@rebasepro/app` constitue l'erreur de l'appel, avec sa ligne. Une erreur lors de son exécution s'affiche à sa place et est signalée au modèle avec le prochain message de l'utilisateur. Une application ne peut utiliser que les collections qu'elle liste. Ses styles sont les utilitaires standard de Tailwind, compilés avec la vue avant l'arrivée de toute application : une valeur arbitraire telle que `h-[560px]` n'y fait rien, une taille exacte doit donc être passée via un `style`.

  Chaque lecture et sauvegarde dans la vue correspond à un appel des outils de lecture et d'écriture, effectué en tant que l'utilisateur sous ses règles RLS, de sorte qu'un formulaire ne propose que ce qui a été accordé à sa connexion : sans `data:write`, il est en lecture seule, et un champ que ses rôles ne peuvent pas lire n'y figure pas. C'est également la limite dans laquelle s'exécute le code d'une application : elle s'exécute dans la vue, donc chaque appel qu'elle effectue est l'un de ces outils, en tant que l'utilisateur, et elle ne peut rien faire que le modèle ne pourrait pas faire avec ces mêmes outils. Sur le connecteur hébergé, chaque écriture est également planifiée et confirmée par le serveur. Dans ce cadre, `useRowWrites` demande confirmation à la personne avant d'écrire, afin qu'une application n'écrive rien sans son clic ; les commandes propres à l'administration (le bouton Enregistrer d'un formulaire, une suppression, une modification dans un tableau) se comportent comme sur un écran `show_collection`. Le modèle est informé de ce qui a été modifié. Il lit les lignes renvoyées par chaque outil, et non les configurations de collection utilisées pour dessiner la vue. Un client sans support des applications MCP, tel que Claude Code ou Cursor, n'affiche rien, et le modèle lit les mêmes lignes qu'il lirait depuis `query_collection`.
- **Les autorisations accordées avant la version 0.24 conservent leur portée.** `mcp:read` est interprété comme `data:read`, et `mcp:write` comme `data:write data:delete`, pour les autorisations stockées et les jetons déjà émis.
- **Une clé d'API fonctionne également.** `/mcp` accepte aussi `Authorization: Bearer rk_…`, pour un client configuré avec un en-tête plutôt qu'un flux OAuth. La clé a accès aux outils couverts par ses portées `data:*`, selon l'identité qu'elle représente : une [clé personnelle](/docs/backend/api-keys/#personal-keys) en tant que son propriétaire, une clé de service en tant que `api-key:<id>`.
- **Le vocabulaire du SDK, les réponses de REST.** Les outils acceptent les mêmes paramètres que le SDK — `where` (`{"status": ["==", "paid"]}`), `orderBy` (`["created_at", "desc"]` ou `"created_at:desc"`), `limit`, `offset`, `searchString`, et `data` pour une écriture — et effectuent leurs lectures via le chemin `GET /api/data/<collection>`, de sorte qu'une ligne est renvoyée telle que REST la fournit (dates ISO, une relation `belongsTo` sous forme de clé étrangère, par ex. `authorId`) et peut être renvoyée inchangée dans une mise à jour. `query_collection` répond `{ data, meta }` avec `meta.total` et `meta.hasMore`, et `count_documents` répond `{ count }`. `aggregate_documents` correspond à `GET /api/data/<collection>/aggregate` : `select` est une liste selon la grammaire de REST (`["count()", "sum(total)"]`), `groupBy` une liste de champs, et il répond `{ data }` avec une ligne par groupe, plus `meta.hasMore` lors d'un appel groupé, dont les groupes se paginent avec `limit` et `offset` et se trient avec `orderBy`. Sur une collection qu'un rappel (callback) `afterRead` réécrit, il ne renvoie que `count()`, tout comme REST. Comme sur REST, une `limit` supérieure à 1000, un argument non déclaré et une modification ou suppression d'une ligne placée dans la corbeille (404) sont refusés ; définir le champ de suppression réversible (soft-delete) à `null` la restaure. `deleted: "only"` (ou `"include"`) sur `query_collection`, `count_documents` et `aggregate_documents` permet de lire la corbeille, tout comme `?deleted=` en REST, afin qu'une ligne mise à la corbeille par `delete_document` puisse être retrouvée pour être restaurée. Sa description indique au modèle que la suppression n'est définitive que si la collection n'a pas de champ de suppression réversible.
- **La liste nomme les collections ; `describe_collection` fournit le schéma de l'une d'elles.** `list_collections` renvoie les attributs `name`, `title` et `description` de chaque collection, et `describe_collection { collection }` renvoie les schémas OpenAPI `row` et `create` de cette collection, ainsi que `softDeleteField` lorsque les lignes vont dans une corbeille. Les descriptions des outils indiquent au modèle de décrire une collection avant d'y écrire. La liste pour un projet de 200 collections représente environ 5k tokens, et chaque description moins de 1k ; inclure chaque schéma dans la liste représentait environ 150k tokens.
- **Un jeton réservé à ce point de terminaison.** Un jeton d'accès MCP est refusé par `/api/data`, `/api/admin` et le WebSocket, de sorte que connecter un assistant ne lui transmet pas de session.

Chaque requête vers `/mcp` relit le compte de l'utilisateur. Un compte supprimé ou désactivé, ou une action « se déconnecter de partout » ou un changement de mot de passe après l'émission du jeton, interrompt immédiatement un client connecté avec une erreur 401. Une rétrogradation s'applique dès son prochain appel d'outil. Chaque rafraîchissement effectue les mêmes vérifications et révoque définitivement une telle autorisation. Une session invité ne peut en aucun cas donner son consentement.

Une limite toutefois : déconnecter un client (`DELETE /api/oauth/grants/:clientId`, avec la propre session de l'utilisateur) révoque immédiatement ses jetons de rafraîchissement, mais un jeton d'accès déjà émis continue de fonctionner jusqu'à son expiration, dans un délai maximal d'une heure.

Les routes sont indiquées dans [Points de terminaison](/docs/backend/endpoints/#mcp-surface) et les variables dans [Configuration](/docs/getting-started/configuration/#mcp-surface).
