# Mise à niveau 0.30 → 0.31

<span class="since-badge" data-since="0.31">Depuis 0.31</span>

La version 0.31 rend le backend Postgres-first. Les tables déclarées avec `defineTable` dans `backend/schema/` sont la seule chose que le backend connaît de vos données ; ce que le panneau d'administration affiche par-dessus réside dans le frontend. Presque chaque entrée ci-dessous est une conséquence de cette séparation, et presque tout est pris en charge automatiquement par une commande unique.

### La liste de contrôle, par projet

1. **Mettez d'abord à niveau chaque paquet `@rebasepro`**, dans chaque paquet du workspace, afin que les types lus par le codemod soient ceux de la version 0.31 : `pnpm -r up "@rebasepro/*@0.31.0"`, puis `pnpm install`. Un projet sur une version antérieure à 0.30 applique d'abord les modifications de code des guides intermédiaires ([Mise à niveau](/docs/upgrading/)) et répond aux prérequis de la chaîne d'outils de 0.31 — Node 22.22, TypeScript 6, React 19.2.7, React Router 8, Vite 8 ([la liste](/docs/upgrading/0-30-to-0-31-by-hand/#a-project-on-a-release-before-030)) : le codemod charge un dossier `config/` en 0.20–0.29 et sa vérification SQL réussit, mais cette vérification compare le compilateur 0.31 à lui-même — seule l'étape 7, exécutée sur votre base de données, prouve que le DDL généré correspond à ce que contient votre base.
2. **Commitez, puis exécutez le codemod à blanc :** `rebase migrate collections-to-tables --dry-run`. Il affiche les fichiers qu'il écrirait, ce qu'il refuse (avec fichier et ligne), les notes et les étapes manuelles, et n'écrit rien. Corrigez d'abord ce qu'il refuse dans `config/`.
3. **Exécutez-le pour de bon :** `rebase migrate collections-to-tables`. Il écrit `backend/schema/`, `frontend/src/cms/` (avec `ui-config.json`), les modules `backend/` et les fichiers du projet, ajoute `rebaseBackendGuard()` au `vite.config.ts` du scaffold, réécrit vos appels SDK, déplace les imports de noms que 0.31 a déplacés vers un autre paquet ([section 135](#135-rebaseprotypes-and-rebaseprocommon-drop-the-collection-model-from-their-roots)), et prouve que le SQL généré est identique à l'octet près — ou restaure chaque fichier. Voir la [section 108](#108-tables-in-backendschema-replace-configcollections--run-the-codemod-first).
4. **Lisez la dernière section de sa sortie, « Review before deploying: these rules change meaning »**, et tranchez pour chaque règle listée ([ci-dessous](#à-examiner-avant-de-déployer--ces-règles-changent-de-signification)).
5. **Effectuez les étapes manuelles qu'il affiche**, dans l'ordre. Chacune nomme son fichier, et la plupart fournissent le fragment de code à écrire : le montage de `<RebaseCMS>` avec `tableCustomizations` et `uiConfig` lorsque votre `App.tsx` n'est pas celui du scaffold (ou lorsque le panneau est monté dans un autre module, que l'étape indique), `rebaseBackendGuard()` lorsque votre `vite.config.ts` n'est pas celui du scaffold et dans chaque autre application statique de `rebase.json` ([section 130](#130-rebase-build-refuses-a-frontend-without-rebasebackendguard)), les hooks globaux, l'import d'un nom supprimé dans 0.31 ([section 135](#135-rebaseprotypes-and-rebaseprocommon-drop-the-collection-model-from-their-roots)), et `rebase skills install` lorsque le projet contient des compétences d'agent ([section 128](#128-the-agent-skill-rebase-collections-is-rebase-tables)). Exécutez `pnpm install` lorsque la sortie indique « Dependencies added ». Lisez ensuite deux listes dans la partie SDK de la sortie :
   - **« Rewritten by name — review »** : les appels `.collection(` sur un récepteur sans type (`any`), réécrits parce que le récepteur est nommé `dataAsAdmin`, ou est `.data` avec un nom de table littéral ; le membre `collection` d'un type contenu dans un slot `data` / `dataAsAdmin` ; et les doublures de test. Vérifiez que chacun correspond bien au SDK.
   - **« Left unchanged — check each »** : les appels `.collection(` pour lesquels le codemod n'a pas pu prouver qu'il s'agissait du SDK, comme un appel via un type déclaré par votre projet lui-même. Un appel laissé ici qui *est* le SDK échouera à l'exécution sur 0.31 : renommez-le manuellement en `.table(`. Le code qui teste l'existence de `collection` (`typeof data.collection === "function"`) constitue une étape manuelle : sur 0.31, il emprunte silencieusement l'autre branche.

   Un fichier commité en tant qu'artefact de build (un `.js` bundlé ou minifié) n'est jamais modifié : il est listé, vous devez donc le reconstruire après la migration, et remplacer toute copie vendorisée du client par le build 0.31. Les étapes répétées d'un même type sont affichées une seule fois, en listant chaque fichier et ligne concernés ; `--json` conserve chaque étape séparément. Lisez ensuite [Ce que les projets ont modifié manuellement](/docs/upgrading/0-30-to-0-31-by-hand/) : les modifications que les vrais projets ont encore dû faire après ces étapes.
6. **Exécutez la ligne `git rm` affichée par le codemod** une fois le diff examiné et que `rebase migrate collections-to-tables --check` réussit : `git rm -r config/collections …` et les raccordements déplacés vers `backend/`, ou `git rm -r config` s'il ne reste rien qui vous appartienne ([section 109](#109-there-is-no-config-package)). Les trois étapes suivantes en ont besoin : `generate-sdk`, `db push`, `doctor` et `verify` refusent un projet qui possède encore `config/collections`.
7. **`rebase generate-sdk`** — les noms du module généré ont changé ([section 115](#115-the-sdk-addresses-a-table-datatableslug)).
8. **Sur votre base de données**, exécutez `rebase db push --dry-run` et attendez-vous à « No changes: the database already matches these tables. », puis `rebase doctor --policies` et vérifiez l'absence de dérive de stratégie (policy drift). La vérification SQL du codemod prouve la fidélité de la conversion ; ces deux commandes la prouvent vis-à-vis de la base de données réelle, et toute différence de stratégie listée par l'une d'elles représente un changement dans les droits d'accès.
9. **`rebase verify`** — il lit désormais également `frontend/src/cms` : une personnalisation nommant une table ou un champ inexistant, une colonne obligatoire exclue du formulaire, un `rebaseBackendGuard()` manquant, un fichier `ui-config.json` non transmis à `<RebaseCMS>`.
10. **Reconstruisez et déployez.** Un bundle compilé avant la version 0.31 ne démarre pas sur un runtime 0.31 ([section 112](#112-bundle-format-3-format-2-bundles-are-refused)). Le premier démarrage réestampille une fois la version de schéma de la base de données ([section 113](#113-the-schema-version-is-computed-from-tables-v2)).

Exécutez `rebase migrate collections-to-tables --check` dans votre CI jusqu'à ce que `config/` ait disparu : cela vérifie que les tables migrées génèrent toujours le même SQL que les collections d'origine, et quitte avec le code 1 tant qu'une règle listée sous « Review before deploying » n'a pas été confirmée — passez `--accept-rule-changes` une fois que vous les avez examinées.

### À examiner avant de déployer : ces règles changent de signification

Le codemod conserve chaque règle de sécurité telle qu'écrite, et chacune garde son nom de stratégie. Mais le compilateur 0.30 ne lisait que la première clause parmi `condition`, `using`, `access: "public"` et `ownerField`, et ne reconnaissait aucune autre valeur de `access`, de sorte que quatre formes de règles accordent désormais des droits différents. Deux d'entre elles élargissent les accès :

| La règle | 0.30 accordait | 0.31 accorde | |
|---|---|---|---|
| un simple `access: "authenticated"` (sans `roles`) | rien | chaque appelant authentifié, invités compris | **élargit** |
| `access` + `check`, sans `condition`, sur `select` / `update` / `delete` / `all` | aucune ligne existante | chaque ligne existante, aux appelants définis par `access` | **élargit** |
| `access: "authenticated"` + `condition` | quiconque correspond à `condition` | uniquement les appelants authentifiés y correspondant | restreint |
| `access: "authenticated"` + `check`, sur `insert` | quiconque insère une ligne correspondante | uniquement les appelants authentifiés | restreint |

Le cas le plus courant est le premier. Écrivez `access: "registered"` pour n'admettre que les appelants possédant un compte (et non les invités anonymes), ou supprimez la règle pour continuer à ne rien accorder. `access` avec `roles`, ainsi qu'une `condition` sous forme d'objet simple, conservent leur comportement antérieur et ne sont pas listés.

Le codemod refuse également toute règle refusée par le compilateur 0.31 : celles combinant des clauses exclues par le type `SecurityRule` (`access` aux côtés de `ownerField`, `using` ou `withCheck` ; `ownerField` aux côtés de `using`, `withCheck`, `condition` ou `check` ; `condition` ou `check` aux côtés de `using` ou `withCheck`), ainsi que celles comportant une valeur `access`, `mode`, `operation(s)` ou `roles` invalide — une faute de frappe dans `"restrictive"` compilait auparavant comme permissive. Voir [Règles de sécurité](/docs/collections/security-rules/).

### Autres changements de comportement

- **Ce que `GET /api/schema/tables` renvoie à un utilisateur.** Les administrateurs et les détenteurs de `schema:read` obtiennent toutes les tables. Tout autre utilisateur connecté, invités compris, n'obtient que les tables accessibles à ses rôles, avec uniquement les règles qui peuvent s'appliquer à lui ; les relations vers d'autres tables sont omises et les indicateurs de hooks sont masqués. Un frontend qui lisait la description d'une autre table en tant qu'utilisateur standard reçoit moins d'informations ; `schemaTables: { persons: "all" }` dans les options du backend permet de rétablir la description complète. Voir [Endpoints](/docs/backend/endpoints/#schema).
- **Les noms de relation sont exacts**, et **les clés étrangères sous forme de grands entiers (big-integer) sont des nombres** ([section 131](#131-rows-on-the-wire-follow-their-column)).
- **L'historique est servi masqué** ([section 132](#132-history-is-served-as-reads)).
- **Les noms des outils MCP et le payload des vues** changent de concert pour le connecteur hébergé et les runtimes qu'il contacte ([section 122](#122-mcp-tools-are-named-for-tables)).
- **Restrictions délibérées.** Les colonnes d'audit (colonnes `.onCreateNow()` / `.onUpdateNow()`) sont désormais masquées par défaut des colonnes de liste du panneau : une liste migrée affichant `created_at` perd cette colonne jusqu'à ce que vous ajoutiez `fields: { created_at: { hidden: false } }` dans son `customizeTable`. Le codemod refuse, avec justification, les tableaux JSON de type tuple, un `vector` / `binary` / `reference` dans une map, `databaseId` sur une collection Postgres, `isId: "cuid"`, une relation `isId` isolée et `disableDefaultPolicies: true` sans règles. Une relation sur une seule colonne pointant vers une table à clé composite est refusée (déclarez-la avec `rel.via()`). Les tags OpenAPI proviennent du slug et non du nom d'affichage. `rebase schema introspect` ignore les tables sans clé primaire et en explique la raison (un serveur qui introspecte la base de données continue de la servir). Une vue simple déclarant des `roles` produit une erreur de compilation ; le codemod la supprime en ajoutant une note.
- **Ce que les projets réels ont tout de même modifié à la main** — exigences minimales de la chaîne d'outils, `({ entity })` dans le code d'administration, inclusions d'une relation renommée, objets de collection modifiés à l'exécution, appels SDK sur des récepteurs non typés : [Ce que les projets ont modifié manuellement](/docs/upgrading/0-30-to-0-31-by-hand/).
- **Restauration vers un autre cluster.** L'empreinte des stratégies d'administration par défaut hache les OID des rôles ; ainsi, après un dump ou une restauration à un instant précis (PITR) sur un cluster différent, le premier `db push` ou démarrage recrée ces stratégies une seule fois, avec les mêmes noms et le même SQL.

### Le vocabulaire

| Avant | Maintenant | Où le terme « collection » subsiste |
|---|---|---|
| une collection dans `config/collections/` | une **table** dans `backend/schema/` (`defineTable`) | — |
| `properties` | `columns` (`col.*`) et `relations` (`rel.*`) | — |
| `securityRules`, `defaultSecurityRules` | `rls` (obligatoire), `defaultRls` | — |
| `callbacks`, `Property.callbacks` | `hooks`, le `.transform()` d'une colonne | — |
| le bloc `admin` | `customizeTable` dans `frontend/src/cms/` | — |
| `data.collection(slug)` | `data.table(slug)` | — |
| ce que le panneau d'administration affiche | une **collection** : une table telle que le panneau la présente, ou une collection Firestore | le CMS : `CollectionPanel`, l'Éditeur de collection, `externalCollections` |

## 108. Tables in `backend/schema` replace `config/collections` — run the codemod first

**Qui est concerné :** tout projet comportant un répertoire `config/collections/`.

**Ce qui a changé :** le backend lit uniquement `backend/schema/index.ts` et les résultats de `defineTable`, `defineAuthTable` et `defineView` qu'il exporte. Les fichiers `defineCollection` ne sont plus lus par rien : le runtime, chaque commande de la CLI et la validation de `rebase.json` refusent tout projet possédant encore `config/collections`, en indiquant la commande ci-dessous. `rls` est obligatoire sur chaque table — une liste de règles, `"admin-only"`, ou `"inherit"` pour le `defaultRls` exporté par l'index — et `disableDefaultPolicies` devient `defaultPolicies: false`.

**Que faire :**

```bash
rebase migrate collections-to-tables            # or --dry-run first
```

Il écrit une table par collection, chaque colonne physique étant explicitée à sa position d'origine (la colonne clé d'un `belongsTo` est donc explicitement générée), l'index avec le `defaultRls` issu de `defaultSecurityRules`, un `customizeTable` pour chaque collection dont la présentation n'était pas celle par défaut, et des fichiers `defineFirestoreCollection` pour les collections Firestore. Les callbacks d'une collection deviennent les `hooks` de sa table et les `.transform()` de ses colonnes ; les `callbacks` globaux exportés par `config/index.ts` constituent une étape manuelle (section 109). Il relit ensuite le résultat à travers le nouveau pipeline : DDL, stratégies (policies), recherche, vector, déclencheurs (triggers), vues et le schéma Drizzle doivent être identiques à l'octet près à ce que les collections généraient, sinon chaque fichier est restauré et l'exécution se termine avec le code 1 en affichant le diff.

Il prend également en charge ce qui nécessitait auparavant une intervention manuelle :

- **Les callbacks construits par un helper** (`callbacks: softDeleteCallbacks(...)`, ou un objet de callbacks importé) deviennent des `hooks:` avec la même expression, et les fonctions du helper sont converties en propriétés de hooks de table là où elles sont écrites (le codemod suit les imports relatifs, les `const`, les lectures de propriétés et un unique `return`). Lorsqu'il ne parvient pas à suivre le helper, une étape indique les hooks à vérifier.
- **Une fonction `storagePath`** migre en deux parties : la fonction devient le `storage.path` de la personnalisation, afin que le panneau détermine toujours la destination d'un téléversement, et le modèle de `path` de la colonne prend la forme des clés qu'elle renvoie — le texte statique de son template literal où chaque `${…}` devient `{path}` (`` `${owner}/cv` `` → `{path}/cv`). Le serveur applique désormais `maxBytes` et `accept` de la colonne à chaque téléversement dont la clé correspond à ce modèle, et pas seulement à ceux nommant la colonne, rendant les limites plus strictes qu'en 0.30. Une fonction dont le résultat ne contient aucun texte statique est refusée : ajoutez-en un au préalable.
- **Un `policy.existsIn({ collection })` de la 0.30** conserve sa table, et `auth: { collection: usersCollection }` dans une entrée backend personnalisée est supprimé (la déclaration `defineAuthTable` est la table d'authentification). L'option de démarrage `collections` devient `schemaDir`.
- **Un constructeur `dynamicProps`** renvoie une personnalisation de champ avec des clés plates en 0.31 (`{ readOnly: true }`, et non `{ admin: { readOnly: true } }`). Le codemod réécrit les constructeurs dont les retours sont des objets littéraux, en ligne ou dans un module partagé, et liste tous les autres.
- **La présentation déstructurée depuis un objet partagé unique** est intégrée dans la personnalisation (`….dynamicProps`) ; la présentation calculée par une fonction d'emballage (wrapper) constitue une étape à vérifier, sans bloquer le projet. Le chemin d'un composant est résolu par rapport au module qui l'a écrit, et une valeur calculée lors du chargement de `config/` (`new Date()`, `Date.now()`, la lecture d'une variable d'environnement) est conservée sous forme d'expression, sans jamais être figée à la valeur d'exécution.
- **Les collections Firestore construites par une fonction** (un `getAllFirestoreCollections()` que l'application propage dans le panneau) sont converties en `defineFirestoreCollection` une par une lorsque le fichier d'une collection contient son littéral ; une étape par constructeur indique le reste et la structure à écrire, et une autre indique une référence écrite en dehors d'un littéral converti, qui mentionnerait encore `path`.
- **Les imports de `config/` via un alias de chemin** (une entrée `paths` de tsconfig, un `resolve.alias` de Vite) sont réécrits ou listés comme des imports relatifs, et un `storageAuthorize` réexporté par `config/index.ts` est reporté dans `backend/storage.ts`.
- **Une relation renommée en `<key>Relation`** conserve son libellé, sa colonne de liste et son titre : la personnalisation référence la nouvelle clé. Le code qui l'inclut ne suit pas automatiquement ([ce qu'il faut changer](/docs/upgrading/0-30-to-0-31-by-hand/#a-belongsto-key-is-a-column-and-a-relation-can-be-renamed)).

Ce qu'il ne peut pas reporter à l'identique est refusé avec mention du fichier et de la ligne, et rien n'est écrit : une collection construite par appel de fonction, un spread ou accesseur impossible à analyser, un moteur autre que Postgres ou Firestore, un fichier de sortie déjà existant avec un contenu différent (déplacez-le ou utilisez `--force`). Un arbre git non propre (dirty) ou un projet hors git est également refusé, de sorte que la migration constitue un unique diff vérifiable. `--json` affiche l'intégralité du rapport pour un script ou un agent. Voir [`rebase migrate`](/docs/cli/schema/#rebase-migrate) et [Tables](/docs/schema/).

Les tables générées écrivent leurs colonnes selon la syntaxe de `pg-core` de Drizzle — `col.varchar({ length: 160 })`, `col.timestamp({ withTimezone: true })`, `col.text().array()`, `pgEnum(...)`, `` .default(sql`…`) ``, `.generatedByDefaultAsIdentity()` — leur sortie ne requiert donc rien de plus ; voir [Colonnes](/docs/schema/columns/). Une table écrite manuellement avec une préversion de la 0.31 selon les anciennes syntaxes (`col.timestamptz()`, `col.varchar(160)`, `col.array(col.text())`, `col.enum(values, { name })`, `.defaultSql()`, `.identity()`, `.column("…")`) ne compile plus : `tooling/scripts/drizzle-sweep.mts` dans le dépôt Rebase la convertit en réécrivant uniquement les chaînes de constructeurs, et prouve avec `--verify` que chaque table convertie compile vers le même descripteur (`npx tsx drizzle-sweep.mts --verify backend/schema`).

La passe `sdk-calls` qui suit réécrit également les sources des règles : `existsIn({ collection })` et `membership: { collection }` deviennent `table` (section 123) ; `--skip-sdk-calls` ignore également cette étape. Ce qui vous incombe est affiché sous forme d'étapes manuelles numérotées, et lorsque le projet possède des compétences d'agent installées, la dernière est la ligne `rebase skills install` qui les actualise (section 128). Un simple `rebase migrate` affiche l'aide des deux sous-commandes.

## 109. There is no config package

**Qui est concerné :** chaque projet — `config/` constituait un workspace à part entière.

La version 0.31 cesse de lire `config/collections` ; elle n'interdit pas pour autant `config/`. Le codemod supprime ce que Rebase lisait — les fichiers de collection et les raccordements qu'il déplace vers `backend/` (`resources.ts`, `storage.ts`, `generated/register.ts`, et leurs réexports dans `config/index.ts`) — et laisse vos propres modules dans `config/` là où ils sont, importables comme auparavant : `config/` reste un paquet de l'espace de travail, et le backend compile toujours `../config/**/*`. Seuls les imports des éléments supprimés sont réécrits : un fichier de collection importé par le code backend pointe vers le module de la table (une étape liste les usages qui le lisent sous forme d'objet) ; importé par le code frontend, il devient un import de type de la table lorsqu'il n'est utilisé qu'en tant que type, ou une étape nommant la personnalisation ; un helper situé dans `config/collections` est copié à côté du code qui en a besoin.

**Ce qui a changé :** ce qui résidait aux côtés des collections migre dans `backend/` :

| Avant | Maintenant |
|---|---|
| `config/resources.ts` | `backend/resources.ts` |
| `config/storage.ts`, `storageAuthorize` depuis `config/index.ts` | `backend/storage.ts` |
| `callbacks` exportés depuis `config/index.ts` | `hooks` exportés depuis `backend/hooks.ts` (`TableHooks` : `table` pour `collection`, `values` pour `row`) |
| `config/generated/register.ts` | `backend/generated/register.ts` |
| `config` dans `rebase.json`, `usersCollection` | `tables` (`backend/schema` par défaut) ; la table d'authentification est celle déclarée avec `defineAuthTable` |

Le runtime lit `storageAuthorize` et `hooks` et rien d'autre dans ces modules ; tout autre export est signalé au démarrage. Le frontend importe `backend/**` sous forme de types uniquement — `pnpm check:frontend-backend-imports` refuse un import de valeur, qui expédierait du code serveur vers le navigateur.

**Que faire :** le codemod déplace `resources.ts`, `storage.ts` et l'enregistrement, et réécrit `rebase.json`, `package.json`, `pnpm-workspace.yaml` et `backend/tsconfig.json`. Les `callbacks` globaux constituent une étape manuelle qu'il affiche : déplacez-les manuellement dans `backend/hooks.ts`, et ajoutez `hooks.ts` dans le `include` de `backend/tsconfig.json` afin que `tsc` le vérifie. Exécutez ensuite la ligne `git rm` qu'il affiche : `git rm -r config/collections …`, ou `git rm -r config` lorsqu'il ne reste plus rien de votre cru.

## 110. Boot options and hooks name tables

**Qui est concerné :** un backend que vous démarrez vous-même (`initializeRebaseBackend`, `createRebaseBackend`), et le code qui attache des hooks après le démarrage.

**Ce qui a changé :**

| Avant | Maintenant |
|---|---|
| `collections`, `collectionsDir` | `tables`, `defaultRls`, `schemaDir` |
| `callbacks` | `hooks` |
| `auth.collection` | supprimé : le `defineAuthTable` dans `tables` |
| `backend.setCollectionCallbacks(slug, cb)` | `backend.setTableHooks(slug, hooks)` |
| propriétés de hook `collection`, `row` | `table` (le descripteur), `values` |
| `composeCallbacks` | `composeTableHooks` de `@rebasepro/common` |
| `openRebase({ collections, callbacks })` | `openRebase({ tables, hooks })`, `tables` issu de `compileSchema([...])` |
| `OpenedRebase.collections` ; la variable `collections` dans `rebase console` | `.tables` ; `tables` |

```diff ts
-await initializeRebaseBackend({ app, server, collectionsDir: "./config/collections", callbacks });
+await initializeRebaseBackend({ app, server, schemaDir: path.resolve(__dirname, "../schema"), hooks });
```

Les hooks attachés à un objet de collection passé sur un point d'appel ne s'exécutent plus : le pilote (driver) exécute les hooks des tables qu'il sert, attachez-les donc avec `setTableHooks`.

**Que faire :** `rebase migrate sdk-calls` réécrit `setCollectionCallbacks` et adapte les propriétés des hooks, et liste chaque objet d'options backend à mettre à jour manuellement. Un script qui ouvre les données compile ses tables :

```diff ts
-const rebase = await openRebase({ databaseUrl, collections, callbacks });
+const rebase = await openRebase({ databaseUrl, tables: compileSchema([products, orders]), hooks });
```

Voir [Scripts](/docs/backend/scripts/#openrebase). Voir [Présentation du backend](/docs/backend/) et [Hooks globaux](/docs/backend/hooks/).

## 111. The admin panel renders the tables the server serves

**Qui est concerné :** tout frontend qui monte `<RebaseCMS>`.

**Ce qui a changé :** `<RebaseCMS collections>` n'existe plus. Le panneau affiche chaque table servie par le backend sur `GET /api/schema/tables`, sans fichier individuel par table, puis `externalCollections` (Firestore). `tableCustomizations` prend les objets `customizeTable` issus de `frontend/src/cms/`. Le plugin Vite pour les collections et `virtual:rebase-collections` sont supprimés. `CollectionsProvider` accepte les trois mêmes entrées (`tableCustomizations`, `externalCollections`, `tables`).

```diff tsx
-import { collections } from "virtual:rebase-collections";
-<RebaseCMS collections={collections}/>
+import { postsCms } from "./cms/posts";
+<RebaseCMS tableCustomizations={[postsCms]}/>
```

**Que faire :** le codemod écrit `frontend/src/cms/index.ts`, qui exporte `tableCustomizations` (et `externalCollections`), et le monte automatiquement dans le `App.tsx` d'un scaffold ; un fichier `App.tsx` non reconnu, le plugin dans `vite.config.ts` et la déclaration de module virtuel font l'objet d'étapes manuelles affichées en sortie. Voir [Personnaliser une table](/docs/frontend/customize-table/).

## 112. Bundle format 3; format-2 bundles are refused

**Qui est concerné :** tout déploiement d'un bundle compilé — auto-hébergé avec l'image runtime ou sur Rebase Cloud.

**Ce qui a changé :** le schéma d'un bundle est `entry.tables`, aux côtés de `entry.resources`, `entry.storage` et `entry.hooks` ; `bundleFormat` passe à 3 et le contrat du runtime à 2. Un bundle au format 1 ou 2 embarque `config/collections`, qu'un runtime 0.31 ne sait plus lire ; il refuse donc de démarrer en affichant la commande du codemod dans le message d'erreur plutôt que d'introspecter la base de données et de servir une API différente.

**Que faire :** migrez le code source, puis lancez `rebase build` et déployez. Sur Rebase Cloud, le déploiement du dépôt migré déclenche sa reconstruction. Voir [Runtime et bundles](/docs/architecture/runtime-and-bundles/).

## 113. The schema version is computed from tables (`v2:`)

**Qui est concerné :** toute base de données provisionnée par un runtime antérieur à 0.31, et tout SDK généré.

**Ce qui a changé :** la version de schéma hache les descripteurs de tables compilés et commence par `v2:`. Une base de données estampillée `v1:` signale une seule fois le changement de modèle — le log de démarrage et `rebase doctor` l'indiquent ainsi que la manière de la réestampiller — et chaque SDK généré est signalé obsolète une seule fois.

**Que faire :** provisionnez une première fois avec le nouveau runtime : démarrez le processus qui détient le schéma ou exécutez `rebase db push`. Avec `REBASE_REQUIRE_SCHEMA_MATCH=true`, réestampillez avant de basculer les autres processus. Régénérez le SDK.

**Ce qui a changé :**

| Avant | Maintenant |

| `COLLECTION_READ_ONLY` (405) | `TABLE_READ_ONLY` |

**Que faire :** `rebase migrate sdk-calls` réécrit les chaînes littérales. Voir [Erreurs](/docs/backend/errors/).

## 115. The SDK addresses a table: `data.table(slug)`

**Qui est concerné :** chaque client, fonction, cron, hook et script qui désigne une table par son slug ou transmet le dictionnaire généré.

**Ce qui a changé :**

| Avant | Maintenant |
|---|---|
| `data.collection(slug)` | `data.table(slug)` |
| `createRebaseClient({ collections: collectionsDictionary })` | `createRebaseClient({ tables: tablesDictionary })` |
| `CollectionName`, `CollectionsDictionary` générés | `TableName`, `TablesDictionary` |
| batch `{ op, collection }` (SDK et `POST /api/data/_batch`) | `{ op, table }` |

```diff ts
+const { data } = await client.data.table("posts").find();
```

Les accesseurs typés (`client.data.posts`) restent inchangés.

**Que faire :** le codemod exécute `rebase migrate sdk-calls` sur votre code — exécutez-le seul sur un projet déjà migré — puis lancez `rebase generate-sdk`. Un appel `.collection(` dont le récepteur n'est pas le SDK est conservé tel quel et listé. Voir [SDK typé](/docs/sdk/).

## 116. CLI flags: `--schema-dir`, not `--collections`

**Qui est concerné :** les scripts et étapes de CI qui appellent la CLI avec un chemin de schéma.

**Ce qui a changé :** `--collections` / `-c` sont refusés sur toutes les commandes lisant le schéma, avec mention du codemod dans le message (`generate-sdk` ignore un `--collections-dir` résiduel) ; `--schema-dir` permet d'indiquer un répertoire de schéma autre que `backend/schema`. `rebase schema introspect` écrit des fichiers `defineTable` dans `backend/schema/` — `--output` est supprimé. `REBASE_STRICT_COLLECTION_CONFIG` n'est plus pris en compte : un schéma qui ne compile pas refuse systématiquement le démarrage.

**Que faire :** remplacez les options. Voir [CLI](/docs/cli/) et [Génération de schéma](/docs/cli/schema/).

## 117. The schema editor edits `backend/schema` with `TablePatch`

**Qui est concerné :** le code qui appelle les routes de l'éditeur de schéma ou de schéma en direct (live-schema), ainsi que les déploiements définissant les variables d'édition en direct.

**Ce qui a changé :** `/api/admin/schema-editor/collection/save`, `collection/delete`, `property/save` et `property/delete` sont supprimés. L'éditeur expose `GET /tables`, `POST /preview` et `POST /apply`, et les routes `/plan` et `/apply` de l'édition de schéma en direct acceptent `{ patches: TablePatch[] }` au lieu d'une collection ou d'un patch de collection. `REBASE_LIVE_SCHEMA_COLLECTIONS_PATH` est refusé au démarrage : il est remplacé par `REBASE_LIVE_SCHEMA_PATH` (`backend/schema` par défaut), et `liveSchema.repository.collectionsPath` devient `schemaPath`. La présentation n'est jamais une modification de schéma : elle est enregistrée sous forme de préférences d'interface (`/api/admin/ui-config`). Une modification dont le fichier a changé sur le disque après sa préparation (sauvegarde dans un IDE, autre processus) renvoie 409 `SCHEMA_EDIT_STALE_FILE` sans rien écrire ; elle renvoyait auparavant 400 `SCHEMA_EDIT_REFUSED`.

**Que faire :** renommez la variable ; réécrivez tout appelant de ces routes pour envoyer des modifications `TablePatch`, et rechargez en cas de `SCHEMA_EDIT_STALE_FILE`. Voir [Édition de schéma en direct](/docs/backend/live-schema-editing/).

## 118. A component slot is a component

**Qui est concerné :** les personnalisations qui référençaient un composant React par un chemin sous forme de chaîne de caractères ou par un thunk paresseux `() => import(…)`.

**Ce qui a changé :** `Field` / `Preview` / `Filter` d'un champ, les `Actions` d'une collection, `entityViews[].Builder`, `collectionViews[].Builder`, `formView.Builder` ainsi que les surcharges de composants acceptent directement le composant lui-même. `ComponentRef`, `ComponentLike`, `LazyComponentRef` et `isLazyComponentRef` (`@rebasepro/types`), `asComponentRef` et `asReactComponent` (`@rebasepro/cms-types`) ainsi que `resolveComponentRef` / `useResolvedComponent` (`@rebasepro/app`) sont supprimés. `customizeTable` refuse une chaîne ou un thunk avec le message « imported by value ».

**Que faire :** importez le composant dans le fichier `frontend/src/cms/` et transmettez-le directement. Voir [Champs personnalisés](/docs/frontend/custom-fields/).

## 119. Panel preferences are UI preferences

**Qui est concerné :** le code qui implémente `UserConfigurationPersistence`.

**Ce qui a changé :** la façon dont un utilisateur redimensionne ou réordonne une table est un delta `UiTablePreferences` : `getTablePreferences` / `saveTablePreferences` remplacent `getCollectionConfig` / `onCollectionModified`, et le type partiel de configuration de collection qu'il acceptait est supprimé. Le stockage du navigateur les conserve sous `table_preferences::<slug>`, et ignore ce qu'un ancien panneau stockait, de sorte que la largeur des colonnes et les modes de vue de chaque utilisateur sont réinitialisés une fois. `userSelect` sur un champ disparaît : une colonne `.userId()` fait office de sélecteur d'utilisateur.

Le pont de Studio s'aligne : `StudioSchemaEditing.updateCollection` devient `applyTablePatches(slug, patches)`, et l'éditeur de collection envoie `{ patches }` à l'éditeur de schéma.

**Que faire :** adaptez toute persistance personnalisée aux deux méthodes, et tout `StudioSchemaEditing` personnalisé vers `applyTablePatches`.

## 120. MongoDB is retired

**Qui est concerné :** un projet utilisant `@rebasepro/server-mongo`, ou déclarant `database(…, { engine: "mongodb" })`.

**Ce qui a changé :** le paquet est supprimé, tout comme les types de collection Mongo et le reste du modèle Mongo. Postgres est le seul moteur côté serveur : une source de transport serveur sur un autre moteur refuse de démarrer, en le nommant explicitement.

**Que faire :** migrez vos données vers Postgres. Il n'existe pas de voie de migration interne à Rebase.

## 121. Firestore collections live in the frontend

**Qui est concerné :** un projet hybride comportant des collections `engine: "firestore"`.

**Ce qui a changé :** une collection Firestore est une source CMS que le navigateur lit directement : `defineFirestoreCollection` de `@rebasepro/firebase`, dans `frontend/src/cms/`, passée à `<RebaseCMS externalCollections>`. Une référence entre Firestore et une table Postgres est stockée sous forme de l'identifiant de la cible, et une référence Firestore dont le `path` est également un slug Postgres cible désormais la table Postgres.

**Que faire :** le codemod écrit les fichiers `defineFirestoreCollection`. Pointez une référence vers une collection Firestore via le slug de cette collection. Voir [Firebase](/docs/frontend/firebase/).

## 122. MCP tools are named for tables

**Qui est concerné :** les prompts, scripts et listes d'autorisation qui nomment des outils MCP.

**Ce qui a changé :** sur le `/mcp` distant : `list_collections`, `describe_collection`, `query_collection`, `show_collection`, `count_documents`, `aggregate_documents`, `get_document`, `create_document`, `update_document`, `delete_document` → `list_tables`, `describe_table`, `query_table`, `show_table`, `count_rows`, `aggregate_rows`, `get_row`, `create_row`, `update_row`, `delete_row` ; l'argument `collection` devient `table`, et `show_app` / `save_app` prennent `tables`. Sur le serveur local : `list_documents` → `query_table`, `get_document` → `get_row`, `create_document` → `create_row`, `update_document` → `update_row`, `delete_document` → `delete_row` ; `rebase_schema_plan` prend `patches` ; les ressources deviennent `rebase://tables/{name}`. Le payload des vues de MCP Apps passe en version 3 : descripteurs de tables caviardés selon l'appelant, autorisations par table, et préférences d'interface de chaque appelant sous `preferences` (`file`, `workspace`, `user` ; une clé d'API ne possède pas de couche utilisateur), avec des blocs et des seeds nommant `table`. La vue `collection-table` est supprimée. `list_tables` n'a pas de `title` ; `describe_table` ajoute `primaryKey`, `relations`, le `rls` de l'appelant, `title` et `presentation`.

**Que faire :** renommez. La vue et le serveur doivent communiquer avec la même version de payload : un connecteur hébergé et les runtimes qu'il contacte doivent être mis à niveau ensemble, et une vue MCP construite par le projet doit être reconstruite avec les paquets 0.31. Voir [Référence des outils MCP](/docs/ai/mcp-tool-reference/) et [MCP distant](/docs/ai/remote-mcp/).

## 123. The rule vocabulary says `table`

**Qui est concerné :** les règles utilisant `policy.existsIn` ou un tenant d'appartenance (membership tenant), ainsi que les règles combinant `access` avec d'autres clauses.

**Ce qui a changé :** `policy.existsIn({ collection, where })` devient `existsIn({ table, where })`, et `tenant.from.membership.collection` devient `membership.table` ; les noms des stratégies (policies) ne changent pas. Quatre formes de règles accordent désormais des droits différents, dont deux accordent davantage ([le tableau ci-dessus](#à-examiner-avant-de-déployer--ces-règles-changent-de-signification)) : un simple `{ access: "authenticated" }`, qui n'accordait rien, admet désormais chaque appelant connecté, et les tables de jonction associées obtiennent leurs stratégies d'écriture d'arête (edge-write policies). Les règles combinant des clauses que le type `SecurityRule` exclut, ou comportant une valeur `access`, `mode`, `operation` ou `roles` invalide, sont refusées.

**Que faire :** le codemod renomme les clés, refuse les règles invalides en indiquant leur fichier et leur ligne, et liste les règles dont le sens change sous « Review before deploying ». Pour chacune, conservez-la, écrivez `access: "registered"` (appelants connectés titulaires d'un compte), ou supprimez-la. Examinez ensuite `rebase db push --dry-run` et `rebase doctor --policies` sur votre base de données.

**Ce qui a changé :** chaque outil conscient du schéma lit `GET /api/schema/tables` ; face à un runtime qui ne le propose pas, ils affichent un avis de mise à niveau. La partie déclarée de l'éditeur de RLS correspond à ce que le serveur a compilé. Un script de console JS reçoit `context.tables` (au lieu de `context.collections`).

**Que faire :** mettez à niveau le runtime en même temps que le panneau. Voir [Studio](/docs/studio/).

## 128. The agent skill `rebase-collections` is `rebase-tables`

**Qui est concerné :** un projet ayant les compétences d'agent installées, ainsi que les prompts ou fichiers d'instructions qui nomment la compétence.

## 129. `useJsonCollectionsConfigController` is removed

**Qui est concerné :** un projet stockant des définitions de collections sous forme de JSON via `@rebasepro/cms`.

**Ce qui a changé :** `useJsonCollectionsConfigController` a disparu, ainsi que son type d'options et la classe de stockage JSON sous-jacente. Le schéma d'une table réside dans `backend/schema`, et sa présentation dans le panneau réside dans les préférences d'interface : `frontend/src/cms/ui-config.json` en développement, et la table `rebase.ui_preferences` en déploiement.

## 130. `rebase build` refuses a frontend without `rebaseBackendGuard()`

**Qui est concerné :** tout projet disposant d'un frontend.

**Ce qui a changé :** le frontend ne peut importer `backend/` que sous forme de types. Un import de valeur introduirait du code serveur — des hooks, et tous les secrets qu'ils lisent — dans le bundle du navigateur. `rebaseBackendGuard()` de `@rebasepro/app/vitePlugin` fait échouer `vite build` et `vite dev` dès qu'un module frontend résout vers `backend/`, en nommant l'importateur, l'import et le fichier, après résolution des alias, des chemins tsconfig, des paquets et chemins absolus, des globs, de `?raw`, des réexports et des imports dynamiques. `rebase build`, ainsi que le build frontend exécuté par `rebase cloud deploy`, refusent tout frontend dont la configuration Vite ne l'utilise pas ; `rebase dev` émet un avertissement ; `rebase verify` signale `cms-backend-guard-missing`.

**Que faire :** le codemod l'ajoute automatiquement au fichier `frontend/vite.config.ts` d'un scaffold, et affiche les lignes à ajouter pour toute autre configuration :

```diff ts
+import { rebaseBackendGuard } from "@rebasepro/app/vitePlugin";

 export default defineConfig({
-    plugins: [react()],
+    plugins: [react(), rebaseBackendGuard()],
 });
```

Transformez ensuite tout import de valeur depuis `backend/` en `import type`.

## 131. Rows on the wire follow their column

**Qui est concerné :** les clients qui lisent des clés étrangères ou nomment des relations, et les écritures qui envoient des colonnes générées ou des objets JSON partiels.

**Ce qui a changé :** les valeurs traversent le codec de leur colonne en sortie et les règles de leur colonne en entrée.

- Une colonne de clé étrangère `bigint` ou `numeric` générée par une relation, que Postgres renvoie sous forme de texte, est servie sous forme de **nombre** dans l'API REST, le SDK et le panneau d'administration. Les clés déclarées comme nombres l'étaient déjà.
- Les éléments d'un tableau natif **sont servis selon leur type scalaire respectif**, dans l'API REST, le SDK, le socket et le pilote (driver) :

  | Colonne | 0.30 servait | 0.31 sert |
  |---|---|---|
  | `timestamptz[]` | `["2026-01-02 11:00:00+01"]` | `["2026-01-02T10:00:00.000Z"]` |
  | `numeric[]` (un pilote ouvert sans le réglage numérique au démarrage : tests, scripts) | `["1.50", "2.25"]` | `[1.5, 2.25]` |
  | `bigint[]` avec un élément null | `[1, 0, 3]` | `[1, null, 3]` |
  | `date[]`, `timestamptz[]` ou un tableau d'enum avec un élément null | `["2026-01-02", "NULL"]` | `["2026-01-02", null]` |

  `date[]`, `time[]`, `text[]`, `uuid[]`, `boolean[]`, `integer[]` et `double precision[]` sont servis comme auparavant. Ce qui est stocké ne change pas : une ligne lue puis réenregistrée stocke le même tableau.
- Une relation nommée dans `include`, un filtre ou un tri doit correspondre à son **nom exact**. Les tentatives de secours avec le slug et la graphie en snake_case sont supprimées.
- Une colonne générée est refusée en écriture et omise du schéma d'entrée OpenAPI.
- Un champ obligatoire à l'intérieur d'un objet JSON est imposé ; `$inc` et les éléments de tableau sur une colonne entière doivent être des nombres entiers.

**Que faire :** lisez les clés étrangères sous forme de nombres là où vous compariez des chaînes, parsez les éléments de `timestamptz[]` selon la norme RFC 3339 et traitez un élément de tableau nul comme `null`, et respectez scrupuleusement la casse et l'orthographe des noms de relation tels que la table les déclare (ses clés `relations`). Cessez d'envoyer des colonnes générées.

## 132. History is served as reads

**Qui est concerné :** les lecteurs d'instantanés d'historique (history snapshots), et quiconque implémente un `DataDriver`.

**Ce qui a changé :** les entrées d'historique sont servies sous forme de lectures : l'accès aux champs d'abord, puis `afterRead` (global, table, colonne). Une colonne masquée par un hook ou un `.transform({ afterRead })` est masquée dans chaque instantané, une colonne que l'appelant ne peut pas lire est exclue et omise de `changed_fields`, les clés des colonnes supprimées sont écartées, et un rétablissement (revert) n'écrit jamais une colonne que l'appelant n'a pas le droit de lire. Un hook qui lève une exception sur un instantané ancien fait échouer la requête. La version 0.30 servait les valeurs brutes stockées : un projet comportant de l'historique et des hooks de masquage doit donc être mis à niveau.

Une entrée contient la ligne telle que `GET /api/data/<table>/<id>` la lit sans `include` : valeurs simples, un `belongsTo` sous forme de sa clé étrangère. Une entrée qu'une version antérieure a enregistrée avec le modèle de vue du panneau d'administration est servie, et rétablie, comme cette ligne : une enveloppe `{ "__type": "date", "value" }` comme valeur, une référence `{ "__type": "relation" }` d'une relation propriétaire comme clé étrangère sous le nom propre de la clé, et toute autre référence comme clé de la ligne liée. La version 0.30 servait ces références telles qu'écrites.

Un pilote sert l'historique via `DataDriver.serveStoredRows(path, rows)`, au sein de la transaction en lecture seule de l'appelant ; les routes d'historique renvoient 501 pour un pilote qui ne l'implémente pas, garantissant que l'historique n'est jamais servi non masqué.

**Que faire :** rien pour le pilote Postgres fourni. Un pilote personnalisé doit implémenter `serveStoredRows`. Voir [Historique](/docs/backend/history/).

## 134. `@rebasepro/server-postgres` exports name tables

## 135. `@rebasepro/types` and `@rebasepro/common` drop the collection model from their roots

**Qui est concerné :** le code important des types de collection ou de propriété, des helpers du panneau d'administration ou le lift depuis `@rebasepro/types` ou `@rebasepro/common` — champs personnalisés, vues personnalisées, plugins, tests avec fixtures de collection — et les pilotes personnalisés implémentant le registre.

**Ce qui a changé :** les paquets centraux (kernel) décrivent désormais exclusivement des tables. Ce qui décrit une collection telle que le panneau d'administration la dessine réside dans `@rebasepro/cms-types` :

- **Types** ayant migré depuis `@rebasepro/types` : `CollectionConfig`, `PostgresCollectionConfig`, `FirebaseCollectionConfig`, `AnyCollectionConfig`, chaque `…Property` (`StringProperty`, `NumberProperty`, `ArrayProperty`, …) et `Properties`, `CollectionCallbacks` et ses propriétés de hooks, les types de relations 0.30 et leurs formes `Resolved…`, `CollectionIndex`, les couleurs de puces (`ColorScheme`, `ColorKey`, …), `FieldAccess`, `EnumValues`.
- **Helpers** ayant migré depuis `@rebasepro/common` : les helpers de stratégies au format collection (`policyToPostgres`, `compileRulePolicies`, `getEffectiveSecurityRules`, `getGeneratedPolicyNames`, …), `CollectionRegistry`, `resolveCollectionRelations`, `resolveRelation`, `getTableName`, `findRelation`, `rowToViewModel`, `resolvePrimaryKeys`, la vue d'accès aux champs d'une propriété (`effectiveAccess`, `canReadField`, `canWriteField`), `evaluateCondition`, `canEditEntity`, `resolveProperty`, `getDefaultValuesFor`, `getSubcollections`, `getCopyValues`, `enumToObjectEntries`. Une règle compilée depuis une expression simple utilise `compilePolicyExpression(expr)` de `@rebasepro/common`.
- **`composeCallbacks`** compose les callbacks d'une collection pour le panneau et a migré vers `@rebasepro/cms-types` ; `@rebasepro/server` ne le réexporte plus. Le code backend compose les hooks d'une table avec `composeTableHooks` de `@rebasepro/common`, et le codemod liste un import backend de `composeCallbacks` sous forme d'une étape manuelle l'indiquant.
- **`defineCollection`** est supprimé de `@rebasepro/common` et `@rebasepro/cms-types` : déclarez la table avec `defineTable` dans `backend/schema` et personnalisez-la avec `customizeTable` dans `frontend/src/cms` ; une collection Firestore utilise `defineFirestoreCollection` de `@rebasepro/firebase`.
- **L'accesseur du panneau d'administration et ses types** : `Entity`, `EntityValues`, `TableAccessor`, `TableTrashAccessor`, `FindResponse`, `QueryBuilderInterface`, `RebaseData` et `AuthState` ont quitté `@rebasepro/types` ; `buildRebaseData`, `wrapAsEntityData`, `buildRoutedRebaseData`, `EntityDataOptions`, `QueryBuilder`, `RelationRef` et `createRelationRef` ont quitté `@rebasepro/common`. Tous s'importent depuis `@rebasepro/cms-types`. La couche de données propre au SDK — `buildSdkData`, `createDriverTableRows`, `buildRoutedSdkData`, dans `@rebasepro/common` — sert directement les lignes et renvoie ce qu'elle renvoyait auparavant.
- **`EntityDataOptions.resolveCollection`** est remplacé par `primaryKeysOf`, `viewModelOf`, `storedValuesOf` et `viewModelSourceOf` ; `collectionEntityDataOptions(resolveCollection, { resolveDataPath, resolveAccessor })` de `@rebasepro/cms-types` les construit.
- **Le convertisseur de migration (lift)** (`collectionsToTableDefs`, `collectionToTableDef`, `LiftNote`, `LiftResult`, `LiftOptions`) a migré vers `@rebasepro/common/migrate`, aux côtés d'une copie figée du modèle de collection 0.30 (types `Legacy…`) et de `defineLegacyCollection`.
- **Également supprimés des racines du noyau**, chacun étant listé par le codemod sous forme d'une étape manuelle : l'API de patch de collection de `@rebasepro/types` (`CollectionPatch`, `CollectionPatchOp`, `applyCollectionPatch`, `collectionPatchProblems`, `isCollectionPatch`, `nestCollectionPatchPaths` → `TablePatch`), ses helpers JSON de collection (`diffCollections`, `diffJsonValues`, `toCollectionJson`, `RUNTIME_ONLY_COLLECTION_KEYS`, `runtimeOnlyKeyIn`), les éléments de l'époque Mongo `DocumentAdmin`, `isDocumentAdmin` et la capacité `supportsDocumentAdmin`, ainsi que `RebaseProjectContract.collectionSlugs` / `.collections` / `.generatedAt` (`/api/meta/contract` sert `tables`) ; de `@rebasepro/common`, `buildTenantSecurityRule` → `tenantSecurityRule`, `defaultPoliciesDisabled` → `tableDefaultPoliciesDisabled`, `restoresSoftDeletedRow` → `isSoftDeleteRestore`, `softDeleteFieldOf` → `softDeleteColumn`, `getJunctionConfigForRelation` → `resolveTableJunctions`, et `isRelationRequired`, `relationDeclaringProperty`, `requireCallbackCollection` sans successeur (lisez le `TableDescriptor`).
- **Le registre d'un pilote** est une `TableRegistryInterface` (auparavant `CollectionRegistryInterface`) : `setGlobalHooks?` et `setTableHooks?` remplacent `getGlobalCallbacks` / `setGlobalCallbacks?`. `globalHooksAsCallbacks`, `resolveDriftCheckName` et `PENDING_TABLE_FEATURES` sont supprimés.

**Que faire :** `rebase migrate sdk-calls` (intégré à `collections-to-tables`) déplace chaque import ci-dessous vers son nouveau paquet — fusionné dans un import de ce paquet déjà présent dans le fichier, en conservant `import type`, les `type` en ligne et les alias `as` — et ajoute le paquet aux dépendances du paquet de workspace qui l'importe ; exécutez `pnpm install` par la suite. Un import d'un nom supprimé, un import d'espace de noms (`import * as`), un `export *`, un `import()` dynamique ou un `require()` utilisant un nom déplacé fait l'objet d'une étape manuelle numérotée. Un test conservant des littéraux de collection comme fixtures les type avec les types `Legacy…` et les convertit via `@rebasepro/common/migrate`.

### Imports ayant été déplacés

Chaque nom que la version 0.31 a déplacé vers un autre paquet, ou supprimé, est répertorié sur la page [Imports ayant été déplacés en 0.31](/docs/upgrading/0-30-to-0-31-imports/), avec ce qu'il convient d'écrire pour chaque élément supprimé. Cette liste est issue de la table même que le codemod consulte, et correspond donc exactement à ce que `rebase migrate sdk-calls` réécrit.

## 136. The Postgres driver and the socket's one-shot reads return the REST row

**Qui est concerné :** une fonction ou un plugin lisant via `requireDriver(c)` / `getDriver(c)`, le code envoyant les trames de socket `FETCH_COLLECTION` / `FETCH_ONE`, et le code lisant des objets `{ __type }` depuis une réponse.

**Ce qui a changé :** il n'existe plus qu'un seul format de lecture. `fetchCollection` et `fetchOne` sur le pilote Postgres — ce via quoi lisent le `requireDriver(c)` d'une fonction, les plugins, les trames ponctuelles du socket, MCP et le simulateur RLS — renvoient ce que `GET /api/data/<table>` renvoie :

| Valeur | Lecture par le pilote en 0.30 | 0.31 |
|---|---|---|
| un timestamp | `{ "__type": "date", "value": … }` | une chaîne RFC 3339 |
| un `belongsTo` | `{ "__type": "relation", "id", "path" }` sous le nom de la relation | la clé étrangère sous sa propre clé (`authorId`) |
| une ligne liée | chaque relation chargée par `fetchOne` | uniquement une relation nommée dans `include`, sous forme de la propre ligne de la cible |
| un vecteur, un `bytea` | `{ "__type": "Vector" }`, une data URL | comme REST les sert |

`FetchOneProps` prend `include` (`ListenOneTarget` est supprimé : utilisez `FetchOneProps`). `rebase.data`, `context.data` et le SDK renvoyaient déjà ce format et restent inchangés.

`@rebasepro/client` lit les corps REST et les trames de socket comme du JSON brut : une valeur comportant une clé `__type` n'est plus convertie en `Date`, `EntityReference`, `EntityRelation`, `GeoPoint` ou `Vector`, et un document JSON contenant une clé `__type` est renvoyé tel qu'il est stocké.

**Que faire :** lisez la ligne brute : analysez les dates à partir de leurs chaînes de caractères, lisez une clé étrangère depuis sa propre clé, et transmettez `include` pour chaque relation que vous lisez :

```diff ts
-const article = await requireDriver(c).fetchOne({ path: "articles", id });
-const authorId = article?.author.id;      // a { __type: "relation" } ref
+const article = await requireDriver(c).fetchOne({ path: "articles", id, include: ["author"] });
+const authorId = article?.authorId;
```

## 138. The backend accepts the values the REST API documents, and nothing else

**Qui est concerné :** un client qui écrit une relation vers-un (to-one) sous la forme d'un objet ou un vecteur sous la forme `{ value }`, le code qui filtre sur une relation avec un objet, le code qui importe les classes de valeurs de l'administration, et une application hors ligne ayant des écritures mises en file d'attente par la version 0.30.

**Ce qui a changé :** une écriture adopte le format qu'une lecture renvoie — un format d'écriture unique pour REST, le socket, MCP et le SDK in-process :

| Valeur | Accepté | Refusé désormais |
|---|---|---|
| une relation vers-un (`belongsTo`, `hasOne`, un `via` vers-un) | la clé de la ligne liée, ou `null` (`""` vaut `null`), sous le nom de la relation ou celui de la clé étrangère | un objet tel que `{ "id": 5 }` : `400 VALIDATION_INVALID_VALUE`, « 'posts.author' links one 'authors' row: write that row's key (a string or a number), or null to unlink — not an object. » |
| une relation vers-plusieurs (`hasMany`, `manyToMany`, un `via` vers-plusieurs accessible en écriture) | une liste de clés, ou de `{ id, _pivot? }` | — (les autres clés sur l'objet sont ignorées, comme auparavant) |
| un vecteur | une liste de nombres | un `Vector`, ou `{ "value": [...] }` : `400`, « 'embedding' expects a vector as a list of numbers » |
| une date, une heure | texte ISO (`Date` in-process) | — |
| un point géographique | `{ latitude, longitude }` | — |
| un `bytea` | une URL `data:application/octet-stream;base64,` (`Buffer` / `Uint8Array` in-process) | — |
| un filtre sur une relation | la clé | un objet n'est plus déroulé : il est comparé tel quel |

La version 0.30 acceptait une relation vers-un écrite sous forme d'objet et extrayait discrètement son `id` ; ce format n'a jamais été documenté et correspondait au modèle de vue du panneau d'administration. Le panneau d'administration convertit désormais son modèle de vue en valeurs réseau dans le navigateur avant chaque écriture et filtrage.

Les classes de valeurs de l'administration ont migré avec le reste de son modèle de vue : `EntityReference`, `EntityRelation`, `GeoPoint`, `Vector` et `EntityReferenceProps` s'importent depuis `@rebasepro/cms-types` (elles ont quitté `@rebasepro/types`), de même que `normalizeToEntityRelation` (qui a quitté `@rebasepro/common`) ; `withRelationReferencesOnly` est supprimé. L'historique stocke la ligne telle qu'une lecture la renvoie ; les entrées enregistrées antérieurement sont servies et rétablies sous forme de valeurs brutes ([section 132](#132-history-is-served-as-reads)).

La file d'attente hors ligne de `@rebasepro/client` stocke des valeurs réseau. Une écriture mise en file d'attente hors ligne par le SDK 0.30 est convertie lors de sa relecture et de son rejeu : aucun élément mis en file d'attente avant la mise à niveau n'est perdu.

**Que faire :** envoyez la clé : `{ "author": 5 }`, et non `{ "author": { "id": 5 } }` ; envoyez un vecteur sous forme d'une liste de nombres, et filtrez une relation par sa clé. `rebase migrate sdk-calls` déplace les imports des classes de valeurs ([la liste](/docs/upgrading/0-30-to-0-31-imports/)). Voir [Écritures](/docs/backend/writes/).

## 139. `/api/docs` is served to the schema endpoint's audience

**Qui est concerné :** une personne ou un outil lisant `/api/docs` ou ouvrant `/api/swagger` — Swagger UI, un générateur de client d'API, une étape de CI.

**Ce qui a changé :** lorsque `enableSwagger` n'est pas défini (`REBASE_ENABLE_SWAGGER` non défini), dans tous les environnements, le document OpenAPI est servi aux appelants auxquels `GET /api/schema/tables` décrit les tables, avec les mêmes refus — 401 pour un appelant anonyme sauf si `schemaTables.public`, 403 pour un identifiant dépourvu de portée de schéma ou de données — et chaque appelant reçoit le document décrivant exactement les tables, colonnes et relations que cet endpoint lui décrit (un administrateur reçoit tout). Il n'y a pas de Swagger UI. Un serveur sans authentification configurée répond `404 DOCS_UNAVAILABLE`. La version 0.30 publiait l'intégralité du document, chaque table servie et chaque colonne non privée, aux appelants anonymes en développement, et la réservait aux administrateurs en production.

| `enableSwagger` / `REBASE_ENABLE_SWAGGER` | `/api/docs` | `/api/swagger` |
|---|---|---|
| non défini (par défaut) | chaque appelant auquel l'endpoint de schéma décrit les tables : ses tables | non servi |
| `true` | l'intégralité du document, pour tout le monde | servi en dehors de la production |
| `false` | l'intégralité du document, protégé par le contrôle d'accès administrateur | non servi |

**Que faire :** appelez `/api/docs` en étant connecté. Pour publier l'intégralité du document comme le faisait la 0.30 en développement, définissez `REBASE_ENABLE_SWAGGER=true` (ou `enableSwagger: true`). Voir [Endpoints](/docs/backend/endpoints/).

## 140. A many-to-many `pivot` column may not declare `.transform()`

**Qui est concerné :** un `rel.manyToMany(…, { pivot: { … } })` dont la colonne pivot possède un `.transform()`.

**Ce qui a changé :** le compilateur la refuse (« the pivot column "x" declares `.transform()` … »). La transformation d'une colonne pivot ne s'exécutait nulle part auparavant, de sorte qu'une valeur que vous pensiez masquer était servie telle qu'elle était stockée.

**Que faire :** supprimez le `.transform()` et masquez `_pivot` dans le `hooks.afterRead` de la table cible. Voir [Relations](/docs/collections/relations/).

## 141. A link is exactly as readable and writable as its key column

**Qui est concerné :** un client qui écrit un `belongsTo` par son nom de relation, lit ou filtre une relation dont la colonne clé est restreinte, ou s'appuie sur `strictWrites: false`.

**Ce qui a changé :** une restriction sur une colonne clé est une restriction sur toute graphie qui la lit ou l'écrit.

- Écrire un lien par son nom de relation (`{ "reviewer": 7 }`) est soumis à chaque règle de la colonne clé qu'il définit — `.readOnly()`, `.private()`, `access.write`, horodatages de création, colonne de tenant, immutabilité de la clé — sur REST, en bloc (bulk), `_batch`, le socket et MCP. Écrire le lien sous les deux noms (`{ "reviewer": 7, "reviewerId": 8 }`) avec des valeurs différentes renvoie un 400 `VALIDATION_INVALID_VALUE`. Déplacer une ligne vers un autre tenant via son lien répond 400 `TENANT_IMMUTABLE` (c'était auparavant un 500).
- Une relation n'est lisible que si l'appelant est autorisé à lire chaque colonne lue par sa jointure, sur chaque table qu'elle traverse : la clé d'un `belongsTo`, la clé étrangère cible pour un `hasMany` / `hasOne`, chaque colonne sur laquelle les étapes d'un `via` se joignent. Une relation qui échoue est omise de `include` et de `_count`, et un filtre, un tri ou un chemin relationnel la traversant renvoie `FIELD_NOT_READABLE` (une relation inconnue lorsque la colonne est `.private()`). Une écriture vers-un par `via` qui copierait une colonne que l'appelant ne peut pas lire est refusée avec `FIELD_NOT_READABLE`. Les cas inverses et `via` étaient également ouverts en 0.30.x.
- Un lien dont la colonne clé ne peut pas être lue par l'appelant est omis de `include`, et un filtre, un tri, une entrée de `fields` ou un chemin relationnel le traversant répond `FIELD_NOT_READABLE` ; un lien lié à une clé `.private()` est considéré comme une relation inconnue. `GET /api/schema/tables`, OpenAPI et `describe_table` de MCP décrivent un lien conjointement à sa clé, de sorte qu'une colonne clé dont le lien est fermé y est également masquée.
- `strictWrites: false` ne décide que d'une chose : une clé non déclarée est transmise au pilote (écrite si la base de données possède la colonne, sinon 400 `VALIDATION_UNKNOWN_FIELDS`). Cela n'ouvre jamais une colonne déclarée, un horodatage (stamp), le tenant, la clé, une cible de relation ou une règle de `_pivot`.

**Que faire :** écrivez un lien sous un seul nom, ou sous les deux avec la même valeur ; lisez les liens restreints avec un rôle autorisé à lire leur clé. Voir [Accès aux champs](/docs/collections/field-access/).
