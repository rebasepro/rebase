# Mise à niveau 0.30 → 0.31

<span class="since-badge" data-since="0.31">Depuis 0.31</span>

La version 0.31 rend le backend « Postgres-first ». Les tables que vous déclarez avec `defineTable` dans `backend/schema/` sont la seule chose que le backend connaît de vos données ; ce que le panneau d'administration affiche par-dessus réside dans le frontend. Presque chaque entrée ci-dessous est une conséquence de cette séparation, et la quasi-totalité est effectuée pour vous par une seule commande.

### La checklist, par projet

1. **Mettez d'abord à niveau chaque paquet `@rebasepro`**, dans chaque paquet de l'espace de travail (workspace), afin que les types lus par le codemod soient ceux de la version 0.31 : `pnpm -r up "@rebasepro/*@0.31.0"`, puis `pnpm install`. Un projet utilisant une version antérieure à 0.30 applique d'abord les modifications de code des guides intermédiaires ([Mise à niveau](/docs/upgrading/)), et respecte les versions minimales de la chaîne d'outils de 0.31 — Node 22.22, TypeScript 6, React 19.2.7, React Router 8, Vite 8 ([la liste](/docs/upgrading/0-30-to-0-31-by-hand/#a-project-on-a-release-before-030)) : le codemod charge un dossier `config/` de la version 0.20–0.29 et sa vérification SQL réussit, mais cette vérification compare le compilateur 0.31 avec lui-même — seule l'étape 7, face à votre base de données, prouve que le DDL généré correspond à ce que possède votre base de données.
2. **Commitez, puis exécutez le codemod à blanc (dry run) :** `rebase migrate collections-to-tables --dry-run`. Il affiche les fichiers qu'il écrirait, ce qu'il refuse (avec fichier et ligne), les remarques et les étapes manuelles, et n'écrit rien. Corrigez d'abord ce qu'il refuse dans `config/`.
3. **Exécutez-le pour de vrai :** `rebase migrate collections-to-tables`. Il écrit `backend/schema/`, `frontend/src/cms/` (avec `ui-config.json`), les modules `backend/` et les fichiers du projet, ajoute `rebaseBackendGuard()` au fichier `vite.config.ts` du scaffold, réécrit vos appels SDK, déplace les imports des noms que 0.31 a déplacés vers un autre paquet ([section 135](#135-rebaseprotypes-et-rebaseprocommon-retirent-le-modèle-de-collection-de-leurs-racines)), et prouve que le SQL généré est identique à l'octet près — ou restaure chaque fichier. Voir la [section 108](#108-les-tables-dans-backendschema-remplacent-configcollections--exécutez-dabord-le-codemod).
4. **Lisez la dernière section de sa sortie, « Review before deploying: these rules change meaning »**, et tranchez pour chaque règle listée ([ci-dessous](#à-examiner-avant-le-déploiement--ces-règles-changent-de-sens)).
5. **Effectuez les étapes manuelles qu'il affiche**, dans l'ordre. Chacune indique son fichier, et la plupart fournissent l'extrait de code à écrire : le montage de `<RebaseCMS>` avec `tableCustomizations` et `uiConfig` lorsque votre `App.tsx` n'est pas celui du scaffold (ou que le panneau est monté dans un autre module, que l'étape indique), `rebaseBackendGuard()` lorsque votre `vite.config.ts` ne l'est pas et dans toute autre application statique de `rebase.json` ([section 130](#130-rebase-build-refuse-un-frontend-sans-rebasebackendguard)), les hooks globaux, un import d'un nom supprimé dans 0.31 ([section 135](#135-rebaseprotypes-et-rebaseprocommon-retirent-le-modèle-de-collection-de-leurs-racines)), et `rebase skills install` lorsque le projet contient des compétences d'agent ([section 128](#128-la-compétence-dagent-rebase-collections-devient-rebase-tables)). Exécutez `pnpm install` lorsque la sortie indique « Dependencies added ». Lisez ensuite deux listes dans la partie SDK de la sortie :
   - **« Rewritten by name — review »** : les appels à `.collection(` sur un récepteur sans type (`any`), réécrits parce que le récepteur s'appelle `dataAsAdmin`, ou est `.data` avec un nom de table littéral ; le membre `collection` d'un type contenu dans un emplacement `data` / `dataAsAdmin` ; et les doublures de test. Vérifiez que chacun correspond bien au SDK.
   - **« Left unchanged — check each »** : les appels à `.collection(` pour lesquels le codemod n'a pas pu prouver qu'il s'agissait du SDK, comme un appel via un type déclaré par votre projet lui-même. Un appel laissé ici qui *est* le SDK échouera à l'exécution sous 0.31 : renommez-le manuellement en `.table(`. Le code testant si `collection` existe (`typeof data.collection === "function"`) constitue une étape manuelle : sous 0.31, il prend silencieusement l'autre branche.

   Un fichier commité en tant que sortie de build (un `.js` bundlé ou minifié) n'est jamais modifié : il est listé, vous devez donc le recompiler après la migration, et remplacer toute copie « vendored » du client par le build 0.31. Les étapes répétées d'un même type ne sont affichées qu'une seule fois, en listant chaque fichier et ligne concernés ; `--json` conserve chaque étape séparément. Lisez ensuite [Ce que les projets ont modifié à la main](/docs/upgrading/0-30-to-0-31-by-hand/) : les modifications que de vrais projets ont encore dû apporter après ces étapes.
6. **`rebase generate-sdk`** — les noms du module généré ont changé ([section 115](#115-le-sdk-adresse-une-table--datatableslug)).
7. **Sur votre base de données**, exécutez `rebase db push --dry-run` et attendez-vous à obtenir « No changes: the database already matches these tables. », puis `rebase doctor --policies` et attendez-vous à aucune dérive de stratégie. La vérification SQL du codemod prouve la fidélité de la conversion ; ces deux commandes la prouvent face à la vraie base de données, et toute différence de stratégie listée par l'une ou l'autre constitue un changement quant à qui peut accéder à quoi.
8. **`rebase verify`** — lit désormais également `frontend/src/cms` : une personnalisation nommant une table ou un champ inexistant, une colonne obligatoire absente du formulaire, un `rebaseBackendGuard()` manquant, un `ui-config.json` non transmis à `<RebaseCMS>`.
9. **Exécutez la ligne `git rm` affichée par le codemod** une fois le diff examiné : `git rm -r config/collections …` et les raccordements qu'il a déplacés vers `backend/`, ou `git rm -r config` s'il ne reste rien de personnel à cet endroit ([section 109](#109-il-ny-a-plus-de-paquet-config)).
10. **Recompilez et déployez.** Un bundle compilé avant 0.31 ne démarre pas sur un runtime 0.31 ([section 112](#112-format-de-bundle-3--les-bundles-au-format-2-sont-refusés)). Le premier démarrage réestampille une fois la version de schéma de la base de données ([section 113](#113-la-version-du-schéma-est-calculée-à-partir-des-tables-v2)).

Exécutez `rebase migrate collections-to-tables --check` en CI jusqu'à ce que `config/` ait disparu : cela vérifie que les tables migrées produisent toujours le même SQL que les collections dont elles sont issues, et renvoie le code d'erreur 1 tant qu'une règle listée sous « Review before deploying » n'a pas été confirmée — passez `--accept-rule-changes` une fois que vous les avez examinées.

### À examiner avant le déploiement : ces règles changent de sens

Le codemod conserve chaque règle de sécurité telle qu'elle a été écrite, et chacune garde son nom de stratégie. Cependant, le compilateur 0.30 ne lisait que la première clause parmi `condition`, `using`, `access: "public"` et `ownerField`, et ne connaissait aucune autre valeur pour `access` ; ainsi, quatre formes de règles accordent désormais des droits différents. Deux d'entre elles élargissent les accès :

| La règle | 0.30 accordait | 0.31 accorde | |
|---|---|---|---|
| un simple `access: "authenticated"` (sans `roles`) | rien | chaque appelant connecté, invités inclus | **élargit** |
| `access` + `check`, sans `condition`, sur `select` / `update` / `delete` / `all` | aucune ligne existante | chaque ligne existante, pour les appelants `access` | **élargit** |
| `access: "authenticated"` + `condition` | quiconque correspond à `condition` | uniquement les appelants connectés y correspondant | restreint |
| `access: "authenticated"` + `check`, sur `insert` | quiconque insère une ligne correspondante | uniquement les appelants connectés | restreint |

Le cas le plus courant est le premier. Écrivez `access: "registered"` pour n'admettre que les appelants possédant un compte (et non les invités anonymes), ou supprimez la règle pour continuer à ne rien accorder. `access` avec `roles`, et une `condition` sous forme d'objet simple, conservent leur signification antérieure et ne sont pas listés.

Le codemod refuse également toute règle refusée par le compilateur 0.31 : une règle combinant des clauses exclues par le type `SecurityRule` (`access` à côté de `ownerField`, `using` ou `withCheck` ; `ownerField` à côté de `using`, `withCheck`, `condition` ou `check` ; `condition` ou `check` à côté de `using` ou `withCheck`), et une règle avec une valeur invalide pour `access`, `mode`, `operation(s)` ou `roles` — un `"restrictive"` mal orthographié était auparavant compilé comme permissif. Voir [Règles de sécurité](/docs/collections/security-rules/).

### Ce qui se comporte différemment par ailleurs

- **Ce que `GET /api/schema/tables` communique à un utilisateur.** Les administrateurs et les détenteurs de `schema:read` obtiennent toutes les tables. Toute autre personne connectée, invités inclus, n'obtient que les tables auxquelles ses rôles peuvent accéder, avec uniquement les règles qui peuvent s'appliquer à elle ; les relations vers d'autres tables sont omises et les indicateurs de hooks sont retenus. Un frontend qui lisait la description d'une autre table en tant qu'utilisateur standard reçoit moins d'informations ; `schemaTables: { persons: "all" }` dans les options du backend rétablit la description complète. Voir [Points de terminaison](/docs/backend/endpoints/#schema).
- **Les noms de relation sont exacts**, et **les clés étrangères de type grand entier (big-integer) sont des nombres** ([section 131](#131-les-lignes-en-transit-suivent-leur-colonne)).
- **L'historique est servi masqué** ([section 132](#132-lhistorique-est-servi-sous-forme-de-lectures)).
- **Les noms des outils MCP et la charge utile (payload) de la vue** changent conjointement pour le connecteur hébergé et les runtimes qu'il contacte ([section 122](#122-les-outils-mcp-sont-nommés-daprès-les-tables)).
- **Délibérément restreint.** Les horodatages d'audit (colonnes `.onCreateNow()` / `.onUpdateNow()`) sont masqués par défaut dans les colonnes de liste du panneau : une liste migrée qui affichait `created_at` perd cette colonne jusqu'à ce que vous écriviez `fields: { created_at: { hidden: false } }` dans son `customizeTable`. Le codemod refuse, avec le motif indiqué, les tableaux JSON de tuples, un type `vector` / `binary` / `reference` à l'intérieur d'une map, `databaseId` sur une collection Postgres, `isId: "cuid"`, une relation `isId` unique et `disableDefaultPolicies: true` sans aucune règle. Une relation sur une seule colonne vers une table ayant une clé composite est refusée (déclarez-la avec `rel.via()`). Les tags OpenAPI proviennent du slug, et non du nom d'affichage. `rebase schema introspect` omet les tables sans clé primaire en indiquant la raison (un serveur effectuant l'introspection de la base de données continue de la servir). Une vue simple déclarant `roles` produit une erreur de compilation ; le codemod la supprime en ajoutant une note.
- **Ce que de vrais projets ont encore modifié à la main** — versions minimales de la chaîne d'outils, `({ entity })` dans le code d'administration, includes d'une relation renommée, objets de collection modifiés à l'exécution, appels SDK sur des récepteurs non typés : [Ce que les projets ont modifié à la main](/docs/upgrading/0-30-to-0-31-by-hand/).
- **Restauration vers un autre cluster.** L'empreinte des stratégies d'administration par défaut hache les OID des rôles ; par conséquent, après un dump ou une restauration à un instant précis (point-in-time restore) sur un cluster différent, le premier `db push` ou démarrage recrée ces stratégies une seule fois, avec les mêmes noms et le même SQL.

### La terminologie

| Avant | Maintenant | Où « collection » subsiste |
|---|---|---|
| une collection dans `config/collections/` | une **table** dans `backend/schema/` (`defineTable`) | — |
| `properties` | `columns` (`col.*`) et `relations` (`rel.*`) | — |
| `securityRules`, `defaultSecurityRules` | `rls` (obligatoire), `defaultRls` | — |
| `callbacks`, `Property.callbacks` | `hooks`, le `.transform()` d'une colonne | — |
| le bloc `admin` | `customizeTable` dans `frontend/src/cms/` | — |
| `data.collection(slug)` | `data.table(slug)` | — |
| ce que le panneau d'administration affiche | une **collection** : une table telle que le panneau la présente, ou une collection Firestore | le CMS : `CollectionPanel`, l'Éditeur de Collection, `externalCollections` |

## 108. Les tables dans `backend/schema` remplacent `config/collections` — exécutez d'abord le codemod

**Qui est concerné :** chaque projet disposant d'un répertoire `config/collections/`.

**Ce qui a changé :** le backend lit uniquement `backend/schema/index.ts` et les résultats de `defineTable`, `defineAuthTable` et `defineView` qu'il exporte. Les fichiers `defineCollection` ne sont plus lus par rien : le runtime, chaque commande CLI et la validation de `rebase.json` refusent tout projet contenant encore `config/collections`, en indiquant la commande ci-dessous. `rls` est obligatoire sur chaque table — une liste de règles, `"admin-only"`, ou `"inherit"` pour le `defaultRls` exporté par l'index — et `disableDefaultPolicies` devient `defaultPolicies: false`.

**Ce qu'il faut faire :**

```bash
rebase migrate collections-to-tables            # or --dry-run first
```

Il écrit une table par collection, chaque colonne physique étant explicite à sa position d'origine (la colonne de clé d'un `belongsTo` est donc écrite en clair), l'index avec `defaultRls` issu de `defaultSecurityRules`, un `customizeTable` pour chaque collection dont la présentation n'était pas celle par défaut, et les fichiers `defineFirestoreCollection` pour les collections Firestore. Les callbacks d'une collection deviennent les `hooks` de sa table et les `.transform()` de ses colonnes ; les `callbacks` globaux exportés par `config/index.ts` font l'objet d'une étape manuelle (section 109). Ensuite, il relit le résultat à travers le nouveau pipeline : DDL, stratégies, recherche, vectoriel, déclencheurs, vues et le schéma Drizzle doivent être identiques à l'octet près à ce que les collections généraient, sans quoi chaque fichier est remis à son état initial et l'exécution se termine avec le code 1 en affichant le diff.

Il prend également en charge ce qui nécessitait auparavant une intervention manuelle :

- **Les callbacks construits par un helper** (`callbacks: softDeleteCallbacks(...)`, ou un objet callbacks importé) deviennent `hooks:` avec la même expression, et les fonctions du helper sont converties en propriétés de hooks de table là où elles sont écrites (le codemod suit les imports relatifs, les `const`, les lectures de propriétés et un unique `return`). Lorsqu'il ne parvient pas à suivre le helper, une étape indique les hooks à vérifier.
- **Une fonction `storagePath`** migre en deux parties : la fonction devient le `storage.path` de la personnalisation, afin que le panneau continue de choisir l'emplacement d'un téléversement, et le modèle (template) `path` de la colonne prend la forme des clés qu'elle renvoie — le texte statique de son gabarit littéral (template literal) avec chaque `${…}` sous la forme `{path}` (`` `${owner}/cv` `` → `{path}/cv`). Le serveur applique désormais `maxBytes` et `accept` de la colonne à chaque téléversement dont la clé correspond à ce modèle, et pas seulement à celui qui nomme la colonne ; les limites sont donc plus strictes qu'en 0.30. Une fonction dont le résultat ne comporte aucun texte statique est refusée : ajoutez-en un au préalable.
- **Un `policy.existsIn({ collection })` de la version 0.30** conserve sa table, et `auth: { collection: usersCollection }` dans un point d'entrée backend personnalisé est supprimé (le `defineAuthTable` est la table d'authentification). Une option de démarrage `collections` devient `schemaDir`.
- **Un générateur `dynamicProps`** renvoie une personnalisation de champ avec des clés aplaties en 0.31 (`{ readOnly: true }`, et non `{ admin: { readOnly: true } }`). Le codemod réécrit les générateurs dont les retours sont des littéraux d'objet, en ligne ou dans un module partagé, et liste tous les autres.
- **La présentation propagée (spread) depuis un objet partagé** est reportée dans la personnalisation (`….dynamicProps`) ; une présentation calculée par une fonction wrapper constitue une étape à vérifier, et non un refus du projet. Le chemin d'un composant est résolu par rapport au module qui l'a écrit, et une valeur calculée lors du chargement de `config/` (`new Date()`, `Date.now()`, une lecture d'environnement) est conservée sous forme d'expression, sans jamais être figée à la valeur lors de l'exécution.
- **Les collections Firestore construites par une fonction** (un `getAllFirestoreCollections()` que l'application propage dans le panneau) sont converties en `defineFirestoreCollection` une par une lorsque le fichier d'une collection contient son littéral ; une étape par générateur indique les autres ainsi que la structure à écrire, et une autre indique une référence écrite en dehors d'un littéral converti, qui mentionnerait encore `path`.
- **Les imports de `config/` via un alias de chemin** (une entrée `paths` de tsconfig, un `resolve.alias` de Vite) sont réécrits ou listés comme des imports relatifs, et un `storageAuthorize` réexporté par `config/index.ts` est transféré vers `backend/storage.ts`.
- **Une relation renommée en `<key>Relation`** conserve son libellé, sa colonne de liste et son titre : la personnalisation nomme la nouvelle clé. Le code qui l'inclut ne suit pas automatiquement ([ce qu'il faut modifier](/docs/upgrading/0-30-to-0-31-by-hand/#a-belongsto-key-is-a-column-and-a-relation-can-be-renamed)).

Ce qu'il ne peut pas reporter fidèlement est refusé avec le fichier et la ligne correspondants, et rien n'est écrit : une collection construite en appelant une fonction, un spread ou un accesseur à travers lequel il ne peut pas lire, un moteur autre que Postgres ou Firestore, un fichier de sortie existant avec un contenu différent (déplacez-le, ou utilisez `--force`). Un arbre git non propre (dirty) ou un projet non versionné avec git est également refusé, afin que la migration constitue un diff unique et vérifiable. `--json` affiche l'intégralité du rapport pour un script ou un agent. Voir [`rebase migrate`](/docs/cli/schema/#rebase-migrate) et [Tables](/docs/schema/).

Les tables qu'il écrit déclarent leurs colonnes selon la syntaxe de `pg-core` de Drizzle — `col.varchar({ length: 160 })`, `col.timestamp({ withTimezone: true })`, `col.text().array()`, `pgEnum(...)`, `` .default(sql`…`) ``, `.generatedByDefaultAsIdentity()` — de sorte que sa sortie ne nécessite rien de plus ; voir [Colonnes](/docs/schema/columns/). Une table écrite à la main pour une préversion de la 0.31 avec les anciennes syntaxes (`col.timestamptz()`, `col.varchar(160)`, `col.array(col.text())`, `col.enum(values, { name })`, `.defaultSql()`, `.identity()`, `.column("…")`) ne compile plus : `tooling/scripts/drizzle-sweep.mts` dans le dépôt Rebase la convertit, en réécrivant uniquement les chaînes de constructeurs, et avec `--verify` prouve que chaque table convertie se compile dans le même descripteur (`npx tsx drizzle-sweep.mts --verify backend/schema`).

La passe `sdk-calls` qui suit réécrit également les sources des règles : `existsIn({ collection })` et `membership: { collection }` deviennent `table` (section 123) ; `--skip-sdk-calls` l'ignore également. Ce qui vous reste à faire est affiché sous forme d'étapes manuelles numérotées, et si le projet contient des compétences d'agent installées, la dernière est la commande `rebase skills install` qui les actualise (section 128). Un simple `rebase migrate` affiche l'aide des deux sous-commandes.

## 109. Il n'y a plus de paquet config

**Qui est concerné :** chaque projet — `config/` était un espace de travail à part entière.

La version 0.31 cesse de lire `config/collections` ; elle n'interdit pas `config/`. Le codemod supprime ce que Rebase lisait — les fichiers de collections et les raccordements qu'il déplace vers `backend/` (`resources.ts`, `storage.ts`, `generated/register.ts`, et les réexports de ceux-ci dans `config/index.ts`) — et laisse vos propres modules dans `config/` là où ils sont, importables comme auparavant : `config/` reste un paquet de l'espace de travail, et le backend compile toujours `../config/**/*`. Seuls les imports de ce qui disparaît sont réécrits : un fichier de collection importé par le code backend pointe vers le module de la table (une étape liste les usages qui le lisent comme un objet) ; importé par le code frontend, il devient un import de type de la table lorsqu'il n'est utilisé que comme type, ou une étape nommant la personnalisation ; un helper situé à l'intérieur de `config/collections` est copié à côté du code qui en a besoin.

**Ce qui a changé :** ce qui résidait aux côtés des collections est déplacé dans `backend/` :

| Avant | Maintenant |
|---|---|
| `config/resources.ts` | `backend/resources.ts` |
| `config/storage.ts`, `storageAuthorize` issu de `config/index.ts` | `backend/storage.ts` |
| `callbacks` exportés depuis `config/index.ts` | `hooks` exportés depuis `backend/hooks.ts` (`TableHooks` : `table` au lieu de `collection`, `values` au lieu de `row`) |
| `config/generated/register.ts` | `backend/generated/register.ts` |
| `rebase.json` `config`, `usersCollection` | `tables` (par défaut `backend/schema`) ; la table d'authentification est celle déclarée avec `defineAuthTable` |

Le runtime lit `storageAuthorize` et `hooks` et rien d'autre depuis ces modules ; tout autre export est signalé au démarrage. Le frontend importe `backend/**` uniquement sous forme de types — `pnpm check:frontend-backend-imports` refuse un import par valeur, qui expédierait du code serveur vers le navigateur.

**Ce qu'il faut faire :** le codemod déplace `resources.ts`, `storage.ts` et l'enregistrement, et réécrit `rebase.json`, `package.json`, `pnpm-workspace.yaml` et `backend/tsconfig.json`. Les `callbacks` globaux constituent une étape manuelle qu'il affiche : déplacez-les manuellement dans `backend/hooks.ts`, et ajoutez `hooks.ts` au tableau `include` de `backend/tsconfig.json` afin que `tsc` le vérifie. Exécutez ensuite la ligne `git rm` affichée : `git rm -r config/collections …`, ou `git rm -r config` s'il ne reste rien de personnel.

## 110. Les options de démarrage et les hooks nomment des tables

**Qui est concerné :** un backend que vous démarrez vous-même (`initializeRebaseBackend`, `createRebaseBackend`), et le code qui attache des hooks après le démarrage.

**Ce qui a changé :**

| Avant | Maintenant |
|---|---|
| `collections`, `collectionsDir` | `tables`, `defaultRls`, `schemaDir` |
| `callbacks` | `hooks` |
| `auth.collection` | supprimé : le `defineAuthTable` dans `tables` |
| `backend.setCollectionCallbacks(slug, cb)` | `backend.setTableHooks(slug, hooks)` |
| propriétés de hook `collection`, `row` | `table` (le descripteur), `values` |
| `composeCallbacks` | `composeTableHooks` depuis `@rebasepro/common` |
| `openRebase({ collections, callbacks })` | `openRebase({ tables, hooks })`, `tables` issu de `compileSchema([...])` |
| `OpenedRebase.collections` ; la variable `collections` de `rebase console` | `.tables` ; `tables` |

```diff ts
-await initializeRebaseBackend({ app, server, collectionsDir: "./config/collections", callbacks });
+await initializeRebaseBackend({ app, server, schemaDir: path.resolve(__dirname, "../schema"), hooks });
```

Les hooks attachés à un objet collection passé au niveau d'un point d'appel ne s'exécutent plus : le pilote exécute les hooks des tables qu'il sert ; attachez-les donc avec `setTableHooks`.

**Ce qu'il faut faire :** `rebase migrate sdk-calls` réécrit `setCollectionCallbacks` et adapte les propriétés des hooks, et liste chaque objet d'options backend à mettre à jour manuellement. Un script qui ouvre les données compile ses tables :

```diff ts
-const rebase = await openRebase({ databaseUrl, collections, callbacks });
+const rebase = await openRebase({ databaseUrl, tables: compileSchema([products, orders]), hooks });
```

Voir [Scripts](/docs/backend/scripts/#openrebase). Voir [Présentation du backend](/docs/backend/) et [Hooks globaux](/docs/backend/hooks/).

## 111. Le panneau d'administration affiche les tables servies par le serveur

**Qui est concerné :** chaque frontend qui monte `<RebaseCMS>`.

**Ce qui a changé :** `<RebaseCMS collections>` n'existe plus. Le panneau affiche chaque table que le backend sert à `GET /api/schema/tables`, sans aucun fichier par table, puis `externalCollections` (Firestore). `tableCustomizations` accepte les objets `customizeTable` provenant de `frontend/src/cms/`. Le plugin collections de Vite et `virtual:rebase-collections` sont supprimés. `CollectionsProvider` accepte les trois mêmes entrées (`tableCustomizations`, `externalCollections`, `tables`).

```diff tsx
-import { collections } from "virtual:rebase-collections";
-<RebaseCMS collections={collections}/>
+import { postsCms } from "./cms/posts";
+<RebaseCMS tableCustomizations={[postsCms]}/>
```

**Ce qu'il faut faire :** le codemod écrit `frontend/src/cms/index.ts`, qui exporte `tableCustomizations` (et `externalCollections`), et le monte lui-même dans le fichier `App.tsx` du scaffold ; un `App.tsx` qu'il ne reconnaît pas, le plugin dans `vite.config.ts` et la déclaration de module virtuel font l'objet d'étapes manuelles affichées. Voir [Personnaliser une table](/docs/frontend/customize-table/).

## 112. Format de bundle 3 ; les bundles au format 2 sont refusés

**Qui est concerné :** chaque déploiement d'un bundle compilé — auto-hébergé avec l'image de runtime, ou sur Rebase Cloud.

**Ce qui a changé :** le schéma d'un bundle est `entry.tables`, aux côtés de `entry.resources`, `entry.storage` et `entry.hooks` ; `bundleFormat` passe à 3 et le contrat de runtime à 2. Un bundle au format 1 ou au format 2 contient `config/collections`, qu'un runtime 0.31 ne peut pas lire ; il refuse donc de démarrer en suggérant le codemod dans le message, au lieu d'effectuer une introspection de la base de données et de servir une API différente.

**Ce qu'il faut faire :** migrez les sources, puis lancez `rebase build` et déployez. Sur Rebase Cloud, le déploiement du dépôt migré le recompile automatiquement. Voir [Runtime et bundles](/docs/architecture/runtime-and-bundles/).

## 113. La version du schéma est calculée à partir des tables (`v2:`)

**Qui est concerné :** chaque base de données approvisionnée par un runtime antérieur à 0.31, et chaque SDK généré.

**Ce qui a changé :** la version du schéma hache les descripteurs de table compilés et commence par `v2:`. Une base de données estampillée `v1:` signale le changement de modèle une seule fois — les logs de démarrage et `rebase doctor` l'indiquent en précisant comment réestampiller — et chaque SDK généré est signalé comme périmé une fois.

**Ce qu'il faut faire :** approvisionnez une fois avec le nouveau runtime : démarrez le processus propriétaire du schéma, ou lancez `rebase db push`. Avec `REBASE_REQUIRE_SCHEMA_MATCH=true`, réestampillez avant de basculer les autres processus. Régénérez le SDK.

## 114. Les codes d'erreur nomment des tables

**Qui est concerné :** le code qui effectue des branchements conditionnels sur un `code` d'erreur.

**Ce qui a changé :**

| Avant | Maintenant |
|---|---|
| `NO_COLLECTIONS` (404) | `NO_TABLES` |
| `COLLECTION_READ_ONLY` (405) | `TABLE_READ_ONLY` |
| `UNKNOWN_COLLECTION` (SDK) | `UNKNOWN_TABLE` |
| `INVALID_COLLECTION_PATH` (SDK) | `INVALID_TABLE_PATH` |

**Ce qu'il faut faire :** `rebase migrate sdk-calls` réécrit les chaînes de caractères littérales. Voir [Erreurs](/docs/backend/errors/).

## 115. Le SDK adresse une table : `data.table(slug)`

**Qui est concerné :** chaque client, fonction, cron, hook et script qui nomme une table par son slug, ou transmet le dictionnaire généré.

**Ce qui a changé :**

| Avant | Maintenant |
|---|---|
| `data.collection(slug)` | `data.table(slug)` |
| `createRebaseClient({ collections: collectionsDictionary })` | `createRebaseClient({ tables: tablesDictionary })` |
| `CollectionName`, `CollectionsDictionary` générés | `TableName`, `TablesDictionary` |
| lot `{ op, collection }` (SDK et `POST /api/data/_batch`) | `{ op, table }` |
| `CollectionClient`, `SDKCollectionClient`, `CollectionAccessor`, `CollectionTrashAccessor` | `TableClient`, `SDKTableClient`, `TableAccessor`, `TableTrashAccessor` |
| hors ligne `maxCachedRowsPerCollection`, `maxCachedQueriesPerCollection` | `…PerTable` |
| accesseur réservé `<name>Collection` ; `collectionCollection` | `<name>Table` ; la table `collection` est `collection` |

```diff ts
-const { data } = await client.data.collection("posts").find();
+const { data } = await client.data.table("posts").find();
```

Les accesseurs typés (`client.data.posts`) demeurent inchangés.

**Ce qu'il faut faire :** le codemod exécute `rebase migrate sdk-calls` sur votre code — exécutez-le seul sur un projet déjà migré — puis `rebase generate-sdk`. Un appel `.collection(` dont le récepteur n'est pas le SDK est conservé tel quel et listé. Voir [SDK typé](/docs/sdk/).

## 116. Options de la CLI : `--schema-dir`, et non `--collections`

**Qui est concerné :** les scripts et étapes de CI qui appellent la CLI avec un chemin de schéma.

**Ce qui a changé :** `--collections` / `-c` sont refusés sur chaque commande qui lit le schéma, en affichant le codemod dans le message (`generate-sdk` ignore un `--collections-dir` superflu) ; `--schema-dir` désigne un répertoire de schéma autre que `backend/schema`. `rebase schema introspect` écrit les fichiers `defineTable` dans `backend/schema/` — `--output` n'existe plus. `REBASE_STRICT_COLLECTION_CONFIG` n'est plus lu : un schéma qui ne se compile pas refuse systématiquement le démarrage.

**Ce qu'il faut faire :** remplacez les options. Voir [CLI](/docs/cli/) et [Génération de schéma](/docs/cli/schema/).

## 117. L'éditeur de schéma modifie `backend/schema` avec `TablePatch`

**Qui est concerné :** le code qui appelle les routes de l'éditeur de schéma ou de schéma en direct (live-schema), et les déploiements définissant les variables d'édition en direct.

**Ce qui a changé :** `/api/admin/schema-editor/collection/save`, `collection/delete`, `property/save` et `property/delete` ont disparu. L'éditeur sert `GET /tables`, `POST /preview` et `POST /apply`, et les routes `/plan` et `/apply` de l'édition de schéma en direct reçoivent `{ patches: TablePatch[] }` au lieu d'une collection ou d'un patch de collection. `REBASE_LIVE_SCHEMA_COLLECTIONS_PATH` est refusé au démarrage : il devient `REBASE_LIVE_SCHEMA_PATH` (`backend/schema` par défaut), et `liveSchema.repository.collectionsPath` devient `schemaPath`. La présentation ne constitue jamais une modification de schéma : elle est enregistrée en tant que préférences d'interface (`/api/admin/ui-config`). Une modification dont le fichier a changé sur le disque après sa préparation (sauvegarde dans l'IDE, autre processus) renvoie une erreur 409 `SCHEMA_EDIT_STALE_FILE` et n'écrit rien ; c'était auparavant une 400 `SCHEMA_EDIT_REFUSED`.

**Ce qu'il faut faire :** renommez la variable ; réécrivez les appelants des routes afin d'envoyer des modifications de type `TablePatch`, et rechargez en cas de `SCHEMA_EDIT_STALE_FILE`. Voir [Édition de schéma en direct](/docs/backend/live-schema-editing/).

## 118. Un emplacement de composant est un composant

**Qui est concerné :** les personnalisations qui nommaient un composant React par un chemin sous forme de chaîne ou un thunk lazy `() => import(…)`.

**Ce qui a changé :** `Field` / `Preview` / `Filter` d'un champ, `Actions` d'une collection, `entityViews[].Builder`, `collectionViews[].Builder`, `formView.Builder` et les surcharges de composants reçoivent directement le composant lui-même. `ComponentRef`, `ComponentLike`, `LazyComponentRef` et `isLazyComponentRef` (`@rebasepro/types`), `asComponentRef` et `asReactComponent` (`@rebasepro/cms-types`) ainsi que `resolveComponentRef` / `useResolvedComponent` (`@rebasepro/app`) sont supprimés. `customizeTable` refuse une chaîne ou un thunk avec le message « imported by value ».

**Ce qu'il faut faire :** importez le composant dans le fichier `frontend/src/cms/` et transmettez-le directement. Voir [Champs personnalisés](/docs/frontend/custom-fields/).

## 119. Les préférences du panneau sont des préférences d'interface (UI preferences)

**Qui est concerné :** le code qui implémente `UserConfigurationPersistence`.

**Ce qui a changé :** la manière dont un utilisateur a redimensionné ou réorganisé une table est un delta `UiTablePreferences` : `getTablePreferences` / `saveTablePreferences` remplacent `getCollectionConfig` / `onCollectionModified`, et le type partiel de configuration de collection qu'il acceptait est supprimé. Le stockage du navigateur les conserve sous `table_preferences::<slug>`, et ignore ce qu'un panneau plus ancien stockait, de sorte que les largeurs de colonnes et les modes de vue de chaque utilisateur sont réinitialisés une fois. `userSelect` sur un champ a disparu : une colonne `.userId()` fait office de sélecteur d'utilisateur.

La passerelle de Studio s'aligne : `StudioSchemaEditing.updateCollection` devient `applyTablePatches(slug, patches)`, et l'éditeur de collection envoie `{ patches }` à l'éditeur de schéma.

**Ce qu'il faut faire :** adaptez toute persistance personnalisée aux deux méthodes, et un `StudioSchemaEditing` personnalisé à `applyTablePatches`.

## 120. MongoDB est abandonné

**Qui est concerné :** un projet utilisant `@rebasepro/server-mongo`, ou déclarant `database(…, { engine: "mongodb" })`.

**Ce qui a changé :** le paquet a été retiré, tout comme les types de collection Mongo et le reste du modèle Mongo. Postgres est l'unique moteur de serveur : une source de transport serveur sur un autre moteur refuse le démarrage en le nommant explicitement.

**Ce qu'il faut faire :** migrez les données vers Postgres. Il n'existe pas de procédure de migration interne dans Rebase.

## 121. Les collections Firestore résident dans le frontend

**Qui est concerné :** un projet hybride avec des collections `engine: "firestore"`.

**Ce qui a changé :** une collection Firestore est une source CMS que le navigateur lit directement : `defineFirestoreCollection` issu de `@rebasepro/firebase`, dans `frontend/src/cms/`, transmis à `<RebaseCMS externalCollections>`. Une référence entre Firestore et une table Postgres est stockée sous forme de l'identifiant de la cible, et une référence Firestore dont le `path` est également un slug Postgres cible désormais la table Postgres.

**Ce qu'il faut faire :** le codemod écrit les fichiers `defineFirestoreCollection`. Pointez une référence vers une collection Firestore à l'aide du slug de cette dernière. Voir [Firebase](/docs/frontend/firebase/).

## 122. Les outils MCP sont nommés d'après les tables

**Qui est concerné :** les prompts, scripts et listes d'autorisation qui nomment des outils MCP.

**Ce qui a changé :** `/mcp` distant : `list_collections`, `describe_collection`, `query_collection`, `show_collection`, `count_documents`, `aggregate_documents`, `get_document`, `create_document`, `update_document`, `delete_document` → `list_tables`, `describe_table`, `query_table`, `show_table`, `count_rows`, `aggregate_rows`, `get_row`, `create_row`, `update_row`, `delete_row` ; l'argument `collection` devient `table`, et `show_app` / `save_app` prennent `tables`. Le serveur local : `list_documents` → `query_table`, `get_document` → `get_row`, `create_document` → `create_row`, `update_document` → `update_row`, `delete_document` → `delete_row` ; `rebase_schema_plan` prend `patches` ; les ressources deviennent `rebase://tables/{name}`. La charge utile de la vue MCP Apps passe en version 3 : descripteurs de table expurgés pour l'appelant, autorisations par table, et préférences d'interface de chaque appelant sous `preferences` (`file`, `workspace`, `user` ; une clé API n'a pas de couche utilisateur), avec les blocs et valeurs d'initialisation (seeds) nommant `table`. La vue `collection-table` est supprimée. `list_tables` n'a pas de `title` ; `describe_table` ajoute `primaryKey`, `relations`, le `rls` de l'appelant, `title` et `presentation`.

**Ce qu'il faut faire :** renommez. La vue et le serveur doivent employer la même version de charge utile : un connecteur hébergé et les runtimes qu'il contacte montent de version ensemble, et une vue MCP personnalisée au projet doit être recompilée avec les paquets 0.31. Voir [Référence des outils MCP](/docs/ai/mcp-tool-reference/) et [MCP distant](/docs/ai/remote-mcp/).

## 123. Le vocabulaire des règles utilise `table`

**Qui est concerné :** les règles qui utilisent `policy.existsIn` ou un tenant d'appartenance (membership tenant), et les règles qui combinent `access` avec d'autres clauses.

**Ce qui a changé :** `policy.existsIn({ collection, where })` devient `existsIn({ table, where })`, et `tenant.from.membership.collection` devient `membership.table` ; les noms de stratégie ne changent pas. Quatre formes de règles accordent désormais des droits différents, dont deux en accordent davantage ([le tableau ci-dessus](#à-examiner-avant-le-déploiement--ces-règles-changent-de-sens)) : un simple `{ access: "authenticated" }`, qui n'accordait rien, autorise désormais chaque appelant connecté, et les tables de jonction d'une telle table obtiennent leurs stratégies d'écriture de bordure (edge-write). Les règles combinant des clauses exclues par le type `SecurityRule`, ou comportant un `access`, `mode`, `operation` ou `roles` invalide, sont refusées.

**Ce qu'il faut faire :** le codemod renomme les clés, refuse les règles invalides en précisant leur fichier et ligne, et liste les règles dont le sens change sous « Review before deploying ». Pour chacune, conservez-la, écrivez `access: "registered"` (appelants connectés possédant un compte), ou supprimez-la. Examinez ensuite `rebase db push --dry-run` et `rebase doctor --policies` face à votre base de données.

## 124. Studio lit les tables depuis le serveur

**Qui est concerné :** Studio pointé vers un backend antérieur à 0.31, et les scripts de console JS de Studio.

**Ce qui a changé :** chaque outil ayant conscience du schéma lit `GET /api/schema/tables` ; face à un runtime qui ne le propose pas, ils affichent un avertissement de mise à niveau. La vue déclarée de l'éditeur de RLS correspond à ce que le serveur a compilé. Un script de console JS reçoit `context.tables` (au lieu de `context.collections`).

**Ce qu'il faut faire :** mettez à niveau le runtime en même temps que le panneau. Voir [Studio](/docs/studio/).

## 125. `rls-check --format agent` utilise `rls`

**Qui est concerné :** un outil qui lit `rls-check --format agent`.

**Ce qui a changé :** `remediation.rebase.securityRules` devient `remediation.rebase.rls`, l'extrait est un `defineTable(…, { rls })`, et la version de format du document est 2. `--json` demeure inchangé. Voir [rls-check](/docs/rls-check/).

**Ce qu'il faut faire :** lisez la nouvelle clé.

## 126. `@rebasepro/plugin-review` : `reviewRls`

**Qui est concerné :** un projet utilisant le plugin review.

**Ce qui a changé :** `reviewSecurityRules(slug, review)` devient `reviewRls(slug, review)`, propagé dans le `rls` de la table ; `findReviewConfigProblems` et `assertReviewConfig` reçoivent des descripteurs de table.

**Ce qu'il faut faire :** renommez l'appel et passez `services.tables()` ou `compileTables(…)`.

## 127. `@rebasepro/codegen` lit des descripteurs

**Qui est concerné :** le code qui appelle directement le générateur.

**Ce qui a changé :** `generateTypedefs(tables)` et `generateSDK(tables, options)` prennent `TableDescriptor[]` — ce que `compileTables` renvoie et ce que `GET /api/schema/tables` sert — au lieu de collections.

**Ce qu'il faut faire :** compilez vos définitions au préalable, ou utilisez `rebase generate-sdk`.

## 128. La compétence d'agent `rebase-collections` devient `rebase-tables`

**Qui est concerné :** un projet ayant installé les compétences d'agent, et les prompts ou fichiers d'instructions qui nomment la compétence.

**Ce qui a changé :** la compétence enseignant le modèle de données est `rebase-tables` : création de tables, colonnes, relations, `rls`, hooks, et la couche CMS au-dessus. `rebase skills install` supprime l'ancienne copie `rebase-collections`, y compris pour les installations réalisées avant l'existence du manifeste de compétences, et conserve tout répertoire de ce nom que vous auriez créé vous-même.

**Ce qu'il faut faire :** exécutez `rebase skills install` après la mise à niveau. Les étapes affichées par `rebase migrate collections-to-tables` l'indiquent également. Renommez la compétence dans tout fichier d'instructions qui la mentionne. Voir [Compétences d'agent](/docs/ai/skills/).

## 129. `useJsonCollectionsConfigController` est supprimé

**Qui est concerné :** un projet qui stockait des définitions de collection sous forme de JSON via `@rebasepro/cms`.

**Ce qui a changé :** `useJsonCollectionsConfigController` est retiré, ainsi que son type d'options et la classe de stockage JSON sous-jacente. Le schéma d'une table réside dans `backend/schema`, et sa présentation dans le panneau réside dans les préférences d'interface : `frontend/src/cms/ui-config.json` en développement, la table `rebase.ui_preferences` sur un déploiement.

**Ce qu'il faut faire :** déclarez les tables avec `defineTable` (`rebase migrate collections-to-tables` les écrit à partir des définitions de collections), et passez le `uiConfig` du scaffold à `<RebaseCMS>`. Voir [Personnaliser une table](/docs/frontend/customize-table/#customizations-ui-configjson-and-preferences).

## 130. `rebase build` refuse un frontend sans `rebaseBackendGuard()`

**Qui est concerné :** chaque projet disposant d'un frontend.

**Ce qui a changé :** le frontend peut importer `backend/` uniquement sous forme de types. Un import
par valeur introduirait du code serveur — des hooks, ainsi que tous les secrets qu'ils lisent — au sein du
bundle du navigateur. `rebaseBackendGuard()` issu de `@rebasepro/app/vitePlugin` fait échouer `vite build` et `vite dev` dès qu'un module frontend résout vers `backend/`, en nommant l'importateur, l'import et le fichier, après résolution des alias, chemins tsconfig, résolutions de paquets et absolues, globs, `?raw`, réexports et imports dynamiques. `rebase build`, ainsi que le build frontend exécuté par `rebase cloud deploy`, refusent un frontend dont la configuration Vite ne l'utilise pas ; `rebase dev` émet un avertissement ; `rebase verify` signale `cms-backend-guard-missing`.

**Ce qu'il faut faire :** le codemod l'ajoute au fichier `frontend/vite.config.ts` d'un scaffold, et affiche les lignes requises pour toute autre configuration :

```diff ts
+import { rebaseBackendGuard } from "@rebasepro/app/vitePlugin";

 export default defineConfig({
-    plugins: [react()],
+    plugins: [react(), rebaseBackendGuard()],
 });
```

Transformez ensuite tout import par valeur depuis `backend/` en `import type`.

## 131. Les lignes en transit suivent leur colonne

**Qui est concerné :** les clients qui lisent des clés étrangères ou nomment des relations, et les écritures qui envoient des colonnes générées ou des objets JSON partiels.

**Ce qui a changé :** les valeurs traversent le codec de leur colonne en sortie et les règles de la colonne en entrée.

- Une colonne de clé étrangère `bigint` ou `numeric` générée par une relation, renvoyée sous forme de texte par Postgres, est servie sous forme de **nombre** dans REST, le SDK et le panneau d'administration. Les clés déclarées comme nombres l'étaient déjà.
- Les **éléments d'un tableau natif sont servis selon leur type scalaire**, dans REST, le SDK, le socket et le pilote :

  | Colonne | 0.30 servait | 0.31 sert |
  |---|---|---|
  | `timestamptz[]` | `["2026-01-02 11:00:00+01"]` | `["2026-01-02T10:00:00.000Z"]` |
  | `numeric[]` (un pilote ouvert sans le paramètre numeric au démarrage : tests, scripts) | `["1.50", "2.25"]` | `[1.5, 2.25]` |
  | `bigint[]` avec un élément null | `[1, 0, 3]` | `[1, null, 3]` |
  | `date[]`, `timestamptz[]` ou un tableau d'enums avec un élément null | `["2026-01-02", "NULL"]` | `["2026-01-02", null]` |

  `date[]`, `time[]`, `text[]`, `uuid[]`, `boolean[]`, `integer[]` et `double precision[]` sont servis comme auparavant. Ce qui est stocké ne change pas : une ligne lue puis réenregistrée conserve le même tableau.
- Une relation nommée dans `include`, un filtre ou un tri doit correspondre à son **nom exact**. Les tentatives de secours avec le slug et la notation snake_case sont supprimées.
- Une colonne générée est refusée à l'écriture, et omise du schéma d'entrée OpenAPI.
- Un champ obligatoire au sein d'un objet JSON est appliqué ; `$inc` et les éléments de tableau sur une colonne entière doivent être des entiers.

**Ce qu'il faut faire :** lisez les clés étrangères comme des nombres là où vous compariez des chaînes, parsez les éléments `timestamptz[]` selon le format RFC 3339 et traitez un élément de tableau null comme `null`, et écrivez les noms de relations exactement tels que déclarés par la table (les clés de ses `relations`). Cessez d'envoyer des colonnes générées.

## 132. L'historique est servi sous forme de lectures

**Qui est concerné :** les lecteurs d'instantanés d'historique, et toute personne implémentant un `DataDriver`.

**Ce qui a changé :** les entrées d'historique sont servies sous forme de lectures : accès aux champs en premier, puis `afterRead` (global, table, colonne). Une colonne masquée par un hook ou un `.transform({ afterRead })` est masquée dans chaque instantané, une colonne que l'appelant n'a pas le droit de lire est retenue et omise de `changed_fields`, les clés des colonnes supprimées sont retenues, et une restauration n'écrit jamais une colonne que l'appelant ne peut pas lire. Un hook qui lève une exception sur un instantané ancien fait échouer la requête. La version 0.30 servait les valeurs brutes stockées : un projet utilisant l'historique et des hooks de masquage doit donc impérativement être mis à niveau.

Une entrée conserve la ligne telle que `GET /api/data/<table>/<id>` la lit sans aucun `include` : des valeurs brutes, un `belongsTo` sous forme de sa clé étrangère. Une entrée qu'une version antérieure avait enregistrée avec le modèle de vue du panneau d'administration est servie, et restaurée, telle quelle : une enveloppe `{ "__type": "date", "value" }` pour sa valeur, une référence `{ "__type": "relation" }` d'une relation propriétaire sous forme de clé étrangère sous le nom propre de la clé, et toute autre référence sous forme de la clé de la ligne liée. La version 0.30 servait ces références telles quelles.

Un pilote sert l'historique via `DataDriver.serveStoredRows(path, rows)`, à l'intérieur de la transaction en lecture seule de l'appelant ; les routes d'historique répondent 501 pour un pilote qui ne l'a pas implémenté, de sorte que l'historique n'est jamais servi non masqué.

**Ce qu'il faut faire :** rien pour le pilote Postgres fourni. Un pilote personnalisé doit implémenter `serveStoredRows`. Voir [Historique](/docs/backend/history/).

## 133. Les exports de `@rebasepro/server` nomment des tables

**Qui est concerné :** un serveur assemblé à partir des composants de `@rebasepro/server` plutôt qu'avec `initializeRebaseBackend` / `createRebaseBackend`.

**Ce qui a changé :**

| Avant | Maintenant |

## 135. `@rebasepro/types` et `@rebasepro/common` retirent le modèle de collection de leurs racines

**Qui est concerné :** le code qui importe des types de collection ou de propriété, des helpers du panneau d'administration ou le lift depuis `@rebasepro/types` ou `@rebasepro/common` — champs personnalisés, vues personnalisées, plugins, tests avec fixtures de collection — et les pilotes personnalisés implémentant le registre.

**Ce qui a changé :** les paquets du noyau décrivent exclusivement des tables. Ce qui décrit une collection telle que le panneau d'administration l'affiche réside dans `@rebasepro/cms-types` :

- **Types** ayant migré depuis `@rebasepro/types` : `CollectionConfig`, `PostgresCollectionConfig`, `FirebaseCollectionConfig`, `AnyCollectionConfig`, chaque `…Property` (`StringProperty`, `NumberProperty`, `ArrayProperty`, …) et `Properties`, `CollectionCallbacks` et ses propriétés de hooks, les types de relation de la version 0.30 et leurs formes `Resolved…`, `CollectionIndex`, les couleurs de puces (`ColorScheme`, `ColorKey`, …), `FieldAccess`, `EnumValues`.
- **Helpers** ayant migré depuis `@rebasepro/common` : les helpers de stratégies au format collection (`policyToPostgres`, `compileRulePolicies`, `getEffectiveSecurityRules`, `getGeneratedPolicyNames`, …), `CollectionRegistry`, `resolveCollectionRelations`, `resolveRelation`, `getTableName`, `findRelation`, `rowToViewModel`, `resolvePrimaryKeys`, la vue d'accès aux champs d'une propriété (`effectiveAccess`, `canReadField`, `canWriteField`), `evaluateCondition`, `canEditEntity`, `resolveProperty`, `getDefaultValuesFor`, `getSubcollections`, `getCopyValues`, `enumToObjectEntries`. Une règle compilée à partir d'une expression brute utilise `compilePolicyExpression(expr)` issu de `@rebasepro/common`.
- **`composeCallbacks`** compose les callbacks d'une collection pour le panneau et a été déplacé vers `@rebasepro/cms-types` ; `@rebasepro/server` ne le réexporte plus. Le code backend compose les hooks d'une table avec `composeTableHooks` depuis `@rebasepro/common`, et le codemod liste tout import backend de `composeCallbacks` sous la forme d'une étape manuelle précisant ce changement.
- **`defineCollection`** est retiré de `@rebasepro/common` et `@rebasepro/cms-types` : déclarez la table avec `defineTable` dans `backend/schema` et personnalisez-la avec `customizeTable` dans `frontend/src/cms` ; une collection Firestore s'écrit avec `defineFirestoreCollection` issu de `@rebasepro/firebase`.
- **L'accesseur du panneau d'administration et ses types** : `Entity`, `EntityValues`, `TableAccessor`, `TableTrashAccessor`, `FindResponse`, `QueryBuilderInterface`, `RebaseData` et `AuthState` ont quitté `@rebasepro/types` ; `buildRebaseData`, `wrapAsEntityData`, `buildRoutedRebaseData`, `EntityDataOptions`, `QueryBuilder`, `RelationRef` et `createRelationRef` ont quitté `@rebasepro/common`. Tous s'importent depuis `@rebasepro/cms-types`. La couche de données propre au SDK — `buildSdkData`, `createDriverTableRows`, `buildRoutedSdkData`, dans `@rebasepro/common` — sert directement les lignes et renvoie ce qu'elle renvoyait auparavant.
- **`EntityDataOptions.resolveCollection`** est remplacé par `primaryKeysOf`, `viewModelOf`, `storedValuesOf` et `viewModelSourceOf` ; `collectionEntityDataOptions(resolveCollection, { resolveDataPath, resolveAccessor })` issu de `@rebasepro/cms-types` les construit.
- **Le lift de migration** (`collectionsToTableDefs`, `collectionToTableDef`, `LiftNote`, `LiftResult`, `LiftOptions`) a été déplacé dans `@rebasepro/common/migrate`, aux côtés d'une copie figée du modèle de collection 0.30 (les types `Legacy…`) et de `defineLegacyCollection`.
- **Sont également retirés des racines du noyau**, chacun étant listé par le codemod comme étape manuelle : l'API de patch de collection de `@rebasepro/types` (`CollectionPatch`, `CollectionPatchOp`, `applyCollectionPatch`, `collectionPatchProblems`, `isCollectionPatch`, `nestCollectionPatchPaths` → `TablePatch`), ses helpers JSON de collection (`diffCollections`, `diffJsonValues`, `toCollectionJson`, `RUNTIME_ONLY_COLLECTION_KEYS`, `runtimeOnlyKeyIn`), l'époque Mongo avec `DocumentAdmin`, `isDocumentAdmin` et la fonctionnalité `supportsDocumentAdmin`, ainsi que `RebaseProjectContract.collectionSlugs` / `.collections` / `.generatedAt` (`/api/meta/contract` sert `tables`) ; depuis `@rebasepro/common`, `buildTenantSecurityRule` → `tenantSecurityRule`, `defaultPoliciesDisabled` → `tableDefaultPoliciesDisabled`, `restoresSoftDeletedRow` → `isSoftDeleteRestore`, `softDeleteFieldOf` → `softDeleteColumn`, `getJunctionConfigForRelation` → `resolveTableJunctions`, et `isRelationRequired`, `relationDeclaringProperty`, `requireCallbackCollection` sans successeur (lisez le `TableDescriptor`).

**Ce qu'il faut faire :** `rebase migrate sdk-calls` (inclus dans `collections-to-tables`) déplace chaque import ci-dessous vers son nouveau paquet — fusionné dans un import existant de ce paquet si le fichier en comporte déjà un, les alias `import type`, `type` en ligne et `as` étant conservés — et ajoute le paquet aux dépendances du workspace qui l'importe ; lancez `pnpm install` ensuite. Un import d'un nom supprimé, un import d'espace de noms (`import * as`), un `export *`, un `import()` dynamique ou un `require()` utilisant un nom déplacé fait l'objet d'une étape manuelle numérotée. ## 136. Le pilote Postgres et les lectures ponctuelles du socket renvoient la ligne REST

**Qui est concerné :** une fonction ou un plugin qui lit via `requireDriver(c)` / `getDriver(c)`, le code qui envoie les trames `FETCH_COLLECTION` / `FETCH_ONE` du socket, et le code qui lisait les objets `{ __type }` d'une réponse.

**Ce qui a changé :** il n'existe plus qu'un seul format de lecture. `fetchCollection` et `fetchOne` sur le pilote Postgres — par lesquels transitent le `requireDriver(c)` d'une fonction, les plugins, les trames ponctuelles du socket, MCP et le simulateur de RLS — renvoient ce que `GET /api/data/<table>` renvoie :

| Valeur | Lecture du pilote 0.30 | 0.31 |
|---|---|---|
| un horodatage | `{ "__type": "date", "value": … }` | une chaîne RFC 3339 |
| un `belongsTo` | `{ "__type": "relation", "id", "path" }` sous le nom de la relation | la clé étrangère sous sa propre clé (`authorId`) |
| une ligne liée | chaque relation chargée par `fetchOne` | uniquement une relation nommée par `include`, sous forme de la propre ligne de la cible |
| un vecteur, un `bytea` | `{ "__type": "Vector" }`, une URL de données | tels que servis par REST |

`FetchOneProps` accepte `include` (`ListenOneTarget` est supprimé : utilisez `FetchOneProps`). `rebase.data`, `context.data` et le SDK renvoyaient déjà ce format et restent inchangés.

`@rebasepro/client` lit les corps REST et les trames de socket sous forme de JSON brut : une valeur comportant une clé `__type` n'est plus convertie en `Date`, `EntityReference`, `EntityRelation`, `GeoPoint` ou `Vector`, et un document JSON contenant une clé `__type` est renvoyé tel qu'il a été stocké.

**Ce qu'il faut faire :** lisez la ligne brute : convertissez les dates à partir de leurs chaînes de caractères, lisez une clé étrangère depuis sa propre clé, et transmettez `include` pour chaque relation que vous lisez :

```diff ts
-const article = await requireDriver(c).fetchOne({ path: "articles", id });
-const authorId = article?.author.id;      // a { __type: "relation" } ref
+const article = await requireDriver(c).fetchOne({ path: "articles", id, include: ["author"] });
+const authorId = article?.authorId;
```

## 138. Le backend accepte uniquement les valeurs documentées par l'API REST

**Qui est concerné :** un client qui écrit une relation to-one sous forme d'objet ou un vecteur sous forme de `{ value }`, le code qui filtre sur une relation avec un objet, le code qui importe les classes de valeurs de l'administration, et une application hors ligne avec des écritures mises en file d'attente sous 0.30.

**Ce qui a changé :** une écriture adopte le format qu'une lecture renvoie — un format d'écriture unique pour REST, le socket, MCP et le SDK in-process :

| Valeur | Accepté | Désormais refusé |
|---|---|---|
| une relation to-one (`belongsTo`, `hasOne`, un `via` to-one) | la clé de la ligne liée, ou `null` (`""` vaut `null`), sous le nom de la relation ou celui de la clé étrangère | un objet tel que `{ "id": 5 }` : `400 VALIDATION_INVALID_VALUE`, « 'posts.author' links one 'authors' row: write that row's key (a string or a number), or null to unlink — not an object. » |
| une relation to-many (`hasMany`, `manyToMany`, un `via` to-many inscriptible) | une liste de clés, ou de `{ id, _pivot? }` | — (les autres clés sur l'objet sont ignorées, comme avant) |
| un vecteur | une liste de nombres | un `Vector`, ou `{ "value": [...] }` : `400`, « 'embedding' expects a vector as a list of numbers » |
| une date, une heure | texte ISO (`Date` in-process) | — |
| un point géographique | `{ latitude, longitude }` | — |
| un `bytea` | une URL `data:application/octet-stream;base64,` (`Buffer` / `Uint8Array` in-process) | — |
| un filtre sur une relation | la clé | un objet n'est plus déballé : il est comparé tel quel |

La version 0.30 acceptait une relation to-one écrite sous forme d'objet et extrayait silencieusement son `id` ; ce format n'a jamais été documenté et représentait le modèle de vue du panneau d'administration. Le panneau d'administration convertit désormais son modèle de vue en valeurs prêtes pour le transit réseau dans le navigateur avant chaque écriture et chaque filtrage.

Les classes de valeurs de l'administration ont été déplacées avec le reste de son modèle de vue : `EntityReference`, `EntityRelation`, `GeoPoint`, `Vector` et `EntityReferenceProps` s'importent depuis `@rebasepro/cms-types` (elles ont quitté `@rebasepro/types`), de même que `normalizeToEntityRelation` (qui a quitté `@rebasepro/common`) ; `withRelationReferencesOnly` est supprimé. L'historique stocke la ligne telle qu'une lecture la renvoie ; les entrées enregistrées auparavant sont servies et restaurées sous forme de valeurs brutes ([section 132](#132-lhistorique-est-servi-sous-forme-de-lectures)).

La file d'attente hors ligne de `@rebasepro/client` stocke des valeurs de transit réseau. Une écriture mise en file d'attente hors ligne par le SDK 0.30 est convertie lorsqu'elle est relue et rejouée : aucun élément mis en attente avant la mise à niveau n'est perdu.

**Ce qu'il faut faire :** envoyez la clé : `{ "author": 5 }`, et non `{ "author": { "id": 5 } }` ; envoyez un vecteur sous forme de liste de nombres, et filtrez une relation à l'aide de sa clé. `rebase migrate sdk-calls` déplace les imports des classes de valeurs ([la liste](/docs/upgrading/0-30-to-0-31-imports/)). Voir [Écritures](/docs/backend/writes/).

## 139. `/api/docs` est servi au public du point de terminaison de schéma

**Qui est concerné :** une personne ou un outil qui lit `/api/docs` ou ouvre `/api/swagger` — Swagger UI, un générateur de client d'API, une étape de CI.

**Ce qui a changé :** lorsque `enableSwagger` n'est pas défini (`REBASE_ENABLE_SWAGGER` non défini), dans chaque environnement, le document OpenAPI est servi aux appelants auxquels `GET /api/schema/tables` décrit les tables, avec les mêmes refus — 401 pour un appelant anonyme sauf si `schemaTables.public`, 403 pour un identifiant sans portée schéma ou données — et chaque appelant reçoit le document contenant exactement les tables, colonnes et relations que ce point de terminaison lui décrit (un administrateur reçoit l'ensemble). Il n'y a pas d'interface Swagger UI. Un serveur sans authentification configurée répond `404 DOCS_UNAVAILABLE`. La version 0.30 publiait l'intégralité du document, chaque table servie et chaque colonne non privée, aux appelants anonymes en développement, et le restreignait aux administrateurs en production.

| `enableSwagger` / `REBASE_ENABLE_SWAGGER` | `/api/docs` | `/api/swagger` |
|---|---|---|
| non défini (par défaut) | chaque appelant auquel le point de terminaison de schéma décrit les tables : leurs tables | non servi |
| `true` | l'intégralité du document, à tout le monde | servi hors production |
| `false` | l'intégralité du document, réservé aux administrateurs | non servi |

**Ce qu'il faut faire :** appelez `/api/docs` en étant authentifié. Pour publier l'intégralité du document comme le faisait la 0.30 en développement, définissez `REBASE_ENABLE_SWAGGER=true` (ou `enableSwagger: true`). Voir [Points de terminaison](/docs/backend/endpoints/).

## 140. Une colonne `pivot` many-to-many ne peut pas déclarer de `.transform()`

**Qui est concerné :** un `rel.manyToMany(…, { pivot: { … } })` dont la colonne pivot possède un `.transform()`.

**Ce qui a changé :** le compilateur le refuse (« the pivot column "x" declares `.transform()` … »). La transformation d'une colonne pivot ne s'exécutait nulle part ; par conséquent, une valeur que vous souhaitiez masquer était servie telle qu'elle était stockée.

**Ce qu'il faut faire :** supprimez le `.transform()` et masquez `_pivot` dans le `hooks.afterRead` de la table cible. Voir [Relations](/docs/collections/relations/).

## 141. Un lien est exactement aussi lisible et inscriptible que sa colonne de clé

**Qui est concerné :** un client qui écrit un `belongsTo` par son nom de relation, lit ou filtre une relation dont la colonne de clé est restreinte, ou s'appuie sur `strictWrites: false`.

**Ce qui a changé :** une restriction sur une colonne de clé s'applique à toute formulation qui la lit ou l'écrit.

- Écrire un lien par son nom de relation (`{ "reviewer": 7 }`) est soumis à chaque règle de la colonne de clé qu'il définit — `.readOnly()`, `.private()`, `access.write`, horodatages de création, colonne de tenant, immutabilité de la clé — sur REST, en bloc (bulk), `_batch`, le socket et MCP. Écrire le lien sous les deux noms (`{ "reviewer": 7, "reviewerId": 8 }`) avec des valeurs divergentes renvoie une 400 `VALIDATION_INVALID_VALUE`. Déplacer une ligne vers un autre tenant via son lien renvoie une 400 `TENANT_IMMUTABLE` (au lieu d'une 500).
- Une relation n'est lisible que si l'appelant est autorisé à lire chaque colonne lue par sa jointure, sur chaque table traversée : la clé d'un `belongsTo`, la clé étrangère de la cible pour un `hasMany` / `hasOne`, chaque colonne sur laquelle portent les étapes d'un `via`. Une colonne inaccessible est omise de `include` et de `_count`, et un filtre, un tri ou un chemin de relation passant par elle répond `FIELD_NOT_READABLE` (une relation inconnue si la colonne est `.private()`). Une écriture `via` to-one qui copierait une colonne que l'appelant ne peut pas lire est refusée avec `FIELD_NOT_READABLE`. Les cas inverses et `via` étaient également ouverts sous 0.30.x.
- Un lien dont l'appelant ne peut pas lire la colonne de clé est omis de `include`, et un filtre, un tri, une entrée dans `fields` ou un chemin de relation passant par celui-ci répond `FIELD_NOT_READABLE` ; un lien lié à une clé `.private()` est considéré comme une relation inconnue. `GET /api/schema/tables`, OpenAPI et `describe_table` de MCP décrivent un lien conjointement avec sa clé ; ainsi, une colonne de clé dont le lien est fermé y est également dissimulée.
- `strictWrites: false` ne décide que d'une chose : une clé non déclarée est transmise au pilote (écrite si la base de données possède la colonne, sinon erreur 400 `VALIDATION_UNKNOWN_FIELDS`). Cela ne déverrouille jamais une colonne déclarée, un horodatage, le tenant, la clé, une cible de relation ou une règle de `_pivot`.

**Ce qu'il faut faire :** écrivez un lien par un seul nom, ou par les deux en utilisant la même valeur ; lisez les liens restreints avec un rôle autorisé à lire leur clé. Voir [Accès aux champs](/docs/collections/field-access/).
