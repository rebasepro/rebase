# Mise à niveau 0.29 → 0.30

Voici les entrées `### Breaking` introduites par la version 0.30 pour une application sous 0.29.

---

## 107. Un backend démarré via la bibliothèque conserve le refresh token dans un cookie

**Qui est concerné :** un backend que vous démarrez vous-même avec `initializeRebaseBackend` qui ne définit pas `auth.cookieAuth`, ainsi que tout appelant lisant le refresh token depuis le corps de la réponse sans envoyer `x-rebase-auth-flow: json` : un client mobile développé manuellement, un script `curl`, ou un `@rebasepro/client` antérieur à la version 0.29 en mode json. Un backend exécuté par le runtime Rebase (`rebase dev`, un bundle, Rebase Cloud) et le modèle éjecté (ejected template) l'avaient déjà activé, rien ne change donc pour eux.

**Ce qui a changé :** `cookieAuth` est activé par défaut à moins que vous ne le configuriez. La connexion (sign-in) et le rafraîchissement (refresh) renvoient `tokens.refreshToken: ""` dans le corps et définissent le jeton sous forme de cookie `HttpOnly`, `Secure`, `SameSite=Lax` (`__rb_refresh`). Auparavant, le jeton était renvoyé dans le corps de la réponse. C'est ce qu'attend un `@rebasepro/client` pour navigateur depuis la version 0.28, raison pour laquelle son application affichait l'écran de connexion à chaque rechargement face à un tel backend.

**Le symptôme constaté :** un client qui lit le corps de la réponse reçoit un refresh token vide, ce qui empêche le renouvellement de sa session et y met fin à l'expiration de l'access token, environ une heure après la connexion.

**Que faire**, selon votre situation :

- Envoyez `x-rebase-auth-flow: json` lors des requêtes d'authentification du client. Le backend répond à cette requête dans le corps, comme auparavant, sans jamais lire ni définir de cookie pour celle-ci. `@rebasepro/client` 0.29 et ultérieur fait cela en mode json (voir [où réside le refresh token](/docs/sdk/authentication/)).
- Conservez l'ancien comportement pour tous les clients :

  ```typescript no-verify
  auth: { jwtSecret, cookieAuth: false }
  ```

  Un client de navigateur connecté à ce backend nécessite `auth: { authFlowMode: "json" }` sur `createRebaseClient`, sans quoi chaque rechargement le déconnectera.

Une application de navigateur sur une autre origine envoie désormais le cookie, le CORS du backend doit donc autoriser les identifiants (credentials) : une liste explicite d'origines, jamais `origin: "*"`. Un frontend situé sur un site différent de l'API a également besoin de `cookieAuth: { sameSite: "None" }`, faute de quoi le navigateur ne renverra jamais le cookie. Voir [Refresh tokens dans un cookie `httpOnly`](/docs/backend/authentication/#refresh-tokens-in-an-httponly-cookie).
