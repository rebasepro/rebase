# Migrer 0.18 → next

**Rien de tout cela n'est publié.** Ce sont les entrées `### Breaking` de la
section [`[Unreleased]`](/fr/docs/changelog/) du changelog : elles sont sur `main`,
et ce site de documentation publie depuis `main` — donc avant que la version qui
les porte n'existe. Si vous avez installé depuis npm, vous êtes en 0.20 et rien
de tout cela ne vous a encore atteint. 0.19 et 0.20 ne déclarent aucune rupture :
c'est donc un seul saut depuis 0.18.

---

## 31. `context.client.data` ne compile plus dans un callback de collection

`RebaseCallContext["client"]` est désormais `RebaseCallbackClient` : `RebaseClient`
sans `data`. Côté serveur, ce client est le singleton `rebase`, qui n'a plus de
`data` depuis la 0.18 — `context.client.data.collection(…)` compilait donc, puis
levait `Cannot read properties of undefined (reading 'collection')` à chaque
appel. C'est désormais une erreur de compilation.

**À changer :** interrogez les données via `context.data`, l'accesseur que les
requêtes d'un callback auraient toujours dû utiliser. Il s'exécute avec le
privilège de ce qui a déclenché le callback, dans la transaction même de
l'écriture. Le [guide des callbacks](/fr/docs/collections/callbacks/) décrit ce
que chaque accesseur du contexte peut atteindre.

```diff lang="ts"
 afterSave: async ({ context }) => {
-    await context.client.data.audit_logs.create({ action: "approved" });
+    await context.data.audit_logs.create({ action: "approved" });
 }
```

```bash
grep -rn "client\.data\b" config
```

`context.client.dataAsAdmin` reste disponible pour un callback qui doit voir ce
qu'un administrateur peut voir. `admin.browserCallbacks` change aussi : l'ancienne
écriture y fonctionnait, car le client du panneau a un `data`, et elle cesse
pourtant de compiler. `useRebaseContext().client` dans un composant React garde
son `data`.
