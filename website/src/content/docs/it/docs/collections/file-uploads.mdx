Un campo file è una colonna [`col.storage()`](/docs/schema/columns/#storage-columns).
La colonna contiene del testo, ovvero la chiave dell'oggetto nel bucket (o il suo URL, se
specificato dalla colonna), e il CMS la visualizza come un campo di caricamento con un'anteprima.

Il funzionamento di un campo storage è suddiviso in due parti, in base a dove viene eseguito:

| Dichiarato | Dove | Opzioni |
|---|---|---|
| sulla colonna, in `backend/schema` | letto dal server **e** dal CMS | `path`, `source`, `accept`, `maxBytes`, `imageResize`, `public`, `fileName`, `metadata`, `includeBucketUrl`, `storeUrl` |
| in `customizeTable`, in `frontend/src/cms` | solo nel browser | `storage.path(…)`, `storage.fileName(…)`, `storage.processFile`, `storage.postProcess`, `storage.previewUrl` |

Le opzioni della colonna sono serializzabili, quindi viaggiano nel descrittore della
tabella e il server applica quelle che può. Le opzioni di `customizeTable` sono
funzioni: non possono raggiungere il server, quindi modellano solo i caricamenti effettuati
dal CMS.

## Un file

<span class="since-badge" data-since="0.31">Da 0.31</span>

```ts
// backend/schema/listings.ts
import { defineTable, col } from "@rebasepro/server/schema";

export const listings = defineTable("listings", {
    columns: {
        id:     col.uuid().primaryKey().defaultRandom(),
        title:  col.text().notNull(),
        cover:  col.storage({ path: "listings/{id}/", accept: ["image/*"], maxBytes: "10MB",
                              imageResize: { maxWidth: 1600, format: "webp", quality: 80 } }),
        photos: col.storage({ path: "listings/{id}/gallery/", accept: ["image/*"] }).multiple(),
    },
    rls: "admin-only",
});
```

`cover` è un campo di caricamento che accetta un'immagine di massimo 10 MB, ridimensionata
a una larghezza massima di 1600 pixel e memorizzata come WebP. Una colonna il cui `accept` specifica un
tipo di immagine mostra un'anteprima come immagine, e la prima colonna di questo tipo occupa lo slot
dell'immagine del record nelle schede e negli elenchi.

## Più file

<span class="since-badge" data-since="0.31">Da 0.31</span>

riordinabile tramite trascinamento. Ogni opzione si applica a ciascun file.

## Opzioni lato browser

<span class="since-badge" data-since="0.31">Da 0.31</span>

```tsx
// frontend/src/cms/listings.tsx
import { customizeTable } from "@rebasepro/cms";
import type { listings } from "../../../backend/schema/listings";

export const listingsCms = customizeTable<typeof listings>("listings", {
    fields: {
        cover: {
            storage: {
                // A folder per listing title, computed in the browser.
                path: ({ values }) => `listings/${String(values.title ?? "untitled").toLowerCase()}/`,
                fileName: ({ file }) => `${Date.now()}-${file.name}`,
            },
            urlPreview: "image",
        },
        photos: {
            sortable: true,
            storage: { processFile: async (file) => file },
        },
    },
});
```

| `storage.` | Esecuzione | Effetto |
|---|---|---|
| `path(context)` | prima di un caricamento | La cartella in cui viene salvato il file, sostituendo il template `path` della colonna. |
| `fileName(context)` | prima di un caricamento | Il nome del file memorizzato, sostituendo il template `fileName` della colonna. Può essere asincrono. |
| `processFile(file)` | prima di un caricamento | Trasforma il file (compressione, rimozione dei metadati). |
| `postProcess(pathOrUrl)` | dopo un caricamento | Trasforma il percorso o l'URL prima che venga scritto nella colonna. |
| `previewUrl(fileName)` | durante il rendering | L'URL per visualizzare l'anteprima di un file memorizzato, quando non corrisponde al valore del campo. |

A `path` e `fileName` viene passato il contesto del caricamento: il `file`, l'`id`
del record (assente su un nuovo record), i suoi `values` così come modificati, la `propertyKey` e le
regole di storage risolte. Su una colonna `.multiple()`, le stesse opzioni `storage` vengono inserite
direttamente sul campo e si applicano a ciascun file.

`urlPreview` imposta la modalità di anteprima del valore memorizzato (`"image"`, `"video"`,
`"audio"`, `"file"` o `true` per un link), e `clearable` aggiunge un controllo che
svuota il campo.

## Cosa verifica il server

<span class="since-badge" data-since="0.31">Da 0.31</span>

`accept` e `maxBytes` vengono applicati dal server in base a **dove viene salvato
il file**. Il `path` di una colonna è la destinazione dei suoi file, quindi è anche dove valgono
i suoi limiti: ogni caricamento la cui chiave è un file direttamente sotto quel percorso deve
rispettarli, che provenga dal CMS, da `client.storage.putObject`, da un caricamento ripristinabile, dallo
storage browser di Studio o da `curl`, indipendentemente dal fatto che indichi o meno la colonna, sul
bucket della colonna stessa. I segnaposto corrispondono a qualsiasi valore che il CMS inserirebbe:
`{id}`, `{rand}`, `{file}` e simili rappresentano un singolo segmento del percorso, `{path}`
un numero qualsiasi di segmenti. Il percorso di una colonna con `public: true` si trova sotto `public/`.

- Più colonne che condividono lo stesso percorso: viene accettato un file accettato da una qualsiasi di esse.
- Un caricamento che specifica anche la propria colonna, come fanno i caricamenti del CMS, è vincolato
  anche a quella colonna. Specificare una colonna con vincoli più permissivi non sblocca il percorso di una più restrittiva.
- Una funzione `storage.path` in `customizeTable` non può essere letta dal server,
  quindi un file caricato nel percorso da essa calcolato è soggetto ai limiti della colonna
  solo quando il caricamento specifica la colonna, cosa che i caricamenti del CMS fanno sempre.
- Un percorso non rivendicato da alcuna colonna è soggetto esclusivamente al limite del bucket stesso
  (`STORAGE_MAX_FILE_SIZE`).

`imageResize`, `processFile` e `postProcess` vengono eseguiti nel browser, prima dell'invio
dei byte: un file caricato con un'altra modalità viene memorizzato così come è stato inviato.

## Dove può essere salvato un file

<span class="since-badge" data-since="0.31">Da 0.31</span>

`path` è un valore predefinito, non un limite invalicabile: nulla sul server confina un caricamento ad
esso. Chi può scrivere e dove è determinato da una regola di autorizzazione dello storage; vedere
[Storage](/docs/backend/storage/).

## I file non vengono mai eliminati automaticamente

<span class="since-badge" data-since="0.31">Da 0.31</span>

Svuotare un campo file, sostituire il suo file o eliminare la riga lascia l'oggetto
memorizzato al suo posto. Ogni caricamento riceve una propria chiave, quindi una sostituzione scrive
un nuovo oggetto e nulla rimuove quello precedente: due righe possono contenere la stessa
chiave, pertanto il CMS non può sapere se un file non è più utilizzato. Gli oggetti a cui nessuna riga fa riferimento
rimangono nel bucket e continuano a essere fatturati finché non li si elimina dallo storage
browser di Studio, con `client.storage.deleteObject(key)` o tramite una regola di ciclo di vita sul
bucket. `rebase storage orphans` elenca i file a cui nessuna riga fa riferimento e li elimina
con `--delete`; vedere [la CLI](/docs/cli/#rebase-storage).

## Spostare una colonna in un altro bucket

<span class="since-badge" data-since="0.31">Da 0.31</span>

Un campo file memorizza la chiave dell'oggetto, non il suo bucket. La modifica del `source`
di una colonna reindirizza ogni valore esistente verso il nuovo bucket, dove tali chiavi non
esistono, facendo sì che le anteprime dei file più vecchi restituiscano "non trovato". Copiare prima gli oggetti
nel nuovo bucket mantenendo le stesse chiavi, utilizzando
`rebase storage move --from <old> --to <new> --prefix <path>` oppure gli strumenti proprietari
del provider, come `aws s3 sync` o `gcloud storage cp`, oppure mantenere il vecchio bucket
per i file esistenti.
