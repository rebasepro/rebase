<span class="since-badge" data-since="0.31">Da 0.31</span>

Le regole di una colonna vengono dichiarate una sola volta, sulla colonna, e vengono applicate dal server a ogni scrittura che raggiunge l'API. Il CMS legge le stesse regole dal descrittore della tabella e le verifica nel modulo prima del salvataggio, in modo che l'operatore veda l'errore direttamente sul campo anziché sotto forma di richiesta rifiutata.

```ts
// backend/schema/events.ts
import { defineTable, col } from "@rebasepro/server/schema";

export const events = defineTable("events", {
    columns: {
        id:      col.uuid().primaryKey().defaultRandom(),
        title:   col.text().notNull().validate({ min: 2, max: 200, requiredMessage: "Every event needs a title" }),
        slug:    col.varchar({ length: 80 }).notNull().unique()
                     .validate({ matches: "^[a-z0-9-]+$", matchesMessage: "Lowercase letters, digits and hyphens only" }),
        isFree:  col.boolean().notNull().default(false),
        price:   col.numeric({ precision: 10, scale: 2 }).validate({ min: 0 }),
        seats:   col.integer().validate({ positive: true }),
    },
    rls: "admin-only",
});
```

:::note[Provieni dalle collezioni?]
Non esiste più un blocco `validation` nel frontend. Le regole vengono definite sulla colonna con `.notNull()` e `.validate({ … })`, e il CMS le legge.
:::

## Cosa controlla il modulo

<span class="since-badge" data-since="0.31">Da 0.31</span>

| Sulla colonna | Nel modulo |
|---|---|
| `.notNull()` | Obbligatorio, con `requiredMessage` come errore se specificato. Non obbligatorio dove nessuno digita il valore: una chiave generata, un timestamp, una colonna generata o `.readOnly()`. |
| `.unique()` | Il valore viene verificato rispetto alla tabella prima di salvare una modifica, e un eventuale duplicato viene segnalato sul relativo campo. |
| `varchar(n)`, `char(n)` | Al massimo `n` caratteri. |
| text `min`, `max`, `length` | Conteggio dei caratteri, estremi inclusi. |
| `matches`, `matchesMessage` | L'intero valore deve corrispondere al pattern; il messaggio costituisce l'errore. |
| `email`, `url` | Il valore deve essere un'email, un URL. |
| `trim`, `lowercase`, `uppercase` | Il valore viene normalizzato rimuovendo gli spazi vuoti (trim) o convertito in minuscolo/maiuscolo prima del salvataggio. |
| number `min`, `max`, `moreThan`, `lessThan`, `positive`, `negative`, `integer` | Limiti e solo numeri interi. Le colonne di tipo integer e serial sono numeri interi indipendentemente da quanto specificato in `.validate()`. |
| date `min`, `max` | La data minima e massima consentita. |
| array `minItems`, `maxItems`, `uniqueItems` | Numero di elementi e nessun duplicato. |

Ogni regola è elencata, con il relativo significato esatto, in [Colonne](/docs/schema/columns/#validation).

## Dove viene eseguita la validazione

<span class="since-badge" data-since="0.31">Da 0.31</span>

Il server controlla le regole di una colonna a livello di confine della richiesta (REST, socket in tempo reale e MCP) sui dati inviati dal chiamante, prima dell'esecuzione di `beforeSave`, e risponde a una scrittura che viola una regola con un errore 400 indicando ogni campo non valido. Il codice server che esegue scritture in-process è considerato attendibile e non viene verificato rispetto a queste regole; in quel caso si applicano solo i vincoli imposti dal database. Consulta [Colonne](/docs/schema/columns/#validation).

Il CMS verifica le stesse regole prima del salvataggio, sia nel modulo del record sia nell'editor inline della tabella. Una cella della tabella valuta un valore non appena viene modificata: un valore già memorizzato che viola una regola aggiunta successivamente non mostrerà alcun errore finché qualcuno non modificherà quella cella.

## Campi condizionali

<span class="since-badge" data-since="0.31">Da 0.31</span>

Un campo può reagire ai valori del record stesso: diventare obbligatorio, disabilitato, in sola lettura o nascosto. Ci sono due modalità, entrambe in `customizeTable`:

```tsx
// frontend/src/cms/events.tsx
import { customizeTable } from "@rebasepro/cms";
import type { events } from "../../../backend/schema/events";

export const eventsCms = customizeTable<typeof events>("events", {
    fields: {
        price: {
            conditions: {
                disabled: { "==": [{ "var": "values.isFree" }, true] },
                required: { "!=": [{ "var": "values.isFree" }, true] },
                min: 0,
                disabledMessage: "Free events have no price",
                clearOnDisabled: true,
            },
        },
        seats: {
            dynamicProps: ({ values, authController }) => ({
                disabled: values.isFree === true || !authController.user?.roles?.includes("admin"),
            }),
        },
    },
});
```

### `conditions`: JSON Logic

`conditions` contiene regole [JSON Logic](https://jsonlogic.com/) applicate al record in fase di modifica (`values.<key>`). Essendo dati, l'editor dello schema può leggerle e modificarle. Una condizione può impostare:

- `disabled`, `disabledMessage`, `clearOnDisabled`, `hidden`, `readOnly`;
- `required`, `requiredMessage`, `min`, `max`;
- `defaultValue`;
- `enumConditions`, `allowedEnumValues`, `excludedEnumValues`;
- `referencePath`, `referenceFilter`;
- `canAddElements`, `sortable`, per gli array.

`disabledMessage` è ciò che l'utente vede accanto al controllo disabilitato (in grigio). Senza di esso, un campo disabilitato non fornisce alcuna spiegazione.

### `dynamicProps`: una funzione

A `dynamicProps` viene passato il record mentre viene modificato (`values`, comprese le modifiche non salvate, e `previousValues` una volta salvato) insieme all'utente autenticato su `authController`, e restituisce le opzioni del campo applicabili in quel momento. Ciò che restituisce viene applicato sopra le altre opzioni del campo ogni volta che il modulo lo richiede, consentendogli di restituire qualsiasi opzione del campo: `disabled`, `hidden`, `readOnly`, `name`, `description`, `enumLabels`…

:::caution[Le condizioni riguardano il comportamento del modulo]
`conditions` e `dynamicProps` vengono eseguiti nel browser e modellano ciò che il CMS offre. L'API accetta scritture che le ignorano. Una regola che deve valere per qualsiasi chiamante appartiene alla colonna (`.notNull()`, `.validate()`) oppure alla [row-level security](/docs/collections/security-rules/) della tabella, che il database applica per chiunque.
:::

## Etichette per un set chiuso di valori

<span class="since-badge" data-since="0.31">Da 0.31</span>

I valori di un `col.enum([...])` o di un `.oneOf([...])` appartengono alla colonna. Le relative etichette, i colori e l'ordinamento appartengono invece al CMS, configurati tramite `enumLabels` ed `enumOrder`; vedi [set chiusi](/docs/collections/properties/#closed-sets-of-values).
