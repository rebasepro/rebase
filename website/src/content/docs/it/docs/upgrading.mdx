# Aggiornare un'applicazione esistente

Dodici passaggi, dai più recenti ai più vecchi. Inizia da quello immediatamente successivo alla versione in uso e procedi verso il basso — oppure, se provieni dalla versione 0.12, parti dal fondo e risali verso l'alto.

| Versione attuale | Da leggere | Cosa comporta |
|---|---|---|
| **0.29** | [0.29 → 0.30](/docs/upgrading/0-29-to-0-30/) | Un backend avviato con `initializeRebaseBackend` conserva il refresh token in un cookie, a meno che non imposti `cookieAuth: false`: chi lo legge dal corpo senza `x-rebase-auth-flow: json` riceve `""`. |
| **0.27 – 0.28** | [0.27 → 0.29](/docs/upgrading/0-27-to-0-29/) | Tutto ciò che l'admin passa al tuo codice è la riga del server con il relativo id a fianco: `context.data` e `browserCallbacks` nel browser passano stringhe ISO e foreign key dove prima passavano `Date` e oggetti di relazione, cosa che nessun compilatore rileva; gli hook dei dati di `Entity` diventano interni; e callback, pannelli, il pannello laterale e la selezione accettano `row` e `id` al posto di `entity` ed `entityId`. La versione 0.28 non dichiara alcuna modifica incompatibile, quindi si tratta di un unico passaggio da 0.27. |
| **0.26** | [0.26 → 0.27](/docs/upgrading/0-26-to-0-27/) | Una pianificazione cron che vincola entrambi i campi dei giorni viene eseguita su uno qualsiasi dei due, quindi viene eseguita più spesso, e una pianificazione con un numero non valido viene rifiutata, interrompendo l'esecuzione di quel job. Una chiave la cui strategia `isId` non può essere rispettata dal relativo tipo blocca l'avvio. Su Rebase Cloud, un deploy o una preview fallisce quando un file di funzione o cron non viene caricato. |
| **0.25** | [0.25 → 0.26](/docs/upgrading/0-25-to-0-26/) | Vengono rifiutate una scrittura che specifica una relazione `via` multi-hop, un nome di ruolo che non corrisponde a un singolo ruolo, un token di pagina in local storage precedente all'aggiornamento e un upstream di funzioni non funzionante. L'accesso OAuth finalizza un account non verificato invece di rispondere con `local-account-unverified`, il server MCP non invia più `REBASE_TOKEN` all'app e i tipi generati rimuovono la chiave di un belongsTo con `excludeFromApi`. Su Rebase Cloud, `rebase cloud webhooks` e `--scale-to-zero true` vengono dismessi, e i token più vecchi potrebbero dover essere ricreati. |
| **0.24** | [0.24 → 0.25](/docs/upgrading/0-24-to-0-25/) | `?count=` in un elenco REST diventa lo switch per il conteggio dietro a `meta.total`, quindi un filtro su una colonna denominata `count` va inserito all'interno di `?where=`; `list_collections` dell'MCP remoto invia il proprio elenco solo nel blocco di testo, senza `structuredContent`; e `@rebasepro/app` non esporta più la tabella di traduzione spagnola `es`. Vengono rifiutate una semplice richiesta `OPTIONS` verso una route senza gestore, tabelle con nomi in conflitto all'avvio, un upsert sulla collection degli utenti, `page` con `offset`, una stringa vuota per un campo obbligatorio e la password di un amministratore che non rispetta i criteri di sicurezza. Le sessioni durano per impostazione predefinita 30 giorni di inattività, `client.cron` chiama `/api/admin/cron`, le letture offline che non possono essere soddisfatte completamente falliscono con `OFFLINE`, e alcune esportazioni interne e prop non utilizzate sono state rimosse. |
| **0.23** | [0.23 → 0.24](/docs/upgrading/0-23-to-0-24/) | L'output SQL generato da `db push` e `db generate` viene spostato da `drizzle/` nella directory non tracciata `.rebase/sql/`, il flag `--generate` di `rebase dev` è stato rimosso perché `dev` rigenera sempre i tipi dell'SDK, e una modifica dello schema in tempo reale non esegue il commit di codice SQL. I permessi diventano scope: le interfacce admin richiedono uno scope anziché il ruolo di amministratore, le chiavi API contengono scope anziché un elenco di permessi e un flag `admin`, e `schema-admin` non è più un amministratore. Un percorso relativo per `--collections` viene risolto a partire dalla posizione in cui viene eseguito il comando, vengono rifiutati un upsert in una riga cestinata e un aggiornamento che modifica una chiave, l'endpoint MCP remoto accetta gli argomenti dell'SDK e i socket realtime aperti, i link di verifica email, `signUp` e i codici di recupero MFA modificano il modo in cui gestiscono una sessione. |
| **0.21 – 0.22** | [0.21 → 0.23](/docs/upgrading/0-21-to-0-23/) | Una chiave API su un percorso nidificato richiede `read` sui nodi padre, variabili numeriche illeggibili e durate di sessione non valide impediscono l'avvio, un repository di autenticazione personalizzato richiede `unlinkUserIdentity` e gli upgrade degli utenti guest richiedono il captcha di `register`. La versione 0.22 non dichiara alcuna modifica incompatibile, quindi si tratta di un unico passaggio da 0.21. |
| **0.18 – 0.20** | [0.18 → 0.21](/docs/upgrading/0-18-to-0-21/) | `context.client.data` non compila più in una callback di collection — effettua le query tramite `context.data` — e `selectedEntities` cede il posto a una selezione che può rappresentare righe non caricate da nessuno. Le versioni 0.19 e 0.20 non dichiarano modifiche incompatibili, quindi si tratta di un unico passaggio da 0.18. |
| **0.17** | [0.17 → 0.18](/docs/upgrading/0-17-to-0-18/) | Undici modifiche incompatibili, la maggior parte delle quali errori di compilazione anziché modifiche silenziose di comportamento. `rebase.data` scompare a runtime, i range delle peer dependency si restringono ai caret (^), e la versione minima supportata di Node passa a 22.22.0. |
| **0.14 – 0.16** | [0.14 → 0.17](/docs/upgrading/0-14-to-0-17/) | I pacchetti admin vengono rinominati, le risorse vengono dichiarate anziché configurate, e un bundle compilato in precedenza non si avvierà su un runtime attuale. Le versioni 0.15 e 0.16 non introducono modifiche incompatibili, quindi si tratta di un unico passaggio da 0.14. |
| **0.13** | [0.13 → 0.14](/docs/upgrading/0-13-to-0-14/) | Tutte le chiavi di trasmissione (wire keys) sono in camelCase e l'accesso anonimo richiede un'attivazione esplicita (opt-in). |
| **0.12** | [0.12 → 0.13](/docs/upgrading/0-12-to-0-13/) | Il passaggio più consistente, e l'unico che modifica **chi può leggere i tuoi dati**. Rimuove lo schema `auth`, rinomina i pacchetti, modifica il significato di `id`, elimina CJS, migra il pannello di amministrazione a react-router 8 e corregge tre casi in cui l'accesso poteva essere concesso senza averlo richiesto. |

Le sezioni di ogni pagina sono disposte nell'ordine in cui devono essere eseguite, e ciascuna indica il sintomo che altrimenti ti ritroveresti a diagnosticare dal punto di vista sbagliato.

Inoltre, a prescindere dal passaggio effettuato:

- [The upgrade checklist](#upgrade-checklist) riportata di seguito — i grep e i comandi utili da eseguire successivamente, raccolti in un unico blocco.

## Upgrade checklist

```
[ ] grep for authenticated() and (auth|rebase).uid() IS NOT NULL in config/collections/
[ ] decide the intent of each rule; rewrite the ones that meant "public"
[ ] replace not(authenticated()) with serverContext()
[ ] if realtime.requireAuth was true with an AuthAdapter, treat the socket as
    having been open — verify RLS on every subscribable collection (section 2)
[ ] SELECT ... FROM pg_policies — record the qual of every policy BEFORE
[ ] update package names and imports
[ ] grep for rebase.data — it is now rebase.dataAsAdmin (section 8)
[ ] grep for the other ten removed deprecated exports (section 8)
[ ] drop react-router-dom; import RouterProvider from "react-router/dom"
[ ] check node >= 22.22.0 and react >= 19.2.7 (react-router 8 requires both)
[ ] move defaultSecurityRules into config/collections/index.ts
[ ] grep for .userId
[ ] grep for row.id on tables not keyed on id
[ ] run db push
[ ] run rebase doctor --policies — expect no Insecure or Orphaned entries
[ ] SELECT ... FROM pg_policies again — confirm every intended change landed
[ ] exercise the app signed OUT, in a private window — watch the websocket too

--- 0.13 → 0.14 (part 2) ---
[ ] re-run rebase generate-sdk, then build — the compiler finds row.author_id
[ ] grep for snake_case where/orderBy keys; a stale one is a 400, not a warning
[ ] grep for raw fetch consumers reading row.<something>_id — these read
    undefined and raise nothing
[ ] if the project was introspected, re-run rebase schema introspect
[ ] decide anonymous sign-in: set auth.allowAnonymous: true, or confirm you
    never used it (grep for signInAnonymously)
[ ] drop @rebasepro/client-postgres from package.json

--- 0.14 → 0.17 (part 3) ---
[ ] rename @rebasepro/admin → @rebasepro/cms and admin-types → cms-types,
    and RebaseAdmin → RebaseCMS
[ ] move dataSources / storageSources out of the backend config into
    rebase.json and config/, then `rebase build` — an old bundle will not boot
[ ] grep collections for admin.titleProperty; it is refused at boot now
[ ] grep crons for ctx.client and for `userId` as an identity key
[ ] rename --legacy to --workspace wherever build/start is scripted
[ ] if you implement EmailService yourself, `send` must return a result
```

`rebase doctor --policies` è il comando da integrare nella CI: restituisce un exit code diverso da zero in presenza di una policy che contiene ancora la tautologia permissiva o di una policy sostituita da un push precedente. I controlli su `pg_policies` prima e dopo valgono comunque il minuto speso: mostrano le espressioni effettive, l'unico modo per individuare una policy fail-open scritta con una formulazione non riconosciuta dal detector. Né i pacchetti né il sistema di tipi te lo segnaleranno: la modifica risiede nel database, e `db push` è l'unica operazione che la applica.

## Tornare a una versione precedente

Prima di tornare a una versione più vecchia di quella che ha introdotto le policy compagne delle richieste di amministrazione (vedi il [changelog](/docs/changelog/)), rendile inerti. Un runtime più vecchio non elimina mai una policy compagna, quindi una regola modificata dopo il ritorno continuerebbe ad ammettere ogni amministratore a ogni riga. Esegui `REVOKE rebase_admin_request FROM rebase_user_admin;` una volta per ogni ruolo di richiesta di amministrazione, oppure elimina le policy `_ar_`. [Le letture degli amministratori usano gli indici del proprietario](/docs/deployment/existing-database/#admin-reads-use-the-owners-indexes) le spiega.
