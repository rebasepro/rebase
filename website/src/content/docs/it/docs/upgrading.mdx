# Aggiornare un'app esistente

Tredici passaggi, dai più recenti ai più vecchi. Inizia da quello subito superiore alla versione su cui ti trovi e procedi verso il basso — oppure, se provieni dalla versione 0.12, inizia dal fondo e risali verso l'alto.

| Ti trovi su | Leggi | Cosa comporta |
|---|---|---|
| **0.30** | [0.30 → 0.31](/docs/upgrading/0-30-to-0-31/) | Le tabelle in `backend/schema` (`defineTable`) sostituiscono `config/collections`, e non esiste più alcun pacchetto di configurazione: esegui `rebase migrate collections-to-tables`, che sposta il progetto e verifica che l'SQL generato sia invariato. Il pannello di amministrazione visualizza le tabelle fornite dal server, personalizzate a partire da `frontend/src/cms`; l'SDK utilizza `data.table(slug)` e `tables: tablesDictionary`; i bundle sono in formato 3, quindi ricompila prima di effettuare il deploy; MongoDB è dismesso. |
| **0.29** | [0.29 → 0.30](/docs/upgrading/0-29-to-0-30/) | Un backend avviato con `initializeRebaseBackend` conserva il refresh token in un cookie a meno che non imposti `cookieAuth: false`, quindi un chiamante che lo legge dal corpo della richiesta senza `x-rebase-auth-flow: json` riceve `""`. |
| **0.27 – 0.28** | [0.27 → 0.29](/docs/upgrading/0-27-to-0-29/) | Tutto ciò che l'admin passa al tuo codice è la riga del server affiancata dal relativo ID: `context.data` e `browserCallbacks` del browser restituiscono stringhe ISO e foreign key dove prima fornivano oggetti `Date` e di relazione, cosa che nessun compilatore rileva; gli hook di dati `Entity` diventano interni; e callback, pannelli, il pannello laterale e la selezione accettano `row` e `id` al posto di `entity` ed `entityId`. La versione 0.28 non dichiara alcuna breaking change, quindi si tratta di un unico passaggio da 0.27. |
| **0.26** | [0.26 → 0.27](/docs/upgrading/0-26-to-0-27/) | Una pianificazione cron che vincola entrambi i campi del giorno viene eseguita su uno qualsiasi dei due, quindi viene eseguita più spesso, e una pianificazione con un numero non valido viene rifiutata, interrompendo l'esecuzione di quel job. Una chiave la cui strategia `isId` non può essere rispettata dal suo tipo blocca l'avvio. Su Rebase Cloud, un deploy o una preview fallisce quando un file di funzione o cron non viene caricato. |
| **0.25** | [0.25 → 0.26](/docs/upgrading/0-25-to-0-26/) | Una scrittura che fa riferimento a una relazione `via` multi-hop, un nome di ruolo che non corrisponde a un singolo ruolo, un token di pagina nel local storage precedente all'aggiornamento e un upstream di funzioni non funzionante vengono rifiutati. L'accesso tramite OAuth finalizza un account non verificato invece di rispondere con `local-account-unverified`, il server MCP non invia più `REBASE_TOKEN` all'applicazione e i tipi generati rimuovono la chiave di una relazione belongsTo con `excludeFromApi`. Su Rebase Cloud, `rebase cloud webhooks` e `--scale-to-zero true` sono dismessi, e potrebbe essere necessario ricreare i token più vecchi. |
| **0.24** | [0.24 → 0.25](/docs/upgrading/0-24-to-0-25/) | `?count=` in un elenco REST diventa il parametro di attivazione per il conteggio dietro a `meta.total`, quindi un filtro su una colonna denominata `count` va inserito all'interno di `?where=`; `list_collections` dell'MCP remoto invia il suo elenco solo nel blocco di testo, senza `structuredContent`; e `@rebasepro/app` non esporta più la tabella di traduzione spagnola `es`. Una semplice richiesta `OPTIONS` a una route senza handler, nomi di tabella in conflitto all'avvio, un upsert sulla collection degli utenti, `page` con `offset`, una stringa vuota su un campo obbligatorio e una password di amministratore che non rispetta i criteri di sicurezza vengono rifiutati. Le sessioni durano per impostazione predefinita 30 giorni di inattività, `client.cron` chiama `/api/admin/cron`, le letture offline a cui non è possibile rispondere interamente falliscono con `OFFLINE`, e sono state rimosse alcune esportazioni interne e proprietà non utilizzate. |
| **0.23** | [0.23 → 0.24](/docs/upgrading/0-23-to-0-24/) | L'SQL generato da `db push` e `db generate` viene spostato da `drizzle/` alla cartella non tracciata `.rebase/sql/`, il flag `--generate` di `rebase dev` è stato rimosso poiché `dev` rigenera sempre i tipi dell'SDK, e una modifica dello schema a runtime non esegue il commit di alcun SQL. I permessi diventano scope: le interfacce di amministrazione richiedono uno scope anziché il ruolo di admin, le chiavi API contengono scope invece di un elenco di permessi e di un flag `admin`, e `schema-admin` non è più un amministratore. Un percorso relativo in `--collections` viene letto a partire dalla posizione in cui viene eseguito il comando, un upsert su una riga cestinata e un aggiornamento che modifica una chiave vengono rifiutati, l'endpoint MCP remoto accetta gli argomenti dell'SDK, e i socket realtime aperti, i link di verifica email, `signUp` e i codici di recupero MFA modificano il modo in cui gestiscono una sessione. |
| **0.21 – 0.22** | [0.21 → 0.23](/docs/upgrading/0-21-to-0-23/) | Una chiave API su un percorso nidificato richiede il permesso di `read` sui nodi padre, variabili numeriche non leggibili e durate di sessione non valide impediscono l'avvio, un repository di autenticazione personalizzato richiede `unlinkUserIdentity`, e gli upgrade da guest richiedono il captcha di `register`. La versione 0.22 non dichiara alcuna breaking change, quindi si tratta di un unico passaggio da 0.21. |
| **0.18 – 0.20** | [0.18 → 0.21](/docs/upgrading/0-18-to-0-21/) | `context.client.data` smette di compilare all'interno di una callback di collection — esegui le query tramite `context.data` — e `selectedEntities` cede il posto a una selezione in grado di rappresentare righe non caricate da nessuno. Le versioni 0.19 e 0.20 non dichiarano alcuna breaking change, quindi si tratta di un unico passaggio da 0.18. |
| **0.17** | [0.17 → 0.18](/docs/upgrading/0-17-to-0-18/) | Undici breaking change, per la maggior parte errori di compilazione anziché modifiche silenziose del comportamento. `rebase.data` scompare a runtime, i range delle peer dependency si restringono ai caratteri di accento circonflesso (caret) e la versione minima di Node passa a 22.22.0. |
| **0.14 – 0.16** | [0.14 → 0.17](/docs/upgrading/0-14-to-0-17/) | I pacchetti admin vengono rinominati, le risorse vengono dichiarate anziché configurate e un bundle compilato in precedenza non si avvierà su un runtime attuale. Le versioni 0.15 e 0.16 non introducono modifiche incompatibili, quindi si tratta di un unico passaggio da 0.14. |
| **0.13** | [0.13 → 0.14](/docs/upgrading/0-13-to-0-14/) | Ogni chiave trasmessa in rete (wire key) è in camelCase e l'accesso anonimo diventa opt-in. |
| **0.12** | [0.12 → 0.13](/docs/upgrading/0-12-to-0-13/) | Il passaggio più importante, e l'unico che modifica **chi può leggere i tuoi dati**. Rimuove lo schema `auth`, rinomina i pacchetti, modifica il significato di `id`, abbandona CJS, migra il pannello di amministrazione a react-router 8 e corregge tre modalità tramite cui l'accesso poteva essere concesso involontariamente. |

Le sezioni di ciascuna pagina sono disposte nell'ordine in cui devono essere applicate, e ciascuna indica il sintomo che altrimenti ti ritroveresti a dover diagnosticare partendo dalla parte sbagliata.

Inoltre, indipendentemente dal passaggio effettuato:

- [La checklist di aggiornamento](#checklist-di-aggiornamento) qui sotto — i controlli con grep e i comandi che vale la pena eseguire successivamente, raccolti in un unico blocco.

## Checklist di aggiornamento

```
[ ] grep for authenticated() and (auth|rebase).uid() IS NOT NULL in config/collections/
[ ] decide the intent of each rule; rewrite the ones that meant "public"
[ ] replace not(authenticated()) with serverContext()
[ ] if realtime.requireAuth was true with an AuthAdapter, treat the socket as
    having been open — verify RLS on every subscribable collection (section 2)
[ ] SELECT ... FROM pg_policies — record the qual of every policy BEFORE
[ ] update package names and imports
[ ] grep for rebase.data — it is now rebase.dataAsAdmin (section 8)
[ ] grep for the other ten removed deprecated exports (section 8)
[ ] drop react-router-dom; import RouterProvider from "react-router/dom"
[ ] check node >= 22.22.0 and react >= 19.2.7 (react-router 8 requires both)
[ ] move defaultSecurityRules into config/collections/index.ts
[ ] grep for .userId
[ ] grep for row.id on tables not keyed on id
[ ] run db push
[ ] run rebase doctor --policies — expect no Insecure or Orphaned entries
[ ] SELECT ... FROM pg_policies again — confirm every intended change landed
[ ] exercise the app signed OUT, in a private window — watch the websocket too

--- 0.13 → 0.14 (part 2) ---
[ ] re-run rebase generate-sdk, then build — the compiler finds row.author_id
[ ] grep for snake_case where/orderBy keys; a stale one is a 400, not a warning
[ ] grep for raw fetch consumers reading row.<something>_id — these read
    undefined and raise nothing
[ ] if the project was introspected, re-run rebase schema introspect
[ ] decide anonymous sign-in: set auth.allowAnonymous: true, or confirm you
    never used it (grep for signInAnonymously)
[ ] drop @rebasepro/client-postgres from package.json

--- 0.14 → 0.17 (part 3) ---
[ ] rename @rebasepro/admin → @rebasepro/cms and admin-types → cms-types,
    and RebaseAdmin → RebaseCMS
[ ] move dataSources / storageSources out of the backend config into
    rebase.json and config/, then `rebase build` — an old bundle will not boot
[ ] grep collections for admin.titleProperty; it is refused at boot now
[ ] grep crons for ctx.client and for `userId` as an identity key
[ ] rename --legacy to --workspace wherever build/start is scripted
[ ] if you implement EmailService yourself, `send` must return a result

--- 0.30 → 0.31 ---
[ ] bump every @rebasepro package to 0.31 first, then pnpm install
[ ] rebase migrate collections-to-tables on a clean tree; read the manual steps
[ ] move config/index.ts `callbacks` to backend/hooks.ts by hand, if you had them
[ ] rebase generate-sdk; rebase db push --dry-run plans no change
[ ] run the git rm line the codemod printed (your own config/ modules may stay)
[ ] send a to-one relation as its key, not { id } — that is a 400 now
[ ] call /api/docs signed in, or set REBASE_ENABLE_SWAGGER=true to publish it
[ ] rename the MCP tools in prompts and allow-lists (list_tables, query_table, …)
[ ] rebuild the bundle and deploy — a format-2 bundle is refused
```

`rebase doctor --policies` è il comando da integrare nella CI: restituisce un exit code diverso da zero in presenza di una policy che presenta ancora la tautologia permissiva o di una policy sostituita da un push precedente. Vale comunque la pena dedicare un minuto alla lettura di `pg_policies` prima e dopo: mostra le espressioni stesse, l'unico modo per individuare una policy fail-open scritta con una formulazione che il rilevatore non intercetta. Né i pacchetti né il sistema di tipi te lo segnaleranno: la modifica risiede nel database e `db push` è l'unico modo per applicarla.

## Rollback di una release

Prima di eseguire il rollback a una versione precedente a quella che ha introdotto i companion delle richieste admin (vedi il [changelog](/docs/changelog/)), rendili inattivi. Un runtime precedente non rimuove mai un companion, quindi una regola modificata dopo il rollback continuerebbe a concedere a qualsiasi admin l'accesso a ogni riga. Esegui `REVOKE rebase_admin_request FROM rebase_user_admin;` una volta per ciascun ruolo di richiesta admin, oppure elimina le policy `_ar_`. [Le letture admin utilizzano gli indici del proprietario](/docs/deployment/existing-database/#admin-reads-use-the-owners-indexes) ne descrive il funzionamento.
