# Aggiornare un'app esistente

Tredici passaggi, dal più recente al meno recente. Inizia da quello immediatamente successivo alla versione in uso e procedi verso il basso — oppure, se provieni dalla versione 0.12, parti dal fondo e procedi verso l'alto.

| Versione in uso | Leggi | Cosa comporta |
|---|---|---|
| **0.31** | [il changelog di 0.32.0](/docs/changelog/) | La versione 0.32 non dichiara alcun breaking change: aggiorna tutti i pacchetti `@rebasepro`. Due aspetti rilevanti per gli script: un comando CLI distruttivo (`api-keys revoke`, `db branch delete`, `cloud env unset`, `cloud compute set`, …) richiede conferma prima di procedere e, in assenza di un terminale o con `--json`, rifiuta l'esecuzione con `confirmation_required` a meno che non si passi `--yes`; inoltre `rebase_cloud_deploy`, `rebase_cloud_env_set`, `rebase_cloud_rollback` e `rebase_cloud_provision` del server MCP locale agiscono solo con `confirm: true`. `REALTIME_CDC=auto` ora legge il write-ahead log dove il database lo consente; imposta `REALTIME_CDC=trigger` per mantenere l'acquisizione tramite trigger. |
| **0.30** | [0.30 → 0.31](/docs/upgrading/0-30-to-0-31/) | Le tabelle in `backend/schema` (`defineTable`) sostituiscono `config/collections` e non c'è più un pacchetto config: esegui `rebase migrate collections-to-tables`, che sposta il progetto e dimostra che l'SQL generato rimane invariato. Il pannello di amministrazione visualizza le tabelle servite dal server, personalizzate da `frontend/src/cms`; l'SDK usa `data.table(slug)` e `tables: tablesDictionary`; i bundle sono in formato 3, quindi ricompila prima di effettuare il deploy; il supporto a MongoDB è stato rimosso. |
| **0.29** | [0.29 → 0.30](/docs/upgrading/0-29-to-0-30/) | Un backend avviato con `initializeRebaseBackend` conserva il refresh token in un cookie a meno che non sia impostato `cookieAuth: false`, quindi un chiamante che lo legge dal body senza l'header `x-rebase-auth-flow: json` otterrà `""`. |
| **0.27 – 0.28** | [0.27 → 0.29](/docs/upgrading/0-27-to-0-29/) | Tutto ciò che il pannello admin passa al tuo codice è la riga del server con il relativo id a fianco: nel browser, `context.data` e `browserCallbacks` passano stringhe ISO e foreign key dove prima passavano oggetti `Date` e relazioni (cosa che nessun compilatore rileva); gli hook dati di `Entity` diventano interni; inoltre callback, pannelli, il pannello laterale e la selezione accettano `row` e `id` al posto di `entity` ed `entityId`. La versione 0.28 non dichiara breaking change, quindi questo è un unico passaggio da 0.27. |
| **0.26** | [0.26 → 0.27](/docs/upgrading/0-26-to-0-27/) | Una pianificazione cron che vincola entrambi i campi del giorno viene eseguita se uno qualsiasi dei due corrisponde, quindi viene eseguita più spesso, mentre una pianificazione con un numero non valido viene rifiutata, interrompendo l'esecuzione di quel job. Una chiave la cui strategia `isId` non può essere rispettata dal suo tipo blocca l'avvio. Su Rebase Cloud, un deploy o una preview fallisce se un file di funzione o di cron non si carica. |
| **0.25** | [0.25 → 0.26](/docs/upgrading/0-25-to-0-26/) | Una scrittura che specifica una relazione `via` multi-hop, un nome di ruolo che non corrisponde a un singolo ruolo, un page token del local storage precedente all'aggiornamento e un upstream per le funzioni che non può funzionare vengono rifiutati. L'accesso tramite OAuth consolida un account non verificato anziché restituire `local-account-unverified`, il server MCP non invia più `REBASE_TOKEN` all'app e i tipi generati rimuovono la chiave di una relazione belongsTo con `excludeFromApi`. Su Rebase Cloud, `rebase cloud webhooks` e `--scale-to-zero true` sono stati ritirati e i token più vecchi potrebbero dover essere ricreati. |
| **0.24** | [0.24 → 0.25](/docs/upgrading/0-24-to-0-25/) | `?count=` su un elenco REST diventa l'interruttore per il conteggio dietro `meta.total`, quindi un filtro su una colonna chiamata `count` va inserito all'interno di `?where=`; l'operazione `list_collections` dell'MCP remoto invia il proprio elenco solo nel blocco di testo, senza `structuredContent`; `@rebasepro/app` non esporta più la tabella delle traduzioni in spagnolo `es`. Una richiesta `OPTIONS` semplice verso una rotta senza handler, nomi di tabelle in conflitto all'avvio, un upsert sulla collection degli utenti, `page` insieme a `offset`, una stringa vuota su un campo obbligatorio e una password di amministratore non conforme ai criteri di sicurezza vengono rifiutati. Le sessioni durano di default 30 giorni di inattività, `client.cron` chiama `/api/admin/cron`, le letture offline che non possono essere soddisfatte per intero falliscono con `OFFLINE`, e sono stati rimossi alcuni export interni e proprietà non utilizzate. |
| **0.23** | [0.23 → 0.24](/docs/upgrading/0-23-to-0-24/) | L'output SQL generato da `db push` e `db generate` viene spostato da `drizzle/` alla cartella non versionata `.rebase/sql/`, il flag `--generate` di `rebase dev` è stato rimosso perché `dev` rigenera sempre i tipi dell'SDK, e una modifica dello schema in tempo reale non esegue il commit di alcun SQL. I permessi diventano ambiti (scope): le interfacce di amministrazione richiedono uno scope anziché il ruolo admin, le chiavi API contengono scope invece di un elenco di permessi e di un flag `admin`, e `schema-admin` non è più un amministratore. Un percorso relativo in `--collections` viene risolto rispetto alla posizione in cui viene eseguito il comando, un upsert su una riga nel cestino e un aggiornamento che modifica una chiave vengono rifiutati, l'endpoint MCP remoto accetta gli argomenti dell'SDK, e i socket realtime aperti, i link di verifica email, `signUp` e i codici di recupero MFA modificano la gestione della sessione. |
| **0.21 – 0.22** | [0.21 → 0.23](/docs/upgrading/0-21-to-0-23/) | Una chiave API su un percorso nidificato richiede i permessi di `read` sui suoi predecessori, le variabili numeriche illeggibili e le durate di sessione non valide impediscono l'avvio, un repository di autenticazione personalizzato richiede `unlinkUserIdentity`, e gli upgrade dagli account guest richiedono il captcha `register`. La versione 0.22 non dichiara breaking change, quindi questo è un unico passaggio da 0.21. |
| **0.18 – 0.20** | [0.18 → 0.21](/docs/upgrading/0-18-to-0-21/) | `context.client.data` non compila più all'interno di un callback di collection — effettua le query tramite `context.data` — e `selectedEntities` lascia il posto a una selezione che può rappresentare righe che nessuno ha caricato. Le versioni 0.19 e 0.20 non dichiarano breaking change, quindi questo è un unico passaggio da 0.18. |
| **0.17** | [0.17 → 0.18](/docs/upgrading/0-17-to-0-18/) | Undici breaking change, per la maggior parte errori di compilazione anziché modifiche silenziose del comportamento. `rebase.data` scompare a runtime, gli intervalli di peer dependency si restringono con il cursore circonflesso (`^`), e la versione minima di Node passa a 22.22.0. |
| **0.14 – 0.16** | [0.14 → 0.17](/docs/upgrading/0-14-to-0-17/) | I pacchetti admin vengono rinominati, le risorse vengono dichiarate anziché configurate, e un bundle creato in precedenza non si avvierà su un runtime corrente. Le versioni 0.15 e 0.16 non introducono modifiche incompatibili, quindi questo è un unico passaggio da 0.14. |
| **0.13** | [0.13 → 0.14](/docs/upgrading/0-13-to-0-14/) | Ogni chiave trasferita in rete usa la convenzione camelCase e l'accesso anonimo diventa facoltativo (opt-in). |
| **0.12** | [0.12 → 0.13](/docs/upgrading/0-12-to-0-13/) | Il passaggio più grande e l'unico che modifica **chi può leggere i tuoi dati**. Rimuove lo schema `auth`, rinomina i pacchetti, ridefinisce il significato di `id`, elimina CJS, migra il pannello di amministrazione a react-router 8 e corregge tre modalità in cui potevano essere concessi accessi non richiesti. |

Le sezioni di ciascuna pagina sono ordinate in base alla sequenza in cui vanno applicate e ognuna indica il sintomo che altrimenti ti troveresti a diagnosticare partendo dalla parte sbagliata.

Quindi, indipendentemente dal passaggio effettuato:

- [La checklist di aggiornamento](#upgrade-checklist) riportata di seguito — i comandi grep e i comandi utili da eseguire subito dopo, raccolti in un unico blocco.

## Upgrade checklist

```
[ ] grep for authenticated() and (auth|rebase).uid() IS NOT NULL in config/collections/
[ ] decide the intent of each rule; rewrite the ones that meant "public"
[ ] replace not(authenticated()) with serverContext()
[ ] if realtime.requireAuth was true with an AuthAdapter, treat the socket as
    having been open — verify RLS on every subscribable collection (section 2)
[ ] SELECT ... FROM pg_policies — record the qual of every policy BEFORE
[ ] update package names and imports
[ ] grep for rebase.data — it is now rebase.dataAsAdmin (section 8)
[ ] grep for the other ten removed deprecated exports (section 8)
[ ] drop react-router-dom; import RouterProvider from "react-router/dom"
[ ] check node >= 22.22.0 and react >= 19.2.7 (react-router 8 requires both)
[ ] move defaultSecurityRules into config/collections/index.ts
[ ] grep for .userId
[ ] grep for row.id on tables not keyed on id
[ ] run db push
[ ] run rebase doctor --policies — expect no Insecure or Orphaned entries
[ ] SELECT ... FROM pg_policies again — confirm every intended change landed
[ ] exercise the app signed OUT, in a private window — watch the websocket too

--- 0.13 → 0.14 (part 2) ---
[ ] re-run rebase generate-sdk, then build — the compiler finds row.author_id
[ ] grep for snake_case where/orderBy keys; a stale one is a 400, not a warning
[ ] grep for raw fetch consumers reading row.<something>_id — these read
    undefined and raise nothing
[ ] if the project was introspected, re-run rebase schema introspect
[ ] decide anonymous sign-in: set auth.allowAnonymous: true, or confirm you
    never used it (grep for signInAnonymously)
[ ] drop @rebasepro/client-postgres from package.json

--- 0.14 → 0.17 (part 3) ---
[ ] rename @rebasepro/admin → @rebasepro/cms and admin-types → cms-types,
    and RebaseAdmin → RebaseCMS
[ ] move dataSources / storageSources out of the backend config into
    rebase.json and config/, then `rebase build` — an old bundle will not boot
[ ] grep collections for admin.titleProperty; it is refused at boot now
[ ] grep crons for ctx.client and for `userId` as an identity key
[ ] rename --legacy to --workspace wherever build/start is scripted
[ ] if you implement EmailService yourself, `send` must return a result

--- 0.30 → 0.31 ---
[ ] bump every @rebasepro package to 0.31 first, then pnpm install
[ ] rebase migrate collections-to-tables on a clean tree; read the manual steps
[ ] move config/index.ts `callbacks` to backend/hooks.ts by hand, if you had them
[ ] rebase generate-sdk; rebase db push --dry-run plans no change
[ ] run the git rm line the codemod printed (your own config/ modules may stay)
[ ] send a to-one relation as its key, not { id } — that is a 400 now
[ ] call /api/docs signed in, or set REBASE_ENABLE_SWAGGER=true to publish it
[ ] rename the MCP tools in prompts and allow-lists (list_tables, query_table, …)
[ ] rebuild the bundle and deploy — a format-2 bundle is refused

--- 0.31 → 0.32 ---
[ ] bump every @rebasepro package to 0.32, then pnpm install
[ ] add --yes to scripted destructive CLI commands (they refuse with confirmation_required)
[ ] rebase verify — fix any rls-policy-recursion it reports
[ ] rebase build — it warns when config/index.ts still exports storageAuthorize
```

`rebase doctor --policies` è il comando da integrare nella CI: restituisce un exit code diverso da zero in presenza di una policy che contiene ancora la tautologia permissiva o di una resa obsoleta da un push precedente. Le letture di `pg_policies` prima e dopo meritano comunque quel minuto di attenzione — mostrano le espressioni effettive, l'unico modo per individuare una policy permissiva (fail-open) scritta con una sintassi non rilevata dallo strumento. Né i pacchetti né il sistema di tipi lo segnaleranno: la modifica risiede nel database e `db push` è l'unica operazione che la applica.

## Ripristino di una versione precedente (Rollback)

Prima di eseguire il rollback a una versione precedente a quella che ha introdotto i companion delle richieste admin (vedi il [changelog](/docs/changelog/)), rendili inattivi. Un runtime precedente non rimuove mai un companion, quindi una regola modificata dopo il rollback continuerebbe a consentire a ogni admin l'accesso a ogni riga. Esegui `REVOKE rebase_admin_request FROM rebase_user_admin;` una volta per ciascun ruolo admin request, oppure elimina le policy `_ar_`. [Le letture admin usano gli indici del proprietario](/docs/deployment/existing-database/#admin-reads-use-the-owners-indexes) ne illustra i dettagli.
